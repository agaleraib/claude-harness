## Why this spec exists (the mantra — do not violate)

`/run-loop` replaces the human merge gate with a **mechanical** one (green tests + Verify + zero surviving CRITICAL/HIGH review findings). **That mechanical gate is the entire reason it is safe to walk away.** If the gate does not actually execute the repo's checks, the loop is not "automated `/close-wave`" — it is "merge whatever the agent wrote, unread." A gate that fails *open* is worse than no gate, because it wears the costume of safety.

**The motivating defect (discovered via `/grill-me`, 2026-06-16, grounded below at file:line):** in the live path, `ShellGateRunner` runs **zero** commands and returns green, so the loop merges blind — and because the verify-gate "reproduces" a review finding by checking whether the gate goes **red** (`run-loop-prod-deps.ts:411`), and the gate is never red, **every Opus review finding is silently downgraded to advisory.** Both safety layers — the exit gate *and* the verify-gate — are no-ops on real repos. Wave 23's T8 "passed" only because nothing was checked.

This wave is the **portability + trust** wave: the work that turns `/run-loop` from "proven once on a single hand-fed item" into "a standing workflow I can point at my other repos and trust." The fix is deliberately narrow — repo-resolved gate commands + a fail-safe default — and explicitly **not** the container lane or the classifier-coherence work (both deferred; see Scope discipline).

|---|--------|------------------------|
| 1 | **Exit gate fails *open*.** When a check command is absent, the gate returns green and the item merges with no checks run. | `ShellGateRunner.runCmd` returns `true` for `cmd === undefined \|\| cmd.length === 0` — "no check declared ⇒ pass (vacuously green)" (`run-loop-prod-deps.ts:222-224`). The doc comment confirms it: "absent ⇒ the gate is vacuously green" (`:209-214`). |
| 2 | **No production path populates the per-item `gate` descriptor.** So in `issues`/`waves` mode every check is absent ⇒ defect 1 fires on every item. | `cmdFor` reads `item['gate']` (`:237-245`); only the clean-room local-item path sets it. | 3 | **Verify-gate neutered as a consequence.** Review findings never block a merge because they can never reproduce. | The verify-gate reproduce predicate is `async () => !(await runExitGate(item, gateRunner)).green` (`run-loop-prod-deps.ts:411`). With the gate always green, `reproduce` is always `false` ⇒ all findings advisory ⇒ Opus review is commentary, not a gate (`:382-390` shows the exit gate is the merge arbiter — and it is vacuous). |
| 4 | **No repo-level gate source exists.** Nothing reads a repo's test/typecheck/verify commands; there is no portability on-ramp for a new repo. | The engine reads only env (`buildBackendConfigFromEnv`, `:168`); `.harness-profile` parsing for loop knobs is an open TODO deferred to SKILL.md wiring (`:173`). No `gate:` block is read or threaded. |
| 5 | **The per-item gate IS the merge gate in serial — the only residual risk is HEAD diverging between branch-cut and merge.** The drive is strictly serial (`engine.ts:52`, one `for(;;)` loop, one item fully done before the next). The temp branch is cut off current HEAD (`createTempBranch` = `git checkout -b`, base = HEAD, `run-loop-prod-deps.ts:336-338`); the per-item gate runs on that tree (`:383`); the merge is `git merge <branch>` (`dispatch/implement.ts:256`). Because HEAD does not move between branch-cut and merge in serial, the merge is a **fast-forward** and the merged tree **equals** the gated tree — so re-running the gate on the merge candidate is **redundant** (it would re-gate an identical tree). The one residual risk: if an **external** commit moves HEAD after the branch was cut, `git merge` would produce a **3-way** merge commit whose tree the gate never saw — an un-gated tree on HEAD. The retired `merge-contract.ts` step-5 `FinalGate` (`:55`) is the *concurrency* design intent and is **NOT wired** into the serial live path. | Live: `ProductionProtocol.runInner` gates the temp branch (`:383`); the merge is `ops.mergeToHead` = plain `git merge <branch>` (`dispatch/implement.ts:255-262`), which would silently create a 3-way (un-gated) merge commit if HEAD diverged. **Wave 24 closes this with a fast-forward-only guard (Task 4): `mergeToHead` becomes `git merge --ff-only <branch>`. On a fast-forward (the serial happy path) HEAD moves to the gated tip — the merged tree is exactly the gated tree. On a non-fast-forward (HEAD diverged) the merge returns `{ok:false}` instead of synthesizing an un-gated 3-way tree, and the EXISTING `!merge.ok` path (`:430-438`) hands off + returns `escalated` — but it must NOT call `git merge --abort`: `--ff-only` exits without ever starting a merge, so there is no `MERGE_HEAD` to abort and an unconditional `git merge --abort` would THROW. The non-fast-forward path therefore goes straight to preserve-branch + `handoff(...)` + `escalated` (no abort), and `abortMerge` is defensively guarded to no-op when no `MERGE_HEAD` exists. No merge-candidate re-gate, no `mergeNoCommit`/`commitMerge`/`restoreClean`, no rollback window — the serial fast-forward + post-gate worktree hygiene (Task 4) make those unnecessary.** Genuine merge-candidate re-gating (a different 3-way tree) belongs to the future concurrency path with the retired contract — see Out of scope + Open Question 5. |

## Decisions (locked — operator-confirmed via `/grill-me` 2026-06-16)

| # | Axis | Decision |
|---|------|----------|
| 1 | **North star** | Make `/run-loop` trustworthy enough to adopt as a **standing workflow on the operator's other repos** — NOT "drain the quickbase-replacement test issues." quickbase-replacement is the live-validation fixture, not the goal. The blocker to that north star is the fail-open gate; this wave fixes exactly that. |
| 2 | **Gate is repo-resolved** | The **target repo declares its checks** in its `.harness-profile` `gate:` block (`tests:`/`typecheck:`/`verify:`). The `/run-loop` SKILL.md reads that block and exports `RUN_LOOP_GATE_TESTS` / `RUN_LOOP_GATE_TYPECHECK` / `RUN_LOOP_GATE_VERIFY` — **same seam as every other loop knob** (`.harness-profile` → SKILL.md → env → engine). The engine consumes the env into a `RepoGateConfig` threaded through the `gate: (item, cwd) => GateRunner` factory (`run-loop-prod-deps.ts:266`) into `ShellGateRunner`. Engine stays **zero-dep** (no YAML parser added). |
| 3 | **Fail-safe — the three-way rule** | (a) **No gate configured at all** for the repo (no `gate:` env/profile **and** no per-item descriptor) ⇒ **fail-safe**: the run is **refused at preflight** (primary) and any item that nonetheless reaches the gate reads **RED** (backstop) — never vacuously green. (b) **Gate configured, individual sub-check empty** (e.g. a repo with tests but no separate typecheck step) ⇒ that sub-check **passes** — legitimate partial gates still work. (c) **Gate configured but nothing runnable overall** ⇒ **RED → escalate**. Net: *"gate block absent → refuse the run; sub-check empty → that sub-check passes; block present but empty overall → red/escalate."* This is the single non-negotiable safety flip — fail-open → fail-safe. |
| 4 | **Refuse-before-work is primary, red-escalate is backstop** | The preflight refusal (Task 3) is the primary guard: do not spend codex tokens implementing N items only to discover none can be safely merged. It mirrors the existing Docker-absent / Claude-hook-absent refusals (`run-loop-driver.ts`). The per-item RED (Task 2) is defense-in-depth for any item that slips past preflight with no resolvable gate. |
| 5 | **Verify-gate heals for free** | Once the gate executes real commands, the verify-gate reproduce path (`:411`) works again automatically — a finding that reddens the gate reproduces and drives a fix round / escalation; a false positive that does not reproduce stays advisory. **No code change beyond Tasks 1–2** — but a regression test (Task 5) proves the heal, since this restoration is a primary point of the wave. |
| 6 | **Lane / backend unchanged** | implement = **codex** (worktree, native `-s workspace-write` sandbox — no denylist hook required, `run-loop-driver.ts:119-120`); review = **`anthropic-api:opus-4.8`** (low-volume, trust-critical, key available, egress permitted for the operator's own repos). The cost split is principled: codex for high-volume implement (un-metered sub auth), Opus for the low-volume gate that lets you walk away. |
| 7 | **Gate command encoding (the trust boundary — locked, was Open Question 1)** | Each check is encoded in **exactly one** of two explicit env forms, with **no auto-detection of shell metacharacters** (auto-detection is brittle and was the source of the false-green/red and unexpected-shell-execution risk Codex flagged): **(a) argv form** — `RUN_LOOP_GATE_TESTS` holds a **JSON array of strings** (e.g. `["npm","test","--silent"]`); parsed with `JSON.parse`, validated to be a non-empty `string[]`, spawned **directly with no shell** via the existing `SpawnFn` (`command = argv[0]`, rest = args). **(b) shell form** — a sibling `RUN_LOOP_GATE_TESTS_SHELL` (scalar string, e.g. `npm test && tsc -p .`) is spawned as `sh ['-c', <value>]` via the same `SpawnFn`, for real-world `&&`/pipes/quoted args. **Precedence per check:** item `gate` descriptor → `*_SHELL` scalar → JSON-argv env → absent. A non-empty JSON-argv and a non-empty `*_SHELL` for the SAME check is a **config error** (red/refuse, named in the note) — never silently pick one. A present-but-empty value (`""` / `[]`) ⇒ key omitted (the sub-check passes per Decision 3b only if the gate is otherwise configured). Quoting rules + the two forms are documented in SKILL.md (Task 6). The SKILL.md profile read decides which form to export from the `.harness-profile` `gate:` block: a **YAML list** value → JSON-argv env; a **scalar string** → `*_SHELL` env. No YAML round-trips through one env var; no shell sniffing. Host execution is consistent with the gate's existing host-side `SpawnFn` and the trusted single-operator worktree posture. |

## Out of scope (deliberately deferred — stated so reviewers don't expand the wave)

- **Prose-compilation of the exit-gate condition into commands** (the `/goal`-flavored ergonomic: write success in prose, compile to runnable checks). Explicitly a **later wave**. Rationale captured: `/goal`'s evaluator *judges the agent's self-reported transcript and runs nothing* (per code.claude.com/docs/en/goal — "doesn't run commands or read files independently"), which re-introduces the exact agent-trust the mechanical gate removes. We borrow only its *authoring ergonomic* later, and only as a **source of commands the loop then executes deterministically** — never as a transcript-judging gate. This wave ships explicit config first.
- **The container / sandcastle lane.** `UnsupportedContainerRunner` stays; sandcastle items remain preflight-refused. Isolation gold-plating the single-operator north star does not need yet. (Candidate next wave: a real `DockerContainerRunner` with `~/.codex` mounted.)
- **Classifier coherence (the AFK/HITL-vs-autonomy overload + pre-approval gap).** Dormant on the default read-only drive (`classifier-reconcile.ts` is skipped unless `RUN_LOOP_TRANSITION_ISSUES`), and only bites when running **secret-bearing items unattended** — which the operator confirmed the first-drain backlog is **not** (non-secret refactors/logic). Required *before* transitions are flipped on or any secret-bearing item is queued; not before.
- **Auto-detection** of a repo's checks (package.json scripts / pytest / cargo / go). A nice future on-ramp, but only ever **on top of** fail-safe (auto-detect that finds nothing must still refuse, not pass). Deferred to keep this wave to explicit-config + fail-safe.
- **Merge-candidate RE-gating and gate ISOLATION — the future concurrency path.** In a concurrent drive, multiple items' branches integrate against a moving HEAD, so a merge can be a genuine 3-way (a *different* tree than any single item's gated tree) — *that* tree must be re-gated, and each gate run wants its own isolated worktree/checkout so concurrent gates don't collide. Both align with the RETIRED-until-concurrency `merge/merge-contract.ts` (its step-5 `FinalGate`, `:55`). The **serial** Wave 24 drive needs neither: it relies on the serial **fast-forward** (`--ff-only`, merged tree == gated tree) plus **post-gate worktree hygiene** (`discardWorktreeChanges`). If a later wave adds concurrency, that is when merge-candidate re-gating + per-gate isolation get wired (with the merge-contract) — not here.

### Phase 3: Fast-forward-only merge guard + post-gate worktree hygiene — F-033

#### Task 4: FF-only merge guard + post-gate worktree hygiene — F-033
- Runner: worktree   # classifier: ready-for-agent (AFK); gates: none — pure TS + node-test code, no host secrets. (sandcastle lane is preflight-refused — see Task 1.)
- Depends on: Task 2

**Closes Defect 5 — and keeps the serial integration tree clean for the next item.** Tasks 1–2 make the **per-item** gate (`run-loop-prod-deps.ts:383`, run on the item's temp branch) real. Because the drive is strictly serial (`engine.ts:52`) and the temp branch is cut off current HEAD (`createTempBranch` = `git checkout -b`, base = HEAD, `:336-338`), the gated tree and the merged tree are **identical whenever the merge is a fast-forward** — so the per-item gate IS the merge gate, and **re-gating the merge candidate is redundant**. The only residual risk is HEAD **diverging** between branch-cut and merge (an external commit), which would turn `git merge` into a 3-way merge producing an un-gated tree on HEAD. This task closes that with `--ff-only` (refuse a non-fast-forward) and adds post-gate worktree hygiene so a gate's filesystem byproducts don't leak into the next serial item's commit.

**Mechanism A — fast-forward-only merge.** Change `mergeToHead` from `git merge <branch>` to **`git merge --ff-only <branch>`** (modify the existing additive method in place, `dispatch/implement.ts:255-262`; same signature, same `{ok, exitCode, stderr}` return). On a fast-forward (the serial happy path), HEAD advances to the gated tip — the merged tree is exactly the gated tree, no new merge commit. On a non-fast-forward (HEAD diverged — an external commit moved HEAD), `--ff-only` exits non-zero and returns `{ok:false}` **instead of synthesizing a 3-way merge** the gate never saw.

**The non-fast-forward escalation MUST NOT call `git merge --abort`.** `git merge --ff-only <branch>` on a non-fast-forward exits **without ever starting a merge** — there is no `MERGE_HEAD`, so there is nothing to abort, and an unconditional `git merge --abort` (the current `abortMerge` at `run-loop-prod-deps.ts:434`) would **throw** ("fatal: There is no merge to abort"). Restructure the existing `!merge.ok` path (`run-loop-prod-deps.ts:430-438`) so the non-fast-forward branch goes **straight to** preserve-the-branch (no `deleteBranch`) + `handoff(...)` + `return escalated`, **skipping `abortMerge` entirely**, with the note `non-fast-forward: HEAD moved since the gated tree was cut; refusing to merge an un-gated tree`. Because `--ff-only` can never produce a conflict-with-`MERGE_HEAD`, the previously-reachable true-conflict branch (a real 3-way `git merge` conflict that left a `MERGE_HEAD`) is **no longer reachable under `--ff-only`** — so `abortMerge`'s only remaining caller is the defensive guard below.

**Defensive guard on `abortMerge` (and any abort step in `discardWorktreeChanges`).** Make `abortMerge` **no-op when no merge is in progress**: guard it with a `git rev-parse -q --verify MERGE_HEAD` probe (only shell `git merge --abort` when that probe succeeds), **or** tolerate `git merge --abort`'s non-zero exit (don't throw on "no merge to abort"). Same guard applies to any merge-abort step inside `discardWorktreeChanges` (Mechanism B) — it must never throw because no merge is in progress. This makes the codebase robust to an `abortMerge` impl that throws on a missing `MERGE_HEAD`. (No `mergeNoCommit`/`commitMerge`/`restoreClean`, no gate-before-commit, no merge-candidate re-gate — the serial fast-forward makes them unnecessary.)

**Mechanism B — gate worktree hygiene wraps EVERY gate invocation (the gate may READ the tree but MUST NOT mutate committed state).** The exit gate runs real test/build commands in the **live** worktree, and `commitAll` (`git add -A && git commit`, `dispatch/implement.ts:150`) runs **before** it. With no cleanup, a gate's working-tree side effects — modifications to tracked files, or **non-ignored** untracked files the gate created — get swept into the **next** item's `git add -A` commit (the next item branches off the same HEAD). Critically, the gate runs in **more than one place**: (i) the **initial per-item exit gate** (`run-loop-prod-deps.ts:383`), AND (ii) the **verify-gate reproducer**, which re-runs the gate **per reviewed finding** (`reproduce: () => !(await runExitGate(...)).green`, `run-loop-prod-deps.ts:411`). Cleaning only after the initial gate (`:383`) leaves the reproducer re-runs un-cleaned — those re-runs can modify tracked files / create non-ignored untracked files **after** the initial cleanup, re-opening the leak.

Fix: the post-gate `discardWorktreeChanges(cwd)` (= `git reset --hard HEAD` + `git clean -fd`, **NO `-x`**) MUST wrap **every** `runExitGate` invocation in the live protocol — the initial per-item exit gate (`:383`) **AND** each verify-gate reproducer run (`:411`) — ideally via a `try/finally` around each gate execution, completing **before** any checkout/merge. **Invariant: NO gate execution (initial or reproducer) may leave working-tree side effects behind.** Implement via **one** new additive committer method `discardWorktreeChanges(cwd)`, called in a `finally` after each gate execution (GREEN, RED, or throw), restoring the just-committed temp-branch state before the checkout/merge. Principle: the gate reads the working tree; its filesystem byproducts are discarded after it returns its verdict, no matter which gate invocation produced them.

**Why `-x` is NOT used (corrects the Codex confirming-pass `git clean -fdx` recommendation):** `git add -A` does **not** stage ignored files, so ignored build caches (`coverage/`, `dist/`, `.next/`) **never** leak into a commit — they need no cleaning. Adding `-x` would additionally **delete precious ignored files** like `.env` / `node_modules`. So `-fd` (no `-x`) discards exactly the leak vectors (tracked-file mods + non-ignored untracked files) and **nothing else**.

- `run-loop-driver.ts` preflight — additive refusal reason + additive `PreflightOptions.gateConfig`, same `PreflightRefusal` shape.
- `RepoGateConfig` — new type, local to the loop module.

`types.ts` / `engine.ts` / `runLoop` are untouched. The `GateRunner` seam (`protocol/gate.ts`) and `runExitGate` do NOT change — thread the config via the `ShellGateRunner` constructor. **One watch-item (Task 4):** post-gate worktree hygiene needs to discard a gate's working-tree side effects after **every** gate execution (the initial per-item gate AND each verify-gate reproducer re-run), between serial items. The existing `mergeOps`/`committer` seam exposes `abortMerge` (`run-loop-prod-deps.ts:434`) and `head`, but **not** a worktree-discard method — so Task 4 adds **one** NEW additive concrete method, `discardWorktreeChanges` (= `git reset --hard HEAD` + `git clean -fd`, NO `-x`), on the (non-frozen) `ShellGitCommitter` + `ShellGitCommitterLike`, exactly like the prior additive committer methods. `-x` is deliberately omitted: `git add -A` never stages ignored files, so ignored caches can't leak into a commit, and `-x` would delete precious ignored files (`.env`/`node_modules`). `abortMerge` is defensively guarded (no-op when no `MERGE_HEAD`) and is **not** called on the non-fast-forward escalation path. If `--ff-only`, the `abortMerge` guard, or `discardWorktreeChanges` cannot be expressed through an additive/behavior-only change, or any task appears to need a `GateRunner`-interface or frozen Phase-1 interface change during build, **STOP and flag it** with the specific interface.

## Open questions

1. **Command tokenization for gate values — RESOLVED, promoted to Decision 7.** The trust-boundary question Codex flagged (round 1) is no longer open: there is **no shell-metacharacter sniffing**. 5. **`merge/merge-contract.ts` reliance (round-1 finding #1) + the merge-candidate question — resolved by the serial fast-forward, not by a re-gate.** The round-1 draft cited `merge-contract.ts:55` for a merge-candidate gate re-run; that contract is RETIRED-until-concurrency and not wired into the live serial drive. The key realization (grounded in code): in the **serial** drive the temp branch is cut off current HEAD (`:336-338`), the per-item gate runs on that tree (`:383`), and HEAD does not move between cut and merge — so the merge is a **fast-forward** and the merged tree **equals** the gated tree. Re-running the gate on the merge candidate would re-gate an identical tree (redundant). The per-item gate IS the merge gate. The only residual risk — an **external** commit moving HEAD between cut and merge, which would make `git merge` synthesize an un-gated 3-way tree — is closed by **`--ff-only`-or-escalate** (Task 4 Mechanism A): a non-fast-forward returns `{ok:false}` and routes through the existing `!merge.ok` handoff (broadened note: `non-fast-forward`), never merging an un-gated tree. That escalation path **does not call `git merge --abort`** — `--ff-only` starts no merge, so there is no `MERGE_HEAD` to abort and an unconditional abort would throw; the path goes straight to preserve-branch + handoff + escalated, and `abortMerge` is defensively guarded to no-op when no merge is in progress. There is no `mergeNoCommit`/`commitMerge`/`restoreClean`, no gate-before-commit, and no rollback window — HEAD only ever fast-forwards to an already-gated tip; and Task 4 Mechanism B (post-gate `discardWorktreeChanges`, `git reset --hard HEAD` + `git clean -fd`, NO `-x`) wraps **every** gate execution — the initial per-item gate AND each verify-gate reproducer re-run (`:411`) — keeping the serial integration tree clean for the next item (invariant: no gate execution leaves working-tree side effects behind). The retired contract stays retired — genuine merge-candidate re-gating (a *different* 3-way tree) and gate isolation are the future **concurrency** path; if that contract's retired-until-concurrency note is touched in a later concurrency wave, that is when candidate re-gating + isolation get wired (see Out of scope).
