# Memory System Redesign — User-global shared root + cowork-mode scaffold

## Overview

The current Claude Code memory system stores everything in a single per-cwd `MEMORY.md` index at `~/.claude/projects/<encoded-cwd>/memory/`. Three concrete failures have surfaced:

1. **The index is over-budget.** `~/.claude/projects/-Users-klorian-workspace-claude-harness/memory/MEMORY.md` is 29.1KB against a 24.4KB auto-load cap — the loader emits "Only part of it was loaded" warnings and silently truncates entries. 137 markdown files live under that one cwd; index lines exceed 200 chars routinely.
2. **Cross-project lookup is broken.** Feedback memories that apply everywhere (e.g. `feedback_harness_too_intrusive`, `feedback_wave_vs_micro_shape_rule`) get written wherever the session reproduced the bug. Looking them up from a different cwd requires `find ~/.claude/projects -name <file>` — there is no user-global home.
3. **No primary unit for non-repo work.** The gobot pivot spec (`gobot/docs/specs/2026-05-11-pivot-to-workspace-as-context.md`) introduces operator-curated folders ("workspaces") that are not git repos. They have no `CLAUDE.md` scaffold today and no place in the memory system.

This spec carves a **user-global shared root at `~/.claude/memory/`** for cross-cutting concerns (USER.md, FEEDBACK.md + `feedback/`, REFERENCES.md, PROJECTS.md, `archive/`), tightens MEMORY.md hygiene via convention + a `/memory-prune` skill (no blocking hooks), renames `~/gobot-workspaces/` → `~/cowork/` and the leaf noun "workspace" → "project" throughout the cascade, and ships a minimal `/new-cowork` skill that scaffolds a cowork project plus a `.claude/desktop-knowledge/` bundle so the same artifacts work in Claude Desktop and on claude.ai.

It is deliberately scoped to the **memory + scaffold layer**. The workspace-mode artifact layout (numbered phase folders, writer-authority table, scope envelope shape, artifact writer) is owned by the gobot pivot spec — this spec cross-references but does not duplicate.

## Design Principles

This spec ships markdown files and two slash commands. No visual UI. Three directives shape the skills' character:

- **Convention before automation.** Per `feedback_harness_too_intrusive`: every behavior shipped here is either a markdown file, a slash command that runs only when invoked, or an AGENTS.md paragraph. No blocking hooks. No mandatory query-before-respond. `/memory-prune` defaults to dry-run; `/session-start` only *warns* about over-budget files, never blocks. The user has rejected enforcement-style harness behavior once; do not re-introduce it.
- **Filesystem-portable data, surface-specific load.** Per the locked-decisions memory: the data layer (markdown under `~/.claude/memory/` + per-project files) is readable by anything with filesystem access — Claude Code, Claude Desktop with Filesystem MCP, web claude.ai with remote-MCP. The auto-load layer (per-cwd hook reading `MEMORY.md`) is Claude-Code-only and stays Claude-Code-only. The `.claude/desktop-knowledge/` bundle is the explicit bridge.
- **Provenance over deduplication.** Per `feedback_cross_project_memory_lookup`: per-cwd auto-memory keeps writing where the session reproduced an insight. Promotion to `~/.claude/memory/feedback/` is **move + frontmatter `originCwd:` stamp**, not copy. Loses zero audit trail. Multiple per-cwd dirs containing the same `feedback_*.md` filename is the bug; promotion is the fix.

## Constraints

- **No blocking hooks.** Per `feedback_harness_too_intrusive`: `/memory-prune` warnings from `/session-start` / `/session-end` are non-blocking. `/new-cowork` does not register a hook. The shared-root directory has no watcher.
- **No new MCP servers.** All access to `~/.claude/memory/` is filesystem-direct. No `memory-mcp` server. Operator can wire Filesystem MCP for Desktop manually; no automation here.
- **No embeddings, no semantic search.** Grep is faster + exact-match at ≤2000 markdown files (claude-harness has 137 today; even 10x growth fits comfortably). Per `mempalace-unused`: bulk-mined wings without curation underperform plain markdown.
- **Outgoing symlinks only.** `skills/memory-prune/` and `skills/new-cowork/` live under `~/workspace/claude-harness/skills/` and are symlinked OUT to `~/.claude/skills/` per the existing convention. No incoming symlinks (CLAUDE.md project instruction).
- **Receipts conform to `docs/protocol/receipt-schema.md` (NORMATIVE).** Codex round-2 finding [high] correctly flagged that round-1's bespoke receipt locations + timestamp-bearing `idempotency_key` diverged from the v2 protocol. This spec therefore aligns every receipt and journal with the canonical schema:
  - **Receipt path (all commands).** `.harness-state/<command>-<wave-or-spec-id>-<timestamp>.yml` per receipt-schema.md §"Receipt path". When the command operates on a repo, the receipt lives under that repo's `.harness-state/`. When the command operates on user-global state with no calling repo (e.g. `/new-cowork` invoked from `~`), the receipt lives at `~/.harness-state/<command>-<wave-or-spec-id>-<timestamp>.yml` (user-global mirror of the same namespace shape). No bespoke locations under `~/.claude/memory/.<x>-receipts/`.
  - **`operation_id` (NORMATIVE).** `operation_id = sha256_hex( "<command>\n<wave_id-or-spec_path-or-command-subject-or-'-'>" )` per receipt-schema.md §"Operation_id derivation". Paths/IDs only, NO input content, NO timestamp. For argumentful commands whose arguments select a distinct scaffold/target (not a wave or spec), the second field is the **command subject** — a canonical identifier derived from the command arguments — so two invocations with different subjects cannot collide on either `operation_id` or `idempotency_key`. For this spec: `command=memory-prune` → `operation_id = sha256_hex("memory-prune\n-")` (no wave/spec/subject context — single-target user-global command); `command=new-cowork` → `operation_id = sha256_hex("new-cowork\n<area>/<project>")` (subject = canonical `<area>/<project>` slug from the command arguments — each scaffold target gets its own operation identity, preventing Stage 1 cross-target no-op resume); `command=wave-migrate` → `operation_id = sha256_hex("wave-migrate\n2026-05-13-memory-system-redesign")` (spec_path slug as the stable identifier).
  - **`idempotency_key` subject inclusion (NORMATIVE for argumentful commands).** When `operation_id` uses a command subject (second field), that same subject also occupies the second field of the `idempotency_key` preimage. This guarantees that two concurrent `/new-cowork` invocations started from byte-identical filesystem state but different `<area>`/`<project>` arguments compute DIFFERENT `idempotency_key` values and Stage 1 lookup cannot wrong-resume one into the other.
  - **`idempotency_key` (NORMATIVE).** lowercase hex SHA-256 of `<command>\n<wave_id-or-spec_path-or-"-">\n<input-content-digest>`, where input-content-digest is sha256 of the sorted `<path>:<sha256-of-bytes>` lines per receipt-schema.md §"Canonical idempotency_key derivation". **Timestamps MUST NOT influence the key.** Re-running with the same inputs produces the same key byte-for-byte across manual/Claude/Codex adapters; mutating an input invalidates the key, and recovery falls back to `operation_id` per receipt-schema.md §"Recovery semantics" Stage 2.
  - **Stage A no-op exemption: NONE of this spec's commands are exempt.** `/memory-prune`, `/new-cowork`, and Wave 12 migration all mutate state and MUST NOT set `idempotency_key.trace.stage_a_exempt: true` per receipt-schema.md §"Stage A no-op exemption (read-only freshness-probe commands)" — they use Stage A unchanged.
  - **Rollback journals (every mutating command in this spec).** Per receipt-schema.md §"Recovery semantics" clause (b) — mutating commands "MUST either (a) write to a temp file and atomically rename into place once all changes for a given output are staged, OR (b) record a rollback journal entry in `.harness-state/` naming the original byte contents (or sha256 + git blob ref) of every input artifact about to be mutated, before mutating it." Where this spec deletes or relocates source files, it uses clause (b) and adds a **byte-exact backup obligation**: a git-blob-equivalent (`git hash-object -w <source>` returning the blob sha) is recorded in the journal BEFORE source deletion, sufficient to reconstruct the original bytes via `git cat-file -p <blob-sha> > <restored-path>`. Per-command application:
    - **Wave 12 migration (Task 7):** journal `.harness-state/wave12-migration.jsonl` — one JSON line per move with `{op_id, source_path, dest_path, source_sha256, source_blob_sha (git-blob-equivalent of pre-mutation bytes), dest_path_basename_collision (boolean), action: promote|archive|keep, ts}`. Order: `cp source dest.tmp` → write frontmatter to `dest.tmp` (promote only) → `mv dest.tmp dest` (atomic) → `git hash-object -w <source>` to capture original bytes into the local git object store → append journal line including `source_blob_sha` → only then `rm <source>`. **Rollback procedure (portable on stock macOS):** `( tail -r .harness-state/wave12-migration.jsonl 2>/dev/null || tac .harness-state/wave12-migration.jsonl ) | jq -r 'select(.action != "keep") | "git cat-file -p \(.source_blob_sha) > \(.source_path) && rm -f \(.dest_path)"' | sh` — restores **byte-exact original source bytes** (not the frontmatter-stamped destination), then removes the destination. The `tail -r` form is BSD/macOS-native; the `tac` fallback covers GNU-only systems; verification of restored bytes uses `shasum -a 256 -c -` on macOS / `sha256sum -c -` on GNU. Wave-level receipt at `.harness-state/wave-migrate-2026-05-13-memory-system-redesign-<ts>.yml` per the canonical schema; human-readable summary at `docs/waves/2026-05-13-wave-12-migration-receipt.md` linking the receipt + journal.
    - **`/memory-prune --apply`:** receipt at `.harness-state/memory-prune-<utc-iso>.yml` per canonical schema; journal lines appended to `.harness-state/memory-prune.jsonl` with `{op_id, source_path, dest_path, source_sha256, source_blob_sha, dest_sha256, ts}` for every entry archived. Apply uses temp-rename (`<file>.new` → fsync → atomic `mv <file>.new <file>`) so interruption leaves either old-intact or recoverable-`.new`. Dry-run mode mutates nothing AND writes no receipt/journal entries.
    - **`/new-cowork`:** receipt at `.harness-state/new-cowork-<area>-<project>-<utc-iso>.yml` per canonical schema (under the calling repo's `.harness-state/` if invoked from a repo; under `~/.harness-state/` if invoked from `~`); journal line at `.harness-state/new-cowork.jsonl` with `{op_id, area, project, scaffold_path, files_created, projects_md_row_added, projects_md_blob_sha_before (pre-edit bytes), ts}`. `op_id` is derived per the command-subject rule above (`sha256_hex("new-cowork\n<area>/<project>")`), so two concurrent invocations with different `<area>`/`<project>` arguments hold distinct operation identities even when started from byte-identical filesystem state. `projects_md_blob_sha_before` enables rollback of the PROJECTS.md row append via `git cat-file -p` even though the file is off-repo. Scaffolding itself is reversible via `rm -rf <scaffold_path>` (the scaffold folder did not exist before this command, so deletion is byte-exact restoration).
- **Macos bash 3.2 compatibility.** All shipped scripts (`prune.sh`, `new-cowork.sh`) avoid associative arrays per `reference_bash_compat_patterns`. Use `eval` + dynamic var names or sidecar files if state needs to span a `$(...)` subshell.
- **Stock-macOS portability for verification (NORMATIVE).** Every acceptance command, manual fallback step, and rollback procedure MUST run on a stock macOS terminal without GNU coreutils. Canonical substitutions: `sha256sum` → `shasum -a 256`; `tac` → `tail -r` with `tac` fallback (`tail -r <file> 2>/dev/null || tac <file>`); `find -printf` → forbidden (already enforced by Wave 2 acceptance). Verify holistic compliance: `grep -nE '\bsha256sum\b|\btac \b' docs/specs/2026-05-13-memory-system-redesign.md | grep -v 'fallback\|substitute\|GNU' | wc -l` returns 0 (every remaining `sha256sum` / `tac` mention is in a clearly-labeled fallback/substitution context, not the primary path).

## Risks

- **Shared root collision with future Claude Code semantics.** `~/.claude/memory/` is a path Anthropic could choose to mean something specific in a future Claude Code release. Mitigation: rename is cheap (one move + AGENTS.md/CLAUDE.md edit + symlink) if a conflict appears. Per Q2: collision risk acknowledged at decision time and accepted.
- **Migration loss of provenance / interrupted-run data loss.** Promoting per-cwd `feedback_*.md` to `~/.claude/memory/feedback/` deletes the source after the copy and adds frontmatter to the destination. If interrupted mid-run (kill -9, disk full, power loss), earlier drafts of this spec either had no rollback (round 1 finding [high]) OR a rollback that restored the frontmatter-stamped destination into the source path (round 2 finding [high] — the destination bytes are NOT the same as original source bytes, so `mv dest source` does not satisfy receipt-schema.md §"Recovery semantics" clause (b)). Mitigation, now layered for round 3: (1) Wave 2 manifest committed before any move, keyed on full `source_path` not basename (round-2 finding [high]); (2) Task 7 uses **copy → frontmatter-stamp dest → atomic mv → verify dest sha256 → `git hash-object -w <source>` for byte-exact backup → append journal with `source_blob_sha` → only then `rm <source>`** ordering; (3) `.harness-state/wave12-migration.jsonl` records every move with `source_sha256`, `source_blob_sha` (git-blob-equivalent of pre-mutation bytes), and `dest_sha256`; (4) **rollback restores byte-exact original source bytes via `git cat-file -p <source_blob_sha> > <source_path>`** — not the frontmatter-stamped destination; (5) canonical wave receipt at `.harness-state/wave-migrate-...yml` per `docs/protocol/receipt-schema.md` (round-2 finding [high]) with content-derived `idempotency_key` (no timestamp); (6) discovered-count is runtime-equality-checked via portable `find ... -type f | sort` (no GNU `-printf`) so the verifier cannot pass on a partial migration AND cannot fail on a non-Linux host (round-2 finding [high]); (7) basename collisions surfaced in an explicit `## Basename Collisions` manifest subsection for operator resolution before any move (round-2 finding [high]).
- **Desktop-knowledge symlink portability.** Claude Desktop's Project Knowledge ingestion may not follow symlinks on first drag, may re-resolve on rescan, or may behave differently across macOS / Windows. Mitigation: `workspace-CLAUDE.md` is a **copy**, not a symlink, because it's the load-bearing persona file. USER.md / FEEDBACK.md are symlinks; if Desktop fails to follow them, operator re-copies and accepts the staleness cost (small files, infrequent edits).
- **Gobot pivot re-review burden post-rename.** Wave 4 mechanically substitutes ~16 patterns across the gobot pivot spec. Codex has already reviewed it in two rounds (§11 of the pivot spec). The substitution is **not a design change** — the operator should not need a third round, but a smoke-read after Wave 4 lands is cheap insurance. Mitigation: Wave 4 verify includes a "no leftover `workspace` term in role-of-noun position" grep; operator does one read-through after merge before promoting any other gobot work.
- **`/new-cowork` produces a stale bundle if `~/.claude/memory/` changes after scaffold.** USER.md / FEEDBACK.md are symlinks so they self-heal. `workspace-CLAUDE.md` is a copy and will go stale if the project's own CLAUDE.md is edited after scaffold. Mitigation: cheap rerun — `/new-cowork` is idempotent in spirit if the operator deletes the bundle first; long-term, a `/cowork-sync-bundle` micro-skill (deferred to Phase 3) re-copies after edits.

## Non-Goals

This spec is the **memory + scaffold half** of the gobot pivot. It is deliberately not:

- A workspace-mode runtime spec (gobot pivot owns).
- A cowork-project lifecycle management system (gobot Phase 3 owns `/cowork-status`, `/cowork-close`, `/cowork-list`).
- A MemPalace replacement (mempalace cleanup is a separate side-quest spec, options A/B/C per `mempalace-unused`).
- A unified memory schema across coding and workspace modes (the 2026-05-11 decision explicitly rejects unification — two specialized systems share a root, do not collapse into one shape).
- A new MCP server (no `memory-mcp`; filesystem-direct only).
- An automated cross-repo registry sync (PROJECTS.md is human-maintained until friction proves otherwise; Open Q #1).
