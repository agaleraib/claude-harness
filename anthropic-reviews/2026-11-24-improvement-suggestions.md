## 2. Note the base-branch REVIEW.md pattern in `AGENTS.md` + `skills/commit/SKILL.md`

**Sources:**
- [How the Claude Code team thinks about verification — claude.dev Blog, 2026-11-16](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/) (secondary coverage: [The New Stack](https://thenewstack.io/anthropic-claude-code-verification/), [InfoQ](https://www.infoq.com/news/2026/11/claude-code-review/), [daily.dev summary](https://daily.dev/posts/how-the-claude-code-team-thinks-about-verification-fwye26i9d)).
- [Customize Code Review — Claude Code Docs](https://code.claude.com/docs/en/code-review-customize) — official doc that confirms Code Review reads `REVIEW.md` **from the pull request's base or default branch, never from the pull request's own changes**.

### Why it's relevant

The Claude Code team's verification playbook (Nov 16) codifies **a principle the harness quietly violates**: *"a change that can modify the check that judges it has broken that check."* The published remediation is to read the review rubric from the **base branch**, not from the working tree. Anthropic's hosted Code Review enforces this by always reading `REVIEW.md` from the base/default branch.

The harness's parallel mechanism is `criteria/*.md` — the rubric the `code-reviewer` agent scores against (see `README.md:408`, `criteria/code-architecture.md`, `criteria/code-simplicity.md`, etc.). These files are read **from the working tree**, which is the branch under review. A sloppy or adversarial change to `criteria/` can therefore lower the bar the `code-reviewer` applies to that same change. The vulnerability is latent because the harness is solo-maintained and no adversarial author exists, but the design is nonetheless the one the Nov 16 post explicitly calls out.

Additional patterns from the post worth surfacing (but not necessarily implementing):

- **A hook that runs tests when Claude finishes** (Stop or PostToolUse). `/commit` already invokes `code-reviewer` synchronously, so this is partly covered — but there is no `Stop` hook in `.claude/settings.json` (confirmed: it holds an empty `"hooks": {}` block), so a session can end without the final verification step firing if the user bails before `/commit`.
- **Commit gate pattern** (`off` / `observe` / `enforce`): blocks a commit unless the session ran a review step. Harness's `/commit` is advisory — the user can `git commit` directly and skip the skill.
- **"Turn misses into rules"**: when an agent repeatedly fails a check, add a hook or a CLAUDE.md rule. The harness has `CLAUDE.md` (small, 59 lines) and `AGENTS.md` (131 lines) — no explicit convention today for codifying recurring misses.

### Concrete change

Because this is **more than a one-line README edit** — it touches the `code-reviewer` agent's prompt (which reads `criteria/`), the `/commit` flow (invocation of that agent), and potentially a new global hook — the recommendation is **spec**, not apply. Draft spec outline:

1. **Intent**: close the "rubric-reads-from-working-tree" gap documented by the Nov 16 verification playbook.
2. **Design question 1**: in `code-reviewer`'s invocation, should the agent `git show origin/master:criteria/<file>.md` instead of reading the working tree? (Yes for `criteria/`; probably not for `AGENTS.md`/`CLAUDE.md` which the user may be deliberately changing in-branch.)
3. **Design question 2**: should the harness ship a `Stop` hook in `~/.claude/settings.json` that re-runs `code-reviewer` (or at least `git diff --cached` emptiness check) before letting a session end? Risk: tight loops. Gate: user opt-in via `setup-harness`.
4. **Design question 3**: does the harness want a "commit gate" (equivalent of the post's `enforce` mode) — refuse `git commit` unless a `.harness-state/commit-*-<started>.yml` receipt from the last 60s exists? Alternative: strengthen the existing pre-commit hook (`5130b9d feat(git-hooks): global dispatcher — secret scan, mass-delete block, profile gate`) to include this check.

**Minimum acceptable scope for a first-cut spec**: just the base-branch read for `criteria/*.md` in `code-reviewer` — the other two are design-questions, not decided outcomes.

Lightweight bookkeeping change to ship **now** (does not need a spec): one sentence in `AGENTS.md` under "what to avoid" (or the closest section) that documents the gotcha:

```diff
 ## What to avoid
...
+- Modifying `criteria/*.md` in the same change that `code-reviewer` is scoring. The harness reads criteria from the working tree, so a change to the rubric lowers the bar on the same change. Until a spec closes this (see `anthropic-reviews/2026-11-24-improvement-suggestions.md#2-...`), review rubric changes as a separate PR landed first.
```

And a one-line note in `skills/commit/SKILL.md` Step 3, immediately before the code-reviewer invocation:

```diff
 ## Step 3: Run code-reviewer

+> **Gotcha (tracked in anthropic-reviews/2026-11-24 §2):** if the staged diff edits `criteria/*.md`, `code-reviewer` sees the modified rubric, not the base-branch rubric. Land rubric changes as a separate commit first — don't bundle them with the change being graded.
+
 Invoke the `code-reviewer` agent on the staged diff. Pass it only the staged changes:
```

### Expected payoff

- (Documentation-only, immediately) — closes the latent self-modification gap at the discipline layer, before it causes a quiet rubber-stamp.
- (Spec'd + implemented) — matches Anthropic's published pattern; makes the `code-reviewer` agent robust against both accidental and adversarial criteria drift.

### Why this isn't a duplicate of 2026-05-10 §1

The 2026-05-10 §1 edit (APPLIED, commit 8b5b12a) positioned the local `code-reviewer` **alongside** Code Review and `/ultrareview`. It did not import any of their specific techniques into the local reviewer — this § is the first to pull a concrete technique (base-branch rubric read) inward.

## 3. Append Claude Ship / `/ship` to the "How this complements Anthropic's cloud reviewers" paragraph

**Source:** [Introducing Claude Ship — claude.com, 2026-11-23](https://claude.com/resources/articles/introducing-claude-ship). Launched one day before this run. Bundles three components for GitHub PRs: **Code Review** (now GA), **PR Steward** (beta — pushes fixes, addresses failing CI + review feedback), and **Claude Approvals** (beta — applies an approval policy the team writes). New `/ship` slash command in Claude Code pushes the change, opens a PR, and keeps it green. Team/Enterprise only; billed by tokens.

### Why it's relevant

The existing README paragraph at **`README.md:423–425`** (shipped in commit `8b5b12a` from 2026-05-10 §1) already positions three layers:

1. Harness's local `code-reviewer` — pre-push, rubric-anchored, blocks at `/commit`.
2. Anthropic's **Code Review** — auto-runs on every PR; fan-out parallel agents + verification.
3. Anthropic's **`/ultrareview`** — user-triggered; 10–20 min cloud run on current branch/PR.

As of Nov 23, Anthropic added a **fourth layer**: `/ship` in Claude Code triggers the Ship bundle (review + fix + approval policy) on a PR the developer just created. This is **concretely different** from `/ultrareview`:
- `/ultrareview` = one-shot cloud review, read-only.
- `/ship` = push + PR + review + autofix (via PR Steward) + optional auto-approval (via Claude Approvals).

For a solo maintainer the gap matters because `/ship` is the first Anthropic command that **writes back to the PR branch** without the user in the loop per-fix — categorically different risk profile from the read-only reviewers the existing paragraph names.

### Concrete change

Append one sentence at the end of the paragraph at `README.md:425`:

```diff
 The harness's `code-reviewer` runs **locally, pre-push, against project `criteria/`**, and is invoked synchronously by `/commit`. As of [Code w/ Claude 2026](https://claude.com/blog/code-review), Anthropic also ships two cloud reviewers that operate at different layers: **Code Review** (Team/Enterprise; auto-runs on every PR; fan-out parallel agents + verification step) and **`/ultrareview`** (Pro/Max; user-triggered; 10–20 min cloud run on the current branch or a PR). Both are billed by token usage — see the linked post for current pricing. Use the local `code-reviewer` for the build/review loop before commit (cheap, rubric-anchored, blocks at `/commit`); use Anthropic's cloud reviewers for the post-push pass on substantive PRs that are about to merge (PR-context-aware, multi-agent fan-out). They are complementary, not redundant — different layers, different costs, different recall/precision.
+
+As of [Claude Ship (2026-11-23)](https://claude.com/resources/articles/introducing-claude-ship), Anthropic also ships a fourth layer: **`/ship`** in Claude Code (Team/Enterprise only today) pushes the current change, opens a PR, invokes Code Review on it, and lets **PR Steward** auto-fix failing CI + review feedback by pushing commits back to the branch. Unlike `/ultrareview`, this layer *writes* to the PR — rely on it only for repos whose branch-protection rules match what you want an agent to merge, and start **Claude Approvals** in observe-only mode before letting it approve anything automatically.
```

Optional second touch: add a one-line bullet to the References section (`README.md` around line 1070):

```diff
 - [Code Review for Claude Code](https://claude.com/blog/code-review) — Anthropic's cloud-hosted multi-agent PR reviewer (May 2026); complement to the local `code-reviewer` agent
+- [Introducing Claude Ship](https://claude.com/resources/articles/introducing-claude-ship) — `/ship` + PR Steward + Claude Approvals (Nov 2026); fourth layer above Code Review that writes to the PR
```

### Expected payoff

The next reader who hears "Claude can now auto-approve my PRs" gets the "when to use which" answer in the README at the same paragraph that already handles that question for the three earlier layers. Also forestalls the temptation to replace the harness's `/commit` + `code-reviewer` flow with `/ship` — those run at different stages (pre-push vs. post-push) and the local flow costs < $0.10 per invocation vs. token-billed per PR.

## 6. Potential `claude plugin eval`-based CI gate for the harness's own skills

**Sources:**
- [Plugin Evals — Claude Code Docs](https://code.claude.com/docs/en/plugin-evals) — official doc.
- Secondary coverage: [MarkTechPost launch article, 2026-09-11](https://www.marktechpost.com/2026/09/11/anthropic-adds-plugin-evals-to-claude-code-6-grader-types-a-no-plugin-baseline-and-a-ci-gate-for-skills/) — Claude Code v2.1.269 adds `claude plugin eval` with six grader types, a no-plugin baseline, and a CI gate.

### Why it's relevant

The harness ships **18 skills** (via symlink to `~/.claude/skills/`). Changes to a skill body can silently regress end-to-end behavior — the existing `skill-creator` plugin has an `evals/evals.json` mechanism, but no CI gating today. Anthropic's Sept 11 launch adds:

- A `claude plugin eval` CLI with six grader types.
- **Comparison against a no-plugin baseline** — the thing missing from the existing in-repo evals.
- A CI gate (threshold + max-cost flags).

The harness's own build hygiene — `.harness-state/` receipts, wave artifacts, pre-commit hooks — is high-discipline, so the lack of an eval gate is a specific gap rather than a pervasive discipline issue.

### Concrete change (deferred)

None this run. If adopted later, roughly:

1. Pick 2–3 high-leverage skills to eval first: `commit`, `run-wave`, `code-reviewer` (the agent, invoked from `/commit`).
2. For each, write 3–5 realistic prompts + expected-behavior assertions.
3. Add a GitHub Action (or a manual pre-push check) that runs `claude plugin eval --threshold 0.8 --max-cost-usd 20 --model claude-opus-5-5 --judge-model claude-haiku-5-5 --no-publish` and blocks merge on regressions.
4. Decide whether evals block merge, or run post-merge for fast feedback without blocking.

### Why this is `defer`, not `apply`

- **No reproducible pain yet.** A specific skill-regression incident hasn't shipped to a consumer project. Spec'ing without a motivating incident risks over-engineering.
- **Cost non-trivial.** Per the official docs, every eval run + judge-model invocation counts against plan usage or API billing. A 20-skill × 5-eval matrix run on each push adds up.

- **Model-pin flux (§1).** This § becomes easier to spec after §1 settles the model-pin — otherwise the `--model` flag drifts under us.

### Expected payoff (when applied)

Regression gate for skill changes catches subtle behavior breaks (e.g. a prompt edit that makes `code-reviewer` miss a whole class of findings). Low-noise because evals compare against a no-plugin baseline — only true regressions surface.
