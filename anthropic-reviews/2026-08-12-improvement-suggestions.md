## 1. Refresh `skills/setup-harness/SKILL.md` Auto Mode paragraph for the 2026-08-14 default flip

**Source:** [Auto mode is now the default in Claude Code for Pro, Max, and Team plans — claude.com/blog, 2026-08-07](https://claude.com/blog/auto-mode-default-in-claude-code). ### Why it's relevant

The 2026-05-08 §1 (`APPLIED in commit ~139-149 of `skills/setup-harness/SKILL.md`) added a "Permission model — Auto Mode + hooks layering" section with three concrete recommendations for solo users. Reading it today:

```markdown
### Permission model — Auto Mode + hooks layering

Claude Code's Auto Mode (GA on Pro/Max/Team/Enterprise/API as of May 2026) runs a Sonnet 4.6 classifier that auto-approves safe tool calls and surfaces only the risky ones. **Hooks run before the classifier**, so anything this harness allow/deny-lists in `.claude/settings.json` (and anything `fewer-permission-prompts` adds for you) is honored as a hard rule; the classifier only sees the residual.

Recommended setup for solo users:

1. Run `/fewer-permission-prompts` once in a project to seed an allowlist for the read-only Bash + MCP calls you actually use.
2. Keep `.claude/settings.json` `hooks` block populated with your policy checks (lint, secret scan, etc.); Auto Mode will not bypass them.
3. Toggle Auto Mode interactively via Shift+Tab. (As of writing, `permissions.defaultMode: "auto"` is parsed but doesn't reliably auto-engage on session start — manual toggle is the safer default. Re-check before relying on a config-only bootstrap.)

If you work in an isolated container, prefer Auto Mode over `bypassPermissions` — Auto Mode keeps the classifier's prompt-injection mitigations active.
```

## 2. Bookkeeping citation: link Anthropic's "self-hosted Claude Code environments" from `sandcastle_mattpocock_architecture.md`

**Source:** [Run Claude Code sessions on your own compute — claude.com/blog, 2026-08-06](https://claude.com/blog/run-claude-code-sessions-on-your-own-compute). Public beta for Team/Enterprise: session starts from web/mobile/desktop/routine, then runs on infrastructure the org provisions (checkouts, secrets, artifacts stay on the org's machines). Different from Remote Control (which continues a session on the developer's own machine tied to their user) — this is shared org-run infra that any user can start a session against.

### Why it's relevant

This repo already ships a written-up local execution architecture in `sandcastle_mattpocock_architecture.md` (152 lines, provenance-stamped source-code review of `@ai-hero/sandcastle@0.9.0` at commit `d7a41c8…`, dated 2026-06-16). Sandcastle's model:

- Session runs in a container the user provisions (Docker, containerd, etc.).
- Checkouts, artifacts, and secrets stay inside that container until an explicit `merge-to-head`.
- No PR is opened — direct merge into the host branch.

Anthropic's new self-hosted environments have the same top-level shape at a different layer:

- Session runs on infrastructure the *org* (not the individual user) provisions.
- Checkouts, artifacts, and secrets stay on org machines.
- Any user with plan access can start a session against the shared infra.

The two are complementary, not competing: sandcastle is a local/per-user container that a solo maintainer can use today (Pro plan is enough); self-hosted environments are a Team/Enterprise cloud equivalent that a small team could adopt without leaking session state to Anthropic-managed infra. A single sentence pointing from the sandcastle doc to the Anthropic post gives future readers ("is there an off-the-shelf managed version of this?") the answer without them re-deriving the search.

**Not proposing a change to `sandcastle_mattpocock_architecture.md` in this run** — that doc is a point-in-time snapshot review (see its `## Provenance` block) and touching it just for this cross-reference risks blurring the snapshot's dated status. Defer to the next time the sandcastle doc is edited for a substantive reason (e.g. a new sandcastle release, or the harness's sandcastle-adoption decision moves).

**Why not `run-loop`?** The `/run-loop` skill's runner already uses `.claude/worktrees/agent-<id>/` for worktree isolation and containers for sandcastle mode (per `CLAUDE.md`). The self-hosted-envs post doesn't change how the runner works; it's a distinct product surface. The parallel is with sandcastle's philosophy, not with `/run-loop`'s implementation.
