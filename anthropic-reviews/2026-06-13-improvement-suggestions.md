## 2. Adopt the "agentic laziness / self-preferential bias / goal drift" failure-mode vocabulary in README

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (Anthropic engineering deep-dive on harness design, written alongside the May 28 dynamic-workflows launch).

### Why it's relevant
The post names **three failure modes** that motivate harness design:

1. **Agentic laziness** — "Claude bails on a complex, multi-step task and announces it's finished after only partial progress, like knocking out 20 of 50 items in a security review and calling that done."
2. **Self-preferential bias** — "Claude leans toward its own outputs and conclusions, most noticeably when it's the one verifying or scoring them against a rubric."
3. **Goal drift** — (implied by the post's framing; the article frames the harness as the thing that keeps a long-running agent pointed at the original objective).

These three names map almost 1:1 onto **why this harness exists** today:

- **Agentic laziness** is what `code-reviewer` catches at `/commit` — it adversarially re-checks the diff against `criteria/*.md` so the in-session model can't just claim "done."
- **Self-preferential bias** is the *exact* reason `code-reviewer` is a separate agent rather than a self-evaluation pass — Anthropic's own `effective-harnesses-for-long-running-agents` post called out the planner/generator/evaluator triple for the same reason.
- **Goal drift** is what `spec-planner` + the plan-archive ritual prevent — the spec is the canonical objective; `archive-plan` and `harness-status` keep it visible across sessions.

The README's "Why Not Superpowers" section (lines 23–34) already cites multiple Anthropic posts as evidence. **The post's vocabulary is now the most concise framing** for what `code-reviewer` and `spec-planner` are *for* — adding it costs one paragraph and earns the harness an Anthropic-blessed problem statement.

### Concrete change

Append a **one-paragraph bullet** to the README's "Why Not Superpowers" evidence list (lines 27–32), or — alternatively — add it to the `code-reviewer (Universal)` agent section around line 406 as the failure-mode rationale. Suggested wording for the evidence list (line 32 area):

```diff
 - **Vendor primitives keep absorbing harness territory**: Claude Code now ships a built-in `/security-review` slash command, and Anthropic launched [Claude Security in public beta on 2026-04-30](https://claude.com/blog/claude-security-public-beta) with full-codebase vulnerability scanning + patch generation on Opus 4.7. A custom security-review skill would have been a reasonable addition to this harness six months ago; today it's redundant with first-party tooling. The pattern repeats — keep the harness lean so vendor releases don't deprecate it.
+- **Three failure modes the harness *should* catch (Anthropic's vocabulary)**: [A harness for every task](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (June 2 2026) names **agentic laziness** (claiming done after partial progress), **self-preferential bias** (the model under-flagging its own output when it scores itself against a rubric), and **goal drift** (the model losing the original objective over a long run). This harness's `code-reviewer` (adversarial, separate-context rubric scoring) targets #1 and #2; `spec-planner` + the plan-archive ritual targets #3. Use these names when explaining *why* a separate-context evaluator exists.
```

If the alternative placement is preferred (under the `code-reviewer (Universal)` agent section), the same paragraph can be reframed as "Why this is a separate agent" instead of an evidence bullet.

### Why this is `apply`, not `defer`
- One paragraph, single file (`README.md`).
- No code change, no model pin touched, no spec required.
- The vocabulary is *durable* — these three failure modes don't change between model versions, so the citation outlives the Opus-4.x window.

### Expected payoff

## 3. Position dynamic workflows in Claude Code alongside the local `orchestrator` agent

**Source:** [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (research preview, ships in Claude Code v2.1.154+). Companion engineering writeup: [A harness for every task — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code).

### Why it's relevant
The harness's `orchestrator` agent (`.claude/agents/orchestrator.md`) is **local, spec-driven, single-process**, and routes per-task to opus/sonnet/haiku based on declared complexity. As of 2026-05-28 Anthropic ships **dynamic workflows**:

- Claude writes a **JavaScript orchestration script** on the fly from a natural-language request.
- A separate runtime executes the script in the background, spawning **up to 1,000 total subagents (16 concurrent)**.
- Intermediate results live in script variables — *not* the main session's context window.
- The chat session stays responsive; the user gets a consolidated report at the end.

These are **complementary, not redundant** — same shape as the relationship between the harness's `code-reviewer` and Anthropic's hosted Code Review / `/ultrareview` (already documented per 2026-05-10 §1, APPLIED). The harness's `orchestrator`:

- runs *inside* the active Claude Code session — no separate runtime;
- routes one task at a time to one subagent — never 1,000;
- is spec-driven — every dispatch is gated on `Files:` and `Verify:` fields;
- costs only the Claude Code session it runs in.

Dynamic workflows:

- run *outside* the active session — JS runtime + 16 concurrent agents;
- target codebase-wide audits and large migrations — fan-out, not in-session task routing;
- are **gated to Claude Code v2.1.154+** and require paid-plan access;
- consume token budget proportional to the fan-out (no published $/run yet).

The two solve different problems. The harness's `orchestrator` is the "build a spec'd phase end-to-end" loop; dynamic workflows are the "answer one cross-codebase question with parallel agents" loop. A one-paragraph note in `.claude/agents/orchestrator.md` (or under the `orchestrator` section in the README) would forestall the next "is the local orchestrator redundant now?" question.

### Why this is `defer`, not `apply`

1. **Premature without adoption signal.** The harness maintainer hasn't tried dynamic workflows yet (`grep -rn "v2.1.154\|dynamic workflows\|orchestration script" /home/user/claude-harness` returns zero hits). Documenting the relationship before *any* hands-on use risks misrepresenting it. The 2026-05-10 §1 Code Review edit was different — Anthropic Code Review had been *in use* by the maintainer's PR cycle.
2. **Version gate.** Claude Code v2.1.154+ requirement means consumer projects pulling this harness might be on older Claude Code. Documenting it as a peer of `orchestrator` for users on v2.1.130 is misleading.
3. **Speculative for solo tooling.** The 1,000-subagent fan-out solves problems this harness's user doesn't yet have — codebase-wide audits, security fan-outs, large migrations across many services. Solo tooling repo with ~50 markdown files isn't the target audience.
4. **Pricing-and-pricing-band TBD.** No published $/run; the fan-out is token-budget proportional. Until pricing settles (see Fable 5's June-22 cliff, dynamic-workflow's research-preview status), citing the comparison risks pinning the doc to a moving number.

### Concrete change (deferred)

When the maintainer adopts dynamic workflows for at least one real task (codebase audit, broad refactor, multi-service migration), append a paragraph to either `.claude/agents/orchestrator.md` (the §How to Invoke area) or the README's `orchestrator` section, modelled on the 2026-05-10 §1 code-reviewer-vs-hosted-Code-Review paragraph:

As of [2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code), Claude Code also ships **dynamic workflows** (v2.1.154+; paid plans) — Claude writes a JavaScript orchestration script on the fly, and a separate runtime spawns up to 1,000 total subagents (16 concurrent) in parallel, with intermediate state in script variables rather than the chat session. Use the local `orchestrator` to build a *spec'd phase end-to-end* (deterministic, gated on Files/Verify, cheap); use dynamic workflows for *cross-codebase audits and large migrations* (fan-out, token-budget proportional). ### Expected payoff (when applied)

## 4. Switch agent output format from Markdown to HTML per "Unreasonable effectiveness of HTML"

**Source:** [Using Claude Code: The unreasonable effectiveness of HTML — claude.com/blog, 2026-05-08](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html) (Thariq Shihipar, Claude Code engineering lead). Viral; 4.4M views in 16 hours. Argues that Markdown's small-context-window roots are obsolete now that context windows are 1M tokens, and that HTML wins on display + reusability for plans, code reviews, design systems, and reports.

### Why it's relevant — and why the answer is `reject`

The post lands on agent-generated artifacts that **the user reads once in chat and discards** — interactive PR-review summaries with inline annotations, design-system mocks, plan documents with rich color/diagrams. For that surface, HTML's display fidelity matters.

The harness's outputs are a different surface:

- `criteria/*.md`, `procedures/*.md`, `docs/specs/*.md`, `docs/waves/*.md`, `anthropic-reviews/*.md` — **committed methodology files** read by future Claude Code sessions, future readers, and `mcp__github__get_file_contents` / `grep`. Markdown is the *correct* format because CLAUDE.md ergonomics, SKILL.md frontmatter, git-grep, and search-in-codebase tools all assume Markdown.
- `evaluator` reports — produced by the `code-reviewer` agent and shown to the user once. *Could* be HTML in theory, but the harness pipes them through `/commit` and they're typically discarded after the diff is fixed; the conversion cost outweighs the readability gain.
- Close-wave receipts, harness-status outputs, run-wave JSONL — structured YAML/JSONL, not prose; HTML doesn't apply.

The HTML post's recommendations (switch system prompts to ask for HTML; render rich diff annotations; build HTML artifacts for plans) are correct **for an end-user chat interface generating one-shot artifacts** — not for a tooling repo's committed Markdown library.

Adopting HTML for any of the harness's existing surfaces would either (a) break readability for the next Claude Code session that has to re-read the file, or (b) require a parallel HTML pipeline alongside the Markdown one. Both costs exceed the benefit.

### Concrete change

None. Skip in this routine; mark `reject — wrong scope` in the tracker so the next run doesn't re-evaluate the HTML pivot.

A *speculative* future scenario where HTML *would* be considered:

- If the harness ever produces a one-shot UI report (e.g. an `harness-status` HTML dashboard for the user to open in a browser), HTML would be the right format for *that artifact only*. Committed Markdown library stays Markdown.

That scenario isn't on the horizon today.

**Verify before applying:**
1. `grep -rn "HTML output\|html artifact\|claude.com/blog/using-claude-code-the-unreasonable" /home/user/claude-harness --include='*.md'` — should return zero hits today. If it returns hits, the HTML pivot has been at least partially considered; re-read this § before re-evaluating.
2. Confirm the harness still produces its primary outputs in Markdown (`ls anthropic-reviews/*.md` returns files, `ls docs/specs/*.md` returns files). If the harness has migrated *any* surface to HTML, this § becomes partially stale — the scope-and-fit assessment may need updating.

**Recommended verdict:** reject — wrong scope; HTML is the right format for one-shot chat artifacts, not for committed methodology files. The harness's outputs are the latter.
