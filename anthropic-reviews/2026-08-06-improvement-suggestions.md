## 3. Trim the harness's longest `SKILL.md` files per Claude 5's "unhobbling" guidance — starts with a `/doctor` baseline

**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models). Two central claims relevant to this repo:
1. Anthropic removed **>80% of Claude Code's system prompt** for Claude 5 models with no measurable coding-eval loss. The premise: constraints written to prevent worst-case behavior in older models now create conflicting instructions and wasted tokens for Claude 5, which has better judgment.
2. Anthropic ships a **`/doctor`** command in Claude Code for rightsizing skills and CLAUDE.md files against the new rules.

### Why it's relevant
The harness has 25 skill files; the five longest are:
```
$ wc -l skills/*/SKILL.md | sort -rn | head -5
719 skills/planning-loop/SKILL.md
675 skills/close-wave/SKILL.md
488 skills/skill-creator/SKILL.md
446 skills/run-wave/SKILL.md
412 skills/triage-parking/SKILL.md
```
Every one of them was written between 2026-04 and 2026-06 — for Opus 4.7 / Sonnet 4.6, the models the current pin targets. Anthropic's Jul-24 essay is the first evidence-backed argument that these files are likely over-scaffolded for Claude 5.

The shortest skills (`shared-root-init` 64, `memory-prune` 93, `micro` 106, `park` 130, `new-cowork` 131, `cowork-area-sync` 139) are already lean and probably don't need attention. The advice concentrates on the top-5.

`CLAUDE.md` (35 lines) and `AGENTS.md` (131 lines) are also short — the "80% removal" advice is unlikely to apply directly. The candidate targets are the five long SKILL.md files above.

### Why this is `spec`, not `apply`
1. **No mechanical baseline exists.** Anthropic removed 80% of Claude Code's prompt only after running their eval suite and confirming no regression. The harness has no equivalent eval fixture — the closest is `skills/planning-loop/evals/evals.json`. Trimming without a canary run risks eating well-earned reliability (see 2026-04-19 §5 on evals, still deferred).
2. **`/doctor` is a Claude Code interactive command.** It rightsizes files against the essay's rules — but it does so in-session, not as a batch tool the harness can run pre-commit. There is no headless invocation surface as of 2026-08-06 (verify via `code.claude.com/docs`).
3. **Some length is load-bearing.** `planning-loop/SKILL.md` (719 lines) codifies the strict-acceptance-check discipline that Wave 25 just landed (`docs/specs/2026-04-27-planning-loop-auto-apply-arbiter.md`). Blanket 80% removal would delete decisions the harness just paid to make.
4. **The essay names a "trust the model's judgment" shift** but explicitly warns that guardrails that catch worst cases can still be worth their tokens — the rightsizing is per-instruction, not per-file. A batch trim isn't the right shape.

The right shape is likely:
- Pin Opus 5 first (§1) — gives the trim a target model to test against.
- Baseline behavior on the top-5 skills (record a golden trace per skill on the current text).
- Run `/doctor` interactively per skill; capture proposed cuts.
- Re-run the trace on the trimmed text; keep only cuts that preserve the trace.
- Ship the trim as one wave per skill, not five in a batch — so a regression is bisectable.

That is a spec, not a `/micro`.

### Concrete change
None this run. When speccing:
1. `/spec-planner` — target: "rightsize the top-5 harness SKILL.md files against Claude 5 context-engineering rules."
2. Spec should include the baseline-trace protocol (this is where the 2026-04-19 §5 evals deferral becomes load-bearing again).
3. Land Opus 5 first (§1) so the trim tests against the model it will be trimmed for.
4. One wave per skill, ordered by length descending (`planning-loop` first). Each wave: baseline trace + `/doctor` pass + trace re-run + review + commit.

### Expected payoff (when applied)
Faster session-start (skill descriptions load on demand, but their content lands the moment they're invoked); less prompt-time overhead per skill invocation; alignment with Anthropic's current guidance for the models the harness will actually target.

### Why not defer instead of spec
Because "trim skills" is an underspecified direction ("rightsize the top-5 skill files") with real design choices (baseline protocol, per-instruction vs. per-file decisions, wave ordering, canary reversibility). Per the README triage rubric: *"Shape is underspecified (direction named, design choices remaining)"* is a spec-signal, not a defer-signal.

**Verify before applying:**
1. `wc -l skills/*/SKILL.md | sort -rn | head -5` — should still show the same top-5 (`planning-loop`, `close-wave`, `skill-creator`, `run-wave`, `triage-parking`). If someone has already trimmed one, drop it from the target list.

4. Confirm §1 (Opus 5 pin) has landed before starting the spec — otherwise the trim tests against the wrong target model.

**Recommended verdict:** spec — direction is right, shape is underspecified, touches five load-bearing skills; needs `/spec-planner` before any coding. Not `defer` because the deferral would be indefinite; a spec fixes that.

## 4. Re-evaluate `.harness-profile`'s `effort_default: xhigh` derivation rule once §1 lands

**Source:** [Claude Code effort level and model selection — claude.com/blog, 2026-07-07](https://claude.com/blog/claude-model-and-effort-level-in-claude-code) (Lydia Hallie, Claude Code team). Now the canonical explanation of the effort knob — clarifies that effort controls not just thinking time but "how much work Claude does on your request overall including the number of files read, tools used, and how many steps it takes before it checks back in with you." Anthropic's guidance: "Choose smaller models for more routine tasks and larger models for more complex or ambiguous tasks. Start with default effort levels for each model and tune as a general preference based on the type of work you do rather than task-by-task."

Companion post: [Introducing Claude Opus 5 — anthropic.com/news, 2026-07-24](https://www.anthropic.com/news/claude-opus-5) — Opus 5 ships with a **low/medium/high** effort surface (three levels), not the low/medium/high/xhigh four-level surface the harness's derivation rule assumes.

### Why it's relevant
The harness's `.harness-profile` uses a derivation rule:
```
# stakes.level: low    → effort_default: high
# stakes.level: medium → effort_default: xhigh
# stakes.level: high   → effort_default: xhigh
```

If §1 lands and `.harness-profile` pins Opus 5, the derivation-rule table above may pin `xhigh` to a model that doesn't offer `xhigh`. What actually happens (does the orchestrator downgrade to `high`? does the model API reject it?) needs verification. Either way, the derivation rule should be re-stated against Opus 5's surface, not Opus 4.7's.

### Why this is `defer` (not `apply`)
1. **Downstream of §1.** Until Opus 5 is actually pinned, editing the derivation rule speculatively risks two churn commits (one for the pin, one for the rule) instead of one considered change.
2. **Anthropic's canonical guidance says "Start with default effort levels for each model and tune as a general preference."** Opus 5's default (per Anthropic's launch post) is not spelled out in the excerpts fetched during this review; a targeted read of the launch post is needed before revising the derivation rule.
3. **The `.claude/agents/orchestrator.md` routing table** encodes per-task effort decisions ("read-only tasks use `low`, code-reviewer and multi-file work use `xhigh`" per `README.md:574`). Any change to the `effort_default` derivation rule should be reviewed against that table simultaneously — it's not a one-file change.

### Concrete change (deferred)

1. Read the full Opus 5 launch post to extract the exact effort defaults per plan/model.
2. Read `.claude/agents/orchestrator.md` in full and identify each place `xhigh` is used per-task.
