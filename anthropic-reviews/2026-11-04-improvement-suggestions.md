## 1. Decision tree in `.claude/agents/orchestrator.md`: when to fold subagents into the main loop vs. dispatch

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com/resources, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) (author: Diane Sarkis, Anthropic).

### Why it's relevant

Anthropic's new guidance reframes the recommended default for agent architectures. The headline claim: **one model, one context window, a tool loop with budgets, procedures-as-skills, actions-as-tools, central ownership of the system prompt**. The post is explicit that subagent fan-out is still appropriate, but **only** when:

- the single loop measurably degrades from context bloat, **or**
- tasks run in parallel and each benefits from a fresh, discardable context window, **or**
- verification / black-box checks / isolated permissions require isolation, **or**
- the agent struggles to pick the right tools, or the system prompt contains conflicting instructions.

The harness's `.claude/agents/orchestrator.md` is a runtime-dispatch orchestrator — every spec task becomes a subagent spawn (Step 1 `Spawn a subagent with the selected model`, Step 2 "For parallel tasks: Spawn subagents with `isolation: \"worktree\"`"). The routing table (`.claude/agents/orchestrator.md:144–152`) assumes dispatch; the retry ladder (`:247–248`) assumes dispatch; the receipt schema (`:327`) assumes dispatch. **This is the "specialists do everything" architecture Anthropic is now explicitly steering harness authors away from.**

The gap is not binary — the post also lists **five concrete signals that it's time to fold**:

1. Specialists chain on each other's output, touch the same data, or are often called together.
2. The agent feels inconsistent in voice, or the prompt has grown into conflicting rules.
3. Many overlapping subagents exist with no clear owner, and the architecture mirrors the org chart.
4. Handoffs lose detail, or latency hurts the user experience.
5. Logic that a model can now handle (intent classifiers, fixed pipelines) is doing work the model no longer needs help with.

And a recommended migration: build a small ~10-example eval set → merge tightly-coupled specialists first → wrap remaining subagents as tools so the main agent keeps the conversation → fold one at a time, comparing eval results with and without each.

### What this harness actually looks like through that lens

Partial overlap already exists. The harness **does** use skills (not subagents) for procedures (`skills/commit/`, `skills/micro/`, `skills/park/`, `skills/run-wave/` etc. — 25 skills under `skills/`). It **does** have a central `AGENTS.md` + `CLAUDE.md` system-prompt pair with documented ownership rules. It **does** gate subagent dispatch on a `model_routing: on` toggle in `.harness-profile` (so dry-run is a single-loop pass). These are compatible with the post's target design.

Where it diverges: when `model_routing: on` is set, **every task is a subagent spawn** (worktree-isolated for parallel-eligible tasks). The post's guidance says that should be the exception, not the default — reached when context bloat is measurable or parallelism is proven worth the handoff cost.

### Why this is `spec`, not `apply`

The suggestion isn't "rewrite the orchestrator to run everything in one loop" — that would be ignoring the post's own signals for keeping subagents (parallel worktree-isolated tasks is a legitimate use case for this harness). The suggestion is **add a decision-tree at the top of `.claude/agents/orchestrator.md` Step 1 that tells the orchestrator when to fold a task into the main session vs. dispatch**. That decision needs:

- A threshold for "small enough to run in main session" (token budget? file count? scoped type?).
- An operational definition of "specialists chain on each other's output" the orchestrator can detect from the spec.
- A way to extend `model_routing: on|off` toggle to `on|off|fold` — i.e., allow the user to keep the current fan-out semantics while the decision tree stabilizes.
- A matching update to the receipt schema (`.harness-state/orchestrator.{log,jsonl}`) so a "folded" task is logged distinguishably from a "dispatched" task.

This is a design choice, not a mechanical edit. Spec it before coding.

### Concrete change (deferred — needs spec)

None this run. When/if the maintainer wants to take this on:

1. `/spec-planner` to produce `docs/specs/<date>-orchestrator-fold-signals.md` with:
   - decision-tree signals (map the 5 fold-signals above to spec-parseable predicates, plus the 4 keep-separate signals as negative predicates)
   - toggle semantics (`model_routing: fold` as a third value, with a documented default)
   - receipt-schema change (one new field, `dispatch_mode: dispatched | folded | dry_run`)
   - the eval harness this depends on (the post mandates ~10 goldens before migrating — the harness doesn't have an orchestrator eval set yet; this is the blocker)
2. Routes to **the deferred 2026-04-19 §5 (agent evals)** — that deferral is now a direct blocker of this one. Note the chain in the spec.

### Expected payoff (when spec'd and built)

- Cheaper runs for single-task spec phases (no cold-context handoff overhead).
- More-faithful cross-task continuity for specs that chain (planner → implement → verify where the three touch the same files).
- Preserves the fan-out pattern where it legitimately helps (parallel-eligible worktree-isolated tasks).

Non-trivial, touches core agent logic + receipt schema + toggle semantics. Deserves `/spec-planner` before any code edit. Chain-blocked on the long-deferred agent evals from 2026-04-19 §5.

## 2. Bump `.harness-profile` + orchestrator routing table to the Claude 5.5 family

**Sources:**
- [Introducing Claude Opus 5.5 — Anthropic News, 2026-09-22](https://www.anthropic.com/news/claude-opus-5-5) (`claude-opus-5-5`; first model in the Claude 5.5 family)
- [Introducing Claude Sonnet 5.5 — Anthropic News, 2026-09-28](https://www.anthropic.com/news/claude-sonnet-5-5)
- [Introducing Claude Haiku 5.5 — Anthropic News, 2026-10-07](https://www.anthropic.com/news/claude-haiku-5-5) (`claude-haiku-5-5`; **first Haiku-class model with adjustable effort** — Low, Med, High, Xhigh, Max)
- Background: [Introducing Claude Opus 4.8 — Anthropic News, 2026-05-28](https://www.anthropic.com/news/claude-opus-4-8) was the intermediate step during this window; the harness's `run-loop` reviewer wires to `anthropic-api:opus-4.8` (`docs/waves/wave21-run-loop-live-wiring.md:45, 81`) but `.harness-profile` was never bumped through it.

### Why it's relevant

The harness pins to a model family (`claude-opus-4-7` / `claude-sonnet-4-6` / `claude-haiku-4.5`) that has been superseded twice since the last tracker entry: once by Opus 4.8 (May 28), then by the full Claude 5.5 family (Sept 22 – Oct 7). The pin shows up in four distinct surfaces:

1. **`.harness-profile:30–32`** — `primary: claude-opus-4-7`, `fallback: claude-sonnet-4-6`.
2. **`.claude/agents/orchestrator.md` routing table (lines 144–152)** — task-shape → model mapping all uses `haiku-4.5`, `sonnet-4.6`, `opus-4.7`.
3. **`.claude/agents/orchestrator.md` escalation chain (lines 247–248, 260, 382)** — `haiku-4.5 → sonnet-4.6 → opus-4.7` and `stops only at opus-4.7/xhigh`.
4. **`skills/project-init/SKILL.md:153–154, 207–208`** — new-project defaults seeded as `claude-opus-4-7` / `claude-sonnet-4-6`.

Plus several `docs/specs/` and `docs/waves/` files reference the old slugs as part of worked examples. Those are historical records and should probably stay (they document what the pin was at the time); only live-config surfaces should move.

### What specifically needs decisions

This is a **routing-logic change**, not a slug-swap, because the 5.5 family has new capabilities that change what each tier is good for:

- **Haiku 5.5** has adjustable effort (Low → Max) for the first time. In the current routing table, Haiku is the "typo fix / read-only scan" tier at `low` effort. With Haiku 5.5's adjustable effort, Haiku can plausibly take on tasks the table currently assigns to Sonnet. The simplest safe change is to swap slugs and leave effort levels alone; the better change is to re-evaluate which task-shapes belong at which tier.
- **Opus 5.5** generates "30% faster than Opus 5" and costs 40% less than Opus 5 on typical workloads (per Anthropic's launch post). Default effort behavior and "thinking can no longer be disabled" changes the semantics of the current `effort_default: xhigh` setting.
- The session's own prompt (fallback chain `claude-opus-5-5[1m]`, `claude-opus-5[1m]`) shows there's already runtime drift between what `.harness-profile` pins and what Anthropic routes requests through. Keeping the pin accurate avoids fallback silently rewriting what the orchestrator thinks it's running.

### Why this is `spec`, not `apply`

One reason, made of several parts:

1. **Routing table design decision.** The simplest pass (slug-swap only: `4.7 → 5-5`, `4.6 → 5-5`, `4.5 → 5-5`) is one `sed`. But Haiku 5.5's adjustable effort means the tier-boundaries are ripe to redraw — something `sed` can't do. A quick swap now locks in misalignment that's harder to unwind later.
2. **Project-init defaults ripple to every consumer repo.** `skills/project-init/SKILL.md` writes `.harness-profile` for every new project that installs this harness. A thoughtless bump re-pins everything downstream. A spec gets the migration-note shape right (what does an existing `.harness-profile` with `claude-opus-4-7` do? is it migrated silently? warned? left alone?).
3. **Effort-default re-derivation.** `effort_default` is derived from `stakes.level` with the mapping: `low → high`, `medium → xhigh`, `high → xhigh` (from `.harness-profile` comments + the 2026-04-19 spec). Opus 5.5 can't disable thinking. Does `effort_default: high` still make sense, or does `medium → high` collapse because thinking is always on now? That needs a spec pass.
4. **Run-loop reviewer backend.** `run-loop` already uses `anthropic-api:opus-4.8` (one step ahead of `.harness-profile`). The spec can either rationalize the two surfaces together or document why the review backend stays one minor version ahead.
5. **Receipt + docs trail.** Old `docs/specs/` and `docs/waves/` references to `haiku-4.5`/`sonnet-4.6`/`opus-4.7` are evidence of what the harness was configured as at the time. The spec needs to decide whether to touch them (probably not) and name an explicit boundary — "new receipts emit the new slugs; old ones stay as written."

### Concrete change (deferred — needs spec)

None this run. When/if the maintainer wants to take this on, the spec should cover:

1. New values for `.harness-profile`'s `primary` + `fallback` and the project-init defaults.
2. Routing-table redesign (12 task-shape rows in `.claude/agents/orchestrator.md:144–152`) — slug-swap plus any tier re-boundary moves given Haiku 5.5's new effort knob.
3. Escalation-chain update (`:247–248, 260, 382`) — same slug swap, plus decision on whether the chain still stops at `opus/xhigh` or whether `thinking always on` changes the top rung.
4. Effort-default mapping revisit (the 2026-04-19 spec on effort routing). The 2026-04-27 §1 (effort_default derivation to `xhigh`) is the current reference point.
5. Migration behavior for consumer `.harness-profile` files that still pin 4.x — warn, migrate on first write, or leave alone.
6. Receipt-schema note: new runs log the new slugs; historical receipts aren't rewritten.

### Expected payoff (when spec'd and built)

Routing decisions use a model-family-accurate view of cost/capability. Opus-tier tasks run on a model that's cheaper and faster for the same quality band. Haiku-tier tasks can take on a strictly larger task-shape set because the tier now has a cost-vs-intelligence dial. Downstream consumer projects that install from this harness pick up a current pin instead of a legacy one.

**Verify before applying:**
1. `grep -n "primary:\|fallback:" .harness-profile` — still shows `4-7` / `4-6`; if either slug has already moved, this § is partially stale.
2. `grep -n "haiku-4.5\|sonnet-4.6\|opus-4.7" .claude/agents/orchestrator.md | wc -l` — must be >0 today (the current count, as of this writing, is 10 hits across the table, escalation chain, and receipt example); if it's 0, the migration has started and this § is stale.
3. `grep -n "claude-opus-4-7\|claude-sonnet-4-6" skills/project-init/SKILL.md` — still shows 4.x defaults; if it already shows 5-5 slugs, the project-init update has landed.
4. Before quoting the "40% cheaper on typical workloads" and the "Haiku 5.5 adjustable effort is a first" facts in the spec, re-confirm on the linked Anthropic news pages — model-family posts sometimes get edited after launch.

**Recommended verdict:** spec — multi-file, touches orchestrator routing logic + effort-default derivation + project-init defaults + ripple-to-consumer-projects migration semantics. Low-risk slug-swap is tempting; doing it without a spec locks in Haiku-5.5-ignorant tier boundaries.
**Status:** PENDING — awaiting triage in PR review

## 3. One-line References note: the SKILL.md spec is now vendor-neutral at `agentskills.io` (Agentic AI Foundation)

**Source:** [Donating Agent Skills to the Agentic AI Foundation — Anthropic News, 2026-10-22](https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation). On Oct 22, Anthropic donated the Agent Skills open standard (the SKILL.md format, agentskills.io domain, the GitHub organization) to the Agentic AI Foundation under the Linux Foundation. Over 70 agent platforms have adopted the standard. **Nothing in the spec changes** — a skill is still a folder with a `SKILL.md` plus scripts and references — but the canonical home moved, and the maintainership shifted from Anthropic-only to "David Soria Parra + Mahesh Murag as Lead Maintainers, individuals from several companies as maintainers."

### Why it's relevant

This harness ships skills (26 of them under `skills/`), symlinked out to `~/.claude/skills/` on install. The skill-creator agent (`skills/skill-creator/`) reads a vendored snapshot of Anthropic's skill-authoring best practices at `skills/skill-creator/references/anthropic-skill-authoring.md`. The README's References section (`README.md:1109–1118`) links to `code.claude.com/docs/en/skills` as the Skill system reference.

With the donation, **the authoritative spec home moved from `platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices` to `agentskills.io`**. Nothing breaks — SKILL.md files remain compatible, the format is unchanged, Anthropic's docs still cover their own implementation — but a future-reader (or future-you) wondering "which URL is canonical for the spec itself" has no pointer in the repo today. Adding one line to `README.md`'s References section resolves that.

### Concrete change

**One bullet added to `README.md:1109–1118` (References section).** Insert after the existing "Skills" line (line 1115):

```diff
 - [Skills](https://code.claude.com/docs/en/skills) — Skill system reference
+- [agentskills.io](https://agentskills.io) — SKILL.md open standard, maintained by the Agentic AI Foundation (Linux Foundation) since [Anthropic's Oct 2026 donation](https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation). Format is unchanged; the harness's skills remain compatible.
 - [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) — "Start simple, add complexity only when needed"
```

Optional second touch (cheap, judgement call): add one sentence to `skills/skill-creator/references/anthropic-skill-authoring.md` noting that the canonical spec is now at `agentskills.io` and this file is a vendored snapshot of Anthropic's implementation guidance. The vendored file is explicitly a fork per `README.md:392`; the note tells future-maintainers where to pull updates from if they want to re-sync.

### Why this isn't a larger change

The donation ships no spec version, no schema migration, no deprecated fields. Engineers maintain the standard as individuals under the AAIF, not as a vendor group. Versioned releases are on the roadmap but unlanded. There is no action required of skill authors, so a one-line pointer is proportional — anything larger (e.g., a docs restructure around "which Anthropic doc governs which part of a skill") is manufacturing work that isn't there.

### Expected payoff

Future readers (and future-you six months on) have one pointer in the repo to the canonical spec home, which matters most when a divergent change lands in AAIF that hasn't rolled back into Anthropic's own docs. No behavior change.

**Verify before applying:**
1. `grep -n "agentskills.io\|Agentic AI Foundation\|AAIF" README.md` — must return nothing today; if it returns hits, the pointer is already there and this § is stale.
2. Confirm `agentskills.io` is still live and still the spec home (Linux Foundation sometimes consolidates donated projects under a shared umbrella URL); if the URL has moved, use the current one.
3. Check that `skills/skill-creator/references/anthropic-skill-authoring.md` still exists and is still the `references/` file name the skill-creator reads (it is, as of this writing, per `README.md:392`).

**Recommended verdict:** apply — one-line reference-section bullet. Low risk, concrete value, closes a documentation gap that exists today and widens over time as the AAIF standard evolves separately from Anthropic's product docs. The optional second touch is a judgement call.
