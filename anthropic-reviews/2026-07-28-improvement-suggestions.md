## 3. Add a "when to reach for the `Workflow` tool vs. `/run-loop`" note to README and `skills/run-loop/SKILL.md`

**Source:**
- [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (Thariq Shihipar + Sid Bidasaria). Anthropic productized *"dynamic workflows"* — Claude can now write its own harness on the fly as a JavaScript script that spawns subagents, assigns per-agent models, manages worktrees, and applies patterns like fan-out, classify-and-act, adversarial verification, and loop-until-done.
- [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) — the launch post.
- The `Workflow` tool schema (visible in this session's tool list) is Anthropic's implementation: it takes a self-contained script with `agent()`, `parallel()`, `pipeline()`, `phase()` primitives; runs deterministically in the background; returns a `runId` for resume.

### Why it's relevant
The harness has its own third execution lane — `/run-loop` (`skills/run-loop/SKILL.md`) — with a shared TypeScript engine at `skills/_shared/loop/`. Its purpose is *drain a work-source (plan.md waves or `ready-for-agent` gh issues) end-to-end behind a mechanical gate*. The `Workflow` tool's purpose is *express a one-shot orchestration pattern (fan-out, adversarial verify, pipeline) as JavaScript over N ephemeral subagents*. These solve different problems:

| Dimension | Harness `/run-loop` | Anthropic `Workflow` tool |
|---|---|---|
| Trigger | Operator drains a queue unattended | Claude authors one on the fly per task |
| State | Persisted receipts under `.harness-state/` | Journaled to a run dir, resumable |
| Gate | Mechanical (implement → exit gate → code-review → auto-fix → merge) | Author-defined pipeline stages |
| Cardinality | One item at a time (or bounded parallel) | Up to hundreds of parallel subagents per call |
| Failure mode | Bounded-retry, then park | Item drops to `null`, pipeline continues |
| Scope | Repo-level; stops when queue drains | Task-level; stops when script returns |

These are **complementary, not competing** — and today the harness's `run-loop` skill body says *"Name chosen over `/loop` — that is the Anthropic interval-scheduler built-in. `/run-loop` is consistent with `/run-wave`"* (an acknowledgement that Anthropic ships an interval scheduler). It does NOT acknowledge the `Workflow` tool, which is the closer conceptual overlap. The next time a maintainer (or future-you) asks *"is `/run-loop` redundant with the `Workflow` tool?"* the answer should be in the SKILL body.

This is exactly the same shape as 2026-05-10 §1 (documenting the local `code-reviewer` alongside Anthropic's `/ultrareview`), which landed cleanly as a one-paragraph docs edit.

## 5. Note Anthropic's "verification loops as skills" pattern as bookkeeping — harness already covers this via `code-reviewer` + `criteria/*.md`

**Source:** [Building verification loops in Claude Code with skills — claude.com/blog, ~2026-07-23](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) (Delba de Oliveira, Claude Code team). Anthropic recommends encoding manual checks (tests, linters, custom validations) as **skills** so every session applies the same verification loop automatically instead of relying on human memory.

### Why it's relevant (and why it defers)
The harness already implements verification loops — just through a different surface:

- `.claude/agents/code-reviewer.md` — adversarial reviewer that runs tests, checks types, and grades against project rubrics. Invoked synchronously by `/commit`.
- `criteria/*.md` — project-specific quality rubrics (code-architecture.md, data-integrity.md, frontend-ui-design.md, performance-accessibility.md, ux-user-flows.md). These are what `code-reviewer` scores against.
- `.claude/agents/ui-evaluator.md` — Playwright-based UI verification for web-app projects.

Anthropic's post argues for **verification as skills** (each verification pattern is its own SKILL.md with helper scripts). These are two implementations of the same abstract pattern.
