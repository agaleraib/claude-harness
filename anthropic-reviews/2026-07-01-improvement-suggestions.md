## 3. Reposition `/run-loop` and `/run-wave` against Anthropic's dynamic workflows / Workflow tool

**Source:**
- [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)
- [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (the deep-dive, by Thariq Shihipar + Sid Bidasaria, TS on Claude Code)
- [Orchestrate subagents at scale with dynamic workflows — code.claude.com docs](https://code.claude.com/docs/en/workflows)
- [Getting started with loops — claude.com/blog, 2026-06-30](https://claude.com/blog/getting-started-with-loops) (Anthropic's loop taxonomy — §4 below cites this from a docs angle)

### Why it's relevant

Anthropic just shipped a first-party primitive whose framing directly overlaps with this repo's tagline: **"A harness for every task"**. The `Workflow` tool lets Claude Code write a JavaScript orchestration script (`agent()`, `pipeline()`, `parallel()`) on the fly for a task the user describes, then a runtime executes it in the background — up to hundreds of parallel subagents per session, with an in-session judge / verify step and structured-output schemas.

That overlaps with **three** things the harness already does:

- **`/run-loop`** — drives ready-for-agent gh issues or plan.md waves end-to-end behind a mechanical gate, AFK. Cross-session, git-branch-scoped, PR-first for HITL.
- **`/run-wave`** — dispatches one wave of specs to sub-agents; `/close-wave` merges.
- **`orchestrator` agent** — the README's `## Multi-agent coordination` section (line 1080) pitches this as the harness's fan-out primitive.

**They are not the same layer.** Dynamic workflows are:
- **In-session** — the workflow completes inside one Claude Code session; there is no branch model, no cross-session pickup, no `ready-for-agent` labeling loop.
- **Model-authored** — Claude writes the JS; the human runs `ultracode` or asks for a workflow.
- **In-process parallelism** — `agent()` calls fan out to subagents that share the session's token budget and concurrency cap.
- **Verification-first-class** — every workflow ships with a judge/verify hook baked in.

`/run-loop` is:
- **Cross-session** — an AFK drainer that persists across days, driven by issue state and git merges.
- **Human-authored** — the maintainer wrote `run-loop-entry.ts` and its providers.
- **Runner-parametrized** — codex / claude / sandcastle / worktree as first-class boundaries.
- **Gate-first-class** — the `gate:` block in `.harness-profile` is the merge boundary.

But there IS a genuine reposition question. Three possibilities the maintainer should choose between (or blend):

**(a) Complement — keep both, name the split explicitly.**
The harness pitches `/run-loop` as the "outer AFK loop over an issue queue" and links to dynamic workflows as "the inner in-session fan-out you can use from inside a `/run-loop` implement step." The README's `## Multi-agent coordination` section (currently `orchestrator` + `generator/code-reviewer` + `ui-evaluator` + `project-tracker`) grows a fifth row: "Workflow (`ultracode`) → in-session parallel fan-out with baked-in verification." This is the low-risk path.

**(b) Delegate — have the `/run-loop` per-item implement step actually spawn a workflow.**
When a `ready-for-agent` issue is large enough (declared via issue label or descriptor field), the runner's implement step invokes a workflow rather than a single `codex exec` call. This gets the harness the "hundreds of parallel subagents + baked-in verify" story for free on the items that need it, but requires the `Workflow` tool to be reachable from whatever runner (codex / claude) does the implement. Non-trivial integration — codex today doesn't have `Workflow`; claude does. This is the interesting-but-risky path.

**(c) Step aside — reposition the harness as an AFK-drain wrapper, deprecate the `orchestrator` agent.**
If Anthropic's Workflow is the durable answer for in-session multi-agent, then the harness's `orchestrator` agent (README line 1083: "fans tasks out to sonnet/haiku in parallel") is a design that will keep drifting behind first-party. Retire it, keep `/run-loop` (still valuable — cross-session AFK is not a Workflow feature), and let consumers use `Workflow` directly for in-session fan-out. This is the maximally-honest path if the maintainer thinks first-party wins on in-session orchestration.

### Why this is `spec`, not `apply`

None of (a)/(b)/(c) is a single-file text edit. The right answer depends on:
- Whether the maintainer sees `/run-loop` as the harness's flagship or one skill among many.
- Whether `orchestrator` gets meaningful use in consumer projects today (`grep -rn "orchestrator" consumer-projects/` — the maintainer would know).
- The current maturity of `Workflow` on the runners `/run-loop` uses (codex vs claude).
- Whether cross-repo `/run-loop` semantics (git-branch-per-item, PR-for-HITL) are worth keeping distinct from an in-session model.

Per the routine's rubric, this is `spec` — needs a design pass via `/spec-planner` producing `docs/specs/2026-07-01-workflow-vs-run-loop.md` before any coding. The spec should decide (a) / (b) / (c) and either:
- Ship a README paragraph (path (a) — small);
- Ship a `Workflow`-invoking implement step for `/run-loop` (path (b) — a wave-sized change);
- Retire `orchestrator` and cite `Workflow` in its place (path (c) — a wave-sized deprecation + README rewrite of §Multi-agent coordination).

### Expected payoff (when the spec lands)
Consumer projects installing this harness know explicitly where the harness sits relative to first-party. The maintainer stops competing with a moving Anthropic surface for in-session orchestration; `/run-loop`'s cross-session AFK niche gets sharper.

1. `grep -rn "dynamic workflow\|ultracode\|Workflow(" /home/user/claude-harness --include="*.md"` — today (2026-07-01) returns zero hits. If it returns hits, the reposition has already started and this § should be re-scoped.

**Recommended verdict:** spec — this is the kind of question that will get expensive if resolved by drift; a one-shot `/spec-planner` pass is the right rung. Once the spec lands, the resulting wave item can be `/run-wave`'d normally.
