## 3. Bookmark Anthropic's 6-step large-scale code-migration methodology (skill-cross-reference or References-list entry)

**Source:** [How Anthropic runs large-scale code migrations with Claude Code — claude.com/blog, 2026-07-16](https://claude.com/blog/ai-code-migration). Anecdotes: Jarred Sumner (Bun co-founder) migrated Bun from Zig to Rust — ~1M lines in <2 weeks, 100% of the existing test suite passing before merge. Mike Krieger migrated 165K lines from Python → TypeScript over one weekend at ~$165K API spend.

### Why it's relevant

The post distills a repeatable 6-step methodology that generalizes beyond Bun/Krieger:

1. **Rulebook + dependency map** — capture idioms/APIs to preserve; graph the module ownership.
2. **Gap inventory** — list what the target language/framework can't do 1:1, decide upfront.
3. **Stress-test mini-migration** — port one representative module end-to-end before scaling.
4. **Parallel translation with smaller models** — fan out per-file translations to Sonnet/Haiku.
5. **Compiler/smoke-test fix loops** — treat the compiler as the arbiter; iterate.
6. **Final parity verification** — original test suite passes on migrated code.

Two takeaways matter more than the checklist itself, per the post's own framing: "**fix the process that produces the code, not the generated code**" (this maps to how the harness's `/commit` + `code-reviewer` loop already works) and "**configure CLAUDE.md project rules and deterministic hooks for safety-critical actions**" (this maps to the harness's `.claude/hooks/` + AGENTS.md machinery).

Today the harness has:
- **`skills/migration-check/SKILL.md`** — narrowly scoped to *database schema* migrations (concurrent-writes safety, backfill strategy, reversibility). Nothing about code migrations. `grep -rn "code migration\|Zig to Rust\|Bun\|Python to TypeScript\|large-scale migration"` returns zero non-tracker hits (verified this run).
- **No `/code-migration` skill or reference doc.**
- **No entry in `README.md:1109-1118` References list** pointing at the migration methodology.

### Why this is `defer`, not `apply` or `spec`

1. **Solo tooling repo with no active large-scale migration.** The harness itself is Markdown + bash — no code to migrate. Consumer projects that install via `setup-harness` are the theoretical beneficiaries, but no one has raised a migration ask.
2. **A skill isn't the right unit yet.** Anthropic's post is a case study, not a mechanized procedure. The 6-step framework is *high-freedom* (prose steps) in `skill-creator`'s taxonomy (see `skills/skill-creator/references/anthropic-skill-authoring.md:32-36`) — the kind of guidance a `SKILL.md` body dilutes rather than concentrates.
3. **The `/spec-planner` cost isn't earned.** No consumer project has produced the "we tried this migration and X went wrong" evidence a spec should be grounded in.
4. **A one-line bookmark is cheap; a full skill is speculative.** The Recommended verdict rubric ("apply / defer / reject / spec") has no cost bar between `defer` and `bookmark-only`, so `defer` is the honest call.
