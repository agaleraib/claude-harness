## 2. Document Claude Code `--safe-mode` (v2.1.169) as the harness's canonical "reset" path

**Source:** [Claude Code Changelog v2.1.169 — 2026-06-08](https://code.claude.com/docs/en/changelog). Third-party confirmation ([digitalapplied.com](https://www.digitalapplied.com/blog/claude-code-safe-mode-fallback-models-production-resilience-guide)): "`--safe-mode` flag (and `CLAUDE_CODE_SAFE_MODE` environment variable) to start Claude Code with all customizations (CLAUDE.md, plugins, skills, hooks, MCP servers) disabled for troubleshooting."

### Why it's relevant

The harness's whole value proposition is *added customization* — 25 skills, 6 agents, `.claude/settings.json` hooks (currently empty but designed to grow), symlinks from `skills/` to `~/.claude/skills/`. When the maintainer's own additions misbehave — a broken hook, a shadowed skill name, a symlink that points to the wrong place — the debug loop today is:

1. Guess which customization is at fault.
2. Manually disable pieces (`mv ~/.claude/skills/foo ~/.claude/skills/foo.bak`) until the session boots cleanly.
3. Re-enable one at a time.

`--safe-mode` collapses steps 1–2 to a single flag. This is **exactly** the reset the solo maintainer wants — plus the `CLAUDE_CODE_SAFE_MODE` env var means it can be scripted for CI or a one-off test.

The harness has **zero documentation** on this today (`grep -rn "safe.mode\|SAFE_MODE\|disableBundledSkills" .` returns nothing). It's absent from:
- `skills/setup-harness/SKILL.md` — no troubleshooting section exists at all
- `README.md` "How to manage sessions" (`README.md:852+`) — talks about `/effort`, `/model`, `/tokens` but not `--safe-mode`
- `AGENTS.md` — no troubleshooting or reset guidance

### Concrete change

**2a. `README.md`** — add a short "Troubleshooting the harness itself" subsection near the existing "How to manage sessions" block (`README.md:852+`), roughly:

```md
### If the harness itself is misbehaving

When a hook, skill, or MCP server you added starts misfiring — sessions won't start,
a skill loads the wrong file, a hook fails silently — bypass every customization
in one flag:

```bash
claude --safe-mode
# or set the env var for a scripted run:
CLAUDE_CODE_SAFE_MODE=1 claude
```

`--safe-mode` (v2.1.169+, 2026-06-08) disables **CLAUDE.md, plugins, skills, hooks,
MCP servers** — everything the harness installs, plus everything else. Use it to
confirm the issue is a harness customization vs. a Claude Code bug, then re-enable
piece-by-piece by inspecting `~/.claude/skills/` symlinks and `.claude/settings.json`
hook matchers. For a narrower reset that leaves plugins on and only hides bundled
skills, use `disableBundledSkills` in `.claude/settings.json`.
```

**2b. `skills/setup-harness/SKILL.md`** — add a one-line pointer near the bottom, under a "Troubleshooting" heading:

```md
## Troubleshooting

If a fresh install of the harness misbehaves — session-start hook fails, a skill
overrides an expected slash command, `harness-status` reads the wrong registry —
run `claude --safe-mode` (or `CLAUDE_CODE_SAFE_MODE=1 claude`) to bypass all
customizations at once, then re-enable piece by piece. See README §"If the harness
itself is misbehaving" for the full flow.
```

### Expected payoff

Solo maintainer benefit is direct: next time an added hook eats a session or a skill collides with a built-in slash command, the reset is one flag away instead of a manual bisect. Two-place doc addition (~15 total lines) that pays off the first time it's needed.

### Why not skip and rely on the Claude Code docs?

Because the harness's whole reason for existing is to be the layer *between* the user and Claude Code. When Claude Code ships a "disable my layer" escape hatch, the harness docs should point at it — otherwise the solo maintainer, three months in, has to remember it exists.

**Verify before applying:**
1. `grep -rn "safe.mode\|SAFE_MODE\|disableBundledSkills\|--safe-mode" /home/user/claude-harness` — must return zero hits today. If any hit, the guidance is already in place and this § is stale.

3. Confirm the `CLAUDE_CODE_SAFE_MODE` env var still works (equivalence with the flag) — was reported in v2.1.169 but env-var names occasionally get retired in favor of settings.

**Recommended verdict:** apply — pure documentation edit; ~15 lines split across README + setup-harness; addresses a real solo-maintainer pain point that recurs; no behavioral change. Cheap to add, painful to be without when you need it.

## 5. Adopt `allowed-tools` YAML frontmatter on read-only skills

**Source:** Same cluster as §4:
- [Steering Claude Code: skills, hooks, rules, subagents and more](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more) — enumerates SKILL.md frontmatter fields: `name`, `description`, `disable-model-invocation`, `allowed-tools`.
- [How and when to use subagents in Claude Code](https://claude.com/blog/subagents-in-claude-code) — subagent frontmatter parallels: `name`, `description`, `model`, `tool access`.

### Why it's relevant

Every SKILL.md in the harness today uses only `name` + `description` (+ `argument-hint` on a few). None use `allowed-tools`. The Steering post lists `allowed-tools` as a frontmatter field that constrains which tools the skill's session can invoke — a lightweight guarantee that a skill can't accidentally reach for a tool outside its purpose.

**Read-only skills** in the harness where `allowed-tools` would make sense:

| Skill | Purpose | Suggested `allowed-tools` |
|-------|---------|---------------------------|
| `harness-status` | Cross-repo state scan | `Read, Grep, Glob, Bash(git status:*), Bash(git log:*)` |
| `memory-prune` | Review + promote memory files | `Read, Grep, Glob, Bash(mv:*), Bash(git status:*)` |
| `park` | Append to `parking_lot.md` | `Read, Edit, Bash(git status:*)` |

Non-read-only skills (`commit`, `run-wave`, `close-wave`, `micro`, `session-end`) would need `Bash, Edit, Write, Read` plus subagent access — `allowed-tools` for them likely lists most of the tool set, which is no meaningful narrowing.

### Why this is `defer`, not `apply`

1. **No permission-review request today.** The maintainer is solo; there's no audit or compliance pressure to constrain skill tool surfaces. Adding `allowed-tools` is defensible engineering hygiene, not a needed guardrail.
2. **Session-level permissions already do the coarse-grained work.** Claude Code's permission prompts + `.claude/settings.json` allowlist handle "should Claude Bash rm -rf?" at the session level. `allowed-tools` on a skill is a *narrower* control that only pays off if a skill actively wants to guarantee non-modification.
3. **Speculative for solo tooling.** Per the routine's rubric, "speculative for solo tooling" is a defer indicator, not a reject indicator — flag it, don't kill it.
4. **Frontmatter drift risk.** Adding `allowed-tools` on 3 skills creates a precedent — if it's not enforced on new skills, future ones will forget, and the field becomes lore. Better to add it once a policy exists.

### Concrete change (deferred)

When/if the maintainer wants this:
