## 4. Consider Claude Code's built-in Workflow tool (dynamic workflows) as the fan-out primitive for `/run-wave` orchestrator dispatch

**Sources:**
- [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) — Claude Code ships a `Workflow` tool that executes JavaScript orchestrating multiple subagents in parallel, each in its own worktree, with per-agent model routing (Sonnet vs Opus). Trigger word: "ultracode". Orchestrator-workers pattern in the runtime, not in a manually-authored SKILL.
- [Loop engineering: Getting started with loops — claude.com/blog, ~2026-06](https://claude.com/blog/getting-started-with-loops) — companion piece framing loops (manual / scheduled / background) as the top-level abstraction and Workflow as the fan-out primitive underneath.
- [Building agents with the Claude Agent SDK — claude.com/blog](https://claude.com/blog/building-agents-with-the-claude-agent-sdk) — the same subagent + orchestrator machinery exposed as a Python/TypeScript SDK.

### Why it's relevant

The harness has an `orchestrator` agent (`.claude/agents/orchestrator.md`) that dispatches wave tasks to opus/sonnet/haiku subagents with model routing. It also has `/run-wave` (batch orchestrator) and `/run-loop` (streaming orchestrator with mechanical gate). Both currently dispatch **sequentially** with model routing decided per task; there is no native fan-out primitive.

Anthropic's `Workflow` tool (documented in this session's own tool schema and in the June 2 post) provides exactly the fan-out shape the harness might otherwise have to build: JavaScript orchestrating N subagents in parallel worktrees with per-agent model choice. The `orchestrator` agent could, in principle, hand off to the `Workflow` tool for tasks that fan out (e.g., adversarial multi-reviewer sweeps, multi-file refactor batches, spec fan-out where 4 phases can run in parallel).

**But** — this is architectural. It would:

- Change the orchestrator's contract from "sequential dispatch with routing" to "sequential OR fan-out via Workflow, with a heuristic".
- Interact with the `run-loop` mechanical gate (a Workflow-tool run is itself an item; how does its verify gate compose with `runLoop`?).
- Interact with the receipt schema (a Workflow run emits N sub-agent results — do they each get a receipt, or one aggregate?).
- Interact with the "ultracode" opt-in gate the Workflow tool honors (the harness's system prompt says to only invoke Workflow when the user explicitly opted in; the orchestrator invoking it under the hood would be a policy decision).

None of these are blockers, but none are simple. And the harness's current sequential dispatch **works** — solo maintainer, single-track repo, no evidence yet that fan-out is a bottleneck.

### Concrete change

**Not now.** The right shape is:

1. Do NOT change any code today.
2. Add a **one-line placeholder in `parking_lot.md`** naming this as a candidate:

   ```diff
   +- Dynamic workflows / Claude Code `Workflow` tool as fan-out primitive inside `orchestrator` agent
   +  (paired with the mechanical-gate composition question in `/run-loop`). See
   +  anthropic-reviews/2026-08-31-improvement-suggestions.md §4. Spec before building.
   ```

3. If/when concrete evidence of fan-out pain surfaces (e.g., a wave that spawns 6+ parallel-safe tasks and blocks the maintainer for hours on sequential dispatch), promote to `/spec-planner` and produce `docs/specs/YYYY-MM-DD-workflow-tool-orchestrator.md`.

### Expected payoff — deliberately deferred

The payoff would be real if the harness ever runs many-way-parallel wave tasks — but today it doesn't, and premature adoption would either (a) reverse the "don't add features beyond what the task requires" principle from CLAUDE.md's own default, or (b) leak a Workflow-tool policy decision into the orchestrator without the "ultracode" opt-in gate the maintainer holds today. Sits in the parking lot until real pain shows up.

If it returns hits, the parking-lot placeholder has already been added or the orchestrator has already been reshaped.

Park in `parking_lot.md`; do not spec until the pain is real.
