## 3. Revisit the `stakes.level → effort_default` derivation now that Opus 5.5 defaults to Medium

**Source:** [Introducing Claude Opus 5.5 — anthropic.com, 2026-09-22](https://www.anthropic.com/claude-opus-5-5) ("Default effort is medium. Benchmarks also reference max and xhigh effort levels"). Pairs with [the 2026-04-23 postmortem](https://www.anthropic.com/engineering/april-23-postmortem) that drove the harness's original `xhigh` choice.

### Why it's relevant
The harness's current derivation table (`.harness-profile:21–25`) is:

```
stakes.level: low    → effort_default: high
stakes.level: medium → effort_default: xhigh
stakes.level: high   → effort_default: xhigh
```

That table was derived in the Opus 4.7 era, with explicit citation of the April 23 postmortem: Claude Code product-defaulted Opus 4.7 to xHigh for Pro / Max users, and the harness followed Anthropic's product default rather than inventing its own. With Opus 5.5 (Sep 22), **Anthropic's product default drops to Medium**. Three defensible reads:

1. **Follow the product default** → derivation collapses to Medium for everything, treat stakes as a knob rather than a tier mapping, trust that Opus 5.5-at-Medium is comparable in quality to Opus 4.7-at-xHigh (which the Opus 5.5 announcement implies but doesn't prove at harness-task shape).
2. **Keep xHigh for medium/high stakes** → defends the current table on the grounds that this harness is central-methodology code where errors propagate (`stakes.why` in `.harness-profile:19` already says so), and the Medium default is Anthropic's *product* default for the broad population, not a methodology-code-at-stakes default.
3. **Hybrid: lower medium-stakes to High, keep xHigh only for high stakes** → split-the-difference position that acknowledges Opus 5.5 is more capable at Medium than 4.7 was.

None of these is obviously right without data. The question has three loose ends:
- No shipped benchmark compares Opus 5.5-Medium against Opus 4.7-xHigh on harness-shaped tasks (methodology edits, review runs, planning rounds).
- The 2026-04-23 postmortem evidence (xHigh correlates with quality) was Opus-4.7-era and may not transfer.
- The harness currently uses `effort_default` as a single input to the orchestrator's dispatch; a derivation-table rewrite ripples through `/project-init` and `/orchestrator`'s dispatch logic in ways that need naming before coding.

This is a **design question**, not a code change. The sensible move is a spec — hence the `spec` verdict rather than `apply`.

### Concrete change
A spec at `docs/specs/2026-10-28-effort-default-at-opus-5-5-generation.md` with:
- One-paragraph problem statement (current derivation + Opus 5.5 default shift).
- Three candidate derivations (see above) as decision rows.
- An evaluation plan: run one representative harness task (e.g. a planning-loop pass on a parked suggestion) under each of the three candidates and capture completion-time, cost, and `/code-review`-caught issue count.
- A fourth candidate: *leave the derivation unchanged and add an override-reminder to `/project-init` so target projects can opt into Medium*; this is the least-disruptive option and may be the right initial state.

The spec doesn't block §1 and §2 — Opus 5.5 can be pinned as the primary model with the `xhigh` default retained; `effort_default` is independent of `model.primary` by design.

### Expected payoff
- Keeps the harness's effort-routing claims **evidence-based** rather than drifting with product defaults.
- Captures the Opus 4.7 → Opus 5.5 transition explicitly in a durable spec, so future generation transitions have a template.
- May lower per-task cost materially if candidate (1) wins; may harden quality claims if candidate (2) wins.

**Scope: speculative** — the ROI depends on an eval that doesn't exist yet. Flagged so a reviewer explicitly green-lights the spec effort before coding.

**Verify before applying:**
1. `grep -n "stakes.level" .harness-profile` must still return the derivation table on lines 21–25; if the table has already been refactored into an external file this § is partially stale.
2. `grep -rn "effort_default" skills/project-init/ skills/orchestrator/ .claude/agents/orchestrator.md` — if the derivation is already consumed in >1 place, the spec should enumerate every call site.
3. Confirm Opus 5.5's Medium default has not shifted (e.g. to High) in a subsequent minor release — re-check `anthropic.com/claude-opus-5-5` at spec time.

**Recommended verdict:** spec — the right path is "name the decision, enumerate the options, run one small eval," not "pick one and ship." Low-cost speculative work; worthwhile precisely because the April 23 postmortem evidence was Opus-4.7-era and shouldn't be assumed to transfer.
**Status:** PENDING — awaiting triage in PR review

## 6. Build end-to-end evals before deciding whether to fold the harness's subagents into one loop

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com/resources, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop).

### Why it's relevant
Anthropic's first-party, concrete guidance on **when subagents help vs. when they hurt**:

> *Keep a subagent separate when at least one of these holds: a single loop shows measurable quality degradation from context bloat; tasks run in parallel and benefit from fresh context windows that can be discarded afterward; the agent struggles to select the right tool, or the system prompt contains conflicting instructions. Otherwise, favor folding it into the main loop as skills and tools.*

The harness has **6 defined subagents** (`.claude/agents/`: `code-reviewer`, `generator`, `orchestrator`, `project-tracker`, `spec-planner`, `ui-evaluator`) plus the built-in Claude Code `Explore` and `Plan`. None has ever been eval-validated against a *single-loop* baseline that uses skills + tools instead of a subagent handoff. Three of the six (`generator`, `project-tracker`, `ui-evaluator`) are each used from exactly one place in the methodology, which is the strongest signal in the Anthropic post that they *may* be fold candidates.

**Nothing in the post says "fold them."** It says "run the eval and decide per subagent." That's the suggestion.

Also noted but not actioned: the post recommends a "subagents as tools" intermediate step with a shared response schema, which the harness already partially does via the `code-reviewer` agent's `ReportFindings` tool call shape. The harness is ahead of the post on this specific pattern.

### Concrete change
A spec at `docs/specs/2026-10-28-subagent-eval-plan.md` with:

- One-paragraph framing: Anthropic's three "keep separate" criteria; the harness's 6 current subagents; the shape of a per-subagent eval.
- A minimal eval: ~10 golden examples per subagent (per Anthropic's "even about 10 golden examples can start it" guidance), each grading **final answer** quality rather than intermediate behavior.
- A proposed order: start with the three single-caller subagents (`generator`, `project-tracker`, `ui-evaluator`) — their fold decision is cleanest because there's no multi-caller surface to worry about.
- A deliberately-outside-scope marker: `code-reviewer`, `orchestrator`, `spec-planner` are the "many callers / high stakes" subagents and should wait until the first three are done.
- Explicit decision rule: a subagent folds only if the single-loop version matches or beats on the eval. Default to keep-separate; folding is the migration cost, not the status quo.

The spec doesn't need to decide ahead of running the eval — it needs to **name** the decision so the eval has a target.

### Expected payoff
- **Methodology integrity:** the harness's subagent architecture becomes evidence-anchored rather than inherited from Opus-4.0-era patterns.
- **Possible context savings:** folded subagents can share one prompt-cache prefix (which the 2026-05-01 "Prompt caching is everything" post identified as the single biggest Claude Code performance lever).
- **Durable framework for future subagents:** every new subagent proposal (there have been three in the last six months) can be routed through the same eval gate.

**Scope: speculative** — the actual eval work (10 golden examples × 6 subagents) is not free, and the outcome may be "keep everything as-is." Flagged so a reviewer explicitly green-lights the spec effort.

**Verify before applying:**
1. `ls .claude/agents/` — confirm the current subagent count (should be 6: `code-reviewer`, `generator`, `orchestrator`, `project-tracker`, `spec-planner`, `ui-evaluator`). If a 7th has shipped or one has been removed, the spec should enumerate the new set.
2. `grep -l "project-tracker\|generator\|ui-evaluator" skills/*/SKILL.md` — confirm these three really are called from only one place; if not, promote the called-from-multiple ones out of the "safe to fold first" group.
3. `grep -rn "golden examples\|subagent eval\|fold subagents" docs/specs/ docs/waves/` — must return no prior spec on the same question; if one exists this § is stale.

**Recommended verdict:** spec — this is the first first-party Anthropic post with concrete architectural guidance on subagent granularity. Spending one spec-planner pass on it defends every future subagent decision with evidence instead of intuition.
**Status:** PENDING — awaiting triage in PR review

## 7. Claude Code mods as a parallel extension layer alongside the harness's current hooks

**Source:** [Customize Claude Code with mods — claude.com/resources, 2026-10-01](https://claude.com/resources/articles/claude-code-mods). The `claude.dev/blog/getting-started-with-claude-code-mods/` companion post was not reachable from this session's network allowlist (ENOTFOUND claude.dev); content below is from the resources mirror only.

### Why it's relevant
Mods are a **new TypeScript extension layer** above hooks. Where hooks can observe and react, mods can:
- Rewrite prompts before the model sees them.
- Replace built-in features (e.g. the `/diff` command is now itself a mod).
- Redact tool output before it enters model context.
- Add UI (terminal + desktop app) — buttons, inputs, panes.
- Stack by load order (`sec-default` first, admin, user).

Mods ship inside **plugins** (same packaging as everything else), aren't sandboxed, and require trusted sources.

**Harness today:** the harness's extension-layer story is the global git-hook dispatcher that shipped in commit `5130b9d` (secret scan, mass-delete block, profile gate — PreToolUse hooks). That's a hook-shaped problem (observe & reject), and hooks are the right tool. There's nothing in the harness today that:
- Needs to rewrite a prompt.
- Needs to replace a built-in command.
- Needs to draw UI.
- Needs to redact tool output before it enters the model.

So "port the hooks to mods" is a non-starter — nothing is wrong with the hooks. The real question is whether **a future piece of harness work** will bump a hook-shaped ceiling where only a mod can help. Candidates to watch:
- A hook that wants to redact secrets from tool output *before* the model reads them (currently hooks run after). This is the single clearest mod-shaped use case.
- A UI pane for `.harness-state/today_goal.md` live view (currently requires reading the file manually).
