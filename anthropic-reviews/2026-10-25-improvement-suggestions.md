## 2. Audit the `orchestrator` + opus/sonnet/haiku subagent-dispatch pattern against Anthropic's "when to fold subagents" guidance

**Source:** [Building agents: When to fold subagents into your main agent loop — Claude Platform, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

**Context.** The harness has shipped an explicit orchestrator-worker pattern since Wave 1 (`.claude/agents/orchestrator.md`, 386 lines; `model: opus`; routes each spec task to opus / sonnet / haiku subagents based on complexity, following `Anthropic's orchestrator-worker pattern: "a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results."`). That citation points to Anthropic's **June 2025 multi-agent-research-system** post — a system where parallel information gathering had a clear win. The Oct 22 post is the **first first-party Claude Platform engineering piece that explicitly argues the opposite direction for most agentic coding workloads**:

> *"a single agent with skills frequently outperformed … a subagent design"* on quality, cost, and latency — with one customer seeing *"roughly 2x faster runtime with a single agent loop than with its multi-agent harness."*

### Why it's relevant

The post names concrete failure modes the harness's current pattern could exhibit:

1. **Subagent sprawl** — "a copy of their org chart"; the harness's three-tier dispatch (opus/sonnet/haiku) is bounded, but any new agent (ui-evaluator, generator, project-tracker, spec-planner) effectively adds another "specialist."
2. **Frankenprompt** — merging many sub-prompts into one brittle super-prompt. Not currently present in the harness, but a risk if §1c (model-5-5 effort knobs) adds dispatch complexity.
3. **Lossy context handoff** — subagents compress their results back to the orchestrator in prose; details are lost, and over-aggressive compression hides which turn/tool caused what. The harness's current Surface A log line `→ <task_id> → ...` captures routing but not the pre-compression subagent context.
4. **Latency** — serial dispatch of subagents is strictly slower than a single loop with the same tool calls. The 2× figure in the post is one data point.
5. **Overly localized evals** — each subagent is evaluated against its own rubric; nobody owns the end-to-end quality number. The harness's `evaluator.md` is one layer; whether it grades the full chain or just the leaf agent is worth checking.

The post offers a four-step **migration recipe** to fold subagents back into the main loop:
1. "Build evals first" — "even a set of 10 golden examples is enough to start." (The harness's deferred 2026-04-19 §5 — "Formalize evals for the adversarial reviewers" — is still DEFERRED. This recipe makes the eval blocker explicit *as a prerequisite for this audit*, which stacks the design justification.)
2. Merge tightly coupled specialists first.
3. Call surviving subagents as tools (not as separate agents) to establish a baseline.
4. Fold one subagent at a time; "convert prompts to skills, API calls to MCP tools"; measure which individual tasks flipped (not just the aggregate).

Operating principle the post closes on: *"measure, change one thing at a time, and keep what holds up."*

### Why this is `spec`, not `apply`

Three reasons:

1. **Touches live mechanism.** The orchestrator and its five sibling agents (`.claude/agents/*.md`) are the harness's load-bearing surface. A re-shape without an eval baseline is exactly the Frankenprompt / lossy-handoff hazard the post warns against.
2. **The eval prerequisite is still deferred.** 2026-04-19 §5 (`Status: DEFERRED`) is the prerequisite the Oct 22 post also names. Spec'ing the audit forces the eval question onto the plan rather than past it.
3. **The architectural question is open.** The harness's orchestrator-worker citation is to a system (multi-agent research) where parallel info gathering is the dominant work. For most of the harness's actual workloads (spec implementation, review, commits), that justification is weaker. Resolving this is a design-level decision, not a `/micro`.

### Concrete change (spec contents to specify)

A `/spec-planner` pass should produce `docs/specs/2026-10-25-orchestrator-fold-audit.md` covering:

- **Inventory.** List the six `.claude/agents/*.md` and their actual invocation surfaces (grep callers; some may already be invoked via the Agent tool with `subagent_type:` from a parent session, which is a different pattern than orchestrator-worker).
- **Pattern classification per agent.** For each, is it (a) parallel info-gather (keep as subagent), (b) sequential specialist (fold candidate), (c) context-isolation only (fold candidate — becomes a skill the main loop reads on demand), or (d) truly separate audience (e.g. `project-tracker` writes to Second Brain — likely stays)?
- **Eval baseline design.** The 10-golden-examples minimum. Likely: five successful waves + five hard failures from `docs/waves/`. Each example graded on (i) correct terminal output, (ii) correct files touched, (iii) was the right skill used?
- **Fold candidates in priority order** — with "fold" vs "keep subagent" vs "promote to skill" verdicts.
- **Measurement plan** — latency delta and token-cost delta on the eval set, pre/post fold.
- **Rollback.** The current orchestrator stays versioned under `.claude/agents/orchestrator.md`; the fold experiment ships behind a `.harness-profile` toggle so a bad baseline can be reverted without a git revert.

### Expected payoff

If the audit concludes "most subagents should fold":
- Fewer agent definitions to maintain (currently 6, likely 2–3 after fold).
- Faster per-task completion (Anthropic reports ~2× for one customer).
- Cleaner evals (one end-to-end rubric, not per-agent rubrics).
- Simpler model-5-5 effort routing (§1c becomes easier — one knob, not per-agent knobs).

If the audit concludes "keep subagents":
- First-party evidence (recorded in the spec) that the orchestrator pattern earns its keep for the harness's actual workloads — closes a design question that will otherwise be re-raised every quarter.

1. `grep -c "^use the orchestrator" docs/plan.md .harness-state/*.md 2>/dev/null` — if the orchestrator is used in less than ~5 live wave entries, the "live mechanism" claim weakens and this § may deflate to a defer.
2. `wc -l .claude/agents/*.md` — the raw size (orchestrator.md is 386 lines) is a signal that any re-shape is non-trivial. If sizes have shrunk since this file was written, the fold may already be in motion.

**Recommended verdict:** spec — needs `/spec-planner` first because the audit touches live orchestrator mechanism and depends on an eval baseline that is itself still deferred. Spec'ing it forces that dependency onto the plan.

**Context.** The harness is skills-first (`skills/` is the source of truth, symlinked out to `~/.claude/skills/` per `CLAUDE.md` "Skills directory layout"). The `AGENTS.md` + `README.md` guidance treats Agent Skills as an Anthropic standard. As of Oct 22 that is no longer strictly correct:

> *"Anthropic is donating the Agent Skills open standard to the Agentic AI Foundation (AAIF), which sits under the Linux Foundation. The donation includes the Agent Skills name and logo, the GitHub organization, and the agentskills.io domain."* — maintainers are now Anthropic + Google + OpenAI engineers acting as individuals.

### Why it's relevant

Two durable facts:

1. **No format breakage today.** The release post explicitly says the core format is unchanged — *"a skill is a folder containing a SKILL.md file, plus any scripts or reference material it needs."* The harness's current `skills/<name>/SKILL.md` layout is still spec-compliant.
2. **Future spec work is now out of Anthropic's unilateral control.** The AAIF roadmap proposes versioned releases, a formal proposal process, and security guidance for skill writers. Any one of those could land conventions the harness would need to track (e.g. a `version:` frontmatter field, a `security.sandbox:` block).

### Why this is `defer`, not `apply`

Nothing to do today. No breaking change announced; the proposed roadmap is proposals, not shipped. The right time to re-open is when AAIF publishes a v1 spec with concrete additions to `SKILL.md`.

### Concrete change (deferred)

When AAIF publishes a numbered spec:

1. Diff the AAIF spec against the current `skills/*/SKILL.md` conventions in the harness; identify delta.
2. If the delta is small (new optional frontmatter field, no breakage), apply via `/micro` to the handful of SKILL.md files that need it.
3. If the delta is substantive (new validation step at skill-load time, new directory layout), spec via `/spec-planner`.
4. Update `AGENTS.md` to cite AAIF as the standard's steward instead of Anthropic.

Optional cosmetic today (small enough to roll into a `/micro`, not blocking):
