## 4. Configure the Claude Code sandboxed Bash tool in `setup-harness` / `.claude/settings.json`

**Source:**
- [Making Claude Code more secure and autonomous with sandboxing — anthropic.com/engineering](https://www.anthropic.com/engineering/claude-code-sandboxing) — Claude Code now ships **filesystem isolation** (Claude can only access/modify specific directories) and **network isolation** (Claude can only connect to approved servers), built on Linux `bubblewrap` and macOS Seatbelt. Internal data: sandboxing reduces permission prompts by **84%**. Anthropic open-sourced the feature.
- [How we contain Claude across products — anthropic.com/engineering (2026-05-25)](https://www.anthropic.com/engineering/how-we-contain-claude) — Engineering principles for containment across Claude.ai / Claude Code / Cowork. Discusses the prompt-injection landscape (a Feb 2026 red-team exercise succeeded 24/25 retries at exfiltrating AWS creds from a phished Claude Code session).

### Why it's relevant

The harness's existing safety primitive is a **`PreToolUse` denylist** the operator installs in `~/.claude/settings.json` (see `CLAUDE.md` "Loop protocol" section + `skills/_shared/loop/safety/denylist.ts`). That denylist works by **rejecting** dangerous commands. Anthropic's new sandboxing primitives work by **allowing** safe commands inside a restricted execution boundary, which means a sandboxed Bash invocation can run without a permission prompt at all.

The two are **complementary, not competing**: the denylist catches catastrophic commands that should never run; the sandbox lets common commands (test runners, type checkers, formatters) run without prompting because they can't reach outside the allowed filesystem/network zones. Adopting both reduces UX friction without trading off safety.

The relevant harness surfaces:

- `skills/setup-harness/SKILL.md` — onboarding for new consumer projects.
- `.claude/settings.json` — the harness's settings file (per-repo).
- `~/.claude/settings.json` — operator-global settings; outside the harness's commit surface.

The skill body in `skills/run-loop/SKILL.md:44` already notes *"global settings (the Codex default lane relies on its native sandbox and needs no hook)"* — sandboxing is already on the radar but not for the Claude Code default lane.

### Concrete change (deferred)

None this run. When/if the maintainer wants to take this on:

1. Read `https://code.claude.com/docs/en/sandboxing` for the current setting names and accepted permissions schema.
2. Decide policy: **default-on sandboxing for new consumer projects** (`setup-harness` writes `.claude/settings.json` with a `permissions.defaultMode: "sandboxed"` block) vs. **opt-in via `.harness-profile` flag** (less aggressive; respects projects with custom permission setups).
3. Confirm the sandbox boundary list (allowed read paths, allowed write paths, allowed network hosts) matches the harness's typical work pattern — at minimum: project root read+write, `~/.cache/` write, `git*.com` / `npmjs.com` / `pypi.org` / Anthropic API hosts for outbound network.
4. Compose: `PreToolUse` denylist runs **first** (hooks-run-first ordering per the 2026-05-08 Auto Mode engineering post, already documented in this routine's tracker); sandbox runs second to silence the permission prompts for everything the denylist hasn't rejected.
5. Document in `setup-harness/SKILL.md` how to opt-out if the maintainer of a consumer project doesn't want sandboxing.

### Why this is `defer`, not `apply`

1. **Permission prompt fatigue is not currently a documented pain point** for the harness or its consumer projects. The denylist + Claude Code's existing prompt flow is the status quo; without evidence the maintainer is being interrupted excessively, applying sandbox config is speculation.

### Expected payoff (when applied)

**Verify before applying:**
