## 3. Audit the 25 harness skills against Anthropic's "single-category" heuristic

**Source:** [Lessons from building Claude Code: How we use skills — claude.com/blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills)

### Why it's relevant
The post lands two claims from Anthropic's internal skill catalog:

1. **After cataloging all internal skills, Anthropic found they cluster into nine categories** — and "the best skills fit cleanly into one category, while those that try to do too much confuse the agent."
2. **Skills are folders, not files** — scripts, assets, references, and evals belong in the folder; a "just markdown" skill misses the primary discoverability signal.

The harness already ships **25 skills** (per `ls skills/ | wc -l`) that are folders-with-lib-and-refs — claim #2 is already lived. But claim #1 has never been audited against the harness. Several skills bundle multiple duties in ways that pattern-match the post's warning:

- **`close-wave`** — merge + quality-gate + secret-scan + cross-repo symlinks + KB upsert + BLOCKING final gate + closure receipt (README:295–304). One skill, five categories.
- **`session-end`** — commit-nudge + parking triage + exit-note + Second-Brain persistence + tomorrow's-first-move (README:186–202). One skill, three categories.
- **`commit`** — pre-commit review + parking triage + code-reviewer dispatch + fix/park choice + plan.md update (README:249–268). Overlapping with `session-end` (both do parking triage).
- **`planning-loop`** — spec drafting + adversarial-review dispatch + verdict-mixing + arbiter selection + auto-apply (README:270–281).

Splitting or not is a real design call — for `close-wave`, the current bundle is what makes the ritual atomic. But the post is specifically about **discoverability under agent load**, which is orthogonal to atomicity. A skill that only fires when the model recognizes its single purpose is a different bar than a skill whose fire-condition is "I am closing a wave, do all six things."

This is not a one-`/micro` change. It's a categorization + split-or-keep decision per skill, and it likely touches receipt keying + skill-creator eval fixtures + `/apply-anthropic-reviews` decomposition rules. Needs a spec.

### Concrete change (as a spec brief for `/spec-planner`)

Not a diff — an audit brief that `/spec-planner` should convert into a spec:

> Audit the 25 skills in `skills/` against the "single category per skill" heuristic from https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills. For each skill:
>
> 1. Name the primary category (workflow / bookkeeping / setup / safety-check / authoring / cross-cutting-orchestration / memory / etc. — pick 8–9 categories that fit the harness).
> 2. List secondary responsibilities the skill also carries.
> 3. Classify as **keep** (single category), **split** (candidate for extraction into N focused skills), or **rename** (name doesn't convey the primary category to the model).
> 4. For each **split** candidate, sketch the extraction: which piece becomes a new skill, which stays in the parent, how receipts/idempotency keying survives the split.
>
> Output: a table + one paragraph per skill, then a prioritized "top 3 splits to consider" list. Do **not** ship any splits in the spec — this is a decision-support artifact.
>
> Explicit non-goals: rewriting the skills themselves; changing receipt schema; expanding beyond the 25 currently-shipped skills.

### Expected payoff
- Objective inventory of which skills are single-category vs multi-category — makes the "should this be one skill or two?" question answerable from data instead of instinct.
- Feeds `/apply-anthropic-reviews` decomposition rules: when a suggestion touches a currently-multi-category skill, the reviewer knows to consider whether the split is on the roadmap first.
- Corroborates or challenges the "atomic ritual" defense for `close-wave` / `session-end` / `commit` etc. with a documented tradeoff.

### Why not just do it as an `/micro`
Because the split-vs-keep call per skill is not mechanical — each involves receipt-schema decisions, cross-skill dependency implications (many skills already share `_shared/lib/emit-receipt.sh`), and idempotency-key stability under a name change. `/micro` writes the audit table in one session; `/spec-planner` writes the plan for what to do with the audit's conclusions. The § is asking for the spec, not the eventual splits.

1. `find /home/user/claude-harness/skills -mindepth 1 -maxdepth 1 -type d | wc -l` — should return 25 (currently) or higher. If the count has dropped, some skills may have been consolidated already.
2. `grep -l 'category\|nine categor\|single-category' /home/user/claude-harness/skills/*/SKILL.md` — must return nothing (no existing single-category framing) to justify a fresh audit.
3. If a spec at `docs/specs/*skills-audit*` or `docs/specs/*category*` already exists, the audit may already be in flight — check the plan.md `## Now` / `## Next` sections first.

**Recommended verdict:** spec — the audit touches every skill and its output will shape multiple future decisions. Solo maintainer; not urgent; probably one afternoon to write the spec, several weeks of ambient decisions to apply it. Explicitly note that the spec's deliverable is the **audit + split-shortlist**, not the splits themselves.

## 5. Reference Claude Code sandboxing as a complementary confinement layer to the loop protocol's worktree guardrails

**Source:** [Making Claude Code more secure and autonomous with sandboxing — anthropic.com/engineering, 2026-05-19](https://www.anthropic.com/engineering/claude-code-sandboxing) (companion: [How we contain Claude across products — 2026-05-28](https://www.anthropic.com/engineering/how-we-contain-claude))

### Why it's relevant
Claude Code now ships a **built-in sandbox runtime** (research preview, launched at Code w/ Claude London on May 19) that enforces filesystem + network isolation without spinning up a container. In Anthropic's internal usage, it **reduces permission prompts by 84%**. Locally, it runs Seatbelt on macOS and Bubblewrap on Linux. The May 28 companion post confirms these primitives are what Anthropic uses across claude.ai (gVisor), Claude Code (Seatbelt/Bubblewrap), and Claude Cowork (full VM).

The harness's **loop protocol** (AGENTS.md §"Loop protocol", `skills/_shared/loop/safety/`) already has:

- A **catastrophic-command denylist** hook (fires regardless of permission mode)
- **Write-root confinement** (worktree dir + run's state dir; OS-enforced where the host supports it, advisory otherwise)
- **Default-deny outbound egress + operator-declared host allowlist** for secret-bearing items
- **Task-scoped credential injection** (only the item's declared secrets, not the full env)

Claude Code's built-in sandbox now covers ~2 of those 4 primitives (filesystem + network isolation) with OS-level enforcement that the loop protocol currently reaches only "advisory where the host doesn't support it." Long-term, the loop's worktree safety guardrails could **rest on top of** the Claude Code sandbox instead of duplicating it — the denylist stays as a `PreToolUse` backstop for classes the sandbox doesn't cover (e.g. destructive git ops within an approved write-root), while filesystem + network confinement is delegated to the runtime.

But: the sandbox is still a **research preview**, the loop's confinement is battle-tested via 20+ waves of use, and the denylist hook's Human-only TODOs (installing the `PreToolUse` hook in `~/.claude/settings.json`) already require operator setup. Adding a "prefer sandbox + denylist as backstop" recommendation on top of a still-shifting Anthropic feature is premature.

### Concrete change (deferred design sketch, not for immediate application)

When Claude Code sandbox leaves research preview, add one paragraph to AGENTS.md §"Loop protocol" ("**Safety guardrails (worktree lane)**", currently the paragraph starting "Before any worktree item runs..."):

```markdown
The worktree lane can additionally run inside Claude Code's built-in sandbox
([Seatbelt on macOS, Bubblewrap on Linux](https://www.anthropic.com/engineering/claude-code-sandboxing))
when the operator opts into it, delegating filesystem + network confinement to
the OS-enforced runtime. The denylist stays as a `PreToolUse` backstop for
destructive commands within an approved write-root — the sandbox and the denylist
are complementary: the sandbox enforces "you can't reach outside these paths / hosts,"
the denylist enforces "even inside those paths, don't run these commands." Neither
replaces the other.
```

Companion: a receipt-schema field on loop run summaries recording whether the sandbox was on (`sandbox: claude-code | none`), for post-hoc reproducibility of what confined the run.

### Expected payoff
- The loop's OS-enforced write-root guarantee (currently "OS-enforced where the host supports it and advisory otherwise") gets promoted to reliably-OS-enforced when the operator opts into the sandbox.
- Permission prompts inside a worktree run drop by Anthropic's reported 84% internal figure — worth measuring in the harness once the plumbing exists.
- Operator setup shrinks: instead of the denylist hook + write-root confinement + egress config all being separate opt-ins, the sandbox toggle covers the two OS-level ones.

### Why this is deferred, not applied
- Claude Code sandbox is a research preview as of the May 19 launch — not stable enough to be baked into AGENTS.md as a recommended primary confinement layer.
- The loop's write-root + denylist + egress plumbing was hardened across Waves 21–24 (per docs/waves/wave2[1-4]-*.md); overriding it with a still-in-beta layer would replace a known-working system with an unknown-shape one.
- The `/run-loop` skill's own "Human-only TODOs" already ask the operator to install the denylist hook — piling another opt-in on top doesn't help the solo maintainer's setup ergonomics.
- Better plan: revisit when Claude Code sandbox reaches GA + the loop protocol has a stable "safety receipts" field to record which confinement layers were active for a given run.
