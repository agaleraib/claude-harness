## 2. Cite "The new rules of context engineering for Claude 5 generation models" in README's anti-patterns + Why-Not-Superpowers evidence list

**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models). ## 3. Consider a `procedures/large-scale-migrations.md` (or `/migration-plan` skill) that codifies "fix the process, not the code"

**Source:** [How Anthropic runs large-scale code migrations with Claude Code — claude.com/blog, 2026-07-16](https://claude.com/blog/ai-code-migration). Highlights: Jarred Sumner's Bun Zig→Rust migration ("a million lines produced in less than two weeks, 100% of Bun's existing test suite passing in CI before merge"); Mike Krieger's 165k-line Python→TypeScript over a weekend; ten packages tens-to-hundreds of thousands of lines each. **Core methodology: fix the process that produces the code, not the generated code itself.** Configure CLAUDE.md rulebooks + deterministic hooks for safety-critical actions; if an agent fails a parity check, adjust phase gates or system instructions rather than patching the diff. Six-step migration recipe (rulebook + dependency map → stress-test → iterative translation → phase gates → parity checks → merge).

**scope: speculative** — the harness has no runnable migration today; suggestion below is a design-time note for when one lands, not immediate work.

### Why it's relevant

The harness's core methodology already privileges "fix the process, not the code" in adjacent form:

- `skills/run-wave/SKILL.md` + `skills/close-wave/SKILL.md` implement **phase gates** via Wave → Task → close-wave receipts.
- `skills/spec-planner/*` writes a `docs/specs/*.md` **rulebook** *before* implementation.
- `procedures/api-security-checklist.md` and `procedures/triage-quality-issues.md` are examples of the harness's **procedure** style — checklist docs the operator runs.
- The `code-reviewer` agent + `criteria/*.md` rubrics are the **parity check** in the harness's flow (rubric-anchored).

What the harness does **not** have is a first-class migration surface. If a consumer project (or `claude-harness` itself, hypothetically) ever needs a Zig→Rust / Python→TypeScript / framework-vN→vN+1 migration, there's no procedure or skill dedicated to it. The most relevant existing surface is `skills/migration-check/SKILL.md`, but its scope is **database schema migrations only** (line 3: "Verify a database migration is reversible, concurrent-safe, and backfill-safe"), not language/framework code migrations.

The gap has two possible shapes:

**Option A — a lightweight `procedures/large-scale-migrations.md`** (the cheaper, more portable path):
- Six-step checklist adapted from Anthropic's post: (1) rulebook + dependency map in CLAUDE.md; (2) stress-test a representative slice; (3) phase-gate the run; (4) parity checks (test suite, output-diff); (5) fix the process on failure; (6) merge behind a feature flag.
- Cross-reference `spec-planner` for the rulebook-writing step and `run-wave` for phase gating.
- Live next to `procedures/api-security-checklist.md` — same style, same discoverability.

**Option B — a `/migration-plan` skill under `skills/`** (the more substantive path):
- Interactive: asks discovery questions (source language, target language, dependency-map source, test-suite entry point, parity-check strategy).
- Emits a `docs/specs/<date>-<source>-to-<target>-migration.md` that includes the rulebook + phase gates + parity checks up front.
- Chains into `run-wave` naturally.

### Why this is `defer`, not `apply`

1. **Speculative for solo tooling.** The harness has no in-flight migration and no known consumer project asking for this pattern. Building either option now is designing against a hypothetical.
2. **The building blocks already exist.** A user who *did* need to migrate a codebase today could invoke `spec-planner` (rulebook-writing) → `run-wave` (phase gates) → `code-reviewer` (parity checks) manually; the missing piece is the *procedure doc that names the pattern*, not any new plumbing.
3. **Risk of premature abstraction.** Anthropic's post describes ten Anthropic-internal migrations across many different domains. Codifying the pattern before the *harness's operator* runs a real migration risks capturing the wrong parts.
4. **Right level to intervene is `procedures/`, not `skills/`** — the pattern is a *checklist*, not an interactive step. Option A is the right size *when* it's needed.

### Concrete change (deferred)

None this run. When triaged for action, prefer **Option A** first:

1. Copy the six-step recipe from Anthropic's post into `procedures/large-scale-migrations.md`.
2. Add cross-references: "This procedure calls `spec-planner` for step 1 and `run-wave` for steps 3–5."
3. Add a one-line pointer from `README.md`'s workflow section to the new procedure.

Upgrade to Option B (dedicated skill) only if the maintainer actually runs a migration and finds Option A too heavy.

### Expected payoff (when applied)

Consumer projects hitting their first framework/language migration have a documented recipe to follow rather than reinventing the phase-gating themselves. The harness gains a citation-strength story for "Anthropic used this exact pattern for a million-line migration."

## 4. Bookkeeping: The AI-Native SDLC playbook's artifact chain corroborates the harness's spec/plan/wave structure — flag one gap (incident-record surface)

**Source:** [The AI-Native SDLC playbook — claude.com/blog, 2026-08-21](https://claude.com/blog/the-ai-native-sdlc-playbook). Six-stage AI-native SDLC organized around a chain of committed artifacts: **`intent.md → spec.md → plan.md → diff → review findings → incident record`**. Related first-party post from the same August-2026 batch: [How Anthropic secures its AI-native software development lifecycle](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle) (Jason Clinton, Deputy CISO) — reports the share of PRs receiving substantive review comments at Anthropic rose from 16% to 54% after requiring automated reviewers to prove findings.

### Why it's relevant

The harness already implements four of the six chain stages:

| Anthropic's chain | Harness's surface | Coverage |
|---|---|---|
| `intent.md` | *implicit* in `spec-planner` discovery questions | **gap** — no dedicated file |
| `spec.md` | `docs/specs/<date>-<topic>.md` (via `spec-planner`) | full |
| `plan.md` | `plan.md` + `docs/waves/*.md` | full |
| `diff` | git + `/commit` skill | full |
| `review findings` | `code-reviewer` output + `criteria/*.md` rubrics | full (with proof-of-finding discipline already in place per 2026-04-25 §1 postmortem alignment) |
| `incident record` | *partial* — `parking_lot.md` triage + `.harness-state/last_exit.md` | **gap** — no post-mortem convention |

Two identified gaps:

- **`intent.md`** — Anthropic's chain separates "why" (intent) from "what/how" (spec). The harness's `spec-planner` currently folds intent into the spec's opening context section. This is defensible for solo work (the operator already knows the intent) but stops being defensible if the harness ever adopts an issue-source loop (`skills/run-loop/SKILL.md`'s `issues` mode already ingests GitHub issues as inputs). The issue body *is* the `intent.md` in that mode; worth naming.
- **`incident record`** — the harness has no dedicated post-mortem file convention. Adjacent surfaces: `parking_lot.md` (unfinished work), `.harness-state/last_exit.md` (session state), `anthropic-reviews/` (this file). None are the right place for a post-mortem.
