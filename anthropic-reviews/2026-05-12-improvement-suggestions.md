## 1. Document `claude agents` / `claude --bg` in the README "Git Worktrees (Parallel Sessions)" section

**Source:** [Agent view in Claude Code — claude.com/blog, 2026-05-11](https://claude.com/blog/agent-view-in-claude-code). Companion docs page: [Manage multiple agents with agent view — code.claude.com/docs/en/agent-view](https://code.claude.com/docs/en/agent-view). Shipped as a Research Preview in Claude Code **v2.1.139** (2026-05-11) on Pro / Max / Team / Enterprise / Claude API plans.

### What Anthropic shipped (one-paragraph summary)
A built-in CLI multi-session manager. `claude agents` opens a full-terminal roster of every background Claude Code session under your config directory, grouped by state (Working / Needs input / Ready for review / Completed / Failed / Stopped). Each row shows a Haiku-generated one-line summary of what the session is doing. `claude --bg "<prompt>"` starts a new background session from the shell; `/bg` inside any interactive session detaches it to the background. Each background session is automatically run inside a git worktree under `.claude/worktrees/`, so parallel sessions read the same checkout but write to their own worktree. A per-user **supervisor process** hosts the sessions; sessions survive shell close and auto-update, but stop on machine sleep (`claude respawn --all` to restart). `/loop` sessions appear in the roster with their run count and a countdown to the next iteration. Administrators can disable via the `disableAgentView` managed setting or `CLAUDE_CODE_DISABLE_AGENT_VIEW` env var.

### Why it's relevant
The harness has a **"Git Worktrees (Parallel Sessions)" section** at `README.md:991–1016` that instructs the reader to:

```bash
git worktree add ../myproject-feat-X feat/X
cd ../myproject-feat-X
claude
```

…specifically for the use cases:

- *"You want to **run Claude Code in parallel** on different features (each session needs its own directory)"* (line 995)
- *"The **generator agent** is building for hours and you want to keep coding something else"* (line 996)
- *"A **scheduled Claude agent** is working on one task while you work on another"* (line 998)

All three of those are **exactly what `claude --bg "<prompt>"` + `claude agents` now does built-in**, with the worktree creation automated. The harness's manual pattern is **still required** for two cases:

1. **`/run-wave`** — dispatches the orchestrator with `isolation: "worktree"` via the Agent tool. This is a multi-task batch with a pre-merge gate (`/close-wave`), a mandatory summary file (`docs/waves/wave<N>-<slug>.md`), and a different worktree-cleanup contract than Agent View's "delete when session ends." The orchestrator's worktree path is managed by the harness, not by the supervisor. (`skills/run-wave/SKILL.md:318` confirms this.)
2. **Keeping a dev server on master** while working on a feature branch — Agent View worktrees are tied to background-session lifetimes, so they aren't a place to leave a long-lived `npm run dev` process for the duration of unrelated coding work.

Today the README has **zero mention** of `claude agents`, `claude --bg`, or `.claude/worktrees/`:

```
$ grep -rn "claude agents\|claude --bg\|disableAgentView\|\.claude/worktrees/" README.md AGENTS.md
(no hits)
```

A reader on Claude Code v2.1.139+ who follows the README's manual worktree instructions for case 1 ("run Claude Code in parallel on different features") would create an *unnecessary* worktree by hand, miss the supervisor-hosted session lifecycle, and miss the roster UI. A short cross-reference inside the existing section keeps the harness-owned manual path correct for `/run-wave`-style multi-task work while surfacing the built-in path for ad-hoc parallel sessions.
