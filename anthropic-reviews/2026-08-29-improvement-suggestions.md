## 1. Audit skills for the folder-as-toolbox pattern (scripts + assets + dynamic hooks)

**Source:** [Lessons from building Claude Code: How we use skills — claude.com/blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills). Anthropic reports "hundreds of skills in active use" internally and argues the biggest misconception is treating a skill as a Markdown file — the most effective skills are **folders** with executable scripts, assets, data, and (in Claude Code) dynamic hook registration.

### Why it's relevant

The harness ships 24 skills under `skills/` (`skills/_shared, apply-anthropic-reviews, close-wave, commit, cowork-area-sync, deploy-check, harness-status, memory-prune, micro, migration-check, new-cowork, park, planning-loop, project-init, run-loop, run-wave, session-end, session-start, setup-harness, shared-root-init, skill-creator, triage-parking, a11y-check, api-smoke-test, archive-plan`). Some are already folder-shaped (`planning-loop/` has `lib/`, `references/`, `evals/`; `shared-root-init/` has `lib/init.sh`; `skill-creator/` has `scripts/*.py`), and every SKILL.md has proper frontmatter (`name` + `description` + often `argument-hint`). But an eyeball scan against the post's four dimensions shows two gaps:

1. **Executable helpers vs. inline shell.** Skills like `commit`, `micro`, `park`, `session-end`, `session-start`, `harness-status`, `deploy-check`, `api-smoke-test`, `archive-plan`, `memory-prune`, `migration-check`, `a11y-check`, `new-cowork`, `cowork-area-sync`, `apply-anthropic-reviews`, `triage-parking` are single-SKILL.md files — no `lib/`, no `references/`. Some of these carry inline shell snippets that could move into `lib/*.sh` (deterministic, testable, out of the model's context). This isn't a bug, but the post argues it leaves compression on the table.
2. **Dynamic hook registration.** `grep -rn "hooks\|register" skills/*/SKILL.md` returns descriptive prose only — no skill declares dynamic hooks the way the post describes. This is genuinely new territory since the last skills refactor.

### Concrete change (SPECULATIVE — read the full post first)

A staged sweep, not a single PR:

1. Read the full post and extract a per-skill checklist (folder layout, script split, dynamic hook opportunities).
2. Pick 2–3 pain-point skills (e.g. `commit` and `session-end`, which have grown organically) and split shell into `lib/`.
3. Only after (2) proves the payoff, extend the pattern.

Do NOT bulk-rename or bulk-restructure — this is exactly the kind of "architectural sweep ahead of need" the harness README warns against.

### Expected payoff

Uncertain until the full post is read. Best case: 2–3 heavy skills get tighter (less prose in context, more deterministic shell). Worst case: the harness already does most of what the post recommends and the sweep produces one or two small wins.

### scope: speculative

The maintainer must read the full post before this § moves out of speculative — the snippet-based intelligence here is thin.

## 3. Adopt the `Workflow` tool (dynamic-workflow scripts) for multi-wave orchestration

**Source:**
- [A harness for every task: dynamic workflows in Claude Code — claude.com/blog](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (announcement)
- [Introducing dynamic workflows — claude.com/blog](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (companion)
- [Orchestrate subagents at scale with dynamic workflows — code.claude.com/docs/en/workflows](https://code.claude.com/docs/en/workflows) (reference)

Anthropic introduced a `Workflow` tool: **a JavaScript scripting layer that fans out subagents at scale** (10s–100s in parallel), with progress-saving for jobs that run for hours/days. Case study: Jarred Sumner used it to port Bun from Zig to Rust — 750k lines, 11 days first-commit-to-merge, 99.8% test-suite pass.

### Why it's relevant (and why the recommendation is `defer`)

The harness has a hand-rolled orchestrator (`/run-wave N` → `.claude/agents/orchestrator.md` → per-task subagent dispatch → `/close-wave N`). This is a shape the `Workflow` tool now productizes. Moving `/run-wave` onto `Workflow` scripts would:

- Replace the orchestrator's hand-rolled dispatch with Anthropic-supported infrastructure (upside: less bespoke code to maintain)
- Enable parallelism ≥10 agents per wave, which the current dispatcher can't do (upside: real speedup for wide waves)
- Require rewriting the orchestrator agent + `/run-wave` + `/close-wave` around a new runtime (downside: significant scope)
- Gate the harness on Max/Team/Enterprise plans (or Pro w/ `/config` opt-in) (downside: portability constraint for solo consumers on lower tiers)

The critical question is: **has any wave in the last 3 months wanted to fan out to 10+ parallel subagents?** `ls docs/waves/*.md | wc -l` and a quick scan of the recent wave summaries (`wave25`, `wave21`, `wave20`, etc.) suggests no — waves are ≤7 tasks each, sequential-with-review. Until that changes, `Workflow` is a solution looking for a problem here.

### Concrete change (deferred; documented for the day the trigger fires)

- Trigger: a wave spec calls for >10 parallel independent tasks, OR a consumer project's methodology needs codebase-wide fanout (security audit, migration).
- When triggered: read the two blog posts and the `/docs/en/workflows` reference in full; author a proof-of-concept `Workflow` script that dispatches one existing wave (`wave20` — safety integration — is a good candidate because it had multiple independent T-tasks). Compare authoring cost + wall-clock + failure mode vs. today's dispatch.
- Only if the PoC clearly wins: draft a spec (`docs/specs/<date>-workflow-adoption.md`) and route through `/spec-planner`.

**Verify before applying:**
1. `ls docs/waves/*.md | xargs grep -l "parallel" | wc -l` — if the number of waves that explicitly requested parallelism is still small (≤2), the trigger hasn't fired.
2. `grep -rn "Workflow tool\|workflow.script\|dynamic workflow" /home/user/claude-harness` — must return only bookkeeping mentions (this §, tracker rows); if a real integration has landed, this § is stale.
3. Confirm dynamic workflows are still gated to Max/Team/Enterprise (with Pro opt-in) — if they've gone universal, the portability cost drops and the defer threshold lowers.

**Recommended verdict:** defer until the harness needs 10+ parallel subagents in a single wave (or a consumer project does) — today's dispatcher fits today's wave sizes; migration cost outweighs benefit until fanout width demands it.

## 6. Reference the sandbox-runtime + Auto Mode classifier work in `setup-harness`'s permissions guidance

**Source:**

### Why it's relevant

The sandbox runtime is a **structurally different** answer: instead of enumerating what's allowed, you enumerate what the agent can even reach.

The two approaches compose (hook allowlists still fire under a sandbox), but the guidance in `setup-harness` should eventually mention the sandbox route so a security-conscious consumer knows the option exists.

- Sandbox runtime configuration is per-OS and per-shell — writing portable guidance requires more than a snippet-based read.
- The maintainer's own permission story (see the 2026-05-08 §1 disposition + `.claude/settings.json`) is stable today.

Do the read + write when the sandbox runtime GAs (or when a consumer project asks first).

### Concrete change (deferred)

### Sandbox runtime (research preview → GA?)

If your consumer project is security-sensitive, consider the [Claude Code sandbox runtime](https://www.anthropic.com/engineering/claude-code-sandboxing). In Anthropic's internal usage this reduced permission prompts by 84%. The sandbox composes with Auto Mode's classifier (already the default on Pro/Max/Team plans).

Sandbox + hook allowlists are complementary, not redundant — sandbox draws the outer perimeter, hooks catch specific tool calls inside it.
