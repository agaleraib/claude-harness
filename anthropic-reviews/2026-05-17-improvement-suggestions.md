## 1. Cite "How Claude Code works in large codebases" in README Why-Not-Superpowers + References

**Source:** [How Claude Code works in large codebases: Best practices and where to start — claude.com/blog, 2026-05-14](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start). ## 2. Package the harness as a Claude Code plugin (the fifth extension point)

**Source:** Same post as §1 — [How Claude Code works in large codebases](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start). The post defines: *"A plugin bundles skills, hooks, and MCP configurations into a single installable package, so when a new engineer installs that plugin on day one, they will immediately have the same context and capabilities as those who have been using Claude already."*

### Why it's relevant

Of Anthropic's five extension points, the harness already ships:

| Extension point | Harness status |
|---|---|
| CLAUDE.md files | ✓ Root `CLAUDE.md` + `AGENTS.md` + example subdirectory `CLAUDE.md` files in `examples/web-app-project/` and `examples/backend-project/` |
| Hooks | ✗ `.claude/settings.json` has `hooks: {}` (empty stub); the `update-config` skill documents hook usage but the harness itself activates none |
| Skills | ✓ 22 skills under `skills/` symlinked into `~/.claude/skills/` |
| Plugins | ✗ Not packaged as a plugin; install path is `skills/setup-harness` → symlinks |
| MCP servers | Partial — `examples/web-app-project/.mcp.json` ships a Playwright MCP example for consumer projects, but the harness itself doesn't depend on one |

The gap is plugins. A future plugin distribution would let a user run `claude --plugin-url https://.../claude-harness.zip` (the v2.1.140 / May-12 release added `--plugin-dir` and `--plugin-url` flags for zip and URL loading) and get the whole bundle — skills + the (currently empty) hooks block + an MCP example — in one step.

### Why this is `defer`, not `apply`

The prior tracker entries already line up on this:
- **2026-04-19 §3** rejected the *progressive-disclosure restructure* suggestion as "already in place" — the SKILL.md layout already matches Anthropic's open standard.
- **2026-05-07** skipped the *Finance Agents plugin pattern* with: *"the harness ships skills via symlink to `~/.claude/skills/` and isn't aiming for multi-distribution today."*

A plugin would add value when:
1. Multiple users install the harness on machines where symlink-based distribution is awkward (Windows, CI runners, ephemeral sandboxes — including the Claude Code web execution environment described in CLAUDE.md);
2. A user wants to install a *versioned snapshot* of the harness (today they `git clone` the head of master);
3. An organization rolls out the harness across many engineers and wants Anthropic's plugin-discovery surface (`/plugins`) rather than `setup-harness`.

None of those are pain points for a solo-maintained repo today. Speculative for solo tooling per the routine's own rubric — defer, not reject.

### Concrete change (deferred)

When/if a maintainer takes this on, the work shape:

1. Add a `plugin.json` manifest at the repo root listing skill names, agent names, the (empty for now) hooks block, and the MCP example.
2. Decide what to do with `setup-harness` — keep it as the canonical install path for symlink-based deployments, and add a `--plugin` alternative path that doesn't symlink.
3. Add a CI job that builds the plugin zip from the repo head on each release tag (no release tags today; would need to start tagging).
4. Document both install paths in `README.md` Architecture section + `setup-harness/SKILL.md`.
5. Re-evaluate the `hooks: {}` empty block — a plugin distribution is the natural moment to ship at least one default hook (e.g. a `SessionStart` hook that surfaces parking-lot count, mirroring `skills/session-start` Step 0).

This is a **substantive** suggestion in the README.md decompose-and-route sense (touches >5 files, introduces a new convention) — would need `/spec-planner` before any implementation.

### Expected payoff (when applied)

Single-command install for new harness users; versioned snapshots; eligibility for `/plugins` discovery; smoother cold-start on ephemeral Claude Code environments (e.g. the web execution environment this very session runs in, where `~/.claude/skills/` is reconstructed each session).

## 3. Bookkeeping: re-cost the deferred 2026-05-10 §2 (Cloud Routines migration) against the new programmatic credit pool

**Source:** [Use the Claude Agent SDK with your Claude plan — support.claude.com, 2026-05-13](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), announced via @ClaudeDevs the same day. Coverage: [Anthropic puts Claude agents on a meter across its subscriptions — InfoWorld, 2026-05-13](https://www.infoworld.com/article/4171274/anthropic-puts-claude-agents-on-a-meter-across-its-subscriptions.html). Effective 2026-06-15: Agent SDK, `claude -p`, Claude Code GitHub Actions, and third-party harness usage draw from a per-month **programmatic credit pool** — $20/Pro, $100/Max 5x, $200/Max 20x — separate from interactive subscription limits. Credits don't roll over.

### Why it's relevant

This is **not a new ask**; it's a bookkeeping update to the deferred [2026-05-10 §2](./2026-05-10-improvement-suggestions.md#2-migrate-the-anthropic-reviews-routine-itself-to-a-claude-code-cloud-routine) (migrate the Anthropic-reviews routine itself to a Claude Code Cloud Routine). That § argued cost was the second of five defer reasons:

> 2. **Cloud Routines bill against the Pro/Max plan.** Even at the cheapest tier, a weekly routine that does a multi-page web survey is non-zero recurring cost ($5–10/run by analogy with `/ultrareview`'s pricing band).

After 2026-06-15, Cloud Routines and other programmatic usage will draw from the dedicated credit pool, not from interactive subscription headroom. Two relevant implications:

1. **The cost ceiling is now numeric.** At Pro ($20/mo) a weekly routine has $4-5/run of headroom before overage; at Max 5x ($100/mo), $20-25/run; at Max 20x ($200/mo), $50/run. The original §2 estimate of "$5–10/run" fits comfortably inside the Max 5x credit but exhausts Pro on a single run if the survey expands.
2. **The "use it or lose it" structure penalizes infrequent automation.** If the harness migrates the routine to weekly and the credit is monthly with no roll-over, four runs/month at $5/run leaves $0 of the Pro $20 credit — fine, but a fifth run (e.g. a manual re-trigger after a missed week) overages immediately. At Max 5x there's slack; at Pro the routine effectively claims the entire programmatic credit pool.
3. **Interactive Claude Code is unaffected.** The maintainer running the routine manually inside a Claude Code session (as today) stays on the interactive subscription pool. This *reinforces* the §2 defer: manual trigger today is materially cheaper than the cloud-routine path will be after 2026-06-15.

### Concrete change

None this run — purely an update to the cost reasoning in the **already-deferred** 2026-05-10 §2. If the maintainer eventually promotes that §, the cost section should be rewritten to reference the programmatic credit pool ($20/$100/$200 by plan, no roll-over) instead of the old "$5–10/run" estimate.

**Optional micro-edit (deferred until promotion):** when 2026-05-10 §2 is acted on, prepend a one-line note to its "Why this is defer, not apply" section 2 — *"After 2026-06-15, Cloud Routines bill against the per-month programmatic credit pool ($20/Pro, $100/Max 5x, $200/Max 20x). At Pro, a weekly routine claims the full credit; at Max 5x, ~25% — see [2026-05-17 §3](./2026-05-17-improvement-suggestions.md#3-bookkeeping-re-cost-the-deferred-2026-05-10-2-cloud-routines-migration-against-the-new-programmatic-credit-pool)."*
