## 2. Add a `## Gotchas` section convention to skill-creator's authoring reference

**Source:** [Lessons from building Claude Code: How we use skills — Claude Blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills). Companion to the existing Anthropic skill-authoring best-practices doc that's already vendored at `skills/skill-creator/references/anthropic-skill-authoring.md`. Key claim from the post: **"the highest-signal content in any skill is the Gotchas section, which should be built up from common failure points that Claude runs into when using your skill."** And: *"every time Claude fails while using a skill, the owner should add that failure to the gotchas. Over time, the skill becomes robust not because someone predicted everything, but because they captured every mistake."*

### Why it's relevant

The harness ships ~24 SKILL.md files (`find skills -maxdepth 2 -name SKILL.md | wc -l` = 24 in this repo's `skills/`) and serves as the skill-authoring template + reference for consumer projects via `setup-harness` and `skill-creator`. Verified state today:

- **Zero SKILL.md files contain a `## Gotchas` heading.** `grep -l "^## Gotchas\\|^### Gotchas\\|^## Common pitfalls\\|^## Pitfalls\\|^## Failure modes" skills/*/SKILL.md` returns nothing.
- **The vendored authoring reference doesn't mention Gotchas.** `grep -n "Gotchas\\|gotchas\\|failure mode\\|common failure\\|stuck-jobs" skills/skill-creator/references/anthropic-skill-authoring.md skills/skill-creator/SKILL.md` returns nothing.
- The closest existing convention is the **Anti-patterns section** in `references/anthropic-skill-authoring.md` (covered around line 70+), but that's prescriptive ("don't do X") rather than empirical ("Claude failed at X — here's the rescue"). They're different shapes of guidance and serve different purposes.

The 2026-06-03 post is the most authoritative current public guidance from the team that ships the largest collection of internal Anthropic skills. It elevates Gotchas from a nice-to-have to **the most valuable section in a SKILL.md**. The harness's authoring guidance shouldn't be silent on it.

This is *not* the same suggestion as 2026-04-19 §3 (which proposed restructuring all skills around progressive disclosure and was REJECTED because that was already in place). This is a **new section convention** layered on top of the existing structure.

### Concrete change

**(a) Append a "Gotchas" subsection to `skills/skill-creator/references/anthropic-skill-authoring.md`** — between the existing "Anti-patterns" and "Pre-ship checklist" sections, or wherever flows best:

```markdown
## Gotchas — capture failures as you find them

Per Anthropic's 2026-06-03 [Lessons from building Claude Code: How we use skills](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills): **the highest-signal content in any skill is the Gotchas section.** Build it up from real failure points — every time Claude fails while using the skill, append the failure (and the rescue) to Gotchas. Over time the skill becomes robust not because the author predicted everything, but because every mistake was captured.

Convention for SKILL.md files in this repo (and consumer-project skills authored against this reference):

- Place a `## Gotchas` section near the bottom of the SKILL.md body (above any References / Footnotes block).
- Each Gotcha is one short paragraph or bullet: **what failed**, **why** (one-sentence root cause if known), and **what to do instead**. Cite the failing session or PR if recoverable.
- Subtle Gotchas that need detail (a quirky API contract, an append-only assumption, a naming variance across systems) go in `references/gotchas/<topic>.md` and are referenced from the SKILL.md line. This stays consistent with the progressive-disclosure rule (references one level deep from SKILL.md).
- Empty Gotchas section is fine on day one — better than no section, because adding the first Gotcha then doesn't trigger structural churn. Seed with a single comment: *"None observed yet; append failures as they surface."*

Do **not** confuse Gotchas with Anti-patterns:

- *Anti-patterns* are prescriptive don'ts written from authoring intuition. They live in the body.
- *Gotchas* are empirical failure-and-rescue notes that grow as the skill runs in production. They live in their own section so additions don't churn surrounding prose.
```

**(b) Add a one-line mention to `skills/skill-creator/SKILL.md`'s "Write the SKILL.md" template list** — between the existing `**description**` line and the closing items:

```diff
 - **compatibility**: Required tools, dependencies (optional, rarely needed)
 - **the rest of the skill :)**
```

## 3. Position Claude Code's new "dynamic workflows" alongside `/run-loop` and `/run-wave` in the README

**Source:** [A harness for every task: dynamic workflows in Claude Code — Claude Blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Companion docs at [code.claude.com/docs/en/workflows](https://code.claude.com/docs/en/workflows). Anthropic shipped a Claude Code feature where **Claude can write a JavaScript script during a task that spawns and coordinates subagents** — choose models per subagent, run subagents in their own worktrees, gather results, decide what to do next, all without intermediate subagent output filling the main session context. Requires Claude Code **v2.1.154 or later**; available on all paid plans + API + Bedrock + Vertex + Foundry.

### Why it's relevant

The harness already has **two execution lanes** that fan out work to subagents:

- **`/run-wave`** (skill: `skills/run-wave/SKILL.md`) — dispatches one plan.md wave of tasks to subagents, in parallel where possible, and stops.
- **`/run-loop`** (skill: `skills/run-loop/SKILL.md`) — the **third execution lane** introduced in Wave 18–21; drives a stream of ready waves or `ready-for-agent` issues end-to-end through a mechanical gate (implement → review → verify → merge) unattended. Wave 21 went LIVE on 2026-06-15 with a real clean-room drain (`codex exec` implement, `anthropic-api:opus-4.8` review, verify-gate, AFK-merge).

Dynamic workflows is the **Claude-Code-native, per-task, in-session, JavaScript-orchestrated** equivalent of what `/run-loop` does at the harness layer in TypeScript, with one critical difference: dynamic workflows live **inside a single Claude Code session** and offload the orchestration to JS, keeping intermediate subagent output out of the parent context. `/run-loop` runs from a CLI engine (`run-loop-entry.ts`) and produces its own JSONL log surface.

The two are **complementary, not redundant**, at three layers:

| Layer | Dynamic workflows | `/run-loop` |
|---|---|---|
| **Where** | In-session, written by Claude per-task | Out-of-session CLI engine, frozen-interface seam |
| **What** | Spawn subagents per JS step, gather, decide next | Drain a queue of ready-work items through a mechanical gate (review → verify → merge) |
| **When** | Ad-hoc multi-agent task within one session | AFK-frontier drain of plan.md waves or `ready-for-agent` issues |
| **Cost shape** | Per-task token cost in your Claude Code session | Per-item review cost via the Anthropic API + Codex executor |
| **State** | Lives in the JS script's variables | Lives in `.harness-state/` + git + gh issues |
| **Auto-merge gate** | None (Claude session is the merge gate) | Mechanical AFK gate (`run-loop`'s frozen contract) |

A future reader asking *"why does this harness have `/run-loop` if Claude Code can now write its own JS subagent harness on the fly?"* needs one paragraph in the README that answers it before they decide to deprecate `/run-loop`.

But this is **defer**, not **apply**, this run, for three reasons:

1. **`/run-loop` is still mid-rollout.** Wave 21 went LIVE on 2026-06-15. The follow-on specs (`docs/specs/2026-06-16-run-loop-merge-to-head.md`, the `_shared` denylist hook install for the Claude-backend worktree lane) are open. Documenting the relationship to dynamic workflows on top of an unfinished lane risks tying the message to whatever the next wave changes.
2. **The dynamic-workflows feature gates on Claude Code v2.1.154+.** `setup-harness` does not currently check `claude --version`. A README note that recommends "use dynamic workflows for X" could land users on an older Claude Code and silently fail.
3. **Speculative for solo tooling.** The harness's actual `/run-loop` user is one person (the maintainer). A "when to use which" framing is high-value if anyone else picks up the harness later, low-value while it's solo and run-loop is stabilizing. Solo-tooling defer signal per the routine's own rubric.

When the maintainer wants to apply this later — likely once run-loop hits a stable post-Wave-21 baseline and `setup-harness` gains a `claude --version` check — the concrete change would be:

- **One paragraph in `README.md`** in the `/run-loop` section (around lines that today introduce the third execution lane) naming dynamic workflows as the in-session counterpart and stating the complementary-not-redundant relationship the table above sketches.
- **One bullet in `skills/run-loop/SKILL.md`** under "Why a separate lane" pointing at the dynamic-workflows docs as the in-session alternative.
- **One reference bullet** in the README References section linking the dynamic-workflows post + docs.

No code changes in either case — purely positioning. **scope: speculative**

### Why this is `defer`, not `apply` or `reject`

- **Not `reject`** — the relationship between the harness's run-loop and Anthropic's new built-in feature is real and worth naming. A future reader *will* ask this. Saying it in the README forestalls a redundant-feature-deprecation instinct, the same way 2026-05-10 §1 forestalled "is `code-reviewer` redundant now that `/ultrareview` exists?".
