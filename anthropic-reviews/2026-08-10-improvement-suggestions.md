## 1. Update `setup-harness` Auto Mode section for the 2026-08-14 default flip

**Source:** [Auto mode is now the default in Claude Code for Pro, Max, and Team plans — claude.com/blog, 2026-08-05](https://claude.com/blog/auto-mode-default-in-claude-code). Companion posts: [Running auto mode in production](https://claude.com/blog/auto-mode-in-production), [How we built Claude Code auto mode (engineering, May 2026)](https://www.anthropic.com/engineering/claude-code-auto-mode) — the engineering post was already reviewed in the [2026-05-08 §1](./2026-05-08-improvement-suggestions.md) run; this § is only about the newly announced default flip.

### Why it's relevant

## 2. Adopt a **Gotchas** section convention across skills

**Source:** [Lessons from building Claude Code: How we use skills — claude.com/blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills). Key quote from the article:

> The highest-signal content in any skill is the Gotchas section, which should be built up from common failure points that Claude runs into when using your skill.

### Why it's relevant
The harness has **24 skills** under `skills/`. Only **`setup-harness`** contains a "Gotchas" section (single match in `grep -c gotcha skills/*/SKILL.md`). Anthropic — writing from experience with hundreds of internally-used skills — explicitly identifies this as the section with the highest per-line payoff.

The harness's skills are stable enough that many *do* have known failure modes captured in prose already, just not in a section that's greppable and top-of-file for the next reader. Examples:

- `skills/planning-loop/SKILL.md` — memory-system-redesign is a recurring source of edge cases; scattered across step-by-step body.
- `skills/run-loop/SKILL.md` — worktree cleanup, gate authorization, and denylist-hook wiring are all failure surfaces the SKILL.md body describes but doesn't concentrate under one heading.
- `skills/commit/SKILL.md` — parking-lot triage vs. commit interleaving is a documented pitfall in the body (Step 2 → Step 4).
- `skills/skill-creator/SKILL.md` — the whole "run_eval.py isn't a distinct Executor" alignment gap (see §5) is a gotcha waiting to be surfaced.

The convention itself is cheap: `## Gotchas` heading, one bullet per recurring failure mode, empty for skills that haven't accumulated any (which is itself a signal). Anthropic's "measurement" pattern uses a `PreToolUse` hook to log skill invocations — the harness doesn't need that infrastructure to start; the Gotchas section is a text-only convention.

### Concrete change

Two edits — one convention, one backfill.

**A. Add the convention to `skills/skill-creator/references/anthropic-skill-authoring.md`** (already the vendored best-practices reference — no new file):

```diff
+## Gotchas section (per Anthropic 2026-06-03)
+
+The highest-signal content in any skill is the Gotchas section — a concentrated list of recurring failure modes Claude hits when using the skill. Convention:
+
+- Heading: `## Gotchas` near the top of the SKILL.md body, immediately after the summary paragraph.
+- One bullet per gotcha. Format: `- <situation> → <consequence> — fix: <what to do>`.
+- Empty is fine for a new skill; back-fill as failures accumulate (from user reports, code-reviewer catches, or session-end triage).
+- Do NOT hide gotchas in the middle of step-by-step content — the section is a "read this first" for the next Claude picking up the skill.
+
+Source: <https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills>
```

**B. Back-fill `## Gotchas` for one high-traffic skill this run** as a worked example. Best candidate: `skills/planning-loop/SKILL.md` (was the subject of Wave 5, Wave 6, and the 2026-05-13 memory-system-redesign spec — has the most documented failure modes). One-paragraph draft (needs the maintainer to confirm accuracy; the point of shipping *one* worked example is to seed the pattern, not to back-fill everything at once):

```diff
+## Gotchas
+
+- Spec path is unreadable/absent → the acceptance-strictness scanner fails open instead of blocking — fix: fail-closed, verified in Wave 25 (see `docs/waves/wave25-*.md`).
+- Focus injection lands in diagnostics instead of the acceptance-review focus block → reviewer never sees the "needs-attention" instruction — fix: inject into focus, not diagnostics (Wave 25 code-review F2).
+- Scanner invoked from anywhere but the canonical `$HOME` install path → scanner and skill see different counts — fix: always call via canonical path; treat scanner count as authoritative (Wave 25 code-review F3).
```

The rest of the skills can be back-filled organically per convention-B; not part of this §.

### Expected payoff
- Every future Claude opening a skill with a Gotchas section sees the failure modes *first* — Anthropic's "highest signal" claim compounds when Claude reads the skill hundreds of times over the harness's lifetime.
- Session-end triage gets a natural home for the "one thing I noticed today that will bite the next session" observations that currently vanish into per-cwd auto-memory or the parking lot.
- The convention costs one paragraph to document + zero-to-a-few lines per skill; no new infrastructure.

### Why this isn't a duplicate of prior "adopt Anthropic's skill authoring guidance" reviews
The 2026-04-19 §3 restructure was about **progressive disclosure** — moving procedural content into references and script files so the skill body stays under 500 lines. That work landed. This § is a **content-shape convention**: what goes at the top of the body, once the body is short. Different axis; no overlap.

**Verify before applying:**
1. `grep -c -i gotcha /home/user/claude-harness/skills/*/SKILL.md | grep -v ":0$"` — should still return only `setup-harness/SKILL.md:1` today (2026-08-10). If more skills already have Gotchas sections, back-fill priority shifts.
2. `grep -n "highest-signal\|Gotchas section" /home/user/claude-harness/skills/skill-creator/references/anthropic-skill-authoring.md` — must return nothing today; if it hits, the convention has been added and only the back-fill remains.
3. Re-read the 2026-06-03 post at apply time to confirm the "highest-signal" framing is still the quote used; Anthropic occasionally edits blog posts and the exact phrasing may drift.

**Recommended verdict:** apply — one-paragraph convention + one worked example; cheap; leverages a pattern Anthropic explicitly identified as its highest-yield section; no risk to existing skill behavior.

## 3. Refresh `.harness-profile` model pin for Sonnet 5 (June 30) + Opus 5 (July 24)

**Source:** [Introducing Claude Sonnet 5 — anthropic.com/news, 2026-06-30](https://www.anthropic.com/news/claude-sonnet-5) and [Introducing Claude Opus 5 — anthropic.com/news, 2026-07-24](https://www.anthropic.com/news/claude-opus-5). Related: [Claude Fable 5 / Mythos 5 — 2026-06-09](https://www.anthropic.com/news/claude-fable-5-mythos-5) — restricted-access frontier models, skipped in tracker.

### Why it's relevant
`.harness-profile` currently pins:

```yaml
model:
  primary: claude-opus-4-7
  fallback: claude-sonnet-4-6
  effort_default: xhigh   # derived from stakes.level: medium
```

Since 2026-04-11 (when the profile was seeded), the model landscape has shifted twice: Sonnet 5 (June 30) became the Free/Pro default; Opus 5 (July 24) became the default Opus tier with a 1M-token context window. Claude Code Fast Mode is now on Opus 5 by default (per the changelog for v2.1.219, 2026-07-24). Both Opus 4.7 and Sonnet 4.6 remain callable, so **nothing is broken today** — but three things degrade with time:

1. **Silent tier lag for consumer projects.** `project-init` seeds new `.harness-profile` files from the harness's own defaults — new projects created after 2026-07-24 are being anchored to Opus 4.7 / Sonnet 4.6 when Opus 5 / Sonnet 5 are the price-comparable current tier.
2. **Deprecation risk.** Claude Sonnet 4.5 / 4.0 lost their 1M-token context window on 2026-04-30 (already noted in the 2026-05-07 tracker row); the 4.6/4.7 line is one deprecation cycle away from a similar cut.
3. **Effort routing.** `effort_default: xhigh` was calibrated for Opus 4.7 in the 2026-04-23 postmortem; Opus 5 may have different sweet spots (Anthropic hasn't published equivalent guidance yet, so this is a "revisit when guidance lands" flag, not a blocker).

### Why this is `defer`, not `apply`

- **No incident driving it.** The current pin still works; every session in this run identifies as `claude-opus-4-7` (per the system prompt). The maintainer isn't blocked.
- **The pin change is trivial** (`sed -i 's/claude-opus-4-7/claude-opus-5/'`) but the *reason to change it* is speculative: is Opus 5 always the right tier for the orchestrator? For rubber-stamp waves it may be over-spec.
- **Consumer-project projection is more valuable than the harness's own pin.** The harness itself inherits the session's active model most of the turn; the pin only bites when the orchestrator explicitly dispatches with a model override. That's a rare-enough surface that a per-run maintainer decision beats a repo-wide flip.

### Concrete change (deferred — placeholder for when the trigger arrives)

When the maintainer wants to take this on:

1. Decide the pin: `claude-opus-5` primary + `claude-sonnet-5` fallback, or keep the 4-line and add an explicit "considered Opus 5 on <date>, held off because <reason>" comment.
2. Update `.harness-profile` model block + the `project-init` template so new projects start on the current tier.
3. Grep-and-replace any hard-coded model IDs in `docs/waves/wave1-harness-model-pin-profile-schema.md`, `docs/specs/2026-04-19-harness-model-pin-and-effort-routing.md`, and `.claude/agents/*.md` (spec-planner etc. may name a model).
4. Re-derive `effort_default` if Anthropic ships tier-specific guidance for Opus 5.

### Expected payoff (when applied)
- Consumer projects created after the flip inherit the current-tier default without a per-project override.
- One less "why is this project pinned to a year-old model" question at handoff time.

## 4. Ship the harness as a Claude Code plugin marketplace alongside the symlink install

**Source:** [Customize Claude Code with plugins — claude.com/blog, 2026-08-05](https://claude.com/blog/claude-code-plugins). Companion: [Discover and install prebuilt plugins through marketplaces](https://code.claude.com/docs/en/discover-plugins). Reference implementations: [`anthropics/claude-plugins-official`](https://github.com/anthropics/claude-plugins-official), [`anthropics/skills`](https://github.com/anthropics/skills).

### Why it's relevant
The 2026-08-05 launch introduced `/plugin install <name>@<marketplace>` as the sanctioned distribution channel for bundles of skills + subagents + hooks + MCP servers. A marketplace is a git repo with a `.claude-plugin/marketplace.json` manifest — architecturally almost identical to how the harness already ships.

Today, the harness installs by cloning the repo and symlinking `skills/` out to `~/.claude/skills/` (see `CLAUDE.md` "Skills directory layout" — "Symlinked OUT to `~/.claude/skills/`"). `INSTALL-FOR-COLLEAGUE.md` documents the setup for hand-off. `grep -rn "marketplace.json\|/plugin install" /home/user/claude-harness` returns **zero hits** — the harness is not (yet) available via `/plugin install`.

Two paths a plugin package would open:

1. **Discovery.** Someone in Anthropic's official or community marketplace could find `claude-harness` without knowing the git URL; the `INSTALL-FOR-COLLEAGUE.md` handoff becomes `/plugin install claude-harness@agaleraib`.
2. **Per-skill installability.** Right now, adopting *one* harness skill (say `run-loop`) requires cloning the whole repo. A marketplace lets a consumer pick individual skills, which matches how Anthropic's own `anthropics/skills` marketplace is structured (`/plugin install document-skills@anthropic-agent-skills`).

### Why this is `defer`, not `apply`

- **Solo tooling, no external consumers today.** The whole distribution story is the symlink install for one maintainer plus (eventually) `INSTALL-FOR-COLLEAGUE.md` for a first collaborator.
- **Plugin format is not yet standardized around the harness's shape.** The harness's `skills/` layout is standard, but its `_shared/` sibling (TypeScript engine for `/run-loop`) and its `.harness-state/` + `.harness-profile` conventions don't have a canonical spot in `.claude-plugin/marketplace.json`. Adopting the plugin format would either force a repackage or accept second-class hosting for the non-skill artifacts.
- **Symlink install has properties the plugin format doesn't.** Skills are the source of truth in this repo; `~/.claude/skills/` is derived. Editing a symlinked skill lets the maintainer test changes without a per-edit reinstall cycle. Plugin installs pin a version.
- **Small speculative cost, small speculative benefit.** Per the routine's rubric, "speculative for solo tooling" defers rather than rejects — flag for the maintainer's awareness.

### Concrete change (deferred)

When/if the maintainer wants to take this on:

1. Add `.claude-plugin/marketplace.json` at the repo root pointing at each skill in `skills/` as a plugin entry. Reference [`anthropics/skills/.claude-plugin/marketplace.json`](https://github.com/anthropics/skills/blob/main/.claude-plugin/marketplace.json) for the schema.
2. Decide the pack shape: one big `claude-harness` plugin (all skills, one install), or one plugin per skill (`/plugin install run-loop@claude-harness`). The `anthropics/skills` repo does per-skill; `anthropics/claude-plugins-official` does per-plugin.
3. Update `INSTALL-FOR-COLLEAGUE.md` to document the plugin-install path alongside the symlink path.
4. Test locally with `/plugin install <name>@file://$PWD` before publishing.

**Scope: speculative** — no external distribution demand today.

### Expected payoff (when applied)
Someone else installing the harness would run `/plugin install claude-harness@agaleraib` instead of following `INSTALL-FOR-COLLEAGUE.md` step by step; discoverable via the community marketplace.

**Verify before applying:**
1. `find /home/user/claude-harness -name "marketplace.json"` — should return nothing today; if it hits, the marketplace file has been added and this § is stale.
2. Confirm the plugin marketplace format is still `.claude-plugin/marketplace.json` (not renamed) at apply time — the format was 3 months old at the time of writing this suggestion.
3. Check whether Anthropic has published a canonical location for **non-skill** artifacts (`_shared/`, `.harness-state/`) that a plugin might carry; if so, that changes the packaging decision in Concrete-change step 1.

**Recommended verdict:** defer until multi-user distribution matters — speculative for solo tooling; symlink install works today; plugin format may still evolve. Flag for maintainer awareness in case a colleague-handoff surfaces the "how do I install this" friction.
**Status:** PENDING — awaiting triage in PR review

## 5. Cross-check the harness's `skill-creator` against Anthropic's improved skill-creator (Executor / Grader / Comparator / Analyzer)

**Source:** [Improving skill-creator: Test, measure, and refine Agent Skills — claude.com/blog](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills). Announced updates: the improved skill-creator plugin ships four composable agents — **Executor** (runs skills against eval prompts), **Grader** (evaluates outputs against expectations), **Comparator** (blind A/B between skill versions), **Analyzer** (suggests improvements) — plus Create / Eval / Improve / Benchmark operating modes.

### Why it's relevant (and why it's `reject — already in place`)
The harness's `skills/skill-creator/` already ships:

- `agents/grader.md` — reviews transcripts + outputs against expectations; equivalent to Anthropic's Grader.
- `agents/comparator.md` — blind A/B judgment of two outputs (labeled A/B, does not know which skill produced which); equivalent to Anthropic's Comparator.
- `agents/analyzer.md` — suggests targeted improvements based on results; equivalent to Anthropic's Analyzer.
- `scripts/run_eval.py`, `scripts/aggregate_benchmark.py`, `scripts/improve_description.py`, `scripts/quick_validate.py`, `scripts/package_skill.py`, `scripts/generate_report.py`, `scripts/run_loop.py` — the execution + eval + iteration + packaging machinery.
- The SKILL.md body has explicit sections for **Creating a skill**, **Running and evaluating test cases**, **Improving the skill**, **Blind comparison**, **Description Optimization** — parity with Anthropic's Create / Eval / Improve / Benchmark modes.

**The one visible gap** is that Anthropic ships an **Executor** as a distinct agent (`agents/executor.md`); the harness bakes that role into `scripts/run_eval.py`. Functionally identical (script runs the skill against an eval prompt and produces a transcript+outputs), just architecturally different.

### Concrete change

None this run. Two paths if the maintainer wants to close the four-agent parity gap for consistency with Anthropic's docs (worth 30 min at most):

1. **Extract `agents/executor.md`** as a thin wrapper that documents the "run skill against eval prompt → produce transcript+outputs" contract, and points at `scripts/run_eval.py` as the implementation. The Grader, Comparator, and Analyzer already exist as separate agent files.
2. **Or, leave it.** The script-based executor is simpler to invoke from `run_loop.py` and doesn't cost anything the maintainer notices. Anthropic's four-agent decomposition serves their multi-plugin marketplace shape; a single-tenant harness doesn't need the same decomposition.

### Expected payoff

## 7. Document Claude Code's new sandbox settings (`sandbox.filesystem.disabled`, `sandbox.network.strictAllowlist`)

**Source:** [Making Claude Code more secure and autonomous with sandboxing — anthropic.com/engineering](https://www.anthropic.com/engineering/claude-code-sandboxing) and [Beyond permission prompts — claude.com/blog](https://claude.com/blog/beyond-permission-prompts-making-claude-code-more-secure-and-autonomous). Confirmed shipped in Claude Code v2.1.216 (2026-07-20, `sandbox.filesystem.disabled`) and v2.1.219 (2026-07-24, `sandbox.network.strictAllowlist`) per [`code.claude.com/docs/en/changelog`](https://code.claude.com/docs/en/changelog).

### Why it's relevant
Anthropic's sandboxing feature (Linux bubblewrap + macOS seatbelt at the OS level) reports "sandboxing safely reduces permission prompts by 84%" internally. The two new settings shipped in July are the escape hatches:

- `sandbox.filesystem.disabled` — turns off filesystem isolation; use when the harness needs to touch paths outside cwd.
- `sandbox.network.strictAllowlist` — forces network calls to go through the allowlist; blocks accidental egress.

`grep -rn "sandbox\.\(filesystem\|network\)\|bubblewrap\|seatbelt" /home/user/claude-harness` returns **zero hits** — none of the harness's docs, skills, or examples reference these settings today. That's not a problem *if* the harness's target sessions all run outside a sandbox (which is the current default: the harness runs in local shells, sandcastle containers, and GitHub-triggered cloud routines — none of which apply Claude Code's own sandboxing on top).

The gap becomes an issue when:
- A consumer project sets up a sandboxed dev container and `run-wave` behaves differently under sandbox rules (e.g., worktree creation outside cwd fails).
- The maintainer wants to opt into sandboxing for the harness itself as a defense-in-depth (the 84% permission-prompt reduction cited by Anthropic is genuinely material for solo autonomous runs).

### Why this is `defer` (with `scope: speculative`)

- Today the harness's sessions don't run under Claude Code sandboxing, so the settings aren't exercised.
- Adding a doc paragraph that names the two settings is trivial (~10 min), but nobody has hit a failure they'd have avoided.
- Sandboxing behavior is under active iteration (v2.1.216 → v2.1.219 shipped both settings in 4 days); the shape may still change.

+### Sandboxing interactions

+Claude Code (v2.1.216+) can run inside an OS-level sandbox (Linux bubblewrap, macOS seatbelt) that isolates filesystem writes to cwd and routes network through an allowlist. See [`code.claude.com/docs/en/sandbox-environments`](https://code.claude.com/docs/en/sandbox-environments). Two escape hatches:
