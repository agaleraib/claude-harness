| Adversarial framing | Documented "blocks merge / degrades quality / minor" priority | No documented priority taxonomy |

## 4. Spec how dynamic workflows relate to the `orchestrator` + `/run-wave` pattern

**Source:** [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) and the follow-up engineering deep-dive [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Docs: [Orchestrate subagents at scale with dynamic workflows — code.claude.com/docs/en/workflows](https://code.claude.com/docs/en/workflows). Available on Pro/Max/Team/Enterprise + Anthropic API + Bedrock/Vertex/Foundry as a research preview; requires v2.1.154 or later. Limits: **up to 16 concurrent agents, 1,000 agents total per run**; no mid-run user input; agents always run in `acceptEdits` mode regardless of session mode. Default trigger: the keyword `ultracode` in a prompt, or `/effort ultracode` for session-wide auto-workflow planning. Built-in bundled workflow: `/deep-research`.

### Why it's relevant

This is the largest architectural overlap with the harness so far in 2026. The two patterns solve the same problem — *orchestrate many subagents on a task too large for one conversation* — with different mechanics:

| | harness `orchestrator` + `/run-wave` | Anthropic dynamic workflows |
|---|---|---|
| Plan lives in | Spec file (`docs/specs/<date>-<topic>.md`) + the orchestrator agent's prompt | JS script Claude writes for the task |
| Intermediate results | Subagent conversation context, with handoffs by file + `last_exit.md` | Script variables (off-context) |
| Concurrency | Sequential (one subagent at a time) with `model_routing: on` dispatch | Up to 16 concurrent agents per run, hard cap 1,000 total |
| Repeatability | Re-run `/run-wave N` from the same spec | Save the JS script to `.claude/workflows/<name>.js` as a slash command |
| Trigger | `/run-wave N` invokes orchestrator on Phase N of a spec | `ultracode <task>` (keyword), `/effort ultracode` (session), or `/<saved-workflow>` |
| Failure mode | Re-run the wave; orchestrator re-reads the spec | Resume cached agents within the same session; restarts fresh across sessions |
| User-in-loop | Heavy: planning-loop, parking-lot triage, exit ritual | None mid-run (only `acceptEdits` for permissions) |
| Cost model | Single session; per-task effort routing | Multi-agent fan-out; significantly more tokens per run |

Three forward paths, each with non-trivial design implications:

1. **Adopt** — replace or supplement `/run-wave` with a dynamic-workflow-shaped `/run-wave-w` that emits a JS script and runs it. Loses the operator-in-loop (parking-lot, exit ritual) but gains 16x concurrency. Significantly cheaper for embarrassingly-parallel waves (e.g. migration across N files).
2. **Ignore** — `/run-wave` keeps its operator-curated, sequential, spec-anchored shape. Dynamic workflows handled by the user as an ad-hoc `ultracode` invocation outside the harness flow. Cheapest path; preserves the planner→orchestrator→evaluator triad.
3. **Hybridize** — keep `/run-wave` as the operator-curated wave runner; introduce a `/workflow-wave` for waves explicitly tagged in the spec as "parallel, no operator review needed". The orchestrator routes wave-by-wave based on the spec's tag. Hardest design — needs a wave-tag schema in `docs/specs/<date>-<topic>.md`, dispatch logic, and a "did anything horrible happen?" check after the workflow exits.

The choice depends on whether the harness's value-prop centers on *operator-in-loop discipline* (path 2) or *substantive multi-agent throughput* (paths 1/3). That's exactly the question `/spec-planner` exists to answer.

### Concrete change

**No code in this run.** Open a spec via `/spec-planner` titled `docs/specs/2026-06-05-dynamic-workflows-orchestrator-overlap.md` with the questions above as the discovery framing:

1. Where does the harness's value-prop sit on the operator-in-loop ↔ throughput axis?
2. What % of waves the harness has run to date were embarrassingly-parallel and would have benefited from 16x concurrency? (Sample: the closed-wave files under `.harness-state/`.)
3. If hybridize: what does a wave-tag schema look like? (`parallel: true`, `requires_operator_review: true`, etc.)
4. If adopt: what's the migration path for the existing `orchestrator` agent, `model_routing` toggle, `task_id` logging contract, and the `_shared/dispatch_logger.sh`?
5. What does the harness give up by losing per-turn operator review? (parking-lot triage during a wave, mid-wave course correction)
6. Does the `ultracode` keyword interact safely with the harness's existing `/effort xhigh` and `model_routing` settings?

### Expected payoff (when applied)

A clear decision (with rationale) on whether dynamic workflows replace, supplement, or stay out of the harness's wave-running flow. Forestalls a costly mid-wave realization later that one path was always strictly better. Spec doc becomes the durable record of the analysis.

## 5. Bookkeeping: `/goal` parallels the harness's `today_goal.md` + `current_micro.md` pattern

**Source:** [Claude Code What's new — Week 20, May 11–15, 2026](https://code.claude.com/docs/en/whats-new/2026-w20). Week 20 shipped `/goal`: *"Set a completion condition and Claude keeps working toward it across turns without you prompting each step. After every turn, a fast model checks whether the condition holds; if not, Claude starts another turn instead of handing control back."* Docs: [Goals — code.claude.com/docs/en/goal](https://code.claude.com/docs/en/goal). Works in interactive, `-p`, and Remote Control modes.

### Why it's relevant

The harness has **two existing goal-tracking layers**, both operator-curated:

- `today_goal.md` — single-day goal, read at `session-start`, updated at `session-end`. References: `skills/session-start/SKILL.md`, `skills/session-end/SKILL.md`, `skills/triage-parking/SKILL.md`, `skills/park/SKILL.md`, `skills/micro/SKILL.md`.
- `current_micro.md` — current micro-task under `/micro`, operator-set, lives until the micro is committed.

`/goal` is a **within-session, machine-verified completion-condition loop**: it keeps Claude grinding on the same task across N turns until a fast-model check says the condition holds. The harness's pattern is **operator-set, cross-session, prose-state**: the operator writes the goal text, the session start/end ritual surfaces it, and progress is measured by the operator looking at `last_exit.md` and committing forward.

They solve **overlapping but distinct** problems:

| | harness `today_goal.md` | `/goal` |
|---|---|---|
| Lifespan | Cross-session (often multi-day) | Single session |
| Verification | Operator reads at `session-end` | Fast-model check after every turn |
| Loop semantics | Operator-driven (open new sessions, re-read goal) | Claude-driven (auto-continues until condition holds) |
| Granularity | Day or sub-day goal | Tight verifiable condition (e.g. "all tests in test/auth pass and lint is clean") |
| Risk | Drift between session and goal | Runaway token spend if condition is hard to satisfy |

Worth noting **but not changing** today — the patterns are complementary. The harness's `today_goal.md` could *call out to* `/goal` inside a session ("`/goal` until `today_goal.md`'s acceptance criterion holds") but that's a workflow tweak, not a structural change. ## 6. Bookkeeping: `/reload-skills` + `SessionStart` `reloadSkills: true` is the hook `shared-root-init` + `setup-harness` install steps want

**Source:** [Claude Code What's new — Week 22, May 25–29, 2026](https://code.claude.com/docs/en/whats-new/2026-w22). Week 22 "Other wins": *"New `/reload-skills` command re-scans skill directories without restarting, and `SessionStart` hooks can return `reloadSkills: true` to make skills they install available in the same session."* Also: *"Plugins in `.claude/skills` directories are now loaded automatically, no marketplace required."*

### Why it's relevant

The harness installs skills in two places:

- `setup-harness` (`skills/setup-harness/SKILL.md`) — guides the operator through symlinking the harness's `skills/` into `~/.claude/skills/`. Today, the install instructions tell the operator to restart Claude Code to pick up the new skills.
- `shared-root-init` (`skills/shared-root-init/SKILL.md`) — initializes `~/.claude/memory/` via an atomic staging-then-rename. Doesn't install skills directly but establishes the shared root that the install layer depends on.

Neither is broken today; both work by virtue of the operator restarting their Claude Code session. But Week 22's `/reload-skills` and `SessionStart` `reloadSkills: true` open up a smoother install path:

- A `SessionStart` hook in `.claude/settings.json` could detect that `~/.claude/skills/<harness>/` was just-installed (last-modified timestamp newer than the session start), run `shared-root-init`'s atomic rename if needed, and return `reloadSkills: true` to make all the just-installed skills available in the current session without restart.
- The same `SessionStart` hook could short-circuit `session-start` ritual steps that today depend on a fresh session (parking-lot triage, `last_exit.md` read).

This is **not a small change** — `.claude/settings.json` is empty today (`{"hooks": {}}`, verified), and adding a `SessionStart` hook means thinking through interaction with the existing `session-start` SKILL, the `git fetch` step it does for the Anthropic-reviews routine, and the install-vs-day-to-day path split. Worth flagging now so the next time `setup-harness` gets material work, the maintainer remembers the option exists.

### Concrete change (deferred)

When `setup-harness` next gets a structural rework:

1. Spec the `SessionStart` hook: what does it detect, what does it run, what does it skip on subsequent runs?
2. Decide where the install detection lives — last-modified timestamp on the symlink dir, a sentinel file in `.harness-state/`, or a hash of the `~/.claude/skills/` contents.
3. Update `setup-harness` install instructions to drop the "restart Claude Code" step.
4. Document the `/reload-skills` slash command as the manual fallback for non-hook-eligible flows (e.g. operator-driven mid-session skill addition).

### Expected payoff (when applied)

Install-then-use becomes one command instead of install-restart-use. Removes a class of confused-operator support questions ("I ran setup-harness but the skills aren't there!"). Cheap, no architectural change.

### Verify before applying

**Recommended verdict:** defer until next material rework of `setup-harness` — neither install path is broken today, and adding a `SessionStart` hook is a structural change that should ride along with other install-layer work rather than be done in isolation. Flagging now is the value; the actual change isn't urgent.
