## 3. Position Anthropic's Dynamic Workflows alongside `/run-loop`

**Source:** [Introducing Claude Opus 4.8 — anthropic.com/news, 2026-05-28](https://www.anthropic.com/news/claude-opus-4-8) (launch companion). Anthropic shipped **Dynamic Workflows** as a Claude Code first-class feature alongside Opus 4.8: an in-session tool where Claude plans work, fans out to parallel subagents (capped at **1,000**), checks intermediate results, and resumes interrupted runs from saved progress. Public demonstration: porting the Bun project from Zig to Rust — **~750,000 lines of code in 11 days**, 99.8% pass rate on the existing test suite. Ships as a research preview.

### Why it's relevant
The harness has its own multi-run parallelism story: `/run-loop` drives ready `plan.md` waves or `gh` `ready-for-agent` issues end-to-end behind a mechanical merge gate (`skills/run-loop/SKILL.md`, Wave 18–25). That story includes:

- **Serial-off-HEAD merge model** — one temp branch per item, `--ff-only` merge, no PR-and-human round-trip on green gates.
- **Multi-runner architecture** — Codex sandbox default lane, Claude worktree lane with denylist PreToolUse hook, sandcastle container lane.
- **Cross-run resume** — "resume is just 'run again.'"

Anthropic's Dynamic Workflows is the **in-session** analog: one Claude Code session that fans out subagents and coordinates them without a cross-run mechanical gate. The two operate at different layers:

| Layer | `/run-loop` (harness) | Dynamic Workflows (Anthropic) |
|---|---|---|
| Session model | Multi-run (each item is a separate `claude` invocation) | Single-session (one session orchestrates all subagents) |
| Merge gate | Mechanical, per-item, `ff-only` off HEAD | Session-internal; PR/merge is out-of-scope |
| Resume | "run the loop again" — state is on disk (`.harness-state/`, `docs/plan.md` waves) | In-session `saved progress`; interrupted runs resume within a single session context |
| Concurrency cap | ~1 concurrent item (serial off HEAD; parallelism is at the multi-runner layer) | Up to 1,000 subagents in parallel |
| Best fit | Long-horizon drain of independent work items with real merge gates | Massive parallel decomposition of a single task inside one session |

They are **complementary**. `/run-loop` still owns the multi-run drain-with-merge-gate story; Dynamic Workflows fills a gap `/run-loop` doesn't try to fill (in-session parallelism for a single large task).

## 4. Bookkeeping: Building a C compiler with parallel Claudes corroborates the `/run-loop` git-task-locking pattern

**Source:** [Building a C compiler with a team of parallel Claudes — anthropic.com/engineering](https://www.anthropic.com/engineering/building-c-compiler). Nicholas Carlini (Anthropic Safeguards Team) built a C compiler in Rust — 100,000 LOC, compiles the Linux kernel, supports x86/ARM/RISC-V — using **16 parallel Claude agents** over ~2,000 sessions, ~$20,000 in API cost, using a **simple loop harness** and **task locking via git**. Key learnings the post foregrounds:

- High-quality tests are the coordination substrate ("tests are the plan").
- Design for LLM limitations: context-window pollution + time blindness.
- Parallelization comes from clever test design, not from smart schedulers.

### Why it's relevant
The harness's `/run-loop` (Wave 18–25) implements the **same conceptual pattern in a smaller frame**: one work source (`plan.md` waves or `gh` issues), a merge gate off HEAD, `--ff-only` auto-merge on green, `git worktree` isolation per item, denylist PreToolUse hook, and a `ReadinessGatedSource` that withholds a blocked item until its blockers merge. See specifically:
- `skills/run-loop/SKILL.md:112` — "The per-item gate IS the merge gate ... `git merge --ff-only` ... no PR, no `git push`, no human, no re-gate."
- `skills/run-loop/SKILL.md:103` — denylist PreToolUse hook as the hard gate for worktree items.
- `skills/_shared/loop/providers/wave-provider.ts` — wave/issue readiness sequencing.
- `sandcastle_mattpocock_architecture.md` — the serial-off-HEAD architecture doc.

Carlini's writeup validates two design choices already in the harness:

1. **Git as the task-locking mechanism** rather than a bespoke coordinator or a distributed lock service. The harness's `/run-loop` uses `git merge --ff-only` off HEAD (no divergence-tolerant 3-way merge) — same "let git be the arbiter" ethos.
2. **Loop harness as a simple, resumable primitive.** Carlini: "a simple loop harness." Harness: "resume is just 'run again.'" Same shape.

This is **corroboration**, not a new ask. Same disposition as `2026-05-10 §3` (dreaming/Managed Agents corroborating `session-end`), but here the corroborated pattern is the freshly-productionized `/run-loop` rather than the older `session-end` ritual.

The `2026-05-10 §3` precedent applies: bookkeeping notes are a durable record, not a to-do.
2. **Promotion path** — *if* the maintainer wants an outbound reference: add one bullet to `README.md` "References" section (`README.md:1111–1118`) linking Carlini's post as an example of the same pattern at 100K-LOC scale. ## 5. Consider packaging the harness as an official Claude Code plugin

**Source:** [`anthropics/claude-plugins-official` on GitHub](https://github.com/anthropics/claude-plugins-official) — Anthropic launched the official Claude Code plugin directory on **2026-05-22**, shipping 55+ vetted plugins (language servers, MCP integrations, security review, git workflows). Out-of-the-box in Claude Code v2.1.143+ the `/plugin` panel comes pre-configured with the Anthropic marketplace; a `/plugin` panel `Discover` screen browses the catalog. Community marketplaces (`claudemarketplaces.com` referenced from third-party coverage) list 70+ additional plugins that passed automated safety screening. A plugin is a packaged folder that bundles one or more skills + MCP server configs + hooks + slash commands + agent definitions into one installable — exactly the surface the harness ships today.

### Why it's relevant
The harness distributes via a **symlink model** (per `CLAUDE.md` and `skills/setup-harness/SKILL.md`): `~/.claude/harness/` is the source-of-truth clone, `~/.claude/skills/<name>` are symlinks into `~/.claude/harness/skills/<name>`, and `/setup-harness` installs the symlinks on target machines. This works today and has real virtues:

- **Live edits.** A change to `~/.claude/harness/skills/foo/SKILL.md` is instantly visible in every consuming project; no re-install cycle.
- **Debuggability.** `readlink -f ~/.claude/skills/foo` returns the source path — nothing hidden.
- **No packaging boundary.** The harness can ship files that don't fit the plugin schema (e.g. shared `_shared/loop/` TypeScript modules that multiple skills import via `../_shared/loop/...`).

Anthropic's plugin directory offers a different set of virtues:

- **Discoverability.** `/plugin` panel `Discover` screen; the harness lives outside that surface today.
- **Standard install UX.** `/plugin install <name>` collapses multi-step setup to one command — matching what most Claude Code users now expect.
- **Safety scanning.** Community plugins pass automated safety screening; the official directory adds curator review. The harness's `/setup-harness` handshake is a manual approval flow, not a scanner.
- **Version pinning.** Plugin installs are versioned; the current `git pull` in `~/.claude/harness/` is unversioned.

This is a real distribution decision the maintainer should evaluate — but not urgently:

- The harness's symlink model is documented, working, and has a clear audit surface.
- Migrating would mean either (a) shipping duals (both symlink + plugin) or (b) rebuilding `/setup-harness` around plugin install. Both are non-trivial.
- No consumer project has asked for `/plugin install claude-harness` yet.

### Concrete change (deferred)
None this run. When/if the maintainer wants to evaluate:

1. **Spec pass first** (via `/spec-planner`). The question isn't "how do we package as a plugin" — it's "what does the harness lose if we do." Cross-plugin skill imports (`_shared/loop/`), the symlink debugging surface, and the git-pull update model all need explicit design decisions.
2. **Decide the dual-vs-single-mode question.** Ship the harness as a plugin **and** keep the symlink flow, or migrate cleanly? The `anthropics/claude-plugins-official` repo has precedent for both — some vetted plugins ship additional install docs beyond the `/plugin install` path.
3. **Confirm plugin schema fits the harness's shape.** In particular, the harness ships `criteria/*.md` files (project-specific review rubrics) — check whether the plugin schema has a first-class slot for these or whether they'd need to move.
4. **Check whether being in the official directory changes the maintenance contract** (Anthropic vets, so bug reports may flow through the directory rather than the repo).

### Expected payoff (when evaluated)
Discovery via `/plugin` panel + one-command install is a real UX win. Whether the trade-offs are worth it depends on how the maintainer values (a) reaching the broader Claude Code user base vs. (b) the current symlink flow's debuggability + live-edit speed.

### Why this is `defer` and not `spec` yet
Two conditions would move this to `spec`:
- A consumer project explicitly asks for `/plugin install claude-harness`.
- The plugin schema evolves to natively support cross-plugin shared modules (would remove the biggest structural blocker).
Until then, the maintainer is right to keep the symlink flow — it's not broken, and the plugin ecosystem is still churning (community marketplaces + official directory both introduced within the last 60 days).

**Verify before applying:**
