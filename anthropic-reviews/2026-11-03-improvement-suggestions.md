## 2. Spec the large-codebases practices Anthropic published 2026-05-14

**Source:** [How Claude Code works in large codebases: Best practices and where to start — claude.com/blog, 2026-05-14](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)

### Why it's relevant
The post lays out a layered configuration model for Claude Code in a large repo. Four of its practices land squarely on this harness's shape:

1. **Path-scoped skills.** The post calls out that skills "can be path-scoped so they activate only in the relevant part of the monorepo." This harness ships 24 global skills (all at `skills/<name>/SKILL.md`, symlinked out to `~/.claude/skills/`). None are path-scoped today — they're all global on the consumer's machine.
2. **`permissions.deny` in `.claude/settings.json`.** The post recommends committing deny rules for generated files, build artifacts, and third-party code. The harness's own `.claude/settings.json` is `{ "hooks": {} }` — no permissions block at all. `grep -r "permissions.deny" .` returns zero hits across the repo.
3. **A 3–6 month configuration review ritual** ("Review configuration every three to six months, and after major model releases if performance plateaus"). The harness has `methodology.pivot_check_auto_days: 30` in `.harness-profile`, which only triggers a plan-level review via `session-start` — not a methodology/skill-level audit. No "after model release" trigger exists; §1 of this file is a direct example of what such a ritual would catch.
4. **Stop hook that proposes CLAUDE.md updates after a session** (optional, for continuous improvement). The harness's `session-end` skill already triages the parking lot and writes an exit note; it does not propose CLAUDE.md edits. This is an opt-in extension, not a replacement.

### Why this is spec, not apply or micro
Each of the four bullets is small individually, but together they:
- introduce a new convention (path-scoped skills — must land in `skill-creator` + `setup-harness` + the public SKILL.md schema docs);
- edit `.claude/settings.json` in a way that propagates to every project running `setup-harness` (so a wrong default `permissions.deny` would be sticky);
- add a new recurrence to the harness (post-model-release audit) that needs to live somewhere between `.harness-profile` and `session-start`;
- extend `session-end` with a loop into CLAUDE.md edits, which touches memory discipline.

This is more than one `/micro` can handle, and the design choices (which files to deny? what triggers the audit? how does path-scoping interact with the `_shared/` convention from Wave 9?) are not derivable from the post alone. Hand to `/spec-planner`.

### Suggested decomposition for the spec

- **§2a Path-scoped skills:** audit which of the 24 global skills would genuinely benefit from path scoping (candidates: `a11y-check` → frontend subtrees only; `api-smoke-test` → services/api; `migration-check` → db/migrations). Decide whether this harness ships path-scoped variants or publishes the pattern as a skill-creator template.
- **§2b `permissions.deny` defaults:** pick a conservative default set that applies to any consumer project (`node_modules/`, `.next/`, `dist/`, `build/`, `*.lock`). Draft the `.claude/settings.json` block in `setup-harness`. Verify no conflicts with existing hooks dispatcher.
- **§2c Post-model-release audit:** add a trigger to `session-start` or `harness-status` that fires once per new primary model ID (compare `model.primary` against a last-seen cache). The audit prompt should run `/anthropic-review-apply` + a drift-detector pass.
- **§2d Optional stop-hook for CLAUDE.md proposals:** gate behind an explicit opt-in in `.harness-profile`; must not run on `session-end` by default (noise risk).

### Expected payoff
Imports two durable practices (path-scoping, deny defaults) and one hygiene ritual (post-release audit) that the harness is already feeling the lack of — §1 of this run is literally the kind of drift the post-release audit would surface automatically.

**Verify before applying:**
1. `grep -r "path-scoped\|path_scoped" skills/ docs/` — must return zero hits for the pattern to still be novel.
2. `cat .claude/settings.json` — if a `permissions` block has been added since this run, §2b's default must not clobber it.
3. `grep -n "post.release\|model.release.*audit\|post.model.audit" .harness-profile skills/session-start/SKILL.md skills/harness-status/SKILL.md` — must return zero hits for §2c to be novel.
4. Confirm the 2026-05-14 blog is still the canonical reference at spec time — Anthropic has published newer best-practices work since (e.g. the "fold subagents" post of 2026-10-22). Pull both and merge.

**Recommended verdict:** spec — four coupled changes, each small, but together they introduce conventions that need design before coding. `/spec-planner` should produce `docs/specs/2026-11-03-large-codebase-practices.md`.

## 3. Record the "fold subagents" migration path against this harness's agent surface

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

### Why it's relevant
The post's thesis — subagents multiply, latency rises, brand voice fragments, and newer models can handle more in one loop — is a useful lens for any harness with its own agent set. This harness ships six agents in `.claude/agents/` (`code-reviewer`, `generator`, `orchestrator`, `project-tracker`, `spec-planner`, `ui-evaluator`) plus session-type agents the Claude Code runtime adds (`general-purpose`, `Explore`, `Plan`, `fork`, `statusline-setup`, `claude-code-guide`). That's well below the ~30–50 degradation band the post identifies, and no symptom of fragmentation is documented today.

The two sections worth bookmarking for the next time an agent plateaus:

- **The migration path** — build an eval, merge tightly coupled specialists, consider converting a subagent into a tool, fold in one at a time and keep only if the folded version scores worse. This is the exact shape 2026-04-19 §5 (adversarial-reviewer evals) sketched for the harness's own reviewers.
- **The 30–50 tool-definition degradation band** — the post reports that tool choice degrades past ~30–50 tool definitions. This repo's tool manifest is driven by Claude Code's own session-start injection; the harness doesn't currently track its own effective tool count. If a future agent gets slow at tool selection, the post gives a concrete threshold to measure against.

### Why this isn't `apply` or `spec`
No active symptom. The harness's agents are small in number, each has a distinct rubric (`criteria/`), and the orchestrator doesn't dispatch them in a fan-out shape where latency compounds. The right trigger is *evidence* — a `code-reviewer` run that misses a known-good catch, or a `generator` that stalls on tool selection. Until then, this is a bookmark.

### Concrete action (if deferred becomes applied)
If a specific agent's rubric score plateaus (say `code-reviewer` misses adversarial findings three runs in a row), run the post's migration playbook on that agent: write a before/after eval, try merging it into the orchestrator, score, keep the folded version only if it scores worse.

**Verify before applying:**
1. `ls .claude/agents/ | wc -l` — if the agent count has grown past ~15 since this run, the post's degradation band is suddenly in range and the deferral should re-open.
2. Pull the current eval scores for each adversarial agent (`criteria/code-reviewer*.md`, `criteria/ui-evaluator*.md`) and confirm no agent has shown a drop vs. its last baseline. A dropped score is the specific trigger this § is waiting for.
3. Confirm the post's URL still resolves and the thesis hasn't been updated with new numbers.

**Recommended verdict:** defer until a specific adversarial agent's eval shows degradation. Bookmark the migration-path playbook for that moment.
**Status:** PENDING — awaiting triage in PR review

## 7. "Agentic coding and persistent returns to expertise" (2026-06-16) corroborates the harness's planning/execution split

### Why it's relevant
