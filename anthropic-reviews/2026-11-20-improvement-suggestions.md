## 2. Add a `verification-strategies` subsection to `.claude/agents/code-reviewer.md` naming end-to-end / property / differential tests as first-class checks

**Source:** [How the Claude Code team thinks about verification — claude.com/blog, 2026-11-16](https://claude.com/blog/how-the-claude-code-team-thinks-about-verification). The Anthropic post describes three test families they lean on when coding agents produce results:
- **End-to-end tests** — the "does the thing we claimed actually work in a real pipeline" check.
- **Property-based tests** — invariants that must hold for *any* input, not a handful of hand-picked ones.
- **Differential tests** — run the new behavior and the reference behavior side-by-side, compare outputs.

Companion post (same theme, two weeks earlier): [Using a "chaos loop" to harden the Claude Docs launch — 2026-11-17](https://claude.com/blog/chaos-loop-claude-docs-launch) — deliberate failure injection in a staging cluster as a verification pattern. That post's methodology is production-scale and doesn't map directly to a solo tooling repo, so §2 focuses on the verification-types post.

### Why it's relevant

The harness's `code-reviewer` agent currently runs tests mechanically ([`.claude/agents/code-reviewer.md:19–30`](../.claude/agents/code-reviewer.md)):

```
Run every verification the project supports. Do NOT skip any:

# Find and run these (adapt to the project)
npm run build / bun run build / cargo build    # Does it compile?
npm run typecheck / tsc --noEmit               # Type errors?
npm test / bun test / cargo test               # Tests pass?
npm run lint / eslint . / ruff check           # Lint clean?
```

The grep confirms today's `code-reviewer.md` does **not** name `differential`, `property`, or `golden` tests as distinct categories:

```
$ grep -n "differential\|property-based\|property test\|golden" /home/user/claude-harness/.claude/agents/code-reviewer.md
(no matches)
```

The Anthropic post's thesis is that *agents miss bugs because they only check the one case they built for* — which is the same failure mode `code-reviewer`'s adversarial stance exists to counter. Naming the three test types explicitly in the reviewer's rubric gives it a concrete axis to push back on. Example: a PR that ships a new function with a single unit test gets a "where are the property-based invariants?" comment instead of a generic "add more tests."

### Concrete change (if applied)

Append a subsection to `code-reviewer.md` between the current "Verify Mechanically" (ends around line 30) and the next section:

```markdown
### 2b. Push on Test Coverage Shape

When tests exist, don't just confirm they pass. Classify what kind of coverage they give:

- **End-to-end** — does an actual user flow run through this change? If the change touches a boundary (CLI, HTTP, DB) and there's no e2e test, flag it.
- **Property-based** — are there invariants that must hold for arbitrary inputs, not just the author's 2–3 picks? Serializers, parsers, and any `fromX(toX(x)) == x` round-trip should have property tests. Name the invariant you'd expect.
- **Differential** — when the change ports behavior from an existing path (new impl, new backend, new library), is there a test that runs both and compares outputs? Flag ports that lack them.

If the author says "it's covered" and none of the above are present, the coverage is shallow.

Reference: [How the Claude Code team thinks about verification](https://claude.com/blog/how-the-claude-code-team-thinks-about-verification) (2026-11-16).
```

Optional: add a bullet to `criteria/data-integrity.md` under "What to check" naming "no property-based invariants on serializers/parsers" as a flaggable finding.

### Expected payoff

Future `code-reviewer` runs produce findings against *the shape* of the test suite, not just its existence. A solo maintainer with no tests on their harness (per `.harness-profile.quality_bar.test_required: false`) gets less direct value, but every consumer project that installs the harness inherits a more rigorous reviewer out of the gate.

4. **Closer-fit triggers exist.** If/when a consumer project asks "why didn't the reviewer catch X?" and the diagnosis is "no differential test between old and new impl," *that* is the natural moment to add this subsection — with evidence.

## 3. Bookkeeping — Anthropic's "components of agent memory" post corroborates the 2026-05-13 memory system redesign, and names "dreaming" as a layer the harness doesn't yet have

**Source:** [The components of agent memory — anthropic.com/research, 2026-11-06](https://www.anthropic.com/research/components-of-agent-memory). The post proposes a four-layer hierarchy plus an offline consolidation pass:
- **Transcripts** — the searchable event log of a session.
- **Memory notes** — salient observations Claude writes *during* work.
- **Memory representations** — structured artifacts like linked wikis.
- **Injected context** — the small always-loaded layer.
- **Dreaming** — offline passes that correct notes against transcripts, build representations, and promote items between layers.

Key operational findings from the Pokémon-run experiments: inject only ~200 lines / 25KB; one page per entity (shared summary tables got overwritten by parallel writers — 57/57 facts vs 41/57); state the *purpose* of memory, not the procedure; wiki bloat is real (one grew 1.77× the source corpus); verify notes against transcripts later because wrong notes propagate.

### Why it's relevant

The harness has invested heavily in memory already — the **2026-05-13 memory system redesign** (`docs/specs/2026-05-13-memory-system-redesign.md`) ships the user-global shared root at `~/.claude/memory/` (USER.md, FEEDBACK.md, REFERENCES.md, PROJECTS.md, `feedback/`, `archive/`), plus the `/memory-prune` skill for manual curation and the `session-end` ritual's `last_exit.md` handoff.

Mapping the Anthropic post's layers onto the current harness:

| Anthropic layer | Harness equivalent | Status |
|---|---|---|
| Transcripts | Claude Code session logs; `.harness-state/orchestrator.log,jsonl` | ✅ present |
| Memory notes | `last_exit.md`; `parking_lot.md`; `current_micro.md` | ✅ present (manual) |
| Memory representations | `~/.claude/memory/FEEDBACK.md` + `feedback/*.md` cross-cutting | ✅ present (manual) |
| Injected context | `~/.claude/memory/USER.md` + per-cwd `MEMORY.md` (24.4KB cap, 200-line / 25KB discipline) | ✅ present — **matches Anthropic's injected-context sizing exactly** |

The alignment on injected-context sizing (post says Claude Code loads "first 200 lines or 25 KB of MEMORY.md") is direct validation of a convention the memory-system-redesign already follows. No change needed there.

The missing layer is **dreaming**: an automated offline pass that reviews recent transcripts + notes, corrects them, promotes patterns, and prunes stale entries. The harness today relies on the operator — `/memory-prune` is manual, session-end ritual's "How did today go?" prompt is user-answered.

## 5. Bookkeeping — "Building always-on agents" names inbox / timers / memory / permissions / outbox as the core primitives, reinforcing the still-deferred 2026-05-10 §2 (Cloud Routines migration for this routine)

**Source:** [Building always-on agents — claude.com/resources, 2026-11-13 (author: William Hu)](https://claude.com/resources/articles/building-always-on-agents). The post names five primitives for agents that run indefinitely across sessions:

1. **Event inbox** — a durable event list; one active worker per inbox.
2. **Timers** — follow-ups the agent sets for itself, plus recurring schedules on a known cadence.
3. **Memory** — durable files for user instructions, user notes, past messages, task progress.
4. **Permissions** — credential proxies, auto mode, deferred tool calls.
5. **Outbox** — a queue of outgoing messages delivered by a dispatcher.

Key architectural guidance: route all triggers through the inbox (not the agent directly), batch related events into one run, keep memory separate from the worker, store pointers for information held elsewhere.
