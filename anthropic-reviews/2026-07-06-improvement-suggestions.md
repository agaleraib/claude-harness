## 3. Position dynamic workflows alongside the harness's `orchestrator` agent + `/run-wave` + `/run-loop`

**Source:** [Introducing dynamic workflows — Claude by Anthropic](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) · [A harness for every task: dynamic workflows in Claude Code](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) · [Orchestrate subagents at scale with dynamic workflows — Claude Code Docs](https://code.claude.com/docs/en/workflows). Dynamic workflows shipped generally available with Opus 4.8 on 2026-05-28 (Claude Code v2.1.154+).

### Why it's relevant
A dynamic workflow is a **JavaScript orchestration script Claude writes**, executed by a Claude Code runtime, that spawns tens-to-hundreds of parallel subagents (nested up to 5 deep) while the main session stays responsive. That is architecturally the same shape as the harness's `orchestrator` agent (`.claude/agents/orchestrator.md`), which "reads spec tasks and dispatches each to opus, sonnet, or haiku subagents based on task complexity" — and the same shape `/run-wave` uses to dispatch spec tasks, and `/run-loop` uses to fan out over a work list.

Concretely, the overlap:
- **Dynamic workflows** = imperative JavaScript, Claude-authored, runtime-executed, hundred-subagent scale, PLAN mode reasoning, cross-checked results.
- **Harness orchestrator** = markdown-spec-driven, human-authored spec + Claude routing, logged decisions (`.harness-state/orchestrator.{log,jsonl}`), effort-tier routing, wave-gated.

Neither obsoletes the other today — dynamic workflows lack the harness's spec/routing-log/effort-tier plumbing; the harness orchestrator lacks the parallelism scale and the sandboxed runtime. But once a downstream project is running Opus 4.8 with dynamic workflows on by default (Max/Team/Enterprise plans), a reader will ask: "why is there a separate `orchestrator` agent in this harness?"

Zero mentions of dynamic workflows in the repo today: `grep -rn "dynamic workflow\|dynamic-workflow\|/workflow " .` returns nothing.

### Concrete change (deferred)
No code change this run. When it's time (see verdict), a single paragraph appended to the `orchestrator` agent's README section (currently `README.md:531–550`, just before the "spec-planner" heading) naming the distinction:

> #### How this differs from Claude Code's dynamic workflows
> As of Claude Code v2.1.154+ / Opus 4.8, a session can spawn a **dynamic workflow** — an ad-hoc JavaScript orchestration script Claude writes at runtime to fan work out over tens-to-hundreds of parallel subagents. The harness's `orchestrator` agent is not that: it consumes a **written spec** with `Files:` / `Verify:` fields, routes each task to a model+effort tier by rule, and logs every decision to `.harness-state/orchestrator.{log,jsonl}` for later `/tokens`-style aggregation. Use a dynamic workflow when you want Claude to plan the fan-out itself for a one-off audit or migration. Use the `orchestrator` agent when the fan-out is prescribed by a spec you've reviewed and you want the routing decisions durable. Both patterns can co-exist; they answer different questions.

### Expected payoff
