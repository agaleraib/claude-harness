## 2. Cite Anthropic's Loop-Engineering rule ("the generator must never grade its own work") in README + code-reviewer

**Source:** [Loop engineering: Getting started with loops — claude.com/blog, 2026-06-30](https://claude.com/blog/getting-started-with-loops)

### Why it's relevant

The harness's central design bet is that an **adversarial evaluator** (the `code-reviewer` agent) is what separates "looks done" from "actually done." That's the first bullet of the README's "What This Is" list (README.md:13, `Adversarial evaluation agents that catch what self-assessment misses`) and the entire opening of `.claude/agents/code-reviewer.md`:

> Developers and AI agents are terrible at judging their own work. They say "looks good" when it doesn't. They call things "done" when they're half-finished. You exist because self-assessment is fundamentally broken.

**Sources:**

- Related: [Orchestrate subagents at scale with dynamic workflows — code.claude.com docs](https://code.claude.com/docs/en/workflows)

### Why it's relevant

[2026-04-19 §2](./2026-04-19-improvement-suggestions.md#2-adopt-the-brainhands-split-in-the-orchestrator-agent) recorded a `defer` on adopting the Managed-Agents "brain/hands" pattern in the harness's `orchestrator` agent. The reasons: (a) Managed Agents was a hosted product without a matching local surface; (b) the harness's own `orchestrator` already dispatches by model tier, so the delta was small; (c) the pattern was speculative for a solo Claude Code harness.

On 2026-05-28 Anthropic shipped **Dynamic Workflows in Claude Code**, which is the on-CLI form of the brain/hands split:

- Claude Code writes a short JavaScript orchestration script on the fly (the "brain") that then dispatches N parallel subagents (the "hands") — the coordination code runs in a real JS runtime, not in the model's context window, and each subagent has its own conversation.
- A new `ultracode` setting flips this on by default for substantive tasks; without `ultracode` on, the user still asks explicitly ("create a workflow").
- Runs cap at up to hundreds of parallel subagents (docs cite 1,000 with `ultracode`); scripts have access to `agent()`, `pipeline()`, `parallel()`, `phase()`, `log()`, and a budget primitive.

This is exactly the "brain plans, hands execute in parallel" architecture 2026-04-19 §2 sketched — but now shipped as a first-party primitive that any Claude Code session can invoke.

**Edit C (optional, not `apply`d yet) — `parking_lot.md`:** consider adding a low-priority entry: "*If run-loop ever needs to dispatch multiple items in parallel (waves+issues concurrently, or parallel independent items on the same board), use Claude Code's built-in `Workflow` tool as the primitive rather than reinventing the dispatcher.*" This is a note-to-future-self, not a scheduled task.

## 5. Audit `setup-harness` + operator prose re: `.claude/settings.json` PreToolUse hook trust-elevation contract

**Source:** [How we contain Claude across products — anthropic.com/engineering, 2026-05-25](https://www.anthropic.com/engineering/how-we-contain-claude)

### Why it's relevant

The engineering post is the first place Anthropic explicitly documents that `.claude/settings.json` hooks were, in a prior Claude Code version, executed *before* the "Do you trust this folder?" prompt appeared — meaning a hostile settings.json in a freshly-cloned repo could run arbitrary code before the operator ever saw a consent surface. The vuln was patched in Claude Code itself (that's the point of the post — three overlapping containment layers), but the post makes the underlying contract explicit for the first time: **hooks are trust-elevated; they run under the operator's shell privileges.**

This has three surfaces in the harness:

1. **`setup-harness`** (`skills/setup-harness/SKILL.md`) writes / merges `.claude/settings.json` into consumer projects — including a `hooks` block (the same one 2026-05-08 §1 documented for Auto Mode compositional guarantees). The hooks the harness ships are trusted (they come from `~/.claude/harness/`, a `git clone` of this repo). But once installed, if a subsequent PR to a consumer project touches `.claude/settings.json`, the operator merging that PR is implicitly re-authorizing every hook in the file.

2. **`CLAUDE.md` / `AGENTS.md`** — currently document the PreToolUse denylist wiring (`skills/_shared/loop/safety/denylist.ts` → operator-installed global hook per CLAUDE.md line 30) but do NOT call out the "hooks run trust-elevated" invariant. A future collaborator or a future-you skimming the docs could reasonably think hooks are policy-checked at runtime; they aren't.

3. **`run-loop` in a sandbox** — the loop's egress and denylist safety layers (`skills/_shared/loop/safety/`) mitigate this on the *containerized* runner, but the *worktree* runner (default) uses the operator's shell.

The harness's current guidance is not wrong — it's just implicit. Making the trust-elevation contract explicit closes the gap.

### Concrete change (deferred sketch)

**Edit A — `skills/setup-harness/SKILL.md`, after the current Auto-Mode section (~line 139):** add a subsection *"`.claude/settings.json` hooks are trust-elevated"* with three lines:

- Hooks in `.claude/settings.json` run under the operator's shell before the Claude Code turn's tool-consent prompt. This is by design — hooks are how you enforce policy before Claude sees any output.
- The harness ships hooks from a git source of truth (`~/.claude/harness/`). Do not accept `.claude/settings.json` edits from a PR you would not accept a shell-script contribution from.
- If a hook needs to run untrusted code (e.g. a plugin author's script), use the sandcastle runner (see `sandcastle_mattpocock_architecture.md`) or wrap the hook in a container.

Cite [How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude) as the source.

**Edit B (optional, may already be covered) — `CLAUDE.md` line 30 (denylist hook mention):** append `Trust invariant: PreToolUse hooks execute before per-turn consent; the operator's global hook is the trust root, not the per-project settings.` The current sentence says "operator installs in `~/.claude/settings.json` (global)" — this is technically correct but doesn't call out *why* global is safer than per-project.

**Do not** attempt to reject or filter PR-supplied settings.json in code — that's a policy problem, not a code problem, and the containment post's whole thesis is that boundaries live outside the agent, not inside it.

### Why this is `defer`, not `apply`

- **The vuln was patched in Claude Code itself.** Anthropic's post is retrospective; there's no live risk to the operator today.
- **The harness's own hook wiring is safe.** The PreToolUse denylist is operator-installed globally, not shipped in a per-project `.claude/settings.json`, so it's not affected by the trust-elevation asymmetry.
- **The setup-harness prose change is small but requires a tone pass** to match the rest of the SKILL.md and doesn't need to ship immediately — it can piggyback on the next setup-harness modification.
- **The maintainer is solo** and reviews their own PRs; the "PR-supplied settings.json" attack requires a collaborator surface the harness doesn't currently have.

### Expected payoff (when eventually applied)

- Makes the trust-elevation contract explicit for future collaborators (Codex, future-you, or a second maintainer if one ever joins).
- Aligns the harness's prose with Anthropic's now-first-party framing.
- No behavior change; the harness's actual hook wiring is already correct.

### Verify before applying

Before applying:
1. `grep -rn "trust-elevated\|trust root\|hook.*consent\|hook.*before.*trust" skills/setup-harness/ CLAUDE.md AGENTS.md` — if the invariant is already documented, this § is redundant.
2. Read `skills/setup-harness/SKILL.md` end-to-end for the current tone of security callouts — match that tone in the added subsection.
3. Confirm the Anthropic post is still live at the cited URL (it may migrate to `docs.claude.com/security/`).
4. If the harness has added a plugin loader or PR-supplied hook surface between now and triage, promote to `apply` — the vuln class becomes live.

**Recommended verdict:** defer until next setup-harness pass — vuln was patched upstream, no live risk today, but the trust contract is worth making explicit before the harness ever gains a plugin/PR-hook surface.
**Status:** PENDING — awaiting triage in PR review
