## 2. Re-evaluate the `effort_default: xhigh` derivation now that Opus 4.8 walked the Claude-Code product default back to `high`

**Source:** [Introducing Claude Opus 4.8 — anthropic.com/news, 2026-05-28](https://www.anthropic.com/news/claude-opus-4-8). Specifically the framing that **"high effort is the best balance of token spend and output quality"** and that Opus 4.8's default Claude-Code effort is `high` (a walk-back from Opus 4.7's `xhigh` default that the harness's derivation table was *deliberately aligned with*).

### Why it's relevant
The harness derives `effort_default` from `stakes.level` on first write (`.harness-profile:22-25`, `skills/project-init/SKILL.md:138-148`):

| `stakes.level` | `effort_default` |
|----------------|------------------|
| low | high |
| medium | xhigh |
| high | xhigh |

The justification line (`skills/project-init/SKILL.md:146`) reads:

> As of Anthropic's [2026-04-23 postmortem](https://www.anthropic.com/engineering/april-23-postmortem), Claude Code defaults Opus-4.7 users to `xhigh`. The derivation above stays at or above that floor for the primary model.

This rationale is **now stale**: Opus 4.8's product default is `high`, not `xhigh`. Anthropic's reasoning (per the launch post) is that on coding tasks specifically, default `high` effort on Opus 4.8 uses a similar number of tokens as Opus 4.7's default but performs better across every coding benchmark — i.e., the model improvement absorbed the effort-tier delta. `xhigh` is now positioned as the "extra-headroom" tier, and the new `ultracode` setting (= xhigh + auto-orchestration) is the explicit on-ramp when a user wants more.

For a solo Claude-Code harness running long sessions, the question is whether to:

1. **Keep `xhigh` as the medium/high-stakes default** (status quo) — argument: the harness is rubric-driven and runs adversarial reviewers; the extra headroom catches more issues. The harness has run at xhigh for six weeks (since 2026-04-19) without observed regression.
2. **Walk back to `high` for medium stakes** and reserve `xhigh` for high stakes — argument: align with Anthropic's product-team judgment that the 4.8 model has absorbed the tier delta. Saves tokens. Matches the new "`ultracode` is the deliberate-headroom opt-in" framing.
3. **Hybrid: keep xhigh for `code-reviewer`-loop tasks (rule 4 in the orchestrator's default-effort rules) and walk back the stakes-derived fallback (rule 5) to `high`.** Argument: the rule-based xhigh triggers are task-shape-driven (multi-file migration, cross-cutting refactor) and remain right; the stakes-derived fallback is the part Anthropic's framing speaks to.

This needs a deliberate design pass — there's no obviously-correct answer, and the choice cascades into all consumer-project `.harness-profile` files generated by `/project-init`.

- `skills/project-init/SKILL.md:138-148` (the derivation table + justification paragraph).
- `.claude/agents/orchestrator.md:140-167` (the routing-table examples + default-effort rules, depending on which option is chosen).

The spec would also need to address: do existing consumer projects auto-rederive? The current contract is "derivation only applies on first write" (`.harness-profile:27`, `skills/project-init/SKILL.md:148`) — so option (2) or (3) only affects newly-init'd projects, leaving existing ones at xhigh. That's probably right (consistent with the no-re-derive contract) but should be confirmed.

### Expected payoff
- Saves tokens on the 80%+ of harness sessions that are medium-stakes (the dogfood `claude-harness` profile, all of the maintainer's solo projects). Anthropic's framing suggests the quality delta is now negligible on Opus 4.8.

## 3. Note Anthropic's new Dynamic Workflows + `ultracode` as the in-product parallel to the harness's hand-rolled `orchestrator` agent

**Source:** [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code). Companion docs: [Orchestrate subagents at scale with dynamic workflows — code.claude.com/docs](https://code.claude.com/docs/en/workflows). Single combined launch with Claude Opus 4.8.

### Why it's relevant
The harness's flagship orchestration affordance is the `orchestrator` agent (`.claude/agents/orchestrator.md` — 600+ lines covering routing rules, dispatch, log surfaces, escalation ladder, JSONL contract). The agent's value-prop, in one sentence: read a spec, dispatch each task to opus/sonnet/haiku based on shape, log the decision to two surfaces, escalate one rung per verify failure.

On 2026-05-28 Anthropic shipped two overlapping product features:

- **Dynamic workflows (research preview)** — Claude dynamically writes a JavaScript orchestration script per task, executes it, and dispatches up to **1,000 parallel subagents** that "approach the problem from independent angles, refute each other's findings, and iterate until the answers converge before reporting back." Available on every paid Claude Code plan (Pro, Max, Team, Enterprise).
- **`ultracode` session setting** — single switch that combines `/effort xhigh` with auto-orchestration (Claude decides per-task when to spin up a workflow). Lasts for the current session, resets on restart. Drop back with `/effort high` for routine work.

This is **not** a direct competitor to the harness's `orchestrator` — they target different shapes:

| Feature | Harness `orchestrator` agent | Anthropic dynamic workflows |
|---------|------------------------------|-----------------------------|
| Input | Spec-file with numbered tasks | Free-form prompt |
| Decomposition | Pre-written tasks with `Depends on:` graph | Claude writes a JS orchestration script per task |
| Routing | Rule-based per-task (haiku/sonnet/opus × low/medium/high/xhigh) | "Hundreds of parallel subagents" attacking independently |
| Verification | Per-task `Verify:` step with one-rung escalation ladder | Refute-and-converge across the parallel agents' outputs |
| Logging | Two-surface (`.harness-state/orchestrator.{log,jsonl}`) | Claude Console traces |
| Audience | Spec-driven multi-wave builds | Single-prompt heavy lifts |

The two are **stacked, not competing**: an orchestrator dispatch could plausibly include "this task is hard enough that the dispatched subagent should use a dynamic workflow," but only once the harness understands that semantic.

For now, the actionable bookkeeping is a one-line "When NOT to use" addition in `orchestrator.md` so the next maintainer-look-down isn't followed by a "wait, didn't Anthropic ship this?" detour. Substantive integration (e.g., adding `ultracode` to the escalation ladder) is a spec.

### Concrete change (small)
In `.claude/agents/orchestrator.md` after the existing "How to Invoke" block (around line 11), add a short comparison note:

```diff
 ## How to Invoke

 ```
 Use the orchestrator to build Phase 1 from docs/specs/2026-04-12-editorial-memory.md
 Use the orchestrator to run Task 3 from docs/specs/2026-04-12-editorial-memory.md
 ```

+## When NOT to use this agent
+
+Anthropic's [dynamic workflows](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (research preview as of 2026-05-28) and the `ultracode` session setting target a different shape: free-form prompts where Claude writes the orchestration script on the fly and dispatches up to 1,000 parallel subagents. This `orchestrator` agent targets the *opposite* shape: a numbered spec file with explicit `Depends on:` and `Verify:` per task, rule-based routing, and a single subagent per task. If your task starts from "here's a hairy free-form prompt; throw a fleet at it," reach for `/effort ultracode`. If your task starts from "here's the spec — dispatch the tasks," use this agent.
+
```

### Expected payoff
- Forestalls the "do we still need this agent now that Claude has dynamic workflows?" question by stating the answer on the agent's own page.
- Costs ~3 lines of prose; zero behavior change; one outbound link.
- Sets up the conceptual scaffolding for a future spec that *combines* the two (rule-based dispatch + per-subagent ultracode for the heavy-lift tasks).

### Why defer instead of apply
- Dynamic workflows are research-preview as of 2026-05-28 — the API surface, pricing, and even the `ultracode` slash command could shift before GA. Locking it into the agent doc now risks a stale citation in a month.
- The "When NOT to use" framing is a doc cleanup, not a behavior change — there's no urgency. Apply on the next harness-doc pass when the maintainer is already touching agent pages.
- If dynamic workflows graduate from research preview *or* the harness starts seeing user questions about "is the orchestrator redundant?", promote this from defer to apply.
