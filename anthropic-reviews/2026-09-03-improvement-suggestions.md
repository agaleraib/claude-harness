## 1. Cite "New rules of context engineering for Claude 5" as first-party evidence in the README's lean-context argument

**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) (Thariq Shihipar, Member of Technical Staff, Applied AI). Companion coverage: [i-scoop](https://www.i-scoop.eu/context-engineering-claude-5/), [Techstrong](https://techstrong.ai/agentic-ai/anthropic-cut-80-of-claude-codes-system-prompt-heres-why-that-matters-for-your-agents/), [Developers Digest](https://www.developersdigest.tech/blog/claude-5-context-engineering-rules-hn-analysis).

### Why it's relevant
This is the strongest first-party evidence for the harness's "keep the harness lean" thesis to date. Per the post, Anthropic **deleted more than 80% of Claude Code's system prompt for Claude Opus 5 / Fable 5** *"with no measurable loss on our coding evaluations."* The reported reasons echo the arguments already in `README.md` lines 23–34 (**Why Not Superpowers / Heavy Skill Systems?**) almost bullet-for-bullet:

- **Rules become judgment.** Anthropic found stacked contradictory rules ("leave documentation as appropriate" vs. "DO NOT add comments") that the model had to spend attention untangling — same failure mode this harness's "prune regularly" rule for CLAUDE.md (README:767–772) already targets.
- **Examples become interface design.** Heavy examples in the prompt are replaced by tools and skills the model discovers on demand.
- **Upfront context becomes progressive disclosure through skills.** Same architecture this harness already uses (SKILL.md YAML frontmatter → activation → reference files).
- **The old rulebook was built for less capable models.** Direct restatement of README:29–31 ("scaffolding that was essential for earlier models became counterproductive").

The current README's evidence list for the lean-context stance cites the [April 23 postmortem](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues) as "first-party" evidence that harness bloat can regress performance. This new post is stronger: it's a first-party report of Anthropic *choosing to remove* 80% of the largest agent-harness system prompt they maintain and confirming zero coding-eval loss. That's the exact experiment the harness's "keep context under 500 tokens at session start" claim would make if scaled up.

### Concrete change
Add **one bullet** to the existing evidence list in `README.md` lines 25–32 (**Why Not Superpowers / Heavy Skill Systems?**). Insert immediately before the closing `**Anthropic's own conclusion**` bullet at line 31:

```diff
 - **System-prompt regressions are subtle and slow to detect**: Anthropic's own [April 23 postmortem](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues) traced a month-long Claude Code quality drop to three harness-layer changes — including a 25-word verbosity cap that knocked 3% off internal coding evals. Confirms first-party that adding instructions to the harness can degrade behavior.
+- **First-party: Anthropic removed 80% of Claude Code's system prompt for Claude 5 with no coding-eval loss**: The July 24, 2026 post [The new rules of context engineering for Claude 5 generation models](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) reports that Anthropic's own harness team deleted more than 80% of Claude Code's system prompt for Claude Opus 5 / Fable 5 with no measurable loss on their coding evaluations. Their reasoning — stacked contradictory rules waste attention, upfront rules become progressive disclosure through skills, examples become interface design — is a direct restatement of the argument this harness makes. If Anthropic's own agent-harness team is trimming aggressively on the newest model generation, the case for a lean external harness is strictly stronger, not weaker.
 - **Anthropic's own conclusion**: Their harness research removed sprint decomposition, reduced evaluator rounds, and simplified the generator — scaffolding that was essential for earlier models became counterproductive
```

Optional companion touch (cheap, one line): add to the **References** section (if present in README) or the CLAUDE.md-layering paragraph at line 772 a parenthetical link to the same post so anyone looking at the "keep CLAUDE.md lean" advice can trace it back to Anthropic's own reasoning.

### Expected payoff

If a future reader (or future-you) is talked into installing a heavier skill system, the response is now "here's Anthropic's own harness team saying they went the opposite direction on the newest model."

- **Fable 5.1 (2026-09-01)** is now Anthropic's coding-benchmark leader and its most cost-efficient front-line model (same list price as Fable 5, with 75% cheaper cache reads). If the maintainer's coding workload is bounded by cost, Fable 5.1 is the new default candidate for `primary`.

## 4. MCP 2026-07-28 spec (stateless core, MCP Apps, Tasks, hardened OAuth)

**Source:** [MCP 2026-07-28 spec: stateless core, coming to Claude — claude.com/blog, 2026-07-28](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude); protocol spec at [modelcontextprotocol.io/posts/2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

### Why it was surfaced
The MCP 2026-07-28 spec is the largest MCP update since launch. Three headline changes:

- **Stateless core.** MCP is now request/response instead of a persistent bidirectional session. Servers can deploy on serverless / edge.
- **Standardized extensions framework** with **MCP Apps** (server-rendered UIs in a sandboxed iframe) and **Tasks** (long-running/async ops) as versioned add-ons.
- **Auth hardening** aligned to production OAuth 2.0 / OIDC (Entra, Okta).

Plus **MCP tunnels (research preview)** — Claude connects to MCP servers inside a private network without exposing them publicly, using an outbound-only tunnel.

### Why rejected
`grep -rn "mcp\|MCP" .` in this repo returns only prose mentions in `AGENTS.md`, `README.md`, and setup guidance — the harness does not vend, host, or wrap an MCP server, and it does not have a client-configuration layer that would need to know about spec version changes.

Consumer projects installed via `setup-harness` pick up MCP client behavior directly from Claude Code, which handles the spec migration transparently.

No harness-side action is identifiable. If the maintainer ever adds a harness-first MCP server (e.g. a `harness-status`-like remote data source), that would be the point to revisit the stateless-core + Tasks patterns.

### Verify before applying
1. `grep -rn "mcp\|MCP" skills/ agents/ .claude/agents/ .claude/settings*.json 2>/dev/null` — must return no meaningful config (only prose mentions). If a real MCP server config or wrapper has been added in the interim, this § is no longer safe to reject and needs a fresh look.
2. Confirm no consumer-project post-install script in the harness attempts to configure MCP servers directly (search `setup-harness/`, `shared-root-init/`).

**Recommended verdict:** reject — no harness surface. Reopen only if a first-party MCP server or client-config layer is added to this repo.
