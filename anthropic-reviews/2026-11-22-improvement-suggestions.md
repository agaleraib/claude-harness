## 1. Cite "Components of agent memory" as corroborating evidence for the harness's four-layer memory system

**Source:** [The components of agent memory — anthropic.com/engineering, 2026-11-06](https://www.anthropic.com/engineering/components-of-agent-memory). Anthropic's engineering team published a four-layer memory hierarchy plus a "dreaming" curation process: **(1) Transcripts** (searchable log of every session) → **(2) Memory notes** (short observations written during a session) → **(3) Memory representations** (structured wiki/index pages built from notes) → **(4) Injected context** (small index loaded every session, pointing to deeper layers) → **(5) Dreaming** (offline reflection over transcripts + memory, promotes/prunes/corrects).

| Injected context | `/session-start` preamble: reads `.harness-state/last_exit.md` + `~/.claude/memory/FEEDBACK.md` top-level index verbatim |
| Dreaming (offline) | **Not present** — the harness has `/memory-prune` (manual, cap-management), but no automated cross-session reflection |

## 3. Add "Building strong safety evaluations" as a methodology reference for the still-deferred 2026-04-19 §5 (agent evals)

**Source:** [Building strong safety evaluations — anthropic.com/engineering, 2026-11-13](https://www.anthropic.com/engineering/building-strong-safety-evaluations). Anthropic published a four-pillar methodology for designing trustworthy evals: **(1) Safety first** (domain experts + sandboxed environments) → **(2) Design** (match the design to the question; define the construct precisely) → **(3) Run** (protect internal validity; calibrate graders; preregister analysis) → **(4) Report** (full statistics; document configurations; disclose flaws). Includes sample-size floors (≈100 items for multi-turn evals, ≈1000 for single-turn) and explicit anti-patterns (refusal rates that don't distinguish appropriate engagement from over-refusal; graders that favor longer answers; single-turn evals that saturate).

### Why it's relevant

The harness's **2026-04-19 §5** proposed formalizing evals for the adversarial reviewers (`code-reviewer`, `ui-evaluator`). Its Status has been **deferred** across six months with the same rationale: *"the harness is too young for fixtures yet — defer until there's a stable-enough adversarial-reviewer surface to score against."*

That rationale remains true (nothing in the November window changes it), but the **"how" is now much more concrete**. Before 2026-11-13 the deferred §5 pointed vaguely at "demystifying evals for AI agents" (2026-01-09) and "BioMysteryBench" (2026-05-03). Now there's a direct engineering checklist:

- **Pair harmful tasks with look-alike benign tasks** — concrete application to this harness: when the deferred eval fixtures land, pair an "intentionally subtle bug in criteria/code-architecture.md" with a "clean refactor that merely moves functions" to test whether `code-reviewer` flags the first and leaves the second alone.
- **Use outcome-based, atomic rubric items ("Did it modify files outside the task scope?")** — maps directly onto the harness's existing `criteria/*.md` structure, which already uses graded yes/no rubric items.
- **Grader validation gate: human-label a sample blind, measure chance-corrected agreement, don't ship the grader if humans don't agree with it as well as humans agree with each other** — the single most concrete blocker the harness needs to design around before building fixtures. Without this, any eval fixture accumulates grader drift that masquerades as code-reviewer improvement.
- **Sample-size floors** — 100 items for multi-turn is the floor; this scopes the eventual fixture investment (one rubric × 100 bug-fix PRs is ~100 hours of curation at ~10 min/item; multiple rubrics is weeks).

### Why this is `defer`, not `apply`

The blocker for 2026-04-19 §5 was never "we don't know the methodology." It was "we don't have a stable-enough `code-reviewer` + `criteria/` surface to measure against." That's unchanged. Writing a fixture spec today, before the surface stabilizes, risks baking grader-validation assumptions into prose that are wrong when the real fixtures land.

## 4. Audit sandboxing posture against "How we contain Claude across products"

**Source:** [How we contain Claude across products — anthropic.com/engineering, 2026-05-25](https://www.anthropic.com/engineering/how-we-contain-claude). Three-layer defense: **environment** (sandboxes, VMs, filesystem boundaries, egress controls) → **model** (classifiers, probes, training) → **external content** (MCP servers, plugins, web results treated as untrusted). Concrete practices include: keep credentials out of the sandbox entirely; resolve symlinks before path validation; authenticate egress through a proxy that passes only requests carrying the sandbox's session token; defer parsing of project-local config (hooks) until the user has accepted a trust prompt; "custom glue code is often the weakest link."

## 5. Note "Building always-on agents" (inbox/timer/outbox primitives) as a conceptual parallel to the deferred Cloud Routines migration (2026-05-10 §2)

**Source:** [Building always-on agents — claude.com/resources, 2026-11-13](https://claude.com/resources/articles/building-always-on-agents). Anthropic's guide to stateful, proactive agents built on four primitives: **event inbox** (durable store all triggers write to), **timers** (follow-ups + schedules, separate from the inbox), **memory** (durable store outliving the worker; load an index, pull details on demand), **outbox** (paced delivery queue of outgoing messages). "An always-on agent is not actually 'always on' — it sleeps, wakes for a run when an event arrives, works in a session, saves state, sleeps again."

### Why it's relevant

The **Anthropic-reviews routine itself** (producing this very file) already matches the inbox-worker-outbox pattern but without the formal vocabulary:

| Always-on primitive | Anthropic-reviews routine equivalent |
|---|---|
| **Event inbox** | Manual trigger: operator starts a Claude Code session whose system prompt is the stored routine prompt. There's no durable queue — each run is standalone. |
| **Timers** | Not present — the schedule is cron-external (whenever the operator decides to run it). |
