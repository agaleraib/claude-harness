## 1. Cite "Loop engineering: Getting started with loops" in AGENTS.md's Loop-protocol header

**Source:** [Loop engineering: Getting started with loops — claude.com/blog, 2026-06-30](https://claude.com/blog/getting-started-with-loops) (also visible in [Claude Code Week 20](https://code.claude.com/docs/en/whats-new/2026-w20) shipping `/goal`). Anthropic's Claude Code team defines four loop types — **turn-based** (interactive), **goal** (`/goal` with evaluator), **time** (`/loop` local + `/schedule` cloud), and **proactive** (schedules + goal checks + skills + automatic permissions) — and pairs each with a canonical stop condition and use-case.

### Why it's relevant
The harness ships a full loop lane already:
- `AGENTS.md:91` opens **`## Loop protocol`** with the wave / issue / gate / runner / escalation / termination model.
- `skills/run-loop/SKILL.md:3` is the operator-facing entry (`/run-loop waves` and `/run-loop issues`).
- `skills/_shared/loop/` is the TypeScript engine (`engine.ts`, `merge/`, `providers/`, `safety/`).

Mapping to Anthropic's four types: the harness's loop is a **time-adjacent proactive** loop — schedule-agnostic (fires when the operator says `/run-loop`, or when the Anthropic-reviews cron fires it), goal-anchored (drains until the source is empty or a stop cap fires), and gated (mechanical exit gate + code review + atomic merge). It is **not** a turn-based loop and is more disciplined than the post's "proactive" example (mandatory per-item gate, fail-safe on gate absence, host-safety guardrails on the worktree lane).

Adding one bullet to the Loop-protocol section header with an external anchor turns a future reader's "wait, how does this map to what Anthropic ships?" question into a footnote instead of an archaeology dig.

```diff
 ## Loop protocol

+> _Related reading:_ Anthropic's [Loop engineering: Getting started with loops](https://claude.com/blog/getting-started-with-loops) (2026-06-30) frames four loop shapes — turn-based, goal, time, proactive. The harness's `/run-loop` is a **gated proactive** loop: schedule-triggered or operator-triggered, goal-anchored (drains a work source), with a mandatory per-item mechanical gate that the post's "proactive" example does not require. `skills/_shared/loop/` is the reference implementation.
```

## 5. Audit oversized skill-frontmatter descriptions — "less-is-more" pass informed by the Claude 5 context-engineering rules

**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models). Anthropic reports that for Claude Opus 5 and Fable 5 they removed >80% of Claude Code's system prompt with **no measurable loss** on their coding evals; the three prescriptions are (a) **give judgment instead of rules**, (b) **use progressive disclosure instead of front-loading**, (c) **stop compounding in CLAUDE.md** (each rule accretes cost with diminishing returns). Anthropic also built `/doctor` in Claude Code to right-size skill and CLAUDE.md content.

### Why it's relevant

The **body-shrink half** of the post targets Claude 5 models (Opus 5, Fable 5). The harness pins `.harness-profile:30 model.primary: claude-opus-4-7` — a Claude 4-generation model — so wholesale system-prompt / skill-body shrinks are **not** obviously safe on the pinned model; the post says Fable 5 was the *first* model where step-by-step scaffolding hurt.

But the **description-shrink half** is model-agnostic: skill frontmatter `description:` fields are what the model matches when deciding whether to invoke a skill. Long descriptions raise the trigger-noise floor (more incidental keyword matches) and burn tokens in the always-visible skills index. Today the harness has:


**Six skills** carry descriptions between 500 and 689 chars on a single line; the smallest six are 150–200 chars. The Anthropic skill-writing guide's rule of thumb is *"200 chars for name+description, one focused trigger clause"* — most of these are 2–3× that.

### Why this is `spec`, not `apply`

Shrinking descriptions is not a mechanical edit:

1. **Trigger accuracy is the whole product of a skill description.** Cutting text can *demote* the skill from natural-language trigger matches ("close wave 3 for me" → `close-wave`). A rewrite needs a per-skill triggers-preserved test, not a one-line delete.
2. **The 6 largest descriptions bundle two concerns each** — what the skill does (needs to stay) and *when* to run it (also needs to stay, but often via examples that could migrate into the skill body's `## When to use` section instead of the frontmatter). Extraction and reassembly is a design pass, not a search-and-replace.
3. **Interaction with skill BODY shrinks is unresolved** on Claude 4.7 — the post says Fable 5 was the *first* model where step-by-step scaffolding hurt. Body-shrinks here need explicit "we're on Opus 4.7, so the frontmatter shrink is safe but the body prescription is deferred" reasoning that only a spec can capture cleanly.
4. **Introduces a new convention** (frontmatter description = ≤N chars + one trigger clause; longer trigger examples live in `## Triggers`). Convention changes are substantive per the `README.md` decompose-first rung table.

Per the `apply-anthropic-reviews` skill's promotion signals (#3 "Introduces a reusable convention" and #4 spans >5 files), this bullet is substantive.

### Concrete change (deferred to `/spec-planner`)

Skeleton for the eventual spec:

1. Add a **skill-description convention** to `AGENTS.md` (near the existing "## What to avoid" that already prohibits dynamic content in prompt files): "Skill frontmatter `description:` MUST be ≤N chars and MUST contain exactly one trigger clause. Additional trigger phrases and examples MUST live in the skill body under `## Triggers` or `## When to use`, not in frontmatter."
2. For each over-cap skill (`new-cowork`, `run-wave`, `archive-plan`, `apply-anthropic-reviews`, `triage-parking`, `harness-status`), rewrite `description:` and migrate the removed trigger phrases into the body.
3. Run each rewritten skill through a triggers-preserved smoke test: canonical operator phrases from `## Triggers` (or from operator-recall / the tracker's prior invocations) should still surface the skill.
4. Consider whether `/doctor` (Claude Code Week 28, [2026-07-06→10](https://code.claude.com/docs/en/whats-new/2026-w28)) can be added as a `harness-status`-adjacent skill or invoked as part of `/session-start` for periodic re-verification once the harness migrates to Claude Opus 5 / Sonnet 5 in a future model-bump wave.
5. Body-shrink prescriptions (the >80% claim) stay **deferred until the pinned model is Claude 5-generation** — record the deferral explicitly in the spec so it doesn't get pattern-matched into scope.

### Expected payoff (when applied)
Lower always-visible skills-index cost, sharper trigger matching (fewer incidental hits), and one durable convention that new skill authors can grep for. Uphill investment; the pay-off is per-invocation.
