## 2. Cite _The components of agent memory_ in README references and add a corroboration note to `AGENTS.md`'s "Memory" section

**Source:** [The components of agent memory — anthropic.com/research, 2026-11-06](https://www.anthropic.com/research/components-of-agent-memory). Formalizes a four-layer memory hierarchy — **transcripts**, **memory notes**, **memory representations**, **injected context** — plus **dreaming** (an offline pass that moves information between layers: corrects notes against transcripts, builds wikis, promotes notes upward). Concrete prescriptions in the post:
- "Persist a memory directory across sessions."
- "Store what can't be re-derived from the environment."
- "Use a small dashboard plus topic folders" — the Pokemon run-comparison contrast: 413 files / 225 folders vs. a tight `global.md` + `locations/` + `gameplay/`.
- "Record provenance and status" (checked / unconfirmed; how known; traps).
- "Keep the injected layer small." Claude Code loads only the first 200 lines or 25 KB of `MEMORY.md`, which acts as an index.
- "Give each writer its own page" (parallel agents writing one shared table: 41 of 57 facts survived; one page per contract: all 57).

## 3. Audit the harness's 6 subagents against the "fold subagents" heuristics

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop).

### Why it's relevant

The post gives a direct test for each subagent: fold into the main loop by default unless (a) the main loop hits measurable degradation from context bloat, (b) the subtask runs in parallel with a throwaway context, or (c) tool-selection conflicts arise in the main system prompt. It names seven anti-patterns, two of which look worth checking against this repo: **subagent sprawl** ("every team ships its own overlapping subagents") and **the Frankenprompt** ("each team adds rules, producing conflicts and no consistent voice"). The migration heuristics it prescribes:

- Build a small end-to-end eval first.
- Merge specialists that are tightly coupled (chain on each other's output, touch the same data, often called together).
- Before fully folding, make a subagent a tool so the main agent keeps the conversation. Reserve full handoffs for when a subagent "needs to talk to the user directly."
- Fold subagents in one at a time. Keep one as a subagent **only if** the folded version scores worse.
- Check which tasks flipped, not just the final score.

### What's in the harness today

`.claude/agents/` has six subagents, all pinned to `model: opus` (except where Claude-Code-side routing overrides):

| Subagent | Current role | Folding pre-check |
|---|---|---|
| `orchestrator` | Reads spec tasks and dispatches each to opus/sonnet/haiku subagents | The orchestrator **is** the main loop for `/run-wave`; keeping it a subagent is defensible — it manages a loop that explicitly produces throwaway contexts (parallel tasks). Likely KEEP. |
| `code-reviewer` | Adversarial post-change review against `criteria/` | Clean interface (reads diff, returns findings). Candidate to stay as a subagent because findings are a bounded black-box output and the subagent needs a fresh context to be adversarial. Likely KEEP. |
| `spec-planner` | Discovery-based specification writing | Conversational, human-facing, persistent across turns — matches the post's "needs to talk to the user directly" exception. Likely KEEP. |
| `generator` | Implementation loop driven by evaluator feedback | Tightly coupled with `code-reviewer` and `ui-evaluator`; the post's heuristic "merge specialists that chain on each other's output" argues for folding `generator` into the main agent (with `code-reviewer` + `ui-evaluator` as tools or subagents). **FOLD candidate.** |
| `ui-evaluator` | Scores a running web app via Playwright against `criteria/` | Only runs in projects with a frontend; otherwise idle. The post's "make it a tool before folding" step applies — turn the Playwright + criteria-scoring call into a tool, then decide. **TOOL-FIRST candidate.** |
| `project-tracker` | Save/resume session state via Second Brain | Called at session-end only; one-shot invocation with a bounded return. The post's "subagent sprawl" anti-pattern applies — this is one more context-boundary for a job that could be a skill with a shell + MCP call. **FOLD candidate.** |

Also worth cross-checking: the harness README says `generator`, `ui-evaluator`, and `orchestrator` are part of the wave-dispatch chain (`README.md:535–558`), and `code-reviewer` is invoked synchronously by `/commit`. These are the pre-existing couplings a fold would have to respect.

2. **`project-tracker` already looks like a skill, not a subagent.** The folding here is more of a schema migration (`skills/project-tracker/` vs. `.claude/agents/project-tracker.md`) than a true fold. Worth doing — not urgently.

4. **Speculative for solo tooling.** The post is written for team-scale harnesses where multiple teams ship overlapping subagents. The harness is solo-maintained; the Frankenprompt + subagent-sprawl anti-patterns don't bite as hard.

## 4. Append _How we contain Claude across products_ to README's "Why Not Superpowers" evidence list

**Source:** [How we contain Claude across products — anthropic.com/research, 2026-05-25](https://www.anthropic.com/research/how-we-contain-claude). Back-filled from the May-Oct silence in the tracker (this run's first chance to record it). The post's framing: cap an agent's "blast radius" by limiting what it can reach, not by supervising every action. Specific prescriptions:

- OS-level sandbox, network denied by default.
- Credentials out of the sandbox entirely.
- Allowlisted domains are **capability grants**, not just hostnames — proxy and validate at the request level.
- Defer parsing project-local config until trust is granted (hooks in a cloned repo's settings must not run before the trust prompt).
- Don't rely on approval prompts alone (~93% approval rate in telemetry).
- Scope tool permissions narrowly.
- Watch persistent state (injections in CLAUDE.md, memory, mounted workspaces reload on every session).
- Prefer standard primitives over custom glue — their custom-proxy / allowlist code was the failure surface, not seccomp / hypervisors.

### Why it's relevant
The harness already implements most of this through `AGENTS.md`'s "Loop protocol" section:
- **Sandcastle runner** (container, OS-level boundary) + **worktree runner** (with explicit per-item guardrails).
- **Catastrophic-command denylist** via `PreToolUse` hook (`skills/_shared/loop/safety/denylist.ts`) — "canonicalizes commands, covers non-shell file writes via write-root confinement, and fails closed on parse ambiguity."
- **Default-deny outbound egress** for secret-bearing worktree items ("only an operator-declared host allowlist plus loopback; the git remote is not auto-allowed").
- **Task-scoped credential injection** ("only the item's declared secrets, never the whole environment").
- **Standard primitives over custom glue** — the loop reuses the wave lane's merge machinery rather than carrying a parallel merge path.

The one gap the post surfaces: _"Watch persistent state. Injections in CLAUDE.md, memory, or mounted workspaces reload on every session."_ The harness has `~/.claude/memory/` as auto-loaded injected context; it's human-written (per `AGENTS.md`) but doesn't have an integrity check on the content. For a solo-maintained harness this is low-risk (only one person writes to it). Worth noting as a corollary when the §4 bullet is added, not as its own §.
