## 2. Position dynamic workflows in Claude Code alongside the orchestrator's parallel-when-safe Phase 2 path

**Source:** [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (Code w/ Claude SF + London adjacent; in research preview on every paid Claude Code plan). Coverage: [TechCrunch — Anthropic releases Opus 4.8 with new 'dynamic workflow' tool](https://techcrunch.com/2026/05/28/anthropic-releases-opus-4-8-with-new-dynamic-workflow-tool/), [MarkTechPost — Dynamic Workflows, capped at 1,000 subagents](https://www.marktechpost.com/2026/05/28/anthropic-ships-claude-opus-4-8-alongside-dynamic-workflows-and-cheaper-fast-mode-with-workflows-capped-at-1000-subagents/).

### Why it's relevant
The orchestrator agent ([`.claude/agents/orchestrator.md`](../.claude/agents/orchestrator.md)) implements an explicit **parallel-when-safe** phase: file-overlap analysis (line 81) → eligible parallel tasks spawn subagents under `isolation: "worktree"` (line 202) → join → commit. That is the same conceptual pattern Anthropic just shipped at much larger scale:

- **Local orchestrator (this harness):** Reads spec tasks, picks model + effort per task, spawns one-per-task subagents (typically ≤5 parallel) with worktree isolation, commits independently. Cited in `README.md:511` as following [Anthropic's orchestrator-worker pattern](https://www.anthropic.com/research/building-effective-agents).
- **Dynamic workflows (Anthropic, May 28):** Claude writes a **JavaScript orchestration script** on the fly from a natural-language request; a separate runtime executes it; the script dispatches **tens to hundreds (cap: 1,000) of parallel subagents**, keeps intermediate state in script variables that live outside the conversation, and a verification step filters outputs before reporting back. Triggered by the word "workflow" in a prompt. On by default on Max/Team; opt-in on Pro; admin-enabled on Enterprise.

These are **complementary, not redundant** — same family, different scale:

| Dimension | Local orchestrator | Dynamic workflows |
|---|---|---|
| Spec source | `docs/specs/*.md` with explicit task markers | Natural-language prompt |
| Routing | Model + effort per task, tuned for the orchestrator-log JSONL contract | Anthropic-runtime-managed; capped at 1,000 |
| Isolation | Git worktree per task | Cloud sandbox per subagent |
| Verification | `/commit` + code-reviewer rubric per task | Anthropic's built-in verification step |
| Cost surface | Same Claude Code session (no extra surface) | Token-billed cloud run; Pro/Max/Team/Enterprise plans only |
| Use case | Sub-10-task waves with spec-driven structure | Codebase-wide bug hunts, profiler-guided optimization audits, security audits |

Today there is **zero mention** of dynamic workflows in the repo (`grep -rn "dynamic workflow\|dynamic-workflows\|introducing-dynamic-workflows" /home/user/claude-harness` returns nothing). The same gap that 2026-05-10 §1 closed for cloud Code Review (vs. local `code-reviewer`) exists here for dynamic workflows (vs. local `orchestrator`). One paragraph closes it before the question "should I rewrite the orchestrator to use dynamic workflows?" is asked aloud by a future reader.

### Concrete change

**One paragraph appended to `.claude/agents/orchestrator.md`** in the existing "File overlap analysis (Phase 2 capability — parallel-when-safe)" section, after the eligibility rules (line 86). Suggested placement: after the line `- Type definition files imported by another parallel-eligible task`:

+The local parallel-when-safe pattern above is the **small-scale, spec-driven** version of [Anthropic's dynamic workflows in Claude Code](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (May 2026, research preview on paid plans). Anthropic's runtime writes a JavaScript orchestration script on the fly from a natural-language prompt and dispatches up to ~1,000 parallel subagents in a cloud sandbox, with a verification step before reporting back. The local orchestrator stays the right tool for **spec-driven waves** (`docs/specs/*.md` task markers, file-overlap-aware routing, per-task `/commit` with rubric-anchored review, no extra cost surface). Dynamic workflows are the right tool when the **shape of the work is unknown ahead of time** (codebase-wide bug hunt, profiler-guided audit, security pass) and parallelism would scale past what a single Claude Code session can dispatch.
