## 4. Audit SKILL.md descriptions against the *Complete guide to building skills* concision guidance

**Source:** [A complete guide to building skills for Claude — claude.com/blog, 2026-06-03](https://claude.com/blog/complete-guide-to-building-skills-for-claude) (companion PDF: [resources.anthropic.com/.../The-Complete-Guide-to-Building-Skill-for-Claude.pdf](https://resources.anthropic.com/hubfs/The-Complete-Guide-to-Building-Skill-for-Claude.pdf)). Anthropic's published guidance:

- **YAML frontmatter is always loaded into Claude's system prompt** (level 1 of progressive disclosure) — so it has to be tight.
- The `description` field must include "**both what the skill does and when to use it**, always written in third person".
- The post's emphasis is on **concision** — "the cheapest fix is making your descriptions shorter and more keyword-dense"; "challenge each piece of information: does Claude really need this explanation?"
- The companion *Skill authoring best practices* page (Claude API Docs) gives a ≤200-character soft target for `description`; collections of 60+ skills should aim for ≤130 chars to avoid skill-listing budget truncation.

### Why it's relevant

The harness ships **22 skills** via symlink to `~/.claude/skills/`. All 22 descriptions load into the system prompt at session start (level 1). A quick audit:

```bash
for f in /home/user/claude-harness/skills/*/SKILL.md; do
  desc_len=$(awk '/^description:/{gsub(/^description: */,""); print length; exit}' "$f")
  echo "$desc_len $(basename $(dirname "$f"))"
done | sort -rn | head -5
```

Returns (as of 2026-06-06):

| Skill | Description length (chars) |
|---|---|
| new-cowork | **676** |
| run-wave | **642** |
| archive-plan | **627** |
| apply-anthropic-reviews | **601** |
| harness-status | **505** |

For comparison, the median description in this harness is ~250 chars, and short skills like `park` (195), `deploy-check` (181), `commit` (210), and `setup-harness` (214) sit cleanly under the 200-char trim threshold the third-party readings of Anthropic's guidance recommend.

The top five together carry **~3,050 chars of description text**, i.e. roughly 760 tokens on average for those five descriptions alone — vs. ~50 tokens each (~250 total) if they were trimmed to ≤130 chars. Multiplied across 22 skills, the harness's "skill listing" in the system prompt is likely **~1.5–2× larger than necessary**.

This matters because the harness's own README claims "**~500 tokens at startup** (agent descriptions only)" — but this number is *agent* descriptions, not skill descriptions. Claude Code now loads both, so the real session-start overhead is higher than the README claims. Untrimmed skill descriptions inflate it further. Not a correctness bug; a precision/calibration issue.

### Why this is `defer` not `apply`

Three reasons:

1. **Discovery triggers live in the descriptions.** `run-wave`'s description includes the explicit trigger phrases ("Use this whenever the user types /run-wave, says 'run wave N', 'execute wave N', …"). Trimming has to preserve those triggers — Anthropic's guidance is "what + when", and the *when* IS the trigger list. This is a careful editorial pass, not a `/micro`.
2. **The exact character target isn't first-party-quoted in this post.** The 200-char / 130-char numbers come from third-party readings of *Skill authoring best practices*. The blog post itself emphasises concision qualitatively but doesn't publish a hard limit. Until the maintainer confirms the target, the audit is a moving target.
3. **No reported pain.** The harness hasn't been observed to skip skill activations or hit listing-budget truncation. The audit is speculative — *might* matter, *might* not.

If a real skill-listing budget pain is reported (skill misfires under load, truncation warnings, etc.), promote this to `spec`.

### Concrete change (deferred)

None this run. When/if the maintainer wants to take this on:

1. Read the *Complete guide to building skills* + *Skill authoring best practices* page end-to-end; extract the first-party concision target (if any).
2. Audit all 22 SKILL.md descriptions; tag each as **{tight / acceptable / over-budget}** against the published target.
3. For over-budget skills, draft a one-paragraph rewrite that preserves the discovery triggers verbatim and the "what + when" framing, then evaluate via a session-start test (do skill activations still fire on the same phrases?).
4. Update the README's "~500 tokens at startup" claim with the actual measured cost (agent descriptions + skill descriptions) — even if no descriptions are trimmed, calibrating the public number to reality is worth doing.

### Expected payoff (when applied)

Session-start overhead drops by ~500–1,000 tokens (estimated) without losing any skill triggers; the README's "~500 tokens at startup" claim becomes accurate; the harness's claimed lean-context advantage gets harder evidence.
