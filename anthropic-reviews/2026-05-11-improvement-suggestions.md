## 1. Set `worktree.baseRef: "head"` in `.claude/settings.json` to lock the v2.1.133 behavior change in favor of `/run-wave`

**Source:** [Claude Code CHANGELOG.md (v2.1.133)](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md) — entry verbatim:

> Added `worktree.baseRef` setting (`fresh` | `head`) to choose whether `--worktree`, `EnterWorktree`, and agent-isolation worktrees branch from `origin/<default>` or local `HEAD`. **Note:** the default `fresh` changes `EnterWorktree`'s base back to `origin/<default>` (it has been local `HEAD` since 2.1.128) — set `worktree.baseRef: "head"` to keep unpushed commits in new worktrees.

(Same content mirrored at <https://code.claude.com/docs/en/changelog>.)

### Why it's relevant

The harness routes every `/run-wave` dispatch through an agent-isolation worktree. From `.claude/agents/orchestrator.md:202`:

> **For parallel tasks:** Spawn subagents with `isolation: "worktree"` so each works on an independent copy.

And from `skills/run-wave/SKILL.md:201, 318`:

> - **Dispatch** — run the orchestrator in an isolated worktree now
> - `isolation: "worktree"` — creates an isolated working copy so commits don't touch the main checkout

The pre-v2.1.133 default (`head` since v2.1.128) was the behavior the `/run-wave` flow was authored against: the orchestrator's worktree inherits whatever the user has *currently* on `HEAD`, including planning commits that updated `docs/plan.md`, fresh spec files in `docs/specs/`, or any cherry-pick the human just made. Under the new default (`fresh`), the orchestrator's worktree branches from `origin/<default>` instead — so any unpushed planning commit on the local branch is *invisible* to the wave run. That's a silent regression: the wave still dispatches, the orchestrator still runs, but it doesn't see the planning context the human just prepared.

`grep -rn "worktree.baseRef" .` returns nothing today, and `.claude/settings.json` currently holds only an empty `hooks: {}` block — so the harness is implicitly riding the new `fresh` default the moment a user upgrades past v2.1.132.

### Concrete change

**One-line edit to `.claude/settings.json`** to pin the historical behavior:

```diff
 {
+  "worktree": {
+    "baseRef": "head"
+  },
   "hooks": {
   }
 }
```

Then add a one-line note to the existing worktree discussion in `README.md` (currently at lines 1001–1016, around the `git worktree add ../myproject-feat-X feat/X` walkthrough) explaining that the project setting pins agent-isolation worktrees to local `HEAD` so `/run-wave` sees pending planning commits:

```diff
 Each worktree is a full working copy with its own `.claude/agents/` and `criteria/` — the harness works in worktrees automatically.
+
+> **Note (Claude Code v2.1.133+).** `.claude/settings.json` pins `worktree.baseRef: "head"` so `/run-wave` and other `isolation: "worktree"` dispatches branch from local `HEAD` (not `origin/<default>`). This preserves the pre-v2.1.133 semantics the harness was authored against; unpushed planning commits on the current branch remain visible inside the dispatched worktree. See `anthropic-reviews/2026-05-11-improvement-suggestions.md` §1.
```

### Expected payoff
- Restores the documented contract of `/run-wave`: planning commits made just before dispatch are visible inside the orchestrator's worktree.
- Removes a quiet failure mode where a wave dispatched on a freshly-planned branch silently ignores the planning context and starts from the remote default branch.
- Zero behavior change for users who keep both branches pushed (the typical case), so the cost is only a documented preference, not a workflow shift.

### Risks / caveats
- If the harness ever needs the `fresh` semantics for some specific agent (e.g. an audit agent that should *not* see in-flight planning commits), the project-wide setting would mask that. Today, no agent in `.claude/agents/` is documented as wanting `fresh`; a future need can be handled per-invocation by passing `worktree.baseRef: "fresh"` at dispatch time once Claude Code surfaces a per-call override.
- The setting only affects users on v2.1.133+. Users on older versions are unaffected (the setting is harmlessly ignored).

### Verify before applying
Run `grep -rn "worktree.baseRef\|baseRef" .claude/settings.json README.md` — if the setting (or a README note about it) already exists, the suggestion is stale. Also re-read the Claude Code CHANGELOG for any reversal of the v2.1.133 default before pinning (Anthropic could revert to `head` as the global default in a later release, making the explicit pin redundant but still harmless).

**Recommended verdict:** apply — one-line config edit + one-line README note; locks the historical `/run-wave` contract against a Claude Code default change that already shipped.

## 2. Park Anthropic's open-sourced Petri alignment toolbox as a candidate fixture source for the deferred 2026-04-19 §5 (agent evals)

**Source:** [Donating our open-source alignment tool — anthropic.com/research/donating-open-source-petri, 2026-05-07](https://www.anthropic.com/research/donating-open-source-petri). Petri is an open-source toolbox of alignment tests (probing for deception, sycophancy, cooperation with harmful requests) originally released in October 2025 as an Anthropic-internal evaluation library; the May 7 post donates governance to an external foundation and opens the probe library for community contribution.

### Why it's relevant (bookkeeping only)

The harness has carried a deferred agent-evaluation item since [2026-04-19 §5](./2026-04-19-improvement-suggestions.md#5-formalize-evals-for-the-adversarial-reviewers), which was attached to the BioMysteryBench tier-split methodology insight on [2026-05-03 §1](./2026-05-03-improvement-suggestions.md#1-adopt-the-biomysterybench-human-solvable--human-difficult-tier-split-when-the-deferred-agent-evals-fixtures-land). Both prior notes assumed the harness would author its own fixture set when the time came. Petri changes that arithmetic: it's a *runnable* probe library, BSD-licensed, with a documented probe schema and pass/fail criteria. The relevance is not "build an integration today" — it's "when §5 unblocks, evaluate Petri as a drop-in source for the adversarial-reviewer evals rather than building from scratch."

### Concrete change

None today. This § exists so the durable record reflects the new option. When the deferred §5 is picked up, the reviewer should explicitly:

1. Read Petri's probe schema and pass/fail criteria
2. Decide whether to wrap a subset of Petri probes as fixtures for `code-reviewer` / `ui-evaluator` / `spec-planner` (single-agent probes are the natural fit; multi-agent organization probes from the May 2026 "AI Organizations" paper are out of scope for a solo harness)
3. Track license/attribution requirements (BSD; trivial)

### Expected payoff
- Skips ~1–2 weeks of fixture authoring if/when §5 is picked up.
- Lets the harness's adversarial reviewers be evaluated against the same probe taxonomy Anthropic uses internally — comparable numbers, not bespoke ones.

### Risks / caveats
- Petri is an *alignment* eval library, not a code-quality eval library. The fit for `code-reviewer` is partial at best — most probes target a chat-agent surface, not a Bash-tool-using coding agent. Likely usable for a slice; not a drop-in.
