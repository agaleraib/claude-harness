## 2. Evaluate whether the harness should ship as a Claude Code plugin (or publish a plugin marketplace) alongside `setup-harness`

**Source:** [Customize Claude Code with plugins — claude.com/blog, 2026-07-02](https://claude.com/blog/claude-code-plugins). Claude Code plugins entered public beta on July 2, 2026. Per the post, a plugin bundles *slash commands, subagents, MCP servers, and hooks* — the same four surfaces the harness ships today (skills, agents, hooks; MCP configs live in `.mcp.json` at consumer projects). Install path is `/plugin` inside Claude Code, and plugins are distributed via *plugin marketplaces* — curated JSON manifests hosted anywhere. Anthropic ships an official `anthropics/skills` marketplace and users can create their own.

### Why it's relevant

The harness's current distribution model is:

- Source of truth: `skills/` in this repo (per `CLAUDE.md:12`).
- Skills are *symlinked out to* `~/.claude/skills/` on the user's machine.
- Agents ship in `.claude/agents/` per-project; user-level agents are copied by `setup-harness` into consumer projects.
- Installation happens via the `setup-harness` slash command, which the maintainer runs inside a consumer project's Claude Code session.

Plugins are the first-party primitive that packages **the same four surfaces** into a single install unit. A `claude-harness` plugin (or plugin marketplace) would let a consumer project do `/plugin install claude-harness/full` (or similar) instead of the current `setup-harness` flow. This overlaps materially — same surfaces, different packaging convention.

The overlap is **not** trivial:

1. `setup-harness` today does project-*specific* customization (auto-detects project type, chooses which criteria/agents to install, writes `CLAUDE.md`, etc.). A vanilla plugin install doesn't do this — plugins install everything or nothing.
2. The harness's user-level assets (`~/.claude/skills/`, `~/.claude/agents/`, `~/.claude/memory/`) are cross-project. Plugins are, per current docs, per-project-*installable*. The distinction matters: some harness skills (e.g. `session-start`, `memory-prune`) presume `~/.claude/`-level presence.
3. Plugins gain a `/plugin` UI surface — users could discover / update / remove harness pieces without touching the filesystem.
4. `setup-harness` writes to `CLAUDE.md`, `.harness-profile`, `parking_lot.md`, etc. — most of that is *not* something a plugin manifest natively expresses.

So the question isn't *"should this become a plugin?"* — it's *"what's the right split between plugin-shaped surfaces (universal skills/agents/hooks) and setup-shaped surfaces (project-tailored bootstrap)?"* — and that's a design question, not a mechanical rewrite.

### Why this is `spec`, not `apply` or `defer`

- **Substantive.** New packaging convention that touches every skill's install path — decompose signals 3 & 4 from the anthropic-reviews decompose-first rubric fire (introduces a reusable convention; spans >5 files).
- **Not urgent.** Plugins are public beta (July 2, 2026 — 8 days old at time of writing). Wait a quarter for the ecosystem to shake out before committing to a distribution split.
- **Not `apply`.** Direct rewrite of `setup-harness` would break every consumer project's re-run flow — the maintainer has to decide the split first.
- **Not just `defer`.** Deferring is what §2 of the 2026-05-10 file (Cloud Routines) does — that's for features that are conceptually clear but not worth the setup cost yet. Plugins are more than a setup cost — they require deciding *which surfaces move* and *how the two install paths coexist*.

### Concrete shape (for the spec pass, when scheduled)

The spec would need to answer:

1. **What ships as a plugin.** Candidate list: universal skills (session-start, session-end, commit, park, micro, run-wave, close-wave, etc.), universal agents (code-reviewer, orchestrator, project-tracker, spec-planner), a small default hook set. Explicitly *excluded* from the plugin: project-specific bootstrap (setup-harness itself, project-init, .harness-profile schema, criteria/, procedures/).
2. **What stays in `setup-harness`.** Everything project-tailored — auto-detection, criteria selection, CLAUDE.md scaffold, .harness-profile creation, `parking_lot.md` seeding, `.mcp.json` write.
3. **Marketplace hosting.** Own the marketplace manifest (a `plugin-marketplace.json` at the repo root, per the plugins doc), or contribute to `anthropics/skills`? For a solo maintainer, self-hosting the marketplace is cheaper — one file, no PR flow.
4. **Backwards compat.** Consumer projects installed via `setup-harness` today have a mix of user-level and project-level files. The migration path must be safe for existing installs — probably a `setup-harness --migrate-to-plugin` that removes the symlinks and swaps in `/plugin install`.
5. **How the plugin authors reference `~/.claude/memory/`.** Skills like `memory-prune` and `shared-root-init` reach into `~/.claude/memory/`. Plugin install semantics for cross-project state have to be pinned down.

### Expected payoff (when specced and applied)

- Consumer projects get a first-party install path (`/plugin install …`) that Anthropic maintains the UX for.
- The harness's user-level surface (skills, agents) rides Anthropic's ecosystem improvements (skill discovery, autoloading, marketplace search) instead of the maintainer having to build them.
- `setup-harness` shrinks to just the project-tailored bootstrap — which is genuinely different from what a plugin does.

### Expected cost (when specced and applied)

- Non-trivial docs rewrite (README §Skills, §Architecture, `INSTALL-FOR-COLLEAGUE.md`).
- New `plugin-marketplace.json` maintenance burden.
- Every skill's install path acquires a second discovery convention — has to be documented consistently.

**Verify before applying:**
1. `grep -rn "\.claude-plugin\|plugin-marketplace\|/plugin install" /home/user/claude-harness` — must return nothing today; if it returns hits, the plugin migration is already underway and this § is stale.
2. `ls skills/` — count of skills should still be in the ~20 range (currently 23 by `README.md:47–68`); a large drop suggests some have already moved out to a plugin.

**Recommended verdict:** spec — new distribution primitive that overlaps with `setup-harness`; needs a design pass before any code moves. Not urgent (public beta; the current path works); not rejectable (plugins are the direction Claude Code is going).
