## 1. Cross-reference Anthropic's "Getting started with loops" and "Dynamic workflows" posts from the `run-loop` SKILL header and README References

**Sources:**
- [Loop engineering: Getting started with loops — claude.com/blog, 2026-06-04](https://claude.com/blog/getting-started-with-loops) — practitioner's intro covering four loop types (turn-based, goal-based, time-based, proactive), stopping conditions, and token management.

### Why it's relevant

- **Anthropic's four loop types** (turn-based / goal-based / time-based / proactive) → the harness's `run-loop` is a **goal-based** loop (drains a work source until it hits a termination cap), and `/loop` (the Anthropic interval scheduler; the harness's `skills/run-loop/SKILL.md:12` explicitly names this distinction to avoid clash) is a **time-based** loop. The harness already namespaces around Anthropic's built-in — good — but doesn't cite the post that gives the taxonomy names.
- **Anthropic's stopping conditions** → the harness's `AGENTS.md:115` documents "work source drained, iteration cap, stall (N consecutive gate failures), token-budget exhausted, or an optional wall-clock cap." Exactly the same shape. Cross-reference costs nothing.
- **Anthropic's dynamic workflows** → the harness's `run-loop` composition root (`skills/_shared/loop/run-loop-prod-deps.ts`) is a **hand-rolled** version of the `Workflow` tool's `agent()`/`parallel()`/`pipeline()` API. Different implementation, same problem shape. Worth naming.

## 3. Adopt Anthropic's "verification loops with skills" pattern as a first-class harness convention

**Source:** [Building verification loops in Claude Code with skills — claude.com/blog, 2026-07-22](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)

### Why it's relevant
Anthropic's post frames Claude Code as **"gather context, take action, check its work, repeat if needed, respond"** — the "agentic loop." The novel piece is packaging the *check its work* step as a dedicated **verification skill** the agent invokes explicitly, rather than a rubric buried in the caller's prompt.

The harness already runs verification at two seams:
- `run-loop` per-item exit gate (`AGENTS.md:97–104`, step 2 in the mechanical gate sequence)
- `run-wave` acceptance gates (spec-declared checks)

Both today are **repo-declared shell commands** (`typecheck`, `tests`, `verify`), not skills. Anthropic's pattern is orthogonal — the verification skill is a *reusable* asset the specifier picks up, not a per-spec shell string. Think: `skills/verify-migration`, `skills/verify-api-schema`, `skills/verify-frontend-render`.

**Not a trivial change**: this affects the spec grammar (would specs declare verification skills alongside `tests`/`typecheck`?), the `run-wave` acceptance-gate contract, and possibly the `run-loop` per-item gate. `/spec-planner` should decompose it.

### Design questions to resolve before coding
- Do verification skills live in `skills/` proper (like `deploy-check`, `a11y-check`) or in a new `verify/` sibling directory?
- What's the interface — an exit-code + stdout capture, or a structured result (JSON with `passed: bool, findings: []`)?
- How does a spec declare `verify_skills: [...]` alongside its existing `verify:` shell command? Additive, replacement, or either?
- How does this interact with the harness's existing `deploy-check` / `api-smoke-test` / `migration-check` / `a11y-check` skills, which already are "safety-check skills" (README.md §"Safety Check Skills", line 330)? These may already fit the verification-skill mold; the question is whether they're currently plumbed as *skills the agent invokes* or *shell commands the harness invokes*.

### Concrete change
No diff — spec-first. Draft `docs/specs/2026-09-02-verification-skills-contract.md` covering the four design questions above, then decide whether the harness's existing safety-check skills already satisfy the pattern (in which case the outcome is a documentation edit citing Anthropic's post) or whether a new spec-grammar field is warranted (substantive).

### Expected payoff
If the design lands: `run-wave` and `run-loop` gain a *reusable* verification vocabulary that project specs can pick up without duplicating shell strings. The harness's safety-check skills already exist — the question is whether they get promoted from "one-shot skill an agent might invoke" to "a spec-declared acceptance gate."

If it lands as documentation-only (existing skills already satisfy the pattern): the harness gets the citation cheaply, and readers of `docs/specs/` know what "verify skill" means in the harness vocabulary.

### Scope
Substantive (touches spec grammar OR is documentation-only, depending on design outcome).

**Verify before applying:**
Two greps: `grep -rn "verify_skills\|verification skill" docs/specs/ skills/` — confirms the pattern isn't already latent in the spec grammar. Also read `README.md` §"Safety Check Skills" (line 330) to check how those four skills are declared — if they're already agent-invoked (not harness-invoked shell), this § may reduce to a documentation citation.

**Recommended verdict:** spec — the pattern is real and complements the harness, but the design decisions above need `/spec-planner` before any code is touched.

## 4. Adopt Anthropic's "dynamic workflows" as a harness lane for the `anthropic-reviews` routine itself

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)

### Why it's relevant
The post ships the built-in `Workflow` tool visible in this session's tool listing (a `script` API with `agent()` / `parallel()` / `pipeline()` primitives and a `meta` block). The tool's own description says the pattern is: *"pipeline by default, each dimension verifies as soon as its review completes."* That is **structurally** what the `anthropic-reviews` routine (this very routine) does today:

- **Fan out**: fetch the top ~15 candidate posts.
- **Per-post**: (a) check whether the tracker has already seen the URL, (b) fetch the post, (c) classify actionable vs skipped, (d) if actionable, generate the § + verify-before-applying line + recommended verdict.
- **Aggregate**: write the dated file + tracker update + open the PR.

Today the routine open-codes this as a single sequential prompt (this session). Migrating it to a Workflow script would:
- Parallelize per-post analysis (the current run-scoped 15-post cap is a serialization artifact, not a real budget).
- Cache the tracker read at meta level, not per-post.
- Make the "check first, suggest second" discipline enforceable in code (a `verify(§)` phase after each `analyze(post)` phase).

**Distinct from the deferred 2026-05-10 §2** (which proposed migrating to a Cloud Routine — a schedule + trigger). This § is about the *execution shape* (Workflow script), not the *scheduling shape* (Cloud Routine). They compose: a Cloud Routine could fire a Workflow-scripted analysis.

### Design questions to resolve before coding
- **Blast radius of `git`/`gh` inside a Workflow**: subagents in a Workflow can each hold their own git worktree, but the current routine opens ONE PR at the end. Does the Workflow return a merged draft that the top-level prompt commits, or does the Workflow itself commit and open the PR? The `workflow-authoring` skill in this session covers this — needs a read.
- **Budget guardrail**: the Workflow description recommends a 15-agent size guideline; the routine's 15-post cap matches by coincidence. Do we increase the cap now that fanout is cheap?
- **Tracker locking**: parallel per-post analysis needs a merge step for the tracker table. Trivially resolvable (one writer at the end) — but worth a design decision.

### Concrete change
No diff — spec-first. Draft `docs/specs/2026-09-02-anthropic-reviews-workflow-migration.md` covering the design questions above, plus a section on whether this belongs in the routine's prompt (called via the top-level `Workflow` tool) or in a saved workflow file at `~/.claude/workflows/anthropic-reviews.mjs`.

### Expected payoff
- Dogfoods Anthropic's dynamic-workflows pattern on the routine that produces suggestions about Anthropic's dynamic-workflows pattern — good story.
- Parallelizes per-post work, which is currently the routine's dominant cost.
- Composable with the deferred Cloud Routines migration (2026-05-10 §2).

### Scope
Substantive: touches routine prompt, tracker semantics, PR-authoring flow. Needs a design pass.

**Verify before applying:**
Two greps: `grep -rn "anthropic-reviews.*workflow\|Workflow.*script" anthropic-reviews/` — confirm nothing latent. Also read the current routine prompt (visible in this session as the stored scheduled prompt) to check whether Workflow migration would preserve the "no empty PR on quiet weeks" invariant.

**Recommended verdict:** spec — the migration is a real win but touches the routine's contract; needs `/spec-planner` before any code.
**Status:** PENDING — awaiting triage in PR review

## 5. Audit `README.md` (1122 lines) against "New rules of context engineering for Claude 5"
