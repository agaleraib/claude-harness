## 2. Position the harness's static skill/agent layer alongside Anthropic's new "dynamic workflows"

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) and its product companion [Introducing dynamic workflows in Claude Code](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code). Headline framing: "a harness is the system around the model that reads files, runs commands, manages context, spawns helpers, checks results, and decides when to stop"; dynamic workflows let Claude *write its own harness on the fly, custom-built for the task at hand*, with explicit token budgets, model-tier choices per subagent, and isolation via worktrees. Launch availability: research preview, Claude Code CLI/Desktop/VS Code on Max/Team/Enterprise, plus API/Bedrock/Vertex/Foundry. Trigger word: `ultracode` (similar pattern to `ultrareview`). Headline case study: Jarred Sumner used dynamic workflows to port Bun from Zig to Rust — ~750k LoC, 99.8% test-suite passing, 11 days first-commit-to-merge.

### Why it's relevant (and why the answer is still "defer")

The harness's tagline (`README.md:3`) is **literally** "A lean agent harness for Claude Code." Anthropic just productized the concept of "a harness for every task" — naming-collision aside, this is a conceptual neighbor worth grappling with explicitly. Two readings:

1. **Layer-disjoint reading (favored):** This harness encodes *pre-task* methodology — spec-planner, code-reviewer, criteria/, .harness-profile, the wave/commit/park rituals. Dynamic workflows encode *per-task* orchestration that Claude assembles at runtime (parallel subagent fan-out, profiler-guided audits, codebase-wide migrations). They are at different layers in the stack: methodology vs. runtime. A solo maintainer using this repo would still benefit from spec-planner+criteria *before* invoking a dynamic workflow that does the actual codebase-wide migration. No methodology change required.
2. **Layer-overlap reading (devil's advocate):** Some harness skills *are* essentially small runtime orchestrators (e.g. `/run-wave`, `/planning-loop`). If dynamic workflows reach GA and become reliable at orchestrating wave-style multi-step builds, those skills become less load-bearing. The maintainer should at least watch for the trigger.

`grep -rn 'dynamic workflow\|ultracode' .` returns hits only in this anthropic-reviews/ tree (last touched 2026-05-10 §intro mentioning the v2.1.120 `${CLAUDE_EFFORT}` variable). No mention in README.md or in any skill body.

## 3. `.claude/settings.json` hook safety guardrail in `setup-harness`

**Source:** [How we contain Claude across products — anthropic.com/engineering, 2026-05-28](https://www.anthropic.com/engineering/how-we-contain-claude). Authored by Max McGuinness, Mikaela Grace, Jiri De Jonghe, Jake Eaton, Abel Ribbink. Discloses three responsible-disclosure CVEs received mid-2025 → January 2026 targeting "code that executes before the user has consented to anything." Specific failure mode quoted: "A developer clones a repository to review a pull request containing a `.claude/settings.json` that defines a hook — because Claude Code reads project settings during startup before presenting the trust prompt, the hook would execute automatically." Fix shipped: "deferring parsing and execution of project-local configuration until after the user accepts the trust prompt." Also documents a February 2026 internal red-team where Claude Code was phished into reading `~/.aws/credentials` and exfiltrating them, succeeding 24/25 times.

### Why this looked actionable on first read

The harness ships `.claude/settings.json` and `.claude/agents/*` patterns that downstream projects install via `skills/setup-harness/`. The disclosed attack class targets *exactly* `.claude/settings.json` shipped in a repo that gets cloned. So a naïve reading says: setup-harness should warn skill authors not to put dangerous hooks in `.claude/settings.json`.

### Why it's actually a `reject`

- The vulnerability was **patched in Claude Code** (the runtime now defers parse+exec until after the trust prompt). A skill author writing a `.claude/settings.json` today has no surface to make this less safe — the runtime guarantees it.
- This harness's `.claude/settings.json` ships with an **empty `"hooks": {}` block** (`cat .claude/settings.json` → `{"hooks":{}}` verbatim). The downstream `skills/setup-harness/SKILL.md:139–147` "Permission model — Auto Mode + hooks layering" section already correctly states that hooks fire *before* the Auto Mode classifier — that's a different (and still-true) layering claim, unrelated to the trust-prompt-startup ordering the post documents.
- The post's takeaways targeted at *users* (don't trust prompts on freshly-cloned repos, expect a trust prompt, use disk sandboxes for unreviewed code) are Claude Code product behavior, not harness-author behavior.

Nothing for the harness to ship. Cite it in README "Why Not Superpowers" only if/when there's a future § that needs a containment reference — but that would be padding, not a fix.

**Verify before applying:** Re-read [anthropic.com/engineering/how-we-contain-claude](https://www.anthropic.com/engineering/how-we-contain-claude) and look for any explicit guidance to **skill authors / harness authors** (not Claude Code product engineers and not end users). If the post adds such guidance in a future revision, re-open this §. Independently confirm `.claude/settings.json` still has an empty hooks block (`cat .claude/settings.json`).

**Recommended verdict:** reject — patched at the Claude Code product layer; harness has no surface delta.

```markdown
> Added 2026-06-08 from [Lessons from building Claude Code: How we use skills](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills) (Thariq Shihipar, 2026-06-03). Reconcile with upstream best-practices doc next time the snapshot is refreshed.

### Gotchas is the highest-signal section

Anthropic's internal Claude Code team runs "hundreds of skills" and reports that **the highest-signal content in any skill is the Gotchas section**, built up from common failure points Claude runs into when using the skill. The iterative authoring loop they describe:

1. Start with a README-style draft.
2. Add a `## Gotchas` section the first time you observe Claude trip over an edge case.
3. Promote a Gotcha to its own reference file (progressive disclosure) when it grows past a paragraph.
4. Replace a recurring natural-language instruction with a deterministic script when you find yourself repeating it.

A skill that has been used in anger for a week and has *no* Gotchas section is almost certainly under-tuned — either the skill hasn't been exercised enough to reveal failure points, or the failure points exist but aren't being captured.

**Recommended SKILL.md structure for high-traffic skills:** frontmatter → one-paragraph intent → Steps → Gotchas → References.

### Product Verification skills are the highest-leverage category

Of the nine categories Anthropic clusters their internal skills into, **Product Verification** ("skills that describe how to test or verify that your code is working, often paired with an external tool like Playwright, tmux, etc.") has had **the most measurable impact on Claude's output quality internally**. The team's recommendation: it can be worth having an engineer spend a week making your verification skills excellent. A typical Verification skill bundles: (a) prose describing what "working" means for this product surface, (b) a script that drives the verification tool, (c) Gotchas covering the failure modes the tool can't catch on its own.

This generalizes to: **a skill that verifies an outcome is worth more than a skill that produces the outcome**, because verification is what catches regressions both before and after this skill itself ages out.
```
