## 1. Reference Agent View / `claude agents` in the README's "Git Worktrees (Parallel Sessions)" guidance

**Source:** [Agent view in Claude Code — claude.com/blog, 2026-05-11](https://claude.com/blog/agent-view-in-claude-code) (shipped in Claude Code v2.1.139, Research Preview). Companion docs: [Manage multiple agents with agent view — code.claude.com/docs/en/agent-view](https://code.claude.com/docs/en/agent-view) and the v2.1.139 [changelog](https://code.claude.com/docs/en/changelog) entry.

### Why it's relevant
The harness's README already documents **running Claude Code in parallel worktrees** as a first-class pattern ([`README.md:991–1015`](../README.md), "Git Worktrees (Parallel Sessions)"). The bullet list there names the use cases:

> - You want to **run Claude Code in parallel** on different features (each session needs its own directory)
> - The **generator agent** is building for hours and you want to keep coding something else
> - You want to keep a **dev server running** on master while working on a branch
> - A **scheduled Claude agent** is working on one task while you work on another

As of 2026-05-11, Claude Code ships **Agent View** (`claude agents` or left-arrow from any active session) as the CLI dashboard that surfaces every background session in one list — including which agent is waiting on input, the last assistant response, and the last-interaction timestamp. Per the v2.1.139 changelog and the linked blog post, Agent View is the **session-discovery counterpart** to the harness's worktree-per-feature pattern: worktrees give you the isolated directories; `claude agents` gives you the list of sessions running in them.

Today the README has **zero mention** of `claude agents`, Agent View, or any of the v2.1.139 session-management additions (`grep -rn "agent view\|claude agents" README.md` returns nothing). A reader who reads the worktrees section today and then opens v2.1.139 won't know the two compose.

The complement matters for the harness's own dispatch pattern too — `/run-wave` dispatches the orchestrator into an isolated worktree ([`README.md:275`](../README.md)), and that orchestrator session will appear in Agent View alongside the user's foreground session. Saying so explicitly is a one-sentence addition; not saying so leaves a discoverability gap.

### Concrete change
**One paragraph appended to the "Git Worktrees (Parallel Sessions)" section in `README.md`**, immediately after the existing closing line at ~line 1015 (`Each worktree is a full working copy with its own .claude/agents/ and criteria/ — the harness works in worktrees automatically.`):

```diff
 Each worktree is a full working copy with its own `.claude/agents/` and `criteria/` — the harness works in worktrees automatically.

+**Discovering parallel sessions.** As of Claude Code [v2.1.139](https://code.claude.com/docs/en/changelog) (Research Preview, May 2026), the `claude agents` command (or left-arrow from any active session) opens an [Agent View](https://claude.com/blog/agent-view-in-claude-code) dashboard listing every background session — session ID, whether it's waiting on you, the last assistant response, and the last-interaction timestamp. It pairs naturally with the worktree-per-feature pattern above: worktrees give you the isolated directories; `claude agents` gives you the list of sessions running in them, including any orchestrator session that `/run-wave` dispatched. Keybindings and command names may shift before GA — re-check the linked changelog if `claude agents` errors.
+
 ### Safety Rules
```

### Expected payoff
A reader who consults the README's parallel-sessions guidance gets the full picture in one place: worktrees for the directories, Agent View for the session list. The "Research Preview" hedge keeps the note honest if Anthropic renames the command before GA. No code change; one paragraph; one external link.

## 2. Note the `/goal` completion-condition command's overlap with `.harness-state/today_goal.md`

**Source:** [Claude Code v2.1.139 changelog, 2026-05-11](https://code.claude.com/docs/en/changelog). The release added a new in-CLI `/goal` command that records a completion condition for the current session and signals when it's met. Released alongside Agent View as part of the Research-Preview multi-session work.

### Why it's relevant
The harness's `skills/session-start/SKILL.md` writes `.harness-state/today_goal.md` (one-sentence "what's the goal of today's session?") at session start, and `skills/micro/SKILL.md` reads it as the **parent goal** for each micro-session block:

- `skills/session-start/SKILL.md:172` — `Write the answer to .harness-state/today_goal.md`
- `skills/micro/SKILL.md:16,65` — `cat .harness-state/today_goal.md` / `**Parent goal:** [today's goal from today_goal.md]`

The new native `/goal` command is **adjacent but not redundant**:

- **`/goal`** scopes per Claude Code session, lives in the CLI's memory, and (per the v2.1.139 entry) emits a completion-condition signal when the goal is judged met. Suited to a single ad-hoc session.
- **`today_goal.md`** scopes per *calendar day*, is a flat file read by every micro-session block within that day, survives `/clear`, survives session crashes, and is the anchor `session-end` ritual reads back when wrapping up.

For solo tooling, this is a true overlap question: does `/goal` subsume the need for `today_goal.md`? Probably not (file-based survives session boundaries; `/goal` doesn't), but the conceptual overlap is real enough that a future reader of `session-start/SKILL.md` who has just read the v2.1.139 release notes will reasonably ask "why two of these?"

### Why this is `defer`, not `apply`

1. **`/goal` is Research Preview.** Per the v2.1.139 changelog (paraphrased in the wider Agent-View Research-Preview note): keybindings, command names, and behaviors may shift before general availability. Wiring `/goal` into `session-start/SKILL.md` today would risk repeated re-edits as the command stabilizes.
2. **No documented programmatic surface.** A hook or script can't yet read what `/goal` records; `today_goal.md` is a flat file any skill can `cat`. Until `/goal` exposes a queryable surface (file, env var, hook input), it can't replace the harness's anchor file even if a maintainer wanted it to.
3. **Solo tooling, low pain.** The maintainer types today's goal once at session start; `/goal` not knowing about that text isn't friction worth solving yet.

### Concrete change (deferred)

None this run. When/if the maintainer wants to take this on (after `/goal` exits Research Preview):

1. Add a one-paragraph note to `skills/session-start/SKILL.md` (near the `today_goal.md` write step at line 172) explaining the two-layer pattern: `/goal` for in-session completion check, `today_goal.md` for the daily anchor that survives `/clear` and session restarts.
2. Decide whether `session-start` should *also* call `/goal` with the same text, once a programmatic surface exists. If yes, add a Step after the `today_goal.md` write that runs `/goal <today's goal>` (or whatever the stable interface ends up being).
3. Update the same note in `skills/session-end/SKILL.md` if `/goal`'s completion signal is something `session-end` should read back as part of the wrap.

### Expected payoff (when applied)
The two adjacent goal-tracking surfaces are documented as complementary rather than redundant — future readers see why the harness keeps the flat-file ritual even after Claude Code shipped a native command for the same concept. Optional Step 1 extension: the harness's daily anchor and the CLI's session-completion signal stay in sync without manual restating.
