## 1. Document Auto Mode + hooks interaction in `setup-harness` (and optionally seed `.claude/settings.json` `permissions.defaultMode`)

**Source:** [Claude Code auto mode: a safer way to skip permissions — Anthropic Engineering, 2026-05](https://www.anthropic.com/engineering/claude-code-auto-mode) (companion product post: [Auto mode for Claude Code — Claude Blog](https://claude.com/blog/auto-mode))

### Why it's relevant

The engineering post explains how Auto Mode works as a Claude Sonnet 4.6 transcript classifier that approves/blocks tool calls in a two-stage pipeline (fast single-token filter → chain-of-thought only if flagged), and — critically for this repo — that **hooks run *before* the classifier and can approve, deny, or escalate before the classifier ever sees the action**. That ordering is the whole reason a harness with curated hooks (this one) keeps full safety control while still benefiting from fewer prompts. As of the May 2026 rollout the feature is GA on Pro / Max / Team / Enterprise / API.

The harness today:
- Has an empty `hooks` block in `.claude/settings.json` (`{"hooks": {}}` — verified).
- Has zero references to Auto Mode, the classifier, `defaultMode`, `acceptEdits`, or `bypassPermissions` anywhere under `skills/`, `procedures/`, or `.claude/` (verified via `grep -rn "auto.mode\|defaultMode\|classifier" skills procedures .claude`; the only `classifier` hit is an unrelated regex in `triage-parking`).
- Ships `fewer-permission-prompts` as a built-in user skill (per the harness skill list) — its allowlist edits to `.claude/settings.json` will be *additive* to Auto Mode (hooks/allowlist clear first, classifier handles the residual). Worth spelling out so users understand the layered model rather than picking one or the other.

### Concrete change

Two small touches, in this order:

**(a) Add a "Permission model" subsection to `skills/setup-harness/SKILL.md`** — a few lines after the existing user-level skill install step (around line 137). Suggested text:

```markdown
### Permission model — Auto Mode + hooks layering

Claude Code's Auto Mode (GA on Pro/Max/Team/Enterprise/API as of May 2026) runs
a Sonnet 4.6 classifier that auto-approves safe tool calls and surfaces only
the risky ones. **Hooks run before the classifier**, so anything this harness
allow/deny-lists in `.claude/settings.json` (and anything `fewer-permission-prompts`
adds for you) is honored as a hard rule; the classifier only sees the residual.

Recommended setup for solo users:

1. Run `/fewer-permission-prompts` once in a project to seed an allowlist for
   the read-only Bash + MCP calls you actually use.
2. Keep `.claude/settings.json` `hooks` block populated with your policy checks
   (lint, secret scan, etc.); Auto Mode will not bypass them.
3. Toggle Auto Mode interactively via Shift+Tab. (As of writing,
   `permissions.defaultMode: "auto"` is parsed but doesn't reliably auto-engage
   on session start — manual toggle is the safer default. Re-check before
   relying on a config-only bootstrap.)

If you work in an isolated container, prefer Auto Mode over `bypassPermissions`
— Auto Mode keeps the classifier's prompt-injection mitigations active.
```

**(b) Optionally**, leave `.claude/settings.json` alone for now. The current empty `hooks` block is correct for the harness repo itself; per-project seeding belongs in `setup-harness`, not in this repo's own settings. Do **not** ship a `permissions.defaultMode` value in this repo's tracked settings — the engineering post documents that the default is interactive toggle, and a wrong default value here would propagate to every consumer project.

### Expected payoff

A solo maintainer who ran `/setup-harness` six months ago and hasn't kept up with Auto Mode rollout gets a one-paragraph mental model in the right place — no need to read the engineering post to understand why `fewer-permission-prompts` and Auto Mode aren't mutually exclusive. Cost: ~15 lines of doc; risk: zero.

**Verify before applying:** `grep -rn "Auto Mode\|defaultMode\|classifier" skills/setup-harness/SKILL.md` should return nothing today; `cat .claude/settings.json` should still show `{"hooks": {}}`. If either changes (someone added a permission-model section, or the settings file gained a `permissions` block), re-read both before editing — at minimum, this § needs a delta against the new state.

**Recommended verdict:** apply — concrete value, single-skill touch, zero blast radius, citation to a fresh primary source.

## 2. Add an "outcome status" field to `evaluator-reports/evaluation-report.md` so generator iteration is rubric-driven, not vibes-driven

**Source:** [New in Claude Managed Agents: dreaming, outcomes, and multiagent orchestration — Claude Blog, 2026-05-06](https://claude.com/blog/new-in-claude-managed-agents) (API reference: [Define outcomes — Claude API Docs](https://platform.claude.com/docs/en/managed-agents/define-outcomes))

### Why it's relevant

The Outcomes feature in Managed Agents formalizes a pattern the harness already runs informally: a markdown rubric describes "what good looks like", a *separate-context* grader scores the artifact against the rubric, and the loop returns a typed verdict — `satisfied`, `needs_revision`, `max_iterations_reached`, or `failed` — that the generator can act on automatically. Anthropic claims +10pp task success on hard problems vs. a standard prompting loop in their internal tests.

The harness has the components:
- **Rubric** → `criteria/<dimension>.md` files (verified — six exist: `code-architecture.md`, `code-simplicity.md`, `data-integrity.md`, `frontend-ui-design.md`, `performance-accessibility.md`, `ux-user-flows.md`).
- **Separate-context grader** → `ui-evaluator` and `code-reviewer` agents (verified at `.claude/agents/ui-evaluator.md`, `.claude/agents/code-reviewer.md`); each is dispatched in its own context.
- **Iteration loop** → `generator.md` step 6 ("Iterate on Evaluator Feedback", `~/claude-harness/.claude/agents/generator.md:50–59`) explicitly says "expect 2–3 build/evaluate rounds" and tells the generator to read full evaluation, fix everything, hand back.

What's *missing* is the **typed verdict**. Today `evaluator-reports/evaluation-report.md` (per `ui-evaluator.md:62–91`) emits a free-text "Verdict" line ("This is not ready" / "Ready" / similar). The generator agent decides whether to iterate by *reading prose*, not by branching on a status field. That's exactly the gap Outcomes closes.

### Concrete change (sketch — needs a spec pass)

A future spec would amend two files:

1. `.claude/agents/ui-evaluator.md` — add to the report schema (around line 88, the "Verdict" section):

   ```markdown
   ### Outcome status

   One of:
   - `satisfied` — every criterion in `criteria/` scores ≥ <project_threshold>; no critical issues.
   - `needs_revision` — at least one criterion below threshold OR a critical issue; iteration N of M.
   - `max_iterations_reached` — round count hit cap (default 3 per generator.md); halt and surface.
   - `failed` — fundamentals broken (won't build, won't run); pivot, not patch.
   ```

2. `.claude/agents/generator.md:50–59` — make step 6 branch on the status field rather than re-reading prose. Pseudocode:

   - `satisfied` → ship; emit a passing receipt.
   - `needs_revision` → fix, increment round counter, hand back.
   - `max_iterations_reached` → escalate to the user (don't loop forever).
   - `failed` → invoke `/spec-planner` for a pivot, not another build pass.

### Why this is `defer`, not `apply`

Three open design questions block direct application:
1. **What's the score threshold per criterion?** The criteria files use 1–10 scoring; a single global cutoff (e.g. ≥ 7) would over-fire on `code-simplicity.md` which calls 6/10 "competent but generic — the gravitational center of AI output" (per `criteria/code-simplicity.md:96`). Per-criterion thresholds need design.
2. **What does `max_iterations_reached` do in this harness?** Managed Agents has a hosted runtime that surfaces it; this harness is solo-CLI. Likely answer: write to `.harness-state/last_exit.md` and ask the user. But that's a contract change worth specifying.
3. **Does this collide with `/run-wave` / `/close-wave` semantics?** Waves already track wave outcomes via `docs/waves/wave<N>-*.md`. A new typed verdict at the agent level needs to compose with — not duplicate — wave-level closure.

A concrete duplication risk: the harness already emits structured receipts via `skills/_shared/lib/emit-receipt.sh` (verified). If "outcome status" becomes a third receipt-shaped artifact alongside that and the existing wave docs, that's overlap, not new value. The spec pass needs to pick the one place this lives.

### Expected payoff (if specced and shipped)

The generator stops being asked to *interpret* prose to decide whether to iterate; it branches on a four-value enum. That removes one class of "evaluator said it was bad but generator shipped anyway" failures, which is exactly the failure mode `criteria/code-simplicity.md`'s "every score must cite specific evidence" rule was written to prevent at the *criterion* level — Outcomes generalizes the same discipline to the *loop* level.

**scope: speculative** — this is a methodology delta, not a bug fix. Maintainer should review whether the existing prose-verdict loop has actually misfired in practice before paying the spec cost.
