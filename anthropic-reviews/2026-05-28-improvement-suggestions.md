## 1. Teach `setup-harness` to scaffold subdirectory `CLAUDE.md` in detected service/package directories of a monorepo

**Source:** [How Claude Code works in large codebases: Best practices and where to start — claude.com/blog, 2026-05-14](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start). Cross-reference: [Set up Claude Code in a monorepo or large codebase — code.claude.com/docs/en/large-codebases](https://code.claude.com/docs/en/large-codebases).

### Why it's relevant

The post's headline recommendation is **layered `CLAUDE.md`**: a lean root file for "big picture and critical gotchas" plus per-subdirectory files that "specify the commands that apply to that part of the codebase, which works well for service-oriented codebases where each directory has its own test and build commands." Claude loads them additively as it moves through the tree. The post also recommends initializing Claude in subdirectories rather than at the repo root.

The harness's `setup-harness` skill writes **exactly one `CLAUDE.md`** at the project root (see `skills/setup-harness/SKILL.md:151–193`, "Step 4: Generate CLAUDE.md"). The detection table at lines 156–168 already inspects `package.json` / `pyproject.toml` / etc. to extract build commands — but it does so once, at the repo root, and emits one file. There is no scan for nested service/package directories with their own lockfiles or test commands.

A consumer project with `apps/api/` (Node) + `apps/web/` (Next.js) + `packages/shared/` (TypeScript) gets one root `CLAUDE.md` listing all build commands as if they were sibling. After this change, each subdirectory with its own buildable manifest gets its own short file with just *its* commands. Per the post, this both keeps the root file lean and lets Claude pick up the right commands when initialized in a sub-tree.

`grep -n "subdirectory\|nested CLAUDE\|layered CLAUDE\|hierarchical CLAUDE\|loads additively" skills/setup-harness/SKILL.md README.md AGENTS.md CLAUDE.md` returns **nothing** today — the layering concept is not in the harness at all.

### Concrete change

**(a)** Extend `skills/setup-harness/SKILL.md` "Step 4: Generate CLAUDE.md" (lines 151–193) with a sub-step that runs after the root file is generated:

```diff
 **CLAUDE.md rules:**
 - Under 50 lines for most projects
 - Only include what Claude can't figure out from reading the code
 - No self-evident rules like "write clean code"
 - Include build/test commands (Claude can't always guess these)

+### Step 4b: Scaffold subdirectory CLAUDE.md for monorepo packages
+
+If the repo is a monorepo (detected: any of `pnpm-workspace.yaml`, `lerna.json`, `nx.json`, `turbo.json`, `Cargo.toml` with `[workspace]`, `go.work`, root `package.json` with `"workspaces"`), scan for subdirectories that have their own buildable manifest (`package.json` with scripts, `pyproject.toml`, `Cargo.toml`, `go.mod`) and offer to scaffold a short CLAUDE.md per package.
+
+Per Anthropic's [large-codebase guidance](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start), layered CLAUDE.md files load additively: root file for big-picture and critical gotchas, subdirectory files for local conventions and commands. This works best when Claude is initialized inside the relevant subdirectory.
+
+For each detected sub-package, generate a ≤20-line file with just:
+- The build/test/lint commands extracted from that manifest
+- One line of "what this package is" (read from manifest description or directory name)
+- Local conventions ONLY if they differ from the root CLAUDE.md
+
+Skip the scaffold for any sub-package that already has CLAUDE.md (don't overwrite — surface a one-line "already present, skipped" message per package).
+
+Then trim the root CLAUDE.md "Build & Test" section to either (a) reference the per-package files ("see `<dir>/CLAUDE.md` for per-package commands"), or (b) keep only the root-level orchestration commands (`pnpm -r build`, `turbo run test`, etc.). The root file should not duplicate per-package commands — that's noise that ages badly.
```

**(b)** Append one bullet to the "CLAUDE.md rules" list at line 188–192 of the same skill so a future operator running `/setup-harness` interactively sees the layering principle in the same place as the existing rules:

```diff
 **CLAUDE.md rules:**
 - Under 50 lines for most projects
 - Only include what Claude can't figure out from reading the code
 - No self-evident rules like "write clean code"
 - Include build/test commands (Claude can't always guess these)
+- In monorepos, prefer per-package CLAUDE.md for build/test commands; keep the root file to the cross-cutting story. CLAUDE.md files load additively as Claude moves through the tree.
```

### Expected payoff

Consumer projects with monorepo structure (which is most non-trivial production codebases) get the layered structure for free at `setup-harness` time, instead of either (a) one bloated root file or (b) the operator having to know the pattern and hand-author per-package files. The 2026-05-14 post is now Anthropic's "set up Claude Code in a monorepo" canonical guidance, and the harness's `setup-harness` should match it.

### Why this isn't a duplicate of existing guidance

The current `setup-harness` is **explicitly single-file** ("If `CLAUDE.md` doesn't exist (or user chose to overwrite), generate a lean one based on detected stack"). There is no branch for monorepo layouts. The examples under `examples/web-app-project/CLAUDE.md` and `examples/backend-project/CLAUDE.md` are single-file too — both are flat single-package layouts.

## 2. Add a `permissions.deny` starter block (sensitive paths) to the `setup-harness` Auto Mode setup step

**Source:** [How Claude Code works in large codebases: Best practices and where to start — claude.com/blog, 2026-05-14](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start). Background: [Claude Code settings — code.claude.com/docs/en/settings](https://code.claude.com/docs/en/settings) and [The Register, Jan 2026 — Claude Code ignores ignore rules meant to block secrets](https://www.theregister.com/2026/01/28/claude_code_ai_secrets_files/).

### Why it's relevant

The post recommends `.claude/settings.json` `permissions.deny` rules as the *version-controlled* mechanism for excluding sensitive paths (`.env`, credentials, build artifacts), complementary to `.claudeignore` (context-window exclusion, not access exclusion). Quoting cross-references: deny patterns like `Read(./.env)`, `Read(./.env.*)`, `Read(./secrets/**)`, `Read(./**/*credentials*)`, `Read(./**/*.pem)`. Permission rule priority is `deny > allow > ask > defaultMode fallback`, so deny rules are the strongest guarantee.

The harness's `setup-harness` Step 3 (lines 138–149 of the skill) already configures Auto Mode and recommends `/fewer-permission-prompts` for the **allow** side of the rule set. There is no parallel step that seeds the **deny** side. `cat /home/user/claude-harness/.claude/settings.json` returns:

```json
{
  "hooks": {
  }
}
```

— an empty hooks block, no `permissions` block at all. The README has one `permissions.allow` example (line 844) but no `permissions.deny` example anywhere.

A consumer project that installs the harness today inherits zero `permissions.deny` rules. Combined with The Register's January-2026 finding that `.claudeignore` does not reliably block secret reads, this is a small but concrete defense-in-depth gap.

### Concrete change

**(a)** Extend `skills/setup-harness/SKILL.md` Step 3 (after the "Recommended setup for solo users" list at lines 144–149) with a new bullet:

```diff
 1. Run `/fewer-permission-prompts` once in a project to seed an allowlist for the read-only Bash + MCP calls you actually use.
 2. Keep `.claude/settings.json` `hooks` block populated with your policy checks (lint, secret scan, etc.); Auto Mode will not bypass them.
 3. Toggle Auto Mode interactively via Shift+Tab. (As of writing, `permissions.defaultMode: "auto"` is parsed but doesn't reliably auto-engage on session start — manual toggle is the safer default. Re-check before relying on a config-only bootstrap.)
+4. Seed a `permissions.deny` block for sensitive paths. The harness writes a default starter into `.claude/settings.json` on `setup-harness` (see the block below); operators can extend per-project. Per Anthropic's 2026-05-14 [large-codebase guidance](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start), `permissions.deny` is the version-controlled mechanism for excluding secret-bearing paths (`.claudeignore` is for context-window scoping, NOT access control — see [The Register, 2026-01-28](https://www.theregister.com/2026/01/28/claude_code_ai_secrets_files/)). Rule priority: `deny > allow > ask > defaultMode fallback`, so deny rules are the strongest guarantee.
+
+   Default starter (merged into `.claude/settings.json` non-destructively — if a `permissions.deny` block already exists, the harness appends only missing patterns and surfaces a diff):
+   ```json
+   {
+     "permissions": {
+       "deny": [
+         "Read(./.env)",
+         "Read(./.env.*)",
+         "Read(./**/.env)",
+         "Read(./**/.env.*)",
+         "Read(./secrets/**)",
+         "Read(./**/*credentials*)",
+         "Read(./**/*.pem)",
+         "Read(./**/*.key)",
+         "Read(./**/id_rsa)",
+         "Read(./**/id_ed25519)"
+       ]
+     }
+   }
+   ```
+
+   Build-artifact paths (`Read(./build)`, `Read(./dist)`, `Read(./node_modules/**)`) are intentionally NOT in the default — those are context-window concerns better handled by `.claudeignore` or by avoiding the `Read` in the first place. Operators with large build outputs can add them per-project.
```

**(b)** Append one line to `~/.claude/CLAUDE.md` template (`skills/setup-harness/templates/user-CLAUDE.md`) so the deny-block convention is visible at the user level too:

```diff
 ## Code Style
 - TypeScript strict mode. No `any` types.
 - Stage files explicitly — never `git add -A` or `git add .`
 - Merge with `--no-ff` to preserve history.
+
+## Permissions
+- Each project's `.claude/settings.json` should carry a `permissions.deny` block for sensitive paths (`.env*`, `secrets/`, `credentials`, `*.pem`, `*.key`). `/setup-harness` seeds a default; extend per-project as needed. `.claudeignore` is for context-window scoping, NOT access control — use `permissions.deny` for secret protection.
```

### Expected payoff

Every consumer project that installs the harness gets a defense-in-depth deny block at install time, without the operator having to know the pattern. Solo workflow: one less thing to remember when starting a new repo.

### Why this isn't a duplicate of existing guidance

The README's "Permission Mode" section (lines 838–852) shows only `permissions.allow` (`Bash(*), Read(*), Write(*), Edit(*), Glob(*), Grep(*)`). That's the right surface for the allowlist + Auto Mode flow — but it never names `permissions.deny`, and the harness doesn't seed any deny rules on install. `grep -rn 'permissions.deny\|Read(\\./\\.env' .` returns **zero hits** outside this very suggestion file.

**Verify before applying:**
1. `grep -n 'permissions.deny\|Read(./.env\|Read(./\\*\\*/credentials' skills/setup-harness/SKILL.md skills/setup-harness/templates/user-CLAUDE.md README.md` — must return nothing today; if any of these hit, the deny block is already seeded and the § is at least partially stale.
2. `cat .claude/settings.json | python -c "import json,sys; print('permissions' in json.load(sys.stdin))"` — must print `False` today (file has only `hooks`). If `True`, the harness's own deny block is already present and the §'s self-application is done.
3. Confirm `.claudeignore` is still NOT the access-control mechanism by re-reading the linked Register piece. If Anthropic shipped a fix between January 2026 and triage that makes `.claudeignore` a hard access-control rule, the framing in this § becomes wrong (the deny block is still defensible defense-in-depth, but the "use deny because claudeignore doesn't" justification weakens).

**Recommended verdict:** apply — small, additive, defense-in-depth, named in fresh Anthropic guidance. Worst case the default deny block over-blocks an unusual workflow and the operator removes a pattern. Touches one skill + one template; non-destructive merge into existing `.claude/settings.json`.

## 3. Add a one-line cadence note: **review prompt files after major Claude model releases**

**Source:** [How Claude Code works in large codebases: Best practices and where to start — claude.com/blog, 2026-05-14](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start). Direct quote: *"As models evolve, instructions written for your current model can work against a future one—CLAUDE.md files that guided Claude through patterns it used to struggle with may become unnecessary or actively constraining when the next model ships."* And: *"Teams should expect to do a meaningful configuration review every three to six months, but it's also worth doing one whenever performance feels like it's plateaued after major model releases."*

### Why it's relevant

The harness has a drift detector for **protocol drift** (`.harness-profile` → `methodology.drift_detector: on`, used by `skills/session-start/SKILL.md` Step 4 "Pivot check"). ## 4. Bookkeeping: `/goal` + `/bg` + Agent View as the local equivalent of Managed Agents Outcomes

**Source:** [Agent view in Claude Code — claude.com/blog, 2026-05-11](https://claude.com/blog/agent-view-in-claude-code). Companion docs: [`/goal` — code.claude.com/docs/en/goal](https://code.claude.com/docs/en/goal). Background: [VentureBeat — Claude Code's `/goals` separates the agent that works from the one that decides it's done](https://venturebeat.com/orchestration/claude-codes-goals-separates-the-agent-that-works-from-the-one-that-decides-its-done).

### Why it's relevant

Claude Code v2.1.139 (released 2026-05-12) shipped three related features:

- **`/goal <condition>`** — sets a completion condition; Claude keeps working across turns until an evaluator model (Haiku by default) judges the condition met. Available in interactive, non-interactive (`-p`), and remote-control modes.
- **`/bg`** — send the current session to the background to continue working while you start a separate session.
- **Agent View** — single CLI dashboard for all background sessions, showing which are running / blocked / done.

This is the **Claude-Code-side equivalent of the Managed Agents Outcomes pattern** that was flagged in [2026-05-08 §2](./2026-05-08-improvement-suggestions.md#2-add-an-outcome-status-field-to-evaluator-reportsevaluation-reportmd-so-generator-iteration-is-rubric-driven-not-vibes-driven) (deferred). Where Outcomes runs on the Managed Agents platform with rubric-based self-correction, `/goal` runs the same separated-agent-and-evaluator architecture in the local CLI.

The harness already has a structurally similar pattern: **`skills/planning-loop/SKILL.md`** drives a spec through a Codex-adversarial-review loop to an `approve` verdict in ≤3 rounds. Same shape: a working agent (spec-planner) and a separated evaluator (Codex) iterate until the evaluator returns an approve verdict. The `/goal` command is the cheaper/lighter (Haiku evaluator, in-tool) equivalent.

### Why this is `defer`, not `apply`

1. **`/planning-loop` already covers the evaluator pattern.** It uses Codex for adversarial review rather than Haiku, but the architecture is structurally identical. Replacing the Codex backend with `/goal` is a *backend swap*, not a *new capability* — and the swap would mean re-doing the planning-loop test fixtures (`skills/planning-loop/lib/test-fixtures/`, ~60 files). High effort, unclear win.
2. **Agent View assumes multi-session.** The harness's contract is single working session per repo (`/session-start` → work → `/session-end`). Multi-session adoption would require a parallel rework of `harness-status`, the `.harness-state/` invariants, and the receipt schema (which currently keys on one session at a time). Not a small project.
3. **`/bg` is orthogonal to current usage.** The harness's only "long-running" surface is `subscribe_pr_activity` for PR babysitting — and that one is event-driven (GitHub webhook wakes the session), not background-polling. `/bg` solves a different problem.
4. **`/goal` is a research preview as of 2026-05-12.** Wait for it to settle. Behavior of the Haiku evaluator on the harness's spec-shape (large markdown specs with criteria tables) is unknown — could be either great or wildly off.

### Concrete change

None this run. When/if the maintainer wants to revisit:

1. **Cheapest experiment:** replace one `/planning-loop` invocation with a manual `/goal "spec passes Codex adversarial review with approve verdict"` and compare round-counts and evaluator agreement. If `/goal`'s Haiku evaluator agrees with Codex >80% of the time, the backend swap becomes interesting.
2. **Adopt `/bg` only if** a concrete async pattern emerges in the harness (e.g. `/triage-parking` becomes long-running enough that background execution + later checkback beats interactive triage).
3. **Adopt Agent View only if** the harness picks up genuine multi-session workflows (e.g. a `cowork` evolution that spawns one Claude session per project under management).
