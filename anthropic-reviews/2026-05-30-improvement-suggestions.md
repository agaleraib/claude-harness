## 3. Adopt HTML over Markdown for harness specs / criteria / evaluator reports

**Source:** [Using Claude Code: The unreasonable effectiveness of HTML — claude.com/blog, 2026-05-20](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html) by Thariq Shihipar (Claude Code team). Argument: as Claude-generated documents are increasingly **specs / reference files / brainstorming outputs** read by both humans (skim-once) and Claude (as next-session context), Markdown's "easy human editing" advantage erodes — you're prompting Claude to edit the doc anyway — while its expressiveness limits (no diagrams, no tabs, no responsive layout, hard to share via link) remain. HTML lets Claude generate richer specs with visualizations, color, and a structure ideal for navigation. The post argues for HTML as the preferred output format for AI-agent-generated documents in 2026+.

### Why it's relevant (and why this is `reject` for the harness)

The harness ships **>200 markdown files** across `docs/specs/`, `docs/waves/`, `criteria/`, `procedures/`, `skills/`, `anthropic-reviews/`, and the various active-state files (`parking_lot.md`, `today_goal.md`, `current_micro.md`, `last_exit.md`). The aggregate token weight of the suggestion to convert these is substantial. More important — the harness's use case **diverges from Thariq's argument on three of the three load-bearing axes**:

| Thariq's argument | Harness reality | Verdict |
|---|---|---|
| *"Documents Claude generates are increasingly used as specs … read and passed into subsequent Claude sessions, not manually edited line by line."* | Harness specs and criteria **are** manually edited and reviewed line-by-line in PR review — `code-reviewer`, `/commit`, and the maintainer's eyes all read the diff before it lands. This is the explicit purpose of the dated `anthropic-reviews/<date>-*.md` files: durable history readable by future-you in a year. | ❌ markdown wins for line-by-line PR review |
| *"Markdown files are fairly hard to share since most browsers do not render them natively well. With HTML, … you can share the link easily."* | Harness specs live in git and are rendered natively by GitHub's markdown view (`/blob/main/docs/specs/<date>-<topic>.md`). Sharing is `gh pr view` or a GitHub permalink — already universal. | ❌ no sharing-friction problem to solve |
| *"Richer visualizations, color and diagrams."* | Harness specs are textual: routing tables, acceptance criteria, file checklists, derivation maps. Diagrams would be **nice-to-have** for the brain/hands spec (2026-04-19 §2, deferred) but are not load-bearing for the harness's current shape. Mermaid in markdown covers the rare case. | ❌ no visualization gap to close |

The harness's documents are **NOT** the use case Thariq targets. His use case (one-shot brainstorming outputs, reference docs read once then discarded, shared as a link with non-engineering colleagues) is real and his recommendation is right *for that use case*. The harness's use case (dated immutable spec / criteria files reviewed in git diff, line-by-line, by the same maintainer) is a different beast.

**None.** Capture the post in the tracker as a "skipped — wrong use case" entry. ## 4. Bookkeeping: CodeRabbit's planning layer corroborates the harness's spec-planner → generator → evaluator chain

**Source:** [How CodeRabbit used Claude to build an agent orchestration system — claude.com/blog, 2026-05-27](https://claude.com/blog/how-coderabbit-used-claude-to-build-an-agent-orchestration-system). Companion engineering write-up on the CodeRabbit blog: [How CodeRabbit built a planning layer on Claude](https://www.coderabbit.ai/blog/how-coderabbit-built-a-planning-layer-on-claude). Architecture summary: a layer that sits between a coding request and a coding agent, runs Opus / Sonnet / Haiku in tandem to *explore the codebase, pull in relevant context from past PRs, surface implicit assumptions, and generate a structured coding plan broken into reviewable phases*. Output is a collaborative **PRD** validated by stakeholders before any code is generated.

### Why it's relevant
The harness already implements the **same pattern** — three named agents that decompose, build, and grade — with explicit handoff points and an immutable spec output:

- `.claude/agents/spec-planner.md` — expands an idea into a full spec with hard-threshold acceptance criteria. Auto-appends a `### Wave N` block to `docs/plan.md` for wave-shaped specs.
- `.claude/agents/generator.md` — implements continuously from a spec, iterates on evaluator feedback.
- `.claude/agents/ui-evaluator.md` — adversarial UI evaluator scored against `criteria/*.md` rubrics. Writes evidence to `evaluator-reports/`.
- `.claude/agents/orchestrator.md` — dispatches tasks across model tiers (opus/sonnet/haiku) at runtime.

CodeRabbit's published architecture is **independent corroboration** of the planner-first pattern Anthropic also documented in its own [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) (cited in 2026-04-19 §4, `APPLIED`). Three independent posts now point at the planner-first pattern in 2026:

1. **Anthropic's own multi-agent harness** (April 4, 2026) — planner / generator / evaluator with context resets.
