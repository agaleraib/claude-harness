## 1. Document monorepo-aware CLAUDE.md + nested-`.claude/skills/` in `setup-harness` and `README.md`

**Source:** [How Claude Code works in large codebases: Best practices and where to start — claude.com/blog, 2026-05-14](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start). First canonical Anthropic post on the *five extension points* framing (CLAUDE.md, hooks, skills, plugins, MCP servers) with explicit monorepo guidance.

### Why it's relevant

The post says two things that aren't yet in this repo:

1. **CLAUDE.md ancestor-loading.** "In monorepos, Claude automatically walks up the directory tree and loads every CLAUDE.md file it finds along the way, so root-level context is never lost." Practical implication: in a monorepo with `packages/frontend/` and `packages/backend/`, you put a root `CLAUDE.md` with the big-picture pointers + critical gotchas, and per-package CLAUDE.md files with package-specific commands and conventions. When Claude is editing `packages/frontend/src/foo.tsx`, both files load additively.

2. **Skills nest differently.** "Skills do NOT have the same loading behavior as CLAUDE.md files. […] When you work with files in subdirectories, Claude Code automatically discovers skills from nested `.claude/skills/` directories. For example, if you're editing a file in `packages/frontend/`, Claude Code also looks for skills in `packages/frontend/.claude/skills/`." So a monorepo can ship per-package skills (e.g. a frontend-only `/storybook-add` skill) without polluting the root skills namespace.

Current state of the harness:

- `skills/setup-harness/SKILL.md` Step 4 (lines 151–192) generates **one root** `CLAUDE.md` per project from a single template. No mention of monorepo support or nested CLAUDE.md.
- `examples/web-app-project/CLAUDE.md` and `examples/backend-project/CLAUDE.md` are single-file examples — flat layout.
- `README.md` Architecture section (line 38+) and Skills section (line 123+) describe the harness but don't reference the "five extension points" framing or monorepo nesting.
- `grep -rn "monorepo\|nested CLAUDE" README.md AGENTS.md CLAUDE.md skills/setup-harness/` returns **zero hits** today.

The repo *does* have an adjacent concept — `area-CLAUDE.md` from Wave 15's `/cowork-area-sync` — but that's a **Cowork** (Claude Cowork desktop app) Project-Knowledge bundle scaffold, not the Claude-Code ancestor-loading behavior the post describes. They look the same on the surface and could confuse a future reader. Worth disambiguating in the same edit.

For the harness itself (`team.size: solo`, `type: tooling`), this isn't urgent — the harness repo is single-package. But:

- The harness ships `setup-harness` to **consumer projects**, some of which are or will be monorepos.
- The maintainer's own consumer projects (wordwideAI / finflow-deck referenced elsewhere in the repo) may grow into multi-package shapes.
- The cost is a ~1-paragraph note + Reference link. The downside risk is approximately zero.

## 2. Switch harness-generated reports from Markdown to HTML per Thariq's "Unreasonable Effectiveness of HTML"

**Source:** [Using Claude Code: The unreasonable effectiveness of HTML — claude.com/blog, 2026-05-08](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html), by Thariq Shihipar (Claude Code engineering lead). Argues Markdown became the default AI output during the GPT-4 tiny-context era, and modern 1M-token contexts should default to HTML for human-consumed reports (information density, sliders/knobs/copy buttons, link-shareable). Discussion: [HN thread](https://news.ycombinator.com/item?id=48071940), [Simon Willison's commentary](https://simonwillison.net/2026/May/8/unreasonable-effectiveness-of-html/). Missed in 2026-05-08 / 2026-05-10 routine runs; surfaced now.

### Why this is reject, not defer

The harness emits several "report"-shaped artifacts that look like the kind of thing Thariq's post is talking about:

- `anthropic-reviews/<date>-improvement-suggestions.md` — this very file
- `docs/plan.md` (current state of waves)
- `docs/waves/wave<N>-<slug>.md` (closed-wave archive, with YAML frontmatter)
- `.harness-state/*.md` (session memory, today_goal, current_micro, last_exit)
- `parking_lot.md` (deferred items)

A surface read of Thariq's post would suggest converting these to HTML. **Don't.** Three concrete reasons:

1. **The audience is Claude Code, not a browser.** Every one of those files is read back by *the next Claude Code session* — at `session-start` (`last_exit.md`, `today_goal.md`, `parking_lot.md`), inside `/run-wave` (spec files + `docs/plan.md`), in `/triage-parking`, in `/apply-anthropic-reviews`. Thariq's post is about reports that humans read on a styled HTML page. None of the harness's report-shaped outputs is that.

2. **Prefix-stability guardrail (`2026-05-05 §1`, APPLIED).** The harness's `AGENTS.md` "What to avoid" section already codifies prefix-stability — outputs Claude consumes should be diff-friendly and grep-friendly for cache reuse and human review. HTML breaks both: a single inserted `<div>` reflows whitespace; grep across `<h3>Wave N</h3>` vs. `### Wave N` is awkward.

3. **YAML frontmatter parsers + `.md` tooling depend on Markdown.** `docs/waves/<file>.md` has a YAML frontmatter block (`wave_number`, `slug`, `spec_path`, `merge_sha`, `closed_at`) that `/close-wave` and `/archive-plan` parse. Switching to HTML breaks the parser path. Switching to HTML *with* embedded YAML in a `<!-- -->` block is uglier than the current state and doesn't gain anything.

The post's thesis **is** correct for what it targets: ad-hoc reports that a human will read once and forget, or that benefit from interactive widgets (a chart, a slider, a copy-button). The harness emits neither of those. The `dangerouslyDisableSandbox` analogy: the right answer to a new shiny tool is sometimes "no — our workflow doesn't have the problem this solves."

### Why log it at all (instead of silently skipping)

Two reasons it earns a § rather than a tracker skip:

1. **It's the closest Anthropic methodology post in this window** that *looks* harness-adjacent on first read. If a future routine run sees the post again (or sees a follow-up that re-asserts the thesis), the recommended response should be `reject — same reasoning as 2026-05-21 §2` rather than re-deliberating from scratch.

2. **One narrow caveat worth recording:** if the harness ever grows a *human-facing* report surface (e.g. a `harness-status` HTML dashboard, a Cowork bundle README rendered for non-engineer collaborators), the HTML default would apply *there*. That isn't the case today; recording it pre-emptively is cheap.

### Concrete change

**None this run.** The decision is to leave all current `.md`-emitting paths alone.

If the maintainer later decides to add a human-facing dashboard or report (the narrow caveat above), the place to start is a single new skill or a `harness-status --html` flag, *not* a switch of the existing artifacts.

**Verify before applying:**
1. `find /home/user/claude-harness -name "*.html" -not -path "*/node_modules/*"` — must return zero results today (no HTML-emitting paths exist). If it returns results, an HTML report path has appeared and this §'s "no human-facing report surface today" premise is stale.
2. `grep -n "prefix.stab" /home/user/claude-harness/AGENTS.md` — must still show the 2026-05-05 §1 guardrail. If that guardrail has been removed, the second-reason argument needs to be re-derived.
3. Confirm Thariq's post hasn't been corrected/superseded: search for `"unreasonable effectiveness of html" retraction OR correction OR followup` before applying any change in the opposite direction.

**Recommended verdict:** reject — harness's report artifacts are consumed by Claude Code sessions (not styled HTML pages), and switching format breaks the prefix-stability + Markdown-tooling invariants already codified. Caveat preserved for future human-facing report surface.

## 3. Bookkeeping: Anthropic acquires Stainless — watch for SDK-distribution path change

**Source:** [Anthropic acquires Stainless — anthropic.com/news, 2026-05-18](https://www.anthropic.com/news/anthropic-acquires-stainless). Plus the [Stainless announcement](https://www.stainless.com/blog/stainless-is-joining-anthropic/) and the [TechCrunch coverage](https://techcrunch.com/2026/05/18/anthropic-has-acquired-the-dev-tools-startup-used-by-openai-google-and-cloudflare/) confirming Anthropic is **winding down all hosted Stainless products** including the SDK generator.

### Why it's relevant (barely)

Stainless built every official Anthropic SDK (Python, TypeScript, Go, Java, Kotlin) and most of the official MCP server tooling. The acquisition consolidates that infra in-house. Two paths it could affect this repo:

1. **Direct SDK use.** Today the harness has **zero direct Anthropic SDK calls** (`.harness-profile` says `llm_apis: []`, confirmed by `grep -rn "anthropic\b" scripts/`). All Claude calls go through Claude Code itself, not a programmatic SDK. So the SDK-source migration is a no-op for the harness today.

2. **Future consumer-project SDK code.** If a consumer project uses the Anthropic Python SDK (or any other), the SDK source-of-truth shifts from `stainless.com` to Anthropic infra. No code-level break expected — generated SDKs still belong to the customer per Anthropic's statement — but the maintainer's mental model should know that "Stainless" stops being a separate vendor and becomes part of Anthropic.

### Why this is defer, not apply or skip

- **Apply** doesn't fit: there's no concrete change to ship today. The harness doesn't import a Stainless-generated SDK.
- **Skip in the tracker** would mean no durable record, and the maintainer (or future-you, six months from now) might re-derive this on the next routine run.
- **Defer** is right: the file records that the change happened, what to watch for, and what to do *if* a future surface ever hits the SDK path.

### Concrete change

**None this run.** The skip-with-reason discipline lives in the tracker (`reviewed-posts.md` row for this post will link here).

If/when the harness grows an Anthropic-SDK code path (e.g. a programmatic eval runner outside Claude Code), the things to re-check:

1. SDK install URLs and `pyproject.toml`/`package.json` entries — should still resolve, but the upstream repo location may have moved.
2. MCP server lists in `~/.claude/mcp_servers.json` (if any are Stainless-hosted, they're sunsetting — `mcp.stainless.com`-prefixed URLs).
3. The `claude-api` skill bundled with Claude Code — if its examples reference Stainless-hosted URLs, those need an update by the Anthropic side, not the harness.

### Expected payoff (when applied)

Pre-emptive: if a future skill ships that uses the Anthropic SDK programmatically, the maintainer doesn't have to re-discover the migration path.

**Verify before applying:**
1. `grep -rn "stainless\|@stainless\|@anthropic-ai/sdk\b" /home/user/claude-harness` — must return zero hits today; if it returns anything, the harness has grown SDK code paths since 2026-05-21 and this § needs updating.
2. Confirm `.harness-profile` still has `llm_apis: []`. If that key has been populated, the harness now talks to an LLM API directly and this § graduates from `defer` to `apply` with concrete steps.
3. Confirm Anthropic's wind-down of hosted Stainless products is complete (or in progress) before relying on `mcp.stainless.com`-style URLs anywhere.

**Recommended verdict:** defer until the harness or a consumer project grows a direct Anthropic-SDK code path — bookkeeping note only; no concrete change today.
