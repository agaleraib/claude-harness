## 1. Upgrade `.harness-profile.model.primary` from `claude-opus-4-7` → `claude-opus-5-5`

**Source:** [Introducing Claude Opus 5.5 — anthropic.com, 2026-09-22](https://www.anthropic.com/claude-opus-5-5). Model ID `claude-opus-5-5`. Pricing: $4/MTok input, $20/MTok output, cache reads $0.20. Reported scores: Terminal-Bench 4.0 66.4%, FrontierCode v1.1 (Main) 54.4%, CursorBench 4.0 57.8%.

### Why it's relevant
`.harness-profile:30` pins `model.primary: claude-opus-4-7` and `skills/project-init/SKILL.md:153,207` propagates that same pin into every project created with `/project-init`. Opus 5.5 is the recommended successor on anthropic.com's model page, is 5+ weeks old at this review (shipped Sep 22), and the harness's existing effort-derivation table (`skills/project-init/SKILL.md:163–166`) still cites the April-23 postmortem's `xhigh` floor — which was established *for Opus 4.7*. The question "should the harness bump its default primary model?" is now overdue.

### Why this is `spec`, not `apply`
Two behavior changes in Opus 5.5 are not drop-in from 4.7:

1. **Thinking cannot be disabled.** The model page says Opus 5.5 "is also no longer available with 'thinking' mode switched off." The harness has no code path today that explicitly disables thinking, but the `effort_default: xhigh` setting at `.harness-profile:32` interacts with per-session effort overrides (`${CLAUDE_EFFORT}` from v2.1.120 — flagged in the 2026-04-30 tracker row). Need to verify no consumer-project profile sets `effort: off` or similar.
2. **Automatic cyber-task rerouting to Opus 4.8.** Opus 5.5 transparently falls back to Opus 4.8 for most cybersecurity tasks. The harness's `/security-review` bundled skill and `procedures/api-security-checklist.md` would run on the fallback model, not the primary — a silent model switch that today's logging doesn't capture.

Plus a pricing + context budget check: Opus 5.5 at $4/$20 vs. Opus 4.7 (currently $15/$75 per Claude Platform docs when 4.7 shipped) represents a material cost drop, which flips the cost-vs-effort math `effort_default` was tuned on. The `effort_default: xhigh` floor derived from the April 23 postmortem was anchored to 4.7 defaults — a 5.5 upgrade is the right moment to re-derive.

## 4. File "fold one subagent at a time" as a check that re-opens when agent-evals land

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com/resources, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop). Argues a single agent with skills + tools sometimes beats a subagent design on quality, cost, and latency. Heuristics: start simple; split by context, not problem type; build evals first; merge tightly-coupled specialists first; call subagents as tools before rewriting them; fold one at a time, compare evals with and without.

### Why it's relevant
The harness ships 6 custom subagents today (`.claude/agents/{code-reviewer,generator,orchestrator,project-tracker,spec-planner,ui-evaluator}.md`). That's well below the article's 30–50 tool-definition fold-threshold, so the near-term action is small. But the article's core discipline — **"fold one at a time, compare evals with and without"** — can't be acted on without the agent-evals fixtures the harness has already deferred (2026-04-19 §5, re-affirmed 2026-04-28 §3 and 2026-05-07 §1).

### Why this is `defer`, not `apply`
The specific candidates for consolidation review (ui-evaluator ↔ generator in the generator-evaluator loop; project-tracker ↔ session-end ritual) all look like genuinely context-distinct work today. The article's test is empirical ("compare evals with and without"), not architectural intuition — and running that test needs the fixture set that doesn't exist yet. Writing a speculative "we should fold agent X into Y" without evals would violate the article's own "build evals first" heuristic.

### Concrete change (deferred — fires when 2026-04-19 §5 lands)
Add a line to the agent-evals spec's acceptance criteria, when written:

```
When the eval fixtures are in place, run the "fold one subagent at a time" protocol
from https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop
against each of the 6 custom agents. For each: compare eval scores with the agent
isolated vs. folded into the orchestrator's main loop. Candidates to test first
(tightly-coupled per the article's heuristic): project-tracker (shares memory
seams with session-end) and ui-evaluator (one half of the generator↔evaluator loop).
```

Nothing to edit in the repo today beyond pinning this reference in the deferred-§5 parking spot in `anthropic-reviews/reviewed-posts.md` and the dated suggestions file.

### Expected payoff
When the deferred evals land, the "should we consolidate agents?" question has a concrete, Anthropic-authored protocol to follow instead of being re-litigated from scratch.
