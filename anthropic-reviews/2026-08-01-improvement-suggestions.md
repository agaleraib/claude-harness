## 2. Add a one-paragraph "Workflow tool ≠ /run-wave orchestrator" note

**Source:** [Introducing dynamic workflows — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) + [orchestration docs — code.claude.com/docs/en/workflows](https://code.claude.com/docs/en/workflows) + [Ultracode explainer](https://claudefa.st/blog/guide/development/ultracode). Anthropic shipped a first-party primitive called **Workflow** — a JS script (`agent()`, `parallel()`, `pipeline()`, `phase()`, `budget`, `args`) that Claude Code writes, then executes to fan out tens-to-hundreds of subagents per session. Opt-in modes: (a) the user says "use a workflow" verbatim, (b) the user turns on the `ultracode` session setting, (c) an installed skill's instructions call it. Available on Pro / Max / Team / Enterprise; concurrency cap 16 parallel agents, 1000 total per run.

### Why it's relevant
The harness already has a very similar-*sounding* mechanism: `/run-wave N` dispatches spec tasks through the `orchestrator` agent (`.claude/agents/orchestrator.md`), which brief-fans-out subagents to `haiku` / `sonnet` / `opus` with a routing table. It looks like it's the local, DIY version of the Workflow tool — and a reader who hasn't paged in the difference will ask "why don't we just replace `/run-wave` with `Workflow`?"

They solve **different** problems at **different** layers:

| Dimension | Claude Code Workflow (2026-05-28) | Harness `/run-wave` + orchestrator |
|---|---|---|
| Substrate | Anthropic-managed JS runtime inside a single Claude Code session | Local Bash + skills + git worktrees |
| Trigger | User says "workflow" / `ultracode` on / skill invokes | User runs `/run-wave N` after `/spec-planner` produces a spec |
| Concurrency cap | 16 parallel, 1000 total | Bounded by local CPU + worktree count |
| State | In-process JS variables; no on-disk artifacts by default | `docs/specs/*.md`, `docs/plan.md`, `.harness-state/*.jsonl`, worktree branches |
| Failure mode | Agent returns `null`; script catches and retries in-script | Verify step fails → escalate one rung per failure per orchestrator §Retry-escalation rung |
| Cross-session persistence | None (session-scoped) | Wave receipts (`docs/waves/*.md`), `parking_lot.md`, `last_exit.md` |
| Cost model | Billed at Pro/Max/Team plan overhead; "meaningfully more usage than a typical Claude Code session" per the launch post | Same session cost + subagent tokens; local artifacts free |

They're **complementary at best, orthogonal at worst.** A `Workflow` can be dispatched *inside* a `/run-wave` task the orchestrator hands off, but the harness's wave + spec + parking-lot + `/commit` discipline lives at the durable layer that the Workflow tool doesn't touch.

The harness's system prompt (visible in this very session) already contains the full Workflow primitive spec, and CLAUDE.md-level guardrails ("ONLY call this tool when the user has explicitly opted into multi-agent orchestration") govern its use. But the *harness README* is silent on when the harness's own orchestrator is the right choice vs. when `Workflow` is. That gap is worth closing before someone rewrites `/run-wave` around Workflow.

This harness's `/run-wave` + `orchestrator` agent solve a *different* problem at a *different* layer: they dispatch **spec-defined tasks** to model-routed subagents, produce **durable artifacts** (`docs/waves/`, `.harness-state/`, wave receipts, `parking_lot.md`), and hand off through `/commit`. `Workflow` is a per-session orchestration primitive; the harness's orchestrator is a per-wave methodology anchor. ## 3. Consider a new `procedures/large-scale-migration-playbook.md` codifying Anthropic's 6-step methodology

**Source:** [How Anthropic runs large-scale code migrations with Claude Code — claude.com/blog, 2026-07-16](https://claude.com/blog/ai-code-migration). Anthropic engineers migrated 10 packages of tens-to-hundreds of thousands of lines each in the month prior using Claude Fable 5 + Opus 4.8 + Dynamic Workflows. Case studies: Bun's Zig→Rust port (~1M LOC in <2 weeks, 100% existing tests pass in CI), Anthropic Labs' internal Python→TypeScript port (~165K LOC in a weekend, hundreds of agents, 8 phase gates, 3 adversarial reviews, final output-parity check).

### The 6-step methodology
1. **Build a rulebook + dependency map.** Front-load human effort. Rulebook governs style, invariants, patterns; dependency map orders the work.
2. **Create a gap inventory.** Enumerate every source file, its target file, and its migration blockers.
3. **Run a stress-test mini-migration.** Pick 1–3 representative modules; migrate them by hand-in-loop; refine the rulebook until they pass parity.
4. **Parallel translation with smaller models.** Fan out with Sonnet/Haiku via a Workflow or hand-orchestrated dispatch; large models are reserved for review + rule-writing.
5. **Compiler / smoke-test fix loops.** Iterate on build errors, test failures until CI is green.
6. **Final parity verification.** Diff every command's output against the original; adversarial-reviewer rounds; merge behind a phase gate.

### Why this is `defer`, not `apply`

1. **The harness is solo, no migration in flight.** Codifying a playbook for a workload nobody is running is speculative documentation — the routine's own rubric says "flag it with 'scope: speculative' and let the maintainer decide."
2. **Overlaps with the existing spec-planner + orchestrator + wave discipline.** `/spec-planner` already produces the "rulebook + dependency map" artifact (a spec); `/run-wave` fans out translation tasks with model routing; `code-reviewer` handles adversarial-review rounds; `/commit` + verify steps handle the smoke-test loops. A migration playbook would be a *consumer* of these primitives, not a replacement for them.
3. **The 6-step shape is domain-specific enough that a generic playbook risks over-fitting.** Bun's Zig→Rust needs different rulebook categories than Python→TypeScript. A playbook that tries to cover both becomes an outline.
4. **Anthropic linked an open-source starter kit in the same post.** If a consumer project needs this, they can fork the starter kit and adapt it — the harness doesn't need to re-implement.

### Concrete change (deferred)

None this run. When a consumer project (or future-me) is starting a real migration:

- Copy the 6-step outline from the source post into `procedures/large-scale-migration-playbook.md`.
- Map each step to the harness's existing primitives: rulebook → `/spec-planner` spec; parallel translation → `/run-wave` with `model_routing: on` and `orchestrator` dispatch; adversarial review → `code-reviewer` agent; final parity → `criteria/*.md` rubric + verify steps.
- Add a `procedures/api-security-checklist.md`-style checklist for the operator running the migration.
- Cite the Anthropic post; note the Fable 5 / Opus 4.8 / Dynamic Workflows tooling context.

### Expected payoff (when applied)
A consumer project starting a Zig→Rust or Python→TS migration has a repo-native reference for how to sequence the work, when to escalate to larger models, and how to structure the phase gates — without having to synthesize the playbook from a blog post and the harness's separate primitives.

1. `ls /home/user/claude-harness/procedures/` — currently returns `api-security-checklist.md`, `triage-quality-issues.md`. If a `large-scale-migration-playbook.md` already exists, this § is done.

### Why this is `reject`, not `apply` for `.harness-profile`

1. **Fallback semantics are ambiguous for a general-purpose harness.** The safety-classifier auto-fallback to Opus 4.8 means a task pinned to Fable 5 may run on Opus 4.8 without the operator knowing — different pricing, different context window, different behavior. For a *harness* that consumer projects install from, opaque model-switching under-the-hood is a bug not a feature.
2. **Pricing not disclosed at launch.** The public post doesn't disclose the Fable 5 per-token price. Cannot compare TCO against Opus 4.8's known $5/$25 without that number.
3. **Adaptive-thinking always-on changes the effort-tier semantics.** The harness's `.harness-profile` `effort_default: xhigh` derivation assumes the operator controls the effort tier per-task via routing rules. Fable 5's "always-on adaptive thinking" pre-empts that control at the model layer, making `effort_default` a partially-redundant knob.
4. **Cybersecurity / biology domain classifiers may bite `/security-review` and `procedures/api-security-checklist.md` workflows.** The harness has an api-security-checklist procedure; running it on Fable 5 would silently downgrade to Opus 4.8 on flagged sub-tasks. Ambiguity that's not worth introducing.
5. **Tier-above-Opus is speculative for solo tooling.** Per the routine's rubric — same reasoning as Managed Agents deferrals in 2026-04-19 §2 and 2026-04-25 memory row.
6. **Opus 4.8 is the safe target** (see §1 above) with same pricing, no auto-fallback, deterministic effort tiers.
