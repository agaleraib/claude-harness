## 4. Bookkeep the parallel between `/goal` and the harness's `/planning-loop` + `/run-loop`

**Source:** [Keep Claude working toward a goal — Claude Code Docs](https://code.claude.com/docs/en/goal), landed in v2.1.139 on 2026-05-12 (Week 20 `/whats-new`). `/goal <condition>` keeps Claude looping across turns until a small fast model (Haiku by default) judges the completion condition met. Works in interactive, `-p`, and Remote Control modes; tracks elapsed time, turns, and tokens.

### Why it's relevant

The harness already ships **two completion-condition loops** that pre-date `/goal`:

- **`/planning-loop`** (`skills/planning-loop/`) — caps at 3 rounds; on `needs-attention` at cap dispatches arbiters (`code-reviewer`, `Plan`) and either auto-applies unanimous mechanical fixes or prints a 4-option menu (README:273).
- **`/run-loop`** (`skills/run-loop/SKILL.md`) — the shared TypeScript loop engine in `skills/_shared/loop/`, executes waves or issues on an interval; catastrophic-command denylist is a `PreToolUse` hook the operator installs in `~/.claude/settings.json` (CLAUDE.md `## Loop protocol — Claude Code invocation notes`).

`/goal` is a **lighter, in-turn primitive** for the same class of problem: bounded work with a verifiable end state. It doesn't replace `/planning-loop` (spec-anchored, arbiter-driven, records receipts under `.harness-state/planning-loop/`) or `/run-loop` (interval-based, worktree/sandcastle runners, HITL classifier). But it's the natural first tool a user would reach for on a "migrate all call sites until tests pass" task — a case the harness currently doesn't have a first-class primitive for.

### Why this is `defer`, not `apply`

1. **The harness's loops are working today.** No first-party pain report says "I wish I had `/goal`." Solo tooling.
2. **`/goal` is a Claude Code product; the harness's loops are the harness.** Adding `/goal` guidance to `AGENTS.md` or `README.md` risks reading like "here's another way to do what we already do" without a clear composition rule. Better to wait for a concrete task where `/goal` beats `/planning-loop` (e.g. mechanical migrations across N files with a compile-passes verifier) and then codify the composition rule in the READ of that experience.
3. **`/goal` uses a fast-model judge (Haiku).** That's a taste question — for the harness's arbiter pattern (`code-reviewer` + `Plan`), a Haiku judge is under-powered. Documenting the choice needs first-hand experience, not speculation.

## 5. Bookkeep Dynamic Workflows alongside the harness's `orchestrator` + `run-wave` fan-out

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (announced with Opus 4.8 on May 28 as a research preview). The Workflow tool lets Claude author and run a JavaScript orchestration script inline (`agent()`, `parallel()`, `pipeline()`), pick sub-agent models/effort, and optionally isolate work in worktrees. Framed as "Claude writes its own harness per task."

### Why it's relevant

The harness has its own fan-out primitive: **`orchestrator`** (`.claude/agents/orchestrator.md`, runtime-model-routing) dispatched by **`/run-wave`** (`skills/run-wave/SKILL.md`) which reads a spec from `docs/plan.md`, creates a worktree at `.claude/worktrees/agent-<id>/`, and runs the wave's tasks in that isolation.

There's a real conceptual overlap:

| Concern | Harness (`orchestrator` + `run-wave`) | Anthropic Dynamic Workflows |
|---|---|---|
| Script | Spec-driven — cherry-picks tasks from `docs/plan.md`, verbatim exit gates from the wave header | Dynamic — Claude writes the script per task |
| Isolation | Git worktrees under `.claude/worktrees/agent-<id>/` | Same primitive (opts.isolation: 'worktree' per script) |
| Model routing | `orchestrator` picks per task (opus/sonnet/haiku) | Script picks per `agent()` call (opts.model) |
| Fan-out | Sequential wave execution + `code-reviewer` gate on each task | `parallel()` / `pipeline()` with concurrency cap 16 |
| Persistence | Receipts under `.harness-state/run-wave-<wave_id>-<ts>.yml` | None (per-run) |

The harness's approach is **deliberately spec-driven** — waves are pre-planned in `docs/plan.md` by `/spec-planner`, and the deterministic dispatch is what lets the receipts + rollback story hold. Anthropic's Workflow is the *other* posture: Claude decides the shape at runtime. Different regimes; the harness's structured approach is a design choice, not a gap.

### Why this is `defer / scope: speculative`

1. **The receipts protocol depends on determinism.** `docs/specs/2026-04-30-universal-harness-protocol-v2.md` §3.0 requires content-derived `idempotency_key`s per receipt so re-invocation is a byte-identical no-op. A Claude-authored per-task workflow would defeat that; adopting Dynamic Workflows without rethinking the receipts contract would corrupt the audit trail the harness is built around.
2. **The one place Dynamic Workflows would fit is the `/run-wave` fan-out.** Today `orchestrator` walks tasks sequentially. A Workflow could parallelize independent tasks (e.g. F-037 + F-038 in Wave 25 could have run concurrently). But that's a spec-worthy change — needs a design pass on when parallelism is safe under the receipts contract.
3. **Solo tooling.** No one has asked for it.

### Bookkeeping only

Track this § as `defer until user pain / scope: speculative` — if the maintainer hits a wave with 5+ independent tasks that would benefit from parallel fan-out, reopen and consider a spec for either (a) an intra-wave parallel dispatcher inside `orchestrator`, or (b) a Workflow-backed alternative to `/run-wave` that preserves the receipt contract.

**Verify before applying:**
1. `grep -rn "Workflow\b\|workflow(" /home/user/claude-harness --include=*.md | grep -v "^Binary"` — verify no Workflow-tool integration exists yet.
2. `git log --format=%s --since=2026-05-28 -- skills/run-wave/ skills/_shared/loop/ .claude/agents/orchestrator.md` — if the orchestrator or run-wave changed for parallelism reasons since Dynamic Workflows shipped, this § is stale (may already have been considered).
3. Confirm Dynamic Workflows is still a research preview (or has graduated) — receipts-vs-dynamism trade-off is different if it's GA and the maintainer might rely on it in target projects.

**Recommended verdict:** defer until user pain / scope: speculative — the harness's spec-driven waves + receipts contract are the intended shape. Only revisit if serial wave execution becomes a bottleneck.

## 6. Bookkeep cross-session `SendMessage` / `ListAgents` alongside the harness's `.harness-state/` inter-session pattern

**Source:** [Claude Code Sessions Can Now Message Each Other — v2.1.224, 2026-08-07](https://code.claude.com/docs/en/whats-new) (Week 32 digest). Two new tools on macOS + Linux (incl. WSL 2; **not Windows**): `ListAgents` finds other active Claude Code sessions on the machine; `SendMessage` delivers a plain-text message that the receiving session reads between tool calls. Messages stay local (never reach Anthropic servers). The same `SendMessage` also handles messages to in-session subagents and agent-team teammates.

### Why it's relevant

The harness's inter-session communication is **file-based, durable, and audit-traced**:

- Wave dispatch writes `.harness-state/run-wave-<wave_id>-<ts>.yml`; close writes `.harness-state/close-wave-<wave_id>-<ts>.yml` (WORKFLOW.md).
- Per-cwd memory lives at `~/.claude/projects/<encoded-cwd>/memory/MEMORY.md` (CLAUDE.md `## Claude-specific notes`); manual promotion to `~/.claude/memory/feedback/` preserves per-cwd provenance.
- Session-end / session-start rituals read prior session state via `last_exit.md` / `today_goal.md` / `current_micro.md` under `.harness-state/` (skills/session-end, skills/session-start).

`SendMessage`/`ListAgents` is a **different regime**: live, in-turn, ephemeral, per-machine. There's a natural composition question — could a two-session workflow (e.g. a long-running `/run-wave` session in one terminal and a `/planning-loop` review session in another) coordinate via `SendMessage` instead of the maintainer manually switching terminals and re-pasting context?

### Why this is `defer / scope: speculative`

1. **The harness is single-session-first.** Every skill assumes one Claude Code session at a time. Adding a live inter-session channel would introduce a new coordination model the rest of the harness hasn't been designed for.
2. **The macOS/Linux-only restriction excludes Windows target projects.** The harness ships to whatever Claude Code runs on, including Windows via Git-Bash (or PowerShell as of Week 18 in April 2026). A pattern that only works on 2/3 of the OS matrix is a hard sell.
3. **Durable state is a feature, not overhead.** `.harness-state/` receipts are how rollback + resume work. `SendMessage` is fire-and-forget. If a coordination pattern earned its keep, it would likely be a hybrid (`SendMessage` for the live wake-up, files for the payload) — worth a spec, but not yet.
4. **Solo tooling.** No one has asked for it.
