## 1. Add a `/skill-doctor` cadence procedure to keep skills-budget in check

**Source:** [Claude Code weekly digest, Week 36 — August 31 – September 4, 2026](https://code.claude.com/docs/en/whats-new/2026-w36) (v2.1.251–v2.1.261). Verbatim from the digest: *"`/skill-doctor` shows what each of your skills costs in context and how often it gets used."* The same command is also referenced by the built-in `fewer-permission-prompts` skill.

### Why it's relevant
The harness already ships **26 skills** (`ls skills/` — this run counted `a11y-check`, `api-smoke-test`, `apply-anthropic-reviews`, `archive-plan`, `close-wave`, `commit`, `cowork-area-sync`, `deploy-check`, `harness-status`, `memory-prune`, `micro`, `migration-check`, `new-cowork`, `park`, `planning-loop`, `project-init`, `run-loop`, `run-wave`, `session-end`, `session-start`, `setup-harness`, `shared-root-init`, `skill-creator`, `triage-parking` plus the two `_shared` and other helpers), and the last recorded skills-budget audit was 2026-05-07 (~6.1K/15.5K). Skills grow over time; when the budget starts pressing, the first question is always "which skills are worth their tokens?" — which is exactly the report `/skill-doctor` gives. Without a documented cadence, nobody runs it. A one-line procedure fixes that.

### Concrete change
Add a small new procedure file `procedures/skill-doctor-cadence.md`:

```markdown
# `/skill-doctor` cadence

Run `/skill-doctor` from a Claude Code session in this repo at these two triggers:

1. **After adding or materially expanding a skill.** The report tells you whether the new instructions actually get loaded and how much context they cost. If a skill's usage frequency is zero after a month, delete or fold it into an adjacent skill.
2. **Whenever the harness's skills-context total crosses 75% of budget.** Rough guide: 26 skills at ≤600 lines each is the current comfort ceiling; past that, the report is required reading before adding another.

Capture the run's summary (top-3 costliest, bottom-3 unused) in a `harness-status` note so audits over time can be compared. The last recorded audit was 2026-05-07 at ~6.1K/15.5K.
```

Optionally cross-link from `skills/harness-status/SKILL.md` (add one bullet: "If skills-budget question arises, invoke `/skill-doctor` per `procedures/skill-doctor-cadence.md`").

### Expected payoff
Turns an implicit "should I audit?" instinct into a scheduled ritual. The alternative today is that skills silently accumulate until a symptom (a hard `/skills` selection failure, or a token-budget compaction) forces a reactive audit.

**Verify before applying:** `ls procedures/skill-doctor-cadence.md 2>/dev/null` and `grep -rn "/skill-doctor" procedures/ skills/harness-status/ AGENTS.md CLAUDE.md README.md` — both should be empty at generation time. If a `skill-doctor` procedure or reference already exists, drop this suggestion.

**Recommended verdict:** apply — small doc addition, no risk, matches the harness's explicit skills-budget concern.

## 5. Adopt `Tool(param:value)` matcher for the `/run-loop` catastrophic-command denylist

**Source:** [Claude Code weekly digest, Week 25 — June 15–19, 2026](https://code.claude.com/docs/en/whats-new/2026-w25) (v2.1.178–v2.1.183). Verbatim: *"deny and ask rules match tool parameters with `Tool(param:value)`, for example `Agent(model:opus)`."*

### Why it's relevant
The `/run-loop` skill documents (per this repo's `CLAUDE.md § Loop protocol`) a `PreToolUse` catastrophic-command denylist installed in `~/.claude/settings.json`. The matcher logic ships from `skills/_shared/loop/safety/denylist.ts`. Today the wiring is tool-name-matched (deny `Bash` under certain patterns), and the fine-grained pattern discrimination happens inside the TS module.

`Tool(param:value)` would let the settings-side matcher pre-filter: e.g., allow `Bash(git commit:*)` while denying `Bash(git reset:--hard)` at the harness-config layer, before Node even runs. That's fewer moving parts and a smaller TS surface to maintain.

**Why this is defer, not apply:** the current denylist works. There's no logged pain point (no false-positives blocking a legitimate `/run-loop` step, no false-negatives that let a destructive command through). Rewriting a working safety module for elegance is a classic YAGNI trap. Park it against a real trigger.

### Concrete change (if a trigger materializes)
1. Enumerate current denylist patterns in `skills/_shared/loop/safety/denylist.ts`.
2. For each pattern that maps cleanly to a `Bash(<verb> <flag>:...)` shape, express it as a `deny` rule in `~/.claude/settings.json` using the `Tool(param:value)` matcher.
3. Update the operator-facing install step in the `/run-loop` skill's "Human-only TODOs" to install the settings-side rules alongside (not instead of) the TS module — belt-and-suspenders during a transition period.
4. Only after a probation period (say, 60 days without regression) prune the TS module for the patterns now enforced by settings.

### Expected payoff
Smaller custom-code footprint in `denylist.ts`; the safety boundary lives closer to the tool call. Also composes better with Auto Mode's own classifier (documented in 2026-05-08 §1 as APPLIED).

**Verify before applying:**
- `grep -rn 'Tool(.*:.*)\|deny.*param' /home/user/claude-harness/.claude/ skills/_shared/loop/safety/` — confirm the matcher isn't already used.
- Check that the operator's `~/.claude/settings.json` (not a repo file, per the loop protocol) is where the denylist actually lives; if not, this § targets the wrong file.

**Recommended verdict:** defer until a denylist false-positive or false-negative surfaces — the current module is safe today; refactoring earns nothing yet.

**Status:** PENDING — awaiting triage in PR review
