## 2. Position Anthropic's Dynamic workflows alongside the harness `orchestrator` agent in README

**Source:** [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) and the companion engineering essay [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Docs: [code.claude.com/docs/en/workflows](https://code.claude.com/docs/en/workflows). Trigger keyword: `ultracode` (renamed from `workflow` on May 30 per the changelog). Disable via `"disableWorkflows": true` in `~/.claude/settings.json` or `CLAUDE_CODE_DISABLE_WORKFLOWS=1`. Requires Claude Code v2.1.154+.

### Why it's relevant
Anthropic just shipped **a runtime where Claude writes its own JS orchestrator script** that dispatches tens-to-hundreds of subagents in the background, picking model and worktree per step. This overlaps in concept with the harness's existing `orchestrator` agent (`.claude/agents/orchestrator.md`) — both are **multi-subagent orchestrators** that choose model + effort per task — but they sit at different layers:

| | Harness `orchestrator` | Anthropic Dynamic Workflows |
|---|---|---|
| **Specified by** | Operator (spec tasks with `Files:` / `Verify:` / optional `Effort:` hints) | Claude (writes a JS script at runtime) |
| **Trigger** | `Use the orchestrator…` prompt or `/run-wave N` skill | `ultracode` keyword (or natural-language ask) |
| **Concurrency model** | File-overlap-safe parallelism gated by `model_routing: on` toggle | "Tens to hundreds" of parallel subagents in the background |
| **Routing inputs** | `.harness-profile` (`stakes.level`, `effort_default`), task complexity rubric | Claude's plan + per-step model choice; isolation via worktree |
| **Audit trail** | `.harness-state/orchestrator.{log,jsonl}`, two-surface logging contract | `/workflows` UI listing of runs |
| **Cost** | One Claude Code session, subagent costs accrue against it | Same; dynamic workflows just spawn more subagents in the same session |
| **Scope** | Bounded to spec tasks; explicit dependency resolution | Open-ended; Claude decides shape |

The two patterns are **complementary, not redundant** — same shape as the 2026-05-10 §1 framing of `code-reviewer` (local, pre-push) vs `/ultrareview` (cloud, post-push). The harness's `orchestrator` is the operator-driven, spec-anchored, low-ceiling cousin; dynamic workflows is the model-driven, runtime-authored, high-ceiling cousin. A solo maintainer benefits from one paragraph in the README that names the relationship so the next reader (or future-you) doesn't ask "do I still need the `orchestrator` agent now that `ultracode` exists?"

### Concrete change

**One paragraph appended to the `orchestrator` section in `README.md`** (the section that contains the routing-table reference around L572–L574). Insert near the end of that section, before the next `---` separator:

```diff
 Each route also picks an `effort` (`low` / `medium` / `high` / `xhigh`) — read-only tasks use `low`, code-reviewer and multi-file work use `xhigh`, and the default tracks `stakes.level` via the `effort_default` pin. See [`.claude/agents/orchestrator.md`](.claude/agents/orchestrator.md) for the full routing table.

+#### How this complements Anthropic's dynamic workflows
+The harness's `orchestrator` is **operator-specified, spec-anchored, with explicit file-overlap parallelism gated by `model_routing: on`**, and logs to `.harness-state/orchestrator.{log,jsonl}`. As of May 2026, Anthropic also ships **[Dynamic workflows](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)** (trigger: `ultracode`) — a Claude-authored JS script that fans out tens-to-hundreds of background subagents and picks model + worktree per step. The two are complementary, not redundant: use the harness `orchestrator` for spec-driven waves with deterministic routing and an audit-trail (`/run-wave N`); reach for `ultracode` when the shape of the work isn't pre-decomposed and you want Claude to choose the harness. Both are accountable to the same `.harness-profile` and consume from the same Claude Code session budget; they just split the work at different layers (operator vs. model).
```

Optional second touch (cheap): add to the **References** section the same way 2026-05-10 §1 did for Code Review:

```diff
 - [Code Review for Claude Code](https://claude.com/blog/code-review) — Anthropic's cloud-hosted multi-agent PR reviewer (May 2026); complement to the local `code-reviewer` agent
+- [A harness for every task: dynamic workflows in Claude Code](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) — Anthropic's runtime-authored JS orchestrator (May 2026); complement to the spec-driven `orchestrator` agent
```

### Expected payoff
Same as the `/ultrareview` framing the maintainer applied on 2026-05-10: a future reader who hits `ultracode` first doesn't conclude the harness's `orchestrator` is obsolete; the relationship is documented at the agent's own section. Zero behavior change.

### Why this isn't already covered by 2026-05-10 §1
2026-05-10 §1 framed `/ultrareview` vs the harness's `code-reviewer`. Dynamic workflows is a different feature at a different layer — it's not a reviewer, it's a multi-agent task harness. Same documentation pattern, different surface.

**Verify before applying:**
1. `grep -rn "dynamic workflows\|ultracode\|disableWorkflows\|/workflows" /home/user/claude-harness` — must still return nothing today (confirmed at routine generation time); if it returns hits, the integration paragraph has already been written.

**Recommended verdict:** apply — pure documentation edit (one paragraph + one reference bullet), same shape as the 2026-05-10 §1 edit the maintainer accepted, addresses a "is X now redundant?" question that the harness's `orchestrator` will otherwise invite.

## 4. Adopt HTML over Markdown for evaluator / code-reviewer / spec-planner reports

**Source:** [Using Claude Code: The unreasonable effectiveness of HTML — claude.com/blog, 2026-05-20](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html), by Thariq Shihipar (Anthropic Claude Code team). Thesis: for >100-line plans / code reviews / design docs / reports, HTML is denser, more visually navigable, and more shareable than Markdown; "Anthropic itself is adopting HTML as the internal default for plans, code reviews, design systems, and reports."

### Why it's relevant
The harness ships several **report-shaped artifacts** as Markdown today:
- `skills/skill-creator/assets/eval_review.html` already uses HTML for the eval-viewer — proving HTML is in scope when the artifact is review-facing.
- But `evaluator-report.md` / `evaluation-report.md` (referenced in criteria + spec docs + a 2026-05-08 §2 suggestion deferred), spec-planner output, and code-reviewer output are all Markdown.
- `skills/skill-creator/scripts/generate_report.py` and `skills/skill-creator/scripts/run_loop.py` reference HTML — partial adoption already.

If reports routinely exceed 100 lines (Thariq's stated readability cliff), an HTML default would give:
- denser visual structure (tables nested in detail panes, collapsible sections);
- embeddable diagrams (SVG) and lightweight interactivity (sortable issue tables);
- shareable artifacts that render in any browser (vs requiring a Markdown renderer).

### Concrete change (sketched, not specified)
This is **convention-level**, not a one-file edit. It would touch:
- `.claude/agents/code-reviewer.md` — emit HTML report option;
- `.claude/agents/spec-planner.md` — spec output schema;
- `skills/skill-creator/` — already partial HTML; consolidate;
- evaluator artifacts referenced in `criteria/`, `skills/run-wave/`, `skills/close-wave/`;
- downstream consumer projects' habits (anything reading `evaluator-report.md` by name).

A `/spec-planner` pass would be appropriate before shipping any of this. **Tag: scope: speculative.**

### Expected payoff
**If** the harness's Markdown reports are routinely hitting the readability cliff Thariq describes, HTML would meaningfully improve the artifact. **If not** (reports are short enough that Markdown remains the right surface), the migration cost dominates.

### Why defer, not apply
No evidence today that any specific harness report has crossed the readability threshold. The Markdown convention is load-bearing across `criteria/`, the eval pipeline, and consumer-project habits. Switching is substantive and merits a `/spec-planner` pass with a "should we?" gate before any code.

**Verify before applying:**
1. `find /home/user/claude-harness -name "*report*.md" -o -name "evaluator-report*" 2>/dev/null | head -20` — confirm the current Markdown-report surface area before deciding.
2. `wc -l /home/user/claude-harness/skills/*/SKILL.md | sort -n | tail -5` — gauge whether the largest SKILL bodies (which often double as report templates) have crossed 100 lines.
3. Sample 2–3 recent evaluator/code-reviewer outputs from `.harness-state/` and judge whether HTML would change the read experience. If yes, escalate to `/spec-planner`; if no, keep deferred.

**Recommended verdict:** defer until report-readability evidence accumulates — convention-level migration; substantive. Tagged `scope: speculative`.

Pricing: **$10 input / $50 output per MTok** — 2× the Opus 4.8 rate. Fable 5 availability on Pro/Max/Team/seat-based Enterprise is **time-boxed through June 23**.

### Why it's relevant
The harness pins `model.primary: claude-opus-4-7` (which §1 above proposes to bump to `claude-opus-4-8`). Fable 5 is the **next tier above Opus 4.8** in raw capability, but at a price multiplier and with a temporary access window that makes it inappropriate as a default pin for a solo coding harness today.

### Why not act now

- **Time-boxed access.** "Through June 23" means a `setup-harness` install pinning Fable 5 today breaks for any user setting up the harness on June 24+.
- **No safety-classifier visibility.** The post says ≥95% of Fable 5 sessions complete without fallback to Opus 4.8, but for coding tasks the harness has no instrumentation today to detect or recover from a Fable→Opus fallback mid-session.
- **No new harness surface added.** The release doesn't change skills, hooks, criteria, or agent shapes — only the model ID set.

### Concrete change today
**None** — this is a tracker-resident note. When a future model-pin review fires (e.g. the 3–6 month cadence the "Large codebases" post recommends, or a price normalization for Fable-tier models), this entry surfaces as context.

### Expected payoff
The durable record names Fable 5 / Mythos 5 as observed-but-deferred, so the next model-pin review doesn't re-derive the cost/availability tradeoff from scratch.

**Verify before applying:**
1. Before pinning Fable 5 in any future PR, check current pricing on the [Claude API pricing page](https://platform.claude.com/docs/en/about-claude/pricing) — if input/output token cost has dropped within 1.5× of Opus 4.8, the cost objection above weakens.
2. Confirm Fable 5 is generally available (no time-box) — search `site:anthropic.com Fable 5 general availability` or `claude.com/blog`.
3. Confirm the harness has a fallback-detection signal (e.g., session-end memory diff that flags model-id changes within a single run) before recommending Fable 5 as a default — without it, the safety-classifier fallback is invisible to the operator.

**Recommended verdict:** defer until pricing parity (within 1.5× Opus tier) and unrestricted availability — bookkeeping; no edit today.
