## 1. Position dynamic workflows / `/ultracode` alongside the harness's existing multi-agent skills

**Source:**
- [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (Thariq Shihipar / Anthropic engineering deep dive)
- [Introducing dynamic workflows in Claude Code — claude.com/blog, ~2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (research-preview launch companion)
- [Orchestrate subagents at scale with dynamic workflows — code.claude.com/docs, current](https://code.claude.com/docs/en/workflows) (the docs surface)

### Why it's relevant
This Claude Code session **already has the `Workflow` tool** exposed in its tool manifest (see the tool schema at the top of the session — it accepts a `script` parameter with `meta`, `agent()`, `parallel()`, `pipeline()`, `phase()` primitives, plus a `budget` object for token targets). The engineering post frames dynamic workflows as **"Claude writes its own harness on the fly, custom-built for the task"** — a claim that directly overlaps with the harness's stated purpose:

- `skills/planning-loop/` runs a Codex adversarial-review loop for spec quality (three-round pattern documented in `skills/planning-loop/SKILL.md`; §6.5 arbiter routing surfaces a third opinion on unresolved findings)
- `skills/run-wave/` dispatches wave tasks to the `orchestrator` agent, which runtime-routes to `opus/sonnet/haiku` based on task complexity (`.claude/agents/orchestrator.md`)
- `skills/run-loop/` runs continuous waves/issues loops with a shared TypeScript engine (`skills/_shared/loop/`), a `PreToolUse` safety denylist, and a worktree runner
- The environment's `Workflow` tool documentation names patterns that **overlap directly** with the harness's existing ones: *adversarial verify* (planning-loop step 6.5), *fan-out-and-synthesize* (run-wave orchestrator dispatch), *loop-until-dry* (run-loop), *judge panel* (planning-loop three-round quorum)

An operator sitting in this Claude Code session today has **two different mechanisms** for the same shape of work — one loaded via slash-command skills, one loaded via the `Workflow` tool — and the harness README currently gives **zero guidance on which to reach for**:

```
$ grep -rn "Workflow tool\|/ultracode\|dynamic workflows\|Workflow(" /home/user/claude-harness --include='*.md' | wc -l
0
```

### The design question
This is a **spec-planner-worthy** decision, not a paragraph:

- **Option A** — Position the two mechanisms as complementary layers. Skills = named, versioned, methodology-encoded patterns (source-controlled in `skills/`, shipped via `setup-harness` symlinks). Dynamic workflows = one-shot orchestration Claude authors at request time when no skill fits. Document the **when-to-reach-for-which** in `AGENTS.md` §"Loop protocol" (next to the existing `/run-loop` guidance) and cross-link from `README.md`. Zero mechanical work; pure positioning.
- **Option B** — Refactor `skills/planning-loop/` and/or `skills/run-loop/` to *emit* dynamic-workflow scripts as their execution mechanism. The engineering post explicitly calls out that a `Workflow` script can replace hand-authored subagent-spawn loops; the harness's `skills/_shared/loop/` engine is a hand-authored version of the same shape. Non-trivial migration; would consolidate infrastructure.
- **Option C** — Add a thin `skills/ultracode/` skill that wraps `/ultracode` invocation with harness conventions (e.g., emits a receipt to `.harness-state/` on completion so the loop-protocol dispatch record survives). Middle-ground; treats dynamic workflows as a first-class primitive in the harness.

Option A is the smallest, safest, and can happen this week. Option B is the biggest opportunity but would need a spec pass to size the migration risk against the "keep the harness lean" philosophy (`README.md:23–34` "Why Not Superpowers"). Option C threads the needle if `/ultracode` becomes the operator's go-to.

### Concrete step to unblock the decision
Have `/spec-planner` produce `docs/specs/2026-07-<date>-dynamic-workflows-integration.md` with:

1. A pass over `skills/planning-loop/`, `skills/run-wave/`, `skills/run-loop/`, and `skills/_shared/loop/` cataloguing every fan-out / adversarial / loop pattern the harness already implements by hand
2. A one-column mapping from each harness pattern → the equivalent `Workflow` script primitive (parallel/pipeline/etc.)
3. A recommendation on A / B / C above with the maintenance-cost / behavior-change tradeoff explicit
4. If the recommendation is A: the exact prose to insert into `README.md` and `AGENTS.md`

This is the shape that survives the `/spec-planner` acceptance-check discipline (F-037–F-039, Wave 25) because the acceptance criteria are literal file edits.

### Expected payoff
Two mechanisms → one clear rule for when-to-reach-for-which. Removes a class of "should I have used a workflow here?" second-guessing for the maintainer. If B is picked later, spec-first means the migration is measurable; if A is picked, one paragraph closes the ambiguity permanently.

**Verify before applying:**
1. `grep -rn "Workflow tool\|/ultracode\|Workflow(" /home/user/claude-harness --include='*.md'` — must return zero non-suggestion matches today; if `README.md` or `AGENTS.md` now mentions the `Workflow` tool or `/ultracode`, some form of Option A has landed and this § is at least partially superseded.

```diff

+
+Per Anthropic's internal experience [1], the highest-signal content in any
+SKILL.md is a `## Gotchas` section that lists concrete failure modes Claude

+as a few lines and a single gotcha, then got better because people kept
+adding to them as Claude hit new edge cases.
+
+**Format:** a bulleted list of `- **<one-line failure mode>** — <how to

+checklist. The section should read as a live changelog of failures, not
```

## 3. Audit the harness skill inventory against Anthropic's 9-category framework

**Source:** [Lessons from building Claude Code: How we use skills — claude.com/blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills) (same post as §2, different lesson)

### Why it might be relevant
The post catalogues Anthropic's internal skills into **nine categories** — library/API reference, product verification, data fetching/analysis, business-process automation, code scaffolding/templates, code quality/review, CI/CD & deployment, runbooks, infrastructure operations — and asserts that **the best skills fit cleanly into one category, while skills that straddle several confuse the agent**. Anthropic singles out **verification** as the highest-value category by measurable impact on output quality.

If the harness's 22 skills contain a few multi-category straddlers, this framework is a lens to catch them.

### Why it's `defer` today
- **The 22-skill inventory is small enough for eyeball review**, not framework audit. The current skills already carry clear single-purpose names (`commit`, `park`, `micro`, `harness-status`, `deploy-check`, `a11y-check`, `migration-check`, `api-smoke-test`, `apply-anthropic-reviews`, `memory-prune`, `triage-parking`, `run-wave`, `close-wave`, `run-loop`, `planning-loop`, `session-start`, `session-end`, `setup-harness`, `project-init`, `archive-plan`, `shared-root-init`, `skill-creator`, `new-cowork`, `cowork-area-sync`). Each is single-purpose today. Solo-maintained; no formal audit debt.
- **The harness's guiding principle is lean context, not process** (`README.md:23–34`). Applying a 9-category taxonomy adds process before any concrete pain has surfaced. Straddler skills would be caught by the maintainer noticing "this skill is doing two things" — not by a framework pass.
- **The insight is worth preserving** as a lens for the next time a new skill is proposed: "which of the 9 categories does this fit — and if it straddles, is it two skills?"

### Concrete deferred change
When the next new skill is proposed, `skills/skill-creator/SKILL.md` should ask the operator: **"Which single Anthropic 9-category slot does this fit — and if it straddles more than one, can we split it?"** That question is the useful shape; the audit is not.

### Expected payoff (if activated later)
Prevents skill scope creep the next time an operator says "I want a skill that does X and also Y." Zero payoff until then.

**Verify before applying:**
1. `ls /home/user/claude-harness/skills/ | wc -l` — if the number has grown well past 22 (e.g., > 35), a lens-driven review is a more useful use of time and this § should be promoted from `defer` to `apply`.

**Recommended verdict:** defer until skill count grows or a straddler-skill complaint surfaces in `parking_lot.md`. Framework is useful; forcing it on a 22-skill inventory adds process ahead of need.
