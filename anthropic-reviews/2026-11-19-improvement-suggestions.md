## 2. Add a `representations/` wiki layer to the shared memory spec — mirror the four-layer hierarchy from "components of agent memory"

**Source:** [The components of agent memory — anthropic.com/research, 2026-11-06](https://www.anthropic.com/research/components-of-agent-memory)

### Why it's relevant
Anthropic's memory post formalizes a **four-layer hierarchy** that the harness implements only partially today:

| Layer | What it holds | Harness equivalent (as of 2026-11-19) |
|---|---|---|
| 1. Transcripts | Searchable event log of everything the agent did | `.harness-state/*.yml` receipts + `.harness-state/orchestrator.{log,jsonl}` |
| 2. Memory notes | Salient per-session observations | `~/.claude/projects/<encoded-cwd>/memory/MEMORY.md` (per-cwd auto-memory) |
| 3. Representations | **Linked wiki pages that map what the agent knows** | **Missing.** `~/.claude/memory/feedback/<slug>.md` is close but is indexed by `FEEDBACK.md` as a flat list, not as a linked graph. |
| 4. Injected context | Small top-layer loaded into every session | `CLAUDE.md` + `AGENTS.md` + `~/.claude/memory/USER.md`/`FEEDBACK.md` |

The harness has layers 1, 2, and 4, with a thin version of 3 in `feedback/`. The post's strongest empirical claim — that wiki+search beat search-alone by ~20,000 tokens per question in their study — argues for making layer 3 a first-class artifact with linking rules, not just an unordered pile of per-pattern files.

The post also surfaces two gotchas the harness's current memory model doesn't address:
- **Concurrent writes to shared files corrupt memory** (41 of 57 → 57 of 57 recall when each entity got its own page). The harness's `FEEDBACK.md` is a shared index written by `/memory-prune` and hand-appended; a write-collision is possible during a `/session-end` burst.
- **Validate notes against transcripts** ("dreaming"). The harness has no `.harness-state` → `~/.claude/memory/feedback/` reconciliation pass. Per-cwd `MEMORY.md` entries can drift from the receipts that generated them.

The 5KB cap on `FEEDBACK.md` + the ≤150 char line budget currently push the system toward very terse one-liners that can't *link* to related patterns — which is exactly what layer-3 representations buy you.

### Concrete direction (needs a spec, not a patch)
A full design is non-trivial and the maintainer should drive it. Rough shape:

- **New dir:** `~/.claude/memory/wiki/<topic>.md` — one file per topic (not per pattern), each linking to related topics with `[[wiki-link]]` or relative markdown links. Index at `~/.claude/memory/WIKI.md` (not auto-loaded in full; follows `MEMORY.md`-style head-truncation convention).
- **Promotion rule:** 3+ patterns in `~/.claude/memory/feedback/*` sharing a topic get consolidated into a `wiki/<topic>.md` page by a `/memory-prune --wiki` subcommand or a new `/memory-dream` skill.
- **Dreaming pass:** `/memory-dream` (new skill, runs offline / on operator trigger): walks `.harness-state/*` receipts, cross-references `feedback/*.md` entries against the receipts that spawned them, flags entries whose receipts no longer exist or contradict current state.
- **Concurrent-write fix:** `/session-end` writes to a per-session temp slice (`~/.claude/memory/feedback/.session-<id>/`) and a separate consolidation step rolls them up — avoids two concurrent `/session-end` runs trampling one another's rows.

### Why `spec` and not `apply`
Four independent design choices here (wiki-link syntax, dreaming cadence, concurrent-write protocol, promotion threshold) each have multiple defensible answers. Writing any of them as a one-session patch risks locking in the wrong convention. The existing `docs/specs/2026-05-13-memory-system-redesign.md` is the precedent — memory system changes get a spec.

**Verify before applying:**
1. `ls ~/.claude/memory/wiki 2>/dev/null` — must return "No such file or directory" (or empty); if a `wiki/` dir already exists, a prior run of this suggestion is in flight and this § should be re-scoped.
2. `grep -rn "dreaming\|representation.*layer\|wiki.*memory" docs/specs/` — must return nothing (or only cross-references to this §); a hit means an existing spec already covers this ground and this § is a duplicate.
3. Re-read the Anthropic post before writing the spec — the "goal-oriented prompting" + "judgment over fixed rules" guidance *contradicts* the harness's current preference for mechanical gates. A spec that tries to reconcile those (mechanical cap limits + judgmental promotion) needs both pieces, not just the mechanical one.

**Recommended verdict:** spec — four interacting design choices, memory is load-bearing for every session, prior memory work went through specs. Needs `/spec-planner` before any code.
**Status:** PENDING — awaiting triage in PR review

## 4. Documentation for `verify:` gate kind in `AGENTS.md` §"Loop protocol" — Claude Code verification-loop pattern

**Source:** [Building verification loops in Claude Code with skills — claude.com/blog, 2026-11](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) (companion to the Claude Code team's verification deep-dive which could not be fetched directly during this run — URL at `claude.dev` currently returns ENOTFOUND for the session's egress rules)

### Why it's relevant (and already addressed)
The post describes a verification-loop pattern:
- `/verify` skill runs the app end-to-end against a project's build/test commands.
- `/code-review` hunts for bugs in the diff.
- `/simplify` cleans up the diff.
- Custom per-project checks (e.g. a `DESIGN.md` ruleset) are composed via standalone / embedded / chained / per-PR modes.

**The harness already implements this pattern**, though under a different naming:

| Blog pattern | Harness equivalent (grep-confirmed) |
|---|---|
| `/verify` runs `build && test && smoke` | `.harness-profile` `gate.verify` scalar/argv forms (`skills/run-loop/SKILL.md:150`); `/run-loop` refuses runs without one (`skills/_shared/loop/run-loop-driver.ts:101`) |
| `/code-review` hunts bugs | `code-reviewer` agent (`.claude/agents/code-reviewer.md`) + Claude-Code-native `/code-review` skill (listed in session's skills manifest) |
| `/simplify` cleans diff | Claude-Code-native `/simplify` skill (listed in session's skills manifest) |
| Standalone / embedded / chained / per-PR | `/run-loop` gate executes exit-gated per item; `/run-wave` chains review+commit; `/commit` chains `code-reviewer`; git hooks (Wave 26, `feat(git-hooks):`) run pre-push |
| `DESIGN.md` ruleset | `criteria/*.md` project-specific rubrics (consulted by `code-reviewer` + `skill-creator`) |

The only additive candidate was "one-paragraph pointer to the blog post in `AGENTS.md`" — but **`AGENTS.md` §"Loop protocol" already documents the three-way gate rule** (lines 100–110 of AGENTS.md: *"no resolvable gate ⇒ refused before any work AND each item is red; configured-but-empty passes; misconfigured fails closed"*), which is the operationally-important part. The blog post just restates the pattern at a higher level.

### Why `reject`, not `apply`
A citation for citation's sake adds noise. The harness's loop-protocol section is already dense; adding a pointer to a blog post that describes the same pattern more loosely would make the file worse, not better. The cross-reference belongs in **the README's References section** at most — which is where Anthropic engineering posts go — and even there the signal-to-noise is marginal since the pattern is already named in AGENTS.md.

If a future contributor asks "why does `/run-loop` refuse without a gate?" the answer is **already in AGENTS.md Loop protocol §Gate rule**, not in a blog citation. Recommending this change would create exactly the kind of duplicate-documentation surface Anthropic's own writing about "injected context should be small" (from §2 above) argues against.

**Verify before applying:**
1. `grep -nE "verify.*gate|gate.*verify|three-way rule" AGENTS.md` — must return the lines in the Loop-protocol block covering the three-way rule; if that documentation has been removed since this review was written, the `reject` recommendation changes to `apply` because the gate behavior is no longer self-documenting.
2. `grep -n "building-verification-loops\|/verify" README.md CLAUDE.md` — must return nothing; if it does, somebody already added the citation and the rejection is moot.

**Recommended verdict:** reject — pattern already implemented and documented in AGENTS.md §"Loop protocol"; a citation to the blog post would be noise, not signal. Preserved as a durable record so a future reviewer doesn't re-propose the same change.

## 5. Bookkeeping: *How we contain Claude across products* corroborates the catastrophic-command denylist + worktree/sandcastle runner split

**Source:** [How we contain Claude across products — anthropic.com/research, 2026-05-25](https://www.anthropic.com/research/how-we-contain-claude)

### Why it's a bookkeeping entry (not a code change)
The post lays out Anthropic's "containment = blast radius" framing: environment boundaries, egress controls, filesystem modes, credentials-out-of-sandbox. The harness's `/run-loop` implementation corroborates this framing on three independent axes:

- **PreToolUse denylist hook** (`skills/_shared/loop/safety/denylist.ts` — installed in `~/.claude/settings.json` by the operator). This is the harness's blast-radius cap on worktree-runner items: a catastrophic command (`rm -rf`, `git push --force` to protected branches, etc.) is refused before the tool fires. The post's "put the boundary in the environment" prescription matches the hook's design: it runs at tool-dispatch, not after the fact.
- **Runner split** (`worktree` vs `sandcastle` — `skills/run-loop/SKILL.md:101`). The worktree runner uses Claude Code's `.claude/worktrees/agent-<id>/` convention (filesystem boundary only). The sandcastle runner uses a container engine (OS-level boundary + egress controls). The post's "claude.ai ephemeral container / Claude Code OS sandbox / Claude Cowork local VM" ladder matches the harness's "no sandbox / worktree / sandcastle" ladder — different vocabulary, same principle.
- **Auto Mode miss-rate caveat** (post: "classifier misses about 17% of risky commands, so it works only inside a sandbox"). The harness's own 2026-05-08 §1 already applied the matching permission-mode guidance; this post adds quantitative backing to that decision.

### Why no code change
Everything the post prescribes is already implemented. The one potentially-new direction — **"inspect tool outputs live"** with a small/fast classifier before results enter model context — is an architectural lift that would overlap with Claude Code's built-in PostToolUse hook mechanism, not something a solo-maintained harness should re-implement.

### Durable-record value
Records that the May 25 post is **retrospectively consistent** with the harness's Wave 24 denylist hook + runner-split design. A future reviewer asking "is this still the right split?" has a dated Anthropic post to anchor on.

**Verify before applying:**
1. `grep -n "denylist\|worktree.*sandcastle\|PreToolUse" skills/_shared/loop/safety/denylist.ts skills/run-loop/SKILL.md AGENTS.md` — must return the three mechanisms named above; if any have been removed, this bookkeeping entry becomes stale and should be re-evaluated (the removal may mean the harness has moved away from containment, in which case the Anthropic post becomes a `revisit`, not a corroboration).

**Recommended verdict:** defer — bookkeeping; no concrete edit. Preserved so the durable record reflects the Anthropic-side corroboration for Wave 24's design.

## 6. Speculative: evaluate a Scion-style API-query shim before `git log/blame` in high-frequency skills

**Source:** [Redesigning source control at Anthropic — anthropic.com/research, 2026-10-13](https://www.anthropic.com/research/redesigning-source-control)

### Why it's speculative
The post describes **Scion**, Anthropic's internal replacement for git aimed at agent-scale workloads: server-heavy / client-light split, content-addressed caches, API-first queries, no fully-materialized clones. Core claim: *"the bottleneck, now, is all of the developer infrastructure built for human scale."*

Scion is **Anthropic-internal** and not generally-available. The harness operates on **consumer repos cloned normally via `setup-harness`**, with `git log`, `git blame`, `git worktree`, etc. invoked directly by skills. So the post's concrete prescriptions aren't directly adoptable.

What's transferable is the **direction of travel**: when a skill repeatedly scans `git log` for commit metadata, that's exactly the pattern Scion replaces with an API query. The harness has at least one example: `/close-wave` walks commits since a branch cut to produce a receipt (`skills/close-wave/lib/*`). If that walk ever gets slow enough to matter (large repos, many commits), the mitigation is the same pattern Scion names: **ask the review tool / forge API, don't scan the log**.

### Concrete direction (defer)
When a skill's git-walk wall-clock exceeds ~5s on representative consumer repos, swap the scan for a `gh api repos/<owner>/<repo>/commits?since=…` query (or equivalent Scion-API when/if that becomes external). Not something to build before the pain shows up.

**Verify before applying:**
1. Before converting any `git log` to an API query, measure current wall-clock on a representative repo: `time bash skills/close-wave/lib/<walker>.sh` (or equivalent). If no skill walks 1000+ commits, there's no payoff for the API swap.
2. Confirm Scion is still Anthropic-internal (the Oct 13 post framed it that way) — if Anthropic ever ships an external Scion client, that changes the cost/benefit on this §.

**Recommended verdict:** defer until repo-scale pain — Scion itself is not generally available; adopting the direction prematurely would complicate code for no payoff.
**Status:** PENDING — awaiting triage in PR review
