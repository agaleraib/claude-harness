## 3. Bookmark dynamic workflows / "ultracode" as an alternate orchestration layer to the harness's `orchestrator` agent

**Source:** [Introducing dynamic workflows in Claude Code — Claude Blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (research preview launch). Follow-up engineering deep-dive: [A harness for every task: dynamic workflows in Claude Code — Claude Blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Reference docs: [Orchestrate subagents at scale with dynamic workflows](https://code.claude.com/docs/en/workflows).

Key claims (from the launch post + the follow-up):

- A dynamic workflow is "a **JavaScript script that orchestrates subagents at scale**. Claude writes the script for the task you describe, and a runtime executes it in the background while your session stays responsive."
- "Claude is now capable enough to **write a harness custom-fit to the situation** in front of it, rather than a catch-all script."
- Common patterns: "a classifier agent to decide on the type of task and then route to different agents," "a classifier at the end to determine output," "splitting tasks into smaller steps with an agent for each step and then synthesizing results."
- Trigger: "by asking Claude to make one, or by using the trigger word **`ultracode`** to ensure that Claude Code creates a workflow."
- Research-preview gating: "available today in research preview in the Claude Code CLI, Desktop, and the VS code extension for **Max, Team, and Enterprise (if admin enabled)** plans, as well as on the Claude API, on Amazon Bedrock, Vertex AI, and Microsoft Foundry."

### Why it's relevant (and why this is `defer`, not `apply`)

The harness already has an orchestration layer with the **exact same shape**: `agents/orchestrator.md` is "a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results" (line 7) — the Anthropic orchestrator-worker pattern, restated. The agent dispatches to Opus/Sonnet/Haiku subagents (line 196), supports worktree isolation for parallel work (line 202), and is gated by `model_routing: on/off` in `.harness-profile` (line 22). Dynamic workflows are conceptually **a different primitive at a different layer**:

| | Harness `orchestrator` agent | Anthropic dynamic workflows |
|---|---|---|
| Authoring | Markdown agent prompt + spec-driven tasks (`docs/specs/*.md`) | Claude generates a **JavaScript script** at runtime from the user's prompt |
| Runtime | Synchronous in the same Claude Code session | **Background runtime**; foreground session stays responsive |
| Scale | Tens of tasks per wave (current `/run-wave` cadence) | Designed for **100+ parallel subagents** in one workflow |
| Trigger | `/run-wave N` or "Use the orchestrator to build Phase X" | "ultracode" trigger word or natural-language ask |
| Verification | Per-task `Verify:` field in the spec | Built-in result-checking step before fold-in |
| Surface | Local subagent dispatch via Task tool | Anthropic-hosted runtime; same plan tiers as `/ultrareview` |
| Cost model | Same session as the user, no extra billing tier | Research-preview; cost not yet published (analogous to `/ultrareview`'s $5–20/run band) |

These are **complementary in principle**, but unlike the 2026-05-10 §1 case (local `code-reviewer` vs. cloud `/ultrareview` — both clearly different layers), here the overlap is **bigger than the gap**: both orchestrate subagents, both can use a classifier-router, both can fan out parallel work. The genuinely-new affordances of dynamic workflows for this harness's use case are:

1. **Background execution** — frees the foreground session while a wave runs. The harness today blocks the user's session for the duration of a `/run-wave`.
2. **100+ parallel scale** — the harness's current waves never exceed a handful of parallel tasks (File-overlap analysis is in `orchestrator.md:81`); the dynamic-workflows scale band doesn't match any current use case.
3. **JS scripting** — Claude can write arbitrary glue between subagents, beyond the current spec's `Files:` / `Verify:` / `Depends on:` field set.

Of those, only (1) is a real ergonomic win for a solo maintainer running one wave at a time. (2) is speculative until the harness ever needs 100-subagent fan-out. (3) is a strict superset of what the spec format provides, but the spec format's narrowness is a *feature* — it's what makes the orchestrator's routing decisions reviewable and auditable (the `Logging Contract` in `orchestrator.md` Step 8 depends on the typed fields).

Reasons to defer rather than apply now:

1. **Research preview.** Pricing, retry semantics, failure modes, and routing-cost guidance aren't yet documented. The same caution that applied to the 2026-05-10 §2 (Cloud Routines defer) applies here.
2. **Plan tier gating.** Workflows require Max, Team, or Enterprise (or API). If the harness ever recommends them in `setup-harness`, the docs need to be explicit that Pro-plan users hit a wall — a UX cliff the harness doesn't have today.
3. **Cost-vs-overlap calculus.** The harness's `orchestrator` is in-session (no extra billing); dynamic workflows are a separate runtime presumably billed by tokens/min. For a solo maintainer running ~1 wave/day, the value-add of background execution isn't worth re-tooling the orchestrator agent against an unstable API surface.
4. **"ultracode" trigger collision risk.** The harness exposes `/run-wave`, `/spec-planner`, `/orchestrator` (implicit), and the user-level `claude-api` skill mentions `ultrareview` as an adjacent cloud feature. Adding "ultracode" to the methodology vocabulary without a clear semantic split risks confusion. Wait until Anthropic publishes naming-stability guarantees.
5. **The bookmark exists for one explicit re-trigger condition:** when the orchestrator agent's synchronous block becomes a measurable pain point (e.g., the maintainer notices waves blocking the session for >10 min routinely), revisit. Until then, defer.

## 4. Add a one-paragraph "trust-folder trap" warning to `setup-harness` for when it eventually templates a hook

**Source:** [How we contain Claude across products — Anthropic Engineering, ~2026-05-28/30](https://www.anthropic.com/engineering/how-we-contain-claude). Vulnerability-class quote:

> "A developer can clone a repository to review a pull request that contains a `.claude/settings.json` which defines a hook. … Claude Code reads project settings during startup — **before presenting the standard 'Do you trust this folder?' prompt** — and attackers had authored and committed hooks that would execute automatically. The fix in each case had the same shape: **defer parsing and execution of project-local configuration until after the user accepts the trust prompt.**"

The post also covers: process sandboxes (Linux Bubblewrap, macOS Seatbelt, gVisor for claude.ai, full VM for Cowork); the May 2026 Auto Mode classifier's defense-in-depth role inside a sandbox ("~17% of overeager actions get through"); the general principle that "project-open, config-load, and localhost listeners should be treated the way you'd treat any inbound request from the internet."

### Why it's relevant (and why this is `defer`, not `apply`)

Today the harness ships `.claude/settings.json` as `{"hooks": {}}` (verified). `skills/setup-harness/SKILL.md` does not template any hook into a consumer project. So the vulnerability class the post describes — a hook firing before the trust prompt — **cannot reach a user via this harness today.** The post is interesting but not actionable for the current surface.

However, two prior anthropic-reviews suggestions opened the door to templating hooks in the future:

- **2026-05-08 §1 (APPLIED)** — `setup-harness` now documents the Auto Mode + hooks layering model and notes the "fewer-permission-prompts" skill writes hook allowlists.
- **2026-05-07 §3 (DEFERRED)** — bookmarked the PostToolUse `updatedToolOutput` hook pattern as a context-compression candidate when token-budget pain triggers.
