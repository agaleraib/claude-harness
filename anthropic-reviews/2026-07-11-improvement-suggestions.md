## 3. Park Opus 4.8's Dynamic Workflow tool + Sonnet 5 native subagent orchestration as a candidate replacement for the harness's runtime dispatch layer

**Source:** [Claude Opus 4.8 dynamic workflows — TechCrunch, 2026-05-28](https://techcrunch.com/2026/05/28/anthropic-releases-opus-4-8-with-new-dynamic-workflow-tool/) · [Opus 4.8 announcement — anthropic.com/news](https://www.anthropic.com/news/claude-opus-4-8). Follow-up detail: [Anthropic ships Opus 4.8 with dynamic workflows and fast mode — MarkTechPost, 2026-05-28](https://www.marktechpost.com/2026/05/28/anthropic-ships-claude-opus-4-8-alongside-dynamic-workflows-and-cheaper-fast-mode-with-workflows-capped-at-1000-subagents/).

### Why it's relevant

Opus 4.8 shipped a first-party **Dynamic Workflow** tool: a JavaScript-based orchestration primitive where Claude writes a script that spawns up to **1000 subagents** and the platform executes it in the background with per-subagent verification. Sonnet 5 inherits the same primitive at Sonnet cost.

The harness has an equivalent dispatch layer — `orchestrator` agent (README architecture, `.claude/agents/orchestrator.md`) + `run-wave` skill (parallel task dispatch through `TaskCreate`/subagent spawning). Today, the harness's dispatch is bounded by Claude Code's per-conversation subagent limit (~16 concurrent per Task tool) and pays the full input-token cost each subagent spawn. Anthropic's Dynamic Workflow gives up direct in-session subagent control in exchange for platform-side management + verification + the higher parallelism ceiling.

### Why this is `defer`, not `apply`

1. **Works today.** The harness's dispatch through `orchestrator` + `run-wave` handles the parallelism this repo actually uses (typically 3–8 subagents per wave, not 1000). No visible bottleneck.
2. **API-level primitive, not Claude Code CLI-level.** Dynamic Workflow is documented as an API tool on the Opus 4.8 platform, not exposed as a `/subagent` slash command or `Task`-tool argument. The harness runs *inside* Claude Code sessions; adopting Dynamic Workflow would need the harness to reach the Anthropic API directly (breaking the "runs inside Claude Code" contract).
3. **Loses the harness's rubric-anchoring.** The `orchestrator` agent's routing is model-agnostic (opus / sonnet / haiku) and reads `.harness-profile` to route by stakes. Dynamic Workflow's platform-side verification uses its own criteria, not the harness's `criteria/` rubrics.
4. **Speculative for solo tooling.** Per the routine's rubric: same triage class as the 2026-04-19 §2 (brain/hands split) deferral. The Anthropic side of the split has now shipped a primitive; the harness side would need a spec pass before adoption. Flag for the maintainer's radar; don't build yet.

### Concrete change (deferred)

Append one line to `parking_lot.md` under a "Speculative — vendor primitives to watch" section (or create one if missing):

```

```

When/if the maintainer wants to take it on:
1. Spec via `/spec-planner`: replace `orchestrator` + `run-wave` dispatch with a Dynamic Workflow call. Preserve `criteria/`-based verification by injecting the rubric into the workflow script.

3. Prototype at small scale (5 subagents) before committing to a full swap.

### Expected payoff (when applied)

For consumer projects with truly wide fan-out work (compiler-style migrations, mass-audit passes), 1000-subagent parallelism at platform speed vs. the current ~16-per-Task Claude-Code ceiling. For the harness itself, no visible payoff today.

## 4. Bookkeeping: Alberta government's 466M-line-of-code parallel-agent security review corroborates the harness's `code-reviewer` + `/commit` human-approval pattern

**Source:** [Government of Alberta uses Claude to find and fix cybersecurity vulnerabilities — anthropic.com/news, 2026-07-06](https://www.anthropic.com/news/alberta-government-claude-cybersecurity).

### Why it's relevant

Alberta's Ministry of Technology and Innovation ran **~50 parallel Claude agents** across **466 million lines of code** in **20 hours** to find and fix cybersecurity vulnerabilities. Anthropic's case study describes the pattern:

- A **"red team" agent** probes the application from the outside as an attacker would;
- A **"blue team" agent** assesses defenses against an international security standard;
- The blue team writes a remediation plan naming exact files to fix;
- **All patches require human engineer review and approval before shipping.**

This is *the same three-step pattern* the harness codifies at a per-commit granularity:

- `code-reviewer` agent runs adversarial review (analogous to red-team + blue-team combined in one adversarial pass — see `.claude/agents/code-reviewer.md` and README:379–394).
- Findings are surfaced as "blocks merge / degrades quality / minor" (analogous to a remediation plan naming specific files).
- **The human maintainer must approve** each finding's fix via the `/commit` flow before the change lands (analogous to Alberta's engineer-approves-before-patch step).

### Why this is bookkeeping, not `apply`

The pattern is already documented in-repo:
- `README.md:44` names `code-reviewer` as adversarial;
- The `/commit` skill routes through code-reviewer + human approval before landing (`skills/commit/SKILL.md`);
- The 2026-04-19 §6 tracker entry already captured the Anthropic-reported multi-agent-supervision trend.

There is no new *methodology insight* to import. What's new is production-scale evidence — external validation that "adversarial agent + mandatory human approval before ship" holds up at 466M-LOC scale, on a real government's systems. That is worth recording in the tracker (below) as corroborating evidence for the deferred 2026-04-19 §5 (agent evals) — the Alberta write-up implies eval fixtures Anthropic could publish — but is not a repo edit request.
