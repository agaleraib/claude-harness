## 4. Adopt a **`## Gotchas`** section convention across `skills/*/SKILL.md`

## 5. Bookkeeping: **dynamic workflows in Claude Code** are the CLI-native form of the `orchestrator` agent's fan-out

**Source:** [Introducing dynamic workflows — claude.com/blog, June 2026](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code). Deep dive: [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, June 2026](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Corroborating case study: [How Anthropic runs large-scale code migrations with Claude Code — claude.com/blog, June 2026](https://claude.com/blog/ai-code-migration) (Bun's Zig → Rust migration ran hundreds of parallel subagents via dynamic workflows).

### Why it's relevant

Dynamic workflows are Claude Code's native primitive for **agent-writes-orchestration-script → parallel subagents → verified handoff**. They shipped GA in June 2026 for Pro/Max/Team/Enterprise, on the CLI + Desktop + VS Code extension + the Claude Developer Platform / Bedrock / Vertex / Foundry.

The harness has an `orchestrator` agent (`.claude/agents/orchestrator.md`, `model: opus`, referenced from `README.md:574`) that dispatches waves of work to specialist subagents at appropriate effort tiers. Same conceptual shape as dynamic workflows — but implemented as **prompt-driven dispatch** rather than as **script-driven fan-out**.

- Orchestrator's advantage today: rubric-anchored (reads `criteria/`), stakes-aware (reads `.harness-profile.effort_default`), integrated with `plan.md` and `/run-wave` / `/close-wave` conventions.
- Dynamic workflows' advantage: scale (hundreds of parallel subagents on the CLI's own dispatcher, not one prompt at a time); native cost tracking; native model routing per-agent; the Bun migration ran 750K lines / 11 days that way.

This is **directly parallel** to:
- `2026-04-19 §2` (brain/hands split for the orchestrator, `Status: DEFERRED until Managed Agents adoption`).
- `2026-05-07 §1` (Managed Agents multiagent orchestration — re-affirmed the same deferral).
- `2026-05-10 §3` (dreaming/memory bookkeeping — same deferral chain).

So this is **not a new ask**; it's an update: **dynamic workflows are now the CLI-native path**, not just the cloud-hosted Managed Agents path. That changes the migration calculus — a rewrite of `orchestrator` around dynamic workflows would run on the same laptop as today, no Managed Agents adoption required.

Still `defer` — the orchestrator is stable, spec-planned (`docs/specs/2026-04-19-harness-model-pin-and-effort-routing.md`), wave-tracked, and there's no user-visible pain that a dynamic-workflow rewrite would fix. But the option is now closer than 2026-04-19 §2 assumed.

### Concrete change

None this run. When/if the maintainer wants to take this on:

1. Spec a rewrite of `.claude/agents/orchestrator.md` from prompt-driven dispatch → dynamic-workflow-script dispatch. The routing table (effort tier by task class) becomes an inline JS heuristic instead of prose.
2. Preserve rubric-anchoring: dynamic workflows can read `criteria/` files just like agents can; the change is in the dispatch primitive.
3. Preserve stakes-awareness: `.harness-profile.effort_default` becomes a runtime input to the workflow script.
4. Measure: run one wave both ways (orchestrator vs. dynamic-workflow); compare wall-clock, cost, and rubric-hit rate.
