## 3. Consider migrating skill distribution from `~/.claude/skills/` symlink to `.claude-plugin/plugin.json`

**Source:** [Customize Claude Code with plugins — claude.com/blog](https://claude.com/blog/claude-code-plugins). Anthropic productized plugins as an extensibility surface for Claude Code (public beta 2026; blog post surfaced during discovery, publication date not confirmed via WebSearch snippets). A Claude Code plugin is a directory with a manifest at `.claude-plugin/plugin.json` that bundles **skills + agents + hooks + MCP servers** as one versioned, installable unit, distributed via `/plugin install <source>`. Ecosystem coverage from search: plugins bundle `skills/`, `agents/`, `hooks/`, `.mcp.json` in one directory tree; installed skills surface as slash commands, agents show up in `/agents`, MCP servers register tools, and hooks/monitors run on their matchers.

### Why it's relevant

The harness currently distributes via `skills/setup-harness/SKILL.md`: it symlinks the repo's `skills/` and `.claude/agents/` into the target machine's `~/.claude/skills/` and `~/.claude/agents/`. Confirmed by `CLAUDE.md`:

> Source of truth: `skills/` in this repo.
> Symlinked OUT to `~/.claude/skills/` (claude-harness ships skills to the user's global Claude Code config).

That works, but a plugin-distribution model would:

- Ship one versioned manifest (`plugin.json`) instead of a symlink graph;
- Let consumer projects install with `/plugin install agaleraib/claude-harness` (Anthropic-blessed path, no bespoke `setup-harness` skill);
- Bundle **agents + hooks + skills + `.mcp.json`** together — the harness already has all four, currently distributed by hand;
- Get versioning + update semantics from Claude Code itself, not from the harness's own `setup-harness` re-run logic.

Today `grep -rn "\.claude-plugin\|plugin\.json\|/plugin install" /home/user/claude-harness` returns zero hits. `ls .claude-plugin/ 2>/dev/null` returns nothing.

### Why this is `spec`, not `apply` (and not just `defer`)

1. **Distribution-model refactor is substantive.** The `setup-harness` skill is 200+ lines of installer logic covering permission modes, symlink strategies, per-project vs global scoping, and the `.harness-profile` bootstrap. Migrating to a `plugin.json` manifest requires deciding: what stays in `setup-harness` (project-level bootstrap, `.harness-profile` creation, `CLAUDE.md` seeding — none of which a plugin manifest covers), what moves to the plugin, and how existing installs migrate. That's a spec-worthy question, not a `/micro`.

2. **The plugin manifest schema is evolving.** Public beta since June 2026; changelog entries through September 2026 (`managedMcpServers`, `/skill-doctor`, `omitClaudeMd`) are still landing in the plugin/manifest ecosystem. Locking the harness into a schema before it stabilizes risks rework.

3. **Consumer projects install via `setup-harness` today, but many also symlink or fork.** A plugin-based install replaces one path; consumers who fork the harness aren't served by `/plugin install`. The migration story needs to cover both.

4. **Skills-as-slash-commands has shifted.** Anthropic unified skills and slash commands in 2026 — every skill gets a `/slash-command` interface automatically. The harness's current invocation style (`/close-wave`, `/run-wave`, `/commit`, etc.) may already be plugin-compatible without any per-skill edits. Worth confirming in the spec.

5. **`setup-harness` also seeds `.harness-profile`, `criteria/`, `procedures/` — none of which are plugin components.** A plugin-only install would leave those non-plugin pieces homeless; the spec would need to decide whether they stay in a `setup-harness` bootstrap or migrate to plugin-post-install hooks.

## 5. Bookkeeping: "Quantifying infrastructure noise in agentic coding evals" corroborates deferred agent-evals work

**Source:** [Quantifying infrastructure noise in agentic coding evals — anthropic.com/engineering](https://www.anthropic.com/engineering/infrastructure-noise). Anthropic ran Terminal-Bench 2.0 across six resource configurations on GKE and found a **6 percentage point gap** between most- and least-resourced setups — sometimes larger than the top-of-leaderboard gap between frontier models. Concrete findings from WebSearch excerpts:

- Moderate resource headroom (up to ~3× spec) primarily prevents spurious failures.
- Generous headroom actively helps agents solve problems they couldn't solve before.
- Every element of the eval setup can influence final scores: cluster health, hardware specs, concurrency, egress bandwidth.
- Pass rates fluctuate with **time of day** — API latency varies with traffic patterns.
- Recommendations: specify both guaranteed allocations and hard kill thresholds; calibrate resource bands empirically; treat resource configuration as a **first-class experimental variable**.

### Why it's relevant

The harness has an outstanding deferral on **agent evaluation fixtures**:

- `2026-04-19 §5` — "Formalize evals for the adversarial reviewers" · **DEFERRED** — solo-tooling scope; would require fixtures + baseline scoring.
- `2026-05-03 §1` — BioMysteryBench floor/ceiling tier split methodology attached to §5's design constraints · **DEFERRED**, tied to §5.

Infrastructure noise is a **methodology constraint** that any future eval work should honor. If/when the maintainer picks up §5, the eval harness needs to:

1. Fix resource allocations (Claude session concurrency, hardware, egress) and record them per-run.
2. Distinguish "the reviewer missed a bug" from "the reviewer was rate-limited or ran on a hot-noon API window."
3. Report resource config alongside pass rates — treat it as a first-class experimental variable, per Anthropic's own recommendation.

The tier split from `2026-05-03 §1` (human-solvable / human-difficult) + the infrastructure-noise controls from this § are complementary constraints on the same deferred spec.

### Concrete change
