## 3. Introducing Dynamic Workflows in Claude Code — bookkeeping only

**Source:** [Introducing dynamic workflows — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (Anthropic engineering announcement); [InfoQ coverage](https://www.infoq.com/news/2026/06/dynamic-workflows-claude-code/).

### Why it's relevant

Anthropic shipped **Dynamic Workflows** — Claude Code's new orchestration primitive where Claude writes an orchestration script on the fly, spins up tens-to-hundreds of parallel subagents on a shared filesystem, and verifies its own work before reporting. The most-cited use case is Bun's Zig→Rust runtime port (750,000 lines of Rust in eleven days, 99.8% test pass rate). GA on Pro / Max / Team / Enterprise + API since roughly Jun 2026. The harness has three surfaces that overlap in concept:

- **`.claude/agents/orchestrator.md`** — the harness's runtime dispatcher; reads tasks and routes each to opus/sonnet/haiku by complexity. Sequential in today's design; not fanning out hundreds of parallel agents.

- **`skills/planning-loop/SKILL.md`** — the planner/generator/reviewer triad for a wave.

Dynamic Workflows do something distinct from any of these: **the model itself writes the workflow script per-task at runtime**, rather than the harness picking a dispatch pattern up front. ## 4. How Warp builds self-improving agents on Claude — pattern to park for a future `learn-from-feedback` skill

**Source:** [How Warp builds self-improving agents on Claude — claude.com/blog, 2026-08-26](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude). Companion Anthropic webinar: [How Warp builds self-improving agents on Claude](https://www.anthropic.com/webinars/how-warp-builds-self-improving-agents-on-claude).

### Why it's relevant

Warp shipped a two-file "inner skill / outer skill" architecture that turns stateless PR-comment feedback into a self-improvement loop:

- **Inner skill** — the base skill file holding domain knowledge and task instructions (for their code-review agent: what to look for in a diff).
- **Outer skill** — reads user/reviewer feedback from where work already happens (mostly PR comments), proposes a mutation to the inner skill's knowledge, and opens a PR the human reviews / approves / merges.
- **The final human step closes the loop** — the next run of the triage skill inherits the new knowledge only after a person actually merges the outer skill's PR.

That last part matters for portability. The pattern is **provider-agnostic**: a text file, PR comments, git. It doesn't need Managed Agents, Skills API, or any hosted platform. Which makes it different in kind from the deferred Managed Agents patterns (2026-04-19 §2, 2026-04-25 memory row, 2026-05-07 §1, 2026-05-08 §2, 2026-05-10 §3) — those all wait on the harness migrating off Claude Code. Warp's pattern would run *inside* Claude Code today.

### Why this is `defer`, not `apply` or `spec`

- **The harness already has the human-curator-in-the-loop half** of Warp's loop: `skills/session-end/SKILL.md` prompts the user to summarize the day and write `last_exit.md`; `skills/memory-prune/SKILL.md` is the manual promotion path (per `CLAUDE.md`: "Promotion to `~/.claude/memory/feedback/` is manual — see AGENTS.md `## Memory` for the move + frontmatter-stamp convention. There is no auto-promotion hook..."). The missing piece is the **outer skill that reads PR comments and drafts the mutation PR automatically**.
- **No evidence yet of the trigger case**: solo maintainer, ~25 skills. For an outer skill to earn its complexity, the same feedback pattern has to keep coming up across multiple sessions in a way that the maintainer keeps re-typing. Today the maintainer's `memory-prune` pass covers the case with lower overhead. Wait for evidence before building the outer skill.
- **`AGENTS.md` portability**: the pattern is portable (`.md` file + git PR + PR comments); when the case emerges, the design won't box the harness into Claude Code — that's a rare property worth preserving.

### Concrete change (deferred — record for future triage)

None this run. When the maintainer wants to prototype the Warp loop:

1. **Pick the target skill** — the smallest one where feedback recurs. `code-reviewer.md` is the most obvious analog to Warp's own case. `spec-planner.md`'s Rule-15 acceptance-strictness check (Wave 25) is a runner-up.
2. **Design the trigger** — cron routine? `session-end` hook? Or user-invoked via a `/learn-from-feedback` skill?
3. **Design the feedback source** — PR comments on this repo (as Warp does), triage-parking markers, or `~/.claude/memory/feedback/` entries the maintainer has already promoted.
4. **Design the mutation shape** — PR that edits a knowledge file (Warp-style), or a spec that goes through `/spec-planner` (harness-style) — the second option threads through the harness's existing governance and is probably the safer default.

### Expected payoff (when applied)

Instead of the maintainer periodically running `memory-prune` and hand-promoting per-cwd insights, an outer skill would surface promotion candidates as draft PRs. At today's scale that's a small win; at consumer-project scale (multiple projects surfacing similar feedback), it starts to matter.

**Verify before applying:**
1. `grep -rn "learn-from-feedback\|self-improving\|outer skill" /home/user/claude-harness` — must return zero today; if it returns hits under `skills/`, the prototype exists and this § is stale.
2. `grep -n "memory-prune\|manual by design" /home/user/claude-harness/CLAUDE.md /home/user/claude-harness/AGENTS.md` — should still show that memory promotion is manual by design (the load-bearing reason a self-improvement loop is not built today). If AGENTS.md has changed that stance, re-triage.
3. Cross-check the Warp post is still the reference implementation (Anthropic occasionally adds follow-ups); a `grep -rn "Warp\|how-warp-builds" /home/user/claude-harness` today returns zero.

**Recommended verdict:** defer until a specific feedback-repetition pain point emerges (e.g. the maintainer notices they've hand-promoted three similar per-cwd insights in a month). Portable, cheap-to-prototype design; don't build ahead of the pain.
