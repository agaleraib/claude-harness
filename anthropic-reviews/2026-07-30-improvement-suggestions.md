## 1. Bump `.harness-profile` `model.primary` from `claude-opus-4-7` to `claude-opus-4-8`

- **Honesty gain, evaluated first-party.** Anthropic reports Opus 4.8 is "around four times less likely than its predecessor to allow flaws in code it generated to go unremarked." The loop is running on 4.8 while the profile documents 4.7.

### Why it's relevant

Dynamic Workflows is a research-preview Claude Code primitive shipped alongside Opus 4.8 on 2026-05-28 and given a deeper engineering write-up on 2026-06-02. What Claude Code can now do without any harness:

- Author a JavaScript orchestration script on the fly for a given task ("A harness for every task").
- Dispatch tens to hundreds of parallel subagents from that script within a single session.
- Cross-verify the subagents' work before returning to the user.

The named production evidence is Bun's Zig-to-Rust port: **750,000 lines of generated Rust, 99.8% test-suite parity, 11 days from first commit to merge.** That is the scale range the harness's `.claude/agents/orchestrator.md` + `skills/run-wave/SKILL.md` + `skills/planning-loop/SKILL.md` were designed for.

- **Migrate:** replace `orchestrator` + `run-wave` dispatch with Claude Code's Workflow tool.
- **Complement:** keep the harness's plan.md-driven waves as the *input* to Workflow scripts (waves as work items, Workflow as executor).
- **Ignore:** the harness's `run-loop` mechanical gate (Wave 21+, LIVE with real Opus/OpenRouter/Codex backends) has properties Dynamic Workflows may not — deterministic per-item gates, resume-as-idempotent-replay, portable to non-Anthropic backends.

Either way, the README's existing lean-harness argument (line 25: *"heavy instruction systems degrade Opus 4.7 performance"*) and line 32 (*"vendor primitives keep absorbing harness territory"*) both need to acknowledge this specific product.

## 4. Audit which harness skills would benefit from progressive-disclosure `references/` / `assets/` subfolders

**Source:** [Lessons from building Claude Code: How we use skills — claude.com/blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills) · [KDnuggets summary](https://www.kdnuggets.com/anthropics-complete-guide-to-claude-skills-building) · [Extend Claude with skills — code.claude.com/docs/en/skills](https://code.claude.com/docs/en/skills).

### Why it's relevant

Anthropic's June 3 post distills what worked across "hundreds" of internal skills. The load-bearing lesson:

> "The entire file system should be thought of as a form of context engineering and progressive disclosure, with Claude reading files at appropriate times. […] The simplest form of progressive disclosure is to point to other markdown files for Claude to use, such as splitting detailed function signatures into references/api.md or including template files in assets/ to copy and use."

State of the harness's skills:

| Skill | Size (bytes) | Has references/ | Has assets/ |
|---|---|---|---|
| `skills/session-start/` | 9354 | no | no |
| `skills/commit/` | 11499 | no | no |
| `skills/run-wave/` | 27867 | no | no |
| `skills/planning-loop/` | (SKILL.md) | **yes** (`references/rules.md`) | no |
| `skills/skill-creator/` | (SKILL.md) | **yes** (`references/schemas.md`) | **yes** |
| `skills/apply-anthropic-reviews/` | (unknown) | no | no |
| Everything else | varies | no | no |

`run-wave/SKILL.md` at ~28KB is the biggest single-file skill and the strongest candidate for the pattern: it likely contains a mix of dispatch protocol (always loaded), receipt schema (referenced), and worked examples (rarely loaded but useful when they are). Extracting the schema and examples to `references/` would let Claude load the dispatch protocol at invocation and pull the extras only when a specific dispatch fails.

`commit/SKILL.md` at ~11KB is on the boundary — worth reviewing but not urgent.

### Concrete change

**Scoped audit, not a rewrite:**

1. Read each SKILL.md > 8KB in `skills/`.
2. For each one, ask: *"What content here is 'always relevant to the skill's core job' vs 'only relevant to a specific sub-case'?"*
3. For the ones with clear separation, extract sub-case content to `skills/<name>/references/<sub-case>.md` and replace with a one-line pointer in SKILL.md ("For receipt schema details, see `references/receipt-schema.md`").
4. **Do NOT restructure a skill just because it's long.** The heuristic is separation-of-concerns, not size.

Candidates from the table above, in order:

- **`run-wave/`** — Wave dispatch protocol vs receipt schema vs worked examples. High-signal candidate.
- **`commit/`** — Review-then-fix protocol vs receipt schema vs manual-fallback recipe. Borderline candidate.

**Skip:**

- `session-start/` (9.3KB) — hits every session; even a small extraction saves tokens at session start. Marginal.
- `run-loop/` — already large but a single tight body; the mechanical-gate protocol doesn't decompose cleanly.

### Expected payoff

Faster skill loading for common-path invocations (dispatch, commit) while keeping the rarely-needed content one file-read away. Zero risk if done as separation-of-concerns rather than size-driven splits.

`scope: speculative` — none of the harness's oversized skills has produced a documented performance complaint yet. The Anthropic post is a "we found this worked" observation, not a benchmark. Solo-maintained project can absorb a 28KB SKILL.md without pain.

**Verify before applying:** `find skills/ -name SKILL.md -size +8k -not -path '*/_shared/*'` — the list should still match the table above. If new large skills have been added since 2026-07-30, re-audit; if `run-wave/` or `commit/` has been split already, this suggestion is done.

**Recommended verdict:** defer until a specific SKILL.md hits a length/cache pain point (invocation slower than needed, or a maintainer edit becomes annoying because the file is too tall to navigate).

## 5. Package the `/commit`-style review-then-fix pattern as a distributable verification-loop skill

**Source:** [Building verification loops in Claude Code with skills — claude.com/blog, 2026-07-22](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) · [Loop engineering: Getting started with loops — claude.com/blog, 2026-06-30](https://claude.com/blog/getting-started-with-loops).

### Why it's relevant

Anthropic's July 22 post argues for packaging verification-with-attempt-cap as a portable skill:

> "A `/loop` skill wraps any task in an iteration cycle. Its instructions tell Claude: 'Execute the task. Run verification. If verification fails, analyze the failure, fix the code, and verify again. Repeat until all checks pass or you've made 5 attempts.' […] The attempt cap is critical. Without it, Claude will chase its tail on genuinely unsolvable problems."

And separately, a Stop hook that re-injects failing test output into context.

The harness already runs this exact pattern in `skills/commit/SKILL.md`:

- Execute the task (staging + pre-commit hooks).
- Run verification (`code-reviewer` agent + `.harness-state/commit-*.yml` receipt with `verification.results` — `skills/commit/SKILL.md:118, 207`).
- Bounded auto-fix (documented in the commit ritual; part of the run-loop's `implement → exit gate → code-review → bounded auto-fix` gate — `skills/run-loop/SKILL.md:11`).
- Attempt cap (`skills/_shared/loop/` runs the loop with termination caps).

What the harness does **not** have: a lean, portable "wrap any task in verification" skill decoupled from `.harness-state/` receipts. Anthropic's proposed shape is smaller than `/commit`, smaller than `/run-loop`, and doesn't presume the harness's plan.md wave grammar.

### Concrete change

**Only if a downstream repo asks for it.** The extraction would be:

- New skill at `skills/verify/SKILL.md` (or similar name — avoid `/loop`, that's Anthropic's) with the Execute → Verify → Fix → Repeat body from Anthropic's post.
- Attempt-cap knob (5 by default) as a skill argument.
- Verification command as a skill argument (`--verify 'npm test'`, `--verify 'bun run build'`, …).
- **No receipt writing.** This is the whole point — the extracted skill is receipt-free so it runs on projects that don't ship `.harness-state/`.

**Do NOT** rewrite `/commit` on top of the extracted skill unless the maintainer wants that refactor separately. `/commit` earns its receipt-shaped-verification because commits are the harness's atomic unit; a distributable verify-loop skill has a different job.

### Expected payoff

Portable pre-commit / pre-PR verification skill for projects that install the harness but don't want the full `.harness-state/` machinery. Also serves as a place to encode the "attempt cap is critical" lesson explicitly.

`scope: speculative` — no downstream repo has asked for this today. Anthropic's post is the first-party version of the pattern; extracting matters mostly if a consumer of the harness needs the small version.

**Verify before applying:** `find skills/ -type d -name 'verify*' -o -name 'verification*'` returns nothing. `grep -rn 'verification loop\|verify-loop' skills/` outside of `run-loop` and `_shared/loop/` returns nothing. If either surfaces, this suggestion is redundant.

**Recommended verdict:** defer until a consumer project of the harness explicitly asks for a portable pre-commit verification skill that doesn't ship with `.harness-state/` machinery.
**Status:** PENDING — awaiting triage in PR review

### Why it's relevant

> "Name chosen over `/loop` — that is the Anthropic interval-scheduler built-in. `/run-loop` is consistent with `/run-wave`."

Anyone reading the current disambiguation line might now expect `/run-loop` to be Anthropic's `/loop` renamed, when the real distinction is: `/loop` iterates one task; `/run-loop` drains many.

### Concrete change
