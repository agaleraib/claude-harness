## 1. Cross-link Anthropic's canonical loop taxonomy from the harness's loop protocol

**Source:** [Loop engineering: Getting started with loops — claude.com/blog, 2026-06-30](https://claude.com/blog/getting-started-with-loops). Companion coverage: [The Anthropic leader who built Claude Code says he ditched prompting — now he just writes loops (The New Stack)](https://thenewstack.io/loop-engineering/).

### Why it's relevant
Anthropic's Claude Code team has now published a canonical name and taxonomy for the exact pattern this harness implements as `/run-loop`. The post categorises "loops" — an agent repeating cycles until a stop condition — by trigger, stop condition, and Claude Code primitive:

- **Turn-based (agentic)** — triggered by a user prompt; Claude decides when it's done or needs context. (Corresponds to a plain Claude Code session.)
- **Goal-based** — triggered manually; stops when a goal is met or a max-turn cap fires; an evaluator model checks the stop condition every attempt. (Corresponds to this harness's `/run-loop` per-item gate + termination cap.)
- **Time-based (scheduled)** — triggered by an event or schedule with no human in real time; each task exits when its goal is met; routine runs until turned off. (Corresponds to the `/loop` built-in Anthropic slash command already noted in `skills/run-loop/SKILL.md`.)
- **Proactive** — an agent decides itself when to fire based on observed state. (No harness equivalent today.)

The harness has been shipping this pattern for months but predates the canonical vocabulary. `grep -rn "loop engineering\|getting-started-with-loops\|turn-based\|goal-based\|time-based.*loop" AGENTS.md skills/run-loop/SKILL.md` returns nothing today.

### Concrete change
**Two-line vocab map appended to `AGENTS.md` §"Loop protocol"** (immediately after the paragraph that introduces the loop as the third execution lane), and a matching **one-line reference** in `skills/run-loop/SKILL.md`.

Example patch to `AGENTS.md`:

```diff
 The loop reuses the wave lane's machinery, it does not replace it: …
+
+**Vocabulary map (Anthropic, [Loop engineering, 2026-06-30](https://claude.com/blog/getting-started-with-loops)):**
+`/run-loop` implements a **goal-based loop** — manually triggered, per-item gate + max-turn cap as the evaluator, drains a work source (plan.md waves or `ready-for-agent` gh issues) to termination. Anthropic's other named types — **turn-based** (a plain Claude Code session), **time-based** (their `/loop` built-in — the reason this harness named its skill `/run-loop`, see `skills/run-loop/SKILL.md`), and **proactive** (agent decides when to fire) — are not implemented by this repo.
```

Example patch to `skills/run-loop/SKILL.md`:

```diff
 Name chosen over `/loop` — that is the Anthropic interval-scheduler built-in. `/run-loop` is consistent with `/run-wave`.
+
+In Anthropic's [loop taxonomy](https://claude.com/blog/getting-started-with-loops), `/run-loop` is a **goal-based loop**: manually triggered; stops when the source drains or a termination cap fires; each item's mechanical gate is the evaluator. Anthropic's `/loop` is the **time-based** variant.
```

### Expected payoff
Aligns the harness's terminology with Anthropic's canonical vocabulary before the divergence becomes a friction point (searches, onboarding docs, future skill authors). Zero code change; two-line doc edit. Also seats `/run-loop` correctly against Anthropic's own `/loop` primitive so a reader doesn't have to reconstruct the naming rationale from `AGENTS.md`.

## 2. Adopt Thariq's "Finding your unknowns" techniques into `spec-planner` / procedures

**Source:** [A field guide to Claude Fable 5: Finding your unknowns — claude.com/blog, 2026-07-03](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns) by Thariq Shihipar (Anthropic Claude Code team). Community distillation showing the eight techniques as installable skills: [Neeeophytee/finding-unknowns-skills](https://github.com/Neeeophytee/finding-unknowns-skills), [GreatMark/fable-field-guide-skills](https://github.com/GreatMark/fable-field-guide-skills).

### Why it's relevant
The field guide names an explicit failure mode ("map vs territory — unknowns are what fill the gap between the prompt and the codebase") and offers eight concrete techniques Anthropic's own Claude Code engineers use, split across pre-implementation, during, and post:

| # | Technique | Stage | One-line purpose |
|---|-----------|-------|------------------|
| 1 | `blindspot-pass` | pre | Surface unknown unknowns in an unfamiliar area, then help you prompt better |
| 2 | `brainstorm-prototypes` | pre | Throwaway variations you can react to, for taste you can't verbalize |
| 3 | `interview-me` | pre | One question at a time, architecture-changing questions first |
| 4 | `reference-hunt` | pre | Use working source code as the spec, even across languages |
| 5 | `implementation-plan` | pre | Plan leads with the decisions most likely to change |
| 6 | `implementation-notes` | during | Log every deviation from the plan so the next attempt learns |
| 7 | `pitch-packager` | post | Bundle spec + prototype + notes into a buy-in doc for reviewers |
| 8 | `change-quiz` | post | Comprehension quiz you must pass before you merge |

Several already overlap deliberately with harness surfaces:
- `spec-planner` (agent) = `interview-me` (#3) — discovery-based specification writer.
- `planning-loop` (skill) = `implementation-plan` (#5) — spec through adversarial review to a Codex-approved verdict.
- `commit` (skill) = the closing gate where `change-quiz` (#8) would slot in.

The overlap is intentional — Thariq is describing the same craft this harness codifies. The two techniques that don't yet have a home in this repo are **`blindspot-pass`** (before the interview) and **`change-quiz`** (before merge). `grep -rn "blindspot\|unknown unknowns\|change-quiz\|finding your unknowns" skills/ agents/ procedures/ AGENTS.md README.md` returns zero hits today.

### Concrete change
This is a design-pass suggestion, not a mechanical patch. The candidate additions are:

- **`blindspot-pass`** — a lightweight pre-`spec-planner` step (or a new field in the spec-planner discovery output) that asks Claude to *name what it doesn't know about this codebase before I answer questions*. Could live as a preface prompt in `agents/spec-planner.md`, or as a new `procedures/blindspot-pass.md` referenced by `/spec-planner` and `/planning-loop`.
- **`change-quiz`** — a gate inserted into `skills/commit/SKILL.md` after the reviewer passes: Claude generates 3–5 short-answer questions about what changed and why; the human answers before the commit lands. Cheap; catches the "I approved without reading" failure mode that the local `code-reviewer` cannot detect.

Both are candidates, not decisions. The right move is a `/spec-planner` pass that:
1. Enumerates the overlap (above) between each of the 8 techniques and existing harness surfaces.
2. For each of the two non-overlapping techniques, decides between (a) inline into an existing agent, (b) new stand-alone skill/procedure, or (c) explicit "not for this harness — reject".
3. Frames the trade-off against the harness's "keep lean; don't tell the model HOW to think" thesis (README lines 10, 23–35) — the field guide's methods are self-elicitation prompts, which is exactly the "process skill" bucket the README argues against loading at startup. Only ones that stay dormant unless invoked survive that thesis.

### Expected payoff
If any technique lands, it's the highest-leverage kind of addition — first-party Anthropic engineer methodology from someone who works on Claude Code, and the same craft the harness already has scaffolding for. If none lands, the design pass produces a durable "we considered and rejected these because …" record for the next time this comes up.

`grep -rn "blindspot\|unknown unknowns\|change-quiz\|a-field-guide-to-claude-fable" /home/user/claude-harness/agents/ /home/user/claude-harness/skills/ /home/user/claude-harness/procedures/ /home/user/claude-harness/AGENTS.md /home/user/claude-harness/README.md` — any hit means at least part of this has landed and this § can be re-scoped or dropped.

**Recommended verdict:** spec — 8-technique methodology from a first-party Claude Code engineer with real overlap surface; the "which two, and how" question is a design decision, not a routine patch.

## 3. Note Anthropic's Dynamic Workflows / Ultracode as the vendor-side equivalent of `/run-loop` + `/run-wave`

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Companion coverage: [Anthropic Explains How Claude Builds Its Own Execution Harnesses (InfoQ, 2026-06)](https://www.infoq.com/news/2026/06/claude-code-harnesses/); [Ships Claude Opus 4.8 Alongside Dynamic Workflows and Cheaper Fast Mode, With Workflows Capped at 1,000 Subagents (MarkTechPost, 2026-05-28)](https://www.marktechpost.com/2026/05/28/anthropic-ships-claude-opus-4-8-alongside-dynamic-workflows-and-cheaper-fast-mode-with-workflows-capped-at-1000-subagents/).

### Why it's relevant
Shipped alongside Opus 4.8: Claude writes its own custom JavaScript orchestration harness per task, then executes it — spawning subagents with `agent()`, running them concurrently with `parallel()`/`pipeline()`, assigning per-agent models and worktrees, capped at 16 concurrent / 1000 total. Triggered by the **Ultracode** keyword or a slash command; available in **Claude Code for Enterprise, Team, and Max plans**.

This is the vendor-side, per-task version of what `/run-loop` (the `_shared/loop/` TypeScript engine) and `/run-wave` (multi-agent dispatch) implement locally in this repo. Key differences:
- **Locality:** Dynamic Workflows script is generated fresh each task, runs in the Claude Code runtime; `/run-loop` reuses one durable engine and per-repo `plan.md` / `gh issues` state.
- **Plan tier:** Enterprise/Team/Max only; a solo Pro-plan user doesn't get Dynamic Workflows.
- **Governance:** Dynamic Workflows runs Anthropic-side, no `.harness-state/` receipts; `/run-loop` writes journal entries to `.harness-state/orchestrator.{log,jsonl}` and integrates with the mechanical gate + risk-proportional auto-merge.

`grep -rn "ultracode\|dynamic workflow\|a-harness-for-every-task" /home/user/claude-harness/` returns nothing outside `anthropic-reviews/`. The harness has no reason to depend on Dynamic Workflows, but the omission means a reader who's used Ultracode will assume `/run-loop` doesn't exist.

### Concrete change
**One paragraph in `AGENTS.md` (or `README.md` §"Loop protocol")** naming the relationship. Suggested text:

> Anthropic's **Dynamic Workflows** (May 2026, [claude.com/blog/a-harness-for-every-task](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)) is a Claude Code runtime feature that generates a per-task JavaScript orchestration harness — spawning subagents with `agent()`, running them concurrently with `parallel()`/`pipeline()`, capped at 16 concurrent / 1000 total, triggered by the `Ultracode` keyword. It ships on Enterprise / Team / Max plans. This harness's `/run-loop` and `/run-wave` implement the same pattern durably (per-repo `plan.md` / `gh issues` state, `.harness-state/` receipts, deterministic resume) and are usable on any plan. Choose Dynamic Workflows when your task is a one-off many-subagent fan-out and you're on a plan that includes it; choose `/run-loop` / `/run-wave` when you want durable, resumable, receipt-audited multi-session work.

Also worth a one-line **Reference** entry.

### Expected payoff
Same failure mode `/security-review` and `/ultrareview` created: a reader familiar with the vendor primitive assumes there isn't a harness equivalent. One paragraph removes the ambiguity. No code change; parks the migration question (should `/run-loop` compose Dynamic Workflows internally on plans that have it?) as an explicit deferral, not a silent gap.

### Verify before applying
`grep -rn "ultracode\|dynamic workflow\|a-harness-for-every-task" /home/user/claude-harness/AGENTS.md /home/user/claude-harness/README.md /home/user/claude-harness/skills/run-loop/SKILL.md /home/user/claude-harness/skills/run-wave/SKILL.md` — if any file already names the vendor primitive, this § is redundant.

## 6. Wire `/session-end` (or a follow-up `/publish-summary`) to emit a Claude Code Artifact URL

**Source:** [Claude Code now supports artifacts — claude.com/blog, 2026-06-18](https://claude.com/blog/artifacts-in-claude-code). Documentation: [Share session output as artifacts — code.claude.com/docs/en/artifacts](https://code.claude.com/docs/en/artifacts).

### Why it's relevant
Claude Code can now capture a session's work as an **Artifact** — a live, shareable web page at a stable URL that updates in-place as the session works and versions on every publish. Anthropic's own use-case list: PR walkthroughs, system explainers, dashboards, release checklists, incident pages, license audits, security findings, architecture diagrams, weekly shipped-work reports.

This overlaps with the harness's `session-end` ritual (which today writes `.harness-state/last_exit.md` + calls `/project-tracker`) and the `/harness-status` cross-repo scanner (which today renders locally). An Artifact URL would be a natural extension: "today's session output as a shareable page" for the maintainer's phone-away review, or "this week's shipped work" for a stakeholder ping.

### Why defer, not apply today
- **Plan gate.** The beta launched Team/Enterprise-plan only (`code.claude.com/docs/en/artifacts` beta gate as of 2026-06-18). A solo Pro-plan maintainer can't publish. The harness's default is solo/Pro.
- **Consumer-project trigger.** If a consumer project already on Team/Enterprise wants a `/publish-summary` skill, that's the moment to design it — not before.
- **`session-end` today is receipts-first, human-review-second.** Artifacts optimize for "shareable public page." Different audience.

### Concrete change (when the plan gate opens or a consumer project asks)
A candidate new skill `/publish-summary` (or a flag on `/session-end`) that:
1. Reads `.harness-state/last_exit.md` + `today_goal.md` + `parking_lot.md` diffs since the previous session-end.
