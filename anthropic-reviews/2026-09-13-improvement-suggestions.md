## 1. Integrate Claude Code's Workflow tool (dynamic workflows / `ultracode`) into the orchestrator + `/run-wave` dispatch surface

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) by Thariq Shihipar and Sid Bidasaria, plus this session's system-prompt evidence for the shipped **`Workflow`** tool (with the `workflow-authoring` skill, the `<<autonomous-loop>>` / `<<autonomous-loop-dynamic>>` sentinels, and the **`ultracode`** opt-in keyword that gates multi-agent orchestration).

### Why it's relevant
The harness already ships a hand-written orchestrator (`/.claude/agents/orchestrator.md`, 384 lines) that reads a spec, routes tasks across opus/sonnet/haiku, and dispatches sub-agents — and it ships `/run-wave` (`skills/run-wave/SKILL.md`) which builds a **synthetic wave-spec from cherry-picked sub-tasks and hands it to the orchestrator inside a worktree** (verbatim from the skill body).

Anthropic's Workflow tool is the same shape — a script authored **at task time** that composes `agent()` / `parallel()` / `pipeline()` / `phase()` primitives, declares a `meta` block, runs in the background, and is gated behind an explicit user opt-in (the `ultracode` keyword or a saved workflow name). Where the harness's orchestrator is one prompt handling every wave, a Workflow script is bespoke per task.

The overlap raises three concrete questions that the durable state should have an answer to:

- **Does `/run-wave` still make sense once the Workflow tool exists?** The harness's answer is probably yes — `/run-wave` enforces the plan.md/spec.md grammar (Wave/Phase/Task/Feature ladder) that the Workflow tool has no opinion on — but nobody has written that down.
- **Should `orchestrator.md` be *rewritten* as a Workflow script** (author `meta.name = 'orchestrator'`, use `pipeline()` for phase ordering, `parallel()` for task fan-out) rather than kept as a prose agent that dispatches sub-agents by hand? The Workflow API's `agent(prompt, {label, phase, schema})` is a stricter contract than the current free-form dispatch, and the runtime handles the isolation/timeout/cache-resume plumbing that `orchestrator.md` currently reinvents in prose.
- **Where does the `ultracode` opt-in fit?** The harness has no place to declare "this wave earned the multi-agent budget" — but that's exactly what the Wave-vs-Micro split in `docs/plan.md` and `/micro` already encode informally. The Workflow tool ships an explicit gate; the harness should decide whether `/run-wave` implicitly grants it or whether the operator has to type it.

None of these are patch-shaped questions. They are **spec-shaped**: which of the harness's dispatch layers survives, which folds into Workflow scripts, and how the plan.md/spec.md grammar propagates into a Workflow's `meta.phases` / labels.

Today's repo has **zero mention** of the Workflow tool, `ultracode`, `<<autonomous-loop-dynamic>>`, or dynamic workflows anywhere:

```
$ grep -rn "workflow-authoring\|ultracode\|<<autonomous-loop\|Workflow tool" \
    .claude/ skills/ AGENTS.md CLAUDE.md README.md 2>/dev/null
# (no output)
```

### What the spec pass needs to cover
1. **Boundary decision.** For a Wave N run:
   - Path A — the harness keeps `/run-wave` as-is, and the orchestrator agent stays a prose dispatcher; the Workflow tool is used only when the operator says `ultracode` and always outside `/run-wave`.
   - Path B — `/run-wave` emits a Workflow script whose `meta.phases` mirrors the spec's `Phase 1..n`, and `orchestrator.md` shrinks to a one-liner that says "author a Workflow script from the wave-spec".
   - Path C — hybrid: `/run-wave` stays, but a new `/run-wave-workflow` (or a `--workflow` flag) opts into Path B.
2. **Grammar mapping.** How the Wave/Phase/Task ladder from AGENTS.md maps onto `meta.phases: [{title, detail?}]` and `agent(prompt, {label, phase})`. The harness's Feature ids (`F-0xx`) should probably land in agent `label`s.
3. **State propagation.** Workflow scripts run in the background and cache resumed agent calls by `(prompt, opts)`. The harness's receipts (`.harness-state/<command>-<wave-id>-<ts>.yml`) need a story for capturing which Workflow run served which wave, and how a re-dispatched Workflow interacts with the receipt schema.
4. **Ultracode gating.** Whether `/run-wave` counts as pre-declared opt-in (the operator typed a wave number, not `ultracode`) or whether the skill has to echo the ultracode requirement back to the operator.
5. **Cost telemetry.** Workflow scripts fan out — the harness's existing `model.effort_cost_multiplier: {}` slot in `.harness-profile` was reserved for a future `/tokens` accounting; a Workflow-shaped orchestrator makes that non-optional.

### Expected payoff
Two possible payoffs, and the spec chooses:

- **Small.** A `/run-wave-workflow` variant lets the operator get Anthropic's built-in isolation/parallel/verify plumbing on demand, without disturbing today's `/run-wave` flow. The prose orchestrator survives.
- **Large.** `orchestrator.md` shrinks from 384 lines to a one-liner ("author and invoke a Workflow script whose meta.phases mirrors this wave's spec phases"). The harness offloads worktree/isolation/timeout/cache-resume to the shipped Workflow runtime and stops maintaining a prose reinvention of it.

Either payoff is real. The spec pass decides which one the harness commits to.

**Verify before applying:**
1. `grep -rn "workflow-authoring\|ultracode\|<<autonomous-loop\|meta.phases" .claude/ skills/ AGENTS.md CLAUDE.md README.md` — if any of these terms now appear in-repo, someone has begun the integration and this § should be updated to reference their work rather than treated as green-field.
2. Read `docs/specs/` for any spec whose title mentions "workflow", "ultracode", or "dynamic dispatch" — if one exists, the spec pass has already begun; roll the § forward into a review of that spec rather than starting from zero.
3. Re-read the current `Workflow` tool schema from this session's environment (search for `Workflow` in the tool list) before writing the spec — the API surface (`agent`/`parallel`/`pipeline`/`phase`/`meta`) may have moved between June 2 and today, and the design must target the current shape.
4. Confirm the `ultracode` keyword is still the opt-in path (not a different keyword) by reading the Workflow tool's description block.

**Recommended verdict:** spec — the change is real and material, but it touches the load-bearing `orchestrator.md` + `/run-wave` axis and needs a design pass through `/spec-planner` before any patch. Path A/B/C above is the exact question the spec answers.

## 2. Audit `CLAUDE.md` + `AGENTS.md` + high-line-count agent prompts against the "judgment over rules" rewrite Anthropic used on Claude Code's own prompt

**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) by Thariq Shihipar. Anthropic engineers removed **over 80%** of Claude Code's system prompt for Claude Opus 5, Fable 5, and Sonnet 5 with **no measurable coding-eval loss**. The article documents the shift: from *rules* (`"default to writing no comments"`, `"never write multi-paragraph docstrings"`, `"do not create planning documents unless asked"`) to *judgment* (`"write code that reads like the surrounding code: match its comment density, naming, and idiom"`), plus a broader push toward progressive disclosure, expressive tool interfaces, and rich references (rubrics, test suites, HTML artifacts) over front-loaded markdown.

### Why it's relevant
The harness's static prompt surface is exactly the shape of prompt the post targets:

```
$ wc -l CLAUDE.md AGENTS.md .claude/agents/*.md
     35 CLAUDE.md
    131 AGENTS.md
    104 .claude/agents/code-reviewer.md
     69 .claude/agents/generator.md
    384 .claude/agents/orchestrator.md
    118 .claude/agents/project-tracker.md
    399 .claude/agents/spec-planner.md
    111 .claude/agents/ui-evaluator.md
   1351 total
```

Sampling AGENTS.md's `## What to avoid` section shows the classic rule-first shape the post argues against:

- `Don't git add -A or git add .` — a rule
- `Don't merge feature branches without --no-ff` — a rule
- `Don't write durable state outside the protocol artifacts above` — a rule
- `Don't invent state when inputs are missing — stop and surface` — a rule
- `Don't bypass the receipt schema` — a rule
- `Don't bake dynamic content into static prompt files` — a rule *plus* a citation of an Anthropic post, which is the strongest form and probably survives.

Some of these are load-bearing (`Don't invent state`, `Don't bypass the receipt schema`) — they encode invariants a Claude-5 model may still need told, because they name **specific machine-readable contracts** the model can't infer. Others are *general engineering hygiene* (`--no-ff`, `git add -A`) that a Claude-5 model may already know without being told.

The post is not a directive to delete rules — it's a directive to **stop paying to say what the model would do anyway**, and to reserve the static prompt for the invariants the model **cannot** infer. That's the exact shape of audit this repo needs, and it's *the harness's job to do it well* since it ships CLAUDE.md/AGENTS.md to every consumer project via `setup-harness`.

The audit is one pass; the rewrite is the follow-up.

### Concrete change (audit-shaped, not a diff)

**Step 1 — enumerate every rule.** For each of `CLAUDE.md`, `AGENTS.md`, `.claude/agents/*.md`, and every `skills/*/SKILL.md`, list every imperative line (patterns: `^-\s*Don't`, `^-\s*Never`, `^\d+\.\s*Never`, `MUST NOT`, `Always`, `NEVER`, `IMPORTANT`, `CRITICAL`). Expect ~150-300 hits across the surface.

**Step 2 — classify each into one of four bins.**

- **KEEP: names a contract the model cannot infer.** Example: `Don't bypass the receipt schema. Adapter divergence on receipt shape breaks cross-tool replay.` The receipt schema is a machine-readable artifact under `docs/protocol/receipt-schema.md`; a Claude-5 model has no way to know its shape from priors.
- **KEEP but soften from rule to judgment.** Example: `Don't merge feature branches without --no-ff — it loses history.` → could become `Match the repo's own merge convention (see recent merges); the harness itself uses --no-ff to preserve wave boundaries.` The reference is still there; the rule is replaced with a pointer at how to answer the question from priors + the repo.
- **DROP: general engineering hygiene a Claude-5 model already knows.** Example: `Don't git add -A or git add .` — Claude Code's own system prompt (visible in this session) already covers this at length. Duplicating it in AGENTS.md costs tokens on every session start for no measurable gain.
- **DEFER: touches a load-bearing skill body or agent prompt.** Anything inside `spec-planner.md` or `orchestrator.md` — those are the two 380+-line prompts where a wrong deletion cascades. Audit-only in this pass; a follow-up spec decides what to change.

**Step 3 — produce a **numbered, per-file audit table** as a new file `docs/audits/2026-09-<slug>-context-engineering-audit.md`**. One row per imperative line, with source file:line, verbatim text, verdict (`KEEP / SOFTEN / DROP / DEFER`), and a one-sentence reason. **No source-file edits in this pass.** The maintainer reads the table, sanity-checks the classification, and lands the DROP/SOFTEN rows in follow-up commits.

**Step 4 (optional, only if the audit surfaces >20 DROP-eligible rules).** Draft the actual diffs in a second pass. Each DROP is one-line delete; each SOFTEN is one-line rewrite. Keep the audit table in `docs/audits/` as the durable record of *why* each line was changed — this is the artifact that survives when someone six months from now asks "why did we remove the `--no-ff` rule?".

### Expected payoff
The `AGENTS.md` file is read by every consumer project's session-start (via the symlink chain). Cutting even 20-30% of its line count trims that many tokens off every session's opening context, on every project that installs this harness. More importantly, it moves the harness's own posture in line with Anthropic's demonstrated finding — the shipped Claude-5 models have the judgment to bridge specific gaps if told what the contract *is* rather than told 20 rules against paths that break it.

**Scope: speculative** — flagged because the audit is speculative on *magnitude*: it might surface 5 DROP-eligible rules (small win, still worth doing) or 60 (significant token savings and a much cleaner AGENTS.md). The audit itself is bounded (one pass over ~1,300 lines, one file produced); the follow-up rewrite is where the risk lives, and that gets its own review.

**Verify before applying:**
1. `wc -l CLAUDE.md AGENTS.md .claude/agents/*.md` — confirm the surface is still in the 1,300-1,400-line range. If it's already dropped substantially (say <900 total), someone has done a partial audit and this § should reference their work rather than start from zero.
2. `ls docs/audits/ 2>/dev/null | grep -i "context-engineering\|prompt-audit"` — if an audit file already exists with a similar slug, roll this § into a review of that audit rather than commissioning a new one.
3. Confirm the harness's primary/fallback pins are still on the Claude-5 generation (or Opus-4.7, which the post explicitly excludes from the "80% cut" finding — the empirical justification is *specifically* about Claude-5 models). If pins are still Opus-4.7 primary, note in the audit's introduction that the harness serves Opus-4.7 today and the DROP-eligibility bar is stricter (soften instead of drop when in doubt).
4. Re-read [the post](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) itself before starting the audit — this § summarizes the post's argument but the classification bins should be anchored in the post's exact language, not the summary here.

**Recommended verdict:** apply (scope: speculative) — the audit is bounded and produces a durable artifact (`docs/audits/2026-09-<slug>-context-engineering-audit.md`) even if the follow-up rewrite never lands. Marked *speculative* because the payoff scales with what the audit surfaces, and the follow-up rewrite is where the real work is. Best done in one focused session, not squeezed into a `/commit` shoulder-touch.
