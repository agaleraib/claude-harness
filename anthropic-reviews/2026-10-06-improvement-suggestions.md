## 2. Note Claude Code mods as a new extensibility layer in README "Why Not Superpowers"

**Source:** [Customize Claude Code with mods — claude.com/blog, 2026-10-01](https://claude.com/blog/claude-code-mods). Companion: [Claude Code 2.1.287 release notes (2026-10-01) — `claude plugin validate` lists each hook a mod registers at a gating site, and the built-in `cc-plugin-you-should-know@builtin` ships](https://code.claude.com/docs/en/changelog).

### Why it's relevant
Mods are a **new, deeper extensibility layer** than this harness has previously had to reason about. Where hooks fire-and-observe, and skills are prose Claude reads at trigger time, a mod is a **TypeScript function that intercepts Claude Code's internal events**: it can rewrite prompts before the model sees them, block/rewrite/retry tool calls, approve or deny permission requests, redact secrets from tool output, and draw new UI in the terminal or desktop app. Mods ship inside plugins; multiple mods on the same event compose in load order.

For this harness, the question isn't "should we write mods" (the methodology stance in `README.md` section "Why Not Superpowers / Heavy Skill Systems" rejects deep behavior-modification layers for a reason) — the question is "does the next contributor know we **deliberately don't**, and that a mod isn't just a bigger skill?" The current README (`:25` "Research and production experience show that heavy instruction systems degrade Opus 4.7 performance", `:32` "Vendor primitives keep absorbing harness territory") lists prior Anthropic-ships-that-absorb-harness patterns (`/security-review`, Claude Security). Mods belong on that same list as **a surface the harness could absorb into, but isn't**.

### Concrete change

**`README.md`** — append one bullet to the "Why Not Superpowers / Heavy Skill Systems" evidence list (currently around line 32, the vendor-primitives bullet). Keep the bullet short:

```diff
 - **System-prompt regressions are subtle and slow to detect**: Anthropic's own [April 23 postmortem](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues) traced a month-long Claude Code quality drop to three harness-layer changes — including a 25-word verbosity cap that knocked 3% off internal coding evals. Confirms first-party that adding instructions to the harness can degrade behavior.
+- **Mods now cover deep behavior modification**: Anthropic shipped [Claude Code mods on 2026-10-01](https://claude.com/blog/claude-code-mods) — TypeScript functions that rewrite prompts, replace built-ins, intercept tool calls, and draw UI. The harness intentionally stays at the methodology layer (skills + agents + rubrics); mods are the right surface for behavior rewrites. If a future "harness feature" starts to look like "intercept Claude's tool calls and rewrite them," ship it as a mod inside a plugin, not as a skill in this repo.
```

### Expected payoff
- Prevents the next contributor from reinventing `/commit`'s pre-push gate as a mod when a skill already covers it.
- Keeps the "lean harness, vendor primitives absorb" narrative current with 2026-10-01 reality.
- No code change; documentation-only.

**Recommended verdict:** defer until the harness needs behavior-modification — bookkeeping note today; low urgency until a contributor proposes "let's write a mod for this harness." scope: speculative (there is no concrete harness pain the mod extensibility would solve today; the note is defensive).

## 3. Package the harness as a plugin on the Claude Marketplace

**Source:**
- [Build plugins for Claude — claude.com/blog, 2026-09-25](https://claude.com/blog/build-plugins-for-claude) — plugin directory submission portal + auto-validation + usage analytics
- [Claude Marketplace: one place to discover plugins, agents, and services from our partners — claude.com/blog, 2026-09-23](https://claude.com/blog/claude-marketplace) — 2,000+ connectors/plugins, built on MCP + Agent Skills

### Why it's relevant
The harness currently distributes via `setup-harness` and a symlink layer that puts the repo's `skills/` into `~/.claude/skills/`. This is a solo-dev-friendly workflow: changes land in the source repo and are live on the next session. The costs are:

- No install analytics (maintainer can't tell if `setup-harness` has been run on more than one machine)
- No validation step at install time (a broken skill ships live until a session surfaces it)
- No versioning (the repo's `master` HEAD is the live config)
- No discovery (users have to be told the repo exists)

Anthropic's plugin + marketplace stack now handles all four for free. Plugins can bundle "LSPs, commands, hooks, and agents" (per the 2026-09-25 post, Claude Code–specific) and ship through the marketplace with per-surface install counts.

**Why defer rather than apply:** the harness is explicitly solo-maintained (`.harness-profile: audience.size_estimate: "1"`; `anthropic-reviews/README.md`: "this repo is solo-maintained (`team.size: solo`)"). The marketplace solves distribution problems the solo workflow doesn't have. The plugin wrapping also complicates the current `skills/ → ~/.claude/skills/` symlink that lets the maintainer edit live code — a published plugin is immutable per version, and would push edit-reload cycles through a publish step.

### Concrete change (deferred)
Pre-work when the trigger fires (second user, drift-detector need, or distribution pain):

1. Define `skills/_shared/plugin-manifest.yaml` with the plugin shape (skills to include, agents, hooks, versioning).
2. Add `/package-plugin` skill that builds a `.plugin.tar.gz` from `skills/` + `.claude/agents/` + `hooks/`.
3. Update `setup-harness` to offer two install modes: **dev** (current symlink) and **plugin** (`claude plugin install …` from the marketplace or a GitHub release).
4. Submit to the directory via the submission portal.

### Expected payoff
- Discoverability: harness becomes findable via `/plugin` → Discover without the user knowing the repo URL.
- Install analytics: maintainer learns if anyone else has installed it.
- Version pinning: consumers can lock a known-good harness version instead of tracking `master`.
- Auto-validation: broken skills surface at submission instead of on first session trigger.

## 4. Render project-tracker session summary as a Claude Code artifact

**Source:** [Claude Code now supports artifacts — claude.com/blog, 2026-06-18](https://claude.com/blog/artifacts-in-claude-code)

### Why it's relevant
The 2026-06-18 announcement positions artifacts as the Claude Code–native way to turn a coding session into a "live, shareable visual page" at a stable URL (PR walkthroughs, dashboards, incident timelines). The harness's `project-tracker` agent (`.claude/agents/project-tracker.md`) already captures session state (files touched, specs, decisions) and persists it to Second Brain. Those two capabilities are the same shape: capture session work, render it for later consumption. The missing piece between them is "render the Second Brain state as a human-readable page that a reviewer can open."

For a solo maintainer, this doesn't matter — the maintainer is the only reader of their own project-tracker output, and the terminal view suffices. But if the harness ever lands in a PR-review context where a reviewer wants to see "what did this session actually touch?", an artifact is the right answer: no bespoke dashboard, no infrastructure, stable URL, auto-refresh on update.

### Concrete change (deferred — needs a design pass)
Pre-work when the trigger fires (first PR review that would benefit, or team.size > 1):

1. Extend `project-tracker.md`'s "UPDATE mode" to emit an Artifact snapshot alongside the Second Brain save.
2. Decide the page shape: diff summary + spec links + decision log + "what still remains" checklist.
3. Add `/project-tracker --artifact` flag to force artifact emission on save (default: no artifact for solo mode).

### Expected payoff
- Zero-infra PR walkthrough: a reviewer opens the artifact URL and sees the session's work without crawling the branch.
- Stable URL means it can be pasted into a PR description or Slack thread.
- Auto-refresh (per the 2026-06-18 post) means the page tracks follow-up work without the reviewer re-fetching.
