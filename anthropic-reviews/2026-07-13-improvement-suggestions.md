## 1. Bump `.harness-profile` model pins from Opus 4.7 / Sonnet 4.6 to Opus 4.8 / Sonnet 5

**Source:** [Choosing a Claude model and effort level in Claude Code — claude.com/blog, 2026-07-07](https://claude.com/blog/claude-model-and-effort-level-in-claude-code). Companion CLI docs: [`code.claude.com/docs/en/model-config`](https://code.claude.com/docs/en/model-config), specifically the "Available models" table which now resolves `opus → claude-opus-4-8` and `sonnet → claude-sonnet-5` on the Anthropic API. Timeline: **Opus 4.8** shipped 2026-05-25 as the default on Max, Team Premium, Enterprise pay-as-you-go, and API accounts ([Week 22 digest](https://code.claude.com/docs/en/whats-new/2026-w22), requires v2.1.154); **Sonnet 5** shipped 2026-06-29 as the default on Pro, Team Standard, and Enterprise subscription seats with a native 1M-token context window ([Week 27 digest](https://code.claude.com/docs/en/whats-new/2026-w27), requires v2.1.197).

### Why it's relevant
`.harness-profile:29-32` currently reads:

```yaml
model:
  primary: claude-opus-4-7
  fallback: claude-sonnet-4-6
  effort_default: xhigh   # derived from stakes.level: medium
  effort_cost_multiplier: {}
```

Both `primary` and `fallback` name model versions that Anthropic has now demoted from the recommended default on this account tier. On the Anthropic API today (per `model-config` docs quoted above) `--model opus` picks Opus 4.8, `--model sonnet` picks Sonnet 5; the harness's pinned strings are one and two generations behind respectively. This is not "breakage" — the pinned strings still resolve to real models — but the pin's original comment (`.harness-profile:26` — *"Aligned with Anthropic's 2026-04-23 postmortem (Claude Code defaults Opus-4.7 users to xhigh)"*) is now stale in one direction (postmortem is old news) and misleading in another (an `xhigh` default was carried forward and expanded to Opus 4.8, so the derivation still holds).

The harness explicitly documents the pinning-vs-alias trade-off. `docs/specs/2026-04-19-harness-model-pin-and-effort-routing.md` argues for **fully-pinned model IDs** (not aliases) so a re-run of a wave in six months uses the same model. That reasoning is still correct — the fix is not to switch to aliases, it's to bump the pins to the current recommended pair.

### Concrete change

Single-file edit to `.harness-profile`:

```diff
 # `.harness-profile` schema comment block unchanged.
-# Aligned with Anthropic's 2026-04-23 postmortem (Claude Code defaults Opus-4.7 users to xhigh).
+# Aligned with Anthropic's 2026-04-23 postmortem (Claude Code defaults Opus-4.7 users to xhigh).
+# 2026-07-13: model pins refreshed to the current defaults on this plan tier — Opus 4.8
+# (default from 2026-05-25 on Max/Team-Premium/Enterprise/API, requires v2.1.154) and
+# Sonnet 5 (default from 2026-06-29 on Pro/Team-Standard/Enterprise, native 1M context,
+# requires v2.1.197). effort_default: xhigh is unchanged — Opus 4.8 defaults to `high`
+# effort with `/effort xhigh` recommended for the hardest tasks, so the pinned xhigh
+# derivation still matches Anthropic's guidance.
 model:
-  primary: claude-opus-4-7
-  fallback: claude-sonnet-4-6
+  primary: claude-opus-4-8
+  fallback: claude-sonnet-5
   effort_default: xhigh   # derived from stakes.level: medium
   effort_cost_multiplier: {}   # optional; keys ∈ {low, medium, high, xhigh} → numeric (reserved for /tokens)
```

**Do NOT switch to aliases.** The v1 spec (`docs/specs/2026-04-19-harness-model-pin-and-effort-routing.md`) intentionally pins for reproducibility; aliases move under the maintainer's feet on Anthropic's release cadence, which would break the reason the profile carries pins in the first place. The bump preserves that shape.

**Do NOT auto-add Fable 5** to the pin set. Fable 5 is not the default model on any plan tier (per the CLI docs quoted above); it's opt-in via `/model fable`. Adding it as a `primary` pin would silently escalate cost on every dispatch. The right time to reconsider is when the orchestrator has a documented "reserved-for-hardest" tier — currently it doesn't.

### Expected payoff
Alignment. Any `harness-status` or setup-harness invocation that inspects `.harness-profile` and hands the pinned model IDs to a downstream tool (e.g. spec-planner or the orchestrator's model routing) starts using the current default pair. No behavioral surprise when a fresh contributor reads `.harness-profile` and sees a model name that matches what `claude --model opus` resolves to.

### Why this isn't a duplicate
The `2026-04-19 §1` bump was Opus 4.6 → 4.7. There has been no bump-suggestion §  since. The tracker's tail rows (`2026-05-05 §1`, `2026-05-08 §2`) touched skill-authoring guidance and evaluator patterns, not the profile schema.

## 3. Position Anthropic's Dynamic Workflows / `ultracode` alongside the harness's `run-loop`, `planning-loop`, `run-wave` orchestrations

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-05-25 (roughly)](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). CLI documentation: [`code.claude.com/docs/en/workflows`](https://code.claude.com/docs/en/workflows). The feature graduated from research preview (Week 22, 2026-05-25) to a documented product surface with an `ultracode` effort tier by 2026-07 (v2.1.203, per Week 28 digest). Six named orchestration patterns are called out by Anthropic: classify-and-act, fan-out-and-synthesize, adversarial verify, generate-and-filter, tournament, loop-until-done. The bundled `/deep-research` workflow ships as the reference implementation; user-authored workflows save to `.claude/workflows/` (project) or `~/.claude/workflows/` (user).

### Why it's relevant
The harness carries **three separate orchestration mechanisms** today, each with its own engine:

- **`/run-loop`** — TypeScript engine at `skills/_shared/loop/`, spawns wave/issue workers, adversarial review dispatch, safety denylist (installed via `PreToolUse` hook). Discovery via `docs/waves/wave18-` through `wave25-`.
- **`/planning-loop`** — Bash + skill body at `skills/planning-loop/SKILL.md`; drives a spec through Codex `/codex:adversarial-review` in ≤3 rounds. Two modes (FRESH/REVISE).
- **`/run-wave`** — Orchestrator agent at `.claude/agents/orchestrator.md` (~380 lines of routing rules, including a `low → medium → high → xhigh → promote-model` rung matrix).

All three implement one or more of Anthropic's six named patterns. Explicit mapping:

| Harness surface | Anthropic pattern name | How the harness expresses it |
|---|---|---|
| `run-wave` orchestrator's model+effort routing | classify-and-act | The bullet-buckets in `.claude/agents/orchestrator.md:140-240` route each task to a `(model, effort)` tuple based on task shape; that's classify-and-act |
| `run-wave`'s per-task dispatch loop | fan-out-and-synthesize | Sequential today (one worker per task); Anthropic's pattern would fan out concurrently across tasks with an in-workflow synthesise stage. Not currently used |
| `planning-loop` FRESH+REVISE 3-round | adversarial verify + loop-until-done | Spec-planner drafts → Codex reviews → optional round-2 revision. Each round is Anthropic's adversarial-verify shape; the 3-round cap is a bounded loop-until-done |
| `run-loop` issue mode + safety denylist | loop-until-done + guardrails | Denylist is `PreToolUse` hook rather than in-workflow, but the semantics are the same as workflow-runtime tool-allowlist enforcement |
| No harness surface | tournament, generate-and-filter | Neither pattern is used today; both would be new engines |

**None of the existing harness engines run as Anthropic's `Workflow` tool.** They run in-process (planning-loop is a shell skill; run-loop is a Node.js/TypeScript engine invoked via a skill; run-wave dispatches through the orchestrator subagent). This has three consequences that the maintainer should decide on deliberately, hence the `spec` verdict:

1. **A saved `.claude/workflows/` file is a code artifact the runtime can pipeline() over.** The harness's shell-driven planning-loop cannot pipeline the 3 rounds — each round is a full new subprocess with no shared script state. Migrating planning-loop to a saved workflow would give the maintainer resumability (`/workflows → p` to resume), free progress UI (`/workflows` view with per-phase agent counts), and cross-run script edits without touching the SKILL.md body. **Cost:** rewriting the 3-round loop in JavaScript inside a `meta` block. Not obviously worth it while the shell version works, but architecturally cleaner.
2. **`ultracode` as an effort tier changes what "xhigh" means at the orchestrator level.** Today `orchestrator.md:225-262` treats `xhigh` as the top rung before promoting model. Anthropic now offers `ultracode = xhigh + auto-workflow-orchestration`. If the harness ever needs a "beyond xhigh" tier, `ultracode` is the natural target — but adopting it means every substantive task in a session becomes a workflow (per the docs), which is a very different execution model from the harness's current per-task dispatch.
3. **The `/deep-research` bundled workflow overlaps with the anthropic-reviews routine itself.** This routine (the one that produced this file) does exactly what `/deep-research` claims to do: fan out searches across sources, cross-check, filter unverified claims, synthesize a cited report. There's an obvious *"could this routine become a saved workflow?"* question here — see also 2026-05-10 §2 (Cloud Routines) which parked the migration for cost/pricing reasons. Workflows are a *different* migration target (local, script-based, not schedule-driven) and worth considering alongside the Cloud Routines question, not instead of it.

### Concrete change (spec-scope)
None this run. When/if the maintainer wants to design this:

1. Spec the boundary: which harness surfaces stay as SKILL.md-driven shell/TypeScript engines, and which convert to `.claude/workflows/` scripts. The likely candidates for conversion are `planning-loop` (small, well-scoped) and the anthropic-reviews routine (naturally fan-out-and-synthesize shaped); `run-loop` and `run-wave` probably stay because they need the safety-denylist hook that in-workflow tool-allowlists partially but not fully replace.
2. Spec the `ultracode` tier decision: does the orchestrator gain a rung above `xhigh`? If yes, what is it (`ultracode`? A dedicated `spawn-workflow` tier?), and does it displace the existing `promote-model` rung or precede it?
3. Spec whether the six Anthropic patterns get named in the orchestrator's routing prose. Naming them creates a shared vocabulary with Anthropic docs — future readers of `orchestrator.md` who arrive from Anthropic's harness post see the pattern names line up. Cost: prose refresh.
4. Reference implementation: pick **one** harness routine (probably this anthropic-reviews routine, since it's naturally fan-out-and-synthesize + already scheduled) and convert it to a saved workflow as a proof-of-concept before deciding on the bigger surfaces.

### Expected payoff (when applied)
The harness's orchestration patterns get a portable vocabulary that maps to Anthropic's documented ones, and the two overlapping migration targets (workflows for orchestration, Cloud Routines for scheduling) get evaluated together rather than in isolation.

### Why this is `spec`, not `apply` or `defer`
`apply` would demand a concrete diff, but there are five reasonable ways to structure the migration and none of them are one-file changes. `defer` would silently drop the alignment opportunity — the "does the anthropic-reviews routine become a workflow?" question is not going to answer itself. `spec` is the routine's own vocabulary for *"this needs a design pass first"* and matches the shape of the work.

**Verify before applying:**
1. `grep -rn 'ultracode\|dynamic workflow\|\.claude/workflows\|/deep-research' /home/user/claude-harness` — must return zero non-tracker hits today (2026-07-13). If it returns hits in `skills/`, `docs/specs/`, or `docs/waves/`, some prior work has landed and this § should be recut from that starting point.
2. Confirm the harness's Node.js/TypeScript engine at `skills/_shared/loop/` still fits inside the SKILL.md-driven model — if Anthropic has meanwhile shipped `.claude/workflows/` as the recommended distribution channel for exactly this kind of engine, the `spec` scope should widen to include the engine relocation.
3. Confirm `/deep-research` is still bundled with Claude Code (not a plugin) before the anthropic-reviews-as-workflow migration is scoped — if Anthropic later spins it out as an installable plugin, the reference-implementation choice may shift.

**Recommended verdict:** spec — architecturally significant; multiple reasonable shapes; single-§ diff would collapse a real design question into an implementation preference.

## 5. Cross-reference `/doctor` (`/checkup`) from `memory-prune` and the session-start memory-cap warning

**Source:** [Week 28 digest — code.claude.com/docs/en/whats-new/2026-w28](https://code.claude.com/docs/en/whats-new/2026-w28), covering `/doctor` in v2.1.205 (2026-07-06 → 2026-07-10). Quote:

> `/doctor` now diagnoses issues and can fix them, instead of printing a read-only report. It checks installation health, finds unused skills, MCP servers, and plugins versus their context cost, deduplicates local `CLAUDE.md` files against checked-in ones, proposes trimming `CLAUDE.md` content Claude could derive from the codebase, and flags slow hooks. It reports findings first and asks for confirmation before changing anything. `/checkup` is its alias.

### Why it's relevant
The harness already carries `skills/memory-prune/SKILL.md` (a Wave-11 cap-management skill for `~/.claude/memory/*.md`) and `skills/session-start/SKILL.md` fires a non-blocking warning at session start when `~/.claude/memory/FEEDBACK.md` etc. is over its 5KB / 1KB cap. Both mechanisms live at a **different layer** than `/doctor`:

| Scope | `memory-prune` | `/doctor` |
|---|---|---|
| Target | `~/.claude/memory/*.md` (harness's shared memory root) | Claude Code global env: installation health, unused skills / MCP / plugins, `CLAUDE.md` content that could be derived, slow hooks |
| Trigger | Manual (`bash skills/memory-prune/lib/prune.sh`) or session-start warning | `/doctor` in any session |
| Output | Receipt + journal in `.harness-state/` | In-session diagnostic list with per-item fix confirmation |

The two are **complementary, not competing** — `memory-prune` operates on files the harness owns; `/doctor` operates on the Claude Code environment. But a maintainer reading `memory-prune/SKILL.md` for the first time — or reading a session-start warning that says *"~/.claude/memory/FEEDBACK.md is over cap, run /memory-prune"* — has no cue that `/doctor` exists at the adjacent layer.

The consequence today: if the maintainer's real problem is *"my session is slow / my CLAUDE.md is duplicated / a plugin isn't being used"*, `memory-prune` will not help and the maintainer has to know to reach for `/doctor` from prior Claude Code experience. ## 6. "How we contain Claude across products" engineering post — no concrete change today, but note the two disclosed regressions for the security-review skill's threat model

**Source:** [How we contain Claude across products — anthropic.com/engineering, 2026-05-30](https://www.anthropic.com/engineering/how-we-contain-claude). Retrospective by Anthropic on containment vs supervision across claude.ai, Claude Code, and Cowork. Notable disclosed incidents:

1. **Mid-2025 → January 2026** — Claude Code parsed project-local configuration before the user saw the trust dialog; a malicious repo could execute code without consent. Fix: defer all parsing until after the trust prompt.
2. **February 2026** — an internal red-team exercise successfully phished an employee into running Claude Code with a malicious prompt requesting AWS credentials; Claude completed the request 24/25 times.

Both are historical regressions (fixed at the CLI level), but both belong on the threat-model list for **any harness that authors skills or ships settings.json defaults**.

### Why it's relevant
The harness ships:

- `skills/setup-harness/SKILL.md` — the entry point that installs `criteria/`, `.claude/agents/`, `CLAUDE.md`, and optionally `.mcp.json` into a target project. This is the exact code path an attacker would use to get a malicious payload in front of Claude Code on the first `setup-harness` invocation on a fresh clone.
- Bundled `/security-review` — the Claude Code built-in skill invoked from harness workflows. It reviews *code* for OWASP-style issues; it does not, today, cover *harness-install-time* attacks (malicious skill contents, malicious `.mcp.json`, malicious hook shell commands).

The two disclosed regressions map to two harness-scoped threat surfaces that the maintainer has not previously enumerated:

1. **Trust-dialog-timing attacks against the harness's install path.** `setup-harness` runs before any project-specific CLAUDE.md has been read, so the trust dialog (Claude Code's) protects the *target* project from `setup-harness`'s writes. If a fork of the harness itself is malicious, the trust dialog does not help — the maintainer's `~/.claude/harness/` root is already trusted. The mitigation is *not* a code change; it's *"never install `~/.claude/harness/` from an untrusted source"* — an operational note, not a diff.
2. **Credential-phishing via harness skills.** A skill body is prose that Claude will follow. A skill body that says *"read `~/.aws/credentials` and paste the contents"* is a valid skill. The harness's own skills don't do this today — but a compromised distribution could. The mitigation is *reviewer discipline* + `criteria/api-security-checklist.md` scope refresh to add "skill body review" as an explicit criterion.

### Why this is `defer`, not `apply`
Both mitigations are non-code:

- **The trust-dialog point** is operational advice ("don't clone the harness from an untrusted source"). It fits in `README.md` as one sentence, but shipping that sentence *without* the deeper security-review overhaul is theatre. Better to bundle the sentence with a scoped criteria refresh, and both should wait until (a) the harness gains a second contributor (currently `team.size: solo` in `.harness-profile`) or (b) `/security-review` gains a harness-install scope.
- **The credential-phishing point** requires a criteria/*.md update, which is a bigger scope than a suggestions-file § — it's arguably its own `/spec-planner` topic. Not this run.

### Concrete change (deferred)
None this run. When/if the maintainer wants to take this on:

1. Add a harness-install-time threat model to `procedures/api-security-checklist.md` covering: (a) skill-body review before shipping to `~/.claude/skills/`, (b) `.mcp.json` server review, (c) hook-command review, (d) trust-dialog assumptions when `~/.claude/harness/` is itself the target of a supply-chain attack.
2. Extend `skills/setup-harness/SKILL.md` with a "before installing on a new machine" checklist that references the above.
3. Cross-reference [How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude) in the security-review context so the disclosed regressions are on the record.

### Expected payoff (when applied)
The harness's supply-chain-attack surface gets a named threat model instead of an implicit *"we trust the source"* assumption. The two Anthropic-disclosed regressions become concrete evidence for why the model is needed.

**Verify before applying:**

**Recommended verdict:** defer until either `team.size > solo` or a triggering incident — bookkeeping today; the two disclosed regressions get placed on the durable record for the next security-review-scoped refresh; no concrete change requested in §6 itself.
