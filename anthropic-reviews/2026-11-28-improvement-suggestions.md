## 3. Map the harness's three execution lanes to Anthropic's four-category loop taxonomy

**Source:** [Loop engineering: Getting started with loops — claude.com/blog](https://claude.com/blog/getting-started-with-loops). Four categories: **turn-based** (user drives turn-by-turn), **goal-based** (`/goal` — iterate until condition met or turn cap), **time-based** (`/loop`, `/schedule` — interval + cancel/completion exit), **proactive** (events or schedules trigger, no human in real time). Quote: *"Loops that write code need loops that check it."*

### Why it's relevant

`AGENTS.md § Loop protocol` already defines three execution lanes:
- **Wave lane** (`/run-wave` → `/close-wave`) — one all-or-nothing batch, human checkpoint between waves.
- **Loop lane** (`/run-loop waves|issues`) — a stream of ready work, mechanical gate, unattended.
- **Issue lane** — subset of the loop lane that reads from `ready-for-agent` gh issues.

The mapping to Anthropic's vocabulary:
- Wave lane ≈ **goal-based** (each wave has a verifiable exit condition — the close-wave checklist).
- Loop lane ≈ **proactive** (events/queue-draining, no human in real time until a cap fires).
- `/run-loop` with no new ready items ≈ **time-based** (polls for more work).

Naming this in `AGENTS.md` saves future-you (or the next operator) the derivation. One sentence.

### Concrete change

Append one paragraph to `AGENTS.md § Loop protocol` (right before the "Work sources" sub-section, after "The reference implementation lives in …"):

```diff
 The loop is a third execution lane alongside the wave lane (`/run-wave` → `/close-wave`). Where the wave lane dispatches and merges **one** all-or-nothing batch with a human checkpoint between waves, the loop drives a **stream** of ready work — board waves or tracker issues — end-to-end behind a mechanical gate, unattended, until the source drains or a termination cap fires. It is tool-neutral: any agent that can run a per-item gate, read a work source, and merge under a precondition can implement it. The reference implementation lives in `skills/_shared/loop/` and the entry command is `run-loop` (see `WORKFLOW.md`).

+**Mapping to Anthropic's loop taxonomy** ([Loop engineering, claude.com](https://claude.com/blog/getting-started-with-loops)): the wave lane maps to **goal-based** loops (each wave has a verifiable exit — the close-wave checklist); the loop lane maps to **proactive** loops (events/queue-draining, no human in real time until a cap fires); the issue lane is the same proactive shape over a different work source. This repo's `run-loop` plays the role Anthropic's `/loop` + `/schedule` play in a Claude Code session; the difference is that `run-loop` is gated by `skills/_shared/loop/safety/denylist.ts` + `PreToolUse` hooks instead of relying on Claude Code's own auto-mode classifier.
```

## 4. Treat the `/verify` → verification-skill pattern as an available-when-needed extension, not a required convention

**Source:** [Building verification loops in Claude Code with skills — claude.com/blog, Jul 2026](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills). Pattern: encode a manual check as a `SKILL.md` with YAML frontmatter (`name`, `description`, `allowed-tools`), numbered steps, "if any step fails, Claude should fix the issue and rerun from step 1." Checks can be **embedded** (appended to the producing skill), **chained** (wrapper skill calls the original then the verifier), **standalone** (invoked deliberately), or **CI-only** (same chain in GitHub Actions).

### Why it's relevant

The harness already does this *inside* its gate mechanisms:
- `/run-loop`'s per-item gate sequence (`AGENTS.md § Loop protocol → Per-item gate sequence`) — build → test → typecheck → lint → review → merge, red-step stops.
- `/commit` invokes the local `code-reviewer` agent synchronously.
- `/close-wave` runs a wave-wide verification step before promoting the wave.

But each of these is an **inline** pattern — the check is embedded in the producing skill's body. Anthropic's post makes a case for **extracting** checks into standalone `SKILL.md` files so they can be chained from skills the author doesn't control (e.g. the built-in `/verify` skill).

**Where this would help the harness today:** Nowhere obviously — every harness-owned skill is owned-by-maintainer, so embedded is already fine.
**Where this would help in the future:** When the harness distributes skills to target projects (via `setup-harness`), those projects can't modify the harness's skill bodies in place; a chainable verifier would let each project add project-specific checks without forking the harness skill.

### Concrete change

**Do not extract today.** Instead, add one sentence to `skills/_shared/loop/README.md` (if it exists; else to `AGENTS.md § Loop protocol`) that **names the escape hatch** for the day a target project needs it:

```diff
+**Project-specific verifications.** If a `setup-harness`-installed project needs a check the harness doesn't ship — e.g. a project-specific lint rule, a performance threshold, a deploy-gate — the recommended pattern is to add a chainable verifier skill at `.claude/skills/verify-<slug>/SKILL.md` and reference it from the project's `CLAUDE.md`. See [Building verification loops with skills](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) for the chain/embed/standalone taxonomy. The harness's per-item gate (in `skills/_shared/loop/`) will run the project's verifier as part of the sequence if it's installed at session-start.
```

(This matches the harness's existing "skills symlinked OUT, not INCOMING" posture from CLAUDE.md § Skills directory layout.)

### Expected payoff

Future-proofs the harness for target-project verification without building anything today. Costs one sentence.

### Why this is `defer` and not `apply`

The post's main recommendation is to extract checks into skills. The harness doesn't have a verification-gap-driven need to do that; the per-item gate works. The one-sentence escape-hatch note is cheap but adds doc surface no one reads until they need it. **Defer until a target project actually asks for a verification hook** — at that point, add the sentence (or build the chainable verifier) as part of the real need.

**Verify before applying:**
1. `grep -rn "chainable verifier\|verification-loop\|verify-<slug>" skills/ AGENTS.md README.md` — must return nothing; if it hits, this § is stale.
2. Confirm no target project (consumer of `setup-harness`) has filed an issue asking for a verification extension point. If one has, promote to `apply`.
3. Confirm Anthropic's post URL still 200s (the Jul 2026 post is older than most of this run's window; URL stability matters).

**Recommended verdict:** defer until a verification-gap complaint from a `setup-harness` consumer — the extracted-skill pattern is architecturally sound but has no forcing function today.
