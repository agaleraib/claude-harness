## 1. Review `.harness-profile` model pin against Opus 5.5's cache improvements + forked-subagent cache inheritance

**Source:** [Coding sessions are longer and use more context. Claude Opus 5.5 is built with that in mind. — claude.com/blog, 2026-09-24](https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context). The post is the Opus 5.5 release note aimed at coding-harness authors.

### Why it's relevant
This harness's `.harness-profile` pins:

```yaml
model:
  primary: claude-opus-4-7
  fallback: claude-sonnet-4-6
  effort_default: xhigh   # derived from stakes.level: medium
```

The 2026-09-24 post reports four changes that are **direct tailwinds for the harness's existing design**:

1. **Cached-token reads are ~60% cheaper on Opus 5.5** vs Opus 5. Since this harness depends on prompt caching across every Agent-tool dispatch and across the planning-loop acceptance scanner, the cache-read line is the dominant cost.
2. **Forked subagents now inherit parent cache** instead of repaying for duplicate context. This harness heavily uses the Agent tool (Explore, Plan, code-reviewer, generator, orchestrator, ui-evaluator) — every spawn previously paid a cold-cache hit. Opus 5.5 removes that.
3. **Effort levels can be changed mid-session without resetting cache.** The harness's `effort_default: xhigh` derivation is a one-time knob today; mid-session routing (orchestrator → sonnet/haiku for sub-tasks) could become cheaper if the orchestrator could step effort down for routine turns.
4. **Opus 5.5 reaches goals in fewer turns** than Opus 5, especially on open-ended work. The planning-loop's long-horizon runs are the exact shape the post optimizes for.

The current pin is **intentional** — the inline comment at `.harness-profile:26` cites Anthropic's 2026-04-23 postmortem for the `effort_default: xhigh` derivation on Opus 4.7. So this isn't "the pin went stale" — it's "the ground has shifted; is the pin still the right call?"

### Not-a-change candidates (why this is `defer`, not `apply`)
- A model-pin switch on a dogfood repo is a maintainer-choice, not a routine-choice. The right owner is `/micro` or `/spec-planner`, not this file.
- The system prompt listing Opus 4.7 as this session's own model confirms the pin is still viable; nothing is broken.
- Model behavior shifts (Opus 5.5 is "more terse", "fewer turns") could invalidate rubric wording in `criteria/` that was tuned to 4.7 — needs an evaluation run, not a one-line pin edit.
- The forked-subagent-cache win *only* applies on Opus 5.5; a doc bullet celebrating it in README is premature while the pin is 4.7.

### Candidate concrete change (for the maintainer to evaluate, not the routine to apply)
If (and only if) the maintainer decides to bump:

```diff
 model:
-  primary: claude-opus-4-7
-  fallback: claude-sonnet-4-6
-  effort_default: xhigh   # derived from stakes.level: medium
+  primary: claude-opus-5-5
+  fallback: claude-sonnet-5-5
+  effort_default: xhigh   # derived from stakes.level: medium (Opus 5.5 keeps the xhigh default)
```

And one new bullet in README's References section (`README.md:1109+`):
```diff
+- [Coding sessions are longer and use more context — Opus 5.5](https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context) — forked-subagent cache inheritance + mid-session effort changes without cache reset; both are tailwinds for this harness's Agent-tool-heavy pattern.
```

### Expected payoff
- 60% cache-read savings compounds across every planning-loop wave and every `/run-wave` dispatch.
- Forked-subagent cache inheritance meaningfully reduces per-spawn cost for Explore/Plan/code-reviewer/generator fan-outs.
- Fewer-turns-to-goal reduces wall-clock on open-ended work.

### Risks
- Rubric drift: `criteria/*.md` entries tuned to Opus 4.7 may trigger differently on Opus 5.5 (different terseness, different failure modes). Needs at least a two-wave dogfood validation before switching master.
- Deprecation uncertainty: the post doesn't commit to a 4.7 deprecation date, so the 4.7 pin isn't *failing*; it's just leaving savings on the table.

**Verify before applying:**
1. `grep -n "claude-opus" .harness-profile README.md` — must still show `claude-opus-4-7` as the primary; if the maintainer has already bumped, this § is stale.
2. `grep -n "forked subagents.*cache\|cache.*forked" README.md` — must return nothing; if present, the README-reference half of this § is done.
3. Confirm Opus 5.5 is still the current recommended coding-session model (not yet superseded by, say, Opus 5.6 at run time) — the post URL stays authoritative but the version string might move.

**Recommended verdict:** defer — bump is maintainer-call, not routine-call. Trigger: either (a) the maintainer evaluates cache-cost / rubric-drift tradeoff and decides, or (b) Anthropic deprecates Opus 4.7 and the pin forces the issue.

## 3. Package select harness skills as a plugin for the Claude Marketplace

**Source:** [Build plugins for Claude — claude.com/blog, 2026-09-25](https://claude.com/blog/build-plugins-for-claude) + [Claude Marketplace: one place to discover plugins, agents, and services from our partners — claude.com/blog, 2026-09-23](https://claude.com/blog/claude-marketplace). The two posts land the official distribution channel: a submission portal at `claude.ai/directory/manage/new` that accepts GitHub-hosted plugin bundles combining MCP servers + Agent Skills (+ for Claude Code: LSPs, commands, hooks, agents), with built-in purchasing against committed Anthropic spend.

### Why it's relevant
Today the harness distributes exclusively via `setup-harness`:
- `skills/` is symlinked out to `~/.claude/skills/` on a single-user machine (the maintainer's).
- Target projects install via `setup-harness` from a cloned repo path, not from a marketplace.

The Marketplace / plugin pathway is **a distinct, additive distribution channel** that would:
- Make the harness installable in one `/plugin` command rather than a clone + symlink dance.
- Give the harness an audience discovery surface (currently zero: the repo is private).
- Package `code-reviewer` / `spec-planner` / `planning-loop` / the `_shared/loop` engine into one atomic installable.

### Why this is `defer`, not `apply`
Four blockers:

1. **The harness is explicitly solo-maintained** (`team.size: solo` + `audience.size_estimate: "1"` in `.harness-profile`). The marketplace exists to find *users*; the harness today has one.
2. **Plugin bundles for Claude Code include commands, hooks, agents in a GitHub-hosted repo** — matches this repo's shape, but publishing requires a submission portal + paid Claude plan + ongoing maintenance of a marketplace-visible listing (support channel, versioning discipline, backward-compat guarantees). None of that infra exists today.
3. **The symlink distribution preserves per-cwd auto-memory + the manual promotion loop** (`CLAUDE.md:§ Per-cwd auto-memory`). A marketplace plugin install would need to re-create that loop at install time; non-trivial.
4. **The `/spec-planner` + planning-loop machinery is highly opinionated** and currently coupled to the maintainer's working style; publishing it would commit to supporting external users' edge cases.

### Candidate concrete step (for a future "yes, distribute" decision)
Not a change to apply now; a design-pass candidate for `/spec-planner`:
- Add a `.claude-plugin/plugin.yml` (format TBD per the submission portal docs) that enumerates the harness's shippable surface (skills to export, agents to register, hooks to install).
- Carve out a `distribution/` directory with marketplace-only metadata (icon, screenshots, README-plugin.md tailored to a wider audience).
- Decide which skills are plugin-ready vs. opinionated-and-private (`run-loop`'s TypeScript engine is probably not plugin-shippable until it has user-facing config).

### Expected payoff
Zero today (solo). Non-zero only if/when the maintainer wants collaborators or external users.

**Verify before applying:**
1. `grep -n "team.size\|audience.size_estimate" .harness-profile` — must still show `solo` + `1`. If either changes, the deferral trigger has fired.
2. `ls .claude-plugin/ 2>/dev/null; echo "---"; grep -rn "claude-plugin\|marketplace" README.md docs/ 2>/dev/null` — must return nothing structural today; if a plugin manifest appears, this § is already in motion and should be re-reviewed, not applied naively.
3. Confirm Marketplace is still the primary submission surface at the time of application (not supplanted by a different Anthropic distribution channel).

**Recommended verdict:** defer until the solo constraint lifts, or until the maintainer wants ≥1 external user. Spec it via `/spec-planner` when triggered.
**Status:** PENDING — awaiting triage in PR review

## 4. "Modernization certificate" vocabulary alongside Wave 25's acceptance-strictness scanner

**Source:** [How to prepare for AI-driven code modernization projects — claude.com/blog, 2026-09-23](https://claude.com/blog/how-to-prepare-for-ai-driven-code-modernization-projects). The post describes a six-step framework; the specific pattern of interest is the **"certificate"** — a set of checkable conditions that an agentic workflow iterates against until met, with no human in the loop.

> *"Each condition should be checkable without a human in the loop, so the agentic workflow can iterate on a change until it meets the certificate or flag it for human review."*

### Why it's relevant
Wave 25 (merged commit `cdb80bb`, 2026-09–10) shipped the **acceptance-strictness scanner** in `/spec-planner`:
- `skills/_shared/acceptance-scanner/` (shared scanner for spec acceptance criteria)

This is **exactly the "certificate" pattern** the modernization post describes, under a different name. The harness got there independently through its own planning-loop development; the Sep 23 post gives the pattern a name and third-party corroboration.

### What this is good for
Not a change — a **vocabulary alignment**. If/when the planning-loop spec (`docs/specs/`) or spec-planner skill text is revised, swapping in "certificate" as a cross-ref term helps future readers connect the harness's internal mechanism to an external Anthropic pattern. Also useful if the harness ever documents itself for external users (see §3): "the acceptance-strictness scanner implements the modernization-post's certificate pattern" is a one-liner that saves paragraphs.

### Candidate concrete change (bookkeeping-only)
In `docs/specs/2026-04-30-universal-harness-protocol-v2.md` or the next revision of the spec-planner SKILL.md, add one line to the acceptance-criteria section:

```diff
+> **Pattern name:** this is the "certificate" pattern from Anthropic's 2026-09-23 modernization-readiness post — a set of conditions the agentic workflow iterates against with no human in the loop, flagging for human review only when the conditions cannot be met.
```

Not worth doing speculatively. Worth doing *when* the spec text is next edited for another reason.

### Expected payoff
Zero functional change. Linkage to an external pattern for future readers.

**Verify before applying:**

## 5. Claude Code artifacts as a rendering surface for `evaluation-report.md`, `plan.md`, wave summaries

Live-updating web pages generated during a Claude Code session, private to the organization by default, surfaced via natural-language requests ("make an artifact walking through this PR"). The post leans on PR walkthroughs, dashboards, incident timelines, checklists as examples.

### Why it's relevant
The harness produces several text artifacts whose natural reading surface is a webpage, not a terminal:

- `docs/plan.md` — the running wave plan.
- Wave summary files `docs/waves/wave<N>-*.md` — build receipts.

Claude Code artifacts turn each of these into a live, shareable, in-session page. For the maintainer alone, this is marginal: a markdown file reads fine in a terminal. For a session narrating "look at the wave 25 build receipt and the acceptance-strictness scanner diagnostics side by side", an artifact that renders both with cross-links is strictly nicer.

- No pain today. Markdown works.
- Artifacts require an org-level toggle (per the post); the maintainer's single-user setup likely has it on by default, but a surface-level change ("every /close-wave now generates an artifact walkthrough") is a workflow habit, not a code change.
- The feature is new enough (Jun 18) that it may still evolve; waiting one more cycle costs nothing.

If the maintainer wants to try it:
- Add one bullet to `/close-wave`'s SKILL.md: *"optional: after writing the wave summary, request an artifact walking through the diff — surface the summary + relevant code-reviewer findings + evaluator rubric scores on one page."*
- One sentence in README that artifact-based reports are supported but not required.

Neither is urgent; both can land in a `/micro` pass if the maintainer tries it once and likes it.

**Verify before applying:**
1. `grep -rn "artifact\(s\)\? in Claude Code\|Claude Code artifacts\|artifacts-in-claude-code" README.md docs/ skills/ 2>/dev/null` — must return nothing structural today; if present, the adoption has already happened and this § is stale.
2. Confirm Claude Code artifacts is still the official feature name (not renamed to e.g. "live pages") and that the org-level toggle is still the control surface at application time.

**Recommended verdict:** defer until the maintainer tries it once in a session and decides whether it's worth wiring into `/close-wave`. No code change pre-trial.
