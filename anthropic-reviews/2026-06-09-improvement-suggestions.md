## 1. Document the harness's static `orchestrator` ↔ Anthropic's Dynamic Workflows in README

**Source:**
- Primary — [A harness for every task: dynamic workflows in Claude Code](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (claude.com/blog, June 2, 2026 — deep dive).
- Companion launch post — [Introducing dynamic workflows in Claude Code](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (May 28, 2026, paired with the Opus 4.8 launch).
- Docs — [Orchestrate subagents at scale with dynamic workflows](https://code.claude.com/docs/en/workflows) (Claude Code docs).

### Why it's relevant

The June 2 post defines a **harness** as "the system around the model — it decides how work gets split, which subagents spawn, what tools each one gets, how their output is verified, which model handles which step, how work is isolated, and when the job is actually done." That definition maps exactly onto **this repo's name (`claude-harness`)** and onto the `orchestrator` agent's job (`.claude/agents/orchestrator.md`: "reads spec tasks and dispatches each to opus, sonnet, or haiku subagents based on task complexity"). Anthropic now ships a feature that addresses the same problem class — but via a *generated JavaScript script* at runtime rather than a *static markdown agent* dispatching via `Agent` calls.

Failure modes Anthropic explicitly attributes to single-context runs in the post — **agentic laziness** (stopping after partial progress), **self-preferential bias** (trusting its own results when verifying), and **goal drift** (losing fidelity across many turns and compactions) — are the same failure modes the harness's `orchestrator` + worktree isolation + adversarial `code-reviewer` were designed to prevent. The harness's solution is **static** (pre-decomposed spec → orchestrator routing → max ~16 parallel subagents in a single Claude Code session). Anthropic's Dynamic Workflows is **dynamic** (Claude writes a JS orchestration script per task, runs it on cloud runtime, caps at 1,000 subagents per workflow, 16 concurrent — research preview on Pro/Max/Team/Enterprise as of May 28).

These are **complementary, not redundant**, but the overlap question is exactly the one a future reader will ask: "the repo is called `claude-harness` and ships an `orchestrator` — is that obsolete now that Anthropic ships dynamic workflows?" Today there is **zero mention of `dynamic workflows`, `ultracode`, or `a harness for every task`** in this repo (`grep -rn 'dynamic workflows\|ultracode\|harness for every task' .` returns nothing).

There are two distinct README touches worth making:

- **(1a) — Position note in the `orchestrator` section.** One paragraph naming the static-vs-dynamic distinction so the answer to "is `orchestrator` redundant?" is on the page.
- **(1b) — Add Dynamic Workflows as a new evidence point to the "Vendor primitives keep absorbing harness territory" bullet** at `README.md:32` (the existing one cites Claude Security). The shape is identical: Anthropic absorbs another harness-pattern into first-party tooling; the lean harness stays useful because it operates at a different layer (pre-spec, in-session, rubric-anchored).

## 3. Re-evaluate the `stakes.level → effort_default` derivation table now that Opus 4.8's product default is `high`

**Source:**
- [What's new in Claude Opus 4.8 — Effort defaults](https://platform.claude.com/docs/en/about-claude/models/whats-new-claude-4-8) — verbatim: "The effort parameter default on Claude Opus 4.8 is `high` on all surfaces, including the Claude API and Claude Code. … On coding tasks, this effort level spends a similar number of tokens as Opus 4.7's default, but with better performance."
- For context, the harness's existing derivation justification cites Anthropic's [April 23, 2026 postmortem](https://www.anthropic.com/engineering/april-23-postmortem) which set Opus 4.7's Claude Code default to `xhigh`.

### Why it's relevant

The `.harness-profile` comment (lines 18–22) documents the derivation table:

```
#   stakes.level: low    → effort_default: high
#   stakes.level: medium → effort_default: xhigh
#   stakes.level: high   → effort_default: xhigh
# Aligned with Anthropic's 2026-04-23 postmortem (Claude Code defaults Opus-4.7 users to xhigh).
```

The justification ("aligned with Anthropic's product default") **no longer holds on Opus 4.8**, which defaults to `high`, not `xhigh`. Two competing readings:

1. **The derivation should follow Anthropic's product default.** Then the table shifts down one tier:
   - `low` → `medium`
   - `medium` → `high`
   - `high` → `xhigh`

   Rationale: same shape as today (one tier above the product default for `medium` stakes, two tiers above for `high`), but anchored to 4.8's new default. Anthropic's own framing — "this effort level spends a similar number of tokens as Opus 4.7's default, but with better performance" — implies that staying at `xhigh` on 4.8 spends *more* tokens than 4.7's `xhigh` for *the same task quality*. The harness pays extra for no methodology benefit.

2. **The derivation is independent of the product default and should not move.** Rationale: the harness's `stakes.level: medium → xhigh` was a deliberate amplification of the postmortem signal ("Claude Code defaults to xhigh because lower defaults regressed coding evals"); on 4.8 the same amplification yields `xhigh` regardless of the product default shift. Anthropic's "better performance at the same token count" framing is at *the same effort tier*, not *the same task quality at lower effort*. Staying at `xhigh` on 4.8 ships the better-tool-triggering and better-compaction-recovery uplifts at the harness's existing cost/quality point.

Both readings are defensible. The choice has cost-impact across every consumer project that installs from this harness (the orchestrator's runtime effort routing flows from this single field). It's not the kind of edit `/micro` should ship without a spec.

### Why this is `spec`, not `apply` or `defer`

- **Not `apply`:** changes the cost profile of every harness installation; needs a decision documented.
- **Not `defer`:** the trigger is fresh (Opus 4.8 launched 12 days ago) and the bump in §2 makes the derivation-justification comment factually wrong (it still cites Opus 4.7 by name after §2 lands).
- **Not `reject`:** the question is real — Anthropic's product default *did* move and the comment *does* cite it as justification.

**Spec scope (for `/spec-planner` to expand):**

- Either way: document the decision so future model bumps (4.9, 4.10) don't re-litigate it.

### Expected payoff

A documented, intentional position on whether the harness's effort-amplification policy is anchored to Anthropic's product default or to a harness-internal signal. Prevents `.harness-profile` drift on the next Opus minor-version bump (Anthropic has shipped 4.5, 4.6, 4.7, 4.8 in roughly six months; the next bump is likely within the routine's cadence).
