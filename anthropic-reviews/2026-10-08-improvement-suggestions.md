## 1. Model-pin migration: Opus 4.7 → Opus 5.5, Sonnet 4.6 → Sonnet 5.5

**Source:**

Thinking can no longer be turned off. See [the migration guide](https://platform.claude.com/docs/en/models/opus-5-5/migration-guide) for breaking-change details.
- [Claude Code changelog — v2.1.280 (Sept 22) + v2.1.284 (Sept 28)](https://code.claude.com/docs/en/changelog) — Opus 5.5 becomes the default Opus model with 1M context; Sonnet 5.5 (`claude-sonnet-5-5`) becomes the default Sonnet model on the Anthropic API, also with 1M context. v2.1.281 (Sept 23) makes Opus 5.5 the default on Pro / Team Standard. v2.1.287 (Oct 1) retires the 200K-context branch except behind `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`.

### Why it's relevant
The `.harness-profile` pins `claude-opus-4-7` / `claude-sonnet-4-6` with an explicit annotation ("Aligned with Anthropic's 2026-04-23 postmortem (Claude Code defaults Opus-4.7 users to xhigh)" — `.harness-profile:26`). This is **not a trivial bump**. Three branches of change-impact:

1. **`.harness-profile:30-31`** — the pins themselves. One-line edits per entry, trivially reversible.
2. **`README.md:10` prose about Opus 4.7 behavior** — needs a re-read against Opus 5.5's reported behavior. 3. **Orchestrator routing (`.claude/agents/orchestrator.md`)** — the harness routes "opus/sonnet/haiku" by task complexity. Opus 5.5 is roughly 20% cheaper per input token than Opus 5 and 30% faster, which may compress the gap between the three tiers. The routing rules may still work but should be re-read.

Also worth noting: **Claude Opus 5.5 can no longer disable extended thinking**, and **cybersecurity-related tasks are rerouted to Opus 4.8**. Neither of those affects the harness directly, but both are the kind of thing a methodology doc that cites model behavior should double-check.

- Separately consider **Fable 5.1** for the orchestrator `primary` slot (its prompt-injection robustness ties Opus 5.5's; its pricing is higher but its reasoning may be the better fit for the orchestrator's "pick the right model" job).

## 2. Position Dynamic Workflows alongside `/run-wave`, `/run-loop`, and the orchestrator agent in README

**Source:** [Orchestrate subagents at scale with dynamic workflows — code.claude.com/docs/en/workflows](https://code.claude.com/docs/en/workflows). Research preview on all paid plans. Scripts are JavaScript with `agent()`, `pipeline()`, `parallel()`, `phase()`; up to 16 concurrent agents by default (configurable to 256 via `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` on v2.1.269+); up to 4,096 items per `parallel()` / `pipeline()` call; 1,000 agents total per run. Opt-in keyword is `ultracode`. One bundled workflow: `/deep-research`. Changelog entries referencing workflows span v2.1.202 through v2.1.293.

### Why it's relevant
The harness ships **three** execution lanes that overlap conceptually with Dynamic Workflows:

- **`/run-wave`** — orchestrator dispatches a wave of tasks to subagents, with human checkpoint between waves (`README.md:295, 535`).
- **`/run-loop`** — stream-driven worker that drains a work source (board waves or GitHub issues) end-to-end behind a mechanical gate (`AGENTS.md:93-96`).
- **`.claude/agents/orchestrator.md`** — "fans tasks out to sonnet/haiku in parallel" (`README.md:535, 1083`), does runtime model routing per task.

Dynamic Workflows do a strictly different thing (the plan lives in a JS script, not in Claude's context; results stay in script variables; the runtime is isolated; resumable in-session), but a reader hitting the harness's three-lane architecture for the first time **will** ask "when do I use `/run-wave` vs. `/deep-research` vs. the `ultracode` keyword?" Today the repo has **zero mentions** of `ultracode`, Dynamic Workflows, or `/workflows`.

The Anthropic docs make the distinction explicit (quoted from `code.claude.com/docs/en/workflows`):

> With subagents, skills, and agent teams, Claude is the orchestrator: it decides turn by turn what to spawn or assign next, and every result goes into a context window. A workflow script holds the loop, the branching, and the intermediate results itself, so Claude's context holds only the final answer.

That's the exact distinction a harness reader needs to make the right call. The harness's `/run-wave` is squarely in the "Claude is the orchestrator" camp (orchestrator agent decides at runtime); workflows are in the "the plan is code" camp.

### Concrete change
**One paragraph appended to the existing orchestrator / `/run-wave` section in `README.md`**, before the `References` section. Suggested wording:

```markdown
#### How this complements Claude Code Dynamic Workflows

The harness's `/run-wave`, `/run-loop`, and `orchestrator` agent all put **Claude in the driver's seat**: a session's orchestrator agent decides turn-by-turn which subagents to spawn, and every intermediate result lands in a context window. As of mid-2026, Anthropic ships [Dynamic Workflows](https://code.claude.com/docs/en/workflows) (research preview; `ultracode` keyword; `/workflows` view), a strictly different primitive where **the plan lives in a JavaScript script** the runtime executes in isolation — Claude's context holds only the final answer, and the run is resumable within the session. Reach for a workflow when the task is larger than one agent can hold in context (a 500-file migration, a cross-source research question, an adversarial-verify fan-out), or when you want the orchestration codified and rerunnable. Reach for `/run-wave` or `/run-loop` when the plan is in a spec and the shape of the next step depends on what the last one found. They are complementary — different control locus, different context model, different resumability guarantees.
```

Optional second touch: one bullet in the `References` section pointing at the docs page.

### Expected payoff
A reader comparing the harness to the newer Claude Code primitive gets the distinction stated plainly. The harness's three-lane architecture doesn't change — the paragraph justifies when each lane remains the right choice vs. deferring to the shipped workflow runtime.

### Verify before applying
1. `grep -rn "ultracode\|dynamic workflow\|Dynamic Workflow\|/workflows\|/deep-research\|code.claude.com/docs/en/workflows" README.md AGENTS.md` — must return nothing today; if it returns hits, this § is stale.
2. Confirm Dynamic Workflows is still a research preview and the `ultracode` keyword still ships (check [the workflow authoring reference](https://code.claude.com/docs/en/workflows) — if it has graduated to GA or been renamed, update the wording).
3. If the harness has grown a fourth execution lane (e.g. a workflow-authoring skill) between now and when this is applied, the paragraph should mention it alongside — `grep -rn "workflow-authoring\|Workflow tool" skills/` to catch that.

**Recommended verdict:** apply — pure documentation, one paragraph + one reference bullet, closes a specific "when do I use which?" gap that *will* otherwise be asked aloud the first time someone else reads the repo.

## 3. Add a `verify` skill (or document why not) for the 2.1.286 pre-commit convention

**Source:** [Claude Code changelog — v2.1.286 (Sept 30, 2026)](https://code.claude.com/docs/en/changelog): *"If a skill or project skill named `verify` exists, Claude is told to run it before committing (except for docs-only and tests-only commits)."*

### Why it's relevant
The harness's existing commit protocol (`skills/commit/SKILL.md`) already runs its own pre-commit flow: `code-reviewer` agent, parking-lot update, plan.md update. But 2.1.286 adds a **CLI-level default**: if the project ships a skill called `verify`, Claude will run it on every commit the CLI drives (including commits made outside `/commit` — e.g. by hooks, agents, or ad-hoc `git commit` wrappers). The harness today has no `verify` skill (`ls skills/` shows 25 skills; `verify` is not one of them).

Two shapes this could take:

1. **A pass-through `verify` skill** that calls the existing `code-reviewer` agent plus the `.harness-profile`-driven quality gate. Would make the Claude Code CLI's commit flow and the harness's `/commit` flow consistent.
2. **A no-op stub** that documents "the harness has no runnable tests; use `/commit` for the harness's quality gate" and keeps the Claude Code CLI from running an inappropriate default.

### Why `defer`
The harness is a tooling repo. `quality_bar.test_required: false` in `.harness-profile` is explicit about this. Shipping a `verify` skill without a clear verification target invites either a vacuous stub or scope creep (what does "verify" even mean for a Markdown + Bash methodology repo?). The real win would come if a *consumer* project installing the harness via `setup-harness` wanted `verify` wired up as part of the install — that's a different suggestion for a different week.

### Verify before applying
1. `ls skills/ | grep -i "^verify"` — must return nothing; if a `verify/` skill exists today, this § is stale.
2. `grep -rn "verify" skills/commit/SKILL.md skills/close-wave/SKILL.md` — read the current pre-commit flow to confirm no `verify`-named step already exists.
3. Decide whether the harness is now driving commits from any surface besides `/commit` (git hooks, orchestrator subagents, a CI loop). If yes, the 2.1.286 default would already run on those commits — the `verify` skill either becomes useful (as a wrapper for the quality gate) or needs an explicit no-op.

**Recommended verdict:** defer — until there's a concrete commit surface outside `/commit` that would benefit from the CLI-default `verify` call. Today the harness's `/commit` already handles the review step; adding a stub would be ritual without payoff.

## 4. Document PreModelSwitch / PostModelSwitch hooks for primary→fallback observability

**Source:** [Claude Code changelog — v2.1.252 (Aug 31, 2026)](https://code.claude.com/docs/en/changelog): adds `PreModelSwitch` and `PostModelSwitch` hook events. `/usage` gains a spend-limit bar; `/cost` shows a per-session prompt-cache line. The events fire when Claude Code switches models mid-session (API retry, safety routing, user `/model` switch, fallback).

### Why it's relevant
The harness's `.harness-profile:30-31` pins both a `primary` and a `fallback` model. Today a silent fallback leaves no trace in `.harness-state/` or any session log. If Opus 5.5 is briefly unavailable and the session silently moves to Sonnet 5.5, the methodology's "stakes.level drives effort_default" invariant may still hold but the orchestrator's model-routing decisions were made against a different cost/latency profile than what actually ran. The 2.1.252 hooks make that visible.

**Note on §1 interaction:** this hook work has strictly more value *after* §1's pin migration, because an Opus 4.7 fallback to Sonnet 4.6 happens rarely enough today that logging it is noise. If the pin flips to Opus 5.5 (newer, higher load variance in the first weeks post-launch), fallback frequency may rise and the logging becomes more useful.

### Concrete change (sketch)
A new hooks file `hooks/model-switch.sh` (or equivalent) that writes a line to `.harness-state/model-switches.jsonl` on each `PostModelSwitch` event:

```json
{"ts":"2026-10-08T14:32:11Z","session":"<id>","from":"claude-opus-5-5","to":"claude-sonnet-5-5","reason":"fallback"}
```

Registered in `.claude/settings.json` under `hooks.PostModelSwitch`. Totally passive observation — no behavior change.

### Verify before applying
1. `grep -n "PreModelSwitch\|PostModelSwitch" .claude/settings.json` — must return nothing; if hooks are already registered, this § is stale.
2. Confirm the hook event names and payload shape against the [current Claude Code hooks reference](https://code.claude.com/docs/en/hooks) — Anthropic has renamed hook events before.
3. Confirm the `.harness-state/` directory is still the canonical session-state location (`.harness-profile:71` points there). If not, write to wherever that moved.

**Recommended verdict:** defer until Opus 5.5 adoption — only becomes useful once §1 has flipped the pin. No action today.
