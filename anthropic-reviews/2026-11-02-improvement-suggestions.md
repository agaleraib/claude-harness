## 3. Methodology note: Anthropic's "fold subagents" heuristic vs. the harness's orchestrator-worker routing

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com/resources, Oct 22, 2026](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop). Core thesis: many enterprise agents mirror the org chart with too many subagents; a single-loop agent with progressive disclosure (load skills/tools only when needed) often produces better answers at lower cost and latency, because context is shared across steps and there are no lossy handoffs. Keep a subagent **only when**:
> (1) *"A single agent loop hits measurable performance degradation from context bloat"*
> (2) Multiple tasks need parallel work with fresh context windows that can be discarded afterward
> (3) A single agent struggles with tool selection, or the system prompt has conflicting instructions

Recommended methodology: "Convert one subagent's prompts into skills and its API calls into tools, build a small end-to-end eval, and keep the subagent only if the folded version scores worse."

### Why it's relevant

The harness's orchestrator agent (`.claude/agents/orchestrator.md`) implements an explicit Haiku/Sonnet/Opus routing table and dispatches worktree-isolated subagents per task from a spec. Separate from the orchestrator, the harness also ships `code-reviewer`, `spec-planner`, `generator`, `Explore`, `Plan`, `project-tracker`, `ui-evaluator`, `statusline-setup`, `claude-code-guide`. README.md:533-536 explicitly cites "[Anthropic's orchestrator-worker pattern](https://www.anthropic.com/research/building-effective-agents)" as the basis.

Anthropic's new post is **not a reversal** of the orchestrator-worker pattern — the post keeps subagents for (1) context bloat, (2) parallel fresh-context work, (3) tool-conflict decomposition. The harness's use case **does** fit all three:
- `/run-wave` fans out worktree-isolated subagents = (2).
- `code-reviewer` runs in an adversarial-context side-loop = (1) + (3).
- `spec-planner` has a prompt distinct enough from the main loop to be its own agent = (3).

So the harness is **plausibly** on the right side of the heuristic. But the post is new (12 days ago as of 2026-11-02) and the harness hasn't been evaluated against the three criteria explicitly. An audit might surface:
- An agent (e.g. `Plan`) whose job is close enough to a progressive-disclosure skill call that the subagent spawn overhead doesn't pay off.
- A per-task subagent spawn (orchestrator → Haiku-routed task) whose context cost + handoff cost exceeds the main-loop version.

### Why this is `defer`, not `apply` or `reject`

- **Not `apply`:** No concrete evidence yet that any specific harness agent is miscategorized. The post itself says "build a small end-to-end eval and compare" — doing that for all 9 harness agents is a substantive scope that belongs in a spec, not an inline edit.
- **Not `reject`:** The thesis is actionable methodology, not vendor-promotion. The harness ships a routing table that was designed before this post; a future redesign has new evidence to incorporate.
- **`defer` with trigger:** Pick this up again when one of these fires:
  1. `/skill-doctor` (§2 above) reveals a skill that's close in function to an existing agent → candidate for folding.
  2. A `/run-wave` or `/run-loop` session's `.harness-state/orchestrator.log` shows a Haiku-routed task completed cheaper by just running it inline next time → datapoint for folding Haiku.
  3. Anthropic publishes an eval harness (hinted at in the article's "build a small end-to-end eval") that this routine could run.

### Concrete change (deferred)

None this run. **Optional bookkeeping edit** (not required to accept this §): add one sentence to `.claude/agents/orchestrator.md` or README.md's `orchestrator (Universal)` section (around README.md:533) acknowledging the heuristic exists and that the harness's design has not been audited against it:

The harness's three subagent-worthy triggers (worktree parallelism, adversarial-context review, decomposed-prompt specialization) still match the three "keep as subagent" criteria in that article. An eval-based audit is parked until there's evidence of context bloat or tool-selection conflict in `.harness-state/orchestrator.log`.
