## 2. Position Anthropic's "dynamic workflows" / "harness for every task" in the README's *Why Not Superpowers* section

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (companion: [Introducing dynamic workflows in Claude Code](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)). Both posts ship with Opus 4.8 on 2026-05-28 and introduce a `ultracode` trigger that opts a turn into **multi-agent orchestration via a per-task generated harness** — Claude writes a one-off workflow definition for the task, then dispatches subagents against it.

### Why it's relevant
This is the first Anthropic launch that **directly challenges the harness's static-skill premise**. The repo's *Why Not Superpowers* section (`README.md:23–34`) defends the design choice that the harness keeps a small fixed set of skills/agents and pushes complexity into `criteria/` and durable specs. The harness and dynamic workflows are **complementary, not redundant**:
- Dynamic workflows generate ephemeral task-specific harnesses inside a session; they don't persist conventions across sessions, don't ship rubrics in `criteria/`, and don't enforce the protocol contract in `AGENTS.md`.

The positioning that needs to land: *use `ultracode` for the in-session orchestration of a single complex task; the harness still owns the cross-session methodology.*

## 5. Adapt `setup-harness` distribution to v2.1.157's `.claude/skills/` auto-loading

**Source:** Claude Code v2.1.157 release ([code.claude.com changelog, 2026-05-29](https://code.claude.com/docs/en/changelog)). Headline item: **plugin auto-loading from `.claude/skills`**, plus `claude plugin init` for scaffolding. (Companion items in the same release: `agent` field honored in settings, auto-mode on Bedrock/Vertex/Foundry.)

### Why it's relevant
Today the harness ships skills via a **global-symlink distribution model**:

- Source of truth: `/home/user/claude-harness/skills/<skill>/SKILL.md`
- Install: `setup-harness` copies (or the operator manually symlinks) these into `~/.claude/skills/<skill>/SKILL.md` — global to the user, every Claude Code session sees them
- Per-consumer-project install: same global path, the project gets visibility because everyone does

v2.1.157 introduces a **second valid distribution surface**: a project-local `.claude/skills/` directory that Claude Code auto-loads when a session starts in that working dir. This is the same pattern as `.claude/agents/` (which this repo already uses — `.claude/agents/code-reviewer.md`, etc.) extended to skills.

Two follow-on questions this opens:

1. **Should the harness repo itself ship a `.claude/skills/` bundle?** Today the repo's skills load globally because the operator who maintains the harness has them installed in `~/.claude/skills/`. A fresh clone on a different machine **wouldn't** see them — `setup-harness` has to run first. A `.claude/skills/` directory in the repo would make a clone-and-go workflow possible.

2. **Should `setup-harness` change its install destination?** Consumer projects could get skills installed at `<project-root>/.claude/skills/` instead of (or in addition to) `~/.claude/skills/`. Tradeoffs:
   - **Pro:** version-locked per project (the consumer's repo carries the skill version it depends on); no cross-project drift; clone-and-go works for the consumer.
   - **Con:** every project gets a copy (storage cost); updates to the harness require re-running `setup-harness` per project; loses the "one source of truth, all projects see the latest" property of the global symlink model.

There are also design questions around **precedence** (if `~/.claude/skills/foo` and `.claude/skills/foo` both exist, which wins? does Claude Code merge or override?) and **version-pinning** (do we hash-pin the bundle to a harness commit?).

### Why this is `spec`, not `apply`

This touches the harness's **core distribution contract**. The current global-symlink model is documented in `setup-harness/SKILL.md` and referenced in `README.md`. Changing it without a design pass risks:
- Breaking existing consumers' install flows
- Introducing dual-write bugs (global + local out of sync)
- Inviting "which one wins?" support questions

A spec should answer:
- Does the harness ship `.claude/skills/` in addition to keeping the global symlink path? (Likely yes — both, with global as primary.)
- Does `setup-harness` add a `--local` flag to install per-project, with global as the default? (Reasonable.)
- What happens to per-cwd auto-memory references that point to global skill paths today? (Probably unaffected — auto-memory is data, not code.)
- Version-pinning model: do consumers freeze to a harness commit when installing locally, or float to whatever's in their global install? (Solo maintainer answer: probably float.)

### Concrete change (when spec lands, not now)
Approximate scope:
- Optional: add `.claude/skills/` to the harness repo as a symlink to `skills/` (the source of truth), so a `git clone` exposes them automatically. Verify Claude Code follows the symlink for auto-load.
- Spec: `docs/specs/2026-06-XX-skills-distribution-v2.md` covering the precedence + pinning decisions and the migration path for consumers.
- `setup-harness/SKILL.md`: add `--local` install mode; document precedence; document the migration path from global-only installs.
- `README.md` Architecture section: name the dual-distribution surface so the next maintainer doesn't trip on it.

### Expected payoff
Consumers can clone-and-go without running `setup-harness` (lower onboarding friction). Per-project version-pinning becomes possible (no global drift). The harness aligns with Anthropic's now-canonical `.claude/skills/` pattern for skill distribution.

**Verify before applying:**
1. Confirm `.claude/skills/` doesn't already exist in the harness repo: `ls /home/user/claude-harness/.claude/skills 2>&1` should return "No such file or directory" as of 2026-06-03. If it exists, this § is partly stale — check `setup-harness/SKILL.md` for the migration state.
2. `grep -rn "claude plugin init\|\\.claude/skills" /home/user/claude-harness/skills/setup-harness/` — should return nothing; if it returns hits, the design is already in flight, narrow the spec scope accordingly.
3. Re-read the v2.1.157 changelog entry just before specing to capture any precedence semantics Anthropic has clarified since 2026-05-29.

**Recommended verdict:** spec — distribution-model change with non-obvious precedence semantics. Worth the design pass; not worth the cost of a one-shot edit. Run `/spec-planner` with this § as the seed.
**Status:** PENDING — awaiting triage in PR review
