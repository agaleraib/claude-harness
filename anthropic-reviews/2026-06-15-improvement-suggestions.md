## 1. Vendor "How we use skills" + audit the harness's 24 skills against Anthropic's 9-category taxonomy

**Source:** [Lessons from building Claude Code: How we use skills — claude.com/blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills). Anthropic's Claude Code team catalogued every skill in active internal use ("hundreds") and found they cluster into nine categories. The post argues: **the best skills fit cleanly into one category; the ones that try to do too much straddle several and confuse the agent.** The nine categories are:

1. Library / API / SDK reference
2. Product verification
3. Data fetching and analysis
4. Business process and team automation
5. Code scaffolding and templates
6. Code quality and review
7. CI/CD and deployment
8. Runbooks
9. Infrastructure operations

## 2. Note dynamic workflows / "harness for every task" alongside `/run-wave` + `orchestrator` agent in the README, deferring adoption

**Source:** Two paired posts: [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (the launch); [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (the engineering deep-dive by Thariq Shihipar and Sid Bidasaria). Reference docs: [Orchestrate subagents at scale with dynamic workflows — code.claude.com](https://code.claude.com/docs/en/workflows).

### Why it's relevant

Anthropic's positioning is **directly adjacent to this harness's framing**: "A harness is the scaffolding around the model that decides how a task is planned, divided, checked, and executed." The dynamic-workflows mechanism:

- Claude reads the task and **writes a custom `.js` harness** for it (orchestration script).
- The runtime executes the script in the background; it spawns subagents (capped at 1000), assigns models per subagent (`/effort`-style), and optionally runs each in its own worktree.
- Triggered by the word "workflow" in a prompt, or by `/effort ultracode`, or by including `ultracode` in the prompt.
- Six composable patterns: classify-and-act, fan-out-and-synthesize, adversarial verification, generate-and-filter, tournament, loop-until-done.

The harness already operates at this layer via a **different mechanism**:

- `.claude/agents/orchestrator.md` — orchestrator-worker agent.
- `skills/run-wave/SKILL.md` — dispatches the orchestrator to execute a wave of plan.md tasks in an isolated worktree.
- `skills/run-loop/SKILL.md` — drives plan.md waves OR `gh` issues end-to-end behind a mechanical gate (Wave 20 shipped; Wave 21 in flight per recent commits).
- `.claude/agents/spec-planner.md` + `skills/planning-loop/SKILL.md` — adversarial-review loop, which is conceptually Anthropic's "adversarial verification" pattern.

Both approaches are the same idea — **decompose, dispatch, verify, synthesize** — just at different infrastructural layers: Anthropic generates a JS harness *per task*; this harness has a stable Markdown-defined orchestrator + skills that *cover the same patterns* but with predictable file conventions.

Today there is **zero mention** of dynamic workflows in the repo (verified: `grep -rln "dynamic workflow\|ultracode" /home/user/claude-harness` returns nothing).

### Why this is `defer`, not `apply`

1. **The harness's existing orchestrator + run-wave + planning-loop covers the same patterns.** Adopting dynamic workflows would be a parallel mechanism, not a replacement — and the harness's pattern is plan.md-driven (durable record), while dynamic workflows are ephemeral (the generated .js is the artifact). For a solo tooling repo this is the wrong tradeoff today.
2. **No pain point.** The maintainer hasn't reported a workflow-shaped task that the orchestrator-worker pattern couldn't handle. Adopting "ultracode" without a concrete trigger task is speculative.
3. **Cost asymmetry.** Dynamic workflows are billed per-subagent (up to 1000 per run). The harness's orchestrator is a single Claude Code session — orders of magnitude cheaper for the current scale.
4. **One small documentation touch helps now.** Anthropic's posts use "harness" as a load-bearing term. Next time someone (or future-you) reads "harness" in a Claude Code context, they may conflate Anthropic's per-task JS harness with this repo's persistent Markdown harness. A one-line clarification in the README's `code-reviewer` / `orchestrator` section prevents that.

### Concrete change (optional, low-stakes)

If the maintainer wants to take the documentation touch without committing to the larger pattern, append **one paragraph** to the existing `orchestrator (Universal)` section in `README.md` (verified to exist; `grep -n "### orchestrator" README.md` returns line 533):

```diff
 ### orchestrator (Universal)
 …existing content…

+#### Relationship to Anthropic's dynamic workflows
+As of [Code w/ Claude 2026](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) Anthropic ships **dynamic workflows** — Claude writes a custom JavaScript harness per task that orchestrates up to 1000 subagents in the background, triggered by the keyword "workflow" or `/effort ultracode` (engineering deep-dive: [A harness for every task](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)). This harness uses a different mechanism for the same composable patterns (classify-and-act, fan-out-and-synthesize, adversarial verification, generate-and-filter, tournament, loop-until-done): a **stable Markdown-defined orchestrator agent + `/run-wave` + `/planning-loop`** dispatched against `docs/plan.md` waves. Both arrive at the same shape; this harness's choice trades the dynamic generality for plan.md-driven durability and lower per-invocation cost. Adopt dynamic workflows when the task shape is one-off and parallelism beyond ~10 subagents matters; stay on the local orchestrator for the build-test-commit loop.
```

Leave the rest deferred — no skill, no `.claude/agents/` change.

### Expected payoff (deferred)

Once the maintainer hits a task that genuinely wants fan-out beyond ~10 subagents (e.g. a 750k-line refactor like Bun's Zig→Rust port cited in the deep-dive), the prior art is on the page. Until then, the documentation touch costs ~10 lines and forestalls the "did dynamic workflows obsolete `/run-wave`?" question the next time someone reads both.

3. **scope: speculative** — the optional concrete-change diff is the minimum-friction action; the deeper question (should the harness adopt dynamic workflows?) is for a `/spec-planner` pass only if a concrete pain trigger appears.

**Recommended verdict:** defer until a workflow-shaped task pain emerges. The optional README touch is low-stakes if the maintainer wants the comparison on the page now, but skipping it entirely is also fine — there's no surface bug to fix.

## 3. Re-evaluate `.harness-profile`'s `model.primary: claude-opus-4-7` pin in light of Claude Fable 5 / Mythos 5

**Source:** [Claude Fable 5 and Claude Mythos 5 — anthropic.com/news, 2026-06-09](https://www.anthropic.com/news/claude-fable-5-mythos-5). Fable 5 is Anthropic's most capable publicly-available model, generally available on Claude API, Bedrock, Vertex AI, and Microsoft Foundry on Pro/Max/Team/Enterprise plans (free through 2026-06-22). Mythos 5 is the same capability tier behind Project Glasswing access only. Distinguishing safety mechanism: **on sensitive topics (cybersecurity, biology, chemistry, model-distillation), Fable 5 transparently falls back to Opus 4.8 for the response** — i.e., the visible model identifier on a single call can be either Fable 5 or Opus 4.8 depending on the query.

### Why it's relevant

`.harness-profile` (verified at `/home/user/claude-harness/.harness-profile`) currently pins:

```yaml
model:
  primary: claude-opus-4-7
  fallback: claude-sonnet-4-6
  effort_default: xhigh
```

The pin was added 2026-04-11 ("First real execution of the methodology, dogfooded on the harness repo itself") and reaffirmed by the deferred 2026-04-19 entries. The 2026-04-23 Claude Code Opus-4.7-defaults-to-xhigh postmortem is the cited rationale for `effort_default: xhigh`.

Since June 9, the **model family has shifted**:

- **Claude Opus 4.7** (the harness's pinned primary) remains valid but is no longer the top public capability tier — it has dropped to second tier behind Opus 4.8 and Fable 5.
- **Claude Opus 4.8** is the canonical fallback for Fable 5's sensitive-topics safety route.
- **Claude Fable 5** is the most capable public model on benchmarks ("more than 10% higher than Claude Opus 4.8 on some benchmarks" per the launch post).
- **Claude Sonnet 4.6** (the harness's fallback) remains valid and unchanged.

### Why this is `defer`, not `apply`

1. **Working pin is a stable pin.** Opus 4.7 is still GA, still the model this Claude Code session is running on, and the harness's effort-routing math (`stakes.level: medium` → `effort_default: xhigh`) was derived against Opus 4.7's behavior. Moving the pin without re-deriving the routing math is the larger risk.
2. **Fable 5's fallback semantics break "single pinned model" invariants.** A `model.primary: claude-fable-5` pin would mean "calls may transparently complete on Opus 4.8 for sensitive topics" — the harness's drift detector, orchestrator dispatch, and effort-routing all assume one model per call. Adopting Fable 5 needs a spec pass on what "pinned model" means under transparent fallback.
3. **Free-promo window closes 2026-06-22.** Fable 5 is included free on Pro/Max/Team plans through June 22; after that, it's a paid tier. The maintainer should let pricing settle and let the community surface any edge cases before re-pinning.
4. **The harness consumes models, doesn't ship them.** Consumer projects installed via `setup-harness` inherit the `.harness-profile.model.primary` value. A change here propagates to every install — error blast radius is wide.

### Concrete (optional, deferred) action

When this is eventually acted on, the change is one line in `.harness-profile`:

```diff
 model:
-  primary: claude-opus-4-7
-  fallback: claude-sonnet-4-6
+  primary: claude-opus-4-8       # bump after re-deriving effort_default for Opus 4.8 behavior
+  fallback: claude-sonnet-4-6
   effort_default: xhigh
```

Skip the Fable 5 jump until the safety-fallback semantics are documented for harness use (the simpler Opus 4.7 → 4.8 bump is the lower-risk first step). The `effort_default: xhigh` derivation comment in the existing `.harness-profile` block cites the 2026-04-23 postmortem — re-verify that Opus 4.8 inherits the same `xhigh`-default behavior before bumping.

### Expected payoff (deferred)

Once Opus 4.8 has been GA for a few more weeks and the harness consumer projects have surfaced any compatibility issues, the bump is a one-line edit. Until then, the existing pin works, and the durable record reflects that the maintainer is aware of the model-family shift.

1. `grep "model.primary\|claude-opus-4-7\|claude-opus-4-8\|claude-fable-5" /home/user/claude-harness/.harness-profile` — must show `primary: claude-opus-4-7` today; if it's already been bumped, this § is stale.

**Recommended verdict:** defer until Fable 5 fallback semantics stabilize.
