## 3. Add a "What to avoid" entry in `AGENTS.md` about committing executable hooks to repo `.claude/settings.json`

**Source:** [How we contain Claude across products — Anthropic Engineering, 2026-05-28](https://www.anthropic.com/engineering/how-we-contain-claude). Secondary corroboration: [Simon Willison's notes on the same post](https://simonwillison.net/2026/May/30/how-we-contain-claude/). The post explicitly flags that **Claude Code read a cloned repo's `.claude/settings.json` hooks at startup, before the "Do you trust this folder?" dialog, so a committed hook executed automatically.**

### Why it's relevant

The harness itself ships a `.claude/settings.json` in this repo (read it: it is `{ "hooks": {} }` — empty by design). The empty-hooks discipline is **not documented anywhere** in the repo, however:

- `AGENTS.md §What to avoid` (lines 47–54) — no entry on this.
- `CLAUDE.md §Loop protocol — Claude Code invocation notes` — references the catastrophic-command denylist as a **global** `~/.claude/settings.json` PreToolUse hook (correct), but says nothing about *repo* `.claude/settings.json`.
- The harness's installer (`skills/setup-harness/SKILL.md`) — has no warning either.

The next contributor to extend this repo who reaches for "let's commit a hook to validate X before commits" would be re-introducing the same vulnerability surface Anthropic just published a containment writeup about. Three lines in `AGENTS.md §What to avoid` immortalize the convention.

This is a small change with high durability: it survives every future reader who would otherwise have to figure out, from scratch, why repo-committed hooks are an anti-pattern.

### Concrete change

Append one bullet to `AGENTS.md §What to avoid` (after line 54, the prompt-caching guidance bullet):

```diff
 - Don't bake dynamic content (timestamps, build IDs, absolute paths, per-session counters) into static prompt files (`CLAUDE.md`, `AGENTS.md`, any `SKILL.md`). Per [Anthropic's prompt-caching guidance](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything), prefix-instability invalidates the conversation-wide cache. Use runtime injection (Claude Code's `system-reminder`, hook output, or a fresh-read of `.harness-state/`) for anything that changes session-to-session.
+- Don't commit executable `hooks:` entries to a repo's `.claude/settings.json`. Per [Anthropic's "How we contain Claude" engineering post](https://www.anthropic.com/engineering/how-we-contain-claude) (2026-05-28), Claude Code loads `.claude/settings.json` hooks at startup **before** the "Do you trust this folder?" dialog — so a committed hook executes against every collaborator's machine on first open. The harness ships `.claude/settings.json` with an empty `hooks: {}` block intentionally; hook configuration belongs in the operator's *global* `~/.claude/settings.json` (e.g. the catastrophic-command denylist documented in `CLAUDE.md §Loop protocol`). If you genuinely need a project-scoped hook, surface it as a documented `setup-harness`-time install into the operator's global settings, not as a committed file.
```

### Expected payoff

1. Future contributors are blocked from re-introducing a known vulnerability surface.
2. The intentional empty-hooks ship state of `.claude/settings.json` is now explained — it's not "we forgot to fill this in," it's "we deliberately don't ship hooks."
3. Anchors the harness's hook-distribution pattern (global settings, never repo settings) in the same place where contributors look for the "what not to do" list.

### Why this isn't paranoia

The Anthropic post is explicit: this is a **known** vulnerability they shipped a containment writeup about. It's the kind of subtlety that future-you (or a future maintainer) will hit when extending the harness and thinking "I'll just commit a small validate-on-edit hook." A single bullet in the right place forestalls a real foot-gun.

**Verify before applying:**
1. `cat /home/user/claude-harness/.claude/settings.json` — must still show `{ "hooks": {} }` (or equivalent empty hooks). If somebody has filled it in, this § is **wrong** to merge as written; first investigate what's been added and whether it's safe.
2. `grep -n "Don't commit executable" /home/user/claude-harness/AGENTS.md` — must return nothing today; if it hits, the convention is already documented.
3. `grep -n "PreToolUse" /home/user/claude-harness/CLAUDE.md` — must still describe the denylist as installed via the operator's global settings, NOT a repo file. If that's been changed, the new bullet's cross-reference may need updating.
4. Confirm `https://www.anthropic.com/engineering/how-we-contain-claude` still resolves (Anthropic does not typically move engineering posts, but the URL is canonical and any 404 would be a publication-side error worth noting in the bullet).

**Recommended verdict:** apply — single bullet, zero risk, documents an intentional safety convention that's currently undocumented, cites a first-party engineering post as the rationale.

## 5. Park "Dynamic Workflows" (Opus 4.8 research preview, 1,000 subagents / 16 concurrent per run) as a parallel to `run-wave` / `run-loop`

**Source:** [Introducing Claude Opus 4.8 — Anthropic News, 2026-05-28](https://www.anthropic.com/news/claude-opus-4-8) and follow-on coverage [Anthropic Ships Claude Opus 4.8 Alongside Dynamic Workflows — MarkTechPost](https://www.marktechpost.com/2026/05/28/anthropic-ships-claude-opus-4-8-alongside-dynamic-workflows-and-cheaper-fast-mode-with-workflows-capped-at-1000-subagents/). Per the launch:

> "A dynamic workflow is a JavaScript script that orchestrates subagents at scale. Claude writes the script for the task you describe. A runtime then executes it in the background. Up to 16 concurrent agents, and 1,000 agents total per run. … Dynamic workflows are launching in research preview for Claude Code users on Enterprise, Team, and Max plans."

### Why it's relevant

The harness already has a multi-lane orchestration story:

- `/run-wave` dispatches a single orchestrator-driven wave into an isolated worktree.
- `/run-loop waves` drains the plan board behind a mechanical exit gate (Wave 24 portable exit gate, just shipped on master at `d9cd506`).
- The `orchestrator` agent routes between Opus / Sonnet / Haiku per task.
- The Anthropic-blessed "subagent fan-out" pattern is already canonical in the harness via the `code-reviewer` adversarial run-after-build.

Dynamic Workflows is the **vendor-platform** version of the same pattern: Claude writes a JS script that orchestrates a population of subagents at fan-out scale Anthropic now bounds at 1,000 total / 16 concurrent. The harness lane operates a tier below that — usually one orchestrator + a handful of named subagents (`code-reviewer`, `Explore`, `Plan`, `generator`, `evaluator`). Per-run token cost is a fraction of Dynamic Workflows; today the harness lane is the right tool.

The defer here is conditional: if a wave's subagent count starts to make the orchestrator-dispatch loop the bottleneck (e.g. very large refactors where the harness wants 50–200 parallel `Explore` subagents at once), Dynamic Workflows is the natural escalation lane.

### Why this is `defer`, not `apply`

1. **Working at the current tier**: `/run-wave` + `/run-loop` is fanning out 1–8 subagents per wave today. Below the level where Dynamic Workflows changes the math.
2. **Research preview gating**: Enterprise/Team/Max plans only. The harness is solo-maintained on whatever the maintainer's plan is; gating isn't necessarily aligned.
3. **JS-script-as-orchestration is new**: The runtime is novel — let the API and operational ergonomics stabilize before building the harness on top of it.
4. **Bidirectional parallel, not predecessor**: Dynamic Workflows didn't replace orchestrator-dispatch; both will coexist. The harness can adopt as a *complementary* lane without retiring the existing one.

### Concrete change (deferred)

None this run. When the maintainer wants to take this on, the smallest concrete experiment is:

1. Identify a single wave where the orchestrator-dispatch lane is bottlenecked by subagent fan-out (e.g. >20 parallel `Explore`s or >50 file-diff readers).
2. Author a Dynamic Workflow JS script that takes the same wave manifest and dispatches its tasks across the cap (16 concurrent / 1,000 total).
3. Compare token cost + wall-clock + observable defects across the two lanes for the same wave.
4. Decide whether to add a third execution lane (`/run-dyn-workflow`) alongside `/run-wave` and `/run-loop`, or whether the existing two suffice.

### Expected payoff (when applied)

A higher-fan-out lane for waves the orchestrator-dispatch lane can't economically reach. No payoff today.
