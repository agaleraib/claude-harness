## 1. Cite Anthropic's loop taxonomy in `AGENTS.md` §"Loop protocol"

**Source:** [Loop engineering: Getting started with loops — Claude blog, 2026-07-07](https://claude.com/blog/getting-started-with-loops)

### Why it's relevant
The post is the first-party consolidation of vocabulary for the pattern this harness has been calling "the loop lane" since Wave 21. The post's taxonomy — **turn-based** (manual `/goal`), **goal-based** (verifiable stop), **time-based** (`/loop`, `/schedule`), and **proactive** (routines that compose skills + goals + workflows) — cleanly labels what `AGENTS.md` §"Loop protocol" already describes without a name. Citing it lets a reader map the harness's `/run-loop waves` and `/run-loop issues` modes onto Anthropic's shared language, and lets `CLAUDE.md` point at Anthropic's own line — *"the verifier is the bottleneck, not the model"* — as the reason the mechanical gate stays authoritative.

```diff

+Code recognizes four loop shapes: **turn-based** (manual, `/goal`-scoped), **goal-based**
+(verifiable stop condition, agent decides when done), **time-based** (`/loop`, `/schedule`

Also flags the deliberate scope boundary (time-based routines live outside `AGENTS.md`) which today is implicit and easy to violate.

## 2. Package the harness's verification skills as an explicit "verification loops" pattern

**Source:** [Building verification loops in Claude Code with skills — Claude blog, 2026-07-22](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)

### Why it's relevant
The post's thesis — *"Without a check it can run, 'looks done' is the only signal available. Give Claude something that produces a pass or fail, and the loop closes on its own"* — is the same discipline `skills/_shared/loop/protocol/verify-gate.ts` encodes (reviewer proposes → reproducer confirms → fix rounds are bounded). The Anthropic team's own example is `/code-review` + `/simplify` + `/verify` + a custom `/design` skill that checks against `DESIGN.md`. Mapping onto this harness:

| Anthropic post's example | Harness equivalent | Gap? |
|---|---|---|
| `/code-review` | `code-reviewer` agent (used by `commit`) | none |
| `/simplify` | `/simplify` skill (already global) | none |
| `/verify` (build/type/test/lint) | `verify-gate.ts` inside `/run-loop` + `deploy-check` + `a11y-check` + `api-smoke-test` + `migration-check` skills | fragmented — no single-entry "verify me now" skill |
| Custom `/design` against `DESIGN.md` | none | intentionally out of scope for a tooling repo |

The gap is real but shallow: a session-level "run all applicable checks against my current changes" skill does not exist. The counter-argument is stronger though — the harness deliberately keeps verification scoped by purpose (deploy vs migration vs API vs a11y) so the reviewer can be adversarial about the *right* check, not a generic pass. A generic `/verify` risks becoming the "restates what Claude would do by default" anti-pattern from §3.

- **Option A** — add `skills/verify/SKILL.md` that dispatches to the applicable check skills based on `.harness-profile.quality_bar.*` flags. Low-cost, adds one entry point.
- **Option B** — reject; document the deliberate fragmentation in `AGENTS.md` and cite this post as the reason (verifiers should be adversarial, not comprehensive).

### Expected payoff
If A: one shortcut a consumer project can install into `.claude/commands/` for a "run everything mechanical" checkpoint. If B: durable answer to future PRs proposing a `/verify` skill.

**Verify before applying:** `find /home/user/claude-harness/skills -maxdepth 2 -name 'SKILL.md' | xargs grep -l 'verify\|verification' | head` — if a `verify` skill has been added since 2026-07-26, drop the suggestion; if the count of `*-check` skills has changed, re-evaluate whether Option B has grown stronger.

## 3. Audit skills against "restates what Claude would do by default" anti-pattern

**Source:** [Lessons from building Claude Code: How we use skills — Claude blog, 2026 (undated)](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills)

### Why it's relevant
The post's most durable rule: *"Claude already knows how to code and can read your codebase, so a skill that restates what Claude would do by default adds context without adding value. If you're publishing a skill that is primarily about knowledge, focus on information that pushes Claude out of its normal way of thinking."* This is the audit criterion the harness has been informally applying since Wave 25 (spec-planner's strict acceptance-check discipline) but has never written down or run systematically. The harness ships 24 SKILL.md files and vendors Anthropic's skill-authoring best-practices reference at `skills/skill-creator/references/anthropic-skill-authoring.md`, so the vocabulary exists — the sweep does not.

Candidates to sweep (by suspicion score, highest first):
- `skills/session-start/SKILL.md` — some of the "at start of day, read X" instructions may restate what Claude would infer from `.harness-state/` filenames.
- `skills/commit/SKILL.md` — the Step-1..Step-5 sequence may include steps Claude would do by default (staging, code-review invocation).
- `skills/park/SKILL.md`, `skills/micro/SKILL.md` — one-file skills whose payload is a workflow verb; check whether the verb is discoverable from `parking_lot.md` / `current_micro.md` naming alone.

The post's secondary rule — *"A common misconception about skills is that they are 'just markdown files'; they're actually folders that can include scripts, assets, data"* — is not a diagnosis of this harness (12 of 24 skills are multi-file — see the file counts in `skills/`), so no diff there.

## 4. Import 1–2 AI-native SDLC controls (SIEM audit events, risk-tiered approval)

**Source:** [How Anthropic secures its AI-native software development lifecycle — Claude blog, 2026-07-21 (Jason Clinton)](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)

### Why it's relevant
The post enumerates Anthropic's security stack for a codebase where ~80% of merged code is Claude-authored: remote development machines, egress allowlists, specialized review agents, deterministic scanners, risk-tiered human approval, and SIEM audit events. This harness already ships direct analogues for three of the six (`_shared/loop/safety/denylist.ts` = egress-ish gate; `code-reviewer` agent = specialized review; the mechanical gate = deterministic scanner). Two Anthropic-side controls are absent and would be tractable for a solo maintainer:

1. **Risk-tiered human approval.** The harness's HITL classifier (`skills/_shared/classifier/`) already routes items to worktree vs sandcastle vs human; it does not carry a *risk tier* per item (touches auth code → higher tier → mandatory human review regardless of gate outcome). Anthropic ties approval strictness to blast radius rather than to whether the AI happens to have needed a credential.
2. **SIEM-shaped audit stream.** `.harness-state/orchestrator.jsonl` is loop-local and readable. A per-item audit event with a stable schema (item id, runner, gate outcome, merged-sha, HITL-reason if any) exported to a durable append-only path outside `.harness-state/` would give the maintainer a review trail across sessions.

The counter-argument is scale: Anthropic ships this scaffolding because 8× coding velocity across dozens of engineers demands it. A solo maintainer already meets both goals by hand (every merge is human-reviewed; git history is the audit trail).

### Concrete change (if pursued)
Not a diff. Two 1-line entries in `parking_lot.md`:
- `risk-tier field on WorkItem — see anthropic-reviews/2026-07-26-improvement-suggestions.md#4`
- `audit-event export from run-loop-driver — see anthropic-reviews/2026-07-26-improvement-suggestions.md#4`

Revisit when either (a) the harness gains a second maintainer or (b) a consumer project sits inside an org that requires an audit trail its compliance team recognizes.

### Expected payoff
None today (deferred). Later, catches the class of "silent merge of high-blast-radius change under a green gate" that the current binary AFK/HITL split misses.

**Verify before applying:** `grep -n 'risk_tier\|risk-tier\|SIEM\|audit_event' /home/user/claude-harness/skills/_shared/loop/types.ts /home/user/claude-harness/AGENTS.md` — if either concept has landed, drop the corresponding bullet.

**Recommended verdict:** defer until team grows past solo — controls target org-scale AI code volume; the solo maintainer already meets both goals with human final approval + git history.
