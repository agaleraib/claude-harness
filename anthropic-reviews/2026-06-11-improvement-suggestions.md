## 2. Reconcile Anthropic's new "dynamic workflows" with the harness's orchestrator-worker pattern

**Source:** [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) + the engineering deep-dive [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Companion docs: [Orchestrate subagents at scale with dynamic workflows — code.claude.com/docs/en/workflows](https://code.claude.com/docs/en/workflows). Companion product trigger: the `ultracode` Claude Code setting that "sets the effort level to xhigh while letting Claude decide automatically when to use a workflow."

### Why it's relevant

Anthropic's framing on June 2 is striking: *"Claude can now write its own harness on the fly, custom-built for the task in front of it, instead of always running inside the one default harness shipped for coding."* The post defines a **harness** as "the system around the model… [that] decides how work gets split, which subagents spawn, what tools each one gets, how their output is verified, which model handles which step, how work is isolated, and when the job is actually done."

That is **literally the job of `.claude/agents/orchestrator.md`** in this repo. The orchestrator currently:

- Parses a spec, extracts tasks, builds a dependency graph (Step 3, lines 75–106).
- Routes each task to opus / sonnet / haiku based on a runtime complexity judgment + per-task `**Effort:**` hints (Step 4, lines 110–166).
- Dispatches subagents and logs a two-surface decision record (Step 8, JSONL + console).

What dynamic workflows add on top of that:

- **Self-generated orchestration scripts.** Claude writes the JS script per task; the harness here uses a spec-defined task list (manual upstream + planning-loop polish).
- **Tens-to-hundreds of parallel subagents per invocation.** This harness's orchestrator dispatches sequentially-then-parallel from the spec's dependency graph; the parallelism ceiling is whatever the spec says.
- **Native handling of three named failure modes**: *agentic laziness* (bails after partial progress), *self-preferential bias* (leans toward its own outputs when verifying them), *goal drift* (degradation over many turns). None of these terms appear in the harness today (`grep -rn "agentic laziness\|self-preferential\|goal drift" /home/user/claude-harness` returns zero hits) — which is **not** a gap necessarily, but is a vocabulary the orchestrator's design intent should now be reconciled against.

The semantic overlap is real, the layer-split is real, and the resolution is not obvious without a design pass:

- **Option A — Cite + complement:** Document explicitly that this harness's orchestrator is the **planning-and-routing** layer; dynamic workflows are the **execution** layer Claude Code can now spin up below it. The harness chooses the model and effort; the dynamic workflow Claude Code generates implements that task in parallel. The two compose. (Closest to the existing 2026-05-10 §1 framing of `code-reviewer` vs. cloud Code Review.)
- **Option B — Defer-to-native:** Retire some of the orchestrator's routing rules (Step 4 buckets, Routing table) in favor of letting `ultracode` decide. Risk: surrenders the rubric-grounded, spec-driven discipline that's the harness's whole point.
- **Option C — Hybrid documentation:** Same as A, but additionally add a section to `skills/run-wave/SKILL.md` and `.claude/agents/orchestrator.md` naming the three failure modes (agentic laziness, self-preferential bias, goal drift) as the failure modes the harness's planner → orchestrator → code-reviewer → planning-loop cycle is *designed to address*. (Harness already addresses all three, just without that vocabulary.)

This is precisely the shape of "needs a design pass via `/spec-planner` before any coding" — not because the right answer is unclear (Option A or C is the obvious starting point), but because **the wrong answer (Option B) is a real risk** if a future micro-session tries to "simplify" the orchestrator without thinking about it.

### Concrete change

None this run. Recommended spec scope when picked up:

1. Spec name: `docs/specs/2026-06-11-orchestrator-vs-dynamic-workflows.md` (or whatever date `/spec-planner` runs).
2. Inputs: the two Anthropic posts above + `code.claude.com/docs/en/workflows` + this repo's `.claude/agents/orchestrator.md`, `skills/run-wave/SKILL.md`, `skills/planning-loop/SKILL.md`.
3. Discovery questions: (a) Does the harness still need its own routing buckets if `ultracode` exists? (b) Is the planner → generator → evaluator pattern (Wave 4 `auto-apply-arbiter` work, planning-loop) at risk of being subsumed? (c) What's the smallest README + orchestrator.md edit that names the layer-split so a future reader doesn't ask the question cold?
4. Expected output: 1–2 README paragraphs + 1 orchestrator.md section + a decision doc in `docs/decisions/`.

### Expected payoff (when applied)

Forestalls a future "rewrite the orchestrator" instinct that misreads layer-split as redundancy. Names the failure modes (agentic laziness, self-preferential bias, goal drift) so the harness's existing design intent is *explicit* against Anthropic's published vocabulary, not implicit. Cost: 1–2 hours of spec-planner discovery + 30 minutes of doc edits.

### Why this isn't `apply` or `defer`

`apply` is wrong because the right concrete edit is genuinely unclear without thinking about it — the choice between Option A vs. C above isn't obvious from the post alone.

`defer` is wrong because dynamic workflows are GA now (Max/Team/Enterprise + the API/Bedrock/Vertex/Foundry surfaces) and a future maintainer encountering `.claude/agents/orchestrator.md` will likely ask "is this still needed?" cold. The longer that question goes unanswered in the repo, the higher the risk of a misguided simplification.

`spec` matches the routine's own rubric: "needs a design pass via /spec-planner before any coding."

**Verify before applying:**

1. `grep -rn "dynamic workflows\|ultracode\|claude.com/blog/a-harness-for-every-task" /home/user/claude-harness` — must return zero hits today; if it returns hits, the spec / docs have already been written and this § is stale (re-evaluate as `apply` follow-up cleanup).

3. Confirm `.claude/agents/orchestrator.md` Step 4 routing buckets are still intact (`grep -n "Route to Haiku when\|Route to Sonnet when\|Route to Opus when" .claude/agents/orchestrator.md`). If the orchestrator has been refactored in the meantime, the spec inputs need refresh.

**Recommended verdict:** spec — Option A vs. C is genuinely ambiguous; Option B is a risk that explicit documentation forestalls. `/spec-planner` is the right rung. Don't ship a micro-edit without thinking.

## 4. Note the HTML-over-Markdown shift for artifact-producing skills

**Source:** [Using Claude Code: The unreasonable effectiveness of HTML — claude.com/blog, 2026-05-20](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html) by Thariq Shihipar (Claude Code team). Core claim: Markdown has become dominant for human-AI communication, but as outputs get longer / more complex, Markdown's read-back failure mode (Claude struggles past ~100 lines) and limited expressivity (no color, no diagrams, no custom UI) bite. HTML — with inline CSS + JS — is a better default for **specs, code reviews, architecture explainers, design explorations, research reports, and custom editing interfaces**.

### Why it's relevant (but speculative)

The harness's artifact-producing surfaces are *all Markdown* today:

- `anthropic-reviews/*.md` (this very file).
- `docs/specs/*.md`.
- `docs/plan.md`.
- `.harness-state/last_exit.md`, `today_goal.md`, `current_micro.md`.
- `parking_lot.md`.
- Skill outputs (`run-wave` synthetic spec at `/tmp/wave-*.md`, etc.).

A maximalist reading of the post would say: bump everything to HTML. That is a **bad** reading for this harness because:

- All consumers of these files are *the next Claude Code session*, not a human reading on a phone. Markdown round-trips losslessly through CLI tooling; HTML doesn't.
- The post's own examples (code reviews with color highlights, architecture explainers with embedded diagrams) presume an interactive **human** consumer with a browser. The harness's consumer for most of these files is the next session's `session-start` rather than a person.
- Markdown's "Claude struggles past 100 lines" failure mode is not the harness's bottleneck — the harness's discipline is to keep files short (planning-loop trims, plan.md `keep_last` cleanup, micro-session brevity).

But the post is **not wrong** for two narrow surfaces in this repo:

1. **Generated review reports / artifact files** that a human will actually look at, such as `skill-creator/eval-viewer/viewer.html` (already HTML!) and `skill-creator/assets/eval_review.html` (already HTML!). These were built before this post; the post corroborates the existing design.
