## 2. Document the Claude Code `MEMORY.md` auto-load hard cap (200 lines / 25 KB) and the one-writer-per-page rule in `AGENTS.md`

**Source:** [The components of agent memory — anthropic.com/research, 2026-11-06](https://www.anthropic.com/research/components-of-agent-memory)

### Why it's relevant

The post gives two concrete, numeric constraints that directly bind the harness's per-cwd auto-memory pattern:

1. **"Auto memory loads only the first 200 lines or 25 KB of `MEMORY.md` into each session."** This is a *Claude Code product-level truncation* — not an advisory limit. Anything past that is not read.
2. **"One writer per page."** The Pokémon experiment lost 16 of 57 facts when concurrent agents wrote to a shared table; one-page-per-agent kept all 57.

`AGENTS.md` currently documents:
- `FEEDBACK.md` ≤ 5 KB hard cap (line 75)
- Line budget ≤ 150 chars per line (line 75)

This matters because:
- The harness's `/run-wave` orchestrator can dispatch multiple subagents in parallel, all operating on the same per-cwd `~/.claude/projects/<encoded-cwd>/memory/MEMORY.md`. The one-writer rule is already implicitly honored (Claude Code writes `MEMORY.md` from the primary session, not from spawned subagents), but a future maintainer refactoring the orchestrator won't know this is load-bearing.
- A `MEMORY.md` that silently grows past 25 KB will have its tail invisibly dropped. `/memory-prune` already enforces discipline on `FEEDBACK.md` (≤ 5 KB) but doesn't surface the 25 KB cap on the per-cwd `MEMORY.md` itself.

1. **Event inbox** — durable queue; webhooks, schedules, user messages; single-worker drain

## 6. Rework `criteria/*.md` rubrics toward atomic-binary grader dimensions + grader versioning + known-good/known-bad fixtures

**Source:** [Building strong safety evaluations — anthropic.com/research, 2026-11-13](https://www.anthropic.com/research/building-strong-safety-evaluations)

### Why it's relevant (scope: speculative)

The 2026-11-13 post publishes Anthropic's eval-design doctrine:

- **Atomic, binary rubric criteria** (not Likert): "Make criteria atomic and binary. Spell out edge cases and what should not change a verdict."
- **Grader-model separation**: "Use a different model from the one being tested."
- **Known-good / known-bad fixtures**: "Maintain a small fixed fixture set with known-good and known-bad examples, and rerun it whenever a rubric or model changes."
- **Reproducibility**: "Preregister metrics and thresholds. Run cases multiple times, report confidence intervals, use paired comparisons, and document configuration."
- **Fail loudly**: "Flag and exclude items where the grader breaks, and alert when grader behavior drifts."

The harness's `criteria/` directory contains 6 rubrics (`code-architecture.md`, `code-simplicity.md`, `data-integrity.md`, `frontend-ui-design.md`, `performance-accessibility.md`, `ux-user-flows.md`), all using **1–10 Likert per dimension** (see `criteria/code-simplicity.md` heading: "Scoring: 1-10 per dimension, all weighted equally"). The `code-reviewer` agent consumes these; `skill-creator/references/schemas.md:98, 134, 169, 221` already has a grader-agent concept but it's local to the skill-creator flow, not applied to criteria/ rubric adjudication.

### Scope: speculative — why this is a `defer`, not `apply`

Migrating to atomic-binary is a **cross-cutting refactor**:
- 6 rubric files need restructuring
- `code-reviewer` agent instructions need to accept a different scoring shape (pass/fail per criterion, with confidence) and drop the dimension-weighting roll-up
- A fixtures directory needs to exist with hand-labeled known-good/known-bad examples per criterion
- Grader-versioning metadata needs to attach to every rubric-scored artifact (`.harness-state/` reviewer receipts would gain a `grader_version:` field)
- Integration with `/commit` flow's existing rubric-score gating needs to be rethought

Anthropic's post is explicit that the statistical floors (100 / 1,000 items) are designed for large evals; a solo harness will have much higher variance, and the post itself tempers: "the practical takeaway is to report uncertainty and treat small score differences skeptically." That tempering is important — adopting atomic-binary without also adopting the statistical rigor just loses expressiveness.

### Concrete changes

None in this run. A `/spec-planner` pass should produce `docs/specs/<date>-criteria-atomic-binary-migration.md` covering:
1. New rubric schema (atomic criteria list + per-criterion pass/fail + explicit "does-not-change-verdict" exclusions)
2. Grader model separation (name the grader model distinctly from the reviewer agent's own model)
3. Fixtures directory (`criteria/fixtures/<criterion-slug>/{known-good,known-bad}/*.md`)
4. Grader-version metadata on every reviewer receipt
5. Migration order (which rubric first, consumer-project impact)

### Expected payoff (if later built)

- Rubric scores stop sliding when the underlying model changes (grader versioning)
- The adversarial `code-reviewer` agent has a measured false-positive / false-negative rate against fixtures, not a vibes-based "I think this is a good reviewer"
- `/ultrareview` and the local `code-reviewer` produce comparable verdicts because both can be scored against the same fixtures

**Verify before applying:**
- `grep -n "Scoring: 1-10" /home/user/claude-harness/criteria/*.md` — if all 6 files still use Likert, the migration is still needed.
- Check `docs/specs/` for an existing atomic-binary or rubric-grader spec; if one exists, dedupe.
- Confirm `skill-creator`'s grader-agent pattern (from `skills/skill-creator/references/schemas.md`) hasn't been generalized to criteria/ in the interim — if yes, half the plumbing already exists.

**Recommended verdict:** defer — needs `/spec-planner` before any file edits (scope: speculative; cross-cutting ≥6 files + reviewer agent + state-schema changes).
