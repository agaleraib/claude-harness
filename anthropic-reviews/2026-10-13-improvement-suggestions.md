## 5. Re-affirm deferred 2026-04-19 §5 (agent evals) using hillclimbing + held-out set as the concrete design

**Source:** [Automating eval design and hillclimbing with Claude — claude.dev/blog, 2026-09-28](https://claude.dev/blog/automating-eval-design-and-hillclimbing/) (as reported via secondary coverage; the claude.dev domain was unreachable from this session's proxy — the pattern is corroborated by the [Model configuration docs](https://code.claude.com/docs/en/model-config) and the [Claude API skill](https://claude.com/blog/claude-api-skill))

- **Hillclimbing loop** — one change at a time, score it, keep if score rises, revert otherwise.
- **Held-out set** — guards against overfitting (bake-off vs. training set).
- **Production transcripts + bug reports + human examples** as eval-data sources.

- The held-out set is a well-known anti-overfit knob.

- 2026-04-19 §5 was deferred because `code-reviewer` / `ui-evaluator` lack fixture suites to score against. Hillclimbing is downstream of that — you cannot hillclimb without a scored eval. The blocker is unchanged.

## 7. Lift the "narrow reviewer with evidence" pattern into `code-reviewer` + `/security-review`

**Source:** [How Anthropic secures its AI-native software development lifecycle — claude.com/blog, 2026-07-21](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)

### Why it's relevant

The post describes several practices Anthropic's Security Engineering team uses to review AI-authored code at scale. Three transfer to this repo:

1. **Several narrow review agents, separate context windows, over one broad prompt.** *"Their blind spots differ, and one can catch another's mistake."* This repo's `code-reviewer` agent is one agent running `criteria/code-architecture.md` + `criteria/code-simplicity.md` + `criteria/data-integrity.md` + three more criteria files, all in one context. The post's shape is 5–8 narrower reviewers, each with one criterion, run in parallel. Different recall/precision regime from a single adversarial reviewer.
2. **Require evidence for findings.** *"Require reviewers to back findings with evidence, such as a proof of validity, to improve signal."* This repo's `code-reviewer` reports findings via `ReportFindings` with a `failure_scenario` field — already partway to the shape. The post pushes toward an explicit `verdict: CONFIRMED | PLAUSIBLE` dimension with evidence attached.
3. **Deterministic SAST alongside agentic review.** The post pairs agentic review with SAST (static analysis) scans. This repo has nothing deterministic in the review pipeline — the `code-reviewer` agent *is* the review. A deterministic layer (semgrep? a repo-specific linter?) would catch the known-shape bugs the agent misses on long sessions.

### Why `spec` not `apply`

Any of these three changes is substantive on its own:

- (1) rewrites the `code-reviewer` agent definition and changes `/commit`'s flow. Also multiplies the token spend per commit — needs a cost-vs-signal design pass.
- (2) is a schema change to `ReportFindings` output and all its consumers.
- (3) picks a SAST tool, decides whether it's a hook or a `/commit` step, and gates on cost.

The post is strong primary-source material for an eventual `code-reviewer` redesign spec; it is not a single-paragraph doc edit.
