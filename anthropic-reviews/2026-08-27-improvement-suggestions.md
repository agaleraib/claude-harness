## 1. Add `claude doctor` to `setup-harness` post-install checks and to `harness-status` as an optional lint

**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models). The post accompanies the Opus 5 launch. Key thread across the search corroboration: Anthropic cut Claude Code's system prompt by ~80% for the Claude 5 generation, and shipped a `claude doctor` (aliased `/checkup`) command that inspects the installed CLAUDE.md files, skills, MCP servers, and plugins, deduplicates local against checked-in CLAUDE.md, proposes trimming derivable content, and flags slow hooks.

### Why it's relevant
The whole reason `claude-harness` exists is to be **the** central authority on CLAUDE.md, AGENTS.md, skills, and agents that ship out to consumer projects via `setup-harness`. Anthropic now ships an official CLI-side auditor for exactly that concern. The harness does not mention it anywhere:

- `grep -rn "claude doctor\|/doctor\|claude-doctor" .` returns nothing (verified 2026-08-27).

Meanwhile the actual state of the repo suggests low but non-zero doctor exposure:

- 24 skills, several long (`skills/planning-loop/SKILL.md` 719 lines, `skills/close-wave/SKILL.md` 675, `skills/skill-creator/SKILL.md` 488, `skills/run-wave/SKILL.md` 446 — see `wc -l skills/*/SKILL.md`).
- `CLAUDE.md` at 35 lines and `AGENTS.md` at 131 lines are already under the widely-reported 200-line target for CLAUDE.md — no cleanup pressure there.

The high-value use of `/doctor` here is (a) **at `setup-harness` time on consumer machines** — where a bloated pre-existing local CLAUDE.md may duplicate the harness's checked-in one; and (b) **as an on-demand lint the maintainer can run from `harness-status`** to see what Claude 5's routing considers dead weight in the shipped skills.

### Concrete change
Two small edits, both single-file:

1. **`skills/setup-harness/SKILL.md`** — add a "Post-install verification" step (or extend an existing one) with:

   ```markdown
   ### Post-install: run `claude doctor`
   After `setup-harness` completes, run `claude doctor` (alias `/checkup` from inside a Claude Code session). It will:
   - deduplicate any pre-existing local CLAUDE.md against the harness-installed one,
   - list skills / MCP servers / plugins the runtime considers unused vs. their context cost,
   - flag slow hooks,
   - propose CLAUDE.md trims Claude can derive from the codebase.
   Treat its output as advisory — a solo methodology repo can legitimately keep skills that are rarely triggered.
   ```

2. **`skills/harness-status/SKILL.md`** — add a one-line optional footer under an existing "diagnostics" section (or create one) noting: *"For a context-cost audit of the installed skills / MCP servers / plugins, run `claude doctor` (or `/checkup`) — it reports what the Claude 5 runtime considers dead weight."*

### Expected payoff
The next time a consumer project runs `setup-harness` on top of an existing CLAUDE-heavy repo, the maintainer of that project sees Anthropic's own audit report — before the noise compounds and the harness gets blamed for context bloat that predated it. Also gives future-you a one-command way to see whether a new skill has drifted into unused territory.

### Why this isn't overkill
The skill body is prescriptive text, not a hook — no new automation, no new files. If `claude doctor` disappears from a future CLI release the line just goes stale (like the many `claude --version`-forensic breadcrumbs already in the repo).

**Verify before applying:**
1. `grep -rn "claude doctor\|/doctor\|claude-doctor\|/checkup" /home/user/claude-harness` — must return nothing today; if it returns hits, the guidance has already landed and this § is stale.
2. Confirm `claude doctor` (or `/checkup`) still ships in the current Claude Code CLI — run `claude doctor --help` locally. If Anthropic renames or deprecates it before the § is applied, adjust the command name in the two skill edits accordingly.
3. Read the live post at `https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models` end-to-end (this run could not — proxy blocked) and confirm the `claude doctor` semantics as described above still match; if the post has shifted to a different tool name, mirror the change.

**Recommended verdict:** apply — two single-file text edits, one command reference each, verified as absent from the repo, aligned with the exact concern the methodology repo already exists to address.

## 5. Adopt the "match surrounding context" phrasing pattern instead of `DO NOT` / `NEVER` in skill and agent prompts

**Source:** Same post as §1 — [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models). The recurring pattern across search corroboration: Anthropic now recommends **replacing strict negative constraints** (`DO NOT add comments`) **with judgment-oriented guidance** (`match the surrounding code's comment density, naming, and idiom`). Rationale: hard negatives that once prevented worst cases now conflict with Claude-5-generation defaults and waste tokens.

### Why it's relevant (and speculative)
The harness's skills and agents use `NEVER` / `DO NOT` / `MUST NOT` extensively — a quick spot-check of `skills/planning-loop/SKILL.md` and `skills/close-wave/SKILL.md` shows several. But **whether rewriting them is net-positive is not obvious**:

- Some are anti-catastrophic (denylist commands, hooks security). Those stay hard-negative regardless — safety guardrails are exactly the case Anthropic still endorses.
- Some are workflow guidance ("never skip step X") — these are the candidates for "match surrounding context" rewrite.
- Distinguishing the two requires reading each hit in context, which is easier once §1's `claude doctor` run produces evidence of which constraints Claude 5 is treating as noise.

**scope: speculative** — this § is a direction, not a shippable change. The concrete work is (a) an audit that classifies each `NEVER`/`DO NOT` hit as safety vs. workflow, and (b) rewrite of the workflow subset. Neither is authored here.

### Concrete change
Two-step, sequenced after §1:

1. **After §1 lands and `claude doctor` has produced its report against this repo**, grep the diff Anthropic's tool proposes:

   ```
   grep -rn "NEVER\|DO NOT\|MUST NOT\|Never\|Do not\|Must not" skills/ agents/ CLAUDE.md AGENTS.md .claude/ | tee /tmp/hard-negatives.txt
   ```

   Cross-reference each hit against the `claude doctor` report — flag ones Anthropic's auditor considers dead weight.

2. **Rewrite only the workflow-guidance subset**, leaving safety guardrails hard-negative. The rewrite pattern is illustrated by Anthropic's own example: from `DO NOT add comments` → `match the surrounding code's comment density, naming, and idiom`.

### Expected payoff
Skills that Claude 5 executes with less friction, and a smaller context footprint on skill-load. **Not** removal of any safety-critical guardrail.

### Why this is a defer, not an apply
Because the value depends on (a) evidence from `claude doctor` about which negatives are actually creating conflict and (b) careful safety-vs-workflow classification. Doing this blindly risks weakening a guardrail that mattered.

**Verify before applying:**
1. Confirm §1 has landed (`grep -n "claude doctor" skills/setup-harness/SKILL.md skills/harness-status/SKILL.md`).
2. Confirm `claude doctor` has actually been run against the harness at least once and its report captured (as a comment on the applied §1 PR, or in `.harness-state/`).
3. Read `https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models` (blocked in this run) end-to-end and confirm the "match surrounding context" phrasing pattern is still Anthropic's current recommendation before starting the rewrite.
4. Do NOT rewrite hard-negatives in `.claude/settings.json` hooks, in the catastrophic-command denylist (`skills/_shared/loop/safety/denylist.ts`), or in any acceptance-check enforcement (`skills/planning-loop/SKILL.md` fail-closed logic) — those are the safety-guardrail category and stay hard-negative.

**Recommended verdict:** defer until §1 doctor-audit output lands — evidence-gated, sequenced downstream of §1, and the safety-vs-workflow split needs a design pass. Reconsider as `spec` if the audit output is ambiguous.
