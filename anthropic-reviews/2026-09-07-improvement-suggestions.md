**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) (Thariq Shihipar). - Some rules in `run-loop/`, `planning-loop/`, `spec-planner/` encode invariants the loops depend on (e.g. `.harness-state/orchestrator.jsonl` schema); those must not be dropped without a downstream review.

## 3. Decide the harness's posture toward native dynamic workflows

**Sources (batched — one announcement + one deep-dive):**
- [Introducing dynamic workflows — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (product announcement)
- [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (engineering deep-dive by Thariq Shihipar and Sid Bidasaria)

### Why it's relevant
Dynamic workflows are now a native Claude Code primitive — the `Workflow` tool is visible in this session's tool list, along with a `workflow-authoring` skill in the available-skills index. Anthropic's framing is deliberately harness-shaped: **"Claude Code writes its own harness on the fly, custom-built for the task at hand."** The deep-dive post's title (`a harness for every task`) collides with this repo's name (`claude-harness`) on a conceptual level.

The overlap surface with existing harness skills:
- `.claude/agents/orchestrator.md` (runtime model routing across subagents) — solves ~30% of what dynamic workflows solve, but as a subagent, not a workflow script.
- `skills/run-loop/` (scheduled recurring work with wave/issue sources) — solves the "long-running task" axis, but dynamic workflows aren't scheduled; they're one-shot at high fan-out.
- `skills/run-wave/` (deterministic wave dispatch) — same neighborhood as a dynamic workflow's fan-out step.

**Why this is `defer` rather than `apply` or `spec` today:**
1. The `Workflow` tool is opt-in via the `ultracode` keyword (or an explicit user request) — it will not fire unless someone types it. Zero risk of the harness's orchestrator getting silently replaced.
2. The harness targets `team.size: solo` and `stakes.level: medium` (per `.harness-profile`); dynamic workflows are pitched at high-fan-out multi-agent research and code review — a scale the harness doesn't yet reach.
3. `orchestrator.md` already routes work across models; running a dynamic workflow *inside* an orchestrator dispatch would double-wrap. Deciding how (or whether) to compose them needs at least one real use case, not a speculative refactor.
4. Neither post cites a case where dynamic workflows replaced a hand-built orchestrator loop; they're pitched at problems where no harness exists yet.

### Concrete change
None right now — this § is a **bookkeeping note** so the parallel is captured in the durable record. The action-forcing trigger is:

- If a maintainer prompt in the anthropic-reviews routine (or another scheduled skill) hits `ultracode` and produces a dynamic workflow, use that concrete artifact to write a spec on how workflows and `orchestrator.md` compose.
- If the harness ever needs to fan out to > 5 parallel subagents (currently it doesn't), that's the trigger to reach for the `Workflow` tool instead of adding fan-out to `run-wave`.

### Expected payoff
Prevents a "should we rewrite the orchestrator on top of dynamic workflows?" scope creep from being asked without an accumulated cost basis. Also flags the collision with the harness's name, so if Anthropic's post ever gets cited in the README the maintainer knows to distinguish the two "harnesses".

**Verify before applying:**
1. `grep -rn "dynamic workflows\|dynamic-workflow\|Workflow tool\|Workflow(" /home/user/claude-harness --include='*.md'` — must return zero hits in live prose today; if hits appear, the parallel has already been captured and this § is redundant.
2. Check `orchestrator.md` and `run-loop/SKILL.md` for any TODO or FIXME mentioning fan-out beyond 5 subagents — that's the trigger condition for promoting this § to `spec`.
3. Check `.harness-profile` for `team.size` or `stakes.level` — if either has risen since 2026-04-11, revisit the "solo-scale" premise.

**Recommended verdict:** defer until orchestrator overlap is measured against a real workload — no action-forcing signal today, and the wrong action (speculatively replacing `orchestrator.md`) is worse than doing nothing.
