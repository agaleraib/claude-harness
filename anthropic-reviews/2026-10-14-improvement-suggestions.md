## 1. Migrate `.harness-profile` from Opus 4.7 / Sonnet 4.6 → Opus 5.5 / Sonnet 5.5 (and surface Haiku 5.5 as a routing option)

**Sources:**
- [Introducing Claude Opus 5.5 — Anthropic News, 2026-09-22](https://www.anthropic.com/news/claude-opus-5-5)
- [Introducing Claude Sonnet 5.5 — Anthropic News, 2026-09-28](https://www.anthropic.com/news/claude-sonnet-5-5)
- [Introducing Claude Haiku 5.5 — Anthropic News, 2026-10-07](https://www.anthropic.com/claude-haiku-5-5)

### Why it's relevant

Five months after the 2026-04-19 §1 bump from Opus 4.6 → Opus 4.7, Anthropic has shipped **three new models in the 5.5 family** and this session itself runs with fallbacks `claude-opus-5-5[1m]`, `claude-opus-5[1m]` configured — i.e. Opus 5.5 is already the serving model when the configured Opus 4.7 is unavailable. The harness, meanwhile, still pins:

```yaml
# .harness-profile:30-32
model:
  primary: claude-opus-4-7
  fallback: claude-sonnet-4-6
  effort_default: xhigh
```

Model-ID deltas (per the release posts):

| Role | Current pin | 5.5-family equivalent | Pricing |
|---|---|---|---|
| primary (reasoning-heavy work) | `claude-opus-4-7` | `claude-opus-5-5` | $4 input / $20 output per 1M (cheaper than Opus 5) |
| fallback (bulk coding) | `claude-sonnet-4-6` | `claude-sonnet-5-5` | $2 input / $10 output per 1M (same as Sonnet 5; cache-read halved on Oct 7) |
| not pinned (small tasks) | — | `claude-haiku-5-5` | $0.10 input / $0.50 output per 1M (prompts ≤100k); first Haiku with an adjustable effort setting |

**Behavioral deltas to validate before swapping (the reason this is `spec`, not `apply`):**

1. **Thinking cannot be turned off in Opus 5.5.** Per the Opus 5.5 post: "It is also no longer available with 'thinking' mode switched off." The harness doesn't configure thinking today, so this probably doesn't bite — but any downstream project pinning `thinking: false` will break. `grep -rn "thinking: false\|thinking: off\|think_off" .` is the pre-flight.
2. **`between_tools` setting required for thinking-off Sonnet 5.5.** Per the Sonnet 5.5 post: "If you run Sonnet with thinking off, you must switch to the new `between_tools` setting before moving to Sonnet 5.5." Same `grep` applies.
3. **Preserved thinking (anti-distillation).** Preserved thinking is now tied to the account that created it; switching accounts mid-session is affected. The harness runs under a single account per session, so this is a note rather than a block.
4. **Default effort on Claude Code sessions is "Medium"** per the Sonnet 5.5 post ("Default effort is Medium in Claude Code and the apps, and High on the Claude Platform"). The harness pins `effort_default: xhigh` and the orchestrator respects it, so this should be unaffected — but worth confirming the `${CLAUDE_EFFORT}` interpolation (noted in the 2026-04-30 skip row) still accepts `xhigh` when the serving model is 5.5.
5. **Cyber safeguards.** Sonnet 5.5 routes higher-risk cybersecurity requests back to Sonnet 5 "visibly." The harness does `/security-review`-adjacent work in `procedures/api-security-checklist.md`; routine bug finding is unaffected per Anthropic, but the spec should list which existing procedures might trigger a visible fallback.
6. **Tokenizer change in Haiku 5.5.** "It uses slightly more tokens per task than Haiku 4.5." If/when the harness ever routes to Haiku (not today — `.harness-profile` has no `routing:` block), token budgets need re-measurement — same note as the 2026-04-19 §1c "tokenizer_note" discussion.

The 2026-04-19 §1 bump (Opus 4.6 → 4.7) was itself spec'd as `docs/specs/2026-04-19-harness-model-pin-and-effort-routing.md` because the model-ID change touched `.harness-profile`, `project-init` defaults, every file under `docs/waves/wave1-*`, and the orchestrator's warning path. **A 4.7 → 5.5 bump has the same surface area plus the deltas above** — behavioral changes to validate before updating consumer-project defaults.  Recommended setup for solo users:

 1. Run `/fewer-permission-prompts` once in a project to seed an allowlist for the read-only Bash + MCP calls you actually use.
 2. Keep `.claude/settings.json` `hooks` block populated with your policy checks (lint, secret scan, etc.); Auto Mode will not bypass them.
-3. Toggle Auto Mode interactively via Shift+Tab. (As of writing, `permissions.defaultMode: "auto"` is parsed but doesn't reliably auto-engage on session start — manual toggle is the safer default. Re-check before relying on a config-only bootstrap.)
+3. +4. Admin-level controls (useful if the harness ever ships a shared `.claude/settings.json` for a team): pin `defaultMode` in managed settings, or set `disableAutoMode: true` to force manual review. [Running Auto Mode in production](https://claude.com/blog/auto-mode-in-production) reports ~10% of sessions see an Auto Mode denial — denies are the signal the classifier is doing real work.

## 3. Add a "Gotchas section" convention + 9-category tag to `skills/_shared/` so new skills follow Anthropic's internal pattern

**Source:** [Lessons from Building Claude Code: How We Use Skills — Thariq / Anthropic, 2026-06-03](https://x.com/trq212/status/2033949937936085378) (claude.dev mirror at `claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/` — not reachable from this execution environment but widely mirrored in third-party summaries). Direct Anthropic reference material: [The Complete Guide to Building Skill for Claude (PDF)](https://resources.anthropic.com/hubfs/The-Complete-Guide-to-Building-Skill-for-Claude.pdf).

### Why it's relevant

The Claude Code team disclosed that internally Anthropic sorts skills into **nine categories** (library/API reference, product verification, data fetching and analysis, business process automation, …; sources differ on the full list, flag that in the spec if written) and that **the highest-signal content in any skill is its "Gotchas section"**. One direct quote carried across the write-ups: *"Most of the best skills began as a few lines and a single gotcha, then got better as people kept adding to them."* The post also warns against stating what Claude already knows ("don't restate the obvious; that adds context without adding value") and recommends writing descriptions that say *when to use the skill*, not what the skill is.

How this stacks against the harness today (`skills/` has 25 directories as of `ls skills/ | wc -l`):

- The harness's own skills (`micro`, `commit`, `run-wave`, `close-wave`, `park`, `session-start`, `session-end`, `planning-loop`, `run-loop`, `apply-anthropic-reviews`, `setup-harness`, `project-init`, `triage-parking`, `memory-prune`, `harness-status`, `migration-check`, `archive-plan`, `shared-root-init`, `new-cowork`, `cowork-area-sync`, `deploy-check`, `api-smoke-test`, `a11y-check`) are overwhelmingly in the "business process automation" category — they encode the harness's own methodology. That's a legitimate single-category cluster, same shape as Thariq's "best skills fit cleanly into one."
- `_shared/` is the only non-skill directory (shared TS modules for `run-loop` + classifier).
- `skill-creator/` is the **vendored Anthropic skill-creator** (has `LICENSE.txt`, `agents/`, `assets/`, `eval-viewer/`, `references/`, `scripts/`) — modifying it in-place would collide with upstream. A harness-side convention has to live outside this directory.
- **No skill in the harness currently has a dedicated "Gotchas" section.** `grep -rn "^## Gotchas\|^## Gotcha\|^### Gotchas" skills/` returns zero. Several skills have inline "note:" / "watch out for" lines, which is the right content without the standard heading. (Candidates for the convention: `run-wave`, `close-wave`, `commit`, `park`, `session-start` — the ones where misuse has a visible blast radius.)

### Why this is `defer` rather than `apply`

Three considerations push this to a parking spot:

1. **Convention cost is only partly paid at the convention-definition step.** Adding "every SKILL.md should have a `## Gotchas` section" to a `skills/_shared/skill-conventions.md` is cheap. Backfilling 25 skills, deciding which three have real gotchas that need surfacing, and keeping that section honest after each change is the actual investment.
2. **The upstream `skill-creator` already encodes most of the "Lessons from" advice.** `skills/skill-creator/SKILL.md` lines 71–115 cover "Skill Writing Guide" / "Anatomy of a Skill" / "Progressive Disclosure" / "Principle of Lack of Surprise" / "Writing Patterns." The gotchas section is the one missing piece. Writing a harness-side override is lower leverage than filing an upstream suggestion to Anthropic.
3. **The nine-category framework is not fully disclosed in the write-ups.** Secondary sources differ on exact list. Encoding a classification scheme off third-party summaries locks in guesses.

### Concrete change (deferred — recorded here for when a trigger arrives)

**Trigger:** The next time the maintainer or an evaluator discovers a gotcha in a harness skill that a reader keeps re-discovering (e.g. a `/commit` flow that silently drops attribution footers, a `/run-wave` edge case that corrupts a `.harness-state/` file).

**Minimal first move:**
1. Create `skills/_shared/skill-conventions.md` with:
   - "Every SKILL.md ends with `## Gotchas` listing the top 3 ways people misuse this skill, when the list isn't empty. If there are no known gotchas yet, omit the section — don't fake content to satisfy a convention."
   - A single-sentence category tag at the top of each SKILL.md (`category: business-process-automation` is the default for most harness skills; a one-off `category: deploy-verification` fits `deploy-check`, `a11y-check`, `api-smoke-test`).
2. Add that known gotcha to the relevant skill as the seed entry.
3. Do **not** backfill speculative gotchas across all 25 skills. Grow the list organically as the trigger case keeps happening.

### Expected payoff (when applied)

The next external contributor (or future-you six months on) reads the top of each SKILL.md and sees the two things that matter most: what category this is (so they know what pattern to compare it to) and what traps to avoid. The 2026-06-03 post reports that at Anthropic the gotchas section is the first thing experienced skill authors read when debugging a new skill — the same convention becomes self-reinforcing here if the maintainer accepts it.

**Verify before applying:**
1. `grep -rn "^## Gotchas\|^## Gotcha\|^### Gotchas\b" /home/user/claude-harness/skills/` — must still return zero. If someone has already seeded the convention in a skill between runs, this § is partially stale.
2. `test -f skills/_shared/skill-conventions.md` — must return 1 (file doesn't exist) before writing it. If a conventions file already exists, update it in place rather than creating a sibling.
3. Confirm the vendored `skill-creator/` still ships without a Gotchas convention in its own writing guide — `grep -n "Gotcha" skills/skill-creator/SKILL.md`. If upstream has already added one (likely, since the post is from June and this is October), the harness should mirror the upstream heading name rather than invent one.
4. Verify the full 9-category list before relying on it: fetch [Anthropic's Complete Guide to Building Skill for Claude PDF](https://resources.anthropic.com/hubfs/The-Complete-Guide-to-Building-Skill-for-Claude.pdf) and extract the authoritative category names before writing the conventions file.

**Recommended verdict:** defer until skill-author pain surfaces — convention cost is in the backfill, not the write-up, and the trigger case hasn't landed. `scope: speculative` for solo tooling in the absence of a recurring gotcha.

## 4. Re-affirm the deferred 2026-04-19 §5 (agent evals) — Anthropic now ships `/claude-api build-eval` + `hillclimb` as a concrete path

**Source:** [Automating eval design and hillclimbing with Claude — Anthropic / Lance Martin, 2026-09-28 (claude.dev)](https://claude.dev/blog/automating-eval-design-and-hillclimbing/) (not reachable from this execution environment; title and content confirmed via Arize's write-up [here](https://arize.com/?p=32658) and The Neuron's summary; original source should be re-fetched at triage time to pull current CLI). Related session recording: [You should build evaluation engineers instead of evaluation sets](https://claude.com/code-with-claude/session/you-should-build-evaluation-engineers-instead-of-evaluation-sets).

### Why it's relevant

The 2026-04-19 §5 ("Formalize evals for the adversarial reviewers") was **DEFERRED until a consumer-project rubric suite needs regression coverage** — the gating condition was "fixture scaffolding is high-effort for solo tooling today." That gating condition hasn't changed. What has changed is that **Anthropic shipped two commands on the user-level `claude-api` skill** that collapse the "high-effort fixture scaffolding" step:

- **`/claude-api build-eval`** — interviews the user and builds an evaluation harness inside the codebase. Secondary sources quote: *"Claude iteratively improved Anthropic's own API skill from about 66% to 88%."* Starts from an existing skill + a few known-good traces.
- **`/claude-api hillclimb`** — the loop: make one change, score it, keep it if the score goes up, revert it if it doesn't, repeat. It holds out test cases, reverts changes that do not improve the test set, and reports uncertainty against the baseline.

The `claude-api` skill is already **available on every machine the harness installs onto** (it's bundled with Claude Code globally and appears in this session's available-skills list as `claude-api`). So a maintainer who picks up §5 later doesn't need to build the eval harness from scratch — the tooling is one slash command away.

### Why this is `defer`, not `spec`

1. **Original gating condition still holds.** The 2026-04-19 §5 defer was conditional on "a consumer-project rubric suite needs regression coverage." No such trigger has landed between April and October. The new tooling lowers the activation cost but doesn't change whether the activation is wanted today.
2. **`build-eval` works best starting from an existing skill with real traces.** The harness's `.claude/agents/code-reviewer.md` + the four `criteria/*.md` rubrics are the right seed, but the harness doesn't currently run `code-reviewer` at scale enough to have the hundreds of production traces that `hillclimb` wants for a representative hold-out set.
3. **Secondary-source caveat.** The direct Anthropic post isn't reachable from this execution environment (DNS doesn't resolve `claude.dev`), so the specific CLI shape above is reconstructed from third-party summaries (Arize, The Neuron, DEV). Spec'ing now would lock in details that need confirmation at build time.
4. **Promotion is reversible.** When/if the maintainer wants to pick up §5, this entry gives them the entry point (`/claude-api build-eval` → seed from `code-reviewer` + `criteria/`) rather than starting from scratch.

### Concrete change this run

None. The 2026-04-19 §5 status line stays `DEFERRED`. This § is a bookkeeping note so that a future reader of the April file sees the deferred item has a concrete tool path now.

### Expected payoff (if/when promoted later)

When a consumer project needs rubric regression coverage, the maintainer runs `/claude-api build-eval` with `code-reviewer` + `criteria/code-architecture.md` as the seed, generates ~30–100 held-out traces (per the Managed Agents guide's "30-100 realistic cases before expanding autonomy" rule), and lets `hillclimb` iterate the `code-reviewer` prompt against the rubric. Expected outcome by analogy with Anthropic's self-reported `claude-api` skill run: a reproducible score gain documented against a held-out set (not vibes-driven as 2026-05-08 §2 warned).

**Verify before applying (when a trigger lands):**
1. `grep -n "DEFERRED until a consumer-project rubric suite needs regression coverage" anthropic-reviews/2026-04-19-improvement-suggestions.md` — should still return line 220. If the status has been changed, re-read §5 before using this entry as the pointer.

**Recommended verdict:** defer until a consumer-project rubric suite needs regression coverage — same gating condition as 2026-04-19 §5; the delta is a concrete tool path (`claude-api build-eval`+`hillclimb`), not a change in demand. Bookkeeping only.
