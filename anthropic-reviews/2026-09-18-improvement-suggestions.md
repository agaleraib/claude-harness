## 2. Cite "How we contain Claude across products" as background evidence that Claude Code already sandboxes — the harness's worktree isolation is a workflow boundary, not a security boundary

**Source:** [How we contain Claude across products — anthropic.com/engineering, 2026-05-30](https://www.anthropic.com/engineering/how-we-contain-claude) — Anthropic's post on how they cap agent blast radius across Claude.ai (gVisor), Claude Code (Seatbelt on macOS, Bubblewrap on Linux), and Claude Cowork (full VMs). The post also discussed three vulnerabilities in Claude Code where hook-loading during clone/startup executed before the trust prompt.

### Why it's relevant
The harness's use of `.claude/worktrees/agent-<id>/` (referenced in `CLAUDE.md` "Loop protocol — Claude Code invocation notes") looks like an isolation mechanism if you skim it, but it's actually a **workflow** boundary — separate branches for concurrent agent dispatch, not a sandbox. Anthropic's post makes the actual containment layer explicit: Claude Code sits inside Seatbelt (macOS) or Bubblewrap (Linux). That's the security boundary; worktrees are just parallel branches.

There's currently **nothing in the harness that names this distinction**. If a future maintainer (or a consumer-project reader) treats the worktree convention as security-relevant, they'll make wrong decisions — e.g., relaxing the denylist because "worktrees isolate it anyway."

The post also names a real risk pattern the harness's `PreToolUse` denylist ostensibly addresses (a `.claude/settings.json` hook executing on clone before the user consents). Worth naming as evidence that the denylist is doing work.

### Why this is `defer`, not `apply`
Applying this today would need a section in the harness README that **doesn't exist yet** — "threat model" or "isolation & trust model". Adding one is a real design decision (what belongs? what's out of scope for a doc-only harness?), and the "How we contain Claude" post is not itself a strong forcing function for it. If the maintainer wants to add such a section for other reasons, this citation slots in naturally; if not, adding a paragraph on isolation just to cite a post is architecture-for-architecture's-sake.

### Concrete change (deferred)
When (if) an "Isolation & trust model" section gets written:

```markdown
### Isolation & trust model

The harness relies on Claude Code's own containment for security (Seatbelt on macOS, Bubblewrap on Linux — see [How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude), May 2026). The `.claude/worktrees/agent-<id>/` convention that `/run-wave` and `/run-loop` use is a **workflow** boundary — parallel branches for concurrent agent dispatch — not a security boundary. The `PreToolUse` denylist for catastrophic commands (installed globally via `~/.claude/settings.json`; see `/run-loop` "Human-only TODOs") is the harness's contribution to the trust story; it catches command classes Claude Code's sandbox alone doesn't (e.g., `rm -rf ~`).
```

Optional: one line under `README.md` "References":

```markdown
- [How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude) — Anthropic's containment story (May 2026); Claude Code uses Seatbelt/Bubblewrap. Background for the harness's denylist hook rationale.
```

### Why not `reject` outright
The **background** (Claude Code has real sandboxing; harness worktree ≠ sandbox) is worth writing down eventually; forgetting the distinction is exactly the kind of thing a solo maintainer will "discover" the third time they explain it to somebody. `defer` gives it a triage lane without wasting a PR-round on it now.

**Verify before applying:**
1. `grep -rn "seatbelt\|bubblewrap\|isolation.*model\|trust.*model" /home/user/claude-harness --exclude-dir=anthropic-reviews` — must return nothing under README/docs; if it hits, someone wrote the section already and this § is stale.
2. Confirm the Seatbelt/Bubblewrap details are still accurate at apply time — the post is a snapshot; Anthropic could ship a different containment strategy in a future Claude Code release. Re-check `code.claude.com/docs/en/best-practices` for the current sandboxing statement.

**Recommended verdict:** defer until the maintainer decides to write a trust-model section — the citation is worth ~2 lines and belongs in an existing structure that doesn't exist. Track alongside the deferred 2026-04-19 §2 Managed Agents item as a "cite when architecture allows" bookkeeping row.

## 3. Adopt Anthropic's test-impact-analysis pattern for the harness's own test suite

**Source:** [Agentic coding is straining CI. Here's how we scaled test impact analysis at Anthropic — claude.com/blog, 2026-09-14](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic) — Sachin Malhotra on Anthropic's internal test-impact-analysis service; CI jobs grew 25× as Claude authored ~80% of merged code, forcing a deterministic test-selection layer based on package relevance + historical run data.

### Why it's relevant (barely)
Anthropic's post is a genuinely-good engineering read on how AI-native codebases stress CI: engineers ship 8× the code, tests scale ~10×, CI job count grows 25×. Solution: a deterministic test-impact-analysis service that patches, redesigns, and re-patches (the fixes lasted 70 / 29 / <1 days respectively).

The natural question the routine has to answer: does the harness benefit from this pattern?

### Why this is `reject`
No.

- `.harness-profile:` `test_required: false`, `typecheck_blocking: false`, `lint_blocking: false`, `stack.languages: [markdown, bash]`. There is no test suite to select against.
- The harness's *consumers* (target projects that install via `setup-harness`) might well benefit from a TIA pattern — but that's a *project-level* choice, not a harness-methodology one; the harness would over-reach by prescribing a CI shape.
- The `run-loop`/`run-wave` engine does have `node:test` fixtures (`skills/_shared/loop/`), but the test count is tiny (`node:test` fixtures + a few `bash` sub-runners) and runs in < 1 min today. TIA is designed for O(10k) tests, not O(10) fixtures.
- The one *methodology* takeaway — "AI ships more code, so review/CI needs to scale" — is already reflected in the harness thesis (adversarial evaluators, `code-reviewer` agent, `/ultrareview` awareness from 2026-05-10 §1). No new mechanism needed.

### Why capture it at all
Bookkeeping. If a future reader (or a target project onboarding via `setup-harness`) asks "should we adopt TIA per the September 2026 Anthropic post?" the answer is on record here rather than re-derived.

### Concrete change
None — the entry lives in the tracker with a link to this §.

**Verify before applying:**
1. `yq '.quality_bar.test_required' .harness-profile` — must still return `false`; if the harness has grown a real test suite the reject rationale is stale and this § should be reopened.
2. `find skills -name '*.test.ts' -o -name '*.test.js' | wc -l` — count node:test fixtures; if this crosses ~50, revisit whether TIA-style test selection would help the loop CI.

**Recommended verdict:** reject — the harness has no CI-strain problem to solve. Kept as a bookkeeping row so the analysis isn't re-run when a future reader spots the post.
