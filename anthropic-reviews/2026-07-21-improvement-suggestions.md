## 1. Add a `## Gotchas` section pattern to the vendored skill-authoring reference

**Source:** [Lessons from building Claude Code: How we use skills — claude.com/blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills) (Thariq Shihipar). Publicly-mirrored gist: <https://gist.github.com/Danm72/467f6d6cd193d19c0042371866d53b75>.

### Why it's relevant

The post — written by an Anthropic engineer who inventories the hundreds of skills in use inside Anthropic — surfaces nine categories of skills and nine best practices for authoring them. Two are already covered by the harness's vendored best-practices file (`skills/skill-creator/references/anthropic-skill-authoring.md`): progressive disclosure and description-as-trigger.

**Two are not.** In particular, Thariq's post calls out:

> "The highest-signal content in any skill is the Gotchas section. These sections should be built up from common failure points that Claude runs into when using your skill. Ideally, you will update your skill over time to capture these gotchas."

Verifying against the harness today:
- `grep -c "gotchas\|Gotchas" skills/skill-creator/references/anthropic-skill-authoring.md → 0`
- `grep -rE "^## Gotchas|Gotchas$|^## Gotcha" skills/ → 0` (no harness skill has one)

The harness's own long-lived skills — `/run-loop` (184 lines), `/planning-loop` (719 lines), `/run-wave` (446 lines), `/commit` (289 lines), `/close-wave` (675 lines) — are exactly the kind of workflow skills that accumulate gotchas across sessions, and would benefit from a designated home for them (versus the current pattern where they get scattered across Rules / Notes / footnotes).

### Concrete change

Two small additions:

**1a.** Append a short section to `skills/skill-creator/references/anthropic-skill-authoring.md` between "Skills with executable code" and "Anti-patterns":

```markdown
## Gotchas section — the highest-signal part of a mature skill

Long-lived workflow skills accumulate a small set of subtle failure modes that
Claude hits every few sessions ("wrong path on macOS", "silently no-ops when
$FOO is unset", "the flag must precede the sub-command"). A dedicated `## Gotchas`
section is the recommended home for these — they don't belong in Rules (those
are prescriptive), don't belong in the argument-hint (too short), and get lost
if scattered inline.

Convention: bullet list, one line each, present-tense description of the trap
+ the correction. Grow it every time you fix a gotcha in the wild.

Source: Thariq Shihipar, "Lessons from building Claude Code: How we use skills",
claude.com/blog, 2026-06-03.
```

**1b.** (Optional, cheap) — in `skills/skill-creator/SKILL.md` under **Anatomy of a Skill**, add one bullet after the `## Rules` / `## Notes` mention:

```markdown
- **`## Gotchas` (recommended for mature workflow skills)** — a bullet list of
  the subtle failure modes Claude has hit while using this skill. Grow over
  time; do not confuse with `## Rules` (which are prescriptive).
```

**Do NOT** retrofit `## Gotchas` sections into existing skills as part of this §. That's a per-skill judgement call by the maintainer (which failure modes have actually reproduced enough to be worth codifying?). This § just makes the pattern first-class.

### Expected payoff

The next time the maintainer (or a future `/apply-anthropic-reviews` session) invokes `skill-creator` to draft or revise a skill, the vendored reference tells them about the Gotchas convention. Long-lived harness skills gain an obvious home for accumulated gotchas — versus the current scatter. Zero token cost until read.

### Why this isn't a duplicate of an existing pattern

The vendored file already covers "anti-patterns" (things NOT to write in a SKILL body) and "core principles" (how to write it well). Gotchas is different — it's a runtime failure log the *skill* records, not authoring guidance for the *author*. The two are complementary and both are worth having.

## 3. Add a "How this complements Anthropic's Workflow tool + dynamic workflows" paragraph to README

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (Thariq Shihipar and Sid Bidasaria). Complementary post: [How Anthropic runs large-scale code migrations with Claude Code — claude.com/blog, 2026-07-16](https://claude.com/blog/ai-code-migration) — a Bun Zig→Rust migration proof-point (~750K lines of Rust, 99.8% test pass rate, 11 days).

### Why it's relevant

Anthropic shipped a first-party multi-agent orchestration surface on 2026-06-02 that overlaps in concept with the harness's `/run-wave` + `/run-loop`:

- **The `Workflow` tool** — visible in this session's tool list. Executes a self-contained JavaScript script with hooks for `agent()`, `parallel()`, `pipeline()`, `phase()`. Spawns concurrent subagents with a per-workflow cap of `min(16, cpu_cores - 2)` and a lifetime cap of 1000. Structured output via schema, model + effort overrides per agent, worktree isolation option.
- **The `ultracode` opt-in** — a session-level keyword that flips the default posture to "author and run a workflow for every substantive task." When on, workflow orchestration is standing, not opt-in-per-task.
- **The docs term "dynamic workflows"** — the wrapper term Anthropic uses for the pattern.

This is the same conceptual layer as the harness's `/run-wave` (dispatch one wave of tasks to an orchestrator subagent + code-reviewer) and `/run-loop` (drain a stream of ready items with a mechanical merge gate). But they differ in ways worth naming:

|  | Harness `/run-wave` + `/run-loop` | Anthropic `Workflow` tool |
|---|---|---|
| **Where the orchestration lives** | Markdown skill + TypeScript engine committed to the repo | JS script authored by Claude at request time |
| **Merge gate** | `/run-loop`'s fast-forward-only merge-to-head + `gate:` block in `.harness-profile` (tests / typecheck / verify) | None built-in; workflow author writes their own |
| **Secrets / egress** | Loop refuses secret-bearing worktree items without pre-approval + task-scoped injection + default-deny egress | Not addressed; workflow inherits the caller's tool permissions |
| **Persistence** | `plan.md` waves + `.harness-state/` receipts + `docs/plan.md` §4.2 status; resume = re-run | Journal at `<transcriptDir>/journal.jsonl`; resume via `resumeFromRunId` (same session only) |
| **Default posture** | Explicit invocation (`/run-wave N`, `/run-loop waves\|issues`) | With `ultracode` on, standing |
| **Fan-out cap** | Serial-off-HEAD in `/run-loop` today (concurrency deferred) | `min(16, cpu_cores - 2)` per workflow, 1000 lifetime |

These are **complementary**, not redundant — same pattern the 2026-05-10 §1 established for `/ultrareview` vs. local `code-reviewer`. The harness's value-prop (mechanical merge gate, secret handling, resume-via-rerun, plan.md integration) doesn't disappear because Anthropic ships a `Workflow` tool; naming the overlap forestalls the "is `/run-wave` still needed?" question.
