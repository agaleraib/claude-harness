## 2. Add a `verify-before-report` second pass to `.claude/agents/code-reviewer.md`

**Source:** [Bringing Code Review to Claude Code — claude.com/blog, 2026-05-06](https://claude.com/blog/code-review) (originally covered by 2026-05-10 §1 which was APPLIED), reinforced by the [Oct 15 GA announcement](https://claude.com/resources/articles/code-review-is-now-generally-available). The internal methodology Anthropic describes: a team of agents searches for bugs in parallel, **verifies candidate findings in a dedicated pass** to filter false positives, ranks by severity, and emits one high-signal overview comment plus inline comments. Anthropic reports the verify step cuts the engineer-rejection rate on findings to **<1%**.

### Why it's relevant

`.claude/agents/code-reviewer.md:21-95` is **single-pass**:
1. Understand what changed → 2. Verify mechanically (run build/typecheck/tests/lint) → 3. Review the code (Critical/Notable/Minor) → 4. Check against criteria → 5. Report.

There is **no step between "find candidate issues" and "emit them"**. A grep confirms:

```
$ grep -n "verify.*finding\|verification pass\|two-pass\|verify step" .claude/agents/code-reviewer.md
(no matches)
```

Rule #4 ("No empty praise") biases toward emitting any finding that looks potentially-real. For a critic-not-fixer agent that's intentional — but Anthropic's dataplane (large repo, high PR volume) shows a verify step is worth the token cost: it keeps engineers trusting the agent's output, which keeps them *reading* the output. For a solo tooling repo with the maintainer as the only reviewer-of-the-reviewer, the opposite calculus may hold — the maintainer *is* the verify step, and a review of 3 real issues + 1 false positive is fine. That's why this is `defer`, not `apply`.

### What a verify-before-report pass would look like

Inserted between `### 3. Review the Code` and `### 4. Check Against Criteria`:

```diff
 ### 3. Review the Code
 ...

+### 3b. Verify Candidate Findings
+
+Before you report, re-read each candidate finding against the code once more:
+
+- **Does the failure actually reproduce from a realistic input/call?** Trace one concrete path from a real caller to the bad state. If you can't find one, drop the finding.
+- **Is the "fix" cheaper than the bug it prevents?** A fix that adds code weight > the surface area it guards is noise. Drop or demote.
+- **Did a later change already address this?** Re-read the full diff, not just the window around your finding — a later hunk may have handled the case.
+
+Findings that survive this pass go into the report. Findings that don't survive, don't ship.
+
 ### 4. Check Against Criteria (if available)
```

Plus a tweak to **Rule #4**: "No empty praise. Don't say 'nice work on X' unless X is genuinely exceptional. Silence means it passed." → add a second clause: *"And a finding you can't trace to a realistic failure path is a false positive — silence beats noise."*

### Why this is `defer`, not `apply`

1. **The harness's current single-pass has not shown a false-positive problem.** The maintainer isn't on record complaining about `code-reviewer` noise. The 2026-05-10 §1 (hosted Code Review complement) was about *positioning*, not *fixing* the local reviewer.
2. **Verify adds tokens and latency** — a second internal pass over the same diff is ~1.5× the review cost. For `/commit` which invokes the reviewer synchronously, that's user-perceivable.
3. **The harness already has a false-positive filter: `criteria/`.** Rubric-scored findings must map to a dimension, which already cuts "vague gut-feel" noise.
4. **The 2026-04-19 §5 "evals for the adversarial reviewers" entry is still DEFERRED** — until the harness has eval fixtures to measure false-positive rate, there's no way to measure whether a verify pass is helping.

### Concrete change (deferred)

None this run. Promote when either:
- The maintainer notices `code-reviewer` emitting findings that don't reproduce (false-positive feedback), *or*
- The 2026-04-19 §5 agent-evals suggestion lands and gives a measurable false-positive baseline.

At that point: adopt the `### 3b. Verify Candidate Findings` subsection above as a trial change, measure false-positive rate before/after, and keep or revert based on the delta.

### Verify before applying
1. `grep -n "verify.*finding\|verification pass\|### 3b\|Verify Candidate Findings" .claude/agents/code-reviewer.md` — must return nothing today (confirms the single-pass structure hasn't been changed in the interim). If it returns hits, the verify step has already been added and this § is stale.
2. `grep -n "DEFERRED" anthropic-reviews/2026-04-19-improvement-suggestions.md` — should still show §5 (agent evals) deferred; this § explicitly depends on §5's resolution.
3. Before promoting, review `.harness-state/parking_lot.md` for any `[code-review]` tagged items complaining about the reviewer's false-positive rate — if the parking lot shows ≥3 such items in the preceding quarter, the pain-point threshold has been crossed.

**Recommended verdict:** defer until false-positive-rate pain warrants — Anthropic's data (<1% rejection rate) is from a 100×-larger PR dataplane than this harness ever sees; the methodology is sound but the solo-maintainer calculus favors keeping single-pass until pain shows up.
**Status:** PENDING — awaiting triage in PR review

## 3. Adopt OTel GenAI semantic conventions for `.harness-state/orchestrator.jsonl`

**Source:** [Agent observability on the Claude Platform — claude.com/resources, 2026-10-14](https://claude.com/resources/articles/agent-observability-on-the-claude-platform) — public beta of **OpenTelemetry (OTel) tracing** for Claude Managed Agents, the Messages API, and the Claude SDKs. Traces follow the [OTel GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) (standardized `gen_ai.*` keys for `agent.name`, `operation.name`, `request.model`, `response.*`, `tool.*`, `token.*`), interoperate with Grafana / Honeycomb / Sentry / Splunk / Arize / Braintrust / Datadog / Langfuse / LangSmith / New Relic / PostHog / Databricks via any OTLP endpoint. The Claude SDKs export automatically; the Messages API and Managed Agents need a destination configured in the Claude Console.

### Why it's relevant

The harness emits structured orchestration state to **`.harness-state/orchestrator.{log,jsonl}`** (`AGENTS.md` and `CLAUDE.md` both cite it as the state surface for `/run-wave` dispatch and loop invocations). Today that log is **debug output** — the maintainer greps it when something goes wrong. It is not an observability feed; nothing consumes it as a trace.

If `.harness-state/orchestrator.jsonl` ever becomes a trace feed (export to a dashboard, run offline analysis, correlate `code-reviewer` findings with model/effort combos, feed the 2026-04-19 §5 agent-evals pipeline), **OTel GenAI semconv keys are the standard that any such consumer would expect**. Adopting them now while the log is still debug output costs almost nothing; retrofitting them later means a migration.

The relevant keys (from the OTel GenAI semconv) that the orchestrator already has data for:
- `gen_ai.agent.name` — the dispatched subagent (`opus` / `sonnet` / `haiku` / specific agent name)
- `gen_ai.operation.name` — "dispatch", "commit", "verify"
- `gen_ai.request.model` — the pinned model (from `.harness-profile`)
- `gen_ai.request.effort` — the effort level (`.harness-profile:effort_default` or the route-chosen level)
- `gen_ai.response.finish_reason` — "complete" / "error" / "parked"
- `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens`

A quick grep confirms the current log is not using these keys:

```
$ grep -rn "gen_ai\." .harness-state/ skills/_shared/loop/ 2>/dev/null | head
(no matches)
```

### Concrete change (deferred)

None this run. When/if the maintainer wants to take this on:

1. Spec a schema for `.harness-state/orchestrator.jsonl` that uses `gen_ai.*` keys for the fields the orchestrator already emits (model, effort, agent, operation, finish_reason, tokens). Keep the harness-specific keys (`wave_id`, `task_id`, etc.) prefixed with `harness.*` so they coexist cleanly.
2. Update whichever skill emits the JSONL (`skills/run-wave/`, `skills/_shared/loop/`) to write both the legacy keys (for backward-compat with `harness-status`) and the `gen_ai.*` keys, for one release cycle. Then drop the legacy keys.
3. Document the schema in `AGENTS.md` under the orchestrator-state section so consumers (and OTel collectors) know what to expect.

### Why this is `defer`

1. **No consumer today.** Debug output doesn't need standards.
2. **The harness has no OTLP endpoint configured** — adopting the keys without a destination is purely aspirational.
3. **The OTel GenAI semconv is still evolving** — the keys above are stable in October 2026 but the spec is at v1.x; waiting a quarter or two for the dust to settle costs nothing.
4. **Speculative for solo tooling.** Same spirit as 2026-05-10 §2 (Cloud Routines migration) — flag for the maintainer; don't build until a consumer appears.

### Expected payoff (when applied)

Any future consumer of `.harness-state/orchestrator.jsonl` (a Grafana dashboard, a cost-dashboard, the deferred 2026-04-19 §5 agent-evals pipeline) can read it with off-the-shelf OTel tooling instead of a bespoke parser. The migration cost is paid once by the harness, not N times by every consumer.

## 4. Adopt Scion-style ideas (sparse checkouts, few refs, query-history-via-API) for `agent-<id>` git worktrees

**Source:** [Redesigning source control at Anthropic — anthropic.com/engineering, 2026-10-19](https://www.anthropic.com/engineering/redesigning-source-control). Anthropic built **Scion**, an in-house VCS, to replace git for its monorepo. Clients are always-online; the server handles commits/merges/rebases/diffs/blame; clients fetch trees and blobs by need (sparse/virtual checkouts work without special support); refs are discouraged except for `main` and release branches (compare-and-swap on one row). The article explicitly says *"Scion is not a general git replacement"* and *"teams should apply its ideas to git without abandoning git's model."*

### Why it's relevant (and why it's `reject`)

The harness uses git worktrees for parallel agent dispatch: `.claude/worktrees/agent-<id>/` per `CLAUDE.md`. Each worktree is a full checkout; `/run-wave` creates and tears them down per wave. Scion's design pressures come from a workload the harness doesn't have:

| Scion pressure | Harness equivalent today | Delta |
|---|---|---|
| Tens of millions of full checkouts per day | A handful of `agent-<id>` worktrees per wave | 6+ orders of magnitude lower |
| Thousands of refs (one per CI run, feature branch, test) | One branch per wave + master + release branches | 2–3 orders of magnitude lower |
| Partial clones breaking diff/blame | Full clones work fine at this size | n/a |
| Clients always online | Agent sessions are always online, so this maps — but the pain is on the server side at Anthropic's scale, not the client side at harness scale | Not a shared pain |

The Scion lessons that **could** translate to the harness (sparse checkouts, fewer refs) would:
- **Sparse checkouts for `agent-<id>` worktrees:** The harness's wave worktrees already live in a tooling repo with ~a few hundred files. Setting up `git sparse-checkout` adds config complexity without saving measurable disk/IO.
- **Fewer refs:** The harness already has few refs. `/run-wave` creates one branch per wave, `/commit` merges it, old branches get deleted. There is no "ref explosion" problem to solve.

Scion is open as a reference design, not as a runnable tool. The harness can't adopt it as code; it can only adopt its ideas, and the ideas don't translate at this scale.

### Why file a § at all

So a future reader (future-you, or whoever picks up the harness) doesn't look at the Oct 19 engineering post, think "we should Scion-ify the worktrees," and spend a week on a config change that saves nothing. This § is the paper-trail that the question was asked and answered.

### Verify before applying
1. `git -C /home/user/claude-harness worktree list | wc -l` — if this ever reports >20, the sparse-checkout / few-refs calculus might shift; revisit. As of 2026-10-20 it's one (`master`).
2. `git -C /home/user/claude-harness branch -r | wc -l` — if this ever reports >100 refs, revisit. As of 2026-10-20 it's a small handful.
3. If Anthropic open-sources Scion or ships a `git-scion` plugin, revisit — a drop-in replacement would change the cost calculus entirely.

**Recommended verdict:** reject — Scion is not user-installable; the harness's git-worktree model doesn't hit the scaling walls Scion was built to escape; the "ideas" (sparse checkouts, few refs) don't translate at harness scale. Filed so a future reader sees the question was considered.
**Status:** PENDING — awaiting triage in PR review
