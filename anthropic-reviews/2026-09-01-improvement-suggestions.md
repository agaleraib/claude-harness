## 2. Cite "The new rules of context engineering for Claude 5 generation models" — spec a harness-wide skill-audit pass

**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) (author: Thariq Shihipar; announcement mirror: https://x.com/trq212/status/2080710971228918066).

### Why it's relevant
The post is a first-party report on Anthropic removing **>80%** of Claude Code's own system prompt for the Claude 5 generation with **no measurable loss on coding evals**. It codifies four rules:

1. **Move from micromanagement to judgment** — stop prescribing specific rules; curate what the model sees.
2. **Progressive disclosure** — load context only when needed (via tools / dedicated skills), not upfront.
3. **Prefer automatic memory** over hand-maintained files.
4. **Rich references, thin specs** — hand the model reference material, not micro-managed prose.

This is a direct challenge to the harness's core design premise. The harness ships **27+ skills** under `skills/`, many of which are intentionally-detailed prescriptive `SKILL.md` bodies with inline rules, examples, and step-by-step protocols (spec-planner, run-wave, close-wave, planning-loop, run-loop, code-review, etc.). Under the Claude 4.x model tier the harness targeted, that verbosity was load-bearing. Under the Claude 5 tier §1 would bump to, the same verbosity is more likely to *narrow* the model's exploration than help it — the specific failure mode Anthropic names.

This is **not** a suggestion to gut the skills — the post is careful to note the rules are model-tier-dependent, and consumer projects installing this harness will run heterogeneous fleets for a long time. It **is** a suggestion to spec a triage pass: for each skill, decide whether its body still needs the current level of prescription for the *newest* pinned model, and where progressive-disclosure (moving detailed content into a `references/` file the SKILL.md points at) buys context-cost without behavioral loss.

### Concrete change (spec-only in this §; no edits yet)
Route to `/spec-planner` with a brief roughly of the form:

> *Audit the harness's `skills/` directory for over-prescription against the Claude 5 model tier the harness now pins (§1). For each `SKILL.md`, decide: (a) is the current inline verbosity still load-bearing at Opus 5 / Sonnet 5?  (b) can the reference material be split into `references/*.md` files the SKILL.md points at (progressive disclosure)?  (c) does any rule prescribe a specific approach where the current-generation model would benefit from being handed judgment?  Produce a per-skill verdict table with three rungs: keep as-is / defactor into references / trim prescriptive rules to references. Output the audit as a wave-shaped spec so trimming can ship incrementally rather than as a big-bang rewrite.*

Also cheap, in the same spec's Prior Work section, cite the post in `README.md`'s existing References section (after `Building Effective Agents`):

```diff
 - [How We Built Our Multi-Agent Research System](https://www.anthropic.com/engineering/multi-agent-research-system) — Orchestrator-worker patterns, model routing
+- [The New Rules of Context Engineering for Claude 5](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) — Progressive disclosure, model judgment over prescription (July 2026)
```

### Expected payoff
- The harness's design assumptions get re-examined at exactly the moment the model-tier assumption underneath them shifts. Doing this *after* the model bump in §1 lands is the natural sequencing.
- A per-skill audit table is durable — future readers see which skills were kept as-is *deliberately* vs. by inertia.
- The `references/` split pattern (already used in `skills/planning-loop/references/rules.md`, `skills/skill-creator/references/anthropic-skill-authoring.md`) generalizes.

### Why this isn't reject
It's tempting to reject on "the harness's detailed skills are its value-prop — don't gut them." The spec framing above **does not** propose gutting; it proposes a per-skill decision. And the post's own carve-out ("model-tier-dependent") is quoted as first-party evidence that the answer *for some skills* will legitimately be "keep as-is."

Not `apply` because scope > 5 files, introduces a reusable convention (references-split pattern applied harness-wide), and touches every skill body — the four promotion signals from `anthropic-reviews/README.md`'s decompose-and-route section all trip.

**Verify before applying:**
1. `grep -rln 'the-new-rules-of-context-engineering\|context-engineering-for-claude-5' /home/user/claude-harness 2>/dev/null` — must return nothing today; if it returns hits, an audit spec (or a partial audit) has already been drafted and this § is stale.
2. Confirm §1's model bump has landed before the spec starts — the spec's premise depends on the pinned tier being Claude 5-class. If §1 is deferred, defer §2 with it.
3. Re-read `skills/skill-creator/references/anthropic-skill-authoring.md` before drafting the spec — it is the vendored snapshot of Anthropic's skill-authoring best practices as of the last skill-creator sync; if it has been updated to reflect the July 2026 post, some of the audit rungs may already have canonical guidance, and the spec's brief should point at it.
4. Confirm the post's URL still resolves (Anthropic occasionally moves blog paths). If it 404s, use the archived tweet-thread linked above as the citation.

**Recommended verdict:** spec — the mechanical trigger is one first-party post, but the resulting work touches every skill body and introduces a reusable convention; `/spec-planner` is the correct rung per `anthropic-reviews/README.md`'s decompose-and-route protocol.

## 5. Assess Claude Skills API / Files API GA as a second distribution channel for harness skills

**Source:** [Build production agents with computer use, the Skills API, and the Files API — claude.com/blog, 2026-08-28](https://claude.com/blog/computer-use-skills-api-files-api) (GA announcement for the Skills API and Files API on the Claude Platform)

**scope: speculative**

### Why it's relevant (and why the recommendation is `defer`)
The Skills API generally-available on the Claude Platform lets a caller **upload and version a skill folder**, then **attach it to any Claude API request**. This is the cloud analogue of what the harness does locally: it symlinks `skills/` to `~/.claude/skills/` so any Claude Code session on the machine sees the skill.

Two consumers can now, in principle, use this harness's skills:
1. **A local Claude Code session** — the current path (symlinked, no upload, no version).
2. **Any Claude Platform caller** (Claude API request from a script, Claude Managed Agents, Claude Cowork instance) — the new path, if the harness maintained a Skills API package alongside the local one.

Building the second path today is speculative for a solo-maintained harness with a single consumer. But the record should note that:
- The `~/.claude/skills/` symlink installer (`skills/setup-harness/`) is the **only** distribution surface today; a second one would need a version convention (Skills API pins by ID + version), a packaging step, and a decision about which skills belong in the cloud lane (the loop / wave / commit skills assume a local filesystem; only the reference-type skills would export cleanly).
- The 2026-04-19 §2 (brain/hands split) + 2026-04-25 (Managed Agents memory) + 2026-05-10 §3 (dreaming) deferrals in the tracker are all the *same shape of consideration* as this: "the harness is single-consumer today; when it's not, revisit." Same parking spot.

### What "defer" means concretely
No files change. This § serves as the bookkeeping row in the durable record so that when the harness *does* pick up a second consumer path (a colleague deploying it into Claude Cowork, a Managed Agents cookbook, a Claude API script), the maintainer starts from "Skills API was considered on 2026-09-01 as a candidate second distribution channel" rather than from zero.

**Recommended verdict:** defer until multi-distribution demand — the harness has one consumer path today; the Skills API is the second-consumer surface. Book the consideration; build when the second consumer arrives.
