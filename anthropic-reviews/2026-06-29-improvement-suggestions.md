## 2. Add a "How this complements dynamic workflows" paragraph + reference bullet

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) + sibling post [Introducing dynamic workflows in Claude Code](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code). Anthropic shipped a runtime where Claude **writes a JavaScript orchestration script on the fly**, executes it in the background, and folds verified sub-agent results into a single answer — explicitly framed as "Claude Code can now write and orchestrate its own multi-agent harness on the fly."

### Why it's relevant
The Anthropic post borrows the repo's central noun ("harness") and applies it to a runtime-constructed pattern that overlaps in shape — but not in purpose — with this repo's static `/run-wave` orchestrator skill + `orchestrator.md` agent. The conceptual map:

| Layer | This repo (`claude-harness`) | Anthropic's Dynamic Workflows |
|---|---|---|
| When the plan exists | Author-time, in `docs/plan.md` (`spec-planner` → `plan.md` → `run-wave`) | Runtime, on each invocation |

| Where sub-agents run | Same Claude Code session (or worktree, via run-loop) | Background runtime, separate from your session |
| What survives across runs | Spec → plan → waves → harness-state (durable) | The script + verified outputs (ephemeral by default) |
| What's the gate | `criteria/`, `/commit`, `code-reviewer`, exit gate | Verification step inside the script |
| When to reach for it | Multi-wave features w/ rubric + parking-lot integration | Codebase-wide bug hunts, migrations, audits, one-shot fan-outs |

## 6. Add a `post-session` lifecycle hook to write `last_exit.md` automatically

**Source:** [Claude Code v2.1.169 changelog — code.claude.com/docs/en/changelog, 2026-06-08](https://code.claude.com/docs/en/changelog). Adds a `post-session` lifecycle hook for **the self-hosted runner**: runs after the session ends, before the workspace is deleted. Use cases per the changelog: snapshot uncommitted work, export logs.

### Why it would seem relevant
The harness's [`skills/session-end/SKILL.md`](../skills/session-end/SKILL.md) is the interactive ritual that:
- Checks for pending commits.
- Asks "how did today go?" + parking-lot triage via `AskUserQuestion`.
- Writes `last_exit.md` summarizing the day for the next session.
- Invokes `project-tracker` to push the session to Second Brain.

It's tempting to think: "wouldn't `post-session` automate the `last_exit.md` write so the user doesn't have to remember to run `/session-end`?"

### Why this is `reject`

1. **Wrong runtime context.** `post-session` fires on **self-hosted runner** teardown — the headless background-runner used by Cloud Routines, scheduled cron jobs, and similar. It does *not* fire on local-CLI sessions. The harness's primary execution surface is the local CLI; the hook would never run for the use case it was hypothetically helping.
2. **Non-interactive.** The session-end skill is interactive on purpose — `AskUserQuestion` prompts collect the day's narrative + parking-lot triage decisions that the user, not Claude, owns. The hook cannot prompt. Reducing session-end to "auto-write last_exit.md" would lose the narrative + the parking-lot triage step.
3. **`/run-loop` already covers the loop-runner scenario.** When the harness runs in headless loop mode, [`skills/run-loop/SKILL.md`](../skills/run-loop/SKILL.md) writes per-item artifacts (status, runner output, exit-gate result) that play the same role `post-session` would play. No gap to fill.
4. **No symmetric `pre-session` problem either.** `skills/session-start/SKILL.md` already runs at session start and reads `last_exit.md`; the lifecycle is already closed without hooks.

### Concrete change
None. Reject so the routine's durable record reflects that this option was considered and dismissed for first-party reasons.

**Verify before applying:**
1. `grep -rn "post-session\|post_session\|SessionStart\|SessionEnd" /home/user/claude-harness/skills/session-end /home/user/claude-harness/skills/session-start /home/user/claude-harness/.claude/settings.json 2>/dev/null` — should return no hook installations today (verified 2026-06-29).
2. If Anthropic later extends `post-session` to fire on local-CLI sessions too, re-open this § — the rejection rests on "self-hosted runner only", not on the broader idea.
3. Confirm `skills/session-end/SKILL.md` Steps 4+ still use `AskUserQuestion` (interactive) — if the maintainer has automated that part already, the calculus may shift.

**Recommended verdict:** reject — `post-session` is a self-hosted-runner hook; the harness's session-end skill is interactive on local CLI; replacing the ritual with the hook would lose the narrative + parking-lot triage step. Record kept for a future routine that might propose the same.
