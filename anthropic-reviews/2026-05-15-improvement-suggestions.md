## 1. Re-evaluate the deferred 2026-05-08 §2 (typed evaluator verdict) in light of the new `/goal` native evaluator

**Source:** [Keep Claude working toward a goal — Claude Code Docs, 2026-05-12](https://code.claude.com/docs/en/goal) (Claude Code v2.1.139 release notes entry on the same page; companion third-party deep-dive linked from VentureBeat). The release shipped on May 12, 2026 and introduces a native, separate-context completion-condition checker that runs after every agent turn.

### Why it's relevant

The harness already runs a planner → generator → evaluator triad (verified at `.claude/agents/generator.md:7`, `.claude/agents/ui-evaluator.md:12`, `.claude/agents/code-reviewer.md`). The deferred 2026-05-08 §2 (DEFERRED status as of 2026-05-10, per `anthropic-reviews/2026-05-08-improvement-suggestions.md:133`) sketched adding a typed verdict — `satisfied` / `needs_revision` / `max_iterations_reached` / `failed` — to `evaluator-reports/evaluation-report.md` so the generator could branch on the verdict instead of re-reading prose.

`/goal` ships the **same shape** as a Claude-Code-native feature:

- A **completion condition** is supplied (e.g. `/goal CHANGELOG.md has an entry for every PR merged this week`).
- After every agent turn, the condition + transcript are sent to the small fast model (defaults to Haiku) configured for the provider.
- The evaluator returns a `yes`/`no` verdict + short reason.
- `no` → Claude keeps working with the reason as guidance; `yes` → goal clears and the session records an achieved entry.
- Works in interactive mode, `claude -p`, and Remote Control. Tracks elapsed time, turns, and tokens.

That's a separate-context, typed-verdict, iteration loop — i.e. it's the Outcomes-style pattern at the **CLI** layer rather than at the harness's **agent** layer.

### Does `/goal` resolve the three open design questions from 2026-05-08 §2?

Recap from §2 (`2026-05-08-improvement-suggestions.md:114–119`):
1. **Per-criterion score threshold** for "satisfied" vs "needs_revision."
2. **What `max_iterations_reached` does** in this harness (escalate? write to `.harness-state/last_exit.md`?).
3. **Composition with `/run-wave` / `/close-wave`** semantics.

`/goal` answers **none** of them:
1. The native evaluator returns binary `yes`/`no`, not a per-criterion score. Threshold semantics still need design if the harness wants `criteria/*.md`-anchored verdicts.
2. `/goal` has no built-in iteration cap exposed via condition text — the user phrases it (e.g. "all tests in `test/auth` pass and lint is clean") and the loop runs until the small model says yes or the session is interrupted. The harness's escalation contract is still TBD.
3. `/goal` is a per-`claude` invocation; it doesn't see `docs/waves/` or `docs/plan.md ## Now`. Wave-level closure is unchanged.

So `/goal` is **evidence the shape is sound** — Anthropic has now productized the separate-context-grader-with-typed-verdict loop into the CLI — but does **not unblock §2**. The same three questions remain; the §2 verify-before-applying tests are unchanged.

## 2. Bookkeep Agent View + background-session model alongside the harness orchestrator pattern

**Source:** [Agent view in Claude Code — Claude Blog, 2026-05-11](https://claude.com/blog/agent-view-in-claude-code) (companion docs: [`claude agents`](https://code.claude.com/docs/en/agent-view))

### Why it's relevant

Agent View introduces a CLI dashboard for managing **multiple parallel Claude Code sessions** running in the background. Commands shipped:

- `claude agents` — opens the dashboard (takes over the terminal; shows the session table with state grouping + dispatch input at the bottom).
- `/bg` inside a session — moves it into the background; press `←` on an empty prompt to background + open Agent View in one step.
- `claude --bg [task]` — launches a fresh session directly in the background, no foreground attachment.
- Each background session is an independent Claude Code process supervised by a per-user supervisor.

The harness today implements parallelism a **different way**: the `orchestrator` agent (`.claude/agents/orchestrator.md`) dispatches sub-agents *within a single Claude Code session* via the Task tool. Sub-agents run concurrently in that one process; `/run-wave` orchestrates them. There is **zero overlap** with Agent View as of today — Agent View is OS-level multi-session parallelism, the orchestrator is in-session sub-agent parallelism (verified: `grep -rn "claude --bg\|claude agents\|/bg\b" /home/user/claude-harness/` returns nothing — no integration today; `grep -rn "subscribe_pr_activity\|background session" .claude/agents/ skills/` also returns nothing).

The two models can coexist; they answer different questions:

| Layer | Question answered | Harness component |
|---|---|---|
| In-session sub-agent dispatch | "Run these N tasks from a wave in parallel inside one wave run" | `orchestrator.md`, `/run-wave` |
| OS-level background sessions | "Keep this task working while I open a different Claude Code session for something else" | (not in harness today) |

A solo maintainer running waves in foreground today is not blocked by the absence of background-session integration. If/when the maintainer wants to run e.g. `/anthropic-reviews` and a separate `/run-wave` concurrently without two terminal windows, Agent View becomes the right primitive. Until then it's bookkeeping.
