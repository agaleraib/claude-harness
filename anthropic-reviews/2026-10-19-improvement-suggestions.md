## 3. Split `code-reviewer` into **find → verify → rank** stages mirroring Anthropic's hosted Code Review

**Sources:**
- [Bringing Code Review to Claude Code — claude.com/blog, 2026-05-06](https://claude.com/blog/code-review) (same URL re-fetched for GA details)
- [Code Review is now generally available — claude.com/resources/articles, 2026-10-15](https://claude.com/resources/articles/code-review-is-now-generally-available) (GA announcement)
- Related and inaccessible from this environment: "How the Claude Code team does code review" (2026-10-16, listed at `claude.dev/blog/solving-code-review-at-anthropic/` on the claude.com/blog index but neither claude.com/blog/… nor claude.dev/… resolves from here) — content appears to overlap with the two above per WebSearch excerpts.

### Why it's relevant

Both the research-preview launch post (May 2026) and the GA announcement (Oct 2026) describe Anthropic's hosted Code Review as a **three-stage pipeline**: (1) parallel bug-finding agents fan out across the diff, (2) a verification stage filters false positives by trying to reproduce each candidate finding, (3) survivors are ranked by severity. Reported outcomes: **under 1% of findings marked incorrect** by engineers at Anthropic; large-PR coverage (>1000 lines) hits 84% find-rate at 7.5 issues/PR.

The harness's local `code-reviewer` agent (`.claude/agents/code-reviewer.md`) has no equivalent verification stage. Its pipeline is:

```
1. Understand what changed
2. Verify mechanically  (= build/typecheck/test/lint)
3. Review the code     (critical / notable / minor)
4. Check against criteria (if criteria/ exists)
5. Report
```

Step 2's "verify mechanically" is a build-the-code pass, **not** a per-finding reproduction pass. There's nothing in the agent prompt that says "for every candidate finding, independently reproduce the failure before reporting" — which is exactly the stage Anthropic credits with the <1% false-positive rate.

### Why `spec`, not `apply`

The local reviewer is single-process; it can't fan-out to parallel agents the way the hosted Code Review does. There are two plausible shapes:

1. **Sequential self-review.** After step 3's draft findings list, re-enter the review with the diff + the candidate findings as context, with a system message that says "for each candidate, attempt an independent reproduction; drop any you can't reproduce from code alone." Cheap, in-session, keeps the single-process constraint.
2. **Second subagent dispatch.** `/commit` dispatches a second `code-reviewer`-shaped subagent with the first reviewer's findings as input; the second agent is instructed only to verify, not to find new issues. More expensive, independent context, closer to the hosted-service shape.

(1) is cheap but may not actually filter false positives — the same model that generated the finding is now asked to filter it. (2) is more expensive and risks approval-fatigue on `/commit` but captures the independent-reproduction property. Neither is a `/micro`; both need a design pass.

A third option is to recommend users run `/ultrareview` on substantive PRs post-push (already documented in README via 2026-05-10 §1 APPLIED) and leave the local reviewer as-is. That's status quo — explicit rejection, not spec. I'm picking `spec` because the <1% false-positive number is a strong enough signal to be worth evaluating in-harness.

### Expected payoff

Reducing false-positive findings from the local `code-reviewer` directly reduces the `/commit` friction loop — every false positive today either costs the user a round of pushback-and-dismiss or (worse) a round of apologetic-fix-that-didn't-need-doing. Even halving the false-positive rate would materially shorten the pre-commit cycle.

### Why not `defer`

Anthropic has shipped three posts (May, Oct × 2) describing the same verify-then-rank pattern as central to their internal code-review methodology. The pattern has first-party evidence of working. Not spec'ing it is a choice to leave that evidence on the table.

### Why not `apply`

See two-shape question above. A one-shot edit to the agent prompt that bolts on "and also verify each finding before reporting" would land but wouldn't settle the self-review-vs-second-subagent question, and getting that wrong is a regression risk.

**Verify before applying:**
1. `grep -n "verify.*finding\|verification stage\|false[- ]positive\|reproduce" /home/user/claude-harness/.claude/agents/code-reviewer.md` — must return nothing substantive today; if a verify stage has been added, re-read before writing the spec.
2. Confirm Anthropic's hosted Code Review still names the three-stage pipeline in its current docs (claude.com/blog/code-review, code.claude.com/docs/en/code-review) — the methodology is the whole citation; if the GA cycle has restructured it, the spec premise shifts.
3. If a verify-stage spec is written, benchmark it on a historical repo's `/commit` runs (pre-change false-positive rate vs post-change) before merging — the only way to tell if the self-review shape (option 1) actually filters anything.

**Recommended verdict:** spec — the pattern has three posts of first-party evidence, but the single-process constraint makes the shape a non-trivial design choice.
**Status:** PENDING — awaiting triage in PR review

Anthropic's containment-ordering rule ("boundaries first, model layer second") is already how AGENTS.md:113 is structured but isn't **named** that way in the README's Auto Mode section (line 873+), which currently reads as if Auto Mode is a standalone defense.
