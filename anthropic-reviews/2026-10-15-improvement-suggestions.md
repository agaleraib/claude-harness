## 2. Add a "Re-examine the harness with each new Claude model" paragraph to README's Philosophy section

**Source:** [Harness design for long-running application development — anthropic.com/engineering, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps) (retroactive review per the 2026-04-28 tracker's flagged backlog).

### Why it's relevant
The README's `## Philosophy` section (lines ~1–30) already **cites this post by name** and **quotes its stress-testing line** verbatim:

```
README.md:3: Inspired by [Anthropic's harness design research](https://www.anthropic.com/engineering/harness-design-long-running-apps)
README.md:7: > *"Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing."*
```

The quote is already there. What is **not** in the README is the post's second-order claim: *why* stress-testing matters — "those assumptions go stale as models improve." The post then prescribes a specific discipline: **"Re-examine the harness with each new model. Keep the simplest design that works, and add complexity only where the model still falls short."**

The harness has already lived through two model bumps during its lifetime (Opus 4.6 → 4.7 in 2026-04-19 §1; Haiku 4.5 → 5.5 pending in §1 above) and neither triggered a formal re-examination pass. The maintainer did the right thing both times (small, local edits), but there is no documented protocol — the next bump will go the same ad-hoc way unless it is written down.

### Concrete changes

In `README.md`, under `## Philosophy` after the "This harness **doesn't tell the model HOW to think**" sentence and before `### What This Is`, add one paragraph:

```markdown
### Re-examine on every model bump

Every harness component encodes an assumption about what the model can't do on its own. Those assumptions go stale as models improve ([Anthropic 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps)). When a new Claude model lands (Opus bump, Sonnet bump, Haiku bump), skim `.claude/agents/`, `skills/`, and `criteria/` for scaffolding that the new model may no longer need, and prune accordingly. The agent/skill prompts should name the simplest design that still works — add complexity only where the current model still falls short. Prior bumps that triggered this cleanup: Opus 4.6 → 4.7 (2026-04-19 §1), Haiku 4.5 → 5.5 (2026-10-15 §1).
```

Also append one line to `parking_lot.md` under the appropriate `[auto-ok]` section:

```markdown
- `[auto-ok]` Re-examine `.claude/agents/`, `skills/`, `criteria/` on the next model bump — ensure the simplest design that still works. Source: 2026-10-15 §2.
```

### Expected payoff
Durable protocol note — the next contributor (or future-you) who sees a new Claude model announcement knows there is a one-pass review to run, and knows where to look. Costs ~8 README lines + 1 parking_lot line. No new skill, no new agent.

## 3. Calibrate `criteria/*.md` rubrics with few-shot anchor examples per score band — spec first

**Source:** Same post as §2 — [Harness design for long-running application development, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps).

### Why it's relevant
The post names **two** evaluator disciplines, not one. §2 above picks up the "re-examine with each new model" half. The other half:

> **"Calibrate the evaluator with few-shot examples and detailed score breakdowns to reduce score drift and align it with your preferences."**

The harness's `criteria/*.md` files (6 files: `code-architecture.md`, `code-simplicity.md`, `data-integrity.md`, `frontend-ui-design.md`, `performance-accessibility.md`, `ux-user-flows.md`) carry **prose score bands only** — e.g. `code-simplicity.md`'s Reuse dimension says:

```
| 9-10  | Uses existing utilities. New code only where no equivalent exists. |
| 7-8   | Mostly reuses; one or two avoidable re-implementations. |
...
```

But there is no concrete-example anchor per band — no "here is a code block that scored 9/10 on Reuse because X, here is one that scored 5/10 because Y." Without anchors, two independent code-reviewer invocations on the same diff can drift several points apart, and the drift grows with each model bump (per the first half of the same post's recommendation).

### Why `spec`, not `apply`
This is **not** a text edit — it is a wave-sized authoring task:
- 6 rubric files × ~5 dimensions each × 3+ anchor examples per band = ~90 code-fragment anchors
- Each anchor needs to be grounded in a real diff that an existing code-reviewer run has scored, so the anchors are empirically calibrated, not fabricated
- The rubric files are consumed by every `/commit` run and by `code-reviewer` directly — changing their shape has repo-wide reach

That lives in `docs/specs/<date>-criteria-calibration.md`, not in a one-shot `/micro`. Flag for `/spec-planner` to design, then `/run-wave` when scheduled.

### Expected payoff (when eventually built)
Reproducible scoring: two code-reviewer runs on the same diff should land within one point of each other on every dimension. Eliminates one source of "the reviewer was harsh today" skepticism that currently dogs criteria interpretation.

### Verify before applying
`for f in criteria/*.md; do grep -q "anchor\|example.*scored\|few-shot" "$f" || echo "no anchors: $f"; done` — if every file prints a "no anchors" line, the spec is still needed. If any file already carries anchor examples (e.g. a prior wave started this work), narrow the spec to the remaining files.

**Recommended verdict:** spec — substantive, repo-wide reach, needs a design pass before coding.
**Status:** PENDING — awaiting triage in PR review

## 4. Attach `infrastructure-noise` two-value resource-spec guidance to the deferred 2026-04-19 §5 (agent-evals) as a durable design constraint

**Source:** [Quantifying infrastructure noise in agentic coding evals — anthropic.com/engineering, 2026-02-05](https://www.anthropic.com/engineering/infrastructure-noise) (retroactive review per the 2026-04-28 tracker's flagged backlog).

### Why it's relevant
This post reports a **6-percentage-point swing on Terminal-Bench 2.0 scores** purely from CPU/RAM configuration between the lowest and highest tiers (p < 0.01). The authors' Kubernetes setup treated per-task specs as both a guaranteed floor and a hard-kill limit, which caused infrastructure errors on **up to 6% of tasks**. They recommend reporting two values per task — a guaranteed allocation and a separate hard-kill threshold — with a ~3× gap, because:
- Tight limits favor lean strategies and penalize exploration.
- Generous limits favor resource-heavy strategies.
- A single pinned spec measures **different things** at different levels.

This is **not actionable in the harness today** — there is no agent-evals suite running. But the deferred `criteria/agent-evals/` work from 2026-04-19 §5 (reaffirmed by 2026-04-28 §3 and 2026-05-03 §1) will eventually need a resource-spec story, and this post is the first-party source for how to do it right.

### Concrete changes

No code change today. When the deferred §5 is unblocked (consumer-project rubric suite surfaces), the spec should encode:

1. **Each agent-eval fixture carries two values**, not one:
   - `resource_floor`: guaranteed CPU/RAM allocation (what the agent is promised)
   - `resource_ceiling`: hard-kill threshold (what the system will terminate at)
   - Target ratio: `resource_ceiling / resource_floor ≥ 3` (per the post, this reduces infra-error rate from ~5.8% to ~0.5% while keeping score change within noise).

2. **Report both numbers alongside each eval score**, so a 5-point score gap between two reviewer-prompt variants can be distinguished from a 3-point noise band driven by resource configuration.

3. **Rerun the eval under the floor and the ceiling** at least once per rubric change, confirm scores at both ends fall within noise of each other (per the post's 1x–3x range).

Attach this bullet set to the **existing** `anthropic-reviews/2026-04-19-improvement-suggestions.md` §5 Status trail as a design-constraint note, following the pattern used for 2026-05-03 §1 (BioMysteryBench floor/ceiling tier split) and 2026-04-28 §3 (postmortem evidence). Do **not** write a separate spec yet — the parent §5 is still blocked.

### Expected payoff (when eventually built)
Any future agent-evals suite will report scores with calibrated noise bands from day one, rather than discovering mid-flight that "the 3-point improvement from reviewer-prompt-v2 is actually infrastructure variance." Also feeds §3 above (criteria calibration): if a 3-point gap can be infra noise, a single-anchor rubric band is probably not reliably distinguishable from an adjacent band.

### Verify before applying
`grep -c 'resource_floor\|resource_ceiling\|infrastructure.*noise' docs/specs/*.md anthropic-reviews/*.md` — if any spec file already encodes the two-value design, verify alignment and skip. Otherwise this is a durable note to attach when the parent §5 is unblocked.

**Recommended verdict:** defer until consumer-project rubric suite exists — bookkeeping only; the parent §5 is still blocked for the same reason it was in 2026-04-19.
**Status:** PENDING — awaiting triage in PR review

## 5. Teach `setup-harness` to warn when `ANTHROPIC_MODEL` / `CLAUDE_CODE_MODEL` env vars pin legacy Haiku IDs

**Source:** [Claude Haiku 5.5, 2026-10-07](https://www.anthropic.com/claude-haiku-5-5) + [Claude Code CHANGELOG v2.1.293, 2026-10-07](https://code.claude.com/docs/en/changelog) (new API default).

### Why it's relevant
After 2.1.293, the Anthropic API's **default** `claude-haiku` family returns 5.5. But a consumer-project operator who pinned `ANTHROPIC_MODEL=claude-haiku-4-5` (or `claude-haiku-4-5-20250902`) in `~/.zshrc` or `.envrc` months ago will keep getting 4.5 silently, including when the harness's orchestrator dispatches a Haiku subagent. The orchestrator reads routing hints from `.harness-profile` + runtime judgment, not from env vars — so it never sees that the operator's env has pinned a legacy ID downstream.

This is **narrow**: it only matters if (a) a consumer-project operator explicitly pinned a Haiku ID in env, and (b) they did so before Oct 7, 2026. The surface area is small enough that `setup-harness` could warn once per install, not block.

### Concrete changes

Add a small env-var check to `skills/setup-harness/SKILL.md`'s existing prerequisites block (near line 141, where Auto Mode interactions are already explained):

```markdown
### Env-var model pins

Check for legacy model pins in the operator's shell env:

\`\`\`bash
env | grep -E '^(ANTHROPIC_MODEL|CLAUDE_CODE_MODEL)=' | grep -E 'haiku-4|sonnet-4\.0|opus-4\.0' && \
  echo "⚠️ Legacy model ID pinned in env. See https://www.anthropic.com/claude-haiku-5-5 for the current default."
\`\`\`

Warn once; do not auto-edit the operator's shell config. This is a hint, not a gate.
```

### Expected payoff
Catches the one obscure failure mode (operator's env silently overrides the orchestrator's cheap-tier dispatch) without blocking any legitimate install. Costs ~8 lines in `setup-harness/SKILL.md`.

### Why `defer`
This is **speculative** until a user actually reports the failure mode. The harness's routing is already runtime-judgment-driven; env pins are a user-side configuration surface the harness doesn't own. Noting here so future-you has the implementation sketch ready if the issue surfaces, but it would be premature to add warnings for a failure mode no one has hit yet.

### Verify before applying
`grep -n 'ANTHROPIC_MODEL\|CLAUDE_CODE_MODEL' skills/setup-harness/SKILL.md` — if non-empty, the env-pin check is already present and this suggestion is already covered.

**Recommended verdict:** defer until a user hits it — the harness owns the routing path, not the env; defer the warning until a consumer-project operator reports an actual failure.
**Status:** PENDING — awaiting triage in PR review
