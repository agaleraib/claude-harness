This is not a straight edit. The harness's model routing is a single-term decision (model → effort tier follows); introducing cross-term routing (model × effort tier) is a **design change** to the orchestrator's dispatch rules.

### Concrete change (spec, not diff)
Open a `/spec-planner` pass with the brief:

> The orchestrator's model-selection step at `.claude/agents/orchestrator.md:114-153` decides a model first; the effort tier follows the model. With Haiku 5.5's effort dial, decide whether the orchestrator should (a) stay single-term and only use Haiku 5.5's default effort, (b) extend the routing table to list `haiku-5.5 + {low, medium, high}` explicitly, or (c) decouple model and effort as independent axes with a cost-vs-latency objective.
>
> Constraints: the existing default effort selection rules at `.claude/agents/orchestrator.md:154-168` must stay valid as a fallback. Cost model must stay legible — the cost column in `effort_cost_multiplier: {}` is the current (empty) hook for this.

Changing which model handles which bucket is a **methodology change**, not a name rename. The harness's `stakes: medium` policy and `methodology: phase_gates: advisory` imply this gets a spec pass rather than a direct edit. Shipping §1 + §2 first captures the cost/capability win at the primary/fallback tier; the Haiku routing re-think can follow if the first few `/run-wave` runs show a cost spike on Sonnet-tier dispatches that Haiku 5.5 could absorb.

## 6. Scion ↔ global-git-hook-dispatcher translation (rejected)

### Why it's relevant
Scion is Anthropic's **in-house server-side VCS**, premised on "clients are always online" (the opposite of git's offline-first design). Agent-relevant takeaways from the post:

- "Agents sometimes violate core system constraints to satisfy a pattern" → engineers' main job is to say "no." The post frames the harness's role as **enforcing constraints the agent won't respect**.
- "Reviewers examine the intent of the change as opposed to reading every line of code." Pairs with the harness's `code-reviewer` agent, which is adversarial on correctness rather than line-by-line stylistic.
- "Prefer few refs." Scion discourages branches except main / release. Not a direct harness recipe (git allows cheap branches; the harness's worktree-per-wave convention is the correct local analogue).
- "Replace merge queues with post-merge testing." Doesn't translate — the harness has no merge queue.

The only insight that even half-translates is #1: engineers set constraints. The harness's **global git-hook dispatcher** (`feat(git-hooks): global dispatcher — secret scan, mass-delete block, profile gate`; merge commit `e0328b8`, 2026-11-13) is the embodiment of that principle, landed one day before this review.

### Why rejected
Citing the Scion post from the hook-dispatcher's code or docs would:

- Add a flattery link ("Anthropic agrees with us") without a new directive.
- Imply a design lineage that doesn't exist — the hook dispatcher was designed from first principles, not from Scion's playbook.
- Age poorly if Scion's design choices evolve (the post says it's early-stage, Anthropic-internal).

If anything, the hook dispatcher's commit message should **stand on its own evidence** (secret scan, mass-delete block, profile gate are all self-justifying).

**Verify before applying:**

2. Re-read the hook-dispatcher README/docs if present (`git show e0328b8 --stat`); if the docs feel incomplete and a philosophical citation would genuinely fit, the rejection could be revisited.

**Recommended verdict:** reject — translation is weak; the hook dispatcher already embodies the principle self-evidently.

## 8. Scope dreaming to goals (per-dossier compaction scoping in the auto-remediation worker)

**Source:** [The components of agent memory — anthropic.com/research, 2026-11-06](https://www.anthropic.com/research/components-of-agent-memory).

### Why it's relevant
The post's memory hierarchy (transcripts → notes → wiki → injected) maps directly onto the harness's memory system as redesigned in [`docs/specs/2026-05-13-memory-system-redesign.md`](../docs/specs/2026-05-13-memory-system-redesign.md):

| Post layer | Harness analogue |
|---|---|
| Transcripts (searchable event log) | `.harness-state/*.jsonl` run logs |
| Memory notes (salient observations) | `~/.claude/projects/<cwd>/memory/project_*.md`, `feedback_*.md` |
| Memory representations (wiki) | `~/.claude/memory/{USER,FEEDBACK,REFERENCES,PROJECTS}.md` (shared root) |
| Injected context | Claude Code auto-memory loading `MEMORY.md` index |

The harness already implements this hierarchy plus **byte-exact-backup auto-remediation** (2026-05-31 spec) — a mature operational layer the post doesn't cover.

The one **genuinely new** prescription in the post is **"scope dreaming to goals":**

> "Scope dreaming to goals. Tune the instructions for each task. In the contract example, one agent per contract page raised graded facts from 41 of 57 to 57 of 57."

Applied to the harness, this would mean: the auto-remediation worker currently compacts over-cap dossiers with a general-purpose compaction prompt; a per-dossier (per-project, per-feedback-topic) scoping could improve the quality of what survives. Example: a `project_memory_system_redesign.md` dossier would be compacted with the instruction "preserve wave boundaries, task IDs, and rollback breadcrumbs"; a `feedback_wave_vs_micro_shape_rule.md` with "preserve the 5-signal classifier and its training inputs."

### Concrete change (defer)
Extend the 2026-05-31 memory-cap-autoremediation spec with a per-dossier scoping layer. Rough shape:

```
worker.compact(dossier_path):
  scope_hint = derive_scope_hint(dossier_path)
    # e.g. basename.startswith('project_') → "preserve wave/task IDs and rollback breadcrumbs"
    # e.g. basename.startswith('feedback_') → "preserve classifier signals and training inputs"
  claude -p --scope "$scope_hint" --file "$dossier_path"
```

This is a spec-level change to the worker's prompt shape, not a trivial edit.

### Why defer, not apply
The auto-remediation layer landed in 2026-05-31 and hasn't yet produced field data on **which** compactions are low-quality. Before adding per-dossier scoping, want to see:

1. How often the worker's general-purpose compaction produces a candidate that fails the deterministic preservation gate.
2. Which dossier shapes (project / feedback / archive) see the most failures.
3. Whether the gate failures cluster by shape in a way that the scoping hint would address.

Shipping the scoping layer before that data would be premature — the Nov 6 post's "41 of 57 → 57 of 57" contract example is domain-specific; the harness's dossier domain may not have the same quality floor.

### Also-worth-noting (no change)
- "Memory as prediction: record verified rules and how you knew they were true." The harness's feedback dossiers already carry `originCwd:` + `promotedAt:` frontmatter (provenance); the "how you knew" is captured in the spec/wave-receipt cross-ref. No gap.
- "Keep the injected layer small; long instruction files reduce adherence." The harness's per-cwd `MEMORY.md` cap is 5KB; the memory-cap-autoremediation worker exists to enforce this. No gap.
- "Give each file or entity a single writer to avoid overwrites." The harness's write-authority discipline is already per-skill (`/micro`, `/commit`, `/close-wave`, `/memory-prune` each own their outputs). No gap.

**Verify before applying:**
1. `grep -c 'needs-review\|gate.failed' .harness-state/*.jsonl` — if the auto-remediation worker has produced ≥10 gate-failure candidates since 2026-05-31, there's enough data to spec the scoping layer. If zero, the defer stands.
2. Re-read `docs/specs/2026-05-31-memory-cap-autoremediation.md` §"Design Principles" — the "open dossier auto-promotion is deferred to a follow-up spec" clause is the hook for this suggestion.

**Recommended verdict:** defer until auto-remediation worker produces gate-failure data.
**Status:** PENDING — awaiting triage in PR review
