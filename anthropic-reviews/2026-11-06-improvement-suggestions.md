## 2. Audit `.claude/agents/` (6 agents) + `skills/` (25 skills) against "When to fold subagents into your main agent loop"

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com/resources, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

### Why it's relevant
The post argues that most multi-subagent agent systems improve on quality, cost, and latency by **folding subagents back into one main loop** that uses skills and progressively-disclosed tools, keeping subagents only where they clearly earn their keep. Verbatim from the post: *"Each new model lets you move more of the decision-making out of the harness and into the model itself."* The recommended discipline:

1. Build an end-to-end eval set first.
2. Fold one subagent in at a time and compare scores task-by-task.
3. Convert subagent prompts into skills; group API calls into tools by user intent; use tool-search since tool choice degrades past ~30–50 tool definitions.
4. Keep a subagent only when it needs **parallel work**, **fresh context**, or **isolated permissions**; use a full handoff only when the subagent must talk to the user directly.

The harness's current shape (verified 2026-11-06):

| Agent | File | Role | Fold-candidate? |
|---|---|---|---|
| orchestrator | `.claude/agents/orchestrator.md` | Dispatches spec-task phases | Keep — parallel-dispatch role, hard to collapse |
| generator | `.claude/agents/generator.md` | Spec → code loop | **Audit** — could it become a `/generate` skill in the main loop? |
| code-reviewer | `.claude/agents/code-reviewer.md` | Adversarial review before commit | Keep (fresh context) — but check whether skill form would suffice |
| ui-evaluator | `.claude/agents/ui-evaluator.md` | Scores against `criteria/*.md` rubrics | Keep (fresh context, Playwright tool isolation) |
| spec-planner | `.claude/agents/spec-planner.md` | Discovery-question loop before spec write | **Audit** — a natural slash-command/skill shape |
| project-tracker | `.claude/agents/project-tracker.md` | Save session to Second Brain | **Audit** — this is now bookkeeping, not a cognitive task; `/session-end` skill may absorb it |

Plus 25 skills (`wc -l skills/*/SKILL.md` = 6,082 total lines; largest: `planning-loop` 719, `close-wave` 677, `skill-creator` 488, `run-wave` 449, `triage-parking` 412). The post's ~30–50 tool-count threshold doesn't apply directly (skills ≠ tool definitions), but the shape of the question is the same: at what point does the harness's specialist-fanout stop paying for itself?

### Concrete change
**No code yet — spec first.** The audit the post prescribes requires (a) an eval set the harness does not have (`test_required: false` in `.harness-profile`), (b) a baseline run of each candidate in main-loop form vs. subagent form, and (c) a verdict per candidate. That's a `/spec-planner` pass, not a `/micro` edit.

Proposed spec scope — three sections, 2026-11-xx:
1. **Methodology** — adopt the post's "evals first, then fold one at a time" protocol as the harness's audit convention; cite the post as the authority.
2. **Candidate list** — the three Audit rows above (`generator`, `spec-planner`, `project-tracker`), with a one-paragraph rationale per candidate for why it might fold.
3. **Eval harness** — the minimum eval set a solo maintainer can run to make the task-by-task comparison legible; drops the `test_required: false` flag only for the agents under review, not the whole harness.

### Expected payoff
- If even one of the three candidates folds cleanly, the harness ships fewer specialist agents to every consumer project — which lowers maintenance surface and makes the harness's "main-loop decision-making" story stronger.
- The eval set is reusable once built — it becomes the test infrastructure the harness has been without.

### Non-goals
- Do NOT fold `code-reviewer`, `ui-evaluator`, or `orchestrator` without evidence. `code-reviewer` and `ui-evaluator` have the "fresh context" property the post names as the retain-criterion, and `orchestrator`'s parallel-dispatch role is exactly what the post keeps as a subagent-worthy shape.
- Do NOT start folding without the eval set. The post is explicit: *"Build an end-to-end eval set first."* Folding without evals is the anti-pattern the post is written to prevent.

### Verify before applying
Run `ls .claude/agents/ skills/ | wc -l` and `grep -c "^name:" .claude/agents/*.md` to confirm the current counts (6 agents, 25 skills) still match before any spec draft; the post's folding advice is index-sensitive, so the recommendation changes if the harness has already shrunk since 2026-11-06.

**Recommended verdict:** spec — methodology-level change that touches six agent files and the eval story; needs a design pass before any code. scope: speculative.

## 3. Add `permissions.blockWritesOutsideWorkingDirectories: true` to the `.claude/settings.json` seed in `setup-harness`

**Sources:**
- [How we contain Claude across products — anthropic.com/research, 2026-05-25](https://www.anthropic.com/research/how-we-contain-claude) — "Agent risk is best controlled by capping blast radius with hard environmental boundaries matched to user oversight… The deterministic boundary is what gets hit when everything probabilistic misses."
- Claude Code changelog [v2.1.314, 2026-10-30](https://code.claude.com/docs/en/changelog) — "Added `permissions.blockWritesOutsideWorkingDirectories`: Write, Edit and NotebookEdit refuse paths outside the working directories in every permission mode."

### Why it's relevant
The May 25 research post is Anthropic's long-form containment thesis: **probabilistic defenses always miss some cases, so blast radius must be capped by environmental boundaries.** The v2.1.314 Claude Code primitive is exactly that shape at the write-path layer — it refuses writes outside the working directories in **every** permission mode, including bypass/auto. This is complementary, not redundant, to the harness's existing containment layers:

- `PreToolUse` denylist (secret scan, mass-delete block, profile gate) — commit `5130b9d`, `e0328b8`. Runs on *every* tool call pre-emptively.
- `permissions.defaultMode` conversation — deferred in [2026-05-08 §1](./2026-05-08-improvement-suggestions.md#1-document-auto-mode--hooks-interaction-in-setup-harness-and-optionally-seed-claudesettingsjson-permissionsdefaultmode) under Auto Mode.

What's **missing** today (verified 2026-11-06 — `grep -rn 'blockWritesOutsideWorkingDirectories\|working.*director' .claude/ skills/setup-harness/` returns nothing): the write-path environmental boundary. `.claude/settings.json` has only an empty `{"hooks": {}}` block. The containment research is explicit — verbatim — that **hook execution from project settings running before the trust prompt was a *missed risk*** at exactly the layer this harness operates at; `setup-harness` installs hooks for consumer projects, so the matching write-path containment is the natural pair.

### Concrete change
**Single JSON edit in `.claude/settings.json`** — add a `permissions` block:

```diff
 {
-  "hooks": {
-  }
+  "hooks": {
+  },
+  "permissions": {
+    "blockWritesOutsideWorkingDirectories": true
+  }
 }
```

And a matching one-paragraph note in `skills/setup-harness/SKILL.md` after the existing user-level-skill install step — something like:

```markdown
### Write-path containment

Seed `.claude/settings.json` in every target project with:

```json
{
  "permissions": {
    "blockWritesOutsideWorkingDirectories": true
  }
}
```

Added in Claude Code v2.1.314 (2026-10-30). Write, Edit, and NotebookEdit refuse paths outside the working directories in every permission mode — including `bypassPermissions` and Auto Mode. Matches Anthropic's containment thesis ("the deterministic boundary is what gets hit when everything probabilistic misses") and complements this harness's PreToolUse denylist.
```

### Expected payoff
- One deterministic boundary at the write path, in every permission mode. A hallucinated `/etc/` or `~/.ssh/` write — the kind of mistake the probabilistic layers aren't guaranteed to catch — gets refused.
- Reinforces the harness's "Why Not Superpowers" thesis that vendor primitives absorb what harnesses used to bolt on: the harness ships the containment seed, Claude Code enforces it.
- Runs in bypass/Auto Mode, which means it composes correctly with the deferred 2026-05-08 §1 (`permissions.defaultMode`). No conflict — adopting §3 doesn't block or require §1.

### Non-goals
- Do NOT enumerate per-directory allowlists. The knob is a binary; keep the seed simple.
- Do NOT add other `permissions.*` fields opportunistically (e.g. `defaultMode`, `allow` lists) — those are either deferred (2026-05-08 §1) or belong to the operator's personal preference.

### Verify before applying
- `cat .claude/settings.json` — confirm the `permissions` block is not already present. If it is, this § is satisfied.
- `grep -rn "blockWritesOutsideWorkingDirectories" skills/setup-harness/` — confirm `setup-harness` doesn't already document the knob.
- Fetch [Claude Code changelog v2.1.314](https://code.claude.com/docs/en/changelog) — confirm the knob is still released as described (not superseded or renamed).

**Recommended verdict:** apply — single JSON line + a `setup-harness` note; clear value prop grounded in both a research post and a shipped Claude Code primitive.
**Status:** PENDING — awaiting triage in PR review

## 5. Flag `CLAUDE_CODE_SUBAGENT_EFFORT` (v2.1.316, 2026-10-31) — a candidate `env` knob for ad-hoc fork cost

**Source:** Claude Code changelog [v2.1.316, 2026-10-31](https://code.claude.com/docs/en/changelog) — "Added `CLAUDE_CODE_SUBAGENT_EFFORT` to set the effort level subagents run at when nothing else names one, instead of inheriting the session's."

### Why it's relevant
The harness has a deliberate **effort-routing story** (per `docs/specs/2026-04-19-harness-model-pin-and-effort-routing.md` and `.claude/agents/orchestrator.md`): the orchestrator names model + effort per task (overrides env), and sessions run at `effort_default: xhigh` because `.harness-profile:18` names `stakes.level: medium` and the derivation table bumps that to `xhigh` (profile line 32).

**Today**, ad-hoc subagents — e.g., forks spawned outside the orchestrator loop (like this review's own discovery/fetch forks earlier this turn) — inherit the session's `xhigh` effort. That is possibly the most expensive default per unit of work. `CLAUDE_CODE_SUBAGENT_EFFORT=medium` would move the default *for ad-hoc forks only*, while orchestrator-named effort still overrides per call — the exact shape the env var is designed for.

But: the harness has **no cost trace** showing fork cost is a real tax. The maintainer is solo, the orchestrator is the primary sub-dispatcher, and ad-hoc forks are operator-initiated (reviewer-model's judgment). Setting this to `medium` now is a cost/quality tradeoff whose cost side is speculative.

### Concrete change (if adopted — do not apply without the cost-trace evidence)
Add to `.claude/settings.json`:

```diff
 {
   "hooks": {
-  }
+  },
+  "env": {
+    "CLAUDE_CODE_SUBAGENT_EFFORT": "medium"
+  }
 }
```

(Combines with §3's `permissions` block if both are applied.) And a corresponding one-paragraph note in `docs/specs/2026-04-19-harness-model-pin-and-effort-routing.md` (or a new spec addendum) naming the env var alongside `effort_default` as part of the harness's effort story.

### Expected payoff (if adopted)
- Ad-hoc forks default to `medium` instead of `xhigh`, which at current Opus 5.5 pricing is a material per-fork savings (output tokens at $20/MTok × effort multiplier). Orchestrator-routed subagents still get their task-specific effort.

### Non-goals
- Do NOT apply without evidence. "Speculative cost optimization at the env-var layer" is exactly the pattern this review's rubric is written to avoid.
- Do NOT override `effort_default` on the session via this env var — this knob is for subagents only. The derivation table in `project-init` still governs the parent session.

### Verify before applying
- `grep -rn "CLAUDE_CODE_SUBAGENT_EFFORT\b" . 2>/dev/null` — confirm the env var isn't already referenced in a spec or settings file.
- Look at `.harness-state/*.yml` or any cost telemetry the maintainer has collected since 2026-10-31. If ad-hoc forks are visibly consuming more cost than orchestrator-routed subagents, that's the trigger. If no trace exists, the defer verdict stands.
- Fetch [Claude Code changelog v2.1.316](https://code.claude.com/docs/en/changelog) — confirm the env var's semantics haven't shifted (e.g. precedence vs. Agent-tool `effort` override).

**Recommended verdict:** defer until cost-trace surfaces fork cost — crisp knob, but applying it now is speculative optimization without a documented pain signal.
**Status:** PENDING — awaiting triage in PR review
