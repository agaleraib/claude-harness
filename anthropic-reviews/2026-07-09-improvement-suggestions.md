## 1. Update `setup-harness` §Permission model to reflect v2.1.200's Manual-default flip (July 3, 2026)

**Source:** Claude Code v2.1.200 changelog (2026-07-03) — default permission mode changed from Auto to Manual across CLI, VS Code, and JetBrains surfaces; documented widely in the ecosystem but shipped without an Anthropic blog post. Third-party summaries: [Claude Code Defaults to Human Approval: Auto Mode Requires Explicit Opt-In](https://www.techtimes.com/articles/319874/20260707/claude-code-defaults-human-approval-auto-mode-requires-explicit-opt.htm) · engineering deep-dive still relevant: [How we built Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode).

### Why it's relevant

On 2026-05-10 this routine applied a §Permission model subsection to `skills/setup-harness/SKILL.md` (verified: lines 139–149 today, added in commit 8b5b12a). That section says Auto Mode is GA and recommends "Toggle Auto Mode interactively via Shift+Tab", noting that `permissions.defaultMode: "auto"` didn't reliably auto-engage at session start. Two months later, Claude Code v2.1.200 (2026-07-03) flipped the out-of-box default: **Manual mode is now the default across every surface**, and Auto Mode requires explicit opt-in via `--permission-mode auto`, `permissions.defaultMode: "auto"` in settings, or `/mode auto` inside a session.

The current setup-harness text now understates the safety default (it implies you have to toggle Auto Mode on) and overstates a config-only bootstrap being unreliable (Manual is the default, so no toggle is needed to get the safer behavior).

### Concrete change

Update the four-line block in `skills/setup-harness/SKILL.md` §"Permission model — Auto Mode + hooks layering" (currently around lines 139–149) to state:

- **Manual mode is Claude Code's default** as of v2.1.200 (2026-07-03). Every file write, shell command, and network call surfaces a prompt unless a hook allow-lists it or the user opts into Auto Mode.
- **Auto Mode is opt-in** via `permissions.defaultMode: "auto"` in `.claude/settings.json` or `~/.claude/settings.json`, `claude --permission-mode auto`, or the interactive `/mode auto`. When on, it runs the Sonnet 4.6 classifier described in [How we built Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode).
- **Hooks-run-first ordering is unchanged**: whatever this harness allow/deny-lists in `.claude/settings.json` (and whatever `fewer-permission-prompts` adds) is honored as a hard rule before any mode decision. This is what makes the harness's curated hook block compose cleanly with either Manual or Auto.
- **Recommended for solo users:** stay on the v2.1.200 Manual default; run `/fewer-permission-prompts` to seed an allowlist for the read-only Bash + MCP calls you actually use, so Manual-mode prompts are limited to the actually-risky residual. Only opt into Auto Mode if you're seeing prompt fatigue on tasks you routinely approve — the classifier is a fallback, not the primary safety layer.

Keep the "isolated container" note: prefer Auto Mode over `bypassPermissions` in an isolated environment, because the classifier's prompt-injection mitigations still fire.

### Expected payoff

A solo maintainer re-running `/setup-harness` in a new project post-v2.1.200 sees a permission-model note that matches the actual current default, instead of one that reads as if Auto Mode were still the recommended toggle. Cost: ~15 lines of doc rewrite in one file; risk: zero (documentation only, no behavior change).

**Verify before applying:** `grep -n "Auto Mode\|defaultMode\|v2\.1\.200" skills/setup-harness/SKILL.md` — the current file names "Auto Mode (GA on Pro/Max/Team/Enterprise/API as of May 2026)" and recommends "Toggle Auto Mode interactively via Shift+Tab" without mentioning v2.1.200 or the Manual default. If the file has already been updated (either to reflect v2.1.200 or via a further release), re-read before editing. Also confirm the v2.1.200 changelog line still stands: `claude --version && claude --help | grep -i "permission.mode"` in a live session should show Manual as default.

**Recommended verdict:** apply — targeted correction of a stale two-month-old recommendation that this routine itself made; primary-source citation replaces speculation.

## 3. Position **dynamic workflows / `ultracode` / `.claude/workflows/`** alongside the harness's `orchestrator` agent in the README

**Source:** [A harness for every task: dynamic workflows in Claude Code](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) — Claude blog, 2026-06-02 (companion product post: [Introducing dynamic workflows](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code); docs: <https://code.claude.com/docs/en/workflows>).

### Why it's relevant

Anthropic just shipped a mechanism — dynamic workflows — that overlaps in *concept* with this harness's `orchestrator` agent (`.claude/agents/orchestrator.md`, verified: 80+ lines of prose describing the same orchestrator-worker pattern that the post's Claude-writes-a-JS-script runtime automates). But they sit at *different layers* and the overlap is not a redundancy — it's a delimiter question:

**Harness `orchestrator` agent (today):**
- Reads a spec file (`docs/specs/<date>-*.md`), extracts tasks, dispatches to Opus/Sonnet/Haiku based on complexity.
- Task-shaped: one task = one subagent invocation, ordered by declared dependencies.
- Runs synchronously in the main Claude Code session; costs the current session's tokens.
- No native fan-out beyond the task list; no `Workflow` tool.

**Anthropic dynamic workflows (2026-06-02):**
- Claude writes a **JavaScript orchestration script** on the fly, targeting the current task's shape (fan-out-and-synthesize / adversarial verification / generate-and-filter / tournament / classify-and-act / loop-until-done — six built-in patterns per the post).
- A **separate runtime** executes it in the background across 10–1000 subagents; the main session stays responsive; progress is journaled and resumable.
- Trigger paths: `ultracode` keyword in a prompt, `/effort ultracode` session-wide, or a saved workflow command in `.claude/workflows/*.js` or `~/.claude/workflows/*.js`.
- Requires Claude Code v2.1.154+ and a paid plan / API access.

The harness has **zero references** to dynamic workflows, `ultracode`, `.claude/workflows/`, or the Workflow tool anywhere in prose (`grep -rn "ultracode\|dynamic workflow\|\.claude/workflows" .` returns nothing except the specs directory hits that are also nothing — verified). `.claude/workflows/` does not exist in this repo; `~/.claude/workflows/` does not exist on this machine.

The next time future-you (or a collaborator) wonders "should I use the orchestrator agent or fire off an ultracode workflow?", the answer is not on the page.

### Concrete change

**One paragraph appended to `README.md` at the `orchestrator (Universal)` agent section**, mirroring the shape applied on 2026-05-10 §1 for the code-reviewer agent (find the section by searching README for `orchestrator (Universal)` — this routine hasn't verified its exact line number today; do the grep before editing):

```markdown
#### How this complements Anthropic's dynamic workflows

The harness's `orchestrator` agent runs **synchronously against a spec file**, dispatching one subagent per spec task with opus/sonnet/haiku routing based on complexity. As of [Code w/ Claude 2026](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (June 2026), Claude Code natively supports **dynamic workflows** — Claude writes a JavaScript orchestration script on the fly, run by a separate runtime that fans out 10–1000+ subagents in the background, journals progress, and resumes on interruption. Trigger via the `ultracode` keyword in a prompt, `/effort ultracode` for a whole session, or a saved workflow command in `.claude/workflows/*.js`. Use the harness's `orchestrator` for **spec-shaped work** (declared tasks, declared dependencies, deterministic routing, current-session cost model); use **dynamic workflows** for **unshaped exploration** (fan-out-and-synthesize, adversarial verification, tournament, loop-until-done — where Claude picks the pattern and the runtime absorbs the wall-clock). They are complementary, not redundant.
```

**Do NOT** wire the orchestrator to invoke the Workflow tool. That's an architectural decision (does the orchestrator delegate its dispatch to the native Workflow runtime? do we start seeding `.claude/workflows/*.js` files? does `/run-wave` know about workflow commands?) and belongs in a `/spec-planner` pass, not a documentation § — hence the `defer` recommendation below.

### Expected payoff

Same as the 2026-05-10 §1 code-reviewer note: a one-paragraph delimiter that future-you can point to when the question "orchestrator or ultracode?" comes up. Zero code change; the design decision to actually adopt dynamic workflows waits for a spec. Cost: ~15 lines of README; risk: zero (documentation only).

**Verify before applying:** `grep -n "ultracode\|dynamic workflow\|/workflow" README.md AGENTS.md WORKFLOW.md CLAUDE.md` should still return nothing today. If any of those docs already position dynamic workflows against the orchestrator, adjust the § to reference the existing text rather than adding a duplicate paragraph. Also confirm the Workflow trigger path is stable: `claude --version` should report ≥ v2.1.154, and the built-in Claude Code system prompt should still mention `ultracode` in this session (it did as of this run — Workflow tool is listed as available with the ultracode opt-in convention documented).

**Recommended verdict:** defer until orchestrator scope pain warrants — documentation-only note is cheap, but the underlying design question (does the orchestrator delegate to Workflow?) needs a spec pass and the maintainer's on-ramp cost to `.claude/workflows/*.js` is not zero. **scope: speculative**

## 4. Note the containment lesson — `.claude/settings.json` hooks execute before folder-trust — as an explicit bullet in `CLAUDE.md`

**Source:** [How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude) — Anthropic Engineering, 2026-05-25.

### Why it's relevant (and why it doesn't need action)

The engineering post reveals a real-world Claude Code security issue: a cloned repo's `.claude/settings.json` `hooks` block executed *before* the "Do you trust this folder?" prompt fired. Three disclosed vulnerabilities shared this shape; upstream fix was to defer config parsing until after trust is accepted. The general lesson for hook authors: hooks in project-level `.claude/settings.json` are a distribution-side supply-chain surface.

**This harness already reflects that lesson in its design.** Verified:

- The project-level `.claude/settings.json` shipped with this repo is `{"hooks": {}}` (empty) — nothing in-tree fires on `PreToolUse` / `SessionStart` / `Stop` for anyone who clones it.
- `CLAUDE.md` §"Loop protocol" already carries the discipline: "The catastrophic-command denylist is a Claude Code `PreToolUse` hook the operator installs in `~/.claude/settings.json` (global). ... wiring it into global settings is an operator action and is NOT done from a session — see the `/run-loop` skill's Human-only TODOs."
- The memory-cap auto-remediation hooks (`docs/specs/2026-05-31-memory-cap-autoremediation.md` §Phase 4) are also installed in **global** `~/.claude/settings.json`, not project-level.
- The consumer-facing `setup-harness` skill copies procedures + criteria + user-level skills to target projects; it does not write hooks into a target project's `.claude/settings.json`.

The containment article's advice is corroborative, not corrective. Adding a bullet to `CLAUDE.md` restating "we don't ship project-level hooks" would be redundant with the loop-protocol note already there.

**Recommended verdict:** reject — the design intent is already reflected in `CLAUDE.md` §"Loop protocol" and the committed `.claude/settings.json`. Retain this § as durable evidence-of-consideration in case the discipline ever slips.
**Status:** PENDING — awaiting triage in PR review
