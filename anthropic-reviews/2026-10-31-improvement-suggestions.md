## 2. Audit the orchestrator's subagent surface against "fold subagents into the main loop" guidance

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com/resources, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

### Why it's relevant

The post reframes orchestrator-worker as a **fallback pattern**, not the default. Headline claims:

- A single agent loop with on-demand skills + tool search often **matches or beats** subagent designs on quality, cost, and latency.
- Subagents are justified when there's measurable degradation from context bloat, when tasks are independent and parallel, or when one agent faces conflicting instructions.
- "Split by context, not by problem type or org chart." Each subagent should get work needing little from the rest of the system and return a compact result.
- Prefer **calling a subagent as a tool** over a full handoff; full handoff is only when the subagent must speak to the user directly.
- Newer models absorb more decision-making back into the main loop — subagent fan-out is more of a legacy affordance than a frontier one.

The harness today ships:

- `.claude/agents/orchestrator.md` — the central runtime orchestrator (opus-4.7 by frontmatter) that dispatches to haiku/sonnet/opus "subagents" per task.
- A roster of specialized agents under `.claude/agents/`: `code-reviewer`, `spec-planner`, `generator`, `ui-evaluator`, `claude-code-guide`, `Explore`, `Plan`, `project-tracker`, `statusline-setup`, plus `general-purpose` and `claude`.
- Skills that explicitly dispatch to subagents through the `Agent` tool.

### Why this is `defer`, not `apply` and not `reject`

- The post describes a **direction of travel** ("newer models absorb more into the loop") rather than a prescription that today's design is wrong. The harness's agent roster is largely **domain-separated** (code-reviewer evaluates against `criteria/`, spec-planner expands ideas into specs, project-tracker reaches into Second Brain) — exactly the "clean interface, independent context" case the post explicitly justifies.
- Three agents are more worth a second look:
  - **`orchestrator` itself** — the "dispatch by complexity" design (Opus/Sonnet/Haiku rungs) is exactly the "split by context" pattern the post endorses; but the escalation-ladder machinery adds complexity that newer models could absorb into a single Opus 5.5 loop. The Opus 5.5 upgrade (§1) is the natural moment to re-ask whether the ladder is still worth its weight.
  - **`Plan` and `Explore`** — both are read-only, no-write-tools subagents. The post's "prefer calling a subagent as a tool" guidance applies cleanly; today the harness uses them as full subagents. A cheaper alternative is a tool-search-exposed skill that does the same reads inline.
  - **`claude-code-guide`** — one-shot lookup agent. Could be a tool-exposed skill call.
- **No evidence the current design is misbehaving.** Pre-emptive refactoring against a direction-of-travel post is exactly the "add architecture or scale ahead of current need" shape the routine prompt flags as speculative.

### Concrete change (deferred)

None this run. When/if the maintainer takes it on:

1. Re-visit this § immediately after the §1 Opus 5.5 model upgrade lands — "newer models absorb more into the loop" is specifically a Claude 5.5-era claim.
2. For `Plan`, `Explore`, `claude-code-guide`: measure a baseline (how many invocations per week? what's the typical token cost? is there a quality gap vs. inline tool-use?) before changing anything.
3. Decide the policy threshold: "fold a subagent into the loop when its P50 invocation touches ≤30 context tokens of unique state and the main loop could cover it with a tool-search-exposed skill."
4. If anything folds, update `README.md`'s agent roster and the `/spec-planner` planning-time dispatch logic that assigns tasks to agent types.

**Scope: speculative** — direction-of-travel post, not a prescription against the current design.

### Expected payoff (when applied)

Fewer agent-definition files to maintain; fewer "which agent does this?" decisions at planning time; cheaper runs for the three candidate agents above if they fold cleanly. No quality improvement expected on domain-separated agents (code-reviewer, spec-planner, project-tracker) — those stay as full agents.

**Verify before applying:**
1. `ls .claude/agents/*.md` — should still enumerate ≥7 agents; if the count has dropped, someone has already folded some, and this § needs a delta rebase.
2. `grep -c 'subagent\|Agent tool\|dispatch' .claude/agents/orchestrator.md` — baseline count of orchestrator subagent references; use the delta pre/post as a quick impact-size proxy.
3. Confirm Anthropic hasn't published a follow-up walking back the "fold-into-loop" guidance by the time this is picked up.
4. If §1 Opus 5.5 upgrade has already landed (model.primary: `claude-opus-5-5`), the premise ("newer models absorb more") is live; if not, the premise is unverified against this harness and the spec may want to run §1 first.

**Recommended verdict:** defer until next harness simplification pass — direction-of-travel evidence, not a prescription; no measured regression on today's design; the §1 model upgrade is a cleaner trigger moment to re-ask the question.
