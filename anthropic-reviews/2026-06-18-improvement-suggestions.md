## 2. Decide the relationship between Claude Code's dynamic workflows / `ultracode` and the harness's `/run-loop` + `effort_default: xhigh`

**Source:** [Introducing dynamic workflows in Claude Code — Claude Blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) · [Orchestrate subagents at scale with dynamic workflows — Claude Code Docs](https://code.claude.com/docs/en/workflows)

### Why it's relevant
Dynamic workflows is a research-preview Claude Code feature where Claude writes a JavaScript orchestration script that fans out tens to hundreds of subagents in a single session, checks results, and synthesizes. Two product surfaces matter to the harness:

1. **`ultracode` setting** — flips `effort` to `xhigh` and lets Claude decide automatically when to spawn a workflow. The harness already pins `effort_default: xhigh` in `.harness-profile:32` (derived from `stakes.level: medium`), so `ultracode` is essentially Claude Code's product-level packaging of routing the harness already does — *plus* the auto-route into dynamic workflows.
2. **Workflow orchestration** — overlaps with the harness's own `/run-loop` (Waves 18–24) and `/run-wave` orchestration patterns. The Wave 24 `2026-06-16-run-loop-portable-gate.md:56` spec already names the `/goal` evaluator pattern explicitly out-of-scope ("re-introduces the exact agent-trust the mechanical gate removes"); dynamic workflows sits in similar territory — it relies on Claude's internal verification rather than an external mechanical gate.

The blog post warns: *"Dynamic workflows consume meaningfully more usage than a typical Claude Code session."* For a solo-maintained tooling repo, the cost asymmetry matters.

### Concrete changes (if applied)
- **`AGENTS.md` §"Loop protocol":** add a one-paragraph orientation row: *"Dynamic workflows (research preview) is Claude Code's in-product fan-out across hundreds of subagents in one session. It is NOT a substitute for `/run-loop`'s mechanical exit gate — dynamic workflows verifies via Claude's internal checks, while `/run-loop` blocks merges on repo-resolved checks the agent did not run. Use dynamic workflows for exploratory codebase-scale work where 'finish before review' is acceptable; use `/run-loop` when the mechanical gate is the reason it is safe to walk away."*
- **`skills/run-loop/SKILL.md` "When NOT to use":** one bullet — *"For codebase-scale migrations that don't need a mechanical exit gate (e.g. profiler-guided audits where you'll review the full diff anyway), Claude Code's dynamic workflows is the cheaper-to-set-up path. `/run-loop` earns its overhead specifically because the merge gate runs without you."*
- **`.harness-profile` (DO NOT auto-enable):** explicitly *do not* set `ultracode` on (it would auto-spawn workflows and 10x the usage). Leave the existing `effort_default: xhigh` as the routing knob.

### Why defer rather than apply
- Dynamic workflows is **research preview** (per the blog post — Pro users opt-in via `/config`, on by default for Max/Team/Enterprise). The harness has explicit deferrals tied to "production-stable Anthropic surfaces" (see the deferred 2026-04-19 §2 on Managed Agents); the same rationale applies here.
- The operator just landed **seven waves (18–24) of `/run-loop` work** culminating in `d9cd506`'s portable exit gate (`anthropic-reviews/2026-06-18-improvement-suggestions.md` is being written 2 days after that wave shipped). Rewiring orchestration around dynamic workflows now would discard fresh, deliberately-designed infrastructure.
- The **cost story** is unresolved. The harness is a single-operator tooling repo on a fixed-subscription Claude account; "meaningfully more usage" with no published numbers translates poorly into a budget.

### Expected payoff (if/when applied later)
- Cheap exploratory codebase fan-out (audits, migration scoping) without standing up a full `/run-loop` issue queue.
- A documented complement, not a replacement — preserves the mechanical-gate rationale for trust-critical work.

### Verify before applying
`grep -nE 'dynamic.workflow|ultracode' AGENTS.md skills/run-loop/SKILL.md .harness-profile docs/specs/2026-06-16-run-loop-portable-gate.md` — if the spec or skill already documents the boundary, this suggestion is in place; if dynamic workflows graduates from research preview before the next routine run, re-evaluate the defer.

**Recommended verdict:** defer until research-preview ends AND a cost study against `/run-loop`'s subscription-only cost is in hand. The boundary doc could ship sooner as a small standalone edit, but the rest waits.

## 3. Cite "How we contain Claude across products" in AGENTS.md sandcastle/worktree note

**Source:** [How we contain Claude across products — Anthropic Engineering, 2026-05-30](https://www.anthropic.com/engineering/how-we-contain-claude) · [Simon Willison's notes on the post, 2026-05-30](https://simonwillison.net/2026/May/30/how-we-contain-claude/)

### Why it's relevant
`AGENTS.md:107` already encodes the harness's runner-selection rule: *"An item runs in one of two runners. The **sandcastle** runner (default) runs the agent in a container — the OS is its security boundary. The **worktree** runner runs the agent natively on the host — the OS is NOT the boundary, so the worktree lane carries the safety guardrails below."*

Anthropic's May 30 post is the first-party engineering write-up of exactly this distinction. It names the specific local-sandbox tech Claude Code uses (Seatbelt on macOS, Bubblewrap on Linux) and the lesson Anthropic drew from the failure of their own custom allowlist proxy: *"The software you build yourself is often the weakest. The hypervisor, seccomp, and gVisor across our products have been dependable; our custom allowlist proxy was the piece that failed."* That is direct evidence for the harness's choice to prefer kernel/OS sandboxes (sandcastle) over custom safety hooks for high-blast-radius work.

It also reiterates the Auto Mode posture already covered by 2026-05-08 §1 APPLIED — no new directive on that surface, just supporting evidence for the existing one.

### Concrete changes
- **`AGENTS.md:107` block:** append one sentence after the sandcastle/worktree definition: *"This OS-boundary framing is the same posture Anthropic documents for Claude Code itself ([Anthropic Engineering, 2026-05-30](https://www.anthropic.com/engineering/how-we-contain-claude)) — Seatbelt (macOS) and Bubblewrap (Linux) as the local sandbox; custom allowlist proxies are explicitly named as the layer Anthropic found most prone to failure, which is why the harness's worktree lane layers guardrails on top of the worktree runner rather than substituting for the kernel boundary."*
- **`README.md` "Why Not Superpowers" evidence list (lines 27–32):** append one bullet — *"- **First-party confirmation that custom safety layers are the weakest link**: Anthropic's [How we contain Claude across products (2026-05-30)](https://www.anthropic.com/engineering/how-we-contain-claude) names their custom allowlist proxy as the only containment layer that failed; gVisor, seccomp, and the hypervisor held. The harness's preference for OS-boundary sandcastle over custom in-process allowlists is the same instinct."*
