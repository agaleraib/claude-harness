## 3. Position the harness's `/run-wave` + `/run-loop` orchestrators against Anthropic's dynamic workflows / `ultracode`

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (engineering deep-dive); shipped in Claude Code v2.1.154 alongside Opus 4.8. The [Claude Code docs page](https://code.claude.com/docs/en/workflows) is the canonical reference. **Trigger keywords:** `ultracode` keyword (renamed from `workflow` in v2.1.160), or `/effort ultracode` to let Claude plan a workflow for every substantive task in the session.

### What dynamic workflows are

A **JavaScript script** the Claude Code runtime executes in an isolated background environment, separate from the user's conversation context. The script orchestrates **subagents** via `agent()` / `parallel()` / `pipeline()` / `phase()` hooks; intermediate results live in script variables, not in Claude's context window, so a fan-out can span tens-to-hundreds of agents (caps: 16 concurrent, 1000 lifetime per run) without context-pollution. Scripts are **resumable in the same session** (the runtime journals each agent's result). Anthropic's blog post names six composable patterns: **classify-and-act, fan-out-and-synthesize, adversarial verification, generate-and-filter, tournament, loop-until-done**. The runtime ships a bundled `/deep-research` workflow as a worked example.

### Why this is harness territory

The harness has **two orchestrators of record**:

- **`/run-wave N`** (`skills/run-wave/SKILL.md`, 446 lines) — typed phase orchestrator that reads a wave file from `docs/waves/wave<N>-*.md`, dispatches each task to opus/sonnet/haiku via the `orchestrator` subagent (`.claude/agents/orchestrator.md`), routes through `/commit` per task.
- **`/run-loop`** (`skills/run-loop/SKILL.md` + `skills/_shared/loop/` TypeScript engine) — autonomous wave-driver that picks up a wave file (or a GitHub issue source), runs to completion, and reports back.

Both implement a subset of what dynamic workflows now expose as a first-class primitive. Specifically:

| Pattern from the dynamic-workflows post | Harness's current handling |
|---|---|
| classify-and-act | `orchestrator` subagent does runtime model routing |
| fan-out-and-synthesize | not in `/run-wave`; `/run-loop` is single-track |
| adversarial verification | `code-reviewer` agent runs once per task in `/commit`; no N-way fan-out |
| generate-and-filter | not present |
| tournament | not present (closest: planner→generator→evaluator in `/run-wave`) |
| loop-until-done | `/run-loop`'s entire premise |

So the **overlap is real but partial**. Two coherent directions:

**Direction A: delegate fan-out to dynamic workflows.** Keep `/run-wave` + `/run-loop` as the typed-spec entry points; when a wave task says "fan out over N files," the orchestrator emits an `ultracode:` request and lets Claude Code write the JS script. Harness keeps the typed-task contract; Anthropic owns the parallelism + verification primitives. Cheap to adopt — mostly a prompt change to `orchestrator` so it knows the trigger.

**Direction B: keep the harness orchestrators as the canonical surface, treat dynamic workflows as a complementary primitive for ad-hoc fan-out.** Document the boundary in `README.md` so the next reader doesn't wonder which to use when. No code change.

Both are defensible. The **wrong** direction would be ignoring the new primitive — `ultracode` is going to be in users' fingers and the harness needs a stance on how it composes with `/run-wave`.

### Why this is `spec`, not `apply`

1. **Cross-skill implications.** The decision touches `orchestrator` (model routing), `run-wave` (per-task contract), `run-loop` (long-running automation), `spec-planner` (does a spec author now think in workflow patterns when planning?), and the README's "How the harness works" mental model. Five-file-edit threshold is hit easily.
2. **Architectural commitment.** Direction A makes the harness lighter (delegate more) at the cost of vendor lock-in to a runtime that's < 1 month old. Direction B preserves harness independence but requires keeping the orchestrator's pattern library in sync with Anthropic's evolving one. Picking one is a design call, not a prompt edit.
3. **The harness's lean-context thesis applies.** The README's case for "doesn't tell the model HOW to think" needs re-reading against dynamic workflows — the post argues for **dynamic** harnesses (Claude writes the script per task) over **static** ones (the harness pre-defines the orchestration). The harness today is closer to the static end. Worth a spec to decide if that's still the right place.
4. **The bundled `/deep-research` workflow is the only real worked example today.** Patterns like *tournament* and *generate-and-filter* are listed in the post but not yet in widespread use. Easier to spec once a wider catalog of workflow scripts exists in the wild.
5. **Token-cost calculus changes.** Dynamic workflows can spawn hundreds of agents; the harness's `/run-wave` runs one task at a time. The cost shape is different and worth understanding before the orchestrator emits `ultracode` automatically.

### Concrete change (deferred to spec)

None this run. When the maintainer wants to take this on:

### Expected payoff (when applied)
Coherent answer to "should I use `/run-wave` or `ultracode` for this task?" baked into the harness. Stops `ultracode` from being a parallel orchestration surface users discover by accident and don't know how to compose with the harness.

## 4. Add a "clean-clone risk" pointer to `skills/setup-harness/SKILL.md` from "How we contain Claude across products"

**Source:** [How we contain Claude across products — anthropic.com/engineering, 2026-05-30](https://www.anthropic.com/engineering/how-we-contain-claude). Engineering postmortem on the containment story for claude.ai, Claude Code, and Cowork. Names the architectures (gVisor for claude.ai; Seatbelt on macOS + Bubblewrap on Linux for Claude Code; full VM for Cowork) and walks through three CVEs reported between mid-2025 and January 2026 where Claude Code executed project-local config **before** the user accepted the trust prompt:
- [CVE-2025-59536](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/) (CVSS 8.7) — RCE via malicious `.claude/settings.json` hook
- CVE-2026-21852 — `ANTHROPIC_BASE_URL` exfiltration
- [CVE-2026-33068](https://advisories.gitlab.com/npm/@anthropic-ai/claude-code/CVE-2026-33068/) — workspace-trust-dialog bypass via repo settings

The architectural fix: **defer parsing and execution of project-local configuration until after the user accepts the trust prompt.** Shipped in the Claude Code v2.1.x series.

### Why it's relevant
The harness's `setup-harness/SKILL.md` lines 139–146 already document the Auto-Mode + hooks composition story (hooks run before the classifier, so harness allow/deny lists are honored as hard rules). That paragraph **assumes** the user is in a trusted repo. What it doesn't name is the **clean-clone window**: when an operator clones a project for the first time (or a new collaborator clones an existing project) and runs Claude Code in it, the trust prompt is the load-bearing safety mechanism. The CVE-class shows what happens when that prompt is bypassed — and the fix is architectural (Claude Code now defers config parsing), not operator-driven.

For the harness, this is mostly **bookkeeping**: the operator can't fix Claude Code's parsing logic, but they should know:
- Always inspect a freshly-cloned `.claude/settings.json` before running Claude Code against the repo.
- The harness's `setup-harness` skill ships its own `.claude/settings.json` template with a populated `hooks` block — that template should be reviewed once at install time, and not re-trusted on every clone.
- If a target project's `.claude/settings.json` is unexpected, that's a security signal, not a "Claude Code being weird" signal.

This is **one paragraph**, possibly two. The bulk of the post is about claude.ai (gVisor) and Cowork (VM) — Claude Code is one section among three, and the harness only cares about Claude Code.

### Why this is `defer`, not `apply`

1. **Small enough to bundle.** This is a 1-paragraph edit to one file. Worth tagging onto the next substantive `setup-harness` change (e.g. when the Auto Mode + hooks section gets revisited, or when a new managed-setting like `sandbox.credentials` (v2.1.187) arrives that needs documentation).
2. **Not net-new operator advice.** Anyone who follows generic "don't run untrusted code" hygiene already does this. The novel content is the CVE-class evidence, which is reference material more than action.
3. **No skill code to change.** Pure SKILL.md prose; the harness has no enforcement hook here.
4. **The architectural fix already landed in Claude Code.** Users on v2.1.x (the harness assumes ≥ v2.1.154 per dynamic-workflows availability) are already protected against the named CVEs. The note is defensive, not corrective.
5. **The newer v2.1.187 `sandbox.credentials` setting and v2.1.169 `--safe-mode` flag are adjacent.** They give the operator more knobs for the same threat model and would be natural co-citations in the same paragraph. Waiting for one or two more containment-knob ships gives the eventual edit more useful surface area.

When the next `setup-harness` edit lands, insert after line 146:

