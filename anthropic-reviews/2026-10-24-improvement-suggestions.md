## 2. Spec a design pass on the `orchestrator` agent against the "fold subagents" rubric

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com/resources, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop). Core thesis: single-loop agents with **skills** (for ordering + domain procedure) and progressively-disclosed **tools** (for lookups + hard limits) outperform multi-subagent designs on quality, cost, and latency in most enterprise deployments. Decision rubric for keeping a subagent: (i) measurable quality loss from context bloat; (ii) parallel work with fresh/discardable context; (iii) tool-selection struggles or conflicting prompt instructions. Otherwise fold.

### Why it's relevant
The harness's `orchestrator` agent (`.claude/agents/orchestrator.md`, 400+ lines) is the canonical example of the pattern this post argues against: it reads a spec, decomposes tasks, and dispatches each to a **separate subagent session** (opus/sonnet/haiku) based on complexity. Lines 196–204:

```markdown
1. **Spawn a subagent** with the selected model. Brief it completely:
2. **For parallel tasks:** Spawn subagents with `isolation: "worktree"` …
3. **Collect the result.** Read what the subagent built.
```

The post argues that for most sequential tasks, the right answer is a **single loop + a routing skill + typed tools**, not a dispatcher-worker split. The harness's `effort_default` derivation (xhigh for stakes.level medium) and the `/run-loop` TypeScript engine already push in this direction — a single long-running session with high-effort reasoning. But the orchestrator agent explicitly fans out.

Two reasons this needs **spec**, not **apply** or **reject**:

1. **The orchestrator is the harness's most-cited design pattern** (README, several specs, the `/run-wave` and `/run-loop` skill bodies). Flipping it to single-loop is architecturally significant — it affects spec authoring (`/spec-planner` output format), the dry-run mode, the Surface A/B logging contract, and the `isolation: "worktree"` parallel pattern.

2. **The rubric is empirical, not categorical.** The post explicitly says keep subagents where "measurable quality loss from context bloat" is observable — which argues for a **spec that includes an eval step** (fold the orchestrator in one wave, run both patterns against the harness's own task set, keep whichever wins). This is exactly the shape `/spec-planner` is for.

### Concrete change (shape, not full spec)
Open a spec at `docs/specs/2026-10-24-orchestrator-fold-evaluation.md` with the shape:

- **Question:** Is the current `orchestrator` → subagent-dispatch pattern net-better than a single-loop orchestrator for this harness's task mix (small-to-medium spec waves, typically 3–8 tasks, often sequential with 1–2 parallel branches)?
- **Hypothesis:** Context bloat on the current session during a 5-task wave is small enough that the dispatcher overhead (subagent cold-start, context duplication across subagents, no shared memory) outweighs the context-isolation benefit — folding would be a net win.
- **Experiment:** Pick 2 recent closed waves. Re-run each with (a) current orchestrator (subagent dispatch), (b) single-loop variant with the same routing logic encoded as a skill (not an agent). Compare: total tokens, wall-clock, quality (per the wave's close file).
- **Decision rule:** If (b) matches or beats (a) on cost + quality, promote (b) and deprecate the agent-based orchestrator. If (a) wins, codify *when* subagent dispatch is worth it (which the post's rubric gives — rewrite `orchestrator.md` to lead with the rubric).
- **Non-goals:** Do not touch `/run-loop` (that's single-session already); do not touch `generator`, `evaluator`, `code-reviewer` (those are legitimate context-isolation subagents by the post's rubric).

### Expected payoff
Either a measurable cost reduction (if the fold wins) or a sharper statement of *when* subagent dispatch is worth its context-duplication cost (if the current pattern wins). Either outcome improves the harness's downstream advice to installed projects.

### Verify before applying
1. `grep -n 'subagent' /home/user/claude-harness/.claude/agents/orchestrator.md | wc -l` — current count should be in the dozens (confirms the pattern is still subagent-centric). If near zero, the orchestrator has already been folded and this § is stale.
2. `test -f /home/user/claude-harness/docs/specs/2026-10-24-orchestrator-fold-evaluation.md && echo exists` — should print nothing. If the spec exists, this § is done.
3. Re-read the "when to fold subagents" post before writing the spec — the rubric may have been clarified by Anthropic in a follow-up (check for an updated version at the same URL).

**Recommended verdict:** spec — architecturally significant, needs /spec-planner before any code change. The rubric gives the decision criterion but applying it requires evaluating the actual harness task mix.

## 4. Add a "cloud sessions" subsection to `skills/setup-harness/SKILL.md`

**Source:** [Claude Code in the cloud: a field guide to cloud sessions — claude.dev/blog, 2026-10-06](https://claude.dev/blog/claude-code-in-the-cloud/) (URL unverified from this environment — same `claude.dev` DNS limitation as §3; secondary coverage confirms cloud sessions GA'd on **2026-09-23**). The harness is now routinely run from cloud sessions (this very review session is one) — the environment-level system prompt documents that "the session lives in an isolated, ephemeral container; the repository was cloned fresh when the container started, and the container is reclaimed after a period of inactivity (or when the session ends), so anything worth keeping needs to be committed and pushed first."

### Why it's relevant
`skills/setup-harness/SKILL.md` is the entry point every project that installs this harness runs through. Its auto-detect table (lines 19–31) and project-type decisions have **zero mention of cloud sessions**. In a cloud session, these specific harness pieces are ephemeral and will be lost on container reclamation:

- `.harness-state/orchestrator.log` and `.harness-state/orchestrator.jsonl` — orchestrator-dispatch audit trail
- `.harness-state/today_goal.md`, `.harness-state/current_micro.md`, `.harness-state/last_exit.md` — session-boundary memory files
- `.claude/worktrees/agent-<id>/` — parallel-task worktrees from the orchestrator

For a local session these persist across invocations. For a cloud session they persist only within the session's lifetime unless committed. A user installing the harness in a cloud session and following `setup-harness` today will create these files, log work into them, and watch them vanish without warning.

### Concrete change
Add a new subsection to `skills/setup-harness/SKILL.md` immediately before the existing "Step 1: Detect or Ask Project Type":

```markdown
## Cloud sessions: what lives, what dies

If this harness is being installed from a Claude Code cloud session (the session's working directory is an ephemeral container, not your laptop), these harness-written files **do not survive container reclamation unless committed**:

| File / directory | Fate at container reclamation | Mitigation |
|---|---|---|
| `.harness-state/orchestrator.{log,jsonl}` | lost | commit at session end, or treat as session-local audit only |
| `.harness-state/{today_goal,current_micro,last_exit}.md` | lost | commit before session exit; `session-end` skill already handles this |
| `.claude/worktrees/agent-<id>/` | lost | worktrees are session-scoped by design — nothing to mitigate |
| `.harness-profile` | **persists** (committed) | no action |
| `skills/`, `.claude/agents/` | **persist** (symlinks / committed) | no action |

**Rule of thumb:** everything under `.harness-state/` is "notes for me" — committed means the next session (local or cloud) can read it; uncommitted means it vanishes with the container. The `session-end` skill in this repo already runs a commit; following it is the mitigation.
```

### Expected payoff
Prevents a specific category of surprise ("why did my `today_goal.md` disappear overnight?") for cloud-session users. The guidance is three paragraphs — no code change, no behavior change, just making the ephemeral/persistent split explicit.

1. `grep -n 'cloud session' /home/user/claude-harness/skills/setup-harness/SKILL.md` — must return nothing today; if it returns hits, the section has already been written and this § is stale.
