## 1. Bump `.harness-profile` model pins from Opus 4.7 / Sonnet 4.6 to Opus 5.5 / Sonnet 5.5

**Source:** https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context (2026-09-24)

**What Anthropic shipped.** Claude 5 family is now the "most recent" generation, with model IDs:
- `claude-opus-5-5` (Opus 5.5)
- `claude-sonnet-5-5` (Sonnet 5.5)
- `claude-fable-5-1` (Fable 5.1)
- `claude-haiku-4-5-20251001` (Haiku 4.5)

Opus 5.5 is billed as "built for coding sessions that use more context" — Anthropic quotes 20% cheaper input/output tokens, 60% cheaper cached-read tokens, ~50% fewer cache misses in Claude Code, ~30% faster output than Opus 5, and fewer turns to complete open-ended tasks. All four levers matter for a harness whose orchestrator dispatches subagents and re-hydrates spec context across long waves.

**Current state (verified 2026-09-29).**
```
$ grep -n "primary\|fallback" .harness-profile
30:  primary: claude-opus-4-7
31:  fallback: claude-sonnet-4-6
```

**Concrete change.** One-file edit to `.harness-profile`:

```diff

-  primary: claude-opus-4-7
-  fallback: claude-sonnet-4-6
+  primary: claude-opus-5-5
+  fallback: claude-sonnet-5-5
   effort_default: xhigh   # derived from stakes.level: medium
   effort_cost_multiplier: {}   # optional; keys ∈ {low, medium, high, xhigh} → numeric (reserved for /tokens)
```

The comment above the block (`# Aligned with Anthropic's 2026-04-23 postmortem (Claude Code defaults Opus-4.7 users to xhigh).`) should also be refreshed to name Opus 5.5's default, or the citation should be softened to "aligned with Anthropic's current recommended default for the pinned model."

**Payoff.** Directly addresses the harness's stated bias in `.harness-profile` (`quality_bar.level: production`, `stakes.level: medium`, `methodology.drift_sensitivity: low`) — the new model is meant for exactly this shape of long-context, low-drift, high-stakes-per-edit tooling work. Cached-read pricing improvements compound on `/run-wave`'s spec re-reads.

**Risks.** Two:
1. The maintainer's Claude Code CLI subscription and any consumer projects that install this harness must have access to `claude-opus-5-5` and `claude-sonnet-5-5`. If either model ID is not yet enabled on the maintainer's plan, the `fallback` chain in Claude Code's session config kicks in — no repo behaviour breaks, but the pinning is aspirational. Worth a quick check via `/model` or the account console before merging.
2. `setup-harness` and any doc that mentions "Opus 4.7" (e.g. session-start hooks, README snippets, comments) will drift out of sync. `grep -rn "opus-4-7\|sonnet-4-6\|Opus 4.7\|Sonnet 4.6" .` before merging is cheap.

**Verify before applying:** `grep -n "primary\|fallback" .harness-profile` — if either line already reads `claude-opus-5-5` / `claude-sonnet-5-5`, the change is done. Also `grep -rn "opus-4-7\|Opus 4.7" .` to catch any doc drift a partial bump would leave.

**Recommended verdict:** apply — single YAML edit, direct match against the post's guidance, and the pin is already 5 months stale.

## 2. Consider a plugin-bundle distribution path alongside `setup-harness` symlinks

**Sources:**
- https://claude.com/blog/build-plugins-for-claude (2026-09-25)
- https://claude.com/blog/claude-marketplace (2026-09-23)

**What Anthropic shipped.** A first-class plugin format for Claude that packages MCP connectors, Agent Skills, LSPs, commands, hooks, and subagents into a single unit hosted on GitHub. Submissions go through a directory portal; approved plugins land in the Claude Marketplace (`claude.com/marketplace`), where users install from a UI (and, for the Claude Code half, from a corresponding CLI surface — Anthropic hasn't formally documented `claude plugin install <name>` in this post, but the plugin bundle format is explicitly Claude-Code-compatible).

**How this relates to the harness today.** The harness distributes itself via the `setup-harness` skill, which creates symlinks from `~/.claude/skills/` into `skills/*` in this repo (see `CLAUDE.md`'s "Skills directory layout" section). That works fine for a solo maintainer who clones the repo once and re-uses it across every project. It does not scale to:
- Someone finding the harness organically without a GitHub URL in hand
- Version pinning per consumer project
- One-click installation without a shell + git dependency

A plugin bundle would in principle collapse the install to a single Marketplace action, but the harness's current shape (18 skills, ~6.1K of ~15.5K skills budget consumed per the 2026-05-07 audit, a `.claude/agents/` directory, a `.claude/settings.json`, plus `AGENTS.md` / `CLAUDE.md` root-level protocol files) doesn't map cleanly onto a plugin manifest without a design pass — the harness is a *methodology*, not just a skill bundle, and the AGENTS.md protocol contract lives above the skills layer.

**Concrete change.** No repo edit today. Add a docs bookmark under `docs/plan.md` (or a parking-lot row via `/park`) noting:
> If the harness ever gains external consumers, evaluate packaging as a Claude Marketplace plugin bundle. Blockers to resolve first: (a) how `AGENTS.md` + `CLAUDE.md` protocol contracts distribute under a plugin manifest, (b) whether `.harness-state/` per-project state files are compatible with plugin sandboxing, (c) whether the `run-loop` / `planning-loop` skills' worktree conventions survive a plugin install path. Source: https://claude.com/blog/build-plugins-for-claude (2026-09-25).

**Payoff.** Keeps a durable pointer to the distribution option so a future maintainer (or future-you) doesn't rediscover the plugin format from scratch. Zero code cost today.

**Risks.** None if left as a bookmark. If the harness ever *does* pursue plugin packaging without a spec, the risk is losing the tool-neutral `AGENTS.md` contract by baking it into a Claude-Code-specific plugin surface — which the plugin format is by design.

**Scope: speculative** — a solo-maintained methodology repo with one user has no distribution problem to solve.

**Verify before applying:** `grep -rln "plugin\|marketplace" AGENTS.md skills/setup-harness/ README.md docs/plan.md` — if a parking-lot row or plan bullet about "plugin distribution" already exists, drop this suggestion.

**Recommended verdict:** defer until multi-repo consumers ask for it — the setup-harness path works and the plugin format is not going away.

## 3. Security-review pass on `setup-harness` symlink installer against the May 25 containment principles

**Source:** https://www.anthropic.com/engineering/how-we-contain-claude (2026-05-25)

**What Anthropic shipped.** An engineering write-up on how the Claude Code team contains agent side-effects across products. Three principles from the piece that map directly onto anything that reads or executes project-local configuration:

1. **Deferred trust.** "Defer parsing and execution of project-local configuration until after the user accepts the trust prompt." Config files (skills, hooks, settings.json) are untrusted input until the user has consented to the trust level.
2. **Symlink-resolution-before-path-check.** "Symlink resolution has to happen *before* path validation, not after, or a symlink inside an authorized folder can point outside and escape."
3. **Capability-based allowlists over destination filters.** "Every function reachable through any domain on an allowlist is now an attack surface."

**How this relates to the harness today.** `setup-harness` (the skill at `skills/setup-harness/SKILL.md`) creates symlinks from `~/.claude/skills/` into the cloned repo. That flow implicitly:
- Trusts `skills/*/SKILL.md` bodies at install time (skill YAML frontmatter and body copy execute inside the user's Claude Code sessions once linked).
- Resolves symlinks as part of the install, but does not (as of last audit) explicitly validate that the resolved target lies inside the expected working tree — a malicious fork could ship a `skills/<name>` entry that is itself a symlink pointing outside the repo, and the install would happily hand that path to `~/.claude/skills/<name>`.
- Grants the target machine's Claude Code session capability-parity with whatever the linked skill declares — no per-skill allowlist scoping (the harness's own `.claude/settings.json` grants a broad set of read/write/exec permissions).

None of these are known-exploited today. But this repo is *distributed methodology*: any consumer cloning from an unexpected fork inherits the trust the install flow assumes.

**Concrete change.** Spec (via `/spec-planner`) a `harness-install-containment` design pass that answers:
- Does `setup-harness` resolve symlinks and re-check the resolved path is inside `${HARNESS_ROOT}` before creating each `~/.claude/skills/<name>` link? If not, add the check.
- Does the install prompt the operator for consent per-skill (or at least surface a summary of hooks and settings.json permissions being installed) before performing the symlink dance? If not, spec what the consent surface should look like.
- Is there a "verify" subcommand (`setup-harness --verify`) that re-runs the containment checks against an already-installed harness so the operator can re-check after a `git pull` in the harness repo?

The output of the spec is a `docs/specs/YYYY-MM-DD-harness-install-containment.md` file; the actual code changes go through the normal wave flow.

**Payoff.** Turns implicit trust into explicit trust before the harness gains multi-user distribution (which the plugin path in §2 would accelerate). Cheap insurance now, painful to add later once consumer projects have shipped.

**Risks of the spec pass itself:** zero (spec-only).
**Risks of the eventual implementation:** the consent prompts might slow first-run install for the sole current user (the maintainer). Mitigation: the consent flow only surfaces new / changed skills on re-install; the initial trust prompt is one-time.

**Verify before applying:** `grep -rn "realpath\|readlink\|symlink" skills/setup-harness/` — if the install already resolves symlinks and validates them against `${HARNESS_ROOT}`, the spec pass is smaller (drop containment invariant 2 from the design). Also `git log --oneline --all --grep="containment\|symlink.*validat"` to catch prior work.

**Recommended verdict:** spec — the pass is worth doing before external consumers appear, and the design surface (consent UX, per-skill scoping, verify subcommand) has enough decisions to justify `/spec-planner` rather than a naked `/micro`.
**Status:** PENDING — awaiting triage in PR review

## 4. Adopt Anthropic's "instrument-first, keep-state-external" pattern for the harness's own smoke tests

**Source:** https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic (2026-09-14)

**What Anthropic shipped.** An engineering piece on rebuilding Anthropic's internal test-impact-analysis (TIA) service after a **25× increase in CI jobs over six months** driven by agent-authored code. Key patterns cited:
- **Instrument early** so the agent can "hill-climb and fix problems" without a human in the loop.
- **Keep state external.** Stateless workers + durable journals scale horizontally; singleton in-memory processes do not.
- **Plan for 25× growth.** Assume 10-20× perceived scale in v0 designs within two quarters in AI-accelerated environments.
- **Rebuild from journal + selector.** Listener appends to a journal; a separate consumer rolls entries into per-test history every few seconds; selector picks which tests to run based on package relevance and historical flakiness.

**How this relates to the harness today.** The harness sits at the opposite end of the CI-scale spectrum:

```
$ grep -n "test_required\|typecheck\|lint" .harness-profile
14:  typecheck_blocking: false   # no TS code
15:  lint_blocking: false        # no lint config
16:  test_required: false        # no runnable tests yet
```

There is no CI, no test runner, no listener, no journal. The `run-loop` engine has a small `node:test` fixture suite (`skills/_shared/loop/*.test.ts`), but it runs on the maintainer's laptop, not in CI. The 25× problem Anthropic solved does not exist here.

The transferable pieces, if the harness ever grows a test surface:
- The `.harness-state/` directory is already the harness's "journal + durable store" — matches the pattern in shape.
- The `run-loop` engine's structured logs (`.harness-state/orchestrator.jsonl`) already look like a TIA listener would want them to.
- The `close-wave` gate could plausibly become a TIA-driven "which acceptance criteria to re-run" selector once the harness has automated acceptance checks.

**Concrete change.** No repo edit today. If the harness ever flips `test_required: false` → `true`, revisit this post as a design constraint on the test runner's architecture (favour stateless workers, JSONL journal, external state, avoid singleton in-memory processes).

**Payoff.** Bookkeeping. Keeps a pointer to a durable engineering piece so a future test-runner design pass doesn't rediscover the pattern.

**Scope: speculative** — the pattern is aimed at teams shipping 8× more code per quarter than pre-agent baselines. The harness ships methodology, not code, and the acceptance surface is prose-driven (spec files, code-review verdicts) rather than runnable-test-driven.

**Verify before applying:** `grep -n "test_required" .harness-profile` — if the value is still `false`, this remains bookkeeping; if it has flipped to `true`, revisit the post and consider a proper TIA-shaped design pass.

**Recommended verdict:** defer until CI or a runnable test surface exists — no acute pain, no immediate change to make.
**Status:** PENDING — awaiting triage in PR review
