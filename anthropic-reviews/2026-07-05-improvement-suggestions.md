## 2. Adopt Claude Code's three-slot `fallbackModel` chain in `.harness-profile`

**Source:** [Claude Code What's New — Week 24 (June 8–12, v2.1.166–v2.1.176)](https://code.claude.com/docs/en/whats-new#week-24-june-8-12-2026) — "`fallbackModel` configures up to three fallback models tried in order." (Related product motivation on the config-guide reporting side: the ["Ultimate Claude Code Config for 2026" summary](https://levelup.gitconnected.com/claude-code-config-2026-ultimate-setup-guide-e29c673d075e) — third-party but references the docs directly.)

### Why it's relevant
`.harness-profile`'s model block is:

```yaml
model:
  primary: claude-opus-4-7
  fallback: claude-sonnet-4-6      # scalar
  effort_default: xhigh
```

Claude Code product-side now accepts a **list** of up to three fallback models, tried in order. The harness's single-string `fallback:` field is a strict subset of the new shape. The mismatch is invisible today (Claude Code doesn't read `.harness-profile` — the harness code does), but the harness's own tooling could benefit from expressing a chain:

- **Primary:** the expensive model you actually want (Opus 4.8 after §1).
- **Fallback 1:** the same-family sibling for rate-limit or capacity overflow (Opus 4.7 or 4.6, both still supported).
- **Fallback 2:** a smaller-tier model for the "just get it done" degraded path (Sonnet 4.6, or Haiku 4.5 for cheap sub-tasks).

The `run-loop` review backend already juggles `anthropic-api:opus-4.8 | codex | openrouter:<model>` at the CLI seam (`docs/specs/2026-06-16-run-loop-portable-gate.md:51`); a chained fallback field would let the profile document a preference order that the loop currently threads through CLI flags. Same for the orchestrator's model routing (`skills/_shared/loop/dispatch/*`).

### Why it's `spec`, not `apply`
Non-trivial questions the routine can't answer alone:
1. Backwards compat — should the schema accept a scalar `fallback:` AND a list `fallback: [...]`? Or is this a one-shot bump with a migration note in the CHANGELOG?
2. Ordering semantics — is the list "try in order until one works", or "primary/secondary/tertiary explicitly named"? Claude Code's shape is the former.
3. Downstream reader updates — every callsite that reads `.harness_profile.model.fallback` (grep candidates: `skills/_shared/loop/dispatch/backends.ts`, `skills/_shared/loop/dispatch/review.ts`, `.claude/agents/orchestrator.md` model routing) needs a small edit to handle a list.
4. Does the `/project-init` template propagate the change or hold-back?

That's a schema change touching 4+ files with a compat question — the "one bullet, one-paragraph /micro?" test fails. It's a `/spec-planner` candidate.

### Concrete direction (for the spec)
- Schema: `model.fallback: string | string[]`, list preferred, scalar accepted as a one-element list for compat.
- Cap at 3 (matches Claude Code product side).
- Reader helper `.harness-profile.getFallbackChain(): readonly string[]` centralized so callsites don't reimplement the scalar/list branch.
- Migration: no automatic rewrite; document the new shape in the profile-version bump.

### Verify before applying
- `grep -n "^  fallback:" /home/user/claude-harness/.harness-profile` — if the value is a YAML list (`fallback: [...]` or block sequence), the change already landed. Today it's `fallback: claude-sonnet-4-6` (scalar).
- Check for a spec file: `ls /home/user/claude-harness/docs/specs/ | grep -i fallback` — if a spec already exists, this § should point at it instead of asking for a new one.

**Recommended verdict:** spec — schema shape + compat rules + downstream reader updates cross the "single /micro" line; hand to `/spec-planner`.
**Status:** PENDING — awaiting triage in PR review

## 3. Dispatch to Dynamic Workflows / `ultracode` from one existing bug-hunt or audit skill

**Source:** [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) · [Orchestrate subagents at scale with dynamic workflows — code.claude.com/docs](https://code.claude.com/docs/en/workflows) · [Claude Code What's New — Week 22](https://code.claude.com/docs/en/whats-new#week-22-may-25-29-2026) — "dynamic workflows orchestrate dozens to hundreds of subagents from a script Claude writes".

### Why it's relevant
Dynamic Workflows are the productized "orchestrator writes a JS script + runs 1,000 subagents in the background + adversarially verifies each finding" pattern. The harness has three skills that already fan out across many items:

- **`/apply-anthropic-reviews`** — decomposes a dated suggestions file into bullets, classifies each, batches trivial ones through `/micro`. Serial today. A workflow could fan out per bullet with adversarial verify per suggestion before batching.
- **`/code-review`** (Anthropic-bundled, integrated by the run-loop at `skills/_shared/loop/protocol/review.ts:3`) — the run-loop already runs it per item; a workflow shape would give per-finding verification instead of a single-agent finding list.
- **`/security-review`** — same shape as `/code-review`. Multi-dimensional (correctness, security, perf, repro) is exactly the "diverse-lens judge panel" pattern the docs highlight.
- **The Anthropic-review routine itself (this routine)** — the 15-post cap and the "check the repo before suggesting" gate are today executed serially by one agent. A workflow could parallelize per-post analysis with a completeness critic at the end.

The Workflow tool is present in this session's system prompt (see the tool list at the top of this transcript); the harness has **zero** invocations of it — `grep -rn "ultracode\|dynamic workflow\|Workflow tool" .` returns hits only in the README (Wave 8-era "workflow tools" language) and the harness-evolution spec.

### Why it's `spec`, not `apply`
Which skill gets it first, when to trigger (fixed keyword? size threshold? explicit maintainer opt-in?), and how the workflow return value composes with the existing skill body are all design decisions. The docs are explicit about caps (16 concurrent, 1,000 total, ~$0.10–$1 per bug-hunt agent), and each skill has different rate-limit and token-budget tradeoffs. This is a `/spec-planner` question.

### Concrete direction (for the spec)
- Pick ONE skill for the pilot — probably `/apply-anthropic-reviews` because (a) it already fans out over a list of items, (b) it's an internal-facing skill so the failure mode is a bad decomposition, not a bad merge, (c) the "adversarial verify" step maps 1:1 onto the existing "Verify before applying" line in each §.
- Trigger shape: an `--ultracode` flag on the skill invocation. Not the session-wide `/effort ultracode` — that's too aggressive for a solo harness.
- Return value: the workflow returns the same shape the current skill's serial pass would (a list of classified bullets); only the compute path changes.
- Cap on size: if the input has < 3 bullets, run serial. If ≥ 3, opt into the workflow.

### Verify before applying
- `grep -rn "ultracode\|dynamic workflow\|Workflow tool" /home/user/claude-harness/skills /home/user/claude-harness/README.md` — should return **nothing** (except in this dated file). If it returns hits in a skill body or a wave doc past 2026-06-19 (the last commit as of this run), someone has started this work and the § needs to be re-aimed at the gap.
- `git -C /home/user/claude-harness log --oneline --since=2026-06-19 --grep 'workflow\|ultracode' -i` — if this returns commits, the § is stale.

**Recommended verdict:** spec — pilot-skill selection, trigger shape, and workflow-vs-serial threshold all need a design pass before any code.

## 5. Tighten `.claude/settings.json` with `Tool(param:value)` deny/ask rules

**Source:** [Claude Code What's New — Week 25 (June 15–19, v2.1.178–v2.1.183)](https://code.claude.com/docs/en/whats-new#week-25-june-15-19-2026) — "deny and ask rules match tool parameters with `Tool(param:value)`, for example `Agent(model:opus)`".

### Why it's relevant
Current `.claude/settings.json`:

```json
{
  "hooks": {
  }
}
```

Empty. No permissions block. The harness's operator-side denylist is documented in `skills/_shared/loop/safety/denylist.ts` (matcher logic) and installed globally in `~/.claude/settings.json` per CLAUDE.md L36. Project-scope rules are absent.

Week 25 shipped a parameter-scoped permission syntax that makes narrow rules cheap. Two low-risk starter entries fit today:

- **`Agent(model:opus)`** — ask before spawning an Opus subagent. The harness's orchestrator (`orchestrator.md:4`) already dispatches to opus/sonnet/haiku by task complexity; this rule lets the operator confirm expensive fan-out in interactive sessions (does not affect headless `-p` runs).
- **`Bash(command:rm -rf *)`** — hard deny at the tool-parameter layer, complementary to the shell-level denylist in `denylist.ts`. This is the exact "backstop layer, not the confinement boundary" posture the denylist header advocates: layered.

### Concrete changes
Replace the empty `.claude/settings.json` with:

```json
{
  "hooks": {},
  "permissions": {
    "ask": [
      "Agent(model:opus)"
    ],
    "deny": [
      "Bash(command:rm -rf *)",
      "Bash(command:git push --force*)",
      "Bash(command:git reset --hard*)"
    ]
  }
}
```

Rationale for each entry:
- `Agent(model:opus)` in `ask` — surfaces expensive subagent fan-out without blocking it. Solo-maintainer regime: the operator sees "about to spawn Opus subagent for X" and can decline.
- `Bash(command:rm -rf *)` in `deny` — hard block a common shell footgun at the tool layer.
- `Bash(command:git push --force*)` and `git reset --hard*` in `deny` — mirrors the CLAUDE-Code system prompt's "Never run destructive git commands" instruction at the enforcement layer.

The three deny rules overlap with (a) the operator's global denylist hook and (b) Auto Mode's built-in destructive-git block (§6). Overlap is intentional — layered defense.

### Expected payoff
- Auto Mode + Tool(param:value) rules + hook denylist = three-layer defense against destructive commands. Today the harness relies on layers 2 and 3; layer 1 is a two-line diff.
- Rules live at project scope, so any consumer project that installs the harness inherits them via `.claude/settings.json`.

### Verify before applying
- `cat /home/user/claude-harness/.claude/settings.json` — if the file already has a `permissions` block, the § is stale.
- `grep -n "Agent(model:\|Tool(param:" /home/user/claude-harness/.claude/settings.json` — should return nothing today.
- Confirm the `Tool(param:value)` syntax is still current: `grep -A2 "Tool(param:value)" /home/user/claude-harness/anthropic-reviews/2026-07-05-improvement-suggestions.md` — this § anchors the syntax; if Anthropic renames it, the § needs a follow-up.

**Recommended verdict:** apply — five-line settings.json diff, layered defense with no runtime cost.
