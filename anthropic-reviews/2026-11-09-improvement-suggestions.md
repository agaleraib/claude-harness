## 2. Re-score subagents against the "fold subagents" protocol before adding a seventh

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com/resources, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop). Also cross-references: [Steering Claude Code — Jun 18](https://claude.com/resources/articles/steering-claude-code-skills-hooks-rules-subagents-and-more) (seven steering surfaces, when to pick which).

### Why it's relevant

The harness ships **six subagents** under `.claude/agents/`:

| Subagent | Role | Article's checklist position |
|---|---|---|
| `code-reviewer.md` | Adversarial PR-time review against `criteria/` | Fresh-context black-box verification — **keep as subagent** per article's guidance |
| `generator.md` | Spec-driven implementation loop | Main loop itself — fold candidate? |
| `orchestrator.md` | Task→model routing across sonnet/opus/haiku | "The model that plans should also carry out the plan" — fold candidate? |
| `project-tracker.md` | Save session to Second Brain at `session-end` | Independent black-box write — **keep** |
| `spec-planner.md` | Spec drafting via discovery questions | Conversational loop; may not need isolation — fold candidate? |
| `ui-evaluator.md` | Playwright-driven UI scoring against `criteria/` | Black-box verification with heavy tool output — **keep** |

Anthropic's article says explicitly: *"When subagents mirror the org chart, with one per team or problem type. This creates overlapping agents, conflicting prompt rules, and fragmented evals."* and *"Specialists that chain on each other's output, touch the same data, or are usually called together [are] candidates to merge."* The harness's `spec-planner → generator → code-reviewer → orchestrator` chain hits both anti-patterns: each produces input the next consumes; several are usually called together via `/run-wave`.

The article's prescribed method for deciding is:

1. Build a small end-to-end eval first (~10 golden examples).
2. Fold one subagent back at a time; compare evals with vs. without.
3. Look at per-task results, not just the overall score.

**This depends on the still-deferred `2026-04-19 §5` (formalize evals for the adversarial reviewers)** — without a baseline eval, the fold-vs-keep decision would be vibes-driven. So this § is not standalone; it should become the first consumer of the eval fixtures when they land.

### Concrete change

**None this run.** This § is a design request, not a code edit.

When the eval harness ships:

1. Freeze ~10 golden tasks spanning wave-sized changes (commit-sized features + a cross-file refactor + a bug-fix-with-spec).
2. For each of `generator`, `orchestrator`, `spec-planner` (the three the article's rubric flags as fold candidates), run the eval twice: with the subagent in place, and with its prompt inlined into the main loop. Hold criteria constant.
3. Decide per-subagent on per-task comparison, not aggregate score.

### Expected payoff (when applied)

Either: (a) confirmation that the current six-subagent architecture is right-sized for the eval set, which is useful evidence to cite in the README's "Why this split" paragraph; or (b) at least one subagent moves back into the main loop, reducing both maintenance surface and per-run token cost. Both outcomes are information gains.

### Why `spec`, not `apply` or `defer`

The article prescribes a measurement protocol, not a diff. A § that says "fold `orchestrator` into the main loop" without eval evidence would violate the article's own method. A § that says "do the measurement" needs a spec: how is the eval harness composed, how are the golden tasks picked, how are prompts inlined. Either `/spec-planner` writes that spec, or the maintainer answers those questions in a PR thread first.

### Verify before applying

1. `grep -n "DEFERRED" anthropic-reviews/2026-04-19-improvement-suggestions.md` should still show §5 (agent evals) deferred. If §5 has been promoted, this § is unblocked.
2. `ls .claude/agents/` should still list six `.md` files (code-reviewer, generator, orchestrator, project-tracker, spec-planner, ui-evaluator). If the count has changed, revise the per-agent classification above.
3. Confirm the article's methodology hasn't been superseded by a follow-up post on the same topic (search `claude.com/resources/articles` for "subagent" after 2026-10-22).

**Recommended verdict:** spec — depends on the deferred eval fixtures (2026-04-19 §5); multi-file architectural review; the measurement protocol itself needs a spec before any subagent is folded.

## 3. Add a "store what can't be re-derived" guardrail to `session-end` Step 7

**Source:** [The components of agent memory — anthropic.com/research, 2026-11-06](https://www.anthropic.com/research/components-of-agent-memory). Anthropic's four-layer memory model: searchable transcript log → model-written notes → curated wikis → injected context (the "top layer" that loads every session). Dreaming moves information down the hierarchy.

### Why it's relevant

The article names a specific guardrail in prose: *"Store what can't be re-derived. Strategies, verified rules, and plans are worth saving. State readable from the screen each turn is redundant."* It also gives Claude Code's memory loader as the canonical cap-sized index example: *"Claude Code's auto memory loads only the first 200 lines or 25 KB of `MEMORY.md`, which serves as an index."*

The harness's own session-end ritual writes **`last_exit.md`** at `skills/session-end/SKILL.md:98–115` with this template:

```markdown
# Exit note — [YYYY-MM-DD]

**Today's goal:** [goal]
**Outcome:** [hit | partial | drifted | blocked]
**Where I ended:** [1-sentence state]

**Parking lot triaged:** [yes/no]
**Tomorrow's first move:** [sentence]

## Commits this session
[short commit list]
```

Three of six fields are irreducible (outcome, where-I-ended, tomorrow's-first-move). Two are near-redundant with git state (**"Commits this session"** replicates `git log --since=<start>`; **"Parking lot triaged: yes/no"** is a single bit that `session-start` could rederive from `parking_lot.md`'s mtime). The template is not egregiously bloated, but the irreducibility principle is not stated in the skill body — a future edit might grow it in exactly the direction the article warns against.

Adding one bullet to `session-end` Step 10 ("Keep in mind") codifies the heuristic so the next revision stays lean. This is a tiny, low-risk change that leaves the current template intact.

### Concrete change

**File 1: `skills/session-end/SKILL.md`** — append one bullet to the "Keep in mind" list at line ~160:

```diff
 5. **Always write last_exit.md.** Even for bad sessions.
+6. **Store what can't be re-derived.** `last_exit.md` is a predicate for next session's context load, not a log. Outcome, state-of-mind, and the one-sentence pointer at tomorrow are irreducible. Commit lists, test counts, and anything `git log` or `.harness-state/` can regenerate on demand should stay thin or move out. Source: [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory) — "state readable from the screen each turn is redundant."
```

## 5. Audit the global `PreToolUse` denylist against the three-layer defense model

**Source:** [How we contain Claude across products — anthropic.com/research, 2026-05-25](https://www.anthropic.com/research/how-we-contain-claude). Three principles: (a) 93% of Claude Code permission prompts are approved — approval fatigue weakens them; (b) defend three layers (environment, model, external content); (c) *"capable models find paths around restrictions nobody wrote down. Pattern-matching bash commands is easy to route around."*

### Why it's relevant

The harness's catastrophic-command safety is a **pattern-based `PreToolUse` hook** installed from `skills/_shared/loop/safety/denylist.ts` into the operator's global `~/.claude/settings.json` (see `CLAUDE.md:30-34` for the Claude-Code wiring). The hook is a probabilistic layer — exactly what the article says is insufficient on its own:

- The hook matches bash command strings; it can be routed around by `base64 -d`, `eval "$(printf …)"`, or writing then executing a shell file.
- The hook doesn't resolve symlinks before path matching (article: *"Resolve symlinks before path validation."*).
- The harness doesn't currently constrain credentials-outside-sandbox (article: *"If secrets never enter the agent's environment, they can't be exfiltrated."*).
- Project-local `.claude/settings.json` in untrusted repos is loaded on open (article flags this as a real vulnerability: *"Defer project-local config until trust is established."*).

**However**, the harness is a solo-maintained tooling repo whose usage model is: the operator reviews each session and clones trusted repositories. The article's heaviest recommendations (OS-level sandbox, proxy-level authN, credential vault outside the container) make sense for Claude Code *as a product* shipped to non-expert users — **not** for a methodology repo that the maintainer runs on their own box with full `claude --dangerously-skip-permissions` trust.

So the question isn't "patch the denylist" (there's no imminent breach) — it's "when does the harness grow a trust boundary, and what does the denylist look like when it does?" Answer today: not yet.

### Concrete change

**None this run.** This § is a design parking-lot item.

When the harness grows a consumer-project trust boundary (e.g. `setup-harness` starts installing on machines the maintainer doesn't operate, or a new skill shells out to untrusted data), the audit should produce:

1. A spec that states which of the article's three layers the harness defends, and which it delegates (to Claude Code, to OS sandboxing, to the operator).
2. A concrete list of `denylist.ts` upgrades: symlink resolution, canonical-path matching, provenance-based network allowlist.
3. A trust-prompt convention for project-local `.claude/settings.json` (today the harness assumes repos are trusted on clone).

### Why `defer`, not `apply`

1. The current pattern-match denylist catches the real failure modes in a solo-operator workflow (accidental `rm -rf`, mass-delete, etc.) — those are the regressions the article's own 93%-approval-fatigue data would most want to catch.
2. Full sandboxing requires a container runtime, a process boundary, and a credential proxy — architectural changes that only pay off against untrusted inputs the harness doesn't currently receive.
3. The article explicitly notes custom security code is a failure mode (*"the team's custom proxy caused the most serious failure"*) — adding half-sandboxing would increase attack surface, not reduce it.

### Verify before applying

1. `grep -rn "denylist.ts\|PreToolUse" skills/_shared/loop/safety/ CLAUDE.md AGENTS.md` — confirm the denylist is still the sole safety layer; if a sandbox or proxy has been added, this §'s scope changes.
2. Check whether any consumer project has reported a bypass (`ls parking_lot.md` — a bypass report would be in the parking lot). If yes, promote this §.
3. Confirm the article's recommendations haven't been issued as concrete Claude Code CLI primitives (e.g., `--sandbox-mode strict`) that the harness could just adopt.

**Recommended verdict:** defer until sandboxing becomes a design priority — the harness's trust model is solo-operator today; the article's heaviest recommendations assume a different product surface; worth revisiting if `setup-harness` or a new skill crosses a trust boundary.
**Status:** PENDING — awaiting triage in PR review
