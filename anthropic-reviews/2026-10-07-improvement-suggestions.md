## 5. Scope note on Claude Code mods as an alternate delivery vector — scope: speculative

**Source:** [Customize Claude Code with mods — claude.com/blog, 2026-10-01](https://claude.com/blog/claude-code-mods). Mods are small event-driven TypeScript / JavaScript functions that hook into Claude Code internal events (tool-call, permission request, UI draw). They can wrap/replace/precede/follow an event, rewrite prompts, swap in UI panes, or add new features. Mods ship inside plugins (`/plugin install <mod>@<org>`); no Node/bundler/build step required (Claude Code loads `.js`/`.ts` directly). Built-in examples: `diff` (opens a `/diff` panel), `agents-md` (loads project AGENTS.md as permanent instructions), `sec-default` (keeps org settings separate from user mods), `telemetry` (usage records to analytics).

### Why it's relevant
Two things to note, both scope-aware:

1. **The mechanics are already covered.** The user-level `plugin-authoring` skill (listed in this session's available-skills roster) already handles mod-authoring instructions — *"Make a mod: a live pane, band, status line, toast or hook inside Claude Code … written as a plugin of function hooks that hot-reloads in this session"*. The harness doesn't need to re-document the authoring surface; Anthropic's upstream skill does that.
2. **The distribution question is open.** This harness currently ships via `setup-harness` + symlinks into `~/.claude/skills/`. Mods ship via plugin registry install (`/plugin install name@org`). Both can coexist, but if the harness ever wanted to be installable as a plugin (one-command install for consumer projects, no `~/.claude/harness/` clone step), the mods API is the natural wrapper. The hook events (PreToolUse / PostToolUse / UserPromptSubmit / SessionStart — already called out in `.claude/settings.json` and the harness's SessionStart hook mentions in `CLAUDE.md:30`) are the harness's existing extension points re-exposed as a first-party plugin surface.

Shipping as a plugin would be an architectural move with real downsides (version pinning across target projects, plugin-registry gatekeeping, loss of the "clone-and-edit" workflow for maintainer debugging). It would also change how `setup-harness` works end-to-end — likely a Wave-sized refactor.

**Scope: speculative.** The current symlink delivery works, is debuggable (operator sees every file on disk), and shipping as a plugin solves a problem the solo repo doesn't yet have.

None in-tree today. If the maintainer wants to seriously evaluate, the path is:
