## 4. OpenTelemetry trace export via Claude SDK / Managed Agents — park, don't adopt

**Source:** [Agent observability on the Claude Platform — claude.com/resources/articles, 2026-10-14](https://claude.com/resources/articles/agent-observability-on-the-claude-platform). Managed Agents, the Messages API, and the Claude SDKs now emit **OpenTelemetry traces following the GenAI semantic conventions**, in public beta. Each agent turn, model call, and tool use is a standard span with latency, token counts, and correlation IDs; traces flow to any OTLP-compatible backend (Grafana / Honeycomb / Sentry / Langfuse). Managed Agents + Messages API need a destination configured in Claude Console; SDKs export automatically. Reference docs: `platform.claude.com/docs/en/manage-claude/opentelemetry`.

### Why it's relevant
The harness today keeps per-decision state in **ad-hoc JSONL at `.harness-state/orchestrator.jsonl`** (`.claude/agents/orchestrator.md:320–340` schema) and in a human-readable `.log` sibling. The schema has `ts`, `session_id`, `task_id`, `model`, `effort`, `status`, `retried_from`, `usage` fields — functionally similar to a GenAI span, but in a bespoke format.

OTel-compliance would:
1. Make orchestrator logs ingestible by any observability backend without a custom shim
2. Give the harness a standard way to correlate turn / tool / model-call spans end-to-end
3. Convert production traces into eval cases automatically (one of the post's explicit patterns)

But: this is a **solo, local-only harness today**. The maintainer runs the orchestrator in a Claude Code session and reads the JSONL by eye or by grep. Standing up an OTLP collector, a backend, and dashboards is pure overhead at `team.size: solo` (per `.harness-profile:63`). The right posture is to **park the pattern** — the OTel GenAI conventions are a sensible target *when* observability becomes a felt need (a second maintainer, a cost-auditing push, or a shift to Managed Agents hosting).
