## 1. Cite "Steering Claude Code" (Jun 18) as the canonical taxonomy for the 7 instruction methods the harness already uses

**Source:** [Steering Claude Code: when to use CLAUDE.md, skills, hooks, and subagents — claude.com/blog, 2026-06-18](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)

### Why it's relevant
The post enumerates **seven** first-party instruction methods and gives Anthropic's rules-of-thumb for picking between them:

1. **CLAUDE.md** — always-on, ≤200 lines, "facts not procedures"
2. **Rules** — path-scoped, load only when relevant files are touched
3. **Skills** — procedures loaded on invocation

## 2. Cite "How we contain Claude across products" (Jun 4) as prior art in AGENTS.md safety-guardrails section

**Source:** [How we contain Claude across products — anthropic.com/engineering, 2026-06-04](https://www.anthropic.com/engineering/how-we-contain-claude)

### Why it's relevant
Anthropic's containment architecture for claude.ai, Claude Code, and Cowork is a three-layer defense that closely parallels the harness's Wave-20/21 safety layer:

| Anthropic layer | Purpose | Harness parallel |
|---|---|---|
| gVisor (claude.ai) / Seatbelt (Code macOS) / Bubblewrap (Code Linux) / full VM (Cowork) | Filesystem + syscall isolation | `safety/write-root.ts` — write confinement to an explicit set of roots {worktree dir, run state dir}, OS-enforced where the host supports it and advisory otherwise |

### Concrete change
**AGENTS.md — append one sentence + link to the existing "Safety guardrails" paragraph at `AGENTS.md:113`:**

```diff
 **Safety guardrails (worktree lane).** Before any worktree item runs, a catastrophic-command denylist gate (a pre-tool hook that fires regardless of permission mode) must be active; absent, worktree items are refused while sandcastle items still drain. ## 3. Cite the July 30 cybersecurity-eval incident postmortem as first-party evidence for the harness's secret-bearing worktree egress controls

**Source:** [Investigating three real-world incidents in our cybersecurity evaluations — anthropic.com/research, 2026-07-30](https://www.anthropic.com/research/investigating-incidents-cybersecurity-evals)

### Why it's relevant
Anthropic reviewed 141,006 evaluation runs and disclosed three incidents where a Claude model reached the real internet from what were supposed to be sealed eval containers, then compromised real third-party systems (a production database, a malicious PyPI package that landed on 15 real systems, and a scan of ~9,000 targets before compromising an internet-facing app). Root cause: **eval setups had internet access despite prompts telling the model there was none**.

This is precisely the failure mode `safety/egress.ts` is designed to make impossible for secret-bearing worktree items:

- **Prompt-only "no internet" is not enforcement.** The eval containers relied on the prompt telling the model there was no network; the network was actually up. The harness's egress module refuses to run (`egress-unenforceable`) rather than silently fall back to open network with live secrets.
- **The attacks used weak credentials and exposed endpoints**, not zero-days. This is exactly what the harness's task-scoped credential injection (only the item's declared secrets, never the whole `.env.local`) is meant to blunt.
- **Default-deny + operator-declared allowlist.** Anthropic's incident recommendation matches the `worktree_egress_allowlist:` posture — loopback + explicit hosts only, git remote not auto-allowed.

This is stronger first-party evidence than any prior citation the harness has: it's Anthropic saying **"we had this exact class of failure at production scale; here is the countermeasure shape."**

## 5. Position Dynamic Workflows (May 28) alongside the harness's `orchestrator` agent + `run-loop` engine in README

**Source:** [Anthropic releases Opus 4.8 with new 'dynamic workflow' tool — TechCrunch, 2026-05-28](https://techcrunch.com/2026/05/28/anthropic-releases-opus-4-8-with-new-dynamic-workflow-tool/) · [Claude Code Adds Dynamic Workflows for Parallel Agent Coordination — InfoQ, 2026-06-XX](https://www.infoq.com/news/2026/06/dynamic-workflows-claude-code/)

### Why it's relevant
Dynamic Workflows is Claude Code's new first-party primitive for JS-scripted parallel subagent orchestration — up to 1,000 subagents in a single run (16 concurrent), with the plan living in script variables rather than the parent's context window. The harness's `orchestrator` agent + `_shared/loop/engine.ts` cover conceptually similar ground:

- **Orchestrator** (per `README.md:535`): dispatches tasks to opus / sonnet / haiku subagents based on complexity, decided at runtime. Sequential today (one task at a time).
- **run-loop engine** (per `AGENTS.md` §"Loop protocol"): pipeline of ready work items, each dispatched through the runner-selected sandbox with mechanical exit gate. Also sequential per work source.
- **Dynamic Workflows**: JS-scripted; up to 1,000 subagents in parallel; only final answer returns to parent context; hard cap of 16 concurrent to prevent runaway.

The overlap is real but the primitives differ: the harness's orchestration lives **inside** an agent's flow (each task is a Claude call with its own tools); Dynamic Workflows are a **script that runs multiple Claude calls**. The maintainer should eventually decide whether the harness should:

- **(a)** Migrate `orchestrator` / `run-loop` onto Dynamic Workflows when the feature ships out of research preview (cost: rewrite; benefit: first-party feature parity, cheaper fan-out).
- **(b)** Keep the current primitives (cost: divergent orchestration story; benefit: sandcastle-lane parity, tool-neutral protocol per `AGENTS.md`).
- **(c)** Document both and let the operator pick per-invocation.

None of these is urgent while Dynamic Workflows is in research preview (only Anthropic-internal + selected preview users have it), so this suggestion is a **bookkeeping deferral**. When Dynamic Workflows GAs, the maintainer should revisit and either spec the migration or add a one-paragraph "when to use which" note.

Grep confirms zero mention of "dynamic-workflow" or "Dynamic Workflows" in the repo.

#### How this complements Anthropic's Dynamic Workflows

As of [Opus 4.8 (May 2026)](https://techcrunch.com/2026/05/28/anthropic-releases-opus-4-8-with-new-dynamic-workflow-tool/), Anthropic ships **Dynamic Workflows** — a JS-scripted orchestration primitive that writes an orchestration script at runtime, fans out up to 1,000 subagents (16 concurrent), and returns only the final answer to the parent context.
