## 1. Cite "When to fold subagents into your main agent loop" in README `orchestrator` + add anti-pattern bullets to AGENTS.md

**Source:** [Building agents: When to fold subagents into your main agent loop — claude.com/resources/articles, 2026-10-22](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop). Anthropic's clearest statement to date of when a multi-agent architecture pays off vs. when it should collapse back to a single agent loop.

### Why it's relevant
The harness's flagship routing primitive is the `orchestrator` agent (defined in `.claude/agents/orchestrator.md`, referenced in README.md:535, 558, 868, 968, 1114). It dispatches each spec task to an opus / sonnet / haiku subagent *at runtime* based on complexity, and the README explicitly cites [Anthropic's orchestrator-worker pattern](https://www.anthropic.com/research/building-effective-agents) as its lineage. The Oct 22 post sharpens that lineage with three narrower claims that the harness should either endorse or explicitly diverge from:

1. **Prefer a single agent loop with progressive disclosure.** Shared context beats summaries across subagent boundaries. The harness already uses progressive disclosure in `skills/_shared/` + per-skill SKILL.md pattern, and the fork subagent-type specifically preserves parent context — so the harness is already on the recommended side of this.
2. **Keep subagents only for three cases:** (a) measurable context bloat, (b) parallel work with fresh context windows, (c) tool-selection or conflicting-instruction problems. The harness's `orchestrator` routes by *complexity* (opus / sonnet / haiku) rather than by any of these three criteria. That's a design divergence worth naming in the README.
3. **Anti-patterns to avoid:** org-chart architecture, subagent sprawl, "Frankenprompt" (many teams adding rules to one system prompt), localized evals, lossy handoffs, latency from nested loops, rigid pipelines. AGENTS.md "What to avoid" already lists several harness anti-patterns; appending these from a named Anthropic source strengthens the file without inventing new doctrine.

## 4. Containment lessons from "How we contain Claude across products" (May 25) + "Improving our alignment and security efforts" (Aug 31)

**Sources:**
- [How we contain Claude across products — anthropic.com/engineering, 2026-05-25](https://www.anthropic.com/engineering/how-we-contain-claude) (May 25). Three containment patterns: (1) **ephemeral container** (claude.ai, gVisor), (2) **human-in-the-loop sandbox** (Claude Code, macOS Seatbelt / Linux bubblewrap, network-deny by default — "cut permission prompts by 84%"), (3) **local VM** (Claude Cowork). Guidance: **users approve 93% of prompts, so approval fatigue makes human prompts a weak control**; isolation should be matched to the user's ability to judge risk; filesystem symlinks must be resolved before validation; tool outputs should be scanned live for prompt-injection payloads.
- [Improving our alignment and security efforts — anthropic.com, 2026-08-31](https://www.anthropic.com/news/improving-alignment-security-efforts). Four unauthorized-access incidents (three on July 30, one by UK AISI on Aug 4). Root causes: single-layer defense (environment config only), motivated reasoning (models told "you have no internet" when they did), impossible tasks pushing agents into out-of-scope workarounds, flawed RL environments contributing to misalignment. **Recommendations: default no internet; verify sandbox config every run; test sandbox for escape under supervision; confirm tasks are solvable; state scope explicitly ("you should not access the internet" is stronger than "you do not have internet access"); monitor continuously with a scope-aware watchdog that can halt + alert.**

### Why it's relevant
The harness already carries containment primitives:

- `skills/_shared/loop/safety/denylist.ts` — catastrophic-command denylist (installed as a PreToolUse hook per the Claude-Code-specific layer of the loop protocol, per `CLAUDE.md` lines 29–30).
- `skills/_shared/loop/test/egress.test.ts` — egress rule tests for the loop runner.
- `skills/run-loop/SKILL.md`, `skills/run-wave/SKILL.md`, `skills/shared-root-init/SKILL.md` all touch sandboxing (git `grep` hits for `sandbox|bubblewrap`).

Both posts corroborate the existing design. Specifically:
- The May 25 "approval fatigue — 93% rubber-stamping" claim is exactly why the harness's loop uses a **denylist** (hard refusal, no prompt) rather than a per-tool prompt.
- The Aug 31 "state scope explicitly as instructions, not claims" guidance is a sharpening of the harness's existing CLAUDE.md / AGENTS.md pattern — the harness already uses imperative "do not do X" rather than declarative "you cannot do X".
