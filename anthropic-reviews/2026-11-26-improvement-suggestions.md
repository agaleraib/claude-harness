## 3. Link Anthropic's "Enterprise guide to securing coding agents" from `procedures/api-security-checklist.md`

**Source:** [The enterprise guide to securing coding agents — claude.com/resources, 2026-11-23](https://claude.com/resources/articles/enterprise-guide-to-securing-coding-agents)

### Why it's relevant

The harness has **one** security checklist: `procedures/api-security-checklist.md`. Its scope is explicit at the top:

> *Framework-agnostic. Run through this for every new or modified API route, endpoint, or RPC handler.*

That's **app-level** security — auth/authZ/input validation/data access for API code the agent writes. It's silent on the orthogonal question Anthropic's Nov 23 guide covers: **how do you secure the Claude Code session itself** — the agent, its tools, its hooks, its settings precedence?

The Anthropic guide gives concrete, non-enterprise-only recommendations that apply to a solo harness user too:

- **Permission rule ordering:** deny > ask > allow. Managed deny rules can't be overridden by user/project. Subagents inherit the parent's rules.
- **PreToolUse hooks with `onFailure: block`** — by default a failing or timed-out hook *lets the call through*, which is the opposite of what users assume.
- **ConfigChange hooks** to reject mid-session attempts to loosen controls.
- **`allowManagedHooksOnly`** so only platform-approved hooks run.
- **Secret scanning on push** (the harness already has this via the global git-hook dispatcher landed in commit `e0328b8` — "global dispatcher — secret scan, mass-delete block, profile gate").
- **Managed settings precedence** — `managedSourcesBehavior: merge` and `/status` to confirm which sources applied; otherwise the highest-ranked source silently wins.

The harness has adjacent infrastructure (`skills/_shared/loop/safety/{denylist,guardrails,hook-probe,write-root}.ts` under `skills/run-loop/`) and a global git-hook dispatcher — but none of the human-readable procedures docs cross-reference the authoritative Anthropic guidance on *how* to configure them safely.

### Concrete change

**Append a new section to `procedures/api-security-checklist.md`.** Exact insertion after the final existing section:

```markdown
---

## Related: securing the Claude Code session itself

The checklist above covers **the code the agent writes**. The orthogonal layer — **how the agent is allowed to run** — lives in the session's settings, hooks, permissions, and sandbox. For harness-level guidance, see [Anthropic's "Enterprise guide to securing coding agents" (2026-11-23)](https://claude.com/resources/articles/enterprise-guide-to-securing-coding-agents). Points relevant to this harness even on solo/individual plans:

- **Permission rules evaluate deny → ask → allow.** An allow rule cannot create an exception to a deny; subagents inherit the parent session's rules. Keep deny rules in managed settings so they can't be loosened by project or user settings.
- **Hooks default to `onFailure: allow`.** If a `PreToolUse` hook fails or times out, the tool call proceeds. Set `onFailure: block` explicitly on any hook whose purpose is to gate a risky action (secret scan, mass-delete guard, etc.).
- **Secret scan at push, not only at pre-commit.** This harness's global git-hook dispatcher (commit `e0328b8`) covers the pre-commit layer; the Anthropic guide recommends secret scanning at `push` as a backstop.
- **`managedSourcesBehavior: merge`** if settings arrive from more than one managed source — otherwise the highest-ranked source silently wins and the others' rules disappear. Use `/status` to confirm which sources are active.
- **Auto Mode classifier** gates tool calls not already decided by a rule — don't rely on it for irreversible or high-stakes actions (prod DB migrations, IAM changes, infra edits). Require human approval for those regardless.

These are complements to the API checklist above, not substitutes.
```

### Expected payoff

- Future readers hit both the app-level and the session-level security layers from one entry point.
- The `onFailure: block` note alone is worth the edit — it's a non-obvious default that turns a safety-critical hook into a no-op, and the harness's `run-loop/safety/hook-probe.ts` is exactly the kind of hook that gets caught by it.
- Low-risk pure doc change; no behavioral code change.

## 5. Bookkeeping: *Building always-on agents* primitives map onto `/run-loop` — no fresh action

**Source:** [Building always-on agents — claude.com/resources, 2026-11-13](https://claude.com/resources/articles/building-always-on-agents)

### Why it's relevant

Anthropic's post defines an **always-on agent** as *stateful and proactive*, sleeping most of the time and waking on events. It identifies **five primitives**:

1. **Event inbox** — durable table, dedup by source ID, one active worker per inbox.
2. **Timers** — separate store for scheduled/follow-up tasks, scheduler polls and enqueues inbox events.
3. **Memory** — durable storage separate from workers; load an index at run start.
4. **Permissions** — credentials out of agent environment, proxy injects them; auto-mode blocks risky actions; deferred tool calls.
5. **Outbox** — plain send tool by default; add formal outbox only to pace / recover.

The harness has **adjacent but not equivalent** infrastructure in `skills/run-loop/`:
