## 4. Flag Scion's "intent-based review" + "post-merge testing" as inspiration for a future review-depth tiering convention

**Source:** [Redesigning source control at Anthropic — anthropic.com/engineering, 2026-10-13 (updated 2026-10-15)](https://www.anthropic.com/engineering/redesigning-source-control). Anthropic built an in-house VCS (**Scion**) and review tool (**Antique**) over 5 months to handle 30k merges/day against a 100 GB monorepo. Highlights:
- **Changesets** (write-ahead-log entries listing changed files + content-addressed blobs) replace commits.
- **Intent-based review** — reviewers check the *intent* of a change, not every line; approval rules distinguish comment-only edits from logic changes.
- **Post-merge testing** replaces a global merge-queue lock — tests run after merge and before deploy.
- **Minimal refs** — refs discouraged except for `main` and release branches.
- **Tiered caching** — daemon / regional cache / server, with sparse + virtual checkouts.

Anthropic says Scion itself **isn't meant for general use**.

### Why it's relevant (speculatively)
The harness today operates in a classic Git / GitHub model: feature branch → PR → CI → merge → run `/commit`'s pre-push `code-reviewer` → push. Scion's conventions are far beyond a solo repo's needs today, but **two patterns are portable and worth parking** for when the user project set grows:

1. **Intent-based review as a convention for the harness's `code-reviewer` agent.** The agent today reports *every* finding above its confidence threshold. "Intent-based review" would mean: *given the stated intent of the diff (title + body + spec reference), does the change implement that intent correctly?* — and demote findings that are correct-but-irrelevant to the stated intent (e.g. "function X doesn't handle the empty-list edge case" when the diff was supposed to add logging). The harness's planning-loop already has a "wrong-premise → option 4" case (`README.md:273`); intent-based filtering would be an extension of that.

2. **Review-depth tiering as a cross-reference to §2's Quick / Standard / Deep.** Code Review GA (§2) shipped per-repo tiered depth. Scion ships per-change-type tiered depth (comment-only vs logic change). Both patterns suggest the harness's planning-loop could carry **per-file-category depth** — e.g. a change to `criteria/*.md` ships with a lighter review than a change to `skills/_shared/loop/`. Today this is implicit (meta-tooling paths trigger the `codex:review` reminder via `README.md:297`); making it explicit would reduce the review budget on low-risk edits.

### Why `defer` and not `spec`
- Scion's problem (30k merges/day across 100 GB monorepo) is three orders of magnitude from the harness's scale. The patterns are *conceptually* portable; the toolchain isn't.
- Anthropic explicitly says Scion isn't for general use. Importing patterns from a tool that won't be released keeps the risk of chasing a moving target low.
- The intent-based-review idea has real design surface (how is "intent" encoded? spec reference? PR title? CLAUDE.md policy?) — a `/spec-planner` session could spec it, but it's **speculative for solo tooling** per the routine's own rubric.
- The depth-tiering idea in §2 is cheaper to prototype (just a `criteria/*.md`-vs-everything-else switch); this § exists to note the cross-reference, not to compete with §2.

### Concrete change
None this run. Two paths when triaging:

1. **Easy path** — leave this § as a bookkeeping note; park for when the harness's user base is more than one person or when a diff-triage experiment surfaces a specific need.
2. **Promotion path** — if the maintainer wants to prototype intent-based filtering now, the smallest experiment is: extend the `code-reviewer` agent's prompt with a one-line directive — *"If a finding is correct but orthogonal to the stated intent (PR title or spec reference), drop it from the main report and surface it as a parked `[nit]` instead of a top-tier finding."* Then measure signal-to-noise on the next three sessions. **This would be a new §, not part of this one.**

### Expected payoff (no-op path)
Decision-trail integrity. When the harness grows past solo (`.harness-profile:12-14` says `team.size: solo` today; the `anthropic-reviews/README.md` lead paragraph notes "If the maintainership ever expands, revise …"), the reader has a pointer to the Scion patterns that framed the discussion.

### Expected payoff (promotion path)
Lower review-finding noise on diffs where the stated intent is narrow. Cheap-to-measure experiment; concrete lift unknown.
