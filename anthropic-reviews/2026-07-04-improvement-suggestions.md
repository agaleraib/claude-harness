## 3. Adopt dynamic workflows / `ultracode` as a fan-out primitive in the orchestrator

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-06-02](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Announced at Code w/ Claude London (May 19–22). Claude Code v2.x now ships a `Workflow` tool: Claude authors a JavaScript orchestration script (`agent()`, `parallel()`, `pipeline()`, `phase()`) at plan time, the runtime executes it in the background across ≤16 concurrent subagents, results stream back to the main session. Explicit opt-in via the keyword `ultracode` in the user prompt or via `Workflow` invocation.

### Why it's relevant
The harness's `orchestrator` agent (`.claude/agents/orchestrator.md`, described in `README.md:566–592`) is the current mechanism for **parallel fan-out with model routing** — it evaluates each task, picks Haiku/Sonnet/Opus, dispatches via worktrees for parallel-safe tasks, and enforces the safety chain (verify → `/commit` → `code-reviewer` → fix/park). Anthropic's Workflow tool is a *different implementation of the same conceptual pattern*:

| Dimension | `orchestrator` (harness) | Dynamic Workflows (Anthropic) |
|---|---|---|
| Author | Prose SKILL.md + agent frontmatter | JavaScript, written by Claude at plan time per task |
| Model routing | Runtime, prose-driven per task | `opts.model` per `agent()` call, defaults to session model |
| Isolation | `Agent isolation: "worktree"` | `agent(prompt, {isolation: "worktree"})` — same primitive |
| Concurrency cap | Implicit (session model concurrency) | Explicit — min(16, cores-2) queue |
| Verification | Runs through `/commit` + `code-reviewer` synchronously | Pattern-optional — `parallel(dimensions.map(verify))` etc. must be authored per workflow |
| State machine | Fixed (task → verify → commit → next) | Dynamic — pipeline vs parallel vs loop-until-dry |

The two overlap enough that a naive "adopt Workflow everywhere" would replace the orchestrator. That's a big enough architectural swing that it's not a `/micro`.

### Why this is `defer` (not `apply`, not `reject`, not `spec`)

Splitting the reasons out:

1. **Workflows require the `ultracode` opt-in or explicit user request.** The harness's design philosophy (`README.md:12–14`) is *"doesn't tell the model HOW to think — tells the model WHAT to check against."* Workflow is the HOW layer. Adopting it means the harness now dictates orchestration shape.
2. **The `orchestrator` skill+agent is one of the mature, dogfooded parts of the harness.** It has been through Wave 1 (model pin), the 2026-04-27 §1 effort-derivation update, and Wave 21 (`run-loop` composition root). Ripping it out has real cost even if Workflow is strictly better.
3. **Managed Agents connection.** Workflow is closely tied to `budget.total` / `budget.spent()` which are Managed-Agents / hosted-agent concepts. The still-DEFERRED 2026-04-19 §2 (brain/hands split) parked adopting Managed-Agents-shaped patterns behind a "when the harness runs on Managed Agents" trigger. Workflow belongs in the same parking spot.
4. **Solo-tooling scale.** Workflow is designed for the `parallel(100 items)` case. The harness's real workloads are `parallel(3–5 waves)` on a single-maintainer repo. The fan-out concurrency isn't the bottleneck.
5. **Ultracode is off by default in this harness.** The system-prompt guard *"ONLY call `Workflow` when the user has explicitly opted into multi-agent orchestration"* is exactly the discipline the harness's lean-context thesis already lives by. Adopting Workflow doesn't relax that guard; it duplicates the ceremony.

### Concrete change (deferred)

None this run. If/when the maintainer takes this on, the smallest-shape experiment is:

1. Spec a single-workflow adoption: replace `orchestrator`'s implicit "run each wave task in parallel worktrees" with an explicit `Workflow` script whose `phases: [{title: 'Implement'}, {title: 'Verify'}, {title: 'Commit'}]` block encodes the safety chain.
2. Keep `orchestrator` prose as the fallback (mode: `ultracode: false` → prose; `ultracode: true` → Workflow).
3. Measure: does the Workflow version reduce wall-clock on a real 5-task wave? If not, revert.

Explicitly a substantive change (`spec`, not `/micro`). Bundle with the 2026-04-19 §2 promotion trigger.

### Expected payoff (when applied)
If waves grow to `n > 10` tasks with real parallelism, the Workflow tool's explicit concurrency cap + budget accounting is worth having. Below that threshold, the prose orchestrator is fine.

**Verify before applying:**
1. `grep -rn "ultracode\|Workflow(script\|dynamic workflow" /home/user/claude-harness/skills /home/user/claude-harness/.claude/agents` — must still return zero hits. If it returns hits, adoption is already underway and this § is stale.
2. Check whether the `Workflow` tool is still gated behind `ultracode` opt-in at apply time. If Anthropic has flipped the default (workflow-on-by-default), the defer calculus changes — the opt-in ceremony argument in point 5 above no longer applies.
3. Confirm the 2026-04-19 §2 (brain/hands split) is still `Status: DEFERRED` in `anthropic-reviews/2026-04-19-improvement-suggestions.md`. If it's been promoted or rejected, re-evaluate this deferral's cross-reference.
4. Re-read `.claude/agents/orchestrator.md` — if the orchestrator has already been rewritten to be Workflow-native, this § is moot.

**Recommended verdict:** defer until orchestrator ergonomics hurt — same parking spot as 2026-04-19 §2 brain/hands split. Not speculative in the "won't happen" sense; speculative in the "not the current bottleneck" sense.

## 6. Wire Claude Code artifacts as an output surface for `harness-status` / `session-end` reports

**Source:** [Claude Code now supports artifacts — claude.com/blog, 2026-06-18](https://claude.com/blog/artifacts-in-claude-code). Claude Code sessions can now produce **artifacts** — live, shareable web pages (dashboards, PR walkthroughs, checklists) rendered on Anthropic-hosted infra, private by default, gated by Team/Enterprise org membership.

### Why it *looks* relevant
The harness has two skills that produce human-readable reports:

- `harness-status` — cross-repo state scanner (`skills/harness-status/SKILL.md`);
- `session-end` — day-end summary (`skills/session-end/SKILL.md`).

Both currently emit **Markdown** to `.harness-state/` files. Anthropic's artifacts feature turns those Markdown reports into shareable web pages that "update themselves as your session works" — which is directly what a `harness-status` cross-repo dashboard *wants* to be.

### Why this is `defer` (not `apply`)

Three concrete gates block adoption today:

1. **Team/Enterprise plan required.** The launch post says *"available as a beta for Claude Team and Enterprise customers."* The harness targets a single Pro/Max maintainer (`audience.kind: internal`, `audience.size_estimate: "1"` in `.harness-profile:14–16`). No team plan → no artifacts.
2. **Anthropic-hosted rendering.** Artifacts render on `claude.ai/code/artifact/{uuid}` — Anthropic infra, not the maintainer's local machine. The harness's whole design is git-tracked, offline-first, local-Markdown. Artifacts require session state to be pushed to Anthropic to render.
3. **Round-trip readability.** `harness-status` output is consumed by *other Claude Code sessions* (via `session-start` reading `last_exit.md`) as much as by the human. A web-page artifact isn't grep-able from another session. That would fork the state (Markdown for machines, artifacts for humans) — YAGNI on solo tooling.

### Concrete change (deferred)

None this run. If/when the maintainer takes this on:

1. Trigger: the harness picks up a team (`audience.kind: team`, `size_estimate: >1`) OR consumer projects with team plans want shared status.
2. Add an opt-in `harness-status --artifact` flag that, when set, writes to a scratchpad HTML file and calls the `Artifact` tool. Keep the default (Markdown to `.harness-state/`) untouched.
3. Do NOT replace `.harness-state/*.md` — always emit Markdown too. Artifact is a *view*, not a *source of truth*.

### Alternative considered

Vendor the `Artifact` tool's HTML skeleton as a template in `skills/harness-status/templates/artifact.html.tmpl` right now, gated behind an unset opt-in flag. **Rejected** as speculative — building infrastructure for a plan tier the harness doesn't have violates YAGNI.

**Verify before applying:**
1. `grep -rn "Artifact\|artifacts-in-claude-code\|claude.ai/code/artifact" /home/user/claude-harness --include="*.md"` — currently returns matches only inside `anthropic-reviews/reviewed-posts.md`. If it starts returning hits in `skills/*/SKILL.md`, adoption is underway.
2. Check whether artifacts have graduated from Team/Enterprise beta to Pro/Max at apply time. If yes, gate 1 is relaxed and this can be reconsidered.
3. Re-check `.harness-profile`'s `audience` block. If `size_estimate` has grown past 1, gate 3 (round-trip readability) may be moot.

**Recommended verdict:** defer until (a) team plan OR (b) artifacts graduate to Pro/Max. Same shape as 2026-05-10 §2 Cloud Routines deferral — interesting new primitive, no current pain, plan-gated.

## 7. Adopt the HTML-over-Markdown thesis for harness-generated reports

**Source:** [Using Claude Code: The unreasonable effectiveness of HTML — claude.com/blog, 2026-05-20](https://claude.com/blog/using-claude-code-the-unreasonable-effectiveness-of-html). Thariq Shihipar argues HTML is a strictly better output format than Markdown for human-agent workflows — richer visuals, tabs, mobile-responsive, "specs, code reviews, architecture explainers, design explorations, research reports, custom editing interfaces." Post accumulated ~8M views on X.

### Why it *looks* relevant
The harness produces a lot of Markdown-formatted reports:

- `docs/plan.md` (active wave board);
- `docs/waves/*.md` (wave receipts);
- `docs/specs/*.md` (technical specs);
- `.harness-state/*.md` (`last_exit.md`, `today_goal.md`, `parking_lot.md`);
- `anthropic-reviews/YYYY-MM-DD-*.md` (this very file).

If HTML is unreasonably effective for these, we should be writing them as HTML.

### Why it's `reject`

**All of the harness's Markdown reports are consumed by other Claude Code sessions**, not by humans in a browser. Specifically:

- `docs/plan.md` is read by `run-wave` / `session-start` to pick the next wave;
- `.harness-state/last_exit.md` is read verbatim by `session-start` under "Where you left off";
- `docs/specs/*.md` are read by `orchestrator` at wave dispatch time;
- `anthropic-reviews/*.md` are read by `apply-anthropic-reviews` to drive the decompose→classify→apply flow.

An HTML report can't be `grep`'d, `Read`'d, or line-referenced (`file_path:line_number`) the way Markdown can. The harness's Markdown format is load-bearing for its *round-trip* semantics: LLM writes → git stores → LLM reads. Switching to HTML breaks the round trip.

The post's core claim — *"HTML has richer visual density than Markdown"* — is **correct for human readers** but the harness's readers are largely other Claude Code sessions. For those, the token cost of HTML wrapping (`<div class="…"><h2>…</h2><p>…</p></div>`) is a **regression**, not an improvement.

### The one place where the HTML thesis might apply

`skills/skill-creator/eval-viewer/generate_review.py` already produces HTML for the skill evaluation review flow — that IS a human-in-browser workflow, and HTML is the right format there. Confirmed:

```
grep -rn "HTML" /home/user/claude-harness/skills/
→ skills/skill-creator/eval-viewer/generate_review.py: embeds all output data into a self-contained HTML page
```

So the harness already uses HTML where HTML is right (human review UI) and Markdown where Markdown is right (LLM round-trip). No change needed.

**Verify before applying:**
1. `grep -rn "Markdown.*docs/plan\|reads.*plan\\.md\|reads.*last_exit\\.md" /home/user/claude-harness/skills` — should still show `session-start` reading `.harness-state/last_exit.md` verbatim. If any of these consumers have been switched to HTML parsing, the round-trip argument weakens.
2. If a future harness feature ships human-facing reports (e.g. a shared dashboard for a team, or the artifacts adoption in §6), reconsider HTML for **that** surface — but not for the Markdown state files.

**Recommended verdict:** reject — surface mismatch. HTML is right where humans read (skill-creator eval viewer, already HTML); Markdown is right where Claude Code sessions round-trip state.
**Status:** PENDING — awaiting triage in PR review
