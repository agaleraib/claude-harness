## 2. Formalize "verification loop" vocabulary alongside existing `/code-review`, `/commit`, and `/verify` surfaces

**Source:** [Building verification loops in Claude Code with skills — claude.com/blog, 2026-07-22](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) (Delba de Oliveira). Defines a **verification loop** as "a repeating cycle in which an agent checks its own work (running tests, linters, or custom checks) and fixes failures before moving on" and describes four placements: **Standalone** (user-invoked, cross-cutting), **Embedded** (appended to a producing skill), **Chained** (one skill wraps another), **On every PR** (CI). The post calls out that project-specific rules generic linters miss belong in skills (its example: rejecting migrations that drop a column without a backfill).

### Why it's relevant

The harness already *implements* this pattern across several surfaces, but under different names:

- `/commit` (`skills/commit/SKILL.md`) is **Embedded**: the `code-reviewer` agent runs before every push, and `scripts/git-hooks/dispatch.sh` runs secret scanning + mass-delete block + profile gate at the git-hook layer.
- `close-wave` and `run-wave` embed verification steps (the "unticked-task gate" that `2f3cb66` fixed is itself a project-specific check that a generic linter would miss — exactly the shape the post calls out).
- `code-reviewer` is **Standalone** in agent form — it's an adversarial pre-push reviewer rubric-anchored to `criteria/`.
- `/verify` is a built-in Claude Code slash command the post lists; this harness doesn't ship a competing one.

**What's missing:** the README has no section that frames these as a *single pattern*. A new reader (or future-you six months on) looking at `commit`, `code-reviewer`, `close-wave`, and `scripts/git-hooks/` individually sees four unrelated pieces. The verification-loop vocabulary ties them together: Standalone (`code-reviewer`, git-hooks), Embedded (`/commit`), Chained (`run-wave` → `close-wave`), On-every-PR (would be a cloud routine, aligned with the still-deferred 2026-05-10 §2).

### Concrete change (deferred)

If the maintainer wants to apply this later, the smallest patch is a **three-paragraph section in `README.md`** right after the `code-reviewer (Universal)` block (currently 2026-05-10 §1's touch landed there). Something like:

> #### How this fits into the harness's verification loops
>
> Across the harness, agents and skills run in verification loops — a repeating cycle in which the agent checks its own work before moving on. The four placements per [Anthropic's 2026-07-22 skills post](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) map onto this harness as follows:
>
> - **Standalone:** `/code-review`, `/security-review`, `scripts/git-hooks/dispatch.sh` — cross-cutting checks invoked explicitly or at the hook layer.
> - **Embedded:** `/commit` wraps `code-reviewer` so every commit touches the adversarial pass first.
> - **Chained:** `/run-wave N` → `/close-wave N` enforces the unticked-task gate before the wave is marked done.
> - **On every PR:** future `/ultrareview` or Anthropic's Code Review GA (see 2026-05-10 §1 complementarity note).

### Why `defer`, not `apply`

1. **Nobody has asked yet.** The pattern is working; the vocabulary is a clarity add, not a bug fix.
2. **Risk of churning the README** — the 2026-05-10 §1 "complement" paragraph was added to the same region 164 days ago. Adding another paragraph risks turning the agent section into a mini-essay.
3. **The pattern is slightly larger than one §.** If the maintainer wants to really adopt the vocabulary, several SKILL.md descriptions ("skills/_shared/loop/" is already named "loop" and does *not* mean verification loop) would need to be checked for name collision. That's a `/spec-planner` territory question, not a `/micro` edit.

1. `grep -rn "verification loop\|verification-loop" README.md AGENTS.md` — must return nothing (if it returns hits, the vocabulary has already been added and this § is stale).
2. `grep -n "code-reviewer (Universal)" README.md` — confirms the insertion target still exists (last touched 2026-05-10 §1).

## 4. Introduce `.claude/rules/` with `paths:`-scoped rules for the harness's three distinct code areas

**Source:** [Steering Claude Code: when to use CLAUDE.md, skills, hooks, and subagents — claude.com, 2026-06-18](https://claude.com/resources/articles/steering-claude-code-skills-hooks-rules-subagents-and-more). Compares CLAUDE.md, skills, hooks, subagents, rules, output styles, and system-prompt appends. Specific guidance on **rules**:
> `.claude/rules/`: Add a `paths:` field to scope a rule to specific files, so it loads only when relevant. Use path-scoped rules for cross-cutting concerns that span some but not all of the codebase.
>
> Avoid: *Unscoped rules for file-specific concerns, which cost tokens in unrelated sessions.*

The post also notes to keep CLAUDE.md "under about 200 lines" and treat it as an index rather than a procedure store (the harness's root CLAUDE.md is 24 lines, well within this).

### Why it's relevant

The harness has three distinct code zones with mutually-exclusive conventions:

1. `skills/_shared/loop/` — TypeScript, Node ≥24 native type-stripping, `node:test`, no build step (per `CLAUDE.md:36`).
2. `scripts/git-hooks/` — bash, strict-mode (`set -euo pipefail`), portable POSIX idioms.
3. `skills/*/SKILL.md` — markdown with YAML frontmatter (`name:`, `description:`, optionally `allowed-tools:`); conventions for section ordering, pseudocode style, etc. are implicit today.

Today these conventions live in **prose scattered across CLAUDE.md, AGENTS.md, individual SKILL.md files, and the maintainer's head**. A session editing `skills/_shared/loop/*.ts` doesn't automatically see the "Node ≥24 native type-stripping, no build step" invariant unless CLAUDE.md's one-liner catches the model's eye. Likewise a session editing a `SKILL.md` doesn't automatically load the frontmatter conventions.

`.claude/rules/*.md` with `paths:` fields would load only when files matching those paths are read, so the convention-sheet loads *scoped* to the zone the model is working in — closer to the "cross-cutting concerns that span some but not all of the codebase" definition the post calls out.

Hypothetical layout:

```
.claude/rules/
  loop-typescript.md      # paths: ["skills/_shared/loop/**/*.ts"]
  git-hooks-bash.md       # paths: ["scripts/git-hooks/**/*.sh"]
  skill-md-frontmatter.md # paths: ["skills/*/SKILL.md"]
```

### Why `defer`, not `apply`

1. **Speculative for solo tooling.** The harness is maintained by one person; the "automatically-load-the-convention-sheet" value is largest when multiple contributors each hit a different code zone. Solo workflow already keeps the TypeScript / bash / SKILL.md invariants in head.
2. **Adds structural surface area.** Three new files under `.claude/rules/` would need to be kept in sync with CLAUDE.md and AGENTS.md — a new source of drift. The 2026-05-10 §1 (`code-reviewer` complementarity doc) and this routine's own tracker are already a two-level documentation stack.
3. **No concrete friction point.** The maintainer hasn't flagged "a session edited `loop/*.ts` and missed the Node-type-stripping invariant" as a problem. Suggesting path-scoped rules without a triggering incident risks over-engineering.
4. **Context budget is already comfortable.** The 2026-05-07 skills audit noted ~6.1K / ~15.5K of the skills budget used; the frontmatter + description of a few extra rules is cheap but the net value in a solo repo is near zero.
5. **The post itself warns against this.** "Unscoped rules for file-specific concerns, which cost tokens in unrelated sessions" is the explicit anti-pattern; the harness's current approach (keep invariants in CLAUDE.md as a one-line index entry pointing to the detailed spec) is closer to the post's recommendation than adding `.claude/rules/` would be.

### Verify before applying

1. `ls .claude/rules/ 2>/dev/null | wc -l` — zero today; if non-zero when applied, part of this § is already in flight.
2. `wc -l CLAUDE.md` — currently 24 lines, well under the post's 200-line cap. If CLAUDE.md has grown past 150 lines, the pressure for path-scoped rules rises (because the "index not a procedure store" principle is strained).
3. Confirm the three code zones' invariants aren't already captured as skills (which the post prefers over rules for procedures): `grep -l "node:test\|type-stripping" skills/*/SKILL.md` should be checked — if a skill already encodes this, don't duplicate as a rule.

**Recommended verdict:** defer until a cross-cutting rule accumulates — speculative; solo repo doesn't need it today; adds surface area the maintainer would have to keep in sync. If a *second* contributor joins or CLAUDE.md crosses ~100 lines, revisit.
