## 1. Cite Anthropic's Dynamic Workflows alongside the local `orchestrator` agent

**Source:** [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code) (research preview May 28; GA in the Claude Code CLI, Desktop, VS Code extension, Claude API, Amazon Bedrock, Vertex AI, and Microsoft Foundry during June). Bun ported ~750,000 lines of Zig → Rust in 11 days using it; the docs (`code.claude.com/docs/en/workflows`) describe a JavaScript orchestration script that a lead Claude writes and executes to run up to ~16 parallel and ~1,000 total sub-agents in a single session with intermediate state held outside the conversation.

### Why it's relevant
The harness's `orchestrator` agent ([`.claude/agents/orchestrator.md`](../.claude/agents/orchestrator.md); `README.md:533–593`) implements the **spec-driven** orchestrator-worker pattern: read a spec, dispatch each task to opus/sonnet/haiku, honor a per-task `**Effort:**` hint, retry with escalation on verify failure, commit through `/commit`. It is **local**, **single-execution-model** (the model that dispatches is the same model that reasons about each task in the parent session), **fan-out via `isolation: "worktree"`**, and coupled to `.harness-profile` for routing.

Anthropic's **Dynamic Workflows** ships a `Workflow` tool (already visible as a built-in in this Claude Code session; see the tool block at the top of the routine's system prompt) that:
- lets the model **write a JavaScript orchestration script** in-turn and execute it
- runs **tens to hundreds of parallel sub-agents** per invocation (~16 concurrent, ~1000 lifetime cap)
- keeps sub-agent state **outside the conversation** in script-local variables
- supports **`pipeline()` / `parallel()` / `phase()` / `log()`** primitives with per-agent `{schema, model, effort, isolation, agentType}` overrides
- runs against the current session's model tier (Pro/Max/Team/Enterprise) without a separate hosted product

These are **complementary layers**, same shape as the `code-reviewer` vs `/ultrareview` split written into the README on 2026-05-10 (§1, APPLIED in commit `8b5b12a`):

- **`orchestrator`** is the *spec-driven, project-tracked* dispatcher: reads `docs/specs/<date>-<topic>.md`, logs to `.harness-state/orchestrator.{log,jsonl}`, commits through `/commit`, escalates via `low → medium → high → xhigh → promote-model`, honors `.harness-profile`. Owned by the harness; portable across projects that install from `setup-harness`.
- **`Workflow`** is the *in-session, one-shot* dispatcher: called by any agent in the middle of a task when the *shape of the fan-out isn't yet known* (discover files → run per-file transform, or "loop until dry" per the Dynamic Workflows docs). Not spec-driven. Not journaled. Not tied to `docs/plan.md` waves. But cheap, immediate, and covers the "quick multi-file audit" case the orchestrator would need a spec file to serve.

The README already names one similar layer split (local `code-reviewer` vs cloud `/ultrareview` / `Code Review`). The **Dynamic Workflows / `orchestrator`** split is the *second* such overlap Anthropic has shipped this year, and it's the biggest concept in the June 2026 update cycle. Not addressing it leaves a reader (or future-you) with the same question that §1 of the 2026-05-10 file forestalled for `code-reviewer`.

Today there is **zero mention of `Workflow`, `dynamic workflows`, or `hundreds of subagents`** in the repo (`grep -rn 'Workflow\|dynamic workflow\|hundreds of subagents' .` returns nothing outside `anthropic-reviews/`).

A spec needs to say whether the flip is (a) immediate for new projects, (b) opt-in via a `/project-init --model=claude-5` flag, or (c) requires a manual bump per project.

Each of these is a small decision on its own but the interaction matters. `/spec-planner` is the right tool.

## 3. Add a "shift-left + close-the-loop" bullet to `procedures/api-security-checklist.md`

**Source:** [How Anthropic secures its AI-native software development lifecycle — claude.com/blog, 2026-07-21](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle). Anthropic's own methodology for shipping secure code when Claude authors ~80% of merged PRs. Reports **30–40% reduction in security-related comments on PRs** after enabling automated in-session security review and **closing the feedback loop** by rolling repeat findings back into CLAUDE.md so Claude stops re-generating the same class of vulnerability.

### Why it's relevant
The harness already ships the two "leftmost" pieces of the pattern:

- **In-session security review** — `README.md:32` names Claude Code's built-in `/security-review` slash command and cites Claude Security's public beta as the "vendor primitive absorbing harness territory" argument. `.claude/agents/code-reviewer.md` also runs security checks as part of the adversarial reviewer's rubric.
- **A framework-agnostic security checklist** — `procedures/api-security-checklist.md` covers Auth / Authz / Input / Data Access / Response / Rate Limiting for user-facing API routes.

What the harness does **not** ship, and what Anthropic's post makes concrete, is the **third piece of the loop**: when the security reviewer catches the same class of issue twice (e.g. missing tenant-scoping on a new `/orders/:id` route, missing `userId`-from-session check on a new endpoint), the pattern is to **update CLAUDE.md** (or the equivalent project-specific context file) with a one-line rule so the same class of finding stops appearing. Anthropic reports this loop is what turns "one-shot security review" into "declining regression rate."

Today `procedures/api-security-checklist.md` treats the checklist as static — each phase-exit gate goes through the list, unchecked items block exit. There is no §14 saying "when the same box gets unchecked three times across three PRs, add the specific-to-this-project version of that rule to CLAUDE.md so Claude generates the check inline." That's the loop.

### Concrete change

**One bullet** appended to the existing `procedures/api-security-checklist.md`, added as a new final §14 (the file currently has §§1–13; verify with `wc -l procedures/api-security-checklist.md` before assuming the section-numbering — this § is aimed at whatever the last section number is + 1).

Draft body:

```diff
+## 14. Close the loop when patterns repeat
+
+> Adapted from [How Anthropic secures its AI-native SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle) (2026-07-21). Anthropic reports a 30–40% drop in security-related PR comments after adopting this loop.
+
+If the same checklist box gets unchecked **three times across three PRs** on the same project — e.g. missing `userId`-from-session check on new endpoints, missing tenant-scoping on new `GET /:id` routes, missing pagination cap on new list endpoints — the fix is not "keep re-checking the box." The fix is to write the project-specific version of the rule into `CLAUDE.md` so Claude generates the check inline the next time.
+
+- [ ] Repeat findings across ≥3 PRs promoted to a project-specific rule in `CLAUDE.md`
+- [ ] Rule references the specific route pattern, not the generic checklist item (e.g. "`GET /orders/:id` must verify `order.userId === session.userId` before returning" — not just "authorize per-user")
+- [ ] Rule includes the code-review question phrased so Claude answers it during generation (e.g. "// SECURITY: does this route derive `userId` from the session? if not, add it before proceeding")
+
+**Anti-pattern:** dumping the entire `procedures/api-security-checklist.md` into `CLAUDE.md`. That grows the context bloat problem the harness is designed to avoid (see `README.md` §"Why Not Superpowers"). Promote **only** the rules that have empirically repeated three times.
```

The addition is a single doc bullet; risk is entirely in the wording, not in the mechanism.

This § is the opposite direction: **importing** one concrete methodology bullet Anthropic's own team uses. Different citation intent; not a rerun.

## 4. Author `procedures/agent-security-checklist.md` from Zero Trust for AI Agents

**Source:** [Zero Trust for AI Agents — claude.com/blog, 2026-05-27](https://claude.com/blog/zero-trust-for-ai-agents). ### Why it's relevant
The harness ships `procedures/api-security-checklist.md` (client-app-facing, framework-agnostic API hardening) but has **no counterpart file** for the security posture of the *agent itself* — the six-agent stack the harness installs (`orchestrator`, `code-reviewer`, `spec-planner`, `generator`, `ui-evaluator`, `project-tracker`) does not currently carry a checklist that answers questions like:

- Which tools can each agent invoke, and at what scope?
- What's the failure mode if a subagent is prompted (or prompt-injected) to leak secrets from `.env` or `.harness-state/`?
- Which agent is allowed to call MCP servers, and which MCP servers are on the allow-list?
- What's the reporting story if a subagent behavior looks compromised?

Anthropic's Zero-Trust framework provides the seven-threat / eight-step scaffolding to answer all of these. A checklist-shaped port would sit alongside `procedures/api-security-checklist.md` and cover the "agent-as-consumer" angle the API checklist doesn't.

### Why this is `defer`, not `apply` today

1. **Solo tooling scope.** The harness is `team.size: solo` per `.harness-profile:65`. The Zero-Trust framework's enterprise integration surface (Entra, Okta, per-tool RBAC via an IdP, agent-attestation) is heavy for solo use. The maintainer can run the harness without formalizing any of it.
2. **Consumer projects don't yet ship harness agents.** The harness's agents run inside `~/.claude/agents/` on the maintainer's own laptop and any project that installs via `setup-harness`. None of them are shipped as an agent-in-a-container that a downstream user deploys into a corporate network. When that changes (e.g. if a consumer project asks to publish the `code-reviewer` as a hosted GitHub App), the Zero-Trust framework becomes the operative reference.
3. **No repeated incident.** Unlike §3 (which formalizes a pattern Anthropic *reports* they use daily), Zero Trust is a *framework* — no proof yet that its bulletin lands as a checkable process for a single-maintainer harness.
4. **Overlap with existing MCP-server discipline.** `AGENTS.md` already carries an MCP-server-trust note (`grep -n 'MCP' AGENTS.md`). Some of the Zero-Trust framework's tool-authority pieces are already loosely covered — porting the full 8-step frame would duplicate that.
