## 1. Adopt a `## Gotchas` section convention in SKILL.md files

**Source:** [Lessons from building Claude Code: How we use skills — Claude Blog, 2026-06-03 (Thariq Shihipar, Anthropic Claude Code team)](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills)

### Why it's relevant

Thariq's post — published by the Claude Code team as an internal-lessons write-up — makes an unusually strong claim: *"The highest-signal content in any skill is the Gotchas section, which should be built up from common failure points that Claude runs into when using the skill. Most of the best skills began as a few lines and a single gotcha, then got better because people kept adding to them as Claude hit new edge cases."* Anthropic runs "hundreds" of Skills internally and groups them into nine categories (library/API reference, product verification, data fetching, business process, code scaffolding, code quality/review, CI/CD, runbooks, infrastructure operations) — this harness ships skills covering ~6 of those categories.

The harness has 24 skills under `skills/` (verified via `ls skills/`). A grep across all `skills/**/SKILL.md` for `## Gotchas`, `## Common pitfalls`, `## Pitfalls`, `## Warnings`, or `## Failure modes` (case-insensitive) returns **zero matches**. A grep for the word "gotcha" (case-insensitive) returns 1 hit — inside `skills/setup-harness/SKILL.md` prose, not as a section. So the convention Thariq describes as *the* highest-signal pattern is entirely absent from this repo's skill authoring today.

The skill-creator skill (`skills/skill-creator/SKILL.md`) is the natural place to seed the convention because it is the how-to-write-a-skill playbook — it defines the anatomy of a skill and points at `references/anthropic-skill-authoring.md`. Adding one paragraph there plus a light nudge in the SKILL.md template would propagate the convention forward.

### Concrete change

Two touches, in this order:

**(a) Add a `## Gotchas` bullet to `skills/skill-creator/SKILL.md`'s "Anatomy of a Skill" section.** Suggested insertion (after line ~80, wherever the anatomy tree is listed):

```markdown
#### Recommended section — `## Gotchas`

Per [Anthropic's June-2026 skills post](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills), the highest-signal
content in any mature skill is a **`## Gotchas`** section: a running list of
concrete failure points Claude has actually hit when using the skill, each
one-to-three sentences. Start with one gotcha and one edge case; grow the
section every time a real session surfaces a new one. A skill with a healthy
Gotchas section teaches the model the failure modes that the prose intro
can't; a skill without one is a wiki article, not a playbook.
```

**(b) Add a `## Gotchas` placeholder to `skills/skill-creator/assets/` (if a SKILL.md template exists there) — a single stub line like:**

```markdown
## Gotchas

<!-- Add one bullet per real failure Claude has hit while using this skill.
     Empty at first; grow with usage. -->
```

Do NOT retroactively add a `## Gotchas` section to every existing skill in this repo — Thariq's point is that *real, observed* failures make the section high-signal, and manufacturing them would produce filler. Instead, let the convention propagate organically: each time a skill is edited to fix a real bug, add the gotcha there.

### Expected payoff

A ~10-line documentation touch in one skill (`skill-creator`) that makes the harness's own skill-authoring guidance match Anthropic's field-tested pattern. Every new skill created via `/skill-creator` inherits the convention. Zero risk (additive, no code change, no existing skill mutated).

**Verify before applying:** `grep -rniE "^##\s+(Gotchas|Common pitfalls|Pitfalls|Warnings|Failure modes)" skills/**/SKILL.md` should return zero matches (verified 2026-07-22); `grep -rn "Gotchas" skills/skill-creator/SKILL.md` should also return zero. If either has grown a section since — e.g. because someone applied this § before triage — the maintainer already agrees with the direction and this suggestion collapses to "extend the existing note", not add a new one.

**Recommended verdict:** apply — verified gap, single-file edit, cited to a primary source, zero blast radius.

## 2. Loop engineering primer — cross-reference `/run-loop` from AGENTS.md's `## Loop protocol` intro paragraph

**Source:** [Loop engineering: Getting started with loops — Claude Blog, 2026-07-07](https://claude.com/blog/getting-started-with-loops)

### Why it's relevant

Anthropic's July-7 post defines the vocabulary of a Claude loop — *"a repeatable workflow around the model that defines what triggers the run, what context Claude should read, what it is allowed to do, how the output is verified, where the state is stored, and when the loop should stop, repeat, or escalate to a human"* — and lists the six components (trigger, context, action, verification, state update, decision). It is a solid *primer* for readers new to the pattern.

This repo already implements the same idea, deeper: `AGENTS.md`'s `## Loop protocol` section (lines 91–117) defines the five-step per-item mechanical gate (implement → exit gate → code-review → atomic merge → post-merge effects), the fail-safe three-way rule for gates, the AFK-vs-HITL 4-gate capability test, the sandcastle-vs-worktree runner selection, and the risk-proportional auto-merge scheduler. The primer's six components map onto the harness's implementation as: trigger → work-source; context → runner workspace; action → agent invocation; verification → exit gate + code review; state update → outbox reconciliation + receipts; decision → AFK-frontier-first scheduler + termination caps.

The harness's `/run-loop` skill is *strictly more* than what the primer describes — there is no missing pattern, no unimplemented component. The one honest deltas are terminology (Anthropic's "state update" ↔ harness's "outbox reconciliation") and scope (the primer includes manual/turn-based loops; the harness only implements the unattended lane).

### Concrete change

**Do nothing structural.** The primer's diagram-vocabulary might be worth citing from `AGENTS.md ## Loop protocol` as an external reference — a single sentence like:

> The primer version of this vocabulary lives at [Anthropic's July-2026 post on loop engineering](https://claude.com/blog/getting-started-with-loops); the definitions below extend it with the fail-safe gate rule, runner-aware AFK/HITL classification, and atomic-merge semantics this repo needs for unattended operation.

— but that is optional bookkeeping, not a methodology change. Leaving AGENTS.md untouched is also defensible.

### Expected payoff

Zero if the citation isn't added; a small onboarding gain (a new reader unfamiliar with the loop pattern gets a canonical primer link before diving into the harness's deeper spec) if it is. Either way, no code or protocol change.

**Verify before applying:** `grep -n "getting-started-with-loops" AGENTS.md CLAUDE.md skills/run-loop/SKILL.md` should return zero matches (verified 2026-07-22); if a citation has been added independently, this § collapses to "already done — nothing to do."

## 3. Claude Code's built-in `Workflow` tool ("dynamic workflows") vs. the harness's `planning-loop` orchestrator

**Source:** [A harness for every task: dynamic workflows in Claude Code — Claude Blog, 2026-06-02 (Thariq Shihipar & Sid Bidasaria, Anthropic)](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (product companion: [Introducing dynamic workflows — Claude Blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code))

### Why it's relevant

The post lands a new Claude-Code-native primitive: **the `Workflow` tool**. Claude reads an incoming task, writes a custom `.js` harness script (with `agent()` / `parallel()` / `pipeline()` / `phase()` primitives), and executes it — spawning subagents, assigning models, and managing worktrees natively. The recommended use cases are the five where custom harnesses had historically been built on top of Claude Code: **research, security analysis, agent teams, code review, migrations**. The `Workflow` tool is visible in this very session's tool list (verified — search for `Workflow` in the deferred tool listing).

This overlaps meaningfully with the harness's existing orchestration seams:

- `skills/planning-loop/` — spec→generator→evaluator triad; single-context, sequential
- `skills/run-wave/` — dispatch a wave to subagents (opus/sonnet/haiku routing); one-shot fan-out with a human checkpoint
- `skills/run-loop/` — mechanical-gate unattended loop over ready items; sequential
- `skills/_shared/loop/` — engine backend behind `/run-loop`

None of these use the `Workflow` tool today. The overlap:

- `run-wave` dispatches to N subagents in parallel → the `Workflow` tool's `parallel([...])` primitive does the same thing with Claude-Code-native accounting (concurrency cap, token budget, resume-from-runId).
- `planning-loop` iterates spec→gen→eval sequentially → the `Workflow` tool's `pipeline([items], stage1, stage2, ...)` primitive does the same with per-item pipelining (no barrier between stages).
- `run-loop` drives a stream of ready items through a mechanical gate → the `Workflow` tool's `pipeline()` with a per-item verify stage covers the same shape (without the atomic-merge / runner-selection / secret-bearing safety semantics).

The harness's implementations are all older than the `Workflow` tool. None *have* to migrate — the harness's orchestrators encode invariants the tool does not (fail-safe gate, atomic merge, receipts, runner selection). But when the next orchestration seam is added — or when `planning-loop` grows subagent fan-out — the maintainer should consider whether the built-in `Workflow` tool is the right substrate, versus rolling another custom orchestrator.

### Concrete change

**None today.** This is a re-evaluation trigger, not a code change. Park it as a design consideration for two upcoming milestones:

1. When `planning-loop` grows subagent orchestration (planner spawning per-task subagents, or evaluator running in a separate context) — evaluate `Workflow` tool `pipeline()` before hand-rolling.
2. When the harness needs a repeatable multi-repo task shape (audit N repos, run the same check across each, aggregate) — evaluate `Workflow` tool `parallel()` over hand-rolled fan-out.

Optional bookkeeping: add a one-line pointer to `parking_lot.md` under a new "Orchestration substrate re-eval" heading citing this post URL and the two triggers above, so the trigger doesn't get forgotten.

### Expected payoff

Zero today. Latent optionality — the next time an orchestrator is designed, the maintainer has an obvious substrate to weigh against a hand-rolled implementation. Cost of the maintenance note in `parking_lot.md`: <5 lines.

**Verify before applying:** `grep -n "Workflow tool\|dynamic workflows\|planning-loop.*Workflow\|Workflow.*planning-loop" parking_lot.md skills/**/SKILL.md` should return zero matches (verified 2026-07-22). If a note has already been added, this § collapses to "confirm the two triggers are correct."

**Recommended verdict:** defer until planning-loop grafts subagent orchestration OR a multi-repo audit skill lands. **scope: speculative** — the Workflow tool is real and shipping, but the harness has no current pain that justifies migrating existing orchestrators.
**Status:** PENDING — awaiting triage in PR review

## 4. Context-engineering strategies (compaction, sub-agent isolation, memory) — codify in a `skills/_shared/context/` reference

**Source:** [Effective context engineering for AI agents — Anthropic Engineering, 2026](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (companion cookbook: [Context engineering: memory, compaction, and tool clearing — Claude Cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools))

### Why it's relevant

Anthropic's post frames context-engineering as *"the natural progression of prompt engineering"* — the discipline of *"finding the smallest set of high-signal tokens that maximize the likelihood of your desired outcome."* It enumerates the concrete levers:

1. **Sub-agent isolation** — each subagent gets exactly the context it needs; main conversation stays focused on orchestration.
2. **Compaction** — start with maximizing recall (capture everything relevant), then iterate to precision. Overly aggressive compaction loses subtle context whose importance only becomes apparent later.
3. **Tool-result clearing** — drop stale tool outputs from context.
4. **Memory notes** — a stack-based structure: current sub-goal + plan on top, older turns compressed and summarized.
5. **Programmatic tool calling** — reducing tokens spent on tool schemas by generating tool calls programmatically.

The harness already implements the two biggest wins from this list:

- **Sub-agent isolation** is what `skills/run-wave/` and the `Agent` tool subagents deliver.
- **Memory** is the `~/.claude/memory/` protocol documented in `AGENTS.md ## Memory` (verified — the six-entity layout is authoritative).

What the harness does *not* have as a documented pattern:

- **Compaction guidance** for authors of long-running loops (`run-loop`, `planning-loop`). Both today rely on the model's default context handling; there is no `skills/_shared/context/` module or reference doc.
- **Tool-result clearing** guidance.
- **Stack-based memory** convention beyond the six-entity flat model.

### Concrete change

**None today.** The harness has no active context-length pain point (no reports of `run-loop` or `planning-loop` blowing context; no operator complaints in `parking_lot.md`). Codifying compaction / tool-clearing / stack-memory conventions ahead of pain would be speculative architecture.

If pain surfaces — a long `run-loop` session that OOMs on context, or a `planning-loop` iteration that loses early spec constraints — that is the moment to draft `skills/_shared/context/COMPACTION.md` and cite this post.

### Expected payoff

Zero today. Latent — a canonical reference to point at when the first context-length failure arrives. Cost of *deferring*: near-zero (the post's URL is in this file, indexed by the tracker).

**Verify before applying:** `ls skills/_shared/context/ 2>&1` should return "No such file or directory" (verified 2026-07-22 — `skills/_shared/` contains `classifier/`, `loop/`, and one `.gitkeep`-adjacent tree, but no `context/`). If a `context/` module has been added, re-scope this § to review the module against the post's five levers rather than propose a new one.

**Recommended verdict:** defer until context-length pain surfaces. **scope: speculative** — Anthropic's guidance is solid, but adopting it as harness convention ahead of a real failure would violate the CLAUDE.md rule against *"designing for hypothetical future requirements."*
**Status:** PENDING — awaiting triage in PR review

## 5. Six-step code-migration playbook — potential new `/migrate` skill

**Source:** [How Anthropic runs large-scale code migrations with Claude Code — Claude Blog, 2026-07-16](https://claude.com/blog/ai-code-migration)

### Why it's relevant

The post describes a **six-step framework** Anthropic engineers used to migrate real codebases (Bun from Zig to Rust; a 165k-line Python→TypeScript port over a weekend):

1. **Set up the arbiter** — a designated agent that decides when a batch is "done".
2. **Write the rulebook** — living document of translation conventions. *"When a reviewer keeps catching the same mistake across files, the fix isn't per-file. You add one sentence to the rulebook and regenerate the affected batch."*
3. **Map the dependency graph** — deterministic dependency map lets the orchestrator group related files, identify foundational packages, and decide which batches can be translated simultaneously.
4. **Create a gap list** — what the destination language/framework can't express directly.
5. **Trial run** — small-scale stress test to identify rule failures before scaling.
6. **Scale to thousands of files** with parallel subagents; grader loops each batch back until it meets the rulebook.

The harness already ships a `migration-check` skill (verified — `skills/migration-check/SKILL.md` exists) and a `deploy-check` skill. But `migration-check` is about *verifying migrations exist and apply cleanly* (schema migrations, config migrations), not about *executing large-scale source-language ports*. The post's framework is a different problem shape and is not implemented anywhere in the harness.

The framework is architecturally non-trivial:

- **Arbiter** is a new agent role — bounded reviewer role with rule-writing authority.
- **Rulebook regeneration loop** is a new control-flow shape — findings feed back into a rules doc that regenerates upstream batches.
- **Deterministic dependency map** is a new tooling requirement — the harness doesn't currently model per-file dependencies as a graph.
- **Parallel batch dispatch with per-batch gating** overlaps with `run-wave` and `run-loop` but has different semantics (rulebook feedback, not merge feedback).

### Concrete change

**Do NOT implement this incrementally.** The framework has enough moving parts (arbiter role, rulebook doc format, dependency-map format, batch coordinator, grader feedback loop) that ad-hoc file-by-file adds would create the same shape as `run-loop` but with subtly wrong invariants. The right path is:

1. Run `/spec-planner` with a prompt like: *"Design a `/migrate` skill that adopts Anthropic's six-step large-scale-code-migration framework (arbiter, rulebook, dependency map, gap list, trial run, scaled batches). Deliverable: a spec under `docs/specs/YYYY-MM-DD-migrate-skill.md` that defines the arbiter agent's authority, the rulebook format, the dependency-map generator, and how the batch-dispatch loop relates to `run-wave` / `run-loop`."*
2. Only after that spec exists and passes review — schedule as a wave.

**Prerequisite check first** before even the spec pass: does this repo (or a consumer project of this harness) have a real upcoming migration that would use `/migrate`? If no consumer has an active migration project, this spec is architecture without a customer — better to wait until a real migration lands than build the skill speculatively.

### Expected payoff

*If* a consumer project needs a large-scale migration: substantial (the framework is genuinely reusable, and Anthropic's own numbers — 1M lines in <2 weeks with 100% test pass — are the strongest proof of methodology in this window). *If* no consumer has an active migration: zero and the spec would be shelfware.

**Verify before applying:** `ls skills/ | grep -i migrat` should return only `migration-check` (verified 2026-07-22 — no `migrate` or `migration-playbook` skill exists). If a `/migrate` skill has been added, this § collapses to "compare the implementation against the six-step framework and file any deltas."

**Recommended verdict:** spec — the methodology is concrete and unambiguously reusable, but wiring it as a harness skill is architecturally non-trivial (arbiter role, rulebook regen loop, dependency-map format, batch-vs-wave semantics) and deserves a `/spec-planner` pass — gated on a real consumer migration.
**Status:** PENDING — awaiting triage in PR review

## 6. "How we contain Claude" — 93% approval-fatigue figure + egress-proxy lesson

**Source:** [How we contain Claude across products — Anthropic Engineering, 2026-05-28 (McGuinness, Grace, De Jonghe, Eaton, Ribbink)](https://www.anthropic.com/engineering/how-we-contain-claude) (external analysis: [simonwillison.net, 2026-05-30](https://simonwillison.net/2026/May/30/how-we-contain-claude/))

### Why it's relevant

The Anthropic containment post is one of the most substantive engineering write-ups of the window. Two harness-touching findings:

1. **Approval fatigue is real: users approved 93% of Claude Code permission prompts, and the more they saw, the less attention they paid.** This is the empirical basis Anthropic used to justify Auto Mode (the two-stage Sonnet 4.6 classifier that auto-approves safe tool calls).
2. **Anthropic's own custom egress proxy broke twice.** A `endsWith()` vs `getaddrinfo()` parser differential affected every Claude Code release from v2.0.24 through v2.1.89 — silently patched in v2.1.90 (2026-04-01) with no security note.

The 93% figure is the *cited empirical basis* for the harness's already-applied 2026-05-08 §1 (Auto Mode + hooks layering in `setup-harness`). Re-citing it here would be duplicative. The egress-proxy lesson lives at the Claude Code *product* level (a bug in Anthropic's own proxy, not in a harness user's config); the harness has no matching surface — it does not run its own egress proxy.

There is one *very* speculative harness angle: the loop protocol's worktree lane (`AGENTS.md` line 113) documents that secret-bearing worktree items require *"default-deny outbound egress (only an operator-declared host allowlist plus loopback; the git remote is not auto-allowed)."* If a future consumer implements that egress allowlist via a Cloudflare-Workers-style hostname-suffix check (which is what tripped Anthropic), the parser differential lesson would apply. But that is a hypothetical implementation detail — no code today.

### Concrete change

**None.** The one actionable insight (approval fatigue → Auto Mode) is already applied. The egress-proxy lesson has no harness surface today. Marking this as a bookkeeping row.

Optional: append one bullet to the README's "Why Not Superpowers" evidence list (if it still exists — verify below) linking this post as evidence that Anthropic itself treats agent containment as a serious engineering surface. That is a marketing/positioning touch, not a methodology change.

### Expected payoff

Zero today (the applied §1 already extracts the value). Latent — if the harness ever grows an egress allowlist for the loop's secret-bearing lane, this post's parser-differential lesson becomes relevant reading.

**Verify before applying:** `grep -n "93%\|approval fatigue\|how-we-contain-claude" anthropic-reviews/*.md skills/**/SKILL.md README.md` should show the 93% figure only inside prior review files (verified 2026-07-22 — cited via context in 2026-05-08 §1). If a new occurrence has appeared in a skill or in `README.md`, re-read before adding another.

**Recommended verdict:** reject — the actionable insight (93% approval-fatigue → Auto Mode) was already extracted and applied in 2026-05-08 §1 (commit 8b5b12a); the egress-proxy lesson has no harness surface today; the parser-differential lesson is latent behind a speculative feature.
