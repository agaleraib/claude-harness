## 1. Fold containment thinking into README references + a session-start trust-gate note

**Source:** [How we contain Claude across products — anthropic.com/engineering, 2026-05-25](https://www.anthropic.com/engineering/how-we-contain-claude). Companion to the 2026-03-25 [auto mode engineering post](https://www.anthropic.com/engineering/claude-code-auto-mode) already captured as 2026-05-08 §1.

### Why it's relevant
The containment post is the first Anthropic engineering piece that pulls together an explicit methodology — *isolation and deterministic environment boundaries carry most of the weight; approval prompts are fallible* — and lists concrete patterns a harness author can adopt. Several of its 10+ patterns map onto surfaces this repo already has:

- **Session-start scan of persistent context.** The post says *"CLAUDE.md files, memory, and workspace state reload every session, so scan them at session start."* This repo has `skills/session-start/SKILL.md` which currently reads `.harness-profile`, `plan.md`, `parking_lot.md`, and `last_exit.md` for *orientation*, not for *trust*. There is no step that treats project-local `CLAUDE.md` / `.claude/settings.json` / memory as untrusted input before use (`grep -rn "trust\|canary\|untrusted" skills/session-start/SKILL.md` returns nothing).
- **Treat repo-local config as untrusted input.** The post notes hooks in `.claude/settings.json` run before the trust prompt. The harness already ships `scripts/git-hooks/dispatch.sh` and a `fewer-permission-prompts` user-level skill; nothing in the harness docs frames `.claude/settings.json` additions as "capability grants" the way the post does.
- **Canary strings.** Not present anywhere in the repo (`grep -rin canary .` returns zero in-repo hits).
- **Vet remote and third-party tools.** The harness distributes skills via symlink and doesn't actively endorse remote MCP servers; this is already conservative. A one-line AGENTS.md callout would make the choice legible.

Full architectural change (sandbox profile, canary scaffolding, trust-gate step inside `session-start`) is a design-pass question — SPEC-shaped if the maintainer decides to pursue it. **This § only proposes the two cheapest, non-controversial touches:** a README reference entry and a one-paragraph note on the `session-start` skill. The bigger spec is explicitly flagged below as speculative follow-up.

## 2. Document cloud-session interaction in `INSTALL-FOR-COLLEAGUE.md` and `setup-harness`

**Source:** [Claude Code in the cloud: a field guide to cloud sessions — claude.com/blog, 2026-10-06](https://claude.com/blog) (via the Claude Code category listing — the article is served at `claude.dev/blog/claude-code-in-the-cloud/`). Pairs with the [GA announcement](https://www.anthropic.com/news/claude-code-on-the-web) on 2026-09-23 and the authoritative [Claude Code on the web docs page](https://code.claude.com/docs/en/claude-code-on-the-web).

### Why it's relevant
Cloud sessions are no longer research preview. The 2026-10-06 field guide + the docs page describe:

- Each cloud session starts from a **fresh GitHub clone**, not a snapshot of your working directory, so local `.claude/`, personal CLAUDE.md, user-scope MCP servers, and auto-memory stay on your machine.
- Users can configure a **setup script** (`/docs/en/cloud-environments#setup-scripts`) that runs before Claude starts, under a ~5-minute cache window.
- `claude --cloud`, `claude --teleport`, `/web-setup`, and `/autofix-pr` are the user-facing hand-offs between a terminal CLI and a cloud session.

Current state in the repo:

- `INSTALL-FOR-COLLEAGUE.md` (`head -50`) describes a local-only install path ("You need **one** thing: a **Claude account**… you do **not** need to install Node, Git, or anything else by hand"). No mention of `--cloud`, cloud environments, `/web-setup`, teleport, or auto-fix (verified: `grep -n "cloud\|teleport\|web-setup\|auto-fix" INSTALL-FOR-COLLEAGUE.md` returns nothing).
- `skills/setup-harness/SKILL.md` detects project type and copies agents/criteria/CLAUDE.md. It assumes a local filesystem it can write to — which it can, in a cloud session, since the session's VM has its own working tree. But the skill offers no guidance on *persisting* harness scaffolding between cloud sessions (each session starts fresh unless the setup script re-installs).
- The routine running this very session is itself a cloud session: the system prompt tells us *"the container is reclaimed after a period of inactivity"* and *"the repository was cloned fresh when the container started."*

This § proposes **documentation-only** touches. The deeper question — should `setup-harness` ship a cloud-environment-friendly setup script that re-installs the harness symlinks in each new VM? — is a design pass and parked below as speculative.

### Concrete changes

**2a. New section in `INSTALL-FOR-COLLEAGUE.md`** (append before the first `---` separator, or at an appropriate "FYI" position):

```diff
+## Running in Claude Code Cloud Sessions
+
+Since September 2026 you can also run Claude Code **in the cloud** instead of on your laptop. From a browser at [claude.ai/code](https://claude.ai/code), from the Claude mobile app, or from your terminal with `claude --cloud "your task"`. Each cloud session starts from a **fresh GitHub clone** of your repo, so your personal setup (user-level CLAUDE.md, personal skills, user-scope MCP servers, auto-memory) **stays on your laptop and does not travel to the cloud session**.
+
+What this means for the harness:
+
+- The harness's project-level files (`.harness-profile`, `plan.md`, `.claude/agents/`, `criteria/`) *do* travel, because they're in the repository.
+- The user-level skills this repo ships to `~/.claude/skills/` **do not** travel. If you want the same skills available inside a cloud session, either (a) run the harness skills from the project checkout (project-scope skills in `.claude/skills/` are picked up), or (b) configure a [cloud-environment setup script](https://code.claude.com/docs/en/cloud-environments#setup-scripts) that re-installs them.
+- Follow-ups to a running cloud session can be sent with `claude -p "message" --cloud <session-id>` from any machine where you're signed in.
+- `/autofix-pr` can also auto-watch a PR Claude just created and respond to CI failures and reviewer comments inside a cloud session.
+
+If you only use Claude Code locally today, this is informational — nothing in the installation above changes.
```

## 3. Note mods vs. skills/agents/hooks mental model in `AGENTS.md`

**Source:** [Customize Claude Code with mods — claude.com/resources, 2026-10-01](https://claude.com/resources/articles/claude-code-mods). Pairs with the [Getting started with Claude Code mods](https://claude.com/blog) tutorial on the same date.

### Why it's relevant
Mods are a new primitive sitting next to skills, agents, hooks, and plugins. From the source:

- A **mod** is a small TypeScript function that hooks into a specific event: a tool call, a permission request, or drawing part of the screen.
- Mods can **rewrite prompts, block/retry tool calls, approve/deny permissions, redact secrets from tool output, replace UI elements**.
- The post explicitly says hooks "can't rewrite events, draw new UI, or replace features" — this is the capability frontier that distinguishes mods from the harness's existing primitive set.
- Mods ship inside plugins and run with full machine access (not sandboxed).

Current state in the repo:

- The harness's "extension points" are documented across `AGENTS.md`, `CLAUDE.md`, and `README.md`. None of them mention mods (`grep -rn "mod\|mods\|/plugin" AGENTS.md CLAUDE.md README.md | grep -v -E "model|method|module|modify|modern"` returns nothing on-topic).
- The available-skills list surfaces a user-level `plugin-authoring` skill ("Make a mod: a change to Claude's own interface or behaviour…") — so a mod-authoring workflow is reachable, but the harness-side mental model that tells a maintainer *when* to reach for one is missing.
- The harness ships 0 mods. There is no concrete hook today that only a mod could provide (hooks + skills + agents cover the current surface area).

The post's capability frontier matters because future harness improvements that need to **rewrite a prompt in-flight**, **redact a specific secret from tool output**, or **draw a session-specific status indicator** have no clean home today — they'd be jammed into a hook (which can observe but not rewrite) or shelved. Captu­ring the delineation preserves the shape of a future decision.

### Concrete change

**One short subsection added to `AGENTS.md`** in the extension-points area (search for the section that enumerates skills/agents/hooks and insert; if no such section exists, add one at the end of the file):

```diff
+### Extension primitives — when to reach for which
+
+The harness composes four Claude Code extension primitives. In increasing power:
+
+| Primitive | Can observe | Can rewrite events | Can draw UI | Scope |
+|---|---|---|---|---|
+| **Skill** | Prompt → model | No (static content) | No | Markdown instructions loaded on-demand |
+| **Agent** | Full subagent context | Within own context | No | Spawned via Agent/Task tool |
+| **Hook** | Tool call / lifecycle event | No | No | Shell command gating a tool call |
+| **Mod** ([2026-10-01](https://claude.com/resources/articles/claude-code-mods)) | Tool call / permission / UI event | Yes (block/retry/rewrite) | Yes | TypeScript function shipped in a plugin |
+
+The harness currently ships skills, agents, and hooks. No mods today. Reach for a mod only when the behavior you need requires **rewriting a tool-call result, approving/denying a permission non-interactively, redacting secrets from tool output, or replacing a built-in UI element** — anything a hook can observe but not change. Mods are not sandboxed, so install only from trusted sources (see 2026-05-25 containment post, [How We Contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)).
```

### Expected payoff
- Zero code change; makes the next "I need to redact X from Y's output" question answerable from `AGENTS.md` instead of a web search.
- Keeps the harness's documentation current with the Claude Code extension surface.

**Verify before applying:** `grep -rn "mods\|/plugin" AGENTS.md CLAUDE.md README.md` — if there's already a mods section, drop this §.

**Recommended verdict:** defer until a specific mod is needed
**Status:** PENDING — awaiting triage in PR review

Rationale for defer rather than apply: this is pure "future map" documentation. No current harness user has asked where mods fit, and the table risks going stale before anyone consults it. If a maintainer-driven feature later needs to rewrite a tool-call result or redact secrets, promote to apply at that point and re-check the four-column comparison against the then-current docs.
