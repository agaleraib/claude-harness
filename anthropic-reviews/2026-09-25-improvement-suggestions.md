## 4. Reconcile the orchestrator's per-subagent model-switching with the "pick model at start" cache principle

**Source:** [Coding sessions are longer and use more context — Claude Opus 5.5 is built with that in mind — claude.com/blog, 2026-09-24](https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context). Key claim: *"Forked subagents now inherit parent cache rather than re-reading identical content."* Companion claim: *"Pick your model at the start of a session rather than switching midway."*

### Why it's relevant

The orchestrator (`.claude/agents/orchestrator.md`) is designed around **per-task model dispatch**:

- Read the task shape (line 142 table).
- Pick a model (`haiku-4.5 / sonnet-4.6 / opus-4.7`).
- Spawn a subagent with that model in a worktree (Step 5, lines 190–208).
- On verify failure, escalate one rung — sometimes across model boundaries (`sonnet → opus`, line 246).

That design predates two 2026-Q3 realities the 5.5 post makes explicit:

1. **Cache inheritance:** a forked subagent that picks the *same* model as the parent inherits the parent's cache. A forked subagent that picks a *different* model does not — it starts a fresh cache lifecycle. So the current orchestrator, by dispatching Haiku for a typo and Opus for a refactor in the same wave, gets **worse** cache economics than a wave that runs everything on the parent's model.
2. **Effort-adjust-without-cache-reset:** on Opus 5.5 and Fable 5.1 the operator can move `/effort` up and down mid-run without invalidating cache. That means the harness's *effort* escalation ladder (low → medium → high → xhigh) is cheap; its *model* escalation ladder (sonnet → opus) is expensive.

The tension isn't "the orchestrator is wrong." It's "the cost/benefit trade-off of routing to different models has shifted." A Haiku call that finishes a typo in 3 seconds and no cache is still probably worth it. But a Sonnet call in the middle of an Opus wave, dispatched only because the task is "standard CRUD," might not be — the cache-miss cost eats the per-token savings.

### Why this is `spec`, not `apply`

Every option here touches a load-bearing agent that runs waves autonomously and logs to `.harness-state/orchestrator.jsonl`. Concrete design choices to make:

1. **Should the orchestrator prefer the parent's model when the task is small enough for the parent to just do it?** (Same-model + inherit cache vs. spawn Haiku + fresh cache.) This inverts today's rule 1 in the effort table.
2. **Should the escalation ladder skip Sonnet when the parent is Opus 5.5?** (Today's `sonnet → opus` promotion doesn't apply if the parent already runs Opus; the current ladder assumes the orchestrator itself runs Opus.)
3. **Should Fable 5.1 appear as an *advisor* tier the way the models-explained post recommends** (Sonnet worker + Fable advisor)? The harness has no advisor pattern today; adding one is a real refactor.
4. **Cost telemetry:** Surface B (JSONL) logs `model` and `effort` per decision. Should it also log a `cache_state: inherit | fresh` field so audits can see when the router chose to break cache?

None of these are wrong. All are non-trivial. All want a spec document, not a diff. `/spec-planner` is the right rung.

### Concrete change (spec-first)

None this run. When/if the maintainer picks this up:

1. `/spec-planner` on the tension above; output `docs/specs/2026-Q4-orchestrator-cache-aware-routing.md`.
2. Decision points for the spec: (a) same-model-first vs. always-route rule; (b) effort-only vs. model+effort escalation; (c) advisor-tier pattern; (d) cache_state telemetry field on Surface B.
3. Consider whether `.harness-profile` needs a `model_routing.prefer_parent_model: bool` toggle to opt into the new behavior without breaking existing wave logs.
4. Add a §4 follow-up here or in the resulting spec that cites 2026-04-19 §5 (Agent Evals, DEFERRED) — an eval fixture that measures cache-hit % across the two routing strategies would settle the design question empirically rather than by argument.

### Expected payoff (when applied)

## 5. Bookkeeping: note the Frontier Red Team's multi-agent failure modes in the orchestrator's design rationale

**Source:** [Patterns and problems in emerging multiagent systems — anthropic.com/research, 2026-08-13](https://www.anthropic.com/research/patterns-and-problems-in-emerging-multiagent-systems). Four failure modes named: (1) coordination breakdown, (2) conformity cascades, (3) epistemic fragility, (4) goal-incompatibility escalation.

### Why it's relevant

The harness's runtime orchestrator uses a **multi-agent-adjacent** pattern: one central Opus orchestrator dispatches worker subagents (Haiku / Sonnet / Opus depending on task), with occasional `isolation: "worktree"` parallelism for independent siblings. The Frontier Red Team paper describes the failure modes that show up when *multiple agents share resources and negotiate outcomes*. The harness dispatches at most one sibling per task path, so most failure modes don't apply as directly. But three points from the paper *do* map onto orchestrator design decisions worth noting:

- **Conformity cascades** (identical prompts → identical decisions, e.g. 18 of 30 agents naming the same branch): the orchestrator dispatches with identical prompt scaffolding across sibling worktrees. If two parallel siblings ever converge on the same branch name or file path, it's this pattern in miniature. Mitigation: the orchestrator already forces `isolation: "worktree"` and unique task IDs; that's the sound direction.
- **Epistemic fragility** (agents either over-trust sources or dismiss dissenters): the code-reviewer agent runs adversarial-by-design, which is the paper's recommended posture. The current `code-reviewer` prompt is already dissent-friendly ("catch what self-assessment misses") — worth citing the paper as external validation.
- **Coordination breakdown** (agents avoid interdependent work by siloing): the harness dispatches each sub-task independently and lets the operator (or `/close-wave`) reconcile. Same avoid-siloing risk in principle; the operator-in-the-loop currently mitigates it.

None of this is a bug in the harness. It's a citation opportunity — the same shape as 2026-04-25 §1 (a Claude Code postmortem cited as *evidence for the harness's lean-context thesis*).
