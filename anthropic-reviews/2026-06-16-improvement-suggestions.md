## 2. Adopt Dynamic Workflows / `~/.claude/workflows/` alongside `/run-loop` and `/run-wave`

**Source:** [A harness for every task: dynamic workflows in Claude Code — claude.com/blog, 2026-05-27](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Shipped alongside Opus 4.8 (May 28). Key features per the post: Claude writes a JavaScript orchestration script at runtime; a Claude Code runtime executes it in the background; up to ~1000 subagents per workflow; per-task token budgets ("use 10k tokens"); workflows save with `s` in the workflow menu to `~/.claude/workflows/` or distribute via a skill (drop JS files in the skill directory and reference from `SKILL.md`); pair with `/loop` for repeats and `/goal` for hard completion gates.

### Why it's relevant
The harness already operates **three skills with the shape of a workflow**:
- `skills/run-loop/SKILL.md` — pluggable implement/review backends, the Wave 21 production composition root (`skills/_shared/loop/run-loop-prod-deps.ts`), TypeScript driver loop.
- `skills/run-wave/SKILL.md` — spec→wave dispatch, parallel subagent dispatch within a wave.
- `skills/planning-loop/SKILL.md` — planner → generator → evaluator loop (the very pattern Dynamic Workflows generalizes).

Anthropic's Dynamic Workflows is **the same shape, productized**: a runtime-emitted JS script that spawns subagents, with the saved-workflow convention (`~/.claude/workflows/` / skill-bundled JS files) that maps cleanly onto the harness's `skills/_shared/loop/` TypeScript engine. The Anthropic implementation is conceptually adjacent enough that it deserves a deliberate decision: **adopt, mirror, or ignore**.

### Why this is `defer`, not `apply`

1. **Just shipped (May 27, 2026)**. Public-API surface, persistence semantics, and skill-distribution conventions for `~/.claude/workflows/` aren't yet documented in the Claude Code reference. Same pattern as 2026-05-10 §2 (Cloud Routines) — wait a quarter for ergonomics to settle.
2. **Conceptual overlap, not duplication**. Dynamic Workflows are *single-session, ephemeral, Claude-emitted JS*; `run-loop` is *multi-session, on-disk TypeScript, hand-authored with tests* (`skills/_shared/loop/test/`). Different lifecycles, different audiences (Dynamic Workflows for ad-hoc Claude-driven orchestration; `run-loop` for codified harness behavior).
3. **Cost shape unclear**. The "use 10k tokens" budget hint plus up-to-1000 subagents implies the cost envelope of a Dynamic Workflow run is much higher than a `run-loop` cycle. Need a real harness task that *needs* 100+ parallel subagents before adopting — and the harness's largest concurrent fan-out today is ~5–10 (per the Wave 21 driver).
4. **Speculative for solo tooling**. The `/loop` + `/goal` pairing the post recommends maps onto the harness's `/run-loop --until` + `/goal` setup already; no behavior change for the maintainer's current scope.

### Concrete change (deferred)

None this run. When/if the maintainer wants to take this on, the smallest concrete experiment is:

1. Pick one existing skill where a workflow would be a natural fit (candidate: `skills/triage-parking/SKILL.md` — many small subtasks, each independent).
2. Author a JS workflow file under `skills/triage-parking/workflow.js` and reference it from SKILL.md, per the post's "distribute via a skill" pattern.
3. Compare to the current prose-driven SKILL.md flow on the same triage task — does Claude actually pick the workflow up reliably, and does it produce a better triage trace?
4. Only then decide whether to introduce a harness convention (e.g. `workflows/` in the project root alongside `.harness-state/`) or stay with the current skill-as-prose pattern.

The harness's existing `run-loop` engine is **not** a candidate for replacement — it's hand-authored with a real test suite and benefits from persistence across sessions, which Dynamic Workflows don't yet promise.

### Expected payoff (when applied)
A productized version of the planner→generator→evaluator pattern that's natively understood by every Claude Code session — fewer prose instructions, more deterministic structure. But only worth the migration if the on-disk TypeScript loop becomes a maintenance burden or if a real fan-out >50 use case shows up.

**Verify before applying:**
1. `grep -rn "Dynamic Workflows\|~/.claude/workflows" /home/user/claude-harness` — must return nothing today; if it returns hits, exploration has already started and this § needs an update.
2. Confirm `~/.claude/workflows/` is still the documented save location for Dynamic Workflows (the May 27 post says press `s` in the workflow menu — verify the path hasn't changed in subsequent Claude Code releases).
3. Re-check Anthropic's release notes for any Dynamic-Workflows-related guidance for skill authors — if Anthropic publishes a "workflows for skill authors" follow-up, that's the cue to revisit.
4. Confirm the harness's `run-loop` engine still hasn't hit the fan-out pain (no PR asks for parallel-subagent expansion). If the production composition root in `skills/_shared/loop/run-loop-prod-deps.ts` adds a >10-way fan-out, that's the cost-shape trigger to re-evaluate.

**Recommended verdict:** defer until Dynamic Workflows API stabilizes AND the harness has a >50-fan-out use case — same disposition as the Cloud Routines deferral (2026-05-10 §2). The on-disk TypeScript loop pays its own way today; switching costs aren't worth it on speculation.

## 3. Trim `close-wave/SKILL.md` (675 lines) and `planning-loop/SKILL.md` (705 lines) below the 500-line guideline using progressive disclosure

**Source:** [Lessons from building Claude Code: How we use skills — claude.com/blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills). Key claim: SKILL.md should be a **routing table** that points to deeper material in sibling files (e.g. a "stuck jobs" subroutine lives in `stuck-jobs.md`), not a single-file methodology dump. Concrete number from the post: a project with 8 skills consumes ~500 tokens at startup vs ~70,000 if all skill bodies were always loaded — and at any moment an agent typically has *one* skill body + *one or two* reference files loaded.

### Why it's relevant
The harness already endorses this pattern in two places:

- `skills/skill-creator/references/anthropic-skill-authoring.md` (vendored 2026-06-16) — *"under-500-line body rule, progressive disclosure"*.
- `skills/skill-creator/SKILL.md` — points authors at the vendored reference before writing.

But two existing skills exceed the recommended body length:

```
$ wc -l skills/*/SKILL.md | sort -n | tail -4
   488 skills/skill-creator/SKILL.md
   675 skills/close-wave/SKILL.md
   705 skills/planning-loop/SKILL.md
  5954 total
```

(All other 22 skills are at or under 488 lines; `skill-creator` is right at the limit.)

`planning-loop` already has a `references/` subdirectory (`references/codex-prompts.md`, `references/rules.md`), so the *infrastructure* for progressive disclosure exists — the body just hasn't been decomposed yet. `close-wave` has no `references/` subdir at all.

### Why this is `spec`, not `apply`
This is **two substantive SKILL.md rewrites**, each touching a skill that drives a critical phase of the harness flow:

- `close-wave` is invoked at the end of every wave by `/run-wave`'s tail; it owns the reconcile/archive/plan-update protocol that gates the next wave starting cleanly. Behavior change here can mute a wave-close failure mode.
- `planning-loop` is the planner→generator→evaluator loop's executor; it's invoked from `/run-wave` and from `/planning-loop` directly. It carries decisions that shape how Wave 21's `_shared/loop/` engine was designed (see `references/rules.md`).

Trimming the bodies isn't a text-swap — it requires:
1. Identifying which sections are routing decisions (stay in SKILL.md) vs. step-by-step procedures (move to `references/<step>.md`).
2. Adding pointer language so Claude knows when to load each ref file (the "stuck-jobs.md" pattern from the post).
3. Re-verifying that the routing-table version still produces the same close-wave / planning-loop trace on a sample wave.

Per the README's "Decompose first, then route" rubric: this hits **promotion signal #2** (touches in-flight or existing mechanisms) and **promotion signal #4** (concrete-changes block spans >5 files once each ref is broken out). It's a `/spec-planner` job, not a `/micro`.

### Concrete change (spec'd, not applied)

The spec would answer:

1. **For `close-wave/SKILL.md` (675 → target <500):**
   - Decompose the current body into routing decisions (when to archive vs. when to leave open; when to reconcile plan-registry vs. when to defer) and step-by-step procedures (the actual archive commands, the reconcile-grep recipes).
   - Extract step-by-step procedures into `skills/close-wave/references/archive-protocol.md`, `references/reconcile-checklist.md`, etc.
   - Leave SKILL.md as a ~250-line routing table that points at each ref file by precondition.
   - Verify the trimmed SKILL.md still triggers reliably on the same `/close-wave` invocations from `/run-wave`.

2. **For `planning-loop/SKILL.md` (705 → target <500):**
   - Already has `references/codex-prompts.md` and `references/rules.md` — decide what else moves out (likely: the evaluator-rubric protocol; the generator-iteration loop).
   - Possibly split into two skills if the planner-vs-loop distinction is sharp enough.
   - Verify against the wave-21 cross-model review protocol that the planning-loop body still routes correctly.

3. **For `skill-creator/SKILL.md` (488 — at the limit):**
   - Note only — not in scope for this spec. Watch list. If the next change pushes it past 500, fold in.

### Expected payoff
Token-budget headroom at session start (concretely: 705 + 675 - ~500 = ~880 lines / ~7K tokens of skill bodies that don't need to be in the system prompt unless the skill is actively invoked). Cleaner separation between routing and procedure that makes future edits less risky. Aligns the harness's actual SKILL.md sizes with the pattern the vendored `anthropic-skill-authoring.md` already documents.

### Why not just trim by hand?
Because both skills are in the critical path of the wave protocol and the failure mode of an over-trimmed SKILL.md is invisible until a wave closes badly (or fails to close). The `/spec-planner` design pass forces an explicit map of "which sections are routing decisions" before the cuts happen — and produces the verification recipe for "did the routing still work".

**Verify before applying:**
1. `wc -l skills/close-wave/SKILL.md skills/planning-loop/SKILL.md` — must still show >500 lines each. If either has already been trimmed, the corresponding half of the spec is moot.
2. `ls skills/close-wave/references/ 2>/dev/null && ls skills/planning-loop/references/ 2>/dev/null` — confirms whether the `references/` infrastructure is in place. Today: `planning-loop/references/` exists; `close-wave/references/` does not.
3. `grep -c "under-500-line\|progressive disclosure" skills/skill-creator/references/anthropic-skill-authoring.md` — confirms the harness's own vendored guidance still endorses the trim direction. Today: matches both terms.
4. Confirm the "Lessons from building Claude Code: How we use skills" post hasn't been superseded by guidance that *raises* the body-line ceiling (e.g. if Anthropic later publishes "SKILL.md can be up to 1000 lines for sufficiently routing-table-shaped skills"). If so, drop this §.

**Recommended verdict:** spec — substantive refactor of two critical-path skills; decompose-then-route is the right discipline before edits. The June 3 post is *new* evidence for an existing harness-internal pattern (the vendored guidance), so the §'s direction is well-anchored even if the spec defers the actual cuts.
