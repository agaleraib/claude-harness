## 2. Cite "How we contain Claude across products" as first-party validation of `safety/egress.ts`

**Source:** [How we contain Claude across products — anthropic.com/engineering, ~2026-05-30](https://www.anthropic.com/engineering/how-we-contain-claude). Independent index entry confirming the publication date: [Simon Willison, 2026-05-30](https://simonwillison.net/2026/May/30/how-we-contain-claude/).

### Why it's relevant
Anthropic's engineering post argues that **environment-level containment** (sandboxes, egress controls, filesystem boundaries) is the right defense against agent over-reach — *not* per-action supervision, because users habituate to permission prompts (telemetry: ~93% approval rate). Their concrete claim: "the only defense that holds in certain situations is the environment, specifically egress controls that block requests regardless of intent and filesystem boundaries that keep credentials out of reach in the first place."

The harness already implements exactly this posture for secret-bearing items in the run-loop:

- **`skills/_shared/loop/safety/egress.ts:1–22`** is the canonical Wave 20 Task 11a module. Its header documents three controls verbatim:
  - (A) Default-deny outbound egress with a `worktree_egress_allowlist:` declaration; refuses to run if no OS-level egress mechanism exists (no silent open-network fallback with live secrets).
  - (B) Per-item pre-execution approval (operator approval token; never silent dispatch).
  - (C) Task-scoped credential injection (only what the item declares in `secrets:`).

These three controls map 1:1 onto Anthropic's published containment thesis — built independently, six weeks before the engineering post. That's a nice coincidence to anchor in writing so the design doesn't drift back toward "just trust the agent" later.

## 3. Add a "skills vs subagents" decision pointer to `skill-creator/SKILL.md`

**Source:** [Steering Claude Code: skills, hooks, subagents and more — claude.com/blog, 2026-06-18](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more). Anthropic's first dedicated comparison of the seven instruction surfaces (CLAUDE.md, rules, skills, subagents, hooks, output styles, appended system prompt) with explicit guidance on when each applies.

### Why it's relevant
The harness ships **both** skills (`skills/`, ~26 entries) and subagents (`.claude/agents/`: `code-reviewer`, `orchestrator`, `project-tracker`, `spec-planner`, `generator`, `ui-evaluator`). A skill author following `skill-creator/SKILL.md` today gets clear guidance on **how** to write a skill (Capture Intent → Interview → SKILL.md → progressive disclosure), but **zero guidance** on the prior question: *should this be a skill at all, or a subagent?*

Anthropic's post answers that question crisply:

> Use a skill when you want the procedure to play out inside the main thread so you can see and steer each step. In contrast, use a subagent when a side task like deep search, a log analysis pass, or a dependency audit would clutter your main conversation with intermediate results you won't reference again.

That's the exact decision a `skill-creator` user is making at step 1 — *Capture Intent* — but currently has to figure out from outside the harness. The harness's own conventions already align with the post (subagents in `.claude/agents/` are explicitly for context-isolating side tasks: `code-reviewer` reads diffs and reports findings; `spec-planner` runs an interview and writes a spec; `project-tracker` saves to Second Brain). But the alignment isn't documented anywhere skill authors will see it.

### Concrete change

**One paragraph inserted into `skills/skill-creator/SKILL.md`, immediately after the *Capture Intent* heading at line 47**, before the existing four numbered questions:

```diff
 ### Capture Intent

 Start by understanding the user's intent. The current conversation might already contain a workflow the user wants to capture (e.g., they say "turn this into a skill"). If so, extract answers from the conversation history first — the tools used, the sequence of steps, corrections the user made, input/output formats observed. The user may need to fill the gaps, and should confirm before proceeding to the next step.

+**Skill or subagent? Decide before writing.** A skill plays out inside the main conversation so the user can see and steer each step; a subagent runs in its own context window and only its final message returns to the main thread. Per Anthropic's [Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more) (2026-06-18): *"Use a skill when you want the procedure to play out inside the main thread so you can see and steer each step. … Use a subagent when a side task … would clutter your main conversation with intermediate results you won't reference again."* If the workflow produces intermediate output the user won't reread (deep search, log analysis, multi-file diff review, rubric scoring), it's a subagent — put it in `.claude/agents/` and stop here. Examples already in this harness: `code-reviewer` (reads diffs, returns findings), `spec-planner` (runs interview, returns spec), `project-tracker` (saves session, returns confirmation).

 1. What should this skill enable Claude to do?
 2. When should this skill trigger? (what user phrases/contexts)
```

That's the entire change — one paragraph, no other edits. The `skill-creator` flow's downstream steps (Write the SKILL.md, Progressive Disclosure, Skill Writing Guide) are untouched.

### Expected payoff
- Catches the "this should have been a subagent" mistake at *intent capture* — before the user spends 20 minutes drafting a SKILL.md, evals, and skill-description tuning for something that belongs in `.claude/agents/`.
- Closes a documentation gap that's currently bridged by tribal knowledge ("the harness uses skills for X, subagents for Y") — making it explicit in the place where skill authors land.

### Why this isn't a duplicate

- `README.md:42–73` documents *that* the harness has both skills and subagents but doesn't give skill authors a decision rule for when to write which.
- The 2026-04-19 §3 (Restructure skills around progressive disclosure) is APPLIED and concerns *internal skill structure*, not the skill-vs-subagent choice.

## 4. Bookkeeping: position Dynamic Workflows / `ultracode` alongside the `orchestrator` agent — defer

**Source:** [Introducing dynamic workflows in Claude Code — claude.com/blog, 2026-05-28](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code). ### Why it's relevant
Anthropic's **Dynamic Workflows** (released as research preview on 2026-05-28, with Opus 4.8) is the Anthropic-native version of a pattern the harness's **`orchestrator`** agent already implements: spawn parallel subagents with worktree isolation, wait for completion, synthesize results. Concrete overlap with `.claude/agents/orchestrator.md`:

| | Harness `orchestrator` | Anthropic Dynamic Workflows |
|---|---|---|
| Trigger | `/run-wave N` reads a spec, dispatches tasks | `/effort ultracode` or the keyword `ultracode` in the prompt; Claude plans for every substantive task |
| Parallelism | `isolation: "worktree"` per parallel task (`.claude/worktrees/agent-<id>/`) (`orchestrator.md:202`) | Up to 1000 subagents per session, with internal verification step |
| Decision authority | Spec-driven (tasks listed in spec; orchestrator routes by complexity) | Claude-driven (Claude writes the orchestration script at runtime) |
| Resume | Wave-level: re-`/run-wave` after partial completion | Session-scoped: paused runs resume completed agents from cache |
| Default ON | Only when `model_routing: on` in `.harness-profile` | Default ON for Max/Team/Enterprise; opt-in on Pro |

The pattern's the same shape — just spec-time vs runtime decision authority. This is **exactly parallel** to the 2026-05-10 §1 framing of the local `code-reviewer` vs Anthropic's hosted `/ultrareview` (different layers, complementary).

### Why this is `defer`, not `apply`

1. **Research preview.** Dynamic Workflows landed on 2026-05-28 as a research preview; the 1000-subagent ceiling, the `/config` opt-in mechanics on Pro, and the cost shape are still settling. The 2026-04-19 §2 Brain/Hands deferral cited the same "wait for the surface to stabilize" reason for Managed Agents — same logic here.
2. **No actual conflict today.** The harness's `orchestrator` runs spec tasks via `/run-wave`; nothing in the harness *competes* with `ultracode` for the same trigger surface. A user can have both — `/effort ultracode` for codebase-wide bug hunts in Claude Code's main session, `/run-wave` for spec-driven phase builds — without overlap.
3. **The "when to use which" question isn't being asked yet.** The 2026-05-10 §1 paragraph on local `code-reviewer` vs cloud `/ultrareview` shipped because the question *was* being asked (every commit invokes the local reviewer; users see `/ultrareview` advertised in the Claude Code system prompt). The orchestrator-vs-ultracode equivalent isn't yet on a reader's radar — `orchestrator` is internal to the `/run-wave` flow, not surfaced at every prompt.
4. **The orchestrator's design assumes spec-time decomposition.** Anthropic's Dynamic Workflows assumes runtime decomposition. They serve different methodologies; conflating them in a README paragraph could mislead a reader into thinking the harness should *replace* `/run-wave` with `ultracode`. The paragraph is easy to get wrong before the patterns are well-understood.
5. **Pro plan opt-in friction.** Dynamic Workflows is on by default for Max/Team/Enterprise; Pro users have to enable it in `/config`. The harness's user base (solo maintainer + colleagues on `INSTALL-FOR-COLLEAGUE.md` path) is plan-mixed; "you can do X with ultracode" guidance in the README would need the "and here's how to enable it" caveat to be useful.

None this run. When/if the maintainer wants to take this on:

Not the case today.

## 5. Cite "Agentic coding and persistent returns to expertise" as evidence for user-as-planner design

**Source:** [Agentic coding and persistent returns to expertise — anthropic.com/research, 2026-06-16](https://www.anthropic.com/research/claude-code-expertise). Authors: Zoe Hitzig, Maxim Massenkoff, Eva Lyubich, Ryan Heller, Peter McCrory. Methodology: privacy-preserving analysis of ~400,000 Claude Code sessions from ~235,000 users between October 2025 and April 2026.

### Why it's relevant
The research's headline findings directly underwrite the harness's session-ritual design:

- **"In a typical session, people make most of the planning decisions (what to do) and Claude makes most of the execution decisions (how to do it)."** Quantified as ~70% planning by humans, ~80% execution by agents.
- **"The greater domain expertise a person brings to a session, the more work Claude does per instruction."**
- **"Success is determined by how well a person understands the problem they are trying to solve, not whether they are trained in coding."**
- Over the 7-month window, **debugging activities within sessions decreased by almost half** while end-to-end agentic use rose.

The harness's design rests on the same premise: the user is the planner (via `session-start` orientation, `today_goal.md`, `current_micro.md`, `spec-planner` interview, parking lot triage), the agent is the executor (via `code-reviewer`, `generator`, `orchestrator`, `/run-wave`). The README's "Why Not Superpowers" section currently makes the argument from *postmortem evidence* (Anthropic harness reduction, April-23 postmortem, vendor-primitive absorption) — adding this research as a fourth evidence bullet shores up the design from the *user-workflow* angle, which the postmortems don't cover.
