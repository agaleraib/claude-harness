## 1. Document Claude Code Agent View cohabitation with `.claude/worktrees/` and the per-worktree `.harness-state/` gotcha

**Source:**
- [Agent view in Claude Code — claude.com/blog, 2026-05-11](https://claude.com/blog/agent-view-in-claude-code) (Code w/ Claude follow-on; research preview ship date)
- [Manage multiple agents with agent view — code.claude.com docs](https://code.claude.com/docs/en/agent-view) (canonical reference for behavior + flags; requires Claude Code v2.1.139+, with subsequent flags landing in v2.1.140–143)
- [What's new — Week 20 (May 11–15)](https://code.claude.com/docs/en/whats-new/2026-w20)

### Why it's relevant

Agent View is the multi-session CLI dashboard that ships with Claude Code v2.1.139. Critical mechanics for harness authors:

1. **Background-session worktree isolation under `.claude/worktrees/`.** From the docs: *"Before editing files, Claude moves the session into an isolated git worktree under `.claude/worktrees/`."* This is the **exact same parent directory** the harness uses today — `/run-wave` creates `.claude/worktrees/agent-<id>/` (verified via `skills/run-wave/SKILL.md:30,351,434` and `skills/close-wave/SKILL.md:12,13,66,145,146,404`). The naming prefixes differ (harness uses `agent-<id>/`; Agent View uses auto-generated short-IDs or `--name`-derived names), so collisions are unlikely *as long as* Agent View doesn't pick an `agent-*` name. But the parent directory is now **shared mutable state**.

2. **`.harness-state/` is per-worktree.** When a user runs `claude --bg "do X"` or presses `←` from a session to background it, the new background session lives in its own `.claude/worktrees/<name>/` worktree, with its **own empty `.harness-state/`**. The main session's `today_goal.md`, `current_micro.md`, `parking_lot.md` baseline, `last_exit.md` — none of those are visible to the background session. A user who `/bg`s "continue today's micro" expecting harness state to follow will silently get a fresh session with no goal context.

3. **`/close-wave`'s cleanup grep is `agent-*`-specific** — that's safe (`skills/close-wave/SKILL.md:145–146,404`), but the harness's own worktree-discipline procedures (Wave 10 retired the legacy `docs/<date>-<project>-wave<N>-summary.md` path) were written **before** Agent View existed. Users adopting Agent View may not realise the harness shares the same parent dir, and may not pin (`Ctrl+T`) or delete (`Ctrl+X Ctrl+X`) their Agent View sessions before running `/close-wave`.

4. **Two opt-outs exist** if the cohabitation becomes a problem:
   - `worktree.bgIsolation: "none"` in `.claude/settings.json` (requires v2.1.143+) — background sessions then edit the working copy directly, no worktree.
   - `disableAgentView: true` setting (or `CLAUDE_CODE_DISABLE_AGENT_VIEW=1`) — turns off the feature entirely.
   - Plus the `←`-opens-agents shortcut can be disabled via `leftArrowOpensAgents` in `/config`.

The harness ships no documentation today on any of this (`grep -rn "claude agents\|agent view\|Agent View\|--bg\b\|/bg\b\|bgIsolation\|disableAgentView\|leftArrowOpensAgents" README.md AGENTS.md skills/ .claude/ procedures/ 2>/dev/null` returns nothing). This is a documentation gap, not a code change.

### Concrete change

**(a) Append a "Coexistence with Claude Code Agent View" subsection to `skills/setup-harness/SKILL.md`** — small note placed after the existing skill-install section. Suggested text:

```markdown
### Coexistence with Claude Code Agent View (v2.1.139+)

Claude Code Agent View (`claude agents`, ships May 11 2026 as research preview)
also writes worktrees under `.claude/worktrees/`. The harness has used that
directory since Wave 1 for `/run-wave`'s `agent-<id>/` worktrees, so the two
mechanisms now share a parent dir. Two practical implications:

1. **`.harness-state/` is per-worktree.** A session backgrounded with `←` or
   `claude --bg` sees its own empty `.harness-state/` — it does NOT inherit
   `today_goal.md`, `current_micro.md`, `parking_lot.md` baseline, or
   `last_exit.md` from the main checkout. Use foreground sessions for
   harness-state-aware work (anything that runs `/micro`, `/park`, or
   `/session-end`), and reserve `/bg` for self-contained tasks like
   "run the test suite, fix any failures" that don't depend on session
   memory.

2. **Worktree naming.** `/close-wave` cleans up `.claude/worktrees/agent-*`
   only — Agent View's worktrees use different prefixes (short-IDs or
   `--name <name>`-derived), so cleanup won't tear down a live Agent View
   session by accident. If you ever need an Agent View session named
   `agent-something`, rename it (`Ctrl+R`) before running `/close-wave`.

If the parent-dir sharing ever becomes a problem (e.g. a harness operation
needs an exclusive `.claude/worktrees/`), opt out per-project in
`.claude/settings.json`:

```json
{ "worktree": { "bgIsolation": "none" } }
```

or disable Agent View entirely with `"disableAgentView": true` /
`CLAUDE_CODE_DISABLE_AGENT_VIEW=1`. For now, the recommended posture is
**coexist; don't opt out** — Agent View is genuinely useful for parallel
exploratory work outside the wave-orchestrator path.
```

**(b) One-line cross-reference in `AGENTS.md`** under the existing protocol section that mentions `.claude/worktrees/` (if any). If none exists, add a one-line bullet to whichever section enumerates harness state directories.

**(c) Optional: update `skills/run-wave/SKILL.md:30` or `:434`** to note that the `.claude/worktrees/agent-<id>/` naming convention is now load-bearing for cohabitation with Agent View (it prevents accidental cross-cleanup). One sentence inline.

### Expected payoff

A future user (or future-you) who adopts Agent View won't lose ten minutes wondering why `/bg`'d sessions can't see today's goal, or why `/close-wave` left worktrees behind. The cost is a ~20-line documentation edit; the benefit is a documented coexistence story before the friction surfaces in practice. The harness's `/run-wave` machinery is unaffected — this is purely about making the parent-dir sharing legible.

The harness's wave-orchestrator already uses `.claude/worktrees/`; the new Agent View feature uses it too. Defer makes sense if a feature is hypothetical or hosted-only; this one is local, opt-in by `←`-keystroke, and immediately available.

## 2. Bookkeep the `/goal` slash command (v2.1.139) overlap with `today_goal.md`

**Source:**
- [What's new — Week 20 (May 11–15)](https://code.claude.com/docs/en/whats-new/2026-w20) — `/goal` section
- [Goals — code.claude.com docs](https://code.claude.com/docs/en/goal) (linked from the Week 20 digest)

### Why it's relevant

Claude Code v2.1.139 introduced `/goal <completion condition>` — a slash command that **sets a completion condition and keeps Claude working across turns until a fast model checks the condition and confirms it holds**. From the digest: *"Useful for substantial work with a verifiable end state, like migrating a module until every call site compiles and tests pass."*

The harness already owns the word **"goal"** in a different semantic register. From `skills/session-start/SKILL.md:172` the session-start ritual writes `.harness-state/today_goal.md` with a one-sentence answer to *"What is today's ONE primary goal?"* The file is consumed by `skills/session-end/SKILL.md:34,47` for the closing summary and cleaned at `skills/session-end/SKILL.md:124`.

These are **different mechanisms**:

| | `/goal` (Claude Code v2.1.139) | `today_goal.md` (harness) |
|---|---|---|
| **Lifetime** | One Claude Code session, until condition met | One day (set at start, cleared at end) |
| **Format** | Verifiable completion condition (predicate) | One-sentence declarative goal (descriptive) |
| **Mechanism** | Programmatic loop; fast model checks each turn | Human-written file; read by session-end ritual |
| **Audience** | The agent (drives looping) | The human (drives focus + closure ritual) |
| **Granularity** | Per-task, often sub-day (e.g. "all tests in test/auth pass") | Per-day, often multi-task (e.g. "ship wave 16 spec") |

They are **complementary, not redundant**. A user could legitimately:
- Set `today_goal.md = "Ship wave 16 spec"` at session-start
- Open `/micro` for the first sub-task
- Inside that sub-task, use `/goal all tests in test/foo pass` to drive a fast iteration loop

But the **name collision** is real: a reader who skims `today_goal.md` and then sees `/goal` in the slash-commands menu may assume they're the same thing or that the harness's convention is now redundant.

### Concrete change (deferred)

Two small touches, when triaged:

1. **Add a one-line "See also" pointer in `skills/session-start/SKILL.md` near line 172** (where `today_goal.md` is written) — something like:

   ```markdown
   > **Note.** `today_goal.md` is the harness's **per-day, human-written** goal,
   > read by `session-end`. It is **not** the same as Claude Code's `/goal`
   > slash command (v2.1.139+), which is a **per-session, programmatic
   > completion condition** that loops Claude until met. The two coexist —
   > use `today_goal.md` for daily focus, `/goal` for verifiable
   > end-state iteration within a micro.
   ```

2. **(Optional)** Add a similar one-line pointer in `skills/session-end/SKILL.md` near line 47 (where the goal is summarized), so a reader who reaches end-of-day from a different entry point also sees the distinction.

### Why this is `defer`, not `apply`

1. **No active confusion to point at.** Nobody has filed a "which goal do I use?" issue yet. The collision is theoretical; the documentation edit is a hedge.
2. **The harness's daily-goal pattern predates `/goal` by months.** A defer-with-context note keeps the option open without spending edit budget on a hypothetical reader.
3. **`/goal` is per-session; `today_goal.md` is per-day.** They are clearly different in lifetime and audience; the overlap is in the name, not the semantics. A one-line note is sufficient if and when a real user reports confusion.

### Expected payoff (when applied)

A reader who lands on `skills/session-start/SKILL.md:172` sees the distinction in one line and doesn't waste cycles wondering if `today_goal.md` is the harness's pre-`/goal` ancestor. Cost: ~5 lines across two files. Benefit: small but durable clarity.

**Verify before applying:**

1. `grep -rn "/goal\b\|today_goal" skills/session-start/SKILL.md skills/session-end/SKILL.md 2>/dev/null` — must still return only the existing `today_goal.md` references and no `/goal` mentions. If `/goal` has been documented, this § is stale.
2. Confirm `/goal` is still the v2.1.139 slash command name (not renamed to `/until`, `/goal-loop`, etc.) before quoting the command in the inline note.
3. Confirm the harness's `today_goal.md` location and consumer skills haven't changed — line numbers will rot, so anchor edits by the surrounding markdown context, not the line number.

**Recommended verdict:** defer until convergence pressure — the name collision is real but harmless today; a one-line "see also" pointer is the right edit *when* a reader gets confused, not pre-emptively. Re-raise if `/goal` lands on a setting (e.g. `goalFile: ".harness-state/today_goal.md"`) that the harness could integrate against.

## 3. Bookkeeping: Agent SDK credit pool split (June 15 2026) updates the cost calculus on the 2026-05-10 §2 Cloud Routines deferral

**Source:**
- [Use the Claude Agent SDK with your Claude plan — support.claude.com (announced 2026-05-13, effective 2026-06-15)](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)
- Coverage: [Anthropic splits billing again: Agent SDK gets separate credit pools — The New Stack](https://thenewstack.io/anthropic-agent-sdk-credits/); [Anthropic puts Claude agents on a meter — InfoWorld](https://www.infoworld.com/article/4171274/anthropic-puts-claude-agents-on-a-meter-across-its-subscriptions.html)

### Why it's relevant

The 2026-05-10 §2 deferral (migrate the Anthropic-reviews routine itself to a Claude Code Cloud Routine) priced the migration at *"~$5-10/run by analogy with `/ultrareview`'s pricing band"* and said *"recurring cost without recurring value yet — defer."* That cost was an estimate of the routine's per-fire token usage drawn from the shared subscription bucket.

As of **2026-05-13** (effective **2026-06-15**), Anthropic split the subscription into two buckets:
- **Interactive pool** — Claude Code in the terminal, Claude on the web/desktop, Claude Cowork. Continues to use the existing subscription usage caps.
- **Agent SDK / programmatic pool** — Claude Agent SDK, `claude -p` (non-interactive CLI), Claude Code GitHub Actions, third-party agent frameworks (OpenClaw, Conductor, Zed, Jean, etc.). Now draws from a **dedicated monthly credit pool**: $20 (Pro), $100 (Max 5x), $200 (Max 20x). **Credits don't roll over and aren't poolable across team members.**

A weekly Cloud Routine that runs the Anthropic-reviews scan is **agent-driven, scheduled, non-interactive** — exactly the pattern that now lands in the Agent SDK pool. Concretely:

- The deferral's stated cost was "~$5-10/run × 4 runs/month = ~$20-40/month from the shared subscription pool."
- Post-June-15, the same workload draws from the **dedicated Agent SDK credit pool**, which is **bounded** ($20-$200/month depending on plan tier) but **separately billed** — i.e. the harness's Cloud Routine would compete for the same $20/$100/$200 with the user's other agent-driven work (e.g. `claude -p` invocations from local scripts, GitHub Actions doing PR auto-fix, etc.).
- Net effect: the **deferral remains the right call**, but the **rationale shifts** from "recurring unbounded cost" to "bounded but separately budgeted."

This is bookkeeping — no concrete change requested. It exists so the durable record reflects that the cost calculus on the 2026-05-10 §2 deferral was re-checked post billing change and the conclusion didn't flip.

### Concrete change

None this run. When/if the maintainer revisits the Cloud Routine migration:

1. Cost model now: ~$5/run × 4 runs/month = ~$20/month, which **uses the full Pro tier's $20 Agent SDK credit pool**. Re-run the cost arithmetic against the user's actual plan (Pro vs Max 5x vs Max 20x) before scheduling.
2. The Agent SDK pool is **per-user, not per-team**, so on a solo repo this is moot; on a team repo it becomes a coordination problem.
3. Credits **expire monthly**, so a routine that fires once a month wastes most of the pool. Weekly cadence is roughly the sweet spot.
4. If the routine triggers a `claude -p` shelled invocation from a local script, that subprocess **also** lands in the Agent SDK pool — so the cost model needs to include the trigger script's invocations, not just the routine itself.

### Expected payoff (no-op path)

Decision-trail integrity for the 2026-05-10 §2 deferral. Without this entry, a future reader of the 2026-05-10 file would see the cost rationale ("$5-10/run × recurring") without knowing that the billing model itself changed on June 15. With this entry, they know the rationale was reviewed and the conclusion stands.
