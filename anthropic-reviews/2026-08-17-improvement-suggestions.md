## 2. Adopt Anthropic's "verification loops as skills" pattern for consumer-project SKILL.md files

**Source:** [Building verification loops in Claude Code with skills — claude.com/blog, 2026-07-22](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) by Delba de Oliveira (Claude Code team). Core thesis: **a "verification loop" is a repeating cycle where an AI agent checks its own work — running tests, linters, or custom checks — and fixes what fails before moving on.** In Claude Code, verification loops can be packaged as skills (SKILL.md files), so every session applies the same checks automatically instead of relying on a human to remember them. The post pairs this with: (a) using tools/connectors so Claude can *see, measure, or interact with the result* (not just re-read its own diff); (b) built-in cloud verification (Code Review PR-time, GitHub Actions with verification-skill invocations, spec-validation, Managed Agents rubric-graded outcomes).

### Why it's relevant

The harness has **two distinct concepts** that both use the word "verify":

- **Engine-level `/run-loop` exit gate** (`AGENTS.md ## Loop protocol`, `skills/run-loop/SKILL.md`, `skills/_shared/loop/`) — the mechanical per-item gate: implement → **exit gate** (repo-declared `tests`/`typecheck`/`verify` commands from `.harness-profile`) → code review → auto-fix → merge. This is a **loop-driver-owned** verification pattern: the shared engine reads the target repo's declared commands and threads them into every work item. Wave 24 shipped the portable-gate refactor; Wave 25 shipped strict-acceptance discipline. This is production.

- **Per-project skill-driven verification loops** (the Delba pattern) — a `SKILL.md` in a consumer project that Claude Code picks up when the session touches that domain, and *the skill itself* encodes the verification recipe (e.g. "after any change to `src/pricing/`: run `pnpm --filter pricing test:integration`; if any test fails, run the diff-focused reproducer script; loop until green or 3 failed attempts"). Different unit of value: **the consumer's Claude Code session, on any task in the domain, opts into the loop** — not just the `/run-loop` execution lane.

Today the harness ships shared skills (18 of them, symlinked from `skills/` to `~/.claude/skills/`) but does **not** scaffold or template per-project verification-loop skills. `setup-harness` installs the shared skills globally; the consumer project gets no domain-specific verification SKILL.md by default.

### Why this is `defer`, not `apply`

1. **No consumer project has asked.** The two existing shared skills that *look* like verification loops (`micro`'s commit-guard flow and `run-loop`'s engine gate) already cover the "loop-executor" pattern. What the Delba post adds is the **per-domain-per-consumer** skill, which is only useful if a consumer project (wordwideAI, other cowork areas) has a domain that repeatedly needs the same verification recipe.

2. **`setup-harness` is not a template scaffolder for per-project skills.** It symlinks the shared skills; scaffolding a per-project skill with placeholders + prompts would be a new capability. That's substantive enough to go through `/spec-planner` if adopted (see the README triage table: new convention used in multiple places ⇒ substantive).

3. **The harness's `apply-anthropic-reviews` skill already implements a variant of this pattern.** `skills/apply-anthropic-reviews/SKILL.md` is a verification loop for the triage-outcome-consistency check (decompose → classify → batch → update Status). It's a **harness-level** verification-loop skill, not a **consumer-project-level** one — but the "loop-as-skill" shape is already understood.

4. **Speculative for solo tooling.** Per the routine's own rubric.

### Concrete change (deferred)

None this run. When/if a consumer project surfaces a repeated verification recipe worth capturing:

1. Draft the per-project SKILL.md following the Delba pattern (frontmatter with `name`/`description`/`allowed-tools`, body with the loop steps + fail-out condition + stop rule).
2. Decide install path: (a) commit into the consumer repo's `.claude/skills/` directly (per-repo, per-Claude-Code-session), or (b) add a `setup-harness --scaffold-verification-loop <domain>` subcommand (harness-level template).
3. Cross-reference with `code-reviewer`'s `criteria/*.md` rubrics — a verification-loop skill can consume the same rubric the reviewer scores against, unifying the two.
4. Update `README.md`'s "How this complements Anthropic's cloud reviewers" paragraph (added by 2026-05-10 §1) with a third layer: **pre-commit local per-domain verification-loop skill** — sits inside the consumer session, upstream of both the harness's `code-reviewer` and Anthropic's hosted Code Review.

### Expected payoff (when applied)

### What this suggestion is **not**

Not a call to redesign `/run-loop`'s engine gate. That's a different pattern at a different layer. Also not a call to author a "verification loop" **shared** skill in `skills/` — the value is at the consumer-project level, so a shared skill would be premature abstraction.

## 3. Fold Fable-5 "Finding your unknowns" framework into spec-planner's discovery questions

**Source:** [A field guide to Claude Fable 5: Finding your unknowns — claude.com/blog, 2026-07-03](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns) by Thariq Shihipar (Claude Code team). 2M views in first 3 days per the-decoder coverage. Core framework: agentic-coding quality is bottlenecked by the ability to clarify your unknowns; split unknowns into **four quadrants** (known knowns, known unknowns, unknown knowns, unknown unknowns); the field guide offers **8 techniques** for surfacing them across pre-implementation, during-implementation, and post-implementation stages — each with a copy-paste-ready prompt.

### Why it's relevant

The harness's `spec-planner` agent (`.claude/agents/spec-planner.md`) is explicitly a **discovery-question-driven planner**:

- Line 34–35: *"Read the user's initial idea carefully. Identify gaps — things you'd need to know to write a great spec but that the user hasn't told you. Pay special attention to implied requirements..."*
- Line 36: *"Ask 1-4 targeted questions per round using `AskUserQuestion`. Focus on the biggest unknowns first."*
- Line 62: *"Which is smaller? Which has more unknowns?"* (referring to spec-vs-spec sizing)
- Line 389: *"Include Open Questions. Park unknowns here; don't let them block the spec."*

So the spec-planner is **already Anthropic's target audience** for the "Finding your unknowns" framework — it just uses the word "unknowns" without a formal taxonomy.

Overlaying Thariq's 4-quadrant taxonomy + a subset of the 8 techniques would:
- Give spec-planner an explicit **unknown-unknowns pass** (currently missing — the agent asks about *known* unknowns via `AskUserQuestion`, but has no ritual for surfacing what the user *doesn't know they don't know*)
- Give a shared vocabulary between spec-planner and downstream agents (planning-loop's acceptance-check, code-reviewer's finding categories)
- Provide copy-paste-ready prompts the maintainer could evaluate against real spec drafts

### Why this is `defer`, not `apply`

1. **Wave 25 just landed strict-acceptance discipline.** Layering a new taxonomy on top of a fresh discipline pass without a triggering failure risks over-engineering the spec-planner interface. Give Wave 25's strictness time to bed in and produce evidence about *where* spec-planner's current discovery is thin.

2. **The 4-quadrant model is famously easy to describe and hard to apply.** A rushed adoption produces "prompt for each quadrant" boilerplate; a considered adoption identifies which of the 8 techniques the agent's actual failure mode calls for.

3. **`/spec-planner` is a Claude-Code-scoped agent, not a shared skill.** Any change to the discovery-question phase should be evaluable — ideally by running the updated agent against an already-shipped spec and checking whether the new taxonomy would have surfaced an unknown-unknown that the shipped spec's `## Open Questions` missed. That's a small eval fixture, not a doc edit.

4. **The framework is orthogonal to model choice.** Thariq positions it as bottlenecking Fable-5-class models specifically ("the first model where the quality of the work is bottlenecked by the ability to clarify its unknowns"). The harness pins Opus (per §1 above); the payoff on Opus is real but smaller than on Fable.
