## 2. Add "model swaps vs effort controls" framing to `orchestrator.md`

**Source:** [Choosing a Claude model and effort level in Claude Code — Claude Blog, 2026-07-07](https://claude.com/blog/claude-model-and-effort-level-in-claude-code)

### Why it's relevant

The July 7 post crystallizes a distinction the harness's `orchestrator.md` implicitly makes but never states in plain English:

> "Model swaps which frozen weights answer your request. Effort controls how much work those weights do — files read, tests run, verification, tool loops — before Claude checks back in."

And the diagnostic:

> "If Claude has all the pertinent context, clearly tried, and still got it wrong, that's a signal to pick a more capable model. If Claude got it wrong by skipping a file, not running the tests, or bailing on a refactor partway through, pick a higher effort level."

`orchestrator.md:118–166` gives detailed "Route to Haiku/Sonnet/Opus when …" bullets and a separate effort-selection ladder, but never spells out *which failure mode escalates which lever*. Post-Sonnet-5, that diagnostic gets more valuable — the model gap between Sonnet 5 and Opus 4.8 is narrower than 4.6 vs 4.7, so "raise effort before raising model" is often the cheaper fix.

### Concrete changes

- **`.claude/agents/orchestrator.md`, between the routing bullets (§"Route to Opus when") and the routing table (§"Routing table (model + effort)"):** insert a short block:

  ```markdown
  ### When to escalate which lever

  Model and effort are separate levers. If a route fails, diagnose which one to bump:

  - **Bump model** — "Claude had the context, clearly tried, still got it wrong."
    Signal: reasoning error, wrong architectural call, missed cross-cutting concern.
  - **Bump effort** — "Claude skipped a file, didn't run the tests, or bailed on the refactor partway."
    Signal: coverage/thoroughness error, not a reasoning error.

  Escalate effort before model when unsure — it's usually cheaper. Source:
  [Choosing a Claude model and effort level in Claude Code](https://claude.com/blog/claude-model-and-effort-level-in-claude-code).
  ```

- **`orchestrator.md:154–166` (Default effort selection rules):** no rule change; the diagnostic sits alongside the existing ladder, doesn't replace it. The ladder still decides the *initial* effort; the diagnostic decides the *retry* lever.

- **Optional — `orchestrator.md` retry path (§"Case A / Case B" around line 221):** the current retry logic promotes model on effort==xhigh. Cross-reference the diagnostic there — the "current effort < xhigh ⇒ bump effort" case is the "skipped a file / bailed partway" failure mode from the post; makes the retry rung readable at a glance.

### Expected payoff

Turns the two-lever intuition into diagnostic vocabulary a future maintainer (or the orchestrator agent under load) can point at. No architectural change; ~15 lines of prose.

**Verify before applying:** `grep -n 'model swap\|escalate.*model\|escalate.*effort' .claude/agents/orchestrator.md` — if any of those phrasings already landed, the diagnostic is in place and this § is done.

**Recommended verdict:** apply — cheap doc edit that codifies a decision rule the orchestrator already half-follows.

## 4. Adopt Fable-5 "blind spot pass" + `implementation-notes.md` as an optional spec-planner discovery step

**Source:** [A field guide to Claude Fable 5: Finding your unknowns — Claude Blog, 2026-07-03](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns) (by Thariq Shihipar, MTS)

### Why it's relevant

The field guide's central pattern for high-capability models is *finding unknowns before they surface as bugs*, via two named techniques:

1. **Blind spot pass** — run before planning; ask Claude to list unknown-unknowns most likely to change the implementation, grouped by codebase/product/test/rollout risk.
2. **`implementation-notes.md`** — a temporary file the agent writes to during a session, logging decisions, deviations from the spec, and surprises. Post-session the notes fold back into `CLAUDE.md` or the spec.

The harness's `/spec-planner` runs a discovery interview (1–3 rounds) and then emits `docs/specs/<date>-<topic>.md`. The interview surfaces the *known* unknowns the maintainer already has in their head — it doesn't try to surface *unknown* unknowns from the codebase itself. The `implementation-notes.md` pattern has no current analog either; `.harness-state/orchestrator.log` records routing decisions, not per-task deviations.

Neither gap is "the harness is broken." Both are additive and specific to how Fable-class models degrade — they overreach into unknowns, so surfacing unknowns before dispatch pays off more the stronger the model gets.

### Concrete changes (needs a design pass — see verdict)

- **`.claude/agents/spec-planner.md`:** add an optional "Blind-spot pass" step at the end of discovery, before writing the spec. Structure suggested by the post — ask Claude to list unknown-unknowns grouped by (codebase risk, product risk, test risk, rollout risk), then surface them to the operator as a "did we miss any of these?" checklist. Design decision needed: is this on by default? Behind a flag? Only for `stakes.level: high`?

- **New skill or `.harness-state/` convention:** `implementation-notes-<wave-or-spec-id>.md` written by the orchestrator during a wave, appended to on every task, folded into the spec on `/close-wave`. Design decision: where does it live (per-wave receipt? per-spec? both?), and what triggers the fold-back?

- **Optional post-implementation:** the post's "pitches and explainers" and "quizzes" ideas map onto the harness's shipped-wave archive (`docs/waves/wave<N>-<slug>.md`) — the wave file already carries a summary; the quiz idea is speculative.

### Expected payoff

Reduces the "spec looked complete, then Claude hit an unknown at implementation time" failure mode — the exact class of bug that grows as models get more autonomous. But this is a spec-planner *shape* change, not a docs tweak, so it wants a design pass first.

**Verify before applying:** `grep -rn 'blind spot\|implementation-notes\.md\|unknown unknown' .claude/agents/spec-planner.md docs/specs/` — if either pattern already landed, this § is stale.

**Recommended verdict:** spec — the pattern is real but the shape (default-on? per-wave file? per-spec?) is underspecified; run `/spec-planner` on this before any coding.
**Status:** PENDING — awaiting triage in PR review

## 5. Cross-reference the "Loop engineering" post in `skills/run-loop/SKILL.md`

**Source:** [Loop engineering: Getting started with loops — Claude Blog, 2026-06-30](https://claude.com/blog/getting-started-with-loops)

### Why it's relevant

The June 30 post names Anthropic's four loop types — **turn-based, goal-based, time-based, proactive** — and ships three slash commands (`/goal`, `/loop`, `/schedule`) that expose them. `skills/run-loop/SKILL.md:13` already carries a naming note ("Name chosen over `/loop` — that is the Anthropic interval-scheduler built-in"), but the note predates the four-type taxonomy. A reader hitting the harness after 2026-06-30 will want to know exactly which of the four types `/run-loop` is, and why the harness ships its own instead of using `/loop`.

Mapping to the taxonomy: `/run-loop waves|issues` is a **goal-based loop** — it drains work until the source is empty (drained = goal met) or a termination cap fires (iteration/stall/token/wall-clock). It is not turn-based (unattended), not time-based (source-drain triggered, not schedule triggered), and not proactive (invoked by the operator, not by an event).

This is a documentation cross-reference, not an architectural change — the mechanical gate, AFK/HITL split, and safety guardrails don't overlap with Anthropic's `/loop` at all.

### Concrete changes

- **`skills/run-loop/SKILL.md`, near line 13 (the existing naming note):** extend to:

  ```markdown
  Name chosen over `/loop` — that is the [Anthropic interval-scheduler built-in](https://claude.com/blog/getting-started-with-loops).
  `/run-loop` is consistent with `/run-wave`. In the [June 30 2026 loop-type taxonomy](https://claude.com/blog/getting-started-with-loops),
  `/run-loop waves|issues` is a **goal-based loop** — it drains a work source
  until the source is empty or a termination cap fires. It is not the turn-based,
  time-based, or proactive types described in that post; use Anthropic's `/loop`
  + `/schedule` for those.
  ```

- **Optional — `WORKFLOW.md`:** add one row mapping the three lanes (wave / loop / manual) to the four loop types for cross-tool discoverability.

### Expected payoff

Removes the "wait, does this replace `/loop`?" question a Claude-Code-native reader will hit within the first 30 seconds of the SKILL.md. Two-line edit.

**Verify before applying:** `grep -n 'getting-started-with-loops\|goal-based loop\|four loop types' skills/run-loop/SKILL.md` — any hit means this § already landed.

## 6. Do NOT add a `/verify` skill — the "Building verification loops" pattern is already what `/commit` does

**Source:** [Building verification loops in Claude Code with skills — Claude Blog, 2026-07-22](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)

### Why it's not actionable

The post's core recommendation is a skill whose instructions read:

> "Execute the task. Run verification. If verification fails, analyze the failure, fix the code, and verify again. Repeat until all checks pass or you've made 5 attempts."

Six verification phases named in the post: build, type check, lint, tests-with-coverage, security scan (leaked keys / debug statements), git-diff review.

The harness's `/commit` skill already implements this exact loop, sequenced against project `criteria/` rubrics:

- `commit` triggers `code-reviewer` on the staged diff (which the code-reviewer agent's own instructions run tests + type-check against, per `.claude/agents/code-reviewer.md`).
- On findings → **fix all / review individually / park all** menu.
- Re-review after fix, capped at 2 rounds (§Flow item 5 in `README.md:249–267`).

The six specific verify phases named in the post map to:

| Post phase | Harness surface |
|---|---|
| build verification | Project's own build command via `code-reviewer` |
| type checking | Project's typecheck via `code-reviewer`; also `PostToolUse` hook example in `README.md:894–911` |
| linting | `lint_blocking` field in `.harness-profile`; hook option in README |
| tests + coverage | `code-reviewer` runs the project's `test` command |
| security scan (keys / debug) | `/security-review` (Claude Code built-in) + `procedures/api-security-checklist.md` |
| git diff review | `/commit` is exactly this |

Adding a `/verify` skill would rename existing capability without adding any. The post's guidance is well-taken; the harness already followed it.

**Verify before applying:** `grep -n 'code-reviewer\|max 2 re-review' skills/commit/SKILL.md README.md` — if `/commit` still triggers `code-reviewer` with a bounded re-review loop, this rejection stands.

**Recommended verdict:** reject — the "execute → verify → fix → verify" loop is what `/commit` already does; introducing `/verify` would fragment the same behavior across two entry points.
**Status:** PENDING — awaiting triage in PR review

## 7. Adopt the rulebook + dependency-map pattern from "How Anthropic runs large-scale code migrations"

**Source:** [How Anthropic runs large-scale code migrations with Claude Code — Claude Blog, 2026-07-16](https://claude.com/blog/ai-code-migration) · companion repo: [anthropics/code-migration-kit-with-claude-code](https://github.com/anthropics/code-migration-kit-with-claude-code)

### Why it's relevant (but not yet actionable)

The post's six-step process is genuinely novel:

1. **Rulebook** — every translator decision that could go two ways, decided once. "If two agents could answer differently, it goes in the rulebook."
2. **Dependency map** — deterministic script, not agent judgment; used to batch and parallelize.
3. Stress-test on a small slice before scaling.
4. Iterative translation with the rulebook as the invariant.
5. Adversarial review rounds.
6. Parity check at the end.

Result: Bun's Zig→Rust migration produced ~1M lines in <2 weeks; Mike Krieger's Python→TypeScript hit 165k lines in a weekend.

The harness's `migration-check` skill is scoped to **database** migrations (reversibility, concurrent-write safety, backfill, index locking) — a different problem. `spec-planner` + `orchestrator` + `run-wave` could in principle be composed into a code-migration lane, but there's no current pressure (no code migration on `docs/plan.md`, and the solo maintainer isn't running the harness against multi-language ports).

### Concrete changes (deferred)

- Park in `parking_lot.md` with `[migration-playbook]` tag and a link to the post + the code-migration-kit repo — so it's findable the day a code migration lands on the plan.
- On the day it becomes real: run `/spec-planner` on the migration itself, and separately spec whether the harness needs a code-migration lane or the ad-hoc `/run-wave` orchestration suffices.

**Verify before applying:** `grep -rn 'ai-code-migration\|rulebook\|dependency map' parking_lot.md docs/specs/ docs/plan.md` — any hit means this § already landed or was superseded.

**Recommended verdict:** defer until a real code migration hits `docs/plan.md` — the playbook is high-quality but the trigger isn't there yet; premature adoption would add scaffolding for a scenario that may never arrive.
