## 4. "How we contain Claude across products" corroborates the sandcastle-vs-worktree runner split

**Source:** [How we contain Claude across products — Anthropic Engineering, 2026-05-25](https://www.anthropic.com/engineering/how-we-contain-claude)

### Why it's relevant

Anthropic's May-25 engineering post describes the containment architecture for three Anthropic-shipped agent products:
- **claude.ai** — ephemeral gVisor container on isolated servers with minimal filesystem access
- **Claude Code** — local tool with real shell access, using OS-native sandboxing (Seatbelt on macOS, Bubblewrap on Linux)
- **Claude Cowork** — full virtual machine (Apple's Virtualization framework on macOS, HCS on Windows)

The lesson is: *supervise what the agent can do, not what it does; the confinement primitive scales with the target audience's trust surface.*

The harness has already made the analogous architectural choice for its two runner lanes (`AGENTS.md:107, 113`; `skills/run-loop/SKILL.md:99-113`):
- **Sandcastle runner (default)** — runs the agent in a container; the OS is the security boundary. Analogous to Anthropic's Cowork layer.
- **Worktree runner** — runs the agent natively on the host with a **catastrophic-command denylist PreToolUse hook** as a backstop, plus explicit write-root confinement (OS-enforced where available, advisory otherwise), plus egress default-deny for secret-bearing items. Analogous to Anthropic's Claude Code layer (native + OS-hint sandboxing where present).

The harness's approach and Anthropic's are structurally the same: pick the confinement level for the trust surface, don't rely on the agent's cooperation.

- No behavior change is proposed. This is a "cite first-party validation" note.
