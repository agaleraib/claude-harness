## 2. Fold "How we contain Claude" containment patterns into `skills/setup-harness/SKILL.md` and `procedures/triage-quality-issues.md`

**Source:** [How we contain Claude across products — anthropic.com/engineering, 2026-05-25](https://www.anthropic.com/engineering/how-we-contain-claude). Anthropic's end-to-end write-up on sandboxing Claude.ai, Claude Code, and Claude Cowork. Three incidents are called out, two of which translate directly to Claude Code harness design:

- **Pre-trust execution of project config.** A `.claude/settings.json` hook was parsed *before* the trust prompt was shown. Fix: defer parsing until the user consents.
- **Approved-domain exfiltration.** `api.anthropic.com` was on the egress allowlist, so an attacker's own API key uploaded files to the attacker's account. Reframe: **allowlists are capability grants**, not just destination filters.

Plus the Seatbelt (macOS) / bubblewrap (Linux) sandbox mechanics for the Bash tool (the piece that's already shipping in `code.claude.com/docs/en/sandboxing`), permission-prompt fatigue data (93% approve → added an OS-level sandbox → cut prompts by 84%), and the fact that `.claude/settings.json` is the pre-trust execution surface.

### Why it's relevant

The harness ships a `.claude/settings.json` scaffold (currently empty hooks:  `.claude/settings.json:1-4`), and `skills/setup-harness/SKILL.md` is the entry point for consumer projects. The 2026-05-08 §1 run (Auto Mode) already added **one** containment-related note; this § supplies the **two concrete design hazards** that Auto Mode doesn't cover:

1. **Pre-trust hook execution.** `setup-harness` writes `.claude/settings.json` as part of its scaffold; it does not currently note that *hooks in that file execute before the trust prompt is shown* if the user hasn't accepted the project yet. For a solo-maintained repo this is low-risk (the maintainer accepts their own repos), but for consumer projects the harness installs into, it's a meaningful disclosure. Doc note, not code change.
2. **Allowlists are capability grants.** `procedures/triage-quality-issues.md` and `skills/setup-harness/SKILL.md` discuss `permissions` / `allow` rules. Adding a one-paragraph "think of each entry as a capability grant, not a destination filter — a reachable `api.anthropic.com` is an upload channel to any Anthropic account" sentence protects consumer projects from the exact incident Anthropic documented.

### Concrete change

Two small doc edits — both apply-sized under the README decompose-first rubric:

**a.** `skills/setup-harness/SKILL.md` — append a short "Security notes for the `.claude/settings.json` scaffold" section:
```markdown
### Security notes for the `.claude/settings.json` scaffold

Two patterns are worth naming explicitly, from
[How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude)
(Anthropic Engineering, 2026-05-25):

1. **Hooks in `.claude/settings.json` execute at the point the project is parsed,
   which can be before the trust prompt resolves if a user opens the project for the
   first time via a non-prompting entry (CLI flag, deeplink).** For a repo you own,
   this is fine. For a repo you clone from someone else or that a teammate hands you,
   skim the hooks block before accepting the project.
2. **Allowlists in the `permissions` block are capability grants, not destination
   filters.** A reachable `api.anthropic.com` entry is an upload channel to any
   Anthropic account, not only yours — Anthropic documented an incident where this
   was the exfiltration path.
```

**b.** `procedures/triage-quality-issues.md` — one bullet near the allow-rules discussion:
```markdown
- When adding an entry to `permissions.allow`, ask: *is this a destination or a
  capability?* An allowlisted domain that terminates on a multi-tenant API
  (`api.anthropic.com`, `api.openai.com`, `*.supabase.co`) grants the capability of
  uploading to *any* account on that service, not only the one you intended.
```

### Expected payoff

- Named forestalling of a real incident class, with Anthropic-blessed framing.
- Zero code impact; zero behavior change; the hazard is on by default and the doc note is additive.
- Harness-authored framing of allowlists survives into consumer projects via `setup-harness`.

## 4. Promote the deferred 2026-04-19 §5 (adversarial-reviewer evals) toward a `/claude-api build-eval` + `/claude-api hillclimb` experiment

**Source:** Anthropic's post **"Automating eval design and hillclimbing with Claude"** by Lance Martin (2026-09-28), published on `claude.dev/blog/automating-eval-design-and-hillclimbing/` per secondary coverage (anthropic.com and claude.com URLs 404 as of this run — see Verify). - **`/claude-api build-eval`** — interviews the user and builds an evaluation suite inside the codebase.
- **`/claude-api hillclimb`** — iterates the application against that eval: one attributable change per round, held-out set to prevent overfitting, auto-revert on regression.

Secondary sources report Anthropic's own `claude-api` skill improved from ~66% to ~88% under hillclimb across ~a dozen rounds; a support-prompt example rose from 78.6% to 90.5% on 14 held-out tickets.

The maintainer could run `build-eval` against `.claude/agents/code-reviewer.md` + a representative set of past code-review runs and get a scored eval back without hand-writing fixtures.
- `/claude-api hillclimb` is attractive **only after** the eval exists — it tunes the reviewer-prompt against the held-out set. Premature hillclimb without a stable eval is the pattern Anthropic's post explicitly warns against.
