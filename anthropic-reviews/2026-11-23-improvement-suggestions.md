## 5. Audit whether the harness's `/commit` chains anything beyond `code-reviewer` along the four-level verification model

**Source:** [Building verification loops in Claude Code with skills — claude.com/blog, 2026-07-22](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)

### Why it's relevant
The verification-loops post names four composition levels:

1. **Standalone** — user invokes `/verify`/`/code-review` by hand.
2. **Embedded** — one skill invokes another as part of its flow.
3. **Chained** — skills chain together (e.g. `/simplify` → `/verify` → `/code-review`).
4. **On every PR** — triggered automatically on every PR (Code Review / `/ultrareview` territory).

The harness's `/commit` skill is at level 1 (Standalone, from the user's perspective) with a hand-coded step into `code-reviewer` (approaching level 2, Embedded). It does not chain into `/verify` (build and run the app) or into a cloud reviewer. The post's internal-team example at Anthropic — `/code-review` → `/simplify` → `/verify` → `/design` — runs all four together.

### Why defer

- **The harness is solo-maintained**, `.harness-profile: team.size: solo`. Chaining multiplies token spend per commit — the post notes "chained verification loops can increase token spend." For a solo maintainer running the harness on their own dev loop, the marginal catch rate from adding a second chained reviewer is not clearly worth the cost **today**.
- **No CI in the repo yet.** The harness ships skills via symlink to `~/.claude/skills/` and consumer projects pick them up — there's no central CI running `/verify` on PRs. Adopting level 4 (On every PR) would need the Routines integration deferred in 2026-05-10 §2 to land first.
- **Not a correctness gap.** The harness already catches issues at `/commit` via `code-reviewer`. The question is marginal: would *also* chaining `/verify` + `/ultrareview` catch more, worth the token cost? Solo maintainer with limited daily commits says "probably not yet."

### What to watch for
- A new regression that `code-reviewer` misses but `/verify` would have caught (something that only fails at runtime, not at type/rubric level). That's the forcing function for adding an Embedded `/verify` step.
- Growth beyond solo — if the harness picks up a second contributor, PR triage changes and level 4 (On every PR) becomes worthwhile.
- Successful cloud-routine adoption (2026-05-10 §2) that makes on-PR-chaining cheap.

**Verify before applying:**
1. `grep -n "chain\|/verify\|/ultrareview" /home/user/claude-harness/skills/commit/SKILL.md` — confirms the current `/commit` flow stops at `code-reviewer` and does not chain further. If any hits appear, the chain may already be in place or in progress; re-triage.
2. Check `team.size:` in `.harness-profile` — if it is no longer `solo`, the solo-cost argument above weakens and this suggestion should be reclassified `apply`.
3. Look at the last 20 `/commit` runs in `.harness-state/orchestrator.jsonl` (if logged) for any post-commit regressions that would have been caught by a build-and-run step. A ≥10% hit rate is the forcing function.

**Recommended verdict:** defer until (a) a runtime regression slips through `code-reviewer`, or (b) team size grows past solo, or (c) the Routines-based on-PR cloud chain from 2026-05-10 §2 becomes cheap enough to adopt.
