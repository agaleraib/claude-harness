## 2. Rules-to-judgment audit across CLAUDE.md, AGENTS.md, and skill bodies (Claude-5-generation context-engineering post)

**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) (Thariq Shihipar). Anthropic reports the Claude Code team **removed ~80% of the system prompt** for Opus-5-generation models with **no measurable loss on coding evals**, replacing explicit rules with judgment-inviting guidance. The post enumerates six shifts; the first is titled *"Rules to judgment"* and its worked example is:

- Old: "*default to writing no comments, never write multi-paragraph docstrings, do not create planning documents unless asked*"
- New: "*write code that reads like the surrounding code: match its comment density, naming, and idiom*"

The claim is that Claude-5-generation models have enough calibration to make the surrounding-code call themselves; the rule-form guidance costs tokens and forecloses good judgment.

### Why it's relevant

This repo carries **7,459 lines of skill/agent prose** across 24 skills (see `wc -l skills/*/SKILL.md` — the largest are `planning-loop/SKILL.md` at 719, `close-wave/SKILL.md` at 677, `skill-creator/SKILL.md` at 488), **plus** 131 lines in `AGENTS.md`, 35 in `CLAUDE.md`, and 1,122 in `README.md`. A meaningful fraction of that prose is explicit rule-form guardrails written **for older Claude models** — the same category the July-24 post argues Claude 5 no longer needs.

Concrete surface areas that plausibly overlap the "rules-to-judgment" trim:

- **CLAUDE.md:1-35** — Claude-specific overrides on top of the tool-neutral AGENTS.md. Small, likely stays as-is.
- **AGENTS.md** — the 131-line tool-neutral protocol. Some sections are procedural (which is legitimate rule-form) and some are behavioral guardrails (which the post argues to trim).
- **Skill bodies** — the /planning-loop, /close-wave, /commit, /run-wave, /skill-creator skills all carry explicit "MUST / NEVER / ALWAYS" bullets. Some are protocol invariants (fail-closed on unreadable spec path — genuine rule); others are style hints for older models.
- **Agent prompts** — `.claude/agents/*.md` (code-reviewer, spec-planner, orchestrator, etc.).

**But — and this is why the recommended verdict is `spec` not `apply` — the harness's rule-form prose is not uniformly trimmable:**

1. **Protocol invariants** (fail-closed exit gates, three-way merge rules, worktree hygiene) are *rules that guard against ambiguous behavior in edge cases*, not style hints. Trimming them breaks the harness's determinism story.
2. **Adversarial-reviewer prompts** (`code-reviewer.md`) rely on explicit rule-form checklists — that's the point of the agent. Judgment-form guidance would flatten the adversarial edge.
3. **Behavioural-test fixtures** in `skills/planning-loop/lib/test-fixtures/` assert on specific behaviours triggered by specific prose. A blind trim breaks tests.

The right shape of the change is: **classify each rule-form span** as one of *protocol invariant* / *safety guardrail* / *style hint written for an older model*, and only trim the third. That classification is design work, not typing — hence `spec`.

### Concrete change

**Not a diff — a `/spec-planner` invocation.** The spec brief:

> **Goal:** Audit `CLAUDE.md`, `AGENTS.md`, and every `skills/*/SKILL.md` for rule-form prose that could migrate to judgment-form under Claude-5-generation models, per `claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models`.
>
> **Constraints:**
> - **DO NOT** trim protocol invariants (fail-closed rules, exit-gate three-way rules, worktree hygiene, merge-conflict resolution rules, permission/hook denylists).
> - **DO NOT** trim adversarial-reviewer checklists (they're the point of `code-reviewer.md`).
> - **DO NOT** trim rule-form prose that has a behavioural-test fixture asserting on it.
> - **DO** flag rule-form style hints (comment density, naming conventions, output length caps written for pre-Claude-5 models) as candidates.
> - **DO** propose a trim ratio (Anthropic reports ~80%; the harness's rule-form prose is probably 20–40% because the protocol invariants dominate — quantify it in the spec).
> - **DO** propose a rollback story: since this repo has no CI regression suite for prose behaviour, the trim must be reversible. Consider a `docs/waves/wave-XX-rules-to-judgment.md` with the exact spans removed, so a re-add is mechanical.
>
> **Blast radius:** every skill invocation, every agent dispatch, every session-start. A bad trim silently degrades harness behaviour for weeks before anyone notices.
>
> **Prerequisite:** primary Anthropic source must be re-fetched (the current summary is a `WebSearch` reconstruction; anthropic.com/claude.com were egress-blocked in the run that generated this suggestion).

The spec then produces a wave plan; the wave produces per-file diffs; the wave's close ritual measures whether harness behaviour on a representative task (e.g. running `/planning-loop` on a fixture spec) is stable before / after.

### Expected payoff

**If the trim is real and defensible**, the harness's per-session token budget for skill preambles drops meaningfully (Anthropic reports 80% on their own system prompt; a plausible harness number is 20–40% of the ~7.5K lines, i.e. 1.5–3K lines of prose no longer eating into the session's context budget). **If the trim is not defensible**, the spec produces a written record of *why* the harness's rule-form prose is load-bearing — useful the next time this suggestion resurfaces.

**scope: speculative** — the actual payoff depends on the trim ratio surfacing from the spec pass. Recommendation-of-recommendation: don't invoke `/spec-planner` on this until Opus 5 is actually being used against the harness (see §4). Applying Claude-5-generation guidance to a repo still running against Opus 4.7 is premature.

### Why this isn't a duplicate

The existing 2026-04-25 § / 2026-04-27 § / 2026-04-28 § entries on the **April-23 postmortem** are about *not injecting verbosity caps that fight the model's own defaults* — the *opposite* direction (the postmortem said "don't override the model's chattiness; the model's default is right"). This § is downstream but distinct: it says "don't inject rule-form style hints the model no longer needs at all". Different scope, different suggested change.

Fetch `https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models` from a session with claude.com egress unblocked and confirm the "Rules to judgment" section is still one of the six shifts named, and that the "~80% system prompt removed for Opus-5" claim is still current. ## 5. Bookmark Claude Code subagent concurrency + depth caps in AGENTS.md

**Source:** Claude Code changelog entries (`code.claude.com/docs/en/changelog`) for **v2.1.217** (2026-07-21) — capped concurrent subagents at 20, disabled nested spawns — and **v2.1.219** (2026-07-24) — reinstated nesting at default depth 3 (down from an earlier depth-5 default in v2.1.172, June 2026). Three independent limits now govern subagent fan-out: **concurrency = 20**, **per-session total = 200** (since v2.1.212), **spawn depth = 3** (since v2.1.219).

### Why it's relevant

`skills/run-wave/SKILL.md` (446 lines) documents the orchestrator dispatch pattern using `.claude/worktrees/agent-<id>/` worktrees per subagent. The harness's own fan-out is **solo-scale** — one operator, one wave at a time, per-wave dispatch typically fires 1–5 subagents. No observed collision with the new caps.

**But** — the harness's methodology docs (AGENTS.md, README.md's "Why Not Superpowers", `skills/run-wave/SKILL.md`) argue for wave-based dispatch as a scale pattern. When a consumer project installs the harness and hits these caps, they need to know:

- **Concurrency = 20** — hard cap, not tunable in the CLI.
- **Depth = 3** — a nested `/run-wave` calling another `/run-wave` at depth 4 will refuse.
- **Per-session total = 200** — long-running sessions with churn may hit this.

Today AGENTS.md has **no mention of subagent fan-out limits at all** (`grep -n "subagent\|concurrency\|depth" AGENTS.md` returns nothing per an earlier verification in this run).

### Why the recommended verdict is `defer`, not `apply`

- The right shape of the note is a **conditional cross-reference** ("if your consumer project hits a subagent cap, see the changelog"), not a rule.
- A better trigger for this edit is *the next time AGENTS.md's orchestrator / fan-out prose is being edited for another reason* — piggyback the note, don't ship a standalone PR for it.
