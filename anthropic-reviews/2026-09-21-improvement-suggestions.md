## 1. Add pre-trust-dialog + persistent-memory-poisoning warnings to `setup-harness`

**Source:** [How we contain Claude across products — Anthropic Engineering, 2026-05-25](https://www.anthropic.com/engineering/how-we-contain-claude). Companion evidence for the two attack patterns cited below lives in the same post's "Risk we missed: everything before the trust dialog" and "Looking ahead / Persistent memory poisoning" sections.

### Why it's relevant

The May 25 engineering post is Anthropic's most explicit statement to date about **two failure modes that structurally affect any repo shipping `.claude/settings.json` or `.claude/hooks/` content to target projects**:

1. **Everything before the trust dialog.** Between mid-2025 and January 2026, Anthropic received disclosures of three vulnerabilities where `.claude/settings.json` hooks (and other project-local config) executed *before* the "Do you trust this folder?" prompt fires. Quoting the post: *"a developer clones a repository to review a pull request, and that repository contains a `.claude/settings.json` which defines a hook. Because Claude Code reads project settings during startup — before presenting the standard 'Do you trust this folder?' prompt — the hook the attacker had authored and committed would execute automatically."* Fixes have shipped, but the class of exposure survives: any config or hook the harness plants into a target repo *is* the trust surface, and target-project maintainers cloning a hostile fork see whatever the fork put in `.claude/`.
2. **Persistent-memory poisoning.** Quoting the post's Looking Ahead section: *"the share of agent context that persists across sessions keeps growing — this includes product memory, CLAUDE.md files, mounted workspaces, and the state directories of scheduled and long-running agents. An injection that lands in any of these is reloaded each time the agent starts."* This harness ships **all of the named surfaces**: CLAUDE.md (35 lines but expected to grow), `AGENTS.md` (131 lines), `~/.claude/skills/*` (18 skills, symlinked out), plus a live `.harness-state/` (30+ `wave*-closed.md` and orchestrator YAML/JSONL files), and `docs/waves/wave*-<slug>.md` archive files — all reloaded (directly or via skill invocation) at session start on every consumer install.

Neither risk is theoretical for this repo. The parking_lot already carries a 2026-04-12 open item flagging *"🔑 OpenAI API key exposed in `~/.claude/settings.json` under the `paperbanana` MCP config — hardcoded in plain text"* — an exact instance of the "credential-in-agent-config" pattern the containment post says the environment layer must catch, because the model layer cannot (`grep -n "OpenAI API key" parking_lot.md`).

The **`setup-harness` skill body is 298 lines** (`wc -l skills/setup-harness/SKILL.md`) and already has a "Permission model — Auto Mode + hooks layering" subsection (lines 139–149) covering the *runtime* interaction of Auto Mode with `.claude/settings.json`. It does **not** cover:

## 3. Consider `.claude/rules/` (path-scoped rules) as a new instruction primitive alongside CLAUDE.md / skills / hooks

**Source:** [Steering Claude Code: when to use CLAUDE.md, skills, hooks, and subagents — Claude Blog, 2026-06-18](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)

### Why it's relevant

The June 18 post formalizes what has been sedimenting in Claude Code for the last few CLI releases: there are now **seven** instruction methods, not the four the harness tends to treat as canonical (CLAUDE.md, skills, hooks, subagents). The new-to-us primitives are:

- **Rules** (`.claude/rules/*.md`): markdown files with a `paths:` frontmatter that scopes when the rule loads. An unscoped rule behaves like CLAUDE.md (always loaded); a scoped rule loads only when Claude reads a file matching the path glob.
- **Output styles** (`.claude/output-styles/*.md`) and **`append-system-prompt`**: system-prompt-level overrides.

Quote from the post's "Rules" section:

> A file-specific constraint, like "migrations are append-only," fits best as a **rule** placed in your `paths:` frontmatter. Reach for a path-scoped rule over a nested CLAUDE.md file when the instruction regards a cross-cutting concern or file that appears in multiple (but not all) corners of the codebase.

For this harness, the interesting shape is: **directory-scoped conventions**. The harness has several such today (`skills/_shared/loop/` follows a TypeScript convention pinned in AGENTS.md; `docs/specs/` has a naming convention documented in AGENTS.md; `.harness-state/` has schema conventions that only apply when a skill reads or writes there). All of these currently live as prose in AGENTS.md (`wc -l AGENTS.md` → 131 lines) or CLAUDE.md (35 lines) — always loaded regardless of what Claude is doing.

None of this is broken today. CLAUDE.md at 35 lines is well under the 200-line ceiling the post cites (*"Keep CLAUDE.md under 200 lines"*), and AGENTS.md's tool-neutral discipline is intentional. But when a future wave adds a new cross-cutting convention (e.g. a data-integrity rule that only applies inside `skills/planning-loop/` and `skills/run-loop/`), the ergonomic choice is now `.claude/rules/data-integrity.md` with `paths: ["skills/planning-loop/**", "skills/run-loop/**"]` rather than a fifth paragraph in CLAUDE.md.

There is nothing to change today. This is a flag so the maintainer sees the primitive before the next round of convention drift.

### Concrete change

**No file edit.** Add one row to `parking_lot.md`'s Open section, so the primitive lives in a place `/triage-parking` scans:

```diff
 ## Open

When a future convention is genuinely cross-cutting-but-scoped (only applies inside 2 of N directories), evaluate whether it belongs in `.claude/rules/` instead of growing CLAUDE.md or AGENTS.md. Do NOT promote existing content — CLAUDE.md is 35 lines and AGENTS.md's tool-neutral discipline is intentional. (source: 2026-09-21 anthropic-reviews §3)
```

### Expected payoff

If the primitive is never useful, the parking_lot row can be closed with `reject — never triggered` at the next `/triage-parking` sweep.

- The AGENTS.md tool-neutral principle is intentionally *not* Claude-Code-specific. Rules are Claude-Code-only, so any Rule the harness introduced would live under `.claude/rules/` and be invisible to Codex/other executors — same posture as `.claude/settings.json` today.

If either has grown past ~180 lines, upgrade the recommendation from `defer` to `apply` and identify which sections should move to `.claude/rules/`.

**Recommended verdict:** defer until per-directory conventions grow past current CLAUDE.md/AGENTS.md capacity — the primitive is real and worth knowing about, but adopting it before there's a scoped-content need would be premature.

## 5. Adopt test-impact-analysis pattern from Sept 14 CI-scaling post

**Source:** [Agentic coding is straining CI. Here's how we scaled test impact analysis at Anthropic — Claude Blog, 2026-09-14](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic)

### Why it's relevant

The post is a substantive methodology piece: Anthropic's CI job volume grew 25× in six months (Claude authored ~80% of merged code in that window), the incumbent test-impact-analysis (TIA) service was patched three times before being redesigned, and the redesigned service is a **deterministic listener + selector split** (a listener records every CI run's per-test results into a durable journal; a selector reads the journal and picks tests to run based on package relevance + past pass/fail history for the touched packages).

The lesson is real and generalizable. But for **this** repo it does not translate:

- The harness's `.harness-profile` explicitly sets `quality_bar.test_required: false` and `typecheck_blocking: false` (`grep -n "test_required\|typecheck_blocking\|lint_blocking" .harness-profile`). There is no CI matrix that TIA would select from.
- The only executable code paths (the loop engine under `skills/_shared/loop/` — TypeScript, `node:test`, no build step) are small enough that a full run is cheap. TIA amortizes across large test matrices; picking a subset when the full set costs <5 s is negative-value overhead.
- The wave engine and `/run-loop` already have their own per-run bookkeeping in `.harness-state/` (which superficially resembles TIA's journal) but that state tracks *wave orchestration outcomes*, not per-test results.

The maintainer *should* know about the deterministic-listener-plus-selector pattern for when consumer projects grow past the "small test suite" phase — but the harness itself has nowhere to land it.

### Concrete change

**None.** Skip.

If the reader wants to import a lesson anyway, the *transferable* insight is architectural: **"batch-verifier state should be a durable journal that a deterministic selector reads, not an ambient cache"**. The harness has one place where a version of this pattern is already latent — `.harness-state/orchestrator.jsonl` — but the code that reads it isn't a selector against past results, it's a status renderer. No action recommended.
