## 3. Audit MCP permission entries after CC 2.1.300 allow-rule tightening

**Source:** [Claude Code 2.1.300 changelog — code.claude.com, 2026-10-14](https://code.claude.com/docs/en/changelog) — "MCP allow rules now match only the named server (no partial-prefix match)."

### Why it's relevant
Before 2.1.300, a permission entry like `mcp__github` would match `mcp__github__*` tools by prefix. After 2.1.300, that same entry matches only a tool literally named `mcp__github` (zero tools in practice). Any harness-installed MCP permission that relied on prefix matching now silently permits nothing where it previously permitted a whole server.

Today, `.claude/settings.json` ships with empty `hooks` and no `permissions` block (verified by `cat .claude/settings.json`). The harness's `setup-harness` SKILL does not auto-install MCP server permissions. So there is **no immediate harness breakage** — but any `mcp__*` entry an operator added later (or any permission the harness grows in future) needs to use the explicit two-underscore server-name match (`mcp__github__*`) rather than a bare prefix.

This § is therefore a **tracker note + future-looking guard**, not a code change.

### Concrete change
Append a one-paragraph "MCP permission gotcha (CC 2.1.300+)" note to `/home/user/claude-harness/skills/setup-harness/SKILL.md`, immediately after the Auto Mode paragraph (around line 147):

```diff
 3. Toggle Auto Mode interactively via Shift+Tab. (As of writing, `permissions.defaultMode: "auto"` is parsed but doesn't reliably auto-engage on session start — manual toggle is the safer default. Re-check before relying on a config-only bootstrap.)

+**MCP permission entries (CC 2.1.300+).** As of Claude Code 2.1.300 (2026-10-14), permission entries targeting MCP tools match only the *exact* named server — partial prefix matches no longer work. If you add an MCP permission, use the two-underscore server-name form (`mcp__github__*`) rather than a bare prefix (`mcp__github`). The bare prefix will silently match nothing. The harness itself ships no MCP permissions today, so no retrofit is needed — this is a forward-looking note for operators who grow their own permission entries.
```

### Expected payoff
Future operators who grow MCP permissions out of this harness get a one-paragraph warning before they discover the behavior change at tool-call time. Zero behavior change today.

**Verify before applying:**
1. `grep -rn "mcp__" /home/user/claude-harness/.claude/settings.json /home/user/claude-harness/skills/setup-harness/SKILL.md` — if any `mcp__<name>` permission *without* `__*` suffix shows up before this is applied, that permission is already broken under 2.1.300+ and the fix becomes `apply now`, not `defer`.
2. Confirm the behavior change is still described this way in the current CC changelog (the specific wording "no partial-prefix match" may evolve) — read [code.claude.com/docs/en/changelog](https://code.claude.com/docs/en/changelog) 2.1.300 entry before quoting it.

**Recommended verdict:** defer until next MCP permission edit — no breakage today; the fix is a one-paragraph forward-looking note the maintainer can batch with the next MCP-adjacent change.

## 5. Add `claude --worktree` detached-HEAD safety note to `/run-wave` troubleshooting

**Source:** [Claude Code 2.1.304 changelog — code.claude.com, 2026-10-19](https://code.claude.com/docs/en/changelog) — "`claude --worktree` no longer deletes a worktree + branch silently on detached HEAD."

If you must run `/run-wave` on CC < 2.1.304, check `git status` first and ensure you are on a named branch, not detached HEAD, before dispatch.
