## 1. Note `/goal` alongside `micro`'s done-boxed budget in `skills/micro/SKILL.md`

**Source:** [Keep Claude working toward a goal — code.claude.com/docs/en/goal](https://code.claude.com/docs/en/goal) (Claude Code 2.1.139, shipped 2026-05-11 per [release notes](https://code.claude.com/docs/en/changelog)). Pairs with the **Outcomes** announcement for Claude Managed Agents at Code w/ Claude SF 2026 on May 6 — same conceptual pattern, with `/goal` being the user-facing version inside Claude Code itself.

### Why it's relevant

The harness's `micro` skill ([`skills/micro/SKILL.md:38–53`](../skills/micro/SKILL.md)) already supports a **done-boxed** budget: the user states a verifiable end-state ("all tests in `profile-extraction.test.ts` pass", "endpoint returns 200 with a valid response shape"), the skill writes it to `.harness-state/current_micro.md` line `**Budget:** [time-boxed Nm | done-boxed: <condition>]`, and the block stays open until the human/agent says "block done." There is **no automated evaluator** in the harness's done-boxed path today — the same agent that's doing the work decides when it's met, with the documented commit-skill ritual as the hand-off back to the human.

Anthropic just shipped the missing piece as a built-in Claude Code primitive on May 11:

- **`/goal "<condition>"`** sets a session-scoped completion condition that a **separate small fast model (defaults to Haiku)** re-evaluates after every turn. The evaluator returns yes/no + a one-line reason; "no" feeds back into the next turn as guidance. Works in interactive mode, `-p` non-interactive, and Remote Control. *([docs/en/goal](https://code.claude.com/docs/en/goal))*

This is **the same conceptual pattern as the harness's done-boxed budget, with the separate-model evaluator filled in**. The harness's separate-model-evaluator pattern already exists in spirit elsewhere in the repo (the planning-loop runs Codex as an adversarial reviewer on round-N specs; the orchestrator routes verification work to Haiku per `effort_default`; the `code-reviewer` agent runs against `criteria/` rubrics before commit). What's new here is that Claude Code itself now provides the every-turn evaluator primitive — no harness code required.

**They are complementary, not redundant** — the harness's done-boxed budget *is* the right shape (one goal, one block, one commit), and `/goal` is the right way to automate the "am I done?" check **inside** a done-boxed block. The harness's discipline (write the goal to disk, commit-at-end, side-quests-go-to-park) doesn't compete with `/goal` — `/goal` is session-scoped and doesn't touch `.harness-state/current_micro.md`.

### Concrete change

One paragraph appended to `skills/micro/SKILL.md` Step 3 (the budget-style block). Insert immediately after the "What's the specific done condition?" example block (currently around line 53), before Step 4:

```diff
 > Must be verifiable. Examples: "all tests in profile-extraction.test.ts pass", "endpoint returns 200 with a valid response shape".

+#### Optional: automate the done-check with `/goal`
+If you picked **done-boxed**, you can layer Claude Code's built-in [`/goal`](https://code.claude.com/docs/en/goal) primitive (shipped 2026-05-11 in v2.1.139) on top — type the same condition as a `/goal` after this step, and Claude Code will run a separate-model evaluator (defaults to Haiku) after every turn to decide whether the condition is met. The micro-session still owns the surrounding ritual (goal written to `current_micro.md`, commit at end, side-quests to `park`); `/goal` just automates the "am I done?" question inside it. Skip this for time-boxed blocks — there's no condition for `/goal` to evaluate.
+
 ## Step 4: Write micro state
```

## 2. Bookkeeping — position Agent View alongside the harness's orchestrator fan-out

**Source:** [Agent view in Claude Code — claude.com/blog, 2026-05-11](https://claude.com/blog/agent-view-in-claude-code) ([docs](https://code.claude.com/docs/en/agent-view)). Shipped as Research Preview in Claude Code 2.1.139. A CLI dashboard for every Claude Code session (running, blocked-on-you, done); supports `claude --bg "<task>"` for fresh background sessions, `/bg` from inside a session to move it to the background, and an arrow-key/peek-panel interaction to reply across sessions without leaving the dashboard.

### Why it's relevant

The harness already has a multi-agent fan-out story: `.claude/agents/orchestrator.md` reads spec tasks and dispatches each to opus/sonnet/haiku subagents based on runtime complexity, and tasks with no dependency / no file overlap run in parallel using **worktrees** (`README.md:568`). That fan-out is **single-process, automated, batched** — one Claude Code session driving the orchestrator, which in turn dispatches subagents.

Anthropic's **Agent View** is a different layer of multi-agent work: **interactive, multi-process, multi-session**. The user runs `claude --bg "<task>"` to spawn a fresh background session and then juggles several sessions via the dashboard (peek panel, reply across sessions, see "blocked-on-you" surfaces). This is **the human-facing equivalent** of what the orchestrator does automatically — fan-out across parallel work, but with the human in the driver's seat for each session.

Today there is **zero mention** of Agent View or `claude --bg` in the harness (`grep -rn "agent.view\|Agent View\|claude.--bg\|claude_agents" /home/user/claude-harness --include="*.md"` returns nothing). That's fine for now — the harness's orchestrator path is the one the maintainer actually uses — but **a future reader who learns about Agent View first** could mistake the orchestrator for Agent View (or vice versa) and try to wire them together. This § is the bookkeeping placeholder.

### Why this is `defer`, not `apply`

1. **The harness doesn't currently use `claude --bg`.** All harness work happens inside a foreground session (or a worktree under the orchestrator's control). Agent View has no orchestrator integration, and there's no obvious harness affordance to add.
2. **Agent View is Research Preview as of 2026-05-11.** Two days old. Setting orientation copy now risks describing pre-GA semantics that will shift.
3. **The two patterns address different problems.** Orchestrator = "I want to run wave N tasks in parallel under one driver." Agent View = "I want to manage several long-running interactive sessions across my workday." Conflating them in the README would muddy both.
4. **Solo maintainership.** The harness is solo (`team.size: solo` in `.harness-profile`). Agent View's value-prop is dispatching ideas across simultaneous sessions and triaging "which agent is blocked on me" — useful at scale, less so for a single-user single-thread workflow. Park until usage forces the question.

### Concrete change (deferred)

None this run. When/if the maintainer wants to take this on, the smallest version is **one paragraph in `README.md`** in the "Architecture" section (around line 568 where parallel-via-worktrees is documented) that says something like:

> The harness's orchestrator fans out **automated** parallel subagents inside one driver session (worktrees per task). Anthropic's **Agent View** (Claude Code 2.1.139+) is the **interactive** parallel-session equivalent: `claude --bg "<task>"` spawns a fresh background session and the agent-view dashboard (`claude agents` from the terminal, or left-arrow from any session) lets you juggle several at once. They compose: a user could run two `claude --bg` sessions in different worktrees, each driving its own orchestrator. The harness does not currently script this; if you need it, `claude --bg` is the Claude-Code-native primitive and no harness change is required to use it.

The bigger version (a new `/multi-session` skill, an updated `setup-harness` advisory about `claude --bg`, etc.) is **speculative** — defer until the maintainer actually wants multi-session interactive work.

Future reader who learns Agent View first doesn't pattern-match it onto the orchestrator and conclude "the harness already does this, so I can ignore Agent View" (or the inverse: "Agent View covers this, so I can ignore the orchestrator"). One paragraph closes that gap.
