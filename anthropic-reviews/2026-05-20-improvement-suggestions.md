## 2. Promote hierarchical CLAUDE.md guidance to `setup-harness` Step 4

**Source:** [How Claude Code works in large codebases — claude.com/blog, 2026-05-14](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start). The post's most concrete operational recommendation for monorepo-scale codebases: **layer CLAUDE.md files** — root file describes only the highest-level structure with pointers to subdirectory CLAUDE.md files for local conventions, "loading on demand as Claude moves through the tree."

### Why it's relevant

`skills/setup-harness/SKILL.md` Step 4 (lines 151–192) generates **exactly one** `CLAUDE.md` at the project root. The template (lines 174–186) is explicitly capped at ~50 lines and structured for a single-tier project. This is correct for small/medium projects (which is what the maintainer's known consumer projects are — `harness-status` registry is small, and tooling repos like `claude-harness` itself don't have hundreds of top-level folders), but Anthropic's May-14 post calls out the specific failure mode at monorepo scale: a single CLAUDE.md grows past ~50 lines because every subdirectory wants its own conventions captured, and either becomes too long to be useful or omits subdirectory-specific context. The recommended pattern is:

- **Root `CLAUDE.md`** — high-level structure, entry directories, generated/third-party code locations, *pointers* to subdirectory CLAUDE.md files.
- **Subdirectory `CLAUDE.md`** files — task-specific instructions, testing commands for that subtree, which files to modify, local conventions. Loaded additively as Claude navigates into the subtree.

The `setup-harness` skill could document this option (as an "if your project has N top-level folders, add subdirectory CLAUDE.md files") without changing the default behavior for small projects.

### Why this is `defer`, not `apply`

1. **None of the harness's known consumer projects are at the trigger size.** The CLAUDE.md hierarchical pattern is concretely advantageous starting at "hundreds of top-level folders" / multi-million-line codebases (per the post's Stripe example). The maintainer's known projects (`claude-harness`, the consumer projects registered in `~/.config/harness/projects.yml`) don't approach that scale.
2. **The `setup-harness` Step 4 template's 50-line cap is doing real work today.** Adding "or split into hierarchical files" risks turning the template into a "pick the right strategy" decision that the maintainer hasn't needed yet — a premature abstraction per the "Don't add features beyond what the task requires" guidance in `CLAUDE.md`.
3. **The pattern is documented first-party at code.claude.com/docs/en/best-practices** (already cited in README references). A user who needs hierarchical CLAUDE.md will find it there before they find it in `setup-harness`. The harness's role is to ship a sane default, not to mirror every Claude Code feature.
4. **Speculative for solo tooling.** Per `apply / defer / reject / spec` rubric: "speculative for solo tooling" is a defer indicator, not a reject indicator — flag it for the maintainer rather than killing it.

### Concrete change (deferred)

None this run. When/if the maintainer wants to take this on — i.e., a consumer project hits the size threshold where a single CLAUDE.md is bloating past the 50-line cap:

1. Append a short subsection to `skills/setup-harness/SKILL.md` Step 4 (after line 192) titled **"Hierarchical CLAUDE.md (for monorepo-scale projects)"** that:
   - Triggers on `≥ N` top-level folders (e.g. `N=20`) detected during Step 1, or on explicit operator request via a `--hierarchical` flag.
   - Generates a root `CLAUDE.md` containing only the "lay of the land" + pointers to subdirectory files.
   - Walks the top-level subdirectories and scaffolds a one-line stub `CLAUDE.md` in each, with a placeholder for the operator to fill in.
   - Cites [claude.com/blog/how-claude-code-works-in-large-codebases](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start) inline as the source for the pattern.

## 3. Bookkeeping: Agent SDK Credits (effective June 15 2026) rewrite the cost calculus for the deferred 2026-05-10 §2 (Cloud Routines migration)

**Source:** [Use the Claude Agent SDK with your Claude plan — support.claude.com Help Center article, announced 2026-05-13 via @ClaudeDevs](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan). Anthropic announced that starting **2026-06-15**, programmatic Claude usage (Agent SDK, `claude -p`, GitHub Actions, third-party agent frameworks) draws from a **dedicated dollar-denominated credit pool** sized to the user's existing plan tier — Pro: $20/month, Max 5x: $100/month, Max 20x: $200/month. Interactive Claude Code in the terminal, web/desktop/mobile chat, and Claude Cowork continue to draw from the standard subscription pool. Credits do not roll over; depletion does not fall back to subscription limits.

### Why it's relevant

`anthropic-reviews/2026-05-10-improvement-suggestions.md` §2 (the "Migrate the Anthropic-reviews routine itself to a Claude Code Cloud Routine" suggestion) is `Status: DEFERRED until pricing/scheduling pain warrants` — and one of its explicit defer reasons (point 2 in the "Why this is defer" block) is **cost**: *"Cloud Routines bill against the Pro/Max plan. Even at the cheapest tier, a weekly routine that does a multi-page web survey is non-zero recurring cost ($5–10/run by analogy with `/ultrareview`'s pricing band)."* That cost-calculus assumption changes materially on June 15.

**What changes for the deferred §2:**

- Cloud Routines almost certainly run via the Agent SDK pathway (they're scheduled programmatic invocations of Claude). So they will draw from the new **dedicated credit pool**, not from the subscription's chat limits.
- For a Pro-tier maintainer, the credit pool is $20/month. A weekly Anthropic-reviews routine that spends, e.g., $1–$3 per run (a web-survey + small writeup, well below `/ultrareview`'s 10–20-minute deep-investigation scale) fits comfortably under $20/month while leaving the chat-subscription pool untouched. This actually *strengthens* the case for the migration: the routine becomes cost-isolated.
- For a Max-tier maintainer, $100 or $200/month is plenty for a weekly routine.
- **But** — the credits expire at month-end with no rollover. So a routine that runs once a month wastes the credit; the maintainer would want to use the same credit pool for other programmatic work (e.g., the deferred Managed Agents items in 2026-04-19 §2) to amortize.

This is **bookkeeping**, not a new ask. The original §2 deferral remains correct (works manually today; setup non-trivial; Routines are new). The cost-calculus reason gets weaker, but the other defer reasons (manual trigger works; setup complexity; ergonomics not settled) still bind.
