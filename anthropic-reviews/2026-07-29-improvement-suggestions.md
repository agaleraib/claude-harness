## 1. Cite "Steering Claude Code" as the canonical reference for the harness's steering-mechanism choices

**Source:** [Steering Claude Code: when to use CLAUDE.md, skills, hooks, and subagents — claude.com/blog, 2026-06-18](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more) — Anthropic staff (Michael Segner) write-up naming seven ways to steer Claude Code (CLAUDE.md, rules, skills, subagents, hooks, output-styles, appended-system-prompt) and giving load-timing / compaction / instruction-authority tradeoffs for each. Quick-decision framework: *"Facts go to CLAUDE.md, scoped constraints go to rules, procedures go to skills, human-triggered procedures go to slash commands, noisy investigations go to subagents, session voice goes to output styles, one-off framing goes to appended system prompts, live capability goes to MCP, always-do behaviour goes to hooks, and never-do boundaries go to permissions."*

### Why it's relevant

The harness is *built around* this exact decision matrix: `AGENTS.md` §"What to do" + §"Loop protocol" pick between hooks and skills for automated vs conversational behaviors; `CLAUDE.md` (this repo's) documents the tool-neutral vs Claude-specific split; `skills/` uses SKILL.md progressive-disclosure; `.claude/agents/*` uses subagents for isolation; and the `.claude/settings.json` hook-installation instructions in `skills/run-loop/SKILL.md` and `~/.claude/settings.json` distinguish PreToolUse denylist hooks from inline instructions.

Today the harness cites specific pieces of Anthropic's engineering canon — the [April 23 postmortem](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues) (`README.md:30`), [prompt-caching lessons](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything) (`AGENTS.md:54`), [harness-design research](https://www.anthropic.com/engineering/harness-design-long-running-apps) (`README.md:3`), [best-practices docs](https://code.claude.com/docs/en/best-practices) (`README.md:3, 852`) — but does **not** cite the one post that specifically explains when each of the harness's own mechanisms (CLAUDE.md / skills / subagents / hooks) is the right tool. `grep -rn "steering-claude-code\|Steering Claude Code" /home/user/claude-harness` returns nothing today.

## 4. Note the `code-migration-kit-with-claude-code` playbook alongside `spec-planner` + `planning-loop`

**Source:** [How Anthropic runs large-scale code migrations with Claude Code — claude.com/blog, 2026-07-16](https://claude.com/blog/ai-code-migration). Companion open-source repo: [`anthropics/code-migration-kit-with-claude-code`](https://github.com/anthropics/code-migration-kit-with-claude-code) (prompts, templates, scripts). The published methodology names an eight-phase-gate structure with three rounds of adversarial review, a final parity-check that diffs command output against the original, and a "you don't fix the code — you fix the process that produced the code" rule (individual failures get fixer agents; recurring failures indict a rulebook rule that gets amended). Case studies: Bun's Zig → Rust port (~1M lines, <2 weeks), Mike Krieger's Python → 165k-line TypeScript port over a weekend.

### Why it's relevant

The methodology is architecturally close to this harness's `spec-planner` + `planning-loop` + `run-loop` stack — both are "declarative rules + iterative loop + adversarial verify + parity-gated merge" — but scoped for multi-language ports rather than incremental feature work. Concrete parallels:

- **Rulebook (kit)** ≈ `docs/specs/*.md` (harness) — durable declarative intent.
- **Gap inventory (kit, one row per site, grep-friendly)** ≈ `docs/plan.md` `## Now`/`## Next` (harness) — the flat work-list agents grep before executing.
- **Phase gates (kit, 8 stages)** ≈ the harness's per-item gate sequence (`AGENTS.md:97–105`) — exit gate + code review + atomic merge + post-merge effects.
- **Adversarial review (kit, 3 rounds)** ≈ `.claude/agents/code-reviewer.md` + the `planning-loop` cross-model spot-check.
- **Parity harness (kit, diff every command output)** ≈ the loop's fast-forward-only "gated tree == merged tree" invariant (`AGENTS.md:105`).

The harness has **no** migration-specific skill — `skills/migration-check/SKILL.md` is a **database-schema** migration reviewer, not a language-port workflow. There is no `skills/code-migration/` or equivalent.

### Why this is `defer`, not `apply`

1. **No active workload.** The maintainer is not currently running a language-port project through this harness. The consumer projects that install this harness (wordwideAI etc., per `sandcastle_mattpocock_architecture.md`) are not doing language migrations either. Speculative for solo tooling.

2. **The kit is a full workflow, not a drop-in.** Adopting it means writing a `skills/code-migration/` skill (or subagent) that operates over the eight phase gates, plus a `RULEBOOK.md` template, plus a parity-harness script — not a one-file edit. Per the `anthropic-reviews/README.md` §"How approved suggestions actually get built" rubric, this is `substantive` (spec-planner → wave item), not `micro`.
