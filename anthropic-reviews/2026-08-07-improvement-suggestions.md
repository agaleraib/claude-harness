## 2. "Unhobbling" audit — apply Claude 5 context-engineering shifts to harness prose

**Source:** [The new rules of context engineering for Claude 5 generation models — claude.com/blog, 2026-07-24](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) (by Thariq Shihipar, member of technical staff at Anthropic).

The post reports that Anthropic removed **over 80% of Claude Code's system prompt for Opus 5 / Fable 5** with no measurable loss on internal coding evals. Anthropic frames the fix as "**unhobbling**" — deleting constraints written to prevent older-model failure modes that Claude 5 no longer produces. The post identifies **six concrete shifts** (verify wording at apply time — different downstream summaries phrase them slightly differently):

1. **Rules → judgment.** Stop writing "never do X" unless there's a documented failure mode Claude can't reason out of on its own.
2. **Examples → interface design.** Type signatures and enum-valued parameters tell Claude more than examples, without boxing it in.
3. **Everything upfront → progressive disclosure via skills.** Load context on trigger, not at session start.
4. **Repeated instructions → consolidate into tool descriptions.** The same rule stated in system prompt + skill + user request creates conflicts.
5. **Manual CLAUDE.md → auto-memory.** Facts Claude learns while working belong in auto-memory (`~/.claude/projects/<encoded-cwd>/memory/MEMORY.md`), not in CLAUDE.md as a diary.
6. **Simple markdown specs → rich references (code, test suites, rubrics).** A rubric or a failing test tells Claude more than a paragraph describing what "good" looks like.

### Why it's relevant

The harness's own README ("Why Not Superpowers / Heavy Skill Systems?", `README.md:24-27`) already argues that lean context beats heavy instruction. Anthropic's July 24 post is the strongest first-party endorsement of that stance yet — but the harness itself has not been audited against the six shifts. Specifically:

- **AGENTS.md (131 lines) + CLAUDE.md (35 lines):** at first read, mostly protocol contract (not "rules Claude can reason out of"), but the "What to avoid" list in `AGENTS.md:47-56` reads exactly like the "never do X" pattern Anthropic warns against for Claude 5.
- **18 skill files:** most already have short frontmatter descriptions (per prior 2026-04-19 §3 audit). But skill *bodies* still carry old-model guardrails — e.g. the `commit` skill's Step 3–4 review flow is essentially prose rules restating what `code-reviewer` already does.
- **6 agent files** (`.claude/agents/*.md`): unaudited against the "rules → judgment" shift.
- **Auto-memory footnote in CLAUDE.md:11** already flags that "promotion to `~/.claude/memory/feedback/` is manual." Anthropic's July guidance says the *manual* half is the artifact — Claude 5 should just be trusted to auto-save. But the harness has a deliberate "promotion is manual by design so per-cwd provenance is preserved" note (`CLAUDE.md:11`, `docs/waves/wave11-memory-system-redesign-shared-root.md`), so this is a decision-to-revisit, not a pure defect.

### Why this is `spec`, not `apply`

1. **Blast radius.** 18 skills + 6 agents + 3 top-level protocol files = ~25+ files at minimum; the "unhobbling" test is subjective per-paragraph. `/spec-planner` is the right ladder.
2. **The context-engineering shift explicitly warns against half-measures.** Deleting rules without also consolidating repeated instructions creates worse conflicts than leaving them alone (per Anthropic's own transcript findings: "several conflicting messages in a single request like 'leave documentation as appropriate,' or 'DO NOT add comments' as our system prompt, skills, and user requests clash with each other"). The audit needs to be whole-repo, not one-file-at-a-time.
3. **It presumes §1 (Claude 5 pin bump).** On Opus 4.7 the harness prose is calibrated correctly; on Claude 5 it's over-constrained. So this only pays back after the model bump. Same-spec bundling gives the operator one decision point instead of two.
4. **Some shifts don't apply, and the spec is where "which" gets decided.** E.g. shift 5 (manual CLAUDE.md → auto-memory) is *incompatible* with the deliberate per-cwd-provenance design of `docs/waves/wave11-memory-system-redesign-shared-root.md`. That contradiction needs surfacing, not silent adoption.

### Concrete change (deferred to spec)

The spec should:

1. Read the primary source verbatim (Anthropic's July 24 post) — vendored copy under `skills/skill-creator/references/anthropic-context-engineering-claude5.md` for future reference (pattern: the existing `anthropic-skill-authoring.md` vendored snapshot).
2. For each of the six shifts, decide **adopt / partial / reject** for this harness, with one-line reasoning. Explicit reject for shift 5 (auto-memory) if the operator wants per-cwd provenance kept.
3. Produce a per-file audit table: file × shift × verdict (change / keep / n/a).
4. Split into `apply`-sized micro-batches so the actual edits ship as `/micro` sessions from a checkable list, not as one big rewrite.
5. Preserve the "add-less-not-more" thesis in `README.md:24-27` (that's what §4 reinforces separately).

### Expected payoff (when applied)

Harness prose stops fighting Claude 5's own defaults. Any measurable eval loss from the audit is a signal that a shift was mis-classified — same feedback loop Anthropic ran internally.

## 3. Add "Gotchas" section convention to skill-authoring reference

**Source:** [Lessons from building Claude Code: How we use skills — claude.com/blog, 2026-06-03](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills) (by Thariq Shihipar). Key quote from the post (as reported by multiple downstream summaries, verify verbatim at apply time): *"The highest-signal content in any skill is the Gotchas section, which should be built up from common failure points that Claude runs into when using the skill, and ideally you will update your skill over time to capture these gotchas."*

### Why it's relevant

The harness ships its own skill-authoring reference at `skills/skill-creator/references/anthropic-skill-authoring.md` (a vendored snapshot of Anthropic's platform docs), plus the `skill-creator` skill that agents invoke to draft or revise skills. Neither one mentions "Gotchas" as a section convention:

- `grep -c 'Gotchas\|gotchas' skills/skill-creator/references/anthropic-skill-authoring.md` → 0 hits (verified 2026-08-07)
- `grep -rl 'Gotchas\|gotchas' skills/` → only `skills/setup-harness/SKILL.md` (verified 2026-08-07)

That means new skills drafted with `/skill-creator` won't get a Gotchas nudge, and 17 of 18 existing skills have no gotchas section to inherit from.

### Concrete change

Two small edits, each independently shippable:

**Edit A** — append a "Gotchas" subsection to `skills/skill-creator/references/anthropic-skill-authoring.md`, in the same style as the existing "Scripts (skills with executable code)" section:

```diff
 ## Skills with executable code
 …
+
+## Gotchas section (the highest-signal skill content)
+
+Per Anthropic's June 2026 post [_Lessons from building Claude Code: How we use skills_](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills), the highest-signal content in any skill is the **Gotchas** section — the accumulated list of failure modes Claude has run into while using this skill in production. Not theoretical warnings; concrete post-mortem-worthy footguns from real invocations.
+
+**Convention.** Add a top-level `## Gotchas` section near the end of SKILL.md (before any appendix). One bullet per gotcha, `[YYYY-MM-DD]`-prefixed so the section grows chronologically. Cite the invocation or the wave receipt that surfaced each one.
+
+**Update discipline.** Every time a skill fails or surprises in a way the operator has to explain to a fresh session, the fix isn't "explain harder" — it's a new Gotchas bullet. This is where the skill's institutional memory lives.
+
+**Example** (from Anthropic's own internal skills): a script-runner skill grew a Gotchas line for each shell that mishandled quoting, each MCP tool that lied about its parameter schema, each Windows path convention that broke on macOS.
```

**Edit B** — a one-line nudge in `skills/skill-creator/SKILL.md` (append to the "final step" of the drafting flow, or wherever the skill currently prompts the author):

```diff
   - Repeat until you're satisfied
   - Expand the test set and try again at larger scale
+  - Seed a `## Gotchas` section with the first failure the evals surface — per Anthropic's June 3 skills post, this is the highest-signal content the skill will ever carry. See `references/anthropic-skill-authoring.md` § Gotchas.
```

### Expected payoff

Every new skill drafted with `/skill-creator` starts with a Gotchas placeholder. Over time, the harness's own skills accumulate a real Gotchas index that survives context resets — the same institutional memory Anthropic's internal skills carry.

### Why it's relevant (and why it's not urgent)

| Anthropic pattern | Harness equivalent | Migration signal |
|---|---|---|

| **Loop engineering: 4-loop taxonomy** — Turn-based (agentic), Goal-based (`/goal`), Time-based (`/loop`, `/schedule`), Proactive/Event-driven (`/schedule` on GitHub webhooks). | `/run-loop` — a Time+Goal hybrid (drain ready items on an interval until source empties or termination cap fires).
